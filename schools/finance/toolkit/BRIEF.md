# Writing one course for the Finance Learning Foundation

The Finance Learning Foundation is a Khan Academy–style self-study site for a 63-course pathway from kindergarten to a career in investment analysis: elementary school (K–5), middle school, high school, a complete college finance degree, and CFA Program exam review with the practice of an investment analyst. Each course follows a 14-week syllabus. You write the lessons for ONE course: weeks 1–12 (one lesson per weekly topic) plus a project/review/final-exam file for weeks 13–14. Your course JSON says who the learner is (`audience`) and the course `level`; write for that learner. Address the learner as "you". Assume the course prerequisites, but briefly remind key prerequisite ideas when you use them. Use the standard names of concepts, models, ratios, statements and rules (net present value, the CAPM, the DuPont decomposition, the Black-Scholes-Merton model, Modigliani-Miller, ASC 842, IFRS 16): learners need them to use the readings, pass exams and talk with colleagues. Do not write about real people themselves (no biographies or anecdotes; eponyms such as "the Sharpe ratio" or "the Gordon growth model" are fine), and never mention the curriculum's author.

The site runs Python in the learner's browser, so learners can write and run real code inside lessons and the site grades it by running your tests.

## Files you write (only these)

- `/home/claude/finance/content/<CODE>/L01.txt` … `L12.txt` — week N lesson = the syllabus topic for week N.
- `/home/claude/finance/content/<CODE>/project.txt` — the week 13–14 project brief, review guide and cumulative exam items.

Your course data (audience, level, topics, block deliverables, project, primary reading) is in `/home/claude/finance/toolkit/courses/<CODE>.json`. Before writing anything, read it and `/home/claude/finance/toolkit/example_finance_lesson.txt`: a complete, valid lesson that shows the exact format and the conventions for money, percents, tolerances and code items. If your course has Python exercises (C5, C12, C17 and P4 always; others where the brief below suggests code), also read `/home/claude/finance/toolkit/example_code_lesson.txt`. The example lessons are format samples: never copy their examples or items (C7, whose week 4 covers the same topic as the finance example, must write entirely new material).

## File format

Sections start with `@name` at the start of a line. Fields are `key: value`; a line that does not begin with a known key continues the previous field, so multi-line values are fine. Text inside ``` fences is kept exactly as written: inside a fence, lines that look like `key: value` or `@name` are just code, so decorators and dictionaries are safe there. Write TeX directly (`$\frac{1}{2}$`); inline math is `$...$`, display math is `$$...$$`.

**Dollar signs.** A `$` outside code starts math. Write every amount of money in prose with a backslash: `\$4.50`, `\$1,250`, `\$2.5 million`, "between \$5 and \$10". Inside math, a dollar sign is also `\$` (`$\$5{,}769.47$`; `{,}` writes a comma without extra space). Put shell prompts, variables such as `$PATH` and anything else with `$` inside backticks or a fence, where `$` is safe. The validator rejects math that looks like a dollar amount ("$5 and $"). Percent signs need no escape in prose; inside math write `\%`.

Code in prose: inline code in single backticks (`npv(rate, flows)`); blocks in fences with a language (```python, ```text). Keep code lines under 80 characters where you can (the hard limit is 100), indent with 4 spaces, never tabs. Journal entries, ledgers and small statements go in markdown tables or ```text blocks.

**The site shows no images.** Describe graphs in words, with equations and small tables ("the demand curve $Q = 100 - 2P$ slopes down; at $P = 20$, $Q = 60$"). Financial statements, schedules, payoff tables and data sets are markdown tables.

Lesson file sections, in order:
- `@lesson` — `title:` (the week's topic as a clear title), `summary:` (one sentence: what the learner will be able to do), `objective:` ×2–4, `reading:` (see below).
- `@article` — markdown: paragraphs, `###` subheadings, **bold**, lists, tables, code blocks, `$math$`. Length by level (see below).
- `@example` ×1–2 — `title:`, `problem:`, `step:` ×2–6 (each step is revealed one at a time, Khan-style; a step may contain a table or a code block), optional `answer:`.
- `@mistakes` — 2–4 lines starting with `- `.
- `@practice <type>` ×5 — ordered easy → hard, each with its own numbers: never reuse the data of a worked example or of the article's own calculations (also in code items' example calls and tests), so learners must work the method rather than copy an answer they have seen.
- `@quiz <type>` ×2 — new problems used only in unit quizzes, the midterm and the final. Never near-copies of practice items, and never the data of a worked example.

## Item types

Item fields: `prompt:`, `answer:`, `check:`, `hint:` ×1–3 (progressive; the last hint gets the learner to the method but not the final answer), `solution:` (complete and short), plus the fields each type needs.

| type | learner does | you give | verified by |
|---|---|---|---|
| `num` | one number | `answer:`, usually `tol:`, and `lead:` or `unit:` | `check:` expression |
| `mc` | one choice | mark the correct `choice*:` | — |
| `ms` | select all that apply | mark every correct `choice*:` | — |
| `self` | writes, explains or builds, then compares with a model | `solution:` (model answer) and `rubric:` ×2–4 | — |
| `code` | writes Python in an editor, runs it, presses Check | `starter:`, `tests:` and/or `stdout:`, `model:` | the validator runs `model` against your tests in CPython **and** in the browser's Python, and checks that `starter` fails them |
| `text` | types an exact short answer, usually what a program prints | `answer:`, optional `accept:` ×n | `check:` that computes the same text, usually `run("...program...")` |
| `list` | several values, any order | `answer:` (`-2, 3` or `none`) | `check:` |
| `tuple` | ordered values | `answer:` (`(2, -1)`) | `check:` |
| `expr` | an expression in `vars` | `answer:`, `vars:` | `check:` lambda |

`mc`/`ms` use `choice:` lines (3–5 total) with the correct ones written `choice*:`. **The site shuffles the choices**, so never use "all/none of the above" or "both A and B", and in hints and solutions name a choice by its content, never by its position ("the second choice", "option B"). Distractors come from real misconceptions (using the annual rate as the periodic rate, forgetting the tax shield, confusing Macaulay and modified duration, debiting the wrong account, mixing up nominal and real). Use `self` for explanations, memos, written analyses, journal entries with reasoning, investment policy statements, ethics case resolutions, models the learner builds on their own computer, and anything a person must judge; give a complete model `solution:` and 2–4 specific `rubric:` lines.

### Numbers, money and percents (`num` items)

- `answer:` is a plain number: `2436.81`, `-21.04`, `0.0725`, `7.25`, `3/4`. No `\$`, commas, `%` or words in the answer field. Learners may type `$1,234.56`, `1,234.56` or `7.25%`: the site removes the dollar sign and thousands separators, and a `%` typed into an item whose unit is `%` is ignored.
- **Money**: `lead: \$` shows a dollar sign before the answer box. Say how to round ("Round to the nearest cent", "to the nearest dollar", "in millions of dollars to one decimal place").
- **Rates, returns and other percentages**: answer as a percent with `unit: %` ("Give the yield as a percent to two decimal places" → `answer: 6.83`, `unit: %`). Use a decimal answer (`0.0683`) only when the prompt asks for a decimal, and then do not set `unit: %`.
- **Other units**: `unit: years`, `unit: shares`, `unit: times` (for ratios such as interest coverage), `unit: ¢` for cents in elementary courses.
- **Tolerance**: whenever the prompt asks for rounding, set `tol:` to one unit of the last place asked for, so that a learner who rounds intermediate steps a little differently is still right: cents → `tol: 0.01`; whole dollars → `tol: 1`; a percent to two places → `tol: 0.01`; a ratio to two places → `tol: 0.01`. For long multi-step valuations where table- or calculator-rounding moves the answer more, a relative tolerance is fine (`tol: 0.1%`), but never for answers that can be near zero (an NPV, a difference, a variance): use an absolute tolerance there. A `num` item without `tol:` must have an exact answer (an integer, or a terminating decimal such as `1.35` that needs no rounding).
- Other optional fields: `domain:`, `form:` and `const:` exist for algebra items; `vars:` for `expr`. Use `expr` only in mathematics-heavy lessons (C6), for a formula in symbols (`answer: P*(1+r)^n`, `vars: P, r, n`).

`check:` is ONE Python expression that computes the expected result independently from the problem statement — never retype your answer. Redo the arithmetic (`2000 * (1 + 0.05/2) ** 8`, `sum(cf / 1.1 ** t for t, cf in enumerate([-1000, 300, 400, 500]))`), use the program itself (`float(run(...))`), or use these helpers:
- `npv(rate, flows)` — the first cash flow is at time 0 (unlike a spreadsheet's NPV); `irr(flows)` — the one IRR between −99% and 1000% (error if there is not exactly one).
- `tvm_pv(rate, nper, pmt, fv=0, when=0)`, `tvm_fv(rate, nper, pmt, pv=0, when=0)`, `tvm_pmt(rate, nper, pv, fv=0, when=0)`, `tvm_nper(rate, pmt, pv, fv=0, when=0)`, `tvm_rate(nper, pmt, pv, fv=0, when=0)` — spreadsheet sign conventions: money paid out is negative, so `tvm_pv(0.05, 10, -100)` is `772.17`; `when=1` puts payments at the start of each period.
- `bond_price(face, coupon_rate, ytm, years, freq=2)` and `bond_ytm(price, face, coupon_rate, years, freq=2)` (on a coupon date, annual rates as decimals); `mac_duration(...)` and `mod_duration(...)` with the same arguments, in years.
- `bsm(S, K, T, r, sigma, q=0, kind='call')` (r and q continuously compounded), `ncdf(x)` and `ninv(p)` (standard normal), `NormalDist`, `statistics`, `Decimal`, `cents(x)` (round half up to the cent).
- General: `math`, `comb`, `perm`, `factorial`, `sqrt`, `exp`, `log` (natural), `log10`, `floor`, `ceil`, `root(f, a, b)` (the one root of `f` in `[a, b]`), `allroots`, `lin`, `det`, `inv`, `mat`, `dot`, `np`, `Fraction`, `nsum`, `quad`, and builtins such as `sum`, `range`, `min`, `max`, `round`, `len`, `sorted`, `int`, `abs`, `zip` and `enumerate`.
For `expr`, the check is a lambda that returns the value the correct expression has for given inputs. Only when an item truly cannot be computed, write `nocheck: <reason>` (at most six per course).

### `code` items

```
@practice code
prompt: Write `payback_period(flows)` that returns the number of whole years until the cumulative cash flow from `flows` (year 0 first) is zero or more, or `None` if it never is.
starter:
```python
def payback_period(flows):
    pass
```
tests:
```python
assert payback_period([-100, 40, 40, 40]) == 3
assert payback_period([-100, 50, 50]) == 2
assert payback_period([-100, 30, 30]) is None
assert payback_period([0, 10]) == 0
```
model:
```python
def payback_period(flows):
    total = 0
    for year, flow in enumerate(flows):
        total += flow
        if total >= 0:
            return year
    return None
```
hint: Keep a running total of the cash flows, year by year.
solution: Add each year's cash flow to a running total and return the first year in which the total is no longer negative; if the loop ends first, the project never pays back.
```

- `starter:` (optional) is the code the editor starts with: usually the function header and `pass`. It must compile and must **fail** the tests. `model:` is your complete reference solution. Each of `starter`, `tests`, `model`, `stdin`, `stdout` holds exactly one fenced block.
- `tests:` is Python run after the learner's code, in the same namespace. Each top-level `assert` is one test: the learner sees a ✓ or ✗ beside each one, and a failing `assert expr == expected` automatically reports what the code gave and what was expected, so prefer `assert f(x) == value` over clever conditions. Write 3–6 asserts: the main case, edge cases (an empty list, a single period, a zero rate, negative cash flows, boundaries) and one case a typical wrong solution gets wrong (end- versus start-of-period payments, the annual rate used as the monthly rate, an off-by-one in the number of periods). Non-assert lines are setup and run in order.
- **Floats**: money and rates computed with floats are not exact, so compare with `math.isclose(f(x), expected, rel_tol=1e-9)` or `abs(f(x) - expected) < 1e-6` (import `math` in the tests), unless the value is exact (an integer count, a `Decimal`, or a result the prompt says to round with `round(x, 2)`). `round()` and float formatting such as `f"{x:,.2f}"` behave exactly as in CPython, including round-half-to-even on the binary value (`round(2.675, 2)` is `2.67`); when a prompt asks for amounts rounded half up to the cent, the model should use `Decimal` and `quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)`.
- `stdout:` (optional) is the exact text the program must print, for "write a program that prints …" exercises (a formatted loan schedule, a budget summary); trailing spaces and trailing blank lines are ignored, everything else must match. `stdin:` (optional) holds the lines that `input()` returns, one per line; `input()` does not echo what it reads, so the expected output contains the prompt text but not the typed line. **A program that reads input must be checked on two or three different inputs**: repeat `stdin:` and `stdout:` as pairs, in order, each holding one fenced block. The first pair is shown to the learner and used by the Run button; the others are hidden checks.
- Helpers available to learner code and tests: `output()` returns the text printed since the tests began or since the last `output()` call; `write_file(name, text)` and `read_file(name)` set up and inspect files, and the learner's `open()` works on these in-memory files in text mode (a CSV of prices: `write_file("prices.csv", "date,close\n2026-01-02,101.50\n")`); `raises(ExcType, func, *args)` is True when the call raises that exception.
- `solution:` explains the approach in words. **The site shows your `model:` code right after the solution**, so do not paste the whole model again.
- The prompt must specify everything the tests check: the function name and parameters, units (decimal rates such as `0.05`, or percents), the timing convention (cash flow 0 at time 0; payments at the end of each period), the return value (returned, not printed, unless the exercise is about printing), how to treat edge cases, and anything not allowed. Give one example call in the prompt when it helps.
- Good code: idiomatic, readable, PEP 8, docstrings for public functions in college and career courses, type hints welcome in college model solutions (tests must not depend on them). Name things as a finance team would (`cash_flows`, `discount_rate`, `ending_balance`).
- Keep the work small: model plus tests must finish in well under a second in the browser, which is about 20–50 times slower than CPython. `Decimal` arithmetic is pure Python in the browser (roughly a millisecond per operation), so keep `Decimal` loops under about 100 steps; use floats for long schedules and simulations (a 360-month mortgage, a Monte Carlo run of a few thousand draws). No timing-based tests.
- **What the browser's Python can run.** It is Brython, implementing Python 3.14, and it also has to pass under CPython 3.13, so use features common to both. Available: the whole core language (classes, dataclasses, generators, comprehensions, `match`, f-strings, exceptions, `with`, `enum`, `typing`) and most of the standard library: `math`, `statistics` (including `mean`, `stdev`, `pstdev`, `variance`, `median`, `quantiles`, `correlation`, `covariance`, `linear_regression`, `NormalDist`), `decimal`, `fractions`, `datetime`, `calendar`, `random`, `itertools`, `functools`, `collections`, `bisect`, `heapq`, `csv`, `io`, `json`, `re`, `string`, `textwrap`, `operator`, `copy`, `unittest`. **Not available in the browser**: `numpy`, `pandas`, `scipy`, `matplotlib` and every other third-party package; `sqlite3`; threads and `asyncio`; networking and live market data. Code items therefore use plain Python: lists of returns, dictionaries of prices, small matrices as lists of lists, and regression with `statistics.linear_regression` or the formulas written out. You may show NumPy or pandas in an article as a ```python block labeled "on your own computer", but no item may need them.
- **Tests must give the same result in any Python**: never test specific random values (test properties instead: length, range, a mean close to its expected value with a generous tolerance and a fixed seed only for reproducibility of your own runs), set iteration order, default object reprs, object ids, the exact wording of a built-in error message (test the exception type with `raises`), or anything that depends on the date or time (pass dates in as arguments).
- Every lesson in a `P` (programming and modeling) course has at least two `code` items among its practice and quiz items. C5 and C12 have at least one `code` item in most lessons. Other courses use `code` where the topic is naturally programmed (an amortization schedule, an NPV or IRR function, a simulation, a ratio calculator) — about one item in every two or three lessons in college quantitative courses, none in elementary courses.

### `text` items

For "what does this program print?" and other short exact answers (an account name, a ticker-style code, a formula term):

```
@practice text
prompt: What does this program print?

```python
balance = 1000.0
for year in range(2):
    balance *= 1.05
print(f"{balance:,.2f}")
```
answer: 1,102.50
check: run("balance = 1000.0\nfor year in range(2):\n    balance *= 1.05\nprint(f\"{balance:,.2f}\")\n").strip()
hint: Each pass through the loop multiplies the balance by 1.05.
solution: After two years the balance is $1000 \times 1.05^2 = 1102.5$, printed with a thousands separator and two decimals.
```

- The learner's text is compared with `answer:` line by line after trimming each line and treating any run of spaces as one space; capital letters and punctuation matter. Multi-line answers go in a fence. `accept:` lines give other forms that are also correct, but keep answers unambiguous: say exactly what to type.
- `check:` must reproduce the answer independently: `run(src)` runs Python (CPython 3.13) and returns what it prints, and `run(src, stdin)` feeds input lines. Copy the program exactly from the prompt into the check as a Python string with `\n` line breaks.
- When the answer cannot be computed, use `nocheck: <reason>` (counted in the limit of six per course). Prefer `mc` for terminology.

## Writing for each level

- **Elementary (K10).** The learner is a child with an adult helper who reads aloud. Short sentences, everyday words, one idea at a time, things a child can see and do: real or pretend coins and bills (penny 1¢, nickel 5¢, dime 10¢, quarter 25¢; \$1, \$5, \$10 and \$20 bills), a pretend store, a savings jar, a chart on paper. Articles 150–350 words; examples with 2–4 steps; amounts under \$20 until the last weeks, and whole dollars or simple cents. Items are mostly `num` (with `unit: ¢` or `lead: \$`, and exact answers), `mc`, and `self` items for hands-on tasks the adult checks with the rubric ("Count the coins in your jar with your grown-up and write the total"). No code and almost no TeX. Use only pretend money for spending and banking activities; never ask a child about the family's real money, income or debts, and never send a child to a website to buy or sign up for anything.
- **Middle school (J10).** Articles 250–450 words; clear, encouraging, concrete before abstract, with realistic teen situations (an allowance, a first job, a phone plan). Calculations a learner can do with a basic calculator; simple and compound interest with whole-number rates; tables for budgets and statements. No code items (the learner may not have taken Python yet).
- **High school (H15, H16).** Articles 300–600 words. H15 uses the current figures in the list below and labels tax figures by year; budgets, loans and savings projections with realistic numbers. H16 works at the level of AP Microeconomics and AP Macroeconomics: precise definitions, curves described with equations and tables, numeric problems (elasticities, surplus, GDP growth, inflation, the money multiplier). A few `code` items are welcome in H15 (a savings projection, a loan payoff loop), since learners have met Python in H14.
- **College (C1–C21).** Articles 350–750 words; university-level precision, as in a good undergraduate finance or accounting course. Formulas in TeX with every symbol defined; worked examples with every step and the intermediate values; realistic numbers. Accounting courses show journal entries (debits and credits that balance) and statement effects; economics courses state assumptions and use small models; quantitative courses give derivations. Problems use fictional companies with invented data ("Larkspur Outfitters", "Bellwether Foods").
- **Professional (P1–P6).** Articles 400–800 words, practical and current, written as an experienced charterholder coaching a candidate or a new analyst. P1–P3 review the CFA Program body of knowledge for each level (see the facts below) with original exam-style practice: P1 mostly standalone `mc` items with exactly three choices, as on the exam; P2 `mc` items built on short vignettes (each item restates the facts it needs, since items appear alone); P3 a mix of vignette `mc` items and `self` items in the constructed-response style (a client case and a question, a model answer with the numbers and the justification, and a rubric that awards the points a grader would). Ethics items apply the Code and Standards to original scenarios and name the specific Standard in the solution. P4 and P5 work like an equity research desk; P6 covers professional conduct, compliance, performance presentation and careers. `self` items for memos, reports, policies and pitches have complete model answers and specific rubrics.

## Content standards

- **Correct above all.** Precise definitions and true statements; formulas that match their standard forms; arithmetic you have checked (run it with `python3 -c`); debits equal credits; statements that balance. State every assumption a calculation depends on: end-of-period cash flows unless stated otherwise, the compounding frequency, nominal versus effective rates, annual versus periodic rates, pretax versus after-tax, the day-count convention when it matters, bond prices per 100 of par or in dollars. Do not invent rules, standards, ratios, laws or exam facts; when unsure, choose a statement you know is true.
- **Education, not advice.** Teach concepts, methods and how professionals reason. Never tell the learner what to buy, sell or hold, and never name specific funds, brokerages, banks, card issuers or apps as choices (regulators and public institutions such as the SEC, FINRA, the Federal Reserve, the FDIC, the IRS, the CFPB and CFA Institute are fine to name). Personal finance lessons describe kinds of accounts, products and trade-offs neutrally. One short reminder in the lessons where it matters ("this is general education, not tax advice") is enough; do not repeat it in every item.
- **Real versus invented data.** Problems use invented companies, people and numbers. You may describe well-documented history accurately (the 1929 crash and the Great Depression, Bretton Woods, the 1987 crash, the dot-com bubble, the 2007–2009 financial crisis and the failure of Lehman Brothers, the failure of Silicon Valley Bank in March 2023). Never state current market data as fact: interest rates, inflation, stock prices, index levels, exchange rates, yields or a real company's current financial figures. Use clearly hypothetical numbers instead ("suppose the 10-year Treasury yields 4%") and tell learners where to find current data (FRED, Treasury, SEC EDGAR).
