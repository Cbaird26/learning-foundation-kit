# Writing one course for the AI Learning Foundation

The AI Learning Foundation is a Khan Academy–style self-study site for a 66-course pathway from kindergarten to research in machine learning: elementary, middle and high school (shared with the Coding Learning Foundation), a complete college degree in artificial intelligence and machine learning, and graduate study and research. Each course follows a 14-week syllabus. You write the lessons for ONE course: weeks 1–12 (one lesson per weekly topic) plus a project/review/final-exam file for weeks 13–14. Your course JSON says who the learner is (`audience`) and the course `level`; write for that learner. Address the learner as "you". Assume the course prerequisites, but briefly remind key prerequisite ideas when you use them. Use the standard names of methods, results, quantities and systems (gradient descent, backpropagation, cross-entropy, the bias–variance trade-off, the kernel trick, the EM algorithm, the VC dimension, the Bellman equation, attention, the transformer, RLHF): learners need them to use the readings, read papers and talk with other practitioners. Attribute methods and results to their authors where the attribution is standard (see Content standards), but do not write biographies or anecdotes about real people, and never mention the curriculum's author.

The site runs Python in the learner's browser, so learners write and run real code inside lessons, and the site grades it by running your tests. The browser's Python has **no NumPy, pandas, scikit-learn or PyTorch**, so every graded exercise builds the idea from scratch in plain Python on small data. That is a feature: implementing gradient descent, backpropagation, k-means or attention in twenty lines is the surest way to understand it. Articles may show how practitioners write the same thing with NumPy or PyTorch.

## Files you write (only these)

- `/home/claude/ai/content/<CODE>/L01.txt` … `L12.txt` — week N lesson = the syllabus topic for week N.
- `/home/claude/ai/content/<CODE>/project.txt` — the week 13–14 project brief, review guide and cumulative exam items.

Your course data (audience, level, profile, topics, block deliverables, project, primary reading) is in `/home/claude/ai/toolkit/courses/<CODE>.json`. Before writing anything, read it and `/home/claude/ai/toolkit/example_ml_lesson.txt`: a complete, valid lesson that shows the exact format, the conventions for math, data and code, and every common item type. The example lesson is a format sample: never copy its examples, data, functions or items. C12 (gradient descent in weeks 5–6) and C15 (week 1) overlap the example's topic and must use entirely new functions, data sets, numbers and exercises.

## File format

Sections start with `@name` at the start of a line. Fields are `key: value`; a line that does not begin with a known key continues the previous field, so multi-line values are fine. Text inside ``` fences is kept exactly as written: inside a fence, lines that look like `key: value` or `@name` are just code, so decorators and dictionaries are safe there. Write TeX directly; inline math is `$...$`, display math is `$$...$$`.

**Dollar signs.** A `$` outside code starts math. Write a literal dollar sign as `\$` (a compute budget of `\$2,000`). Put anything else with `$` inside backticks or a fence.

**Math notation** (use it consistently): scalars in italics ($x$, $y$, $\eta$); vectors bold lowercase ($\mathbf{x}$, $\mathbf{w}$) written `\mathbf{x}`; matrices bold uppercase ($\mathbf{X}$, $\mathbf{W}$); parameters $\boldsymbol{\theta}$ (`\boldsymbol{\theta}`); the transpose $\mathbf{x}^\top$ (`^\top`); a data set $\{(\mathbf{x}_i, y_i)\}_{i=1}^{n}$; a loss $L(\boldsymbol{\theta})$ or $\ell(\hat{y}, y)$; the gradient $\nabla_{\boldsymbol{\theta}} L$; expectation $\mathbb{E}$, probability $P(\cdot)$ for events and $p(\cdot)$ for densities; norms $\lVert \mathbf{x} \rVert_2$ (`\lVert`, `\rVert`); named functions with `\operatorname{softmax}`, `\operatorname{ReLU}`, `\arg\max`. **$\log$ means the natural logarithm** unless you write $\log_2$; say "nats" or "bits" when it matters. Matrices of data have one example per row.

**Algorithms.** Give an algorithm as runnable Python in a ```python fence whenever you can (the site adds a Try it button to code that runs the same in the browser), or as numbered steps in prose. Use ```text for pseudocode or for NumPy or PyTorch code you show for reference (it does not run in the browser).

**The site shows no images.** Describe what a picture would show in words and tables: a learning curve as a table of epochs and losses, a decision boundary by its equation and a few labeled points, a network or a causal graph as a list of nodes and edges, an image as a small grid of numbers, a confusion matrix as a table.

Code in prose: inline code in single backticks; blocks in fences with a language (```python, ```text, ```bash). Keep code lines under 80 characters where you can (the hard limit is 100), and indent with 4 spaces, never tabs.

Lesson file sections, in order:
- `@lesson` — `title:` (the week's topic as a clear title), `summary:` (one sentence: what the learner will be able to do), `objective:` ×2–4, `reading:` (see below).
- `@article` — markdown: paragraphs, `###` subheadings, **bold**, lists, tables, code blocks, `$math$`. Length by level (see below).
- `@example` ×1–2 — `title:`, `problem:`, `step:` ×2–6 (each step is revealed one at a time, Khan-style; a step may contain a table or a code block), optional `answer:`.
- `@mistakes` — 2–4 lines starting with `- `.
- `@practice <type>` ×5 — ordered easy → hard, each with its own data and numbers: never reuse a worked example, the article's own data or its numbers (also in code items' example calls and tests), so learners must apply the idea rather than recognize an answer they have seen. A code item never asks for a function the article already gives in full: ask for a variant, an extension or the next step (a different separator, a second dimension, a stopping rule, an edge case the article's version mishandles).
- `@quiz <type>` ×2–3 — new problems used only in unit quizzes, the midterm and the final. Never near-copies of practice items, and never the data of a worked example.

## Item types

Item fields: `prompt:`, `answer:`, `check:`, `hint:` ×1–3 (progressive; the last hint gets the learner to the method but not the final answer), `solution:` (complete and short), plus the fields each type needs.

| type | learner does | you give | verified by |
|---|---|---|---|
| `num` | one number | `answer:`, usually `tol:`, and `unit:` when it helps | `check:` expression |
| `expr` | an expression in `vars` (a derivative, a gradient component) | `answer:`, `vars:` | `check:` lambda |
| `mc` | one choice | mark the correct `choice*:` | — |
| `ms` | select all that apply | mark every correct `choice*:` | — |
| `self` | derives, proves, designs, writes or builds, then compares with a model | `solution:` (model answer) and `rubric:` ×2–4 | — |
| `code` | writes Python in an editor, runs it, presses Check | `starter:`, `tests:` and/or `stdout:`, `model:` | the validator runs `model` against your tests in CPython **and** in the browser's Python, and checks that `starter` fails them |
| `text` | types an exact short answer, usually what a program prints | `answer:`, optional `accept:` ×n | `check:` that computes the same text |
| `list` | several values, any order | `answer:` (`-2, 3` or `none`) | `check:` |
| `tuple` | ordered values | `answer:` (`(2, -1)`) | `check:` |

`mc`/`ms` use `choice:` lines (3–5 total) with the correct ones written `choice*:`. **The site shuffles the choices**, so never use "all/none of the above" or "both A and B", and in hints and solutions name a choice by its content, never by its position ("the second choice", "option B"). Each `mc` item has exactly one best answer. Distractors come from real misconceptions: confusing training error with test error, precision with recall, correlation with causation, a parameter with a hyperparameter, the gradient with the loss, L1 with L2 regularization, bias with variance, batch with layer normalization, keys with values, on-policy with off-policy, validation data with test data, a model's confidence with its accuracy, or one method's assumption with another's. `ms` items suit "which of these would reduce overfitting?" and "which of these are valid adjustment sets?". Use `self` for derivations, proofs, designs, critiques, model cards, experiment plans and short essays; give a complete model `solution:` and 2–4 specific `rubric:` lines.

**What an auto-graded item may test.** An `mc`, `ms`, `num`, `text`, `list` or `tuple` item must have an answer that is correct whatever view the learner holds: what a method computes, what a result states, what a paper or a law says, what follows from given numbers, or a computed value. Never make a contested claim (that advanced AI will or will not be dangerous, that a regulation is good or bad, that current models do or do not understand or reason, that one research agenda is right) the correct answer, and never mark a reasonable view wrong. Questions about what the learner thinks go in `self` items, whose model answers argue one view well and give the strongest reply, and whose rubrics reward the quality of the reasoning, never agreement with a position.

### Numbers (`num` items)

`num` items are the backbone of the math: a gradient at a point, a loss value, an accuracy, precision or recall, an entropy, a probability, a step of an algorithm, a count of parameters, an output shape, a sample size, a regret bound.
- `answer:` is a plain number: `3`, `0.95`, `-0.25`, `3/4`, `2.83`, `1.5e9`. No `%`, commas or words in the answer field. Learners may type `1,234` or `7.25%`: the site removes thousands separators, and a `%` typed into an item whose unit is `%` is ignored.
- **Percentages**: answer as a percent with `unit: %` ("Give the accuracy as a percent to one decimal place" → `answer: 87.5`, `unit: %`). A probability or a rate asked for as a decimal has no unit.
- **Other units**: `unit: bits`, `unit: nats`, `unit: parameters`, `unit: FLOPs`, `unit: GB`, `unit: examples`.
- **Tolerance**: whenever the prompt asks for rounding, set `tol:` to one unit of the last place asked for (two decimal places → `tol: 0.01`); `tol: 1%` gives a relative tolerance for large numbers. A `num` item without `tol:` must have an exact answer (an integer, or a terminating decimal such as `0.95` that needs no rounding).

`check:` is ONE Python expression that computes the expected result independently from the problem statement — never retype your answer. Redo the arithmetic (`-log(0.7)`, `sum(p * log2(1 / p) for p in [0.5, 0.25, 0.25])`, `2 * 0.8 * 0.6 / (0.8 + 0.6)`), use the program itself (`float(run("...program..."))`), or use the helpers: `math`, `np` (NumPy), `exp`, `log` (natural), `log2`, `log10`, `sqrt`, `tanh`, `erf`, `comb`, `perm`, `factorial`, `floor`, `ceil`, `Fraction`, `pi`, `e`, `inf`, `mat(A)` (a NumPy array, so `mat(A) @ mat(B)` works), `dot`, `norm`, `det`, `inv`, `eig`, `lin(A, b)`, `rank`, `nderiv(f, x)`, `pderiv(f, point, i)`, `root`, `quad(f, a, b)`, `nsum`, and builtins such as `sum`, `range`, `min`, `max`, `round`, `len`, `sorted`, `zip`, `enumerate`, `abs`, `all`, `any`, `int`, `float`. Check expressions run only in the validator (in CPython with NumPy), never in the learner's browser. Only when an item truly cannot be computed, write `nocheck: <reason>` (at most six per course).

`expr` items: `answer:` in calculator syntax (`2*w*x^2 - 2*x*y`, `e^(-z)/(1+e^(-z))^2`, `ln(x)`), `vars: w, x, y`, and a `check:` lambda giving the correct value (`lambda w, x, y: 2 * w * x**2 - 2 * x * y`). Use them for derivatives and gradient components; optional `domain: x: 0.5..3` sets the sampling range.

### `code` items

```
@practice code
prompt: Write `mse(preds, targets)` that returns the mean squared error of two equal-length lists of numbers. For example, `mse([1, 2], [1, 4])` returns `2.0`.
starter:
```python
def mse(preds, targets):
    pass
```
tests:
```python
assert abs(mse([1, 2], [1, 4]) - 2.0) < 1e-9
assert abs(mse([0.5], [0.5])) < 1e-9
assert abs(mse([1, 2, 3], [2, 2, 2]) - 2 / 3) < 1e-9
assert abs(mse([-1, 1], [1, -1]) - 4.0) < 1e-9
```
model:
```python
def mse(preds, targets):
    """Mean of the squared differences between predictions and targets."""
    return sum((p - t) ** 2 for p, t in zip(preds, targets)) / len(preds)
```
hint: Square each difference, add them up, and divide by the number of pairs.
solution: Pair each prediction with its target, square the differences, and average them; dividing by the count, not by the count minus one, makes it a mean.
```

- `starter:` (optional) is the code the editor starts with: usually the function header and `pass`. It must compile and must **fail** the tests. `model:` is your complete reference solution. Each of `starter`, `tests`, `model`, `stdin`, `stdout` holds exactly one fenced block.
- `tests:` is Python run after the learner's code, in the same namespace. Each top-level `assert` is one test: the learner sees a ✓ or ✗ beside each one, and a failing `assert expr == expected` automatically reports what the code gave and what was expected. Write 3–6 asserts: the main case, edge cases (one example, a zero vector, a tie, an empty cluster, a terminal state) and one case a typical wrong solution gets wrong (dividing by n − 1 instead of n, forgetting the bias term, not subtracting the maximum before `exp` in a softmax, an off-by-one output size in a convolution, updating values in place during value iteration, using the test set for a choice that belongs to validation data).
- **Data and representations.** State the representation in the prompt and keep to it within a lesson. Vectors are lists of floats; matrices are lists of rows; a data set is a list of `(features, label)` pairs or a list of rows plus a list of labels; a grayscale image is a list of rows of integers from 0 to 255; a graph is a dictionary of adjacency lists; an MDP is given by dictionaries of transitions and rewards. Data sets are tiny and invented: a handful to a few dozen examples.
- **Floating point.** Compare computed floats with a tolerance, never with `==`: `assert abs(f(x) - 0.5) < 1e-6`, or for lists `assert all(abs(a - b) < 1e-6 for a, b in zip(got, want))`. `math.exp`, `math.log` and `math.tanh` can differ in the last digit between the browser and CPython, so always allow a tolerance (1e-6 relative to the size of the numbers is usually right). Integer results, shapes, counts, argmax indices and labels may be compared exactly.
- **Randomness.** Functions that need randomness take a `seed` or a `random.Random` instance as an argument. Tests never check specific random values; they check properties (the output has the right length, values are in range, the loss went down, calling twice with the same seed gives the same result). Prefer deterministic algorithms in graded items: fixed initializations, a fixed order of examples.
- **Keep the work small.** The model plus the tests must finish in well under a second in the browser, which runs Python about 20–50 times slower than CPython: aim for at most about 100,000 arithmetic operations per check (200 steps of gradient descent on 20 points with 3 features is fine; training a network on hundreds of examples for hundreds of epochs is not). No timing-based tests.
- `stdout:` (optional) is the exact text the program must print; trailing spaces and trailing blank lines are ignored, everything else must match. `stdin:` (optional) holds the lines `input()` returns. A program that reads input must be checked on two or three different inputs: repeat `stdin:` and `stdout:` as pairs; the first pair is shown to the learner, the others are hidden checks. Prefer functions that return values over programs that print.
- Helpers available to learner code and tests: `output()` returns the text printed since the tests began or since the last `output()` call; `write_file(name, text)` and `read_file(name)` set up and inspect files (the learner's `open()` works on these in-memory files in text mode, so CSV-reading exercises work); `raises(ExcType, func, *args)` is True when the call raises that exception.
- `solution:` explains the approach in words. **The site shows your `model:` code right after the solution**, so do not paste the whole model again.
- The prompt must specify everything the tests check: the function name and parameters, the representation, the return value (returned, not printed, unless the exercise is about printing), how to treat ties and edge cases, and anything not allowed. Give one example call in the prompt when it helps.
- Good code: idiomatic, readable, PEP 8, docstrings for public functions, small helper functions where they clarify; type hints welcome in model solutions (tests must not depend on them).
- **What the browser's Python can run.** It is Brython, implementing Python 3.14, and it also has to pass under CPython 3.13, so use features common to both. Available: the whole core language (classes, dataclasses, generators, comprehensions, `match`, f-strings, exceptions, `with`, `enum`, `typing`) and most of the standard library: `math`, `random`, `statistics`, `itertools`, `functools`, `collections`, `heapq`, `fractions`, `string`, `re`, `json`, `csv`, `copy`, `operator`, `textwrap`. **Not available in the browser**: `numpy`, `pandas`, `scipy`, `sklearn`, `torch` and every other third-party package; `sqlite3`; threads and `asyncio`; networking. Graded code is plain Python.
- **The built-in `sum` of floats differs**: CPython 3.12 and later add floats with compensated summation, so `sum([0.1] * 10)` is `1.0` there but `0.9999999999999999` in the browser. Never show or test the exact printed result of `sum` over floats; use an explicit loop when rounding is the point, and integers in `text` items.
- **Tests must give the same result in any Python**: never test specific random values, set iteration order or the printed form of a set, default object reprs, object ids, the exact wording of a built-in error message (test the exception type with `raises`), or anything that depends on the date or time.
- **How many.** In a P (programming) course, every lesson has at least two `code` items among its practice and quiz items, usually three or four, plus `text` items that trace code and `num` items worked by hand. In T courses (C12, C13, C22, P1, P2, P3, P4), add a `code` item in about half the lessons where the topic is naturally programmed (an optimizer step, a sampler, an estimator, a scaling-law fit, a preference loss, an attribution method). C23 and the E courses (P5, P6) have no `code` items; their computations are `num` items.

### `text` items

For "what does this program print?" and other short exact answers:

```
@practice text
prompt: What does this program print?
```python
scores = [0.2, 0.7, 0.1]
print(scores.index(max(scores)))
```
answer: 1
check: run("scores = [0.2, 0.7, 0.1]\nprint(scores.index(max(scores)))")
hint: `max` finds the largest score; `index` gives its position, counting from 0.
solution: The largest score is 0.7, at position 1, so the program prints `1`: the predicted class is the index of the highest score.
```

- The learner's text is compared with `answer:` line by line after trimming each line and treating any run of spaces as one space; capital letters and punctuation matter. Multi-line answers go in a fence. `accept:` lines give other forms that are also correct, but keep answers unambiguous: say exactly what to type.
- `check:` must reproduce the answer independently: `run(src)` runs Python (CPython 3.13) and returns what it prints, and `run(src, stdin)` feeds input lines; copy the program exactly from the prompt into the check as a Python string with `\n` line breaks.
- Prefer `mc` for names and terms (which method, which metric, which researcher): spellings vary, and a learner who knows the answer should not be marked wrong for a hyphen.

## Writing for each level

- **College (C11–C24).** Articles 450–850 words, with university-level precision, as in a good undergraduate machine learning course. Teach in this order: a small concrete case with numbers the learner can follow by hand, then the precise definition or derivation with every step shown, then code that implements it. State results with their conditions (gradient descent with step size $1/L$ on an $L$-smooth convex function; the EM algorithm never decreases the likelihood; the backdoor criterion's two conditions). In P courses the code items are the backbone: implement the week's algorithm from scratch on a tiny data set, with `text` items that trace code and `num` items worked by hand. In T courses, derivations, `num` and `expr` items, `mc`/`ms` on concepts and conditions, `self` items for proofs and derivations, and code where natural. C23 (W, reading and writing) teaches ethics, safety and governance with `mc`/`ms` on concepts, definitions and what laws and standards say, `num` items for fairness metrics, privacy noise and audits, and `self` items for analyses, model cards and balanced arguments with model answers.
- **Graduate (P1–P6).** Articles 500–900 words, written as a faculty member coaching a graduate student: the shape of the current research, the main results with accurate attributions, the arguments and evidence behind them, open problems, and how to read and contribute to the literature. `self` items are research work (a proof, a critique paragraph, an experimental design, a referee report paragraph, a section of a proposal, a timed exam answer) with model answers a faculty reader would admire and rubrics that name what earns credit. P1 is rigorous: complete proofs and exact statements. P3 and P4 cover a fast-moving field: teach the concepts and the well-established results with their dates, say plainly which questions are open, and never describe the current state of the art, current leaderboards or any company's current models. P5 and P6 teach research practice accurately: programs and venues differ, so describe common practice and tell learners to check the rules that apply to them.

## Content standards

- **Correct above all.** Precise definitions and true statements; derivations correct line by line; results stated exactly, with their assumptions; numbers you have checked by running the computation (`python3 -c`). Do not invent results, methods, data sets, dates, names or terminology; when unsure, choose a statement you know is true.
- **Attribution.** Attribute a method or result only when you are sure of the attribution. Standard ones you may use: the perceptron (Rosenblatt, 1958); backpropagation popularized for neural networks (Rumelhart, Hinton and Williams, 1986); convolutional networks for digit recognition (LeCun and colleagues, 1989 and 1998); LSTM (Hochreiter and Schmidhuber, 1997); AlexNet (Krizhevsky, Sutskever and Hinton, 2012); dropout (Srivastava and colleagues, 2014); Adam (Kingma and Ba, 2014); batch normalization (Ioffe and Szegedy, 2015); layer normalization (Ba, Kiros and Hinton, 2016); residual networks (He and colleagues, 2015); attention for translation (Bahdanau, Cho and Bengio, 2014); the transformer, "Attention Is All You Need" (Vaswani and colleagues, 2017); word2vec (Mikolov and colleagues, 2013); byte-pair encoding for subword units (Sennrich, Haddow and Birch, 2016); BERT (Devlin and colleagues, 2018); GPT-3 (Brown and colleagues, 2020); scaling laws for language models (Kaplan and colleagues, 2020); compute-optimal training, often called the Chinchilla result (Hoffmann and colleagues, 2022); learning from human preferences (Christiano and colleagues, 2017); InstructGPT and RLHF for instruction following (Ouyang and colleagues, 2022); Constitutional AI (Bai and colleagues, 2022); direct preference optimization (Rafailov and colleagues, 2023); GANs (Goodfellow and colleagues, 2014); variational autoencoders (Kingma and Welling, 2013); denoising diffusion probabilistic models (Ho, Jain and Abbeel, 2020); Q-learning (Watkins, 1989); temporal-difference learning (Sutton, 1988); REINFORCE (Williams, 1992); deep Q-networks (Mnih and colleagues, 2013 and 2015); AlphaGo (Silver and colleagues, 2016); PPO (Schulman and colleagues, 2017); UCB1 (Auer, Cesa-Bianchi and Fischer, 2002); Thompson sampling (Thompson, 1933); PAC learning (Valiant, 1984); the VC dimension (Vapnik and Chervonenkis, 1971); support vector machines (Cortes and Vapnik, 1995); AdaBoost (Freund and Schapire, 1997); random forests (Breiman, 2001); gradient boosting (Friedman, 2001); the EM algorithm (Dempster, Laird and Rubin, 1977); k-means++ (Arthur and Vassilvitskii, 2007); differential privacy (Dwork, McSherry, Nissim and Smith, 2006); impossibility results for fairness criteria (Kleinberg, Mullainathan and Raghavan, 2016; Chouldechova, 2017); LIME (Ribeiro, Singh and Guestrin, 2016); SHAP (Lundberg and Lee, 2017); integrated gradients (Sundararajan, Taly and Yan, 2017); adversarial examples (Szegedy and colleagues, 2013) and the fast gradient sign method (Goodfellow, Shlens and Szegedy, 2014); induction heads (Olsson and colleagues, 2022); toy models of superposition (Elhage and colleagues, 2022); double descent (Belkin and colleagues, 2019); potential outcomes (Rubin, 1974) and causal graphs and the do-calculus (Pearl); BLEU (Papineni and colleagues, 2002); ROUGE (Lin, 2004); ImageNet (Deng and colleagues, 2009); the Dartmouth workshop (1956); Turing's imitation game (1950). Years are those of the first public versions (many papers appeared on arXiv a year before the conference); when you are unsure of a year or who was first, leave the year or the name out ("a widely used method…"). Never invent a quotation, a title, a date, a number or a citation. Describe living researchers only through their well-known published work and public positions, and never attribute personal beliefs, motives or private life to anyone.
- **Quotation.** Paraphrase. Never quote modern papers, books, lectures, websites or laws beyond a short defined term in quotation marks (the EU AI Act's term "general-purpose AI model"); explain what a source says in your own words and say where it is. Do not reproduce textbook passages, exercises or exam questions from the readings; write original items.
- **Well-known data sets** may be described factually: MNIST has 60,000 training and 10,000 test images of handwritten digits, 28 by 28 pixels in grayscale; CIFAR-10 has 60,000 color images of 32 by 32 pixels in 10 classes (50,000 for training and 10,000 for testing); the ImageNet classification challenge used about 1.2 million training images in 1,000 classes. Everything you put in an item is invented and small.
- **Balance on contested questions.** Where informed researchers disagree (how fast AI will progress and whether and when systems will match humans at most tasks; how large the risks from advanced AI are, including catastrophic and existential risks, and how to weigh them against present harms; whether large language models understand, reason or are conscious; whether some abilities emerge suddenly with scale; open versus closed release of models; how AI should be regulated; how AI will affect jobs and wages; how copyright applies to training data), present the strongest version of each main position with its evidence and the best objections, and do not tell the learner which view is true. Say plainly when something is unknown. Never caricature a position or the people who hold it.
- **Products and companies.** Name published research systems in their historical context, with their paper (GPT-3, AlphaGo, BERT, ResNet). Do not compare, rank or describe current commercial AI products or any company's current models, plans or market position, and do not state what any current system can or cannot do; the field changes too fast, and lessons must stay true.
- **Safety and security.** Teach security-relevant ideas (adversarial examples, data poisoning, prompt injection, jailbreaks, membership inference, model extraction, privacy attacks) at the conceptual level of textbooks and survey papers, always with defenses and limits, and with toy demonstrations on tiny invented models (a perturbation that flips a two-feature linear classifier). Never give step-by-step instructions or working code for attacking real deployed systems, and nothing that would help anyone build weapons or malware or harm people.
- **Current facts to teach as current** (verified; use them where your course touches them, and tell learners that laws and standards change, so they should check the current text):
  - **EU AI Act.** Regulation (EU) 2024/1689 entered into force on 1 August 2024 and takes a risk-based approach: prohibited ("unacceptable-risk") practices, high-risk systems, transparency obligations for some systems (such as chatbots and AI-generated content), minimal-risk systems, and separate rules for general-purpose AI models; models trained with more than $10^{25}$ floating-point operations are presumed to pose systemic risk. The prohibitions and the AI literacy duty apply from 2 February 2025; the obligations for general-purpose AI models from 2 August 2025; the transparency obligations of Article 50 from 2 August 2026. The Digital Omnibus on AI, adopted in June 2026 and published in the Official Journal on 24 July 2026, moved the high-risk obligations to 2 December 2027 for systems listed in Annex III and to 2 August 2028 for AI in products covered by Annex I.
  - **United States.** There is no comprehensive federal AI statute that you may describe as enacted; federal preemption of state AI laws has been actively debated in Congress since 2025, so tell learners to check its current status. In January 2025 the 2023 executive order on AI (EO 14110) was revoked and EO 14179, "Removing Barriers to American Leadership in Artificial Intelligence," was issued; America's AI Action Plan followed in July 2025; EO 14365, "Ensuring a National Policy Framework for Artificial Intelligence" (11 December 2025), directs federal agencies to challenge and discourage state AI laws they judge burdensome, but an executive order does not by itself preempt state law.
