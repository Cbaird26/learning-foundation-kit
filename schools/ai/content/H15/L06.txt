@article
**Polymorphism** ("many forms") means the same call does the right thing for different kinds of objects. When you write `shape.area()`, you do not care whether `shape` is a circle or a rectangle; each class supplies its own version of `area`, and Python picks the right one at run time.

```python
shapes = [Rectangle(2, 3), Triangle(4, 3), Rectangle(1, 1)]
total = 0
for s in shapes:
    total += s.area()      # a different method may run each time
```

This loop never mentions a specific class. If you later add `Hexagon`, the loop keeps working without a single change. That is the payoff: new behavior is added by adding classes, not by editing every `if kind == "..."` chain in the program.

### Abstract base classes

Often a parent class exists only to define *what* its children must do. A `Shape` has no meaningful area by itself. An **abstract base class** (ABC) states this formally:

```python
from abc import ABC, abstractmethod


class Shape(ABC):
    @abstractmethod
    def area(self):
        """Return the area as a number."""

    def describe(self):
        return f"{type(self).__name__} with area {self.area():.1f}"
```

- `ABC` marks the class as abstract.
- `@abstractmethod` marks a method that **subclasses must override**.
- You cannot create a `Shape()`: Python raises `TypeError` because the class still has abstract methods.
- A subclass that overrides *all* abstract methods becomes concrete and can be instantiated. A subclass that forgets one stays abstract, and the error appears the moment you try to create an object, not later in the middle of a calculation.
- `describe` is a **concrete** method that uses the abstract one. This is called the *template* idea: the parent writes the shared logic and children fill in the varying step.

```python
class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height
```

An older, weaker style is to write `raise NotImplementedError` in the parent method. That works, but the mistake shows up only when the method is called. Prefer `abc` when you want the contract enforced early.

### Duck typing

Python does not require a shared parent for polymorphism. If an object has the method you call, it works: "if it walks like a duck and quacks like a duck, it is a duck". A function `total_area(shapes)` works for any objects with an `area()` method, even classes written by someone else that know nothing about `Shape`. Inheritance and ABCs are still valuable because they document the contract, give shared code, and catch missing methods early, but they are not the only route.

### Choosing

- Many related classes sharing code and a contract: an ABC with concrete helper methods.
- Unrelated classes that happen to offer the same method: duck typing is fine; keep the method names and meanings consistent.
- If a function checks `isinstance` for ten different classes, that is a sign the behavior should be a method on those classes instead.

### The hierarchy deliverable

For this block you build a small hierarchy: an abstract parent, two or three concrete children, and code that treats them all the same way. The practice items include one.

@example
title: Spotting polymorphism and an abstract error
problem: What does this program print?

```python
from abc import ABC, abstractmethod


class Pet(ABC):
    @abstractmethod
    def sound(self):
        pass


class Dog(Pet):
    def sound(self):
        return "woof"


class Fish(Pet):
    pass


print(Dog().sound())
try:
    Fish()
except TypeError:
    print("cannot create Fish")
```
step: `Dog` overrides `sound`, so it is concrete. `Dog().sound()` returns `woof`, which is printed.
step: `Fish` inherits the abstract `sound` and does not override it, so `Fish` is still abstract.
step: `Fish()` raises `TypeError` at the moment of creation, and the handler prints a message.
answer: `woof`, then `cannot create Fish`

@example
title: Adding a new kind without changing the loop
problem: `report(shapes)` prints each shape's description. Add a `Square` shape and show that `report` needs no change.
step: Here is `report`. It only calls `describe()`:

```python
def report(shapes):
    for s in shapes:
        print(s.describe())
```
step: Add a new concrete class that implements the abstract method:

```python
class Square(Shape):
    def __init__(self, side):
        self.side = side

    def area(self):
        return self.side ** 2
```
step: `report([Square(3), Rectangle(2, 3)])` prints `Square with area 9.0` and `Rectangle with area 6.0`. The function was written before `Square` existed and still works.

@mistakes
- Trying to instantiate an abstract class and being surprised by `TypeError`; only concrete subclasses can be created.
- Forgetting to import `ABC` and `abstractmethod` from `abc`, or writing `@abstractmethod` without making the class inherit from `ABC`, in which case the method is not enforced.
- Checking `isinstance(x, Circle)`, `isinstance(x, Square)` and so on in a long chain instead of calling a method every class provides.
- Overriding an abstract method with a different signature (different parameters), which breaks code written against the parent.

assert Hourly("Bo", 10, 45).pay() == 475

assert Hourly("Di", 20, 0).pay() == 0

model:
```python
from abc import ABC, abstractmethod


class Worker(ABC):
    def __init__(self, name):
        self.name = name

    @abstractmethod
    def pay(self):
        """Return this worker's pay."""


class Salaried(Worker):
    def __init__(self, name, annual):
        super().__init__(name)
        self.annual = annual

    def pay(self):
        return self.annual / 12


class Hourly(Worker):
    def __init__(self, name, rate, hours):
        super().__init__(name)
        self.rate = rate
        self.hours = hours

    def pay(self):
        regular = min(self.hours, 40)
        overtime = max(self.hours - 40, 0)
        return regular * self.rate + overtime * 1.5 * self.rate


def payroll(workers):
    return {w.name: w.pay() for w in workers}
```
hint: Put `name` and the abstract `pay` in `Worker`; the subclasses call `super().__init__(name)`.
hint: For overtime, split the hours: `min(hours, 40)` at the normal rate and `max(hours - 40, 0)` at one and a half times the rate.
solution: `Worker` stores the name and requires `pay`. `Hourly.pay` pays the first 40 hours normally and the rest at 1.5 times the rate. `payroll` is polymorphic: it calls `pay()` on each worker without caring about the type, so it works for any future kind of worker.

@quiz code
prompt: Write an abstract class `Discount` with an abstract method `apply(price)` that returns the discounted price. `Percent(p)` takes `p` percent off (`Percent(25).apply(80)` is `60`). `Flat(amount)` subtracts a fixed amount but never goes below `0`. Then write `best_price(price, discounts)` that returns the lowest price obtainable by applying **one** of the discounts in the list (the original price if the list is empty).
starter:
```python
class Discount:
    pass
```
tests:
```python
assert Percent(25).apply(80) == 60
assert Flat(10).apply(25) == 15
assert Flat(10).apply(5) == 0
assert raises(TypeError, Discount)
assert best_price(100, [Percent(10), Flat(30), Percent(20)]) == 70
assert best_price(100, [Percent(10), Flat(5)]) == 90
assert best_price(50, []) == 50
assert best_price(20, [Flat(100)]) == 0
```
model:
```python
from abc import ABC, abstractmethod


class Discount(ABC):
    @abstractmethod
    def apply(self, price):
        """Return the price after the discount."""


class Percent(Discount):
    def __init__(self, p):
        self.p = p

    def apply(self, price):
        return price * (100 - self.p) / 100


class Flat(Discount):
    def __init__(self, amount):
        self.amount = amount

    def apply(self, price):
        return max(price - self.amount, 0)


def best_price(price, discounts):
    best = price
    for d in discounts:
        best = min(best, d.apply(price))
    return best
```
hint: Make `Discount` inherit from `ABC` and put `@abstractmethod` on `apply`.
hint: In `best_price`, start the best value at the original price and lower it with `min` for each discount.
solution: `Percent.apply` returns `price * (100 - p) / 100` and `Flat.apply` uses `max(price - amount, 0)` as a floor. `best_price` starts from the full price (so an empty list is right) and keeps the smallest result, calling `apply` polymorphically.
