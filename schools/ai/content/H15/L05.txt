@article
Suppose a game has a `Monster` class with a name and health, and you want a `Dragon` that is a monster but can also breathe fire. Copying the whole class would duplicate code, and fixing a bug would mean fixing it twice. **Inheritance** lets a new class start from an existing one and add or change only what is different.

### Subclasses and superclasses

```python
class Employee:
    def __init__(self, name, salary):
        self.name = name
        self.salary = salary

    def pay(self):
        return self.salary


class Manager(Employee):
    def __init__(self, name, salary, bonus):
        super().__init__(name, salary)
        self.bonus = bonus

    def pay(self):
        return super().pay() + self.bonus
```

`Manager(Employee)` means `Manager` is a **subclass** (child, derived class) of `Employee`, the **superclass** (parent, base class). A `Manager` object automatically has everything `Employee` defines, plus its own additions.

- `super().__init__(name, salary)` runs the parent's initializer so the inherited attributes get set. If the subclass defines `__init__` and forgets this, those attributes are never created.
- `pay` in `Manager` **overrides** the parent's version. When you call `m.pay()` Python looks for `pay` in `Manager` first, then in `Employee`, and uses the first one it finds.
- `super().pay()` calls the parent's version, so the subclass can *extend* behavior instead of rewriting it.

### The "is a" test

Use inheritance only when the child really **is a kind of** the parent, and can be used anywhere the parent can: a `Manager` is an `Employee`. If the relationship is "has a", use **composition**: store an object in an attribute. A `Car` has an `Engine`, so `Car` keeps an `engine` attribute and does not inherit from `Engine`. Misusing inheritance for reuse alone creates confusing designs, and the rule of thumb "prefer composition unless it is clearly an is-a" is a good one.

### Type checks

```python
m = Manager("Ann", 5000, 800)
isinstance(m, Manager)    # True
isinstance(m, Employee)   # True: a Manager is an Employee
isinstance(Employee("Bo", 1), Manager)  # False
issubclass(Manager, Employee)           # True
```

`isinstance(obj, C)` is true if `obj` was built from `C` **or any subclass** of `C`. By contrast, `type(obj) == C` is true only for `C` itself.

### Method lookup

When you write `obj.method()`, Python searches the object's class, then its parent, then the parent's parent, up to the built-in class `object` that every class ultimately inherits from. Because `self` is always the actual object, a method in the parent that calls `self.other()` will run the **subclass's** `other` if it overrides it. That is the reason inheritance is powerful, and also why you must keep overridden methods compatible with what the parent expects: same parameters, similar meaning of the result.

### Hierarchies

Subclasses can have subclasses (`Employee`, then `Manager`, then `Director`). Keep hierarchies shallow: two or three levels is usual. Python also supports **multiple inheritance** (`class C(A, B)`), but it needs care with the lookup order; for now, stay with a single parent.

### A common pattern

Put shared data and behavior in the parent, and put only the differences in each child. If two subclasses repeat the same code, move it up into the parent.

@example
title: Which method runs?
problem: What does this program print?

```python
class Base:
    def hello(self):
        return "base " + self.name()

    def name(self):
        return "B"


class Child(Base):
    def name(self):
        return "C"


print(Base().hello())
print(Child().hello())
```
step: `Base().hello()` finds `hello` in `Base`. It calls `self.name()`, and `self` is a `Base`, so it runs `Base.name` and returns `"B"`. The result is `base B`.
step: `Child().hello()`: `Child` has no `hello`, so Python uses `Base.hello`.
step: Inside it `self` is a `Child`, so `self.name()` finds `Child.name` first and returns `"C"`.
step: The result is `base C`: the parent's code ran, but the child's override was used for the call on `self`.
answer: `base B` then `base C`

@example
title: Extending a parent class
problem: Write `Square` as a subclass of `Rectangle` (which stores `width` and `height` and has `area()`).
step: A square is a rectangle whose sides are equal, so it passes the same number twice to the parent's initializer:

```python
class Rectangle:
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height


class Square(Rectangle):
    def __init__(self, side):
        super().__init__(side, side)
```
step: `Square` defines no `area`, so it inherits the rectangle's. `Square(4).area()` computes `4 * 4`, which is `16`.
step: `isinstance(Square(4), Rectangle)` is `True`, so a `Square` can be passed to any function that expects a rectangle.

@mistakes
- Forgetting `super().__init__(...)` in a subclass `__init__`, so inherited attributes such as `name` do not exist and later code raises `AttributeError`.
- Using inheritance for a "has a" relationship (a `Car` inheriting from `Engine`), instead of storing an engine object as an attribute.
- Calling the parent method by mistake as `self.pay()` inside the overriding `pay`, which calls itself forever; use `super().pay()`.
- Writing `isinstance(Employee, m)` with the arguments reversed; the object comes first and the class second.

```python
class Parent:
    def __init__(self):
        self.a = 1

class Child(Parent):
    pass

class Other(Parent):
    def __init__(self):
        self.b = 2

c = Child()
o = Other()
```
choice*: `c.a` is `1`, because `Child` has no `__init__` and inherits the parent's.
choice*: `isinstance(o, Parent)` is `True`.
choice*: `o.a` raises `AttributeError`, because `Other.__init__` never calls the parent's `__init__`.
choice: `issubclass(Parent, Child)` is `True`.
choice: `o.a` is `1`, because Python always runs the parent's `__init__` first.

@practice code
prompt: Below is a class `Account`. Write `SavingsAccount(Account)` with `__init__(self, owner, balance, rate)` (store `rate`, a fraction such as `0.25`). Its `add_interest()` deposits `balance * rate` into the account (using the inherited `deposit`). Its `withdraw(amount)` charges a fee of `1`: it behaves like the parent's `withdraw` of `amount + 1`, so it raises `ValueError` (and changes nothing) if the balance does not cover the amount plus the fee. Do not change `Account`.
starter:
```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self.balance += amount

    def withdraw(self, amount):
        if amount <= 0 or amount > self.balance:
            raise ValueError("invalid withdrawal")
        self.balance -= amount


class SavingsAccount(Account):
    pass
```
tests:
```python
s = SavingsAccount("Ann", 100, 0.25)
assert s.owner == "Ann"
assert s.rate == 0.25
s.withdraw(3)
assert s.balance == 96
assert raises(ValueError, s.withdraw, 96)
assert s.balance == 96
s.add_interest()
assert s.balance == 120
a = Account("Bo", 50)
a.withdraw(10)
assert a.balance == 40
assert isinstance(s, Account)
t = SavingsAccount("Cy", 0, 0.5)
assert raises(ValueError, t.withdraw, 1)
```
model:
```python
class Account:
    def __init__(self, owner, balance=0):
        self.owner = owner
        self.balance = balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("deposit must be positive")
        self.balance += amount

    def withdraw(self, amount):
        if amount <= 0 or amount > self.balance:
            raise ValueError("invalid withdrawal")
        self.balance -= amount


class SavingsAccount(Account):
    def __init__(self, owner, balance, rate):
        super().__init__(owner, balance)
        self.rate = rate

    def add_interest(self):
        self.deposit(self.balance * self.rate)

    def withdraw(self, amount):
        super().withdraw(amount + 1)
```
hint: Call `super().__init__(owner, balance)` and then store the rate.
hint: `withdraw` can delegate: `super().withdraw(amount + 1)` already raises when the balance is too low, and it leaves the balance unchanged in that case.
solution: `add_interest` reuses the inherited `deposit` with `self.balance * self.rate`. The overriding `withdraw` adds the fee to the amount and hands the request to the parent, which performs the check and the subtraction. A withdrawal from an empty account is refused, because even the fee of `1` cannot be covered.

```python

    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

    def describe(self):
        return f"{type(self).__name__} {self.width}x{self.height}"


class Square(Rectangle):
    def __init__(self, side):
        super().__init__(side, side)
```
