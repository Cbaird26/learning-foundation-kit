@article
A model in a notebook helps nobody; a model behind a reliable service does. **Deployment** means making predictions available to the rest of a system, and the first design decision is when predictions are computed.

### Batch, online and streaming

**Batch prediction** runs on a schedule over many records at once, for example scoring every customer each night and storing the scores in a table. It is simple, cheap per prediction, easy to retry and to test, and has no strict latency requirement, but predictions are as stale as the last run and records that arrive later wait. **Online prediction** answers each request when it arrives, typically over a network call, so it can use fresh inputs, but it must be fast and always available. **Streaming prediction** processes a continuous flow of events with small delays. Choose the simplest option that meets the product's freshness need: if scores used by tomorrow's email campaign are good enough, batch is the right answer.

### Latency is a distribution

The **latency** of a request is the time from its arrival to its response. Averages hide the slow requests that users feel, so report **percentiles**: the $p$th percentile is a value that $p\%$ of requests do not exceed. With $n$ sorted measurements, the **nearest-rank** method takes the value at rank $\lceil p n / 100 \rceil$ (counting from 1). The names p50 (median), p95 and p99 are standard. A **service-level objective** (SLO) is a target such as "p95 below 100 ms".

```python
def percentile(values, p):
    """Nearest-rank percentile for an integer p between 1 and 100."""
    ordered = sorted(values)
    rank = (p * len(ordered) + 99) // 100     # integer form of ceil(p n / 100)
    return ordered[rank - 1]

lat = [12, 15, 11, 14, 13, 16, 12, 13, 15, 14,
       12, 18, 13, 14, 95, 12, 15, 13, 14, 250]
print(percentile(lat, 50), percentile(lat, 95), percentile(lat, 99))  # 14 95 250
print(sum(lat) / len(lat))                                            # 29.55
```

Here twenty requests have a median of 14 ms and a mean of 29.55 ms; the mean is more than double the median because two slow requests (95 and 250 ms) pull it up. The p99 is 250 ms. At scale, a user whose page needs several predictions will meet a p99 delay often, which is why tail latency (p95, p99) is what SLOs usually target.

### Throughput, concurrency and replicas

**Throughput** is the number of requests completed per second. **Little's law** relates it to the average number of requests being handled at once (the **concurrency**) $L$, the arrival rate $\lambda$ and the average time in the system $W$:

$$L = \lambda W .$$

At 200 requests per second with an average latency of 0.05 s, about $200 \times 0.05 = 10$ requests are in flight. If one replica of the service can run 4 requests at a time and you want it no more than 70% busy so that bursts do not queue (a planning assumption, not a law), each replica handles $4 \times 0.7 = 2.8$ requests, so you need $\lceil 10 / 2.8 \rceil = 4$ replicas.

### Batching

Accelerators do more work per second on a batch than on single inputs because the fixed cost of launching a computation is shared. Model a batch of $b$ inputs as taking $t(b) = a + c\,b$, with fixed overhead $a = 10$ ms and per-input cost $c = 2$ ms. Capacity is $b / t(b)$: for $b = 1$ it is $1/12$ per ms, or 83.3 requests per second, and for $b = 8$ it is $8/26$ per ms, or 307.7 per second. **Dynamic batching** collects requests for a short window and runs them together, which trades some latency (the wait for the batch to fill, plus a longer batch time) for throughput. The right batch size is the largest one whose worst-case latency still meets the SLO.

### Operating a deployed model

Version every model and keep the previous one ready for rollback; set timeouts and a fallback (a simple rule or the last good score) for when the model service fails; log inputs and outputs, with privacy controls, so that you can monitor them (next week); and test the service end to end with the same input validation as training.

title: Percentiles and a replica count
problem: Ten request latencies in milliseconds are 21, 18, 19, 25, 20, 22, 19, 80, 23 and 20. (a) Find the p50 and p90 by the nearest-rank method. (b) The service receives 60 requests per second with an average latency of 0.1 s, each replica handles 3 requests at a time, and you plan for 50% utilization. How many replicas do you need?
step: Sort the latencies: 18, 19, 19, 20, 20, 21, 22, 23, 25, 80.
step: For p50, the rank is $\lceil 0.50 \times 10 \rceil = 5$, so the p50 is the fifth value, 20 ms. For p90, the rank is $\lceil 0.90 \times 10 \rceil = 9$, so the p90 is 25 ms; only the very slowest request, 80 ms, lies above it.
step: By Little's law, the concurrency is $L = 60 \times 0.1 = 6$ requests in flight.
step: Each replica should hold at most $3 \times 0.5 = 1.5$ requests, so we need $\lceil 6 / 1.5 \rceil = 4$ replicas.
answer: p50 = 20 ms, p90 = 25 ms, and 4 replicas.
@mistakes
- Reporting only the mean latency; a few slow requests can ruin the user experience and barely move the mean.
- Running replicas at full utilization; as load approaches capacity, queues and tail latency grow quickly.
- Choosing online prediction when a nightly batch would meet the need, which adds cost and failure modes for no benefit.
- Averaging percentiles from several servers; compute percentiles from the merged measurements instead.

```python
import math

def replicas_needed(rps, avg_latency_s, concurrency_per_replica, max_utilization):
    """Replicas required to carry the average concurrency (at least one)."""
    in_flight = rps * avg_latency_s
    per_replica = concurrency_per_replica * max_utilization
    return max(1, math.ceil(in_flight / per_replica - 1e-9))
```
hint: Compute the in-flight requests, divide by the usable concurrency per replica, and round up after subtracting a tiny tolerance.
solution: Rounding up means 4.9999999 and 5.0000001 would give 5 and 6; subtracting `1e-9` before `ceil` removes that rounding noise so exact ratios such as the fourth test (12 divided by 2.4) give 5. The `max(1, ...)` keeps at least one replica when there is almost no traffic.

model:
```python
def best_batch_size(overhead_ms, per_item_ms, arrival_per_s, slo_ms, max_batch):
    """Largest batch size whose wait plus run time meets the latency target."""
    best = 0
    for b in range(1, max_batch + 1):
        wait = (b - 1) * 1000 / arrival_per_s
        run = overhead_ms + per_item_ms * b
        if wait + run <= slo_ms:
            best = b
    return best
```
hint: Try every batch size from 1 to `max_batch`, compute the wait and the run time, and remember the largest one that meets the SLO.
solution: The worst-case latency grows with `b` (longer waiting and a longer batch), so the feasible sizes form a prefix of 1 to `max_batch`; scanning all of them and keeping the largest feasible one is simple and correct. The third test has no feasible size, and the fourth shows `max_batch` capping the answer.

model:
```python
def windowed_percentile(values, window, p):
    """Nearest-rank percentile of each consecutive window of values."""
    result = []
    for start in range(0, len(values), window):
        chunk = sorted(values[start:start + window])
        rank = (p * len(chunk) + 99) // 100
        result.append(chunk[rank - 1])
    return result
```
hint: Step through the list in jumps of `window`, sort each chunk, and use the integer form `(p * n + 99) // 100` of the ceiling for the rank.
solution: Integer arithmetic gives the ceiling of `p * n / 100` without floating-point error. A short final chunk is handled by using its own length, and an empty input produces an empty list because the range is empty.
