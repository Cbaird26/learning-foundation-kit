@article
A model is only as good as the data it is trained on, and data fails quietly. A column is renamed upstream, a sensor starts reporting temperatures in the wrong unit, a join drops half the rows. The code still runs; the model just gets worse. A **data pipeline** is the chain of steps that turns raw records into the tables a model trains and predicts on, and a **validation** step is a test that the data satisfies what the rest of the pipeline assumes.

### Stages and checks

A typical pipeline has these stages: **ingest** (read raw records), **clean** (fix or drop bad records), **transform** (compute features), **split** (train, validation, test) and **store** (write a versioned table, often in a feature store, a service that keeps feature definitions and values consistent between training and serving). Put a check at each boundary:

| check | question | example |
|---|---|---|
| schema | are the expected fields present with the right types? | `age` is an integer |
| range | are values plausible? | $0 \le \text{age} \le 120$ |
| completeness | how many values are missing? | at most 2% of `income` |
| uniqueness | are there duplicate records? | one row per `user_id` and day |
| distribution | does the batch look like the last one? | the mean is within a set band |

The last row is the subject of weeks 9 and 10; this week we write the first four.

### A validation function

Describe the **schema** as a dictionary from field name to the allowed type and range. The function below returns a list of error strings, which is better than raising on the first problem: one run then shows everything that is wrong.

```python
schema = {"age": (int, 0, 120), "income": (float, 0.0, 1e7)}

def validate_row(row, schema):
    """Return a list of error strings; an empty list means the row is valid."""
    errors = []
    for field, (typ, low, high) in schema.items():
        value = row.get(field)
        if value is None:
            errors.append(field + ": missing")
        elif not isinstance(value, (int, float)) or isinstance(value, bool):
            errors.append(field + ": not a number")
        elif typ is int and not isinstance(value, int):
            errors.append(field + ": not an integer")
        elif not low <= value <= high:
            errors.append(field + ": out of range")
    return errors

print(validate_row({"age": 34, "income": 52000.0}, schema))   # []
print(validate_row({"age": -2}, schema))
```

The second call prints `['age: out of range', 'income: missing']`. At the batch level you decide what to do: fail the pipeline, drop the bad rows, or alert and continue. A common rule is to compute the **fraction of bad rows** and fail when it exceeds a budget. If 3 of 4 rows are bad the budget of 5% is far exceeded, but a single bad row in 10,000 may just be dropped and logged.

### Leakage and splitting

**Data leakage** means the model sees, during training, information that will not be available at prediction time. A feature recorded after the outcome is the classic case. Leakage also comes from the split: if the same user appears in both training and test data, or if you shuffle time-ordered data at random, the test set no longer resembles the future. For data that arrive over time, split by time: train on records before a **cutoff** and evaluate on records at or after it. Two further traps: **duplicates** (the same record in both train and test inflates the score), and **train/serve skew**, where a feature is computed one way in the training pipeline and another way in the online service. Defend against skew by using one shared implementation of each transformation for both.

### What to log

Every pipeline run should record the row counts at each stage (for example 1,250 in, 50 duplicates removed, 1,200 out), the fraction missing for each field, and the version of the schema. A sudden change in those counts is often the first sign that something upstream changed.

@mistakes
- Shuffling time-ordered data into random train and test sets, so the model is evaluated on the "past" it has already seen.
- Checking only types and ignoring ranges: a temperature of 9999 is a valid float and an obviously wrong value.
- Raising an error on the first bad value, which hides the others and makes each fix a separate run.
- Computing a feature one way for training and another way in the online service (train/serve skew), so the model sees inputs in production that it never saw in training.

model:
```python
def validate_batch(rows, ranges, max_bad_fraction):
    """Fraction of bad rows and whether it is within the budget."""
    def is_bad(row):
        for field, (low, high) in ranges.items():
            value = row.get(field)
            if value is None or not low <= value <= high:
                return True
        return False

    bad = sum(1 for row in rows if is_bad(row))
    fraction = bad / len(rows)
    return fraction, fraction <= max_bad_fraction
```
hint: Write a small helper that says whether one row is bad, count the bad rows, and divide by the number of rows.
solution: A row is bad if any required field is missing, `None` or outside its inclusive range, so the helper returns as soon as it finds one problem. The fraction of bad rows is compared with the budget using `<=`; the last test checks that values equal to the bounds are valid.

model:
```python
def time_split(records, cutoff):
    """Split records into those before the cutoff and those at or after it."""
    train = [r for r in records if r[0] < cutoff]
    test = [r for r in records if r[0] >= cutoff]
    if not train or not test:
        raise ValueError("both parts must be nonempty")
    return train, test
```
hint: Use two list comprehensions with opposite conditions on the timestamp, then check that both lists have records.
solution: Records exactly at the cutoff belong to the test part, so the two comprehensions together cover every record once and none appears in both. Raising when a part is empty stops a pipeline from silently evaluating on nothing; the tests check both empty cases.

```python
def missing_rates(rows, fields):
    """Fraction of rows in which each field is absent or None."""
    rates = {}
    for field in fields:
        missing = sum(1 for row in rows if row.get(field) is None)
        rates[field] = missing / len(rows)
    return rates
```
hint: Use `row.get(field) is None`; note that the value 0 is present, not missing.
solution: `row.get(field)` returns `None` both for an absent key and for a stored `None`, so one test covers both. Testing `is None` rather than truthiness keeps a legitimate value of 0 from being counted as missing, which the third test checks.

@quiz mc
prompt: A pipeline computes the feature "average order value" in a nightly batch job for training, while the online service computes it inside the web application with slightly different rounding and a different handling of canceled orders. What is this problem called, and what is the standard defense?
choice*: Train/serve skew; use one shared implementation of the transformation for training and serving.
choice: Data leakage; split the data by time instead of at random.
choice: Concept drift; retrain the model every night.
choice: Overfitting; add regularization to the model.
hint: The problem is a mismatch between how a feature is computed in two places, not a property of the model or of the split.
solution: When the same feature is computed differently in training and in production, the model receives inputs in production that differ from what it learned from: train/serve skew. Sharing one implementation (or reading both from a single feature store) removes the mismatch. Leakage, concept drift and overfitting are different problems with different remedies.
