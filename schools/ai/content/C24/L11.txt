@article
Offline evaluation on a held-out set says a new model is better. Production says whether it is better where it matters: with live inputs, on the real system, for real users. Replacing the old model for everyone at once bets the whole product on the offline number. Safer rollout strategies expose the new model gradually, and each answers a different question.

### Three strategies

| strategy | what happens | what it tells you | risk to users |
|---|---|---|---|
| shadow | the new model receives live inputs and its outputs are logged, not used | does it run, how fast, how do its outputs compare with the old model's? | none |
| canary | a small share (say 5%) of traffic is served by the new model | do error rates, latency and guardrail metrics hold up? | small |
| A/B test | users are randomly split between old and new, and an outcome metric is compared | is the new model better for the business metric, and by how much? | moderate |

A typical path is shadow, then canary, then a larger A/B test. In a shadow test you can compute, for example, the fraction of requests where the two models' scores differ by more than a tolerance and the latency percentiles of the new model under real load, with no risk, but you learn nothing about user response. A **canary** is judged mostly by safety metrics, the **guardrail metrics** (errors, latency, complaints) that must not get worse. An **A/B test** measures the effect on the **primary metric** (clicks, conversions, losses).

### Randomization

For an A/B test to support a causal claim, assignment must be random with respect to everything that affects the outcome, and stable: a user should see the same variant every time. A common method hashes the user identifier together with an experiment name (a salt) and takes the remainder modulo 100 as a bucket; users in buckets below the treatment percentage get the new model. Changing the salt for a new experiment reshuffles users, so that one experiment's groups do not correlate with the next one's.

### The two-proportion z-test

Suppose variant A has $x_1$ successes among $n_1$ users and variant B has $x_2$ among $n_2$. Under the null hypothesis that both have the same rate, estimate that common rate by the pooled proportion $\hat{p} = (x_1 + x_2)/(n_1 + n_2)$. The test statistic is

$$z = \frac{\hat{p}_2 - \hat{p}_1}{\sqrt{\hat{p}(1 - \hat{p})\left(\frac{1}{n_1} + \frac{1}{n_2}\right)}},$$

where $\hat{p}_i = x_i/n_i$. For a two-sided test at the 5% level, reject the null when $|z| > 1.96$. For a canary that should only be rolled back if it is worse, use a one-sided test and a critical value such as 1.645.

```python
import math

def two_prop_z(x1, n1, x2, n2):
    """z statistic for the difference in rates of two groups."""
    p1, p2 = x1 / n1, x2 / n2
    pooled = (x1 + x2) / (n1 + n2)
    se = math.sqrt(pooled * (1 - pooled) * (1 / n1 + 1 / n2))
    return (p2 - p1) / se

print(round(two_prop_z(500, 5000, 560, 5000), 3))   # 1.949
```

### How many users?

Before the test, decide the smallest effect worth detecting. To detect an absolute difference $\delta$ from a baseline rate $p$ with a two-sided 5% test and 80% power, a standard approximation gives, per group,

$$n \approx \frac{2\,(z_{\alpha/2} + z_{\beta})^2\, p(1 - p)}{\delta^2}, \qquad z_{\alpha/2} = 1.96,\ z_\beta = 0.84 .$$

For $p = 0.10$ and $\delta = 0.01$: $n \approx 2(2.8)^2(0.09)/0.0001 = 14{,}112$ users per group. Halving $\delta$ quadruples $n$.

### Pitfalls

**Peeking**: checking the result every day and stopping at the first $|z| > 1.96$ makes false positives far more frequent than 5%; fix the sample size in advance or use a method designed for sequential looks. **Many metrics**: with 20 independent metrics, one will look significant by chance, so name one primary metric first. **Interference and novelty**: users in the two groups may affect each other, and a new model may get attention only because it is new, so run long enough to see stable behavior. **Statistical and practical significance** differ: a significant 0.01% gain may not justify the cost of a new model.
@example
title: Reading an A/B test
problem: Variant A (the old model) converts 500 of 5,000 users and variant B (the new model) converts 560 of 5,000. Compute the z statistic and decide at the two-sided 5% level.
step: The rates are $\hat{p}_1 = 500/5000 = 0.100$ and $\hat{p}_2 = 560/5000 = 0.112$, so the difference is $0.012$.
step: The pooled proportion is $\hat{p} = 1060/10000 = 0.106$.
step: The standard error is $\sqrt{0.106 \times 0.894 \times (1/5000 + 1/5000)} = \sqrt{0.094764 \times 0.0004} = \sqrt{3.79 \times 10^{-5}} \approx 0.00616$.
step: Then $z = 0.012/0.00616 \approx 1.95$.
step: The critical value is 1.96 and $1.95 < 1.96$, so the result is just short of significance. Neither declare a win nor a tie: the sample size was planned for a larger effect; collect the pre-planned amount of data rather than stopping now.
answer: $z \approx 1.95$, not significant at the 5% level; the evidence is inconclusive.
@mistakes
- Stopping an A/B test as soon as the result looks significant; the false-positive rate is then well above the nominal 5%.
- Letting users choose their variant or assigning by an attribute such as region, so that the groups differ in more than the model.
- Testing a dozen metrics and reporting the one that moved; choose the primary metric before the test.
- Skipping the shadow and canary stages and discovering a crash or latency problem when half of the users are on the new model.

model:
```python
import math

def canary_decision(canary_errors, canary_n, base_errors, base_n, z_crit, min_n):
    """Roll back on a significantly higher error rate, else promote when enough data."""
    p1 = base_errors / base_n
    p2 = canary_errors / canary_n
    pooled = (base_errors + canary_errors) / (base_n + canary_n)
    if pooled in (0, 1):
        z = 0.0
    else:
        se = math.sqrt(pooled * (1 - pooled) * (1 / base_n + 1 / canary_n))
        z = (p2 - p1) / se
    if z > z_crit:
        return "rollback"
    if canary_n >= min_n:
        return "promote"
    return "continue"
```
hint: Compute the z statistic with the guard for a pooled rate of 0 or 1, then test for rollback first, then for enough data to promote.
solution: Rollback is checked first, so a clearly worse canary is stopped even before it has `min_n` requests (the last test). Without a significant increase, the canary is promoted only after enough traffic; a small canary with too little data keeps running (the third and fifth tests). Zero errors in both groups would otherwise divide by zero, which the fourth test covers.

model:
```python
def in_treatment(user_id, salt, percent):
    """Deterministic assignment: the same user and salt always give the same answer."""
    text = salt + ":" + str(user_id)
    h = 0
    for ch in text:
        h = (h * 31 + ord(ch)) % 1000003
    return h % 100 < percent
```
hint: Compute the rolling checksum of the text exactly as described, then compare the bucket with `percent`.
solution: Hashing the identifier with the salt gives each user a fixed pseudo-random bucket, so assignment is stable across requests and roughly uniform, and a different salt gives a different split. Using `bucket < percent` makes 0 percent select nobody and 100 percent select everybody, as the tests check.

model:
```python
def shadow_report(old_scores, new_scores, tol):
    """Agreement and difference statistics between two logged score lists."""
    if not old_scores or len(old_scores) != len(new_scores):
        raise ValueError("need two nonempty lists of equal length")
    diffs = [abs(a - b) for a, b in zip(old_scores, new_scores)]
    agree = sum(1 for d in diffs if d <= tol) / len(diffs)
    mean_d = sum(diffs) / len(diffs)
    return agree, mean_d, max(diffs)
```
hint: Compute the list of absolute differences first; the three results are all simple summaries of it.
solution: All three numbers come from the list of absolute differences: the share at or below the tolerance, the mean, and the maximum. A shadow test lets you check them on live traffic with no user impact, and large disagreement on a few requests is a reason to inspect those inputs.
