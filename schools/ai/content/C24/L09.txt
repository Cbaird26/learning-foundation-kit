@article
A deployed model fails differently from ordinary software. A web service that breaks returns errors; a model that breaks keeps returning answers, just worse ones. Nothing crashes, so someone must look. **Monitoring** is the continuous measurement of a running system, and **alerting** is the rule that decides when a person is called.

### Four layers of metrics

| layer | examples | what it catches | what it misses |
|---|---|---|---|
| system | latency percentiles, error rate, memory | outages, slowdowns | bad predictions from a healthy service |
| data | fraction of missing values, ranges, new categories | broken upstream pipelines | changes that keep values in range |
| model | distribution of scores, fraction predicted positive | shifts in behavior | which side is right |
| business | conversions, complaints, losses | the outcome that matters | slow, noisy, hard to attribute |

No single layer is enough. Data and model metrics need no labels, so they are available at once, and they are early warnings. **Accuracy** needs the true label, which often arrives late: whether a loan defaults is known after months, whether a recommendation was good after a click or never. When labels are **delayed**, track accuracy by cohort (the predictions of one week, evaluated when their labels arrive), and use label-free metrics as proxies in the meantime.

### Baselines and control limits

An alert needs a baseline for "normal". Collect a metric's values over a healthy period, for example the daily fraction of predictions that are positive, and compute their mean $\mu$ and sample standard deviation $s$. **Control limits** at $n$ standard deviations are $\mu \pm n s$; a new value outside them is an alert. The **z-score** $z = (x - \mu)/s$ says how many standard deviations a value is from the baseline. For five baseline days $0.10, 0.12, 0.11, 0.09, 0.13$ the mean is $0.11$, $s \approx 0.0158$, and 3-sigma limits are $[0.063, 0.157]$. A day at $0.14$ has $z \approx 1.9$ and is normal; a day at $0.19$ has $z \approx 5.1$ and fires.

### Smoothing and persistence

A metric computed over a small number of requests is noisy, and alerting on every spike teaches people to ignore the alerts (**alert fatigue**). Two simple tools reduce noise. An **exponentially weighted moving average** (EWMA) smooths a series with $s_t = \alpha x_t + (1 - \alpha) s_{t-1}$, where $0 < \alpha \le 1$ sets how quickly old values fade. And a **persistence rule** fires only when the metric violates its limit for $k$ consecutive periods.

```python
def ewma(values, alpha):
    """Exponentially weighted moving average, starting from the first value."""
    s = values[0]
    smoothed = [s]
    for x in values[1:]:
        s = alpha * x + (1 - alpha) * s
        smoothed.append(s)
    return smoothed

print(ewma([10, 10, 10, 20], 0.5))   # [10, 10.0, 10.0, 15.0]
```

### Service-level objectives and error budgets

An **SLO** states a target, for instance "99.9% of requests succeed within 100 ms over 30 days". The complement, $1 - \text{SLO}$, is the **error budget**: with 1,000,000 requests the budget is $1{,}000$ failed requests. The fraction of the budget left is $1 - \text{failures}/\text{budget}$; spending it quickly is a signal to slow down releases and fix reliability.

### Good alerts

A useful alert is **actionable** (someone knows what to do), **specific** (it points to a metric and a segment, not just "model bad") and **rare** enough to be read. Every alert should link to a runbook: what the metric means, how to check it and how to roll back. Keep a dashboard for exploration and reserve pages for conditions that need a person now.

title: Control limits and a persistence rule
problem: The daily fraction of missing `income` values has a healthy baseline of $0.02, 0.03, 0.01, 0.02, 0.02$. Compute the 3-sigma upper limit, then decide whether the next three days at $0.05, 0.06, 0.07$ trigger an alert under a rule that requires the limit to be exceeded on 2 consecutive days.
step: The baseline mean is $\mu = 0.10/5 = 0.02$. The deviations are $0, 0.01, -0.01, 0, 0$, whose squares sum to $0.0002$.
step: The sample variance is $0.0002/4 = 0.00005$, so $s \approx 0.00707$. The 3-sigma upper limit is $\mu + 3s = 0.02 + 0.02121 = 0.04121$.
step: The first day, $0.05$, exceeds $0.0412$, so it is a violation, but the rule needs 2 in a row, so no alert yet.
step: The second day, $0.06$, also exceeds the limit: two consecutive violations, so the alert fires on day 2 (and stays on for day 3 at $0.07$).
answer: Upper limit about 0.0412; the alert fires on the second day.
@mistakes
- Alerting on raw spikes of a noisy metric, which trains people to ignore alerts; smooth, aggregate over enough requests, or require persistence.
- Watching only system metrics: a model that returns confident nonsense has perfect latency and error rate.
- Computing accuracy on whatever labels have arrived without grouping by prediction date, so late labels bias the number.
- Setting limits from a baseline that already contains the incident, or too short to show the weekly pattern.

model:
```python
def first_alert(values, threshold, k):
    """Index where the metric has been below threshold k times in a row."""
    run = 0
    for i, x in enumerate(values):
        run = run + 1 if x < threshold else 0
        if run >= k:
            return i
    return -1
```
hint: Keep a counter of the current run of low values; reset it to zero whenever a value is not low.
solution: The counter grows on each low value and resets on any other, so it reaches `k` exactly at the `k`th consecutive low value. Values equal to the threshold reset the run (fifth test), and the second test shows that a run broken by 0.9 must restart.

model:
```python
import math

def flag_outliers(baseline, new_values, n_sigma):
    """Indices of new values outside mean +/- n_sigma sample std."""
    n = len(baseline)
    if n < 2:
        raise ValueError("need at least two baseline values")
    mean = 0.0
    for x in baseline:
        mean += x
    mean /= n
    var = 0.0
    for x in baseline:
        var += (x - mean) ** 2
    std = math.sqrt(var / (n - 1))
    low, high = mean - n_sigma * std, mean + n_sigma * std
    return [i for i, x in enumerate(new_values) if x < low or x > high]
```
hint: Compute the baseline mean, then the sum of squared deviations divided by $n - 1$, and compare each new value with the two limits.
solution: The limits depend only on the baseline, so compute them once and then scan the new values. Dividing by $n - 1$ makes this the sample standard deviation, which is slightly larger than the population version and gives wider limits. With 3 sigma the value 0.54 is inside but with 2 sigma it is outside (third and fourth tests).

model:
```python
def rolling_accuracy(pairs, window):
    """Accuracy over the latest `window` labeled predictions, at each label."""
    correct = []
    result = []
    for pred, label in pairs:
        if label is None:
            continue
        correct.append(1 if pred == label else 0)
        recent = correct[-window:]
        result.append(sum(recent) / len(recent))
    return result
```
hint: Keep a list of 1s and 0s for the labeled pairs only, and average its last `window` entries after each new label.
solution: Skipping unlabeled pairs means the window counts only labeled examples. Slicing `correct[-window:]` takes fewer entries at the start, which is why the first outputs average fewer than `window` values. Integer sums make the results exact for the tests that compare lists directly.
