@article
A model that trains without errors can still be wrong. A feature function that divides by a standard deviation of zero, a wrapper that accepts a row with the wrong number of columns, a gradient with a sign error: none of these crash, and each quietly lowers the quality of the model. **Tests** are small programs that check that code does what you intend, and they are the cheapest way to catch these failures. Machine learning code is harder to test than ordinary code because the outputs are numbers with rounding error and often depend on random seeds, so tests must use tolerances and fixed seeds.

### Kinds of tests

| kind | what it checks | example |
|---|---|---|
| unit test | one function on a known input | `standardize([2, 4, 6])` has mean 0 |
| edge-case test | boundaries and degenerate inputs | an empty list, a constant column, one example |
| property test | a rule that holds for many inputs | the output has the same length as the input |
| invariance test | the output does not change under an irrelevant change | shuffling the rows does not change a mean |
| regression test | the output matches a stored, trusted value | the model's score on a fixed batch is 0.7312 |
| integration test | several parts work together | raw rows go through the pipeline and the model without error |

Data tests (week 2) check the data; the tests of this week check the code.

### Testing a transformation

The **standardization** of values $x_1, \dots, x_n$ is $z_i = (x_i - \mu)/\sigma$, where $\mu$ is the mean and $\sigma$ the population standard deviation. Two mathematical facts become tests: the standardized values have mean 0 and standard deviation 1. A third test is an edge case: when every value is equal, $\sigma = 0$ and the formula divides by zero, so you must decide what to return (here zeros).

```python
import math

def standardize(values):
    """Return (x - mean) / std for each value; zeros if std is 0."""
    n = len(values)
    mean = sum(values) / n
    std = math.sqrt(sum((x - mean) ** 2 for x in values) / n)
    if std == 0:
        return [0.0] * n
    return [(x - mean) / std for x in values]

z = standardize([2.0, 4.0, 6.0, 8.0])
assert abs(sum(z) / len(z)) < 1e-9                       # mean is 0
assert abs(sum(v * v for v in z) / len(z) - 1) < 1e-9    # variance is 1
assert standardize([3.0, 3.0, 3.0]) == [0.0, 0.0, 0.0]   # constant column
assert len(standardize([1.0])) == 1                      # one example
```

Notice that the float checks use a **tolerance** (`< 1e-9`) rather than `==`: computed floats differ from exact values in their last digits, and a different Python or machine can change those digits.

### Testing gradients

A hand-derived gradient is a common source of silent bugs. The **central finite difference** $\dfrac{f(x + h) - f(x - h)}{2h}$ approximates the derivative with error of order $h^2$, so for a small $h$ such as $10^{-5}$ it should match the analytic gradient to about six digits. This gradient check is a regression guard for every hand-written backward pass.

### Testing a model wrapper

Production code usually wraps a trained model in a function or class that validates its input, calls the model and post-processes the result. Test the wrapper separately from the model by giving it a tiny stand-in model, such as a function that sums its inputs. Check that it rejects rows of the wrong length, rejects missing values, returns the same output when called twice with the same input (determinism), and keeps outputs in their valid range (a probability must lie in $[0, 1]$).

### Two more habits

A **behavioral test** states how the model should respond to a change in the input: raising a house's floor area while holding the rest fixed should not lower the predicted price. And an **overfit-one-batch test** trains on eight examples for a few hundred steps and asserts that the training loss falls near zero: if it does not, the training loop, the loss or the gradients are broken, and no amount of data will fix that. Run all tests automatically in a test runner on every change.
@example
title: Finding a bug with an edge-case test
problem: A function scales a list to the range $[0, 1]$: `scale01(v)` returns `[(x - lo) / (hi - lo) for x in v]` with `lo = min(v)` and `hi = max(v)`. Design tests that expose a bug, then fix it.
step: Typical case: `scale01([2, 4, 6])` should be `[0.0, 0.5, 1.0]`; this passes, because $(4 - 2)/(6 - 2) = 0.5$.
step: Property test: for any input, every output lies in $[0, 1]$ and the minimum maps to 0 and the maximum to 1. This also passes on varied inputs.
step: Edge case: a constant column such as `[5, 5, 5]` has `lo == hi`, so the denominator is $0$ and the call raises `ZeroDivisionError`. This test fails and exposes the bug.
step: Fix: decide a rule (return zeros for a constant column), add `if hi == lo: return [0.0] * len(v)`, and keep the constant-column test so the bug cannot return.
answer: The constant-column edge case raises `ZeroDivisionError`; guarding `hi == lo` fixes it, and the test stays as a regression test.
@mistakes
- Comparing computed floats with `==`: use `abs(a - b) < tol`, with a tolerance sized to the numbers involved.
- Testing only typical inputs: most bugs live at the edges (empty input, one example, a constant column, a missing value).
- Testing with random data and no seed, so a failure cannot be reproduced.
- Never checking a hand-written gradient numerically; a sign error or a missing factor trains slowly and silently.

model:
```python
def gradient_matches(f, grad_f, point, h=1e-5, tol=1e-6):
    """True if grad_f agrees with central finite differences of f."""
    analytic = grad_f(point)
    for i in range(len(point)):
        up = list(point)
        down = list(point)
        up[i] += h
        down[i] -= h
        numeric = (f(up) - f(down)) / (2 * h)
        if abs(numeric - analytic[i]) > tol:
            return False
    return True
```
hint: For each index, make two copies of the point, one with `h` added and one with `h` subtracted at that index only.
solution: The central difference at coordinate `i` moves only that coordinate by plus and minus `h`, so it approximates the partial derivative; comparing it with `grad_f` coordinate by coordinate catches a wrong term (the second test), a wrong sign (the third) and, with copies, leaves the caller's list unchanged (the fourth).

model:
```python
class SafeModel:
    """Validate rows, call the model and clip its output to [0, 1]."""

    def __init__(self, model, n_features):
        self.model = model
        self.n_features = n_features

    def predict(self, row):
        if len(row) != self.n_features:
            raise ValueError("wrong number of features")
        for v in row:
            if v is None or v != v:
                raise ValueError("missing value")
        return min(1.0, max(0.0, self.model(row)))
```
hint: Check the length first, then each value (`v is None or v != v` catches both kinds of missing value), then clip with `min` and `max`.
solution: A NaN is the only float that differs from itself, so `v != v` detects it; testing `None` first avoids comparing `None` with itself later. Clipping with `min(1.0, max(0.0, y))` keeps outputs in range, and the tests cover the three error cases, both ends of the range and determinism.

model:
```python
import random

def is_order_invariant(f, items, seed, trials=5):
    """True if f gives the same value for shuffled copies of items."""
    rng = random.Random(seed)
    expected = f(list(items))
    for _ in range(trials):
        copy = list(items)
        rng.shuffle(copy)
        if abs(f(copy) - expected) > 1e-9:
            return False
    return True
```
hint: Make a fresh copy for every trial, shuffle it with one generator created from the seed, and compare `f` of the copy with `f(items)`.
solution: One `random.Random(seed)` makes the shuffles repeatable, and copying keeps the caller's list unchanged (the last test). A function that reads a particular position, such as the first element, gives different values on some shuffles, so with enough trials the check returns `False`.

List five tests you would write, naming for each the kind of test (unit, edge case, property, invariance, regression) and what it asserts.

solution: (1) Unit test: on a column `[2, 4, 6, 8]` the transformed values equal the hand-computed z-scores within a tolerance. (2) Property test: the transformed training data has column means near 0 and standard deviations near 1, and the output has the same number of rows and columns as the input. (3) Edge case: a constant column does not raise and gives zeros; also a table with one row. (4) Invariance test: shuffling the rows before fitting gives the same mean and standard deviation. (5) Regression or leakage test: fit the scaler on the training rows only and assert that transforming test rows with it does not change the stored mean and standard deviation, and that the same function is used in training and serving; a stored expected output for a fixed small table guards later changes.
