@article
A hospital releases a table with no names: age, ZIP code, sex and diagnosis for every patient. A reporter knows that a local official is a 58-year-old woman who lives in a particular ZIP code, and finds that exactly one row matches. She now knows the official's diagnosis. No identifier was released, yet the person was identified. Removing names is not the same as protecting people.

### Kinds of attributes

Privacy work starts by classifying the columns:

- **Direct identifiers** point to one person: name, email address, national ID number.
- **Quasi-identifiers** do not identify anyone alone but do in combination with each other or with outside data: age, ZIP code, sex, job title, birth date.
- **Sensitive attributes** are the facts that would harm someone if linked to them: a diagnosis, income, religion.

Under the European Union's General Data Protection Regulation (Regulation (EU) 2016/679), **personal data** is any information relating to an identified or identifiable person, which is a broad definition that includes quasi-identifiers. Laws differ by country and change, so for any real data set check the rules that currently apply and consult the people responsible for compliance. The statistical ideas below hold whatever the law says.

### Pseudonymization is not anonymization

**Pseudonymization** replaces direct identifiers with codes (`p1`, `p2`, ...) while keeping the rest of the table. The same person keeps the same code, so rows can be linked, and anyone with the key, or with outside data matching the quasi-identifiers, can undo it. It lowers risk but the data remain personal data. **Anonymization** means that people can no longer be identified by any reasonably likely means, which is a much higher bar and is hard to guarantee.

### k-anonymity

A table is **k-anonymous** (Sweeney, 2002) with respect to chosen quasi-identifiers if every combination of their values occurs in at least $k$ rows, so that each person hides among at least $k - 1$ others. The $k$ of a table is the size of its smallest group. Consider six rows with (age, ZIP prefix): $(23, 021)$, $(27, 021)$, $(34, 021)$, $(36, 021)$, $(35, 946)$, $(38, 946)$. Every exact (age, ZIP) pair is unique, so $k = 1$. **Generalization** coarsens values: replacing age by a 10-year band gives the groups (20 to 29, 021) with 2 rows, (30 to 39, 021) with 2 and (30 to 39, 946) with 2, so $k = 2$. **Suppression** removes the rows that are still in groups smaller than $k$ (or blanks their quasi-identifiers).

```python
def generalize_age(age, width):
    low = (age // width) * width
    return f"{low}-{low + width - 1}"

print(generalize_age(34, 10), generalize_age(67, 20))
```

This prints `30-39 60-79`. There is a cost: wider bands lose information, and the choice of bands is a trade-off between privacy and usefulness. And k-anonymity has limits. If all $k$ rows in a group share the same diagnosis, an attacker learns the diagnosis without singling anyone out, and an attacker with other data can sometimes narrow the group further.

### Differential privacy

**Differential privacy** (Dwork, McSherry, Nissim and Smith, 2006) gives a guarantee about a *computation* rather than a table: the result of a query changes very little, in a precise probabilistic sense controlled by a parameter $\varepsilon$, whether or not any one person's record is in the data. A standard tool is the **Laplace mechanism**: to answer a numeric query whose value changes by at most $\Delta$ (its **sensitivity**) when one person's record is added or removed, add noise drawn from the Laplace distribution with scale $b = \Delta/\varepsilon$. A counting query has $\Delta = 1$. With $\varepsilon = 0.5$ the noise scale is $b = 2$; a smaller $\varepsilon$ means more noise and stronger privacy. The trade-off is again between privacy and accuracy, and repeated queries spend the budget: the $\varepsilon$ values of separate answers add up.

### Responsible practice

Privacy is mostly decided before any code runs. **Data minimization**: collect only the columns you need for the stated question. **Purpose limitation**: use data only for the purpose that people were told about. Also set a **retention period** after which data are deleted, limit access, keep the key that links pseudonyms apart from the data, and record all of this in the datasheet of week 11. Ask before collecting whether the benefit justifies the risk, and who could be harmed if the data leaked or were linked to other data.

@example
title: Raising k by generalizing
problem: Six rows have quasi-identifiers (age, ZIP prefix): (23, 021), (27, 021), (34, 021), (36, 021), (35, 946), (38, 946). Compute the k of the table, then the k after replacing ages by 10-year bands.
step: Count the rows for each exact combination. All six pairs differ, so every group has size 1 and $k = 1$: each row is unique and could be re-identified by someone who knows a person's age and ZIP prefix.
step: Replace each age by its band: 23 and 27 give 20-29; 34, 36, 35 and 38 give 30-39.
step: Count the new groups. (20-29, 021) has 2 rows: ages 23 and 27. (30-39, 021) has 2 rows: 34 and 36. (30-39, 946) has 2 rows: 35 and 38.
step: The smallest group has 2 rows, so $k = 2$. The data are now 2-anonymous, at the cost of knowing an age only to within ten years. If a seventh row, (41, 946), were added, its group (40-49, 946) would have size 1 and $k$ would drop back to 1 unless that row were suppressed.
answer: $k = 1$ before and $k = 2$ after generalizing.

@mistakes
- Believing that removing names makes a data set anonymous, when quasi-identifiers can single people out.
- Treating pseudonyms as anonymous: the same code links all of a person's rows, and outside data can reverse it.
- Choosing $k$ by the groups that exist today and forgetting that new rows, or other data sets, can break it.
- Collecting every column "in case it is useful" instead of the columns the question needs.

tests:
```python
rows = [
    {"age": "40-49", "zip": "100"}, {"age": "40-49", "zip": "100"},
    {"age": "40-49", "zip": "100"}, {"age": "50-59", "zip": "100"},
    {"age": "50-59", "zip": "100"}, {"age": "50-59", "zip": "200"},

extra = rows + [{"age": "60-69", "zip": "200"}]
assert k_anonymity(extra, ["age", "zip"]) == 1
assert k_anonymity([], ["age"]) == 0

```
model:
```python
def k_anonymity(rows, qi):
    """Size of the smallest group of rows sharing the same quasi-identifiers."""
    counts = {}
    for row in rows:
        key = tuple(row[c] for c in qi)
        counts[key] = counts.get(key, 0) + 1
    return min(counts.values()) if counts else 0
```
hint: Count the rows for each tuple of quasi-identifier values and return the smallest count.
solution: Rows are grouped by the tuple of their quasi-identifier values, and the k of the table is the size of the smallest group. Checking fewer columns can only merge groups, which is why the tests with one column give the same or larger k than with two.

tests:
```python
rows = [
    {"id": 1, "g": "x"}, {"id": 2, "g": "y"}, {"id": 3, "g": "x"},
    {"id": 4, "g": "z"}, {"id": 5, "g": "x"}, {"id": 6, "g": "y"},
]
out = suppress_small_groups(rows, ["g"], 2)
assert [r["id"] for r in out] == [1, 2, 3, 5, 6]
out = suppress_small_groups(rows, ["g"], 3)
assert [r["id"] for r in out] == [1, 3, 5]
assert suppress_small_groups(rows, ["g"], 1) == rows
assert suppress_small_groups(rows, ["g"], 4) == []
assert len(rows) == 6
```
model:
```python
def suppress_small_groups(rows, qi, k):
    """Keep only rows in groups of at least k rows."""
    counts = {}
    for row in rows:
        key = tuple(row[c] for c in qi)
        counts[key] = counts.get(key, 0) + 1
    return [r for r in rows if counts[tuple(r[c] for c in qi)] >= k]
```
hint: Count the rows in each quasi-identifier group first, then keep the rows whose group count is at least `k`.
solution: Group sizes are computed over all the rows before any row is removed, and the final filter keeps the original order. Removing rows one at a time while counting would give wrong group sizes, which the case with `k = 3` would reveal.
