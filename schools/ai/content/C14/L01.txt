@article
A bike-share company wants to know whether warm weather brings more riders. Someone hands you a spreadsheet. Before you plot anything, you need to know what one row means, what each column holds, and whether the question can even be answered from this table. Data science is mostly this kind of careful, unglamorous work, and it is the foundation of every model you will train.

### The workflow

A data science project moves through stages, and it loops back often:

1. **Ask** a question the data could answer ("Do daily rides rise with temperature?").
2. **Acquire** the data: files, databases, logs, surveys.
3. **Wrangle** it: read it into a structure, then clean and reshape it (weeks 2 to 5).
4. **Explore** it with summary statistics and charts (weeks 6 to 8).
5. **Model or conclude**: build features and a predictor, or answer the question directly (week 9).
6. **Communicate and document**: say what you found, what the data cannot tell you, and how it was made (weeks 10 to 12).

Most real effort goes into stages 2 to 4. A model trained on a table you misread is wrong however good the model is.

### Tables: rows, columns and types

A **table** is a collection of **rows** (observations, also called records or examples) and **columns** (variables, also called fields or features). Here are four rows of bike-share data:

| day | station | rides | temp_c |
|---|---|---|---|
| Mon | Park | 120 | 18.5 |
| Mon | Dock | 80 | 18.5 |
| Tue | Park | 150 | 21.0 |
| Tue | Dock | 95 | 21.0 |

Its **shape** is the pair (number of rows, number of columns) $= (4, 4)$. In plain Python, the most direct representation is a **list of dictionaries**, one dictionary per row, keyed by column name:

```python
rows = [
    {"day": "Mon", "station": "Park", "rides": 120, "temp_c": 18.5},
    {"day": "Mon", "station": "Dock", "rides": 80, "temp_c": 18.5},
    {"day": "Tue", "station": "Park", "rides": 150, "temp_c": 21.0},
    {"day": "Tue", "station": "Dock", "rides": 95, "temp_c": 21.0},
]
shape = (len(rows), len(rows[0]))
rides = [r["rides"] for r in rows]
print(shape, sum(rides) / len(rides))
```

This prints `(4, 4) 111.25`. A second representation is a **dictionary of columns**, `{"rides": [120, 80, 150, 95], ...}`. It makes column-wise work (means, scaling) natural, while a list of rows makes row-wise work (filtering) natural. You will convert between them often. Libraries such as pandas wrap exactly this idea in a `DataFrame`; the browser-based exercises here build the operations by hand so that you know what a library call does.

### Variable types

The type of a column decides which operations make sense.

- **Numeric** variables are quantities: rides, temperature. Averages and differences are meaningful. They may be discrete (counts) or continuous (measurements).
- **Categorical** variables are labels: station, day. Counting and grouping are meaningful, averaging is not. An **ordinal** variable is categorical with an order (small, medium, large).
- Identifiers such as ZIP codes or user IDs are stored as digits but are labels: the average of two ZIP codes means nothing.

A common bug is storing a number as text, or a label as a number, so that a library silently does the wrong thing.

### Tidy data

A table is **tidy** (Wickham, 2014) when each variable is a column, each observation is a row, and each kind of observational unit has its own table. The bike-share table above is tidy: one row per (day, station). A "wide" table with columns `rides_mon`, `rides_tue` hides a variable (the day) inside its column names, so you cannot group or plot by day without first reshaping it. Week 5 teaches that reshaping.

### Asking what a row means

Always write down the **unit of observation**: here, one station on one day. The same column name can mean different things at different units, and a mean over rows is a mean over that unit. If the table also had a separate row for each hour, averaging `rides` over rows would give rides per hour, not per day. Write the question, the unit and the types down first, and every later step goes faster.

@example
title: Spotting a table that is not tidy
problem: A teacher stores exam results as a table with columns `student`, `math_2023` and `math_2024`, and two students, Ana (71, 78) and Bo (64, 70). Name the variables, say why the table is not tidy, and write the tidy version.
step: Identify the variables. There are three: the student, the year, and the math score. Each score belongs to one student in one year.
step: Find the problem. The year is a variable but it appears in the column names, and the score variable is spread across two columns. The unit of observation, one student in one year, is not one row.
step: Write one row per (student, year). The tidy table has columns `student`, `year`, `math`, and four rows: (Ana, 2023, 71), (Ana, 2024, 78), (Bo, 2023, 64), (Bo, 2024, 70).
step: Check the result by computing the mean score for 2024. In the tidy table it is the mean of the `math` values where `year` is 2024: $(78 + 70)/2 = 74$. In the wide table you had to know which column to use.
answer: Variables: student, year, math score. The tidy table has four rows and three columns.

@mistakes
- Treating an identifier (ZIP code, user ID) as a number: averaging or sorting it numerically has no meaning.
- Not writing down the unit of observation, so that a mean over rows is reported as if it were a mean over people or days.
- Reading `len(rows[0])` on an empty table: check for zero rows before taking a column count from the first row.
- Putting a variable (year, month) in the column names, which makes grouping and plotting by it awkward.

```python
def shape_of(rows):
    """Return (number of rows, number of columns) of a list-of-dicts table."""
    if not rows:
        return (0, 0)
    return (len(rows), len(rows[0]))
```

```python
    return None
```
tests:
```python
assert to_columns([{"a": 1, "b": "x"}, {"a": 2, "b": "y"}]) == {"a": [1, 2], "b": ["x", "y"]}
assert to_columns([]) == {}
assert list(to_columns([{"z": 1, "a": 2}]).keys()) == ["z", "a"]

assert to_columns([{"n": 5}, {"n": 7}, {"n": 9}])["n"] == [5, 7, 9]
```
model:
```python
def to_columns(rows):
    """Turn a list of row dictionaries into a dictionary of column lists."""
    if not rows:
        return {}
    return {name: [row[name] for row in rows] for name in rows[0]}
```
hint: Loop over the names in the first row, and for each name collect `row[name]` from every row.
solution: A dictionary comprehension over the first row's keys builds one list per column, and a list comprehension over the rows fills it in row order. The empty table needs its own case because there is no first row to take names from.

@quiz code
prompt: Write `column_kinds(rows)` for a table stored as a list of dictionaries with the same keys (no value is `None`). It returns a dictionary that maps each column name to `"numeric"` if every value in that column is an `int` or a `float` and not a `bool`, and to `"text"` otherwise. An empty table gives `{}`. For example, `column_kinds([{"a": 1, "b": "x"}])` returns `{"a": "numeric", "b": "text"}`.
starter:
```python
def column_kinds(rows):
    return None
```
tests:
```python
assert column_kinds([{"a": 1, "b": "x"}, {"a": 2.5, "b": "y"}]) == {"a": "numeric", "b": "text"}
assert column_kinds([{"a": 1}, {"a": "two"}]) == {"a": "text"}
assert column_kinds([{"f": True}, {"f": False}]) == {"f": "text"}
assert column_kinds([]) == {}
assert column_kinds([{"p": 0.5, "q": 3}]) == {"p": "numeric", "q": "numeric"}
```
model:
```python
def column_kinds(rows):
    """Classify each column as numeric or text."""
    if not rows:
        return {}
    kinds = {}
    for name in rows[0]:
        numeric = all(
            isinstance(r[name], (int, float)) and not isinstance(r[name], bool)
            for r in rows
        )
        kinds[name] = "numeric" if numeric else "text"
    return kinds
```
hint: Use `all(...)` over the rows for each column, and remember that in Python `True` is an instance of `int`.
solution: A column is numeric only if every value passes the test, so one stray string makes the whole column text. The `bool` exclusion matters because `isinstance(True, int)` is true, which the third test checks.
