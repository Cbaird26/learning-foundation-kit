@article
Training a model is a one-time cost. Serving it is a cost paid per token, forever, and it is dominated by something different from training: memory. When a model generates one token, it multiplies a vector by every weight matrix, which uses each weight once; the arithmetic is tiny compared with the effort of moving the weights from memory to the processor. Almost every efficiency technique in this lesson is a way to move fewer bytes.

### Two phases

Generating from a prompt has a **prefill** phase, which processes all prompt tokens in parallel (as in training, with the causal mask), and a **decode** phase, which produces one token at a time, each depending on the last. Prefill is typically limited by arithmetic; decode at small batch sizes is typically limited by **memory bandwidth**, because each step reads all the weights (and the cache, below) to produce a single token per sequence. If the weights occupy $W$ bytes and the memory bandwidth is $B$ bytes per second, one decode step takes at least $W/B$ seconds, so a single sequence cannot exceed $B/W$ tokens per second. For $W = 14$ GB and a hypothetical accelerator with $B = 1000$ GB/s that is about $71$ tokens per second; batching several sequences shares the weight reads among them.

### The key-value cache

In a causal transformer, the keys and values of earlier positions do not change when new tokens are appended: position $a$'s keys and values depend only on tokens up to $a$. So at each step we store them and compute the query, key and value only for the new token, attending over the stored keys and values. This **key-value cache** (KV cache) gives **exactly** the same outputs as recomputing everything, because no approximation is made, and it removes the repeated work of reprocessing the whole prefix at each step. Its price is memory. For $L$ layers, $n_{\text{kv}}$ key-value heads of width $d_{\text{head}}$, a sequence of $s$ tokens, a batch of $b$ sequences and $q$ bytes per number,

$$\text{KV bytes} = 2 \cdot L \cdot n_{\text{kv}} \cdot d_{\text{head}} \cdot s \cdot b \cdot q ,$$

where the 2 is for keys and values. With $L = 32$, $n_{\text{kv}} = 32$, $d_{\text{head}} = 128$, $s = 4096$, $b = 1$ and 16-bit numbers ($q = 2$) this is $2\,147\,483\,648$ bytes, that is 2 GiB ($1\text{ GiB} = 2^{30}$ bytes), or 0.5 MiB per token. The cache grows linearly with sequence length and batch size and can exceed the weights. Sharing keys and values among groups of query heads reduces it: multi-query attention (Shazeer, 2019) uses a single key-value head, and grouped-query attention (Ainslie and colleagues, 2023) uses an intermediate number; with 8 key-value heads instead of 32 the example above needs 0.5 GiB. Exact attention can also be computed without storing the full score matrix by an IO-aware algorithm (FlashAttention, Dao and colleagues, 2022).

### Quantization

Weights in 16-bit formats take $2$ bytes each, so $7\times 10^{9}$ parameters need $14$ GB; with 8-bit integers, 7 GB, and with 4-bit, 3.5 GB (ignoring the small cost of scales). **Symmetric integer quantization** stores, for a tensor $\mathbf{w}$, a scale $s = \max_i |w_i| / 127$ and integers $q_i = \operatorname{round}(w_i / s)$, and reconstructs $\hat w_i = s\, q_i$. The rounding error of each weight is at most $s/2$.

```python
def quantize_int8(w):
    """Symmetric per-tensor quantization of a list of floats."""
    scale = max(abs(x) for x in w) / 127
    q = [round(x / scale) for x in w]
    return q, scale

def dequantize(q, scale):
    return [scale * v for v in q]
```

A single outlier makes $s$ large and every other weight coarse, so practical methods use a scale per small group of weights, calibration data, or treat outliers separately. Quantization trades quality for memory, and how much quality is lost depends on the model, the bit width and the method; measure it on your task.

### Decoding

At each step the model gives logits $\mathbf{z}$ and the decoder picks a token. **Greedy** decoding takes the largest. **Temperature** $T$ samples from $\operatorname{softmax}(\mathbf{z}/T)$: $T < 1$ sharpens and $T > 1$ flattens. **Top-$k$** keeps the $k$ most probable tokens, renormalizes and samples. **Top-$p$** or **nucleus** sampling (Holtzman and colleagues, 2019) keeps the smallest set of tokens whose cumulative probability reaches $p$, so the number of candidates adapts to the model's confidence. **Beam search** keeps the $b$ most probable partial sequences. For open-ended text, the highest-likelihood sequences are often dull and repetitive, which motivated sampling methods; for tasks with one right answer, such as translation or code, likelihood-based search often works well. No decoding rule is best for all tasks.

**Speculative decoding** (Leviathan and colleagues, 2022; Chen and colleagues, 2023) uses a small draft model to propose $\gamma$ tokens, then the large model scores all of them in one pass and accepts a prefix by a rejection rule that leaves the output distribution **exactly equal** to that of the large model. If each proposed token is accepted with probability $\alpha$, independently, one large-model pass yields on average $(1 - \alpha^{\gamma+1})/(1 - \alpha)$ tokens; for $\alpha = 0.8$ and $\gamma = 4$ that is $3.36$.

@example
title: Memory of a key-value cache
problem: A model has $L = 40$ layers, 8 key-value heads of width 128, and runs a batch of 4 sequences of 2,048 tokens in 16-bit precision. How large is the KV cache in GiB?
step: Per token, keys and values: $2 \times 40 \times 8 \times 128 \times 2$ bytes $= 163{,}840$ bytes.
step: Tokens in the batch: $4 \times 2048 = 8192$.
step: Total: $163{,}840 \times 8192 = 1{,}342{,}177{,}280$ bytes; dividing by $2^{30}$ gives $1.25$ GiB.
answer: 1.25 GiB.

@example
title: Quantizing three weights
problem: Quantize $\mathbf{w} = (0.534, -2.54, 1.322)$ with symmetric 8-bit quantization and give the reconstruction.
step: The scale is $s = 2.54/127 = 0.02$.
step: The integers are $0.534/0.02 = 26.7 \to 27$, $-2.54/0.02 = -127$, and $1.322/0.02 = 66.1 \to 66$.
step: Reconstruction: $(0.54, -2.54, 1.32)$. The errors are $0.006$, $0$ and $0.002$, all below $s/2 = 0.01$.
answer: $q = (27, -127, 66)$ with scale $0.02$, reconstructed as $(0.54, -2.54, 1.32)$.

@mistakes
- Believing the KV cache approximates attention: it is exact, since earlier keys and values do not change under a causal mask.
- Ignoring the cache in memory planning: for long sequences and large batches it can exceed the weights.
- Mixing GB and GiB: $10^9$ bytes and $2^{30}$ bytes differ by about 7 percent, so state which you use.
- Assuming top-$p$ always keeps the same number of tokens: the size of the nucleus depends on how peaked the distribution is.

model:
```python
def top_p_filter(probs, p):
    """Nucleus filtering: keep the smallest top set with mass >= p."""
    order = sorted(range(len(probs)), key=lambda i: (-probs[i], i))
    keep = []
    mass = 0.0
    for i in order:
        keep.append(i)
        mass += probs[i]
        if mass >= p:
            break
    total = 0.0
    for i in keep:
        total += probs[i]
    kept = set(keep)
    return [probs[i] / total if i in kept else 0.0 for i in range(len(probs))]
```
hint: Sort indices by decreasing probability, accumulate until the running mass reaches `p`, and divide the kept probabilities by their sum.
solution: Sorting indices, not values, lets you map the result back to the original order. The loop adds a token before testing the mass, so at least one token is always kept and the first token that reaches `p` is included. The tie test, where two tokens have probability 0.4, checks that the lower index goes first. The last test uses `p = 1.0` and must keep every token, including when floating-point sums fall just short of 1.

@quiz self

solution: Translation: beam search or greedy, because a single best output exists and high-likelihood sequences are usually good; a risk is that beam search favors short or generic outputs, handled with length normalization. Story: top-p sampling with a moderate temperature, because many continuations are acceptable and likelihood-maximizing text tends to be bland and repetitive in open-ended generation; a risk is incoherence at high temperature or repeated phrases at low temperature, so I would tune both and inspect samples.
