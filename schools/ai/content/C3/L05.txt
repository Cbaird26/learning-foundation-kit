@article
**Git** is a distributed version control system: it records the history of a project so you can see what changed, return to an earlier state, and work in parallel with others. You will use it every day as an engineer.

### The data model: snapshots, not diffs

A Git repository stores **objects**, each named by a hash of its content (SHA-1 by default; the name is the same whenever the content is the same). A **blob** holds the bytes of one file. A **tree** lists file names and the blobs and subtrees they point to, so it describes one directory. A **commit** points to one tree (a complete **snapshot** of the project), to its **parent** commit(s), and holds the author, a timestamp and a message. A commit's name is a hash of all of that, so changing anything, including an ancestor, changes the name. The hash of a blob is `sha1("blob " + size + "\0" + content)`, which you can check with `git hash-object file`.

The history is therefore a chain of commits, each pointing back to its parent: `A <- B <- C`. A **branch** is just a movable name that points to a commit, and **HEAD** says which branch (or commit) you currently have checked out. `HEAD~1` means the first parent of `HEAD`, and `HEAD~2` its grandparent.

### Three places for your files

1. The **working tree**: the files you edit.
2. The **index** (staging area): the snapshot you are preparing for the next commit.
3. The **repository**: the committed history.

`git add file` copies the file's current content into the index. `git commit` turns the index into a new commit. If you edit a file after `git add`, the *staged* version is what gets committed; the later edit stays unstaged until you add it again.

### Everyday commands

```bash
git init -b main              # new repository whose first branch is main
git config user.name "Ana"    # identity recorded in commits
git config user.email "ana@example.com"
git status                    # what is modified, staged, untracked
git add notes.txt             # stage a file (git add . stages everything)
git commit -m "Add notes"     # record the staged snapshot
git log --oneline             # one line per commit, newest first
git diff                      # working tree vs index (unstaged changes)
git diff --staged             # index vs last commit (what you will commit)
git show HEAD                 # the latest commit and its changes
```

Undoing: `git restore file` discards unstaged edits to a file (permanently), and `git restore --staged file` unstages it while keeping the edits. `git commit --amend` replaces the latest commit (use it only before you share the commit). `git revert HASH` creates a **new** commit that undoes an old one, which is the safe way to undo shared history. `git rm file` and `git mv old new` stage a deletion or rename.

List patterns you never want to commit (build output, virtual environments, secrets) in a file named `.gitignore`, one pattern per line, such as `__pycache__/` or `.venv/`. It affects only untracked files: a file already committed stays tracked.

### Good commits

Commit small, coherent changes that each do one thing. Write the message as a short imperative summary line (about 50 characters, "Fix off-by-one in pager"), a blank line, then, if needed, a paragraph about *why*. Never commit passwords or API keys: removing them later does not remove them from history.

@example
title: A first repository
problem: Create a repository, commit `notes.txt`, edit it, and commit the edit. How many commits does `git log --oneline` show, and which `git diff` command shows the edit before you commit it?
step: `git init -b main` creates the repository. Create `notes.txt` with the line `hello`.
step: `git add notes.txt` stages it and `git commit -m "Add notes"` records commit 1, which has no parent (a root commit).
step: Append the line `world` to the file. `git status` lists `notes.txt` as modified but not staged, and `git diff` shows `+world`.
step: `git add notes.txt` then `git commit -m "Add second line"` records commit 2 whose parent is commit 1. Now `git diff` is empty, since the working tree matches the index.
step: `git log --oneline` shows two lines, newest first.
answer: Two commits; `git diff` shows the unstaged edit (`git diff --staged` after `git add`).
@example
title: What gets committed
problem: `a.txt` contains `v1` and is committed. You change it to `v2`, run `git add a.txt`, change it to `v3`, and run `git commit -m "Update a"`. What does the new commit contain, and what does `git status` show afterwards?
step: `git add` copied `v2` into the index. The later edit to `v3` changed only the working tree.
step: `git commit` snapshots the index, so the commit contains `v2`.
step: The working tree (`v3`) now differs from the commit, so `git status` lists `a.txt` under "Changes not staged for commit".
step: To record `v3` as well, run `git add a.txt` and commit again.
answer: The commit contains `v2`; `a.txt` is still modified (holding `v3`).
@mistakes
- Believing `git commit` saves the working tree: it saves only what was staged, so unstaged edits are left out.
- Running `git add .` without checking `git status`, and committing build output or secrets.
- Using `git restore file` on work you wanted to keep: it discards unstaged changes with no undo.
- Amending or rewriting commits that other people already have, which breaks their history.

import hashlib


def blob_hash(data):
    header = b"blob " + str(len(data)).encode() + b"\0"

@quiz code
prompt: A repository is stored as a dictionary `commits` mapping each commit id to a tuple `(parent, message)`, where `parent` is another id or `None` for the first commit. Write `history(commits, head)` that returns the list of messages from commit `head` back to the root, newest first, like `git log`. Example: with `{"a": (None, "init"), "b": ("a", "add x")}`, `history(commits, "b")` returns `["add x", "init"]`.
starter:
```python
def history(commits, head):
    pass
```
tests:
```python
c = {"a": (None, "init"), "b": ("a", "add x"), "c": ("b", "fix x")}
assert history(c, "c") == ["fix x", "add x", "init"]
assert history(c, "b") == ["add x", "init"]
assert history(c, "a") == ["init"]
assert history({"z": (None, "only")}, "z") == ["only"]
```
model:
```python
def history(commits, head):
    messages = []
    current = head
    while current is not None:
        parent, message = commits[current]
        messages.append(message)
        current = parent
    return messages
```
hint: Start at `head` and repeatedly follow the parent pointer.
hint: Stop when the parent is `None`; append each message as you visit its commit.
solution: Follow parent pointers from `head` until a commit with no parent, appending each message. The loop visits each ancestor exactly once, in newest-first order, which is the order of `git log` for a linear history.
