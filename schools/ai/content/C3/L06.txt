@article
A **branch** lets you work on a feature or a fix without disturbing the main line of development. In Git, branching is cheap because a branch is only a **name that points to a commit**; creating one writes a few bytes.

### Branches are pointers

Suppose `main` points to commit `C`, and `HEAD` points to `main`. `git branch feature` creates a second pointer to `C` and nothing else; `git switch feature` moves `HEAD` onto it (the older spelling is `git checkout feature`). Combine them with `git switch -c feature` (older: `git checkout -b feature`). Each new commit moves only the current branch's pointer forward, so the branches **diverge**:

```text
A --- B --- C            main
             \
              D --- E    feature
```

`git branch` lists local branches, `git branch -d feature` deletes a merged one, and `git log --oneline --graph --all` draws the picture above. Before switching, commit or stash your changes: Git refuses a switch that would overwrite uncommitted work.

### Merging

`git merge feature`, run while `main` is checked out, brings the work of `feature` into `main`. Which of two things happens depends on the graph.

**Fast-forward.** If `main` has not moved since `feature` was created, `main` is an ancestor of `feature`. There is nothing to combine, so Git just moves the `main` pointer forward to `feature`'s commit. No new commit is created. `git merge --no-ff feature` forces a merge commit anyway, which some teams prefer to keep the record of a feature branch.

**Three-way merge.** If both branches have new commits, Git finds their **merge base**, the most recent common ancestor (commit `C` in the diagram below, where `main` and `feature` split). It compares the base with each branch tip and combines the changes. When the two sides changed different parts of the files, Git produces a new **merge commit** with **two parents**:

```text
A --- B --- C --- F ----- M     main
             \          /
              D ------ E        feature
```

For each region of a file, the rule is: if only one side changed it relative to the base, take that side's version; if both sides made the same change, take it once; if both changed it differently, that is a **conflict** (next lesson).

### Reachability

A commit is **reachable** from a branch if you can get to it by following parent links. `git log feature` shows everything reachable from `feature`. `main..feature` means "reachable from `feature` but not from `main`" (the commits a merge would bring in). Commits that no branch or tag can reach are eventually garbage collected, though `git reflog` records where `HEAD` has been and can usually recover a lost branch for a while.

A typical workflow: create a branch per task, commit as you go, merge into `main` when the work is reviewed and tests pass, then delete the branch. Short-lived branches merge more easily than long-lived ones.

@example
title: A fast-forward merge
problem: `main` points to commit `B`. You run `git switch -c login`, make commits `C` and `D`, then `git switch main` and `git merge login`. What happens to `main`, and is a new commit created?
step: After the two commits on `login`, the graph is `A <- B <- C <- D` with `login` at `D` and `main` still at `B`.
step: `main` is an ancestor of `login`, since `B` is reachable from `D` by following parents.
step: Git can therefore move `main` forward to `D`. This is a fast-forward and it creates no new commit.
step: Afterwards both branches point to `D`. `git branch -d login` removes the now redundant name safely.
answer: `main` fast-forwards to `D`; no merge commit is created.
@example
title: Finding the merge base
problem: The parent links are `B -> A`, `C -> B`, `D -> C` (on `feature`) and `E -> B` (on `main`). Find the merge base of `D` and `E`, and say what `git merge feature` does from `main`.
step: Ancestors of `D` (including itself): `D`, `C`, `B`, `A`. Ancestors of `E`: `E`, `B`, `A`.
step: The common ancestors are `B` and `A`; the most recent one is `B`, so `B` is the merge base.
step: `main` (at `E`) is not an ancestor of `D`, so a fast-forward is impossible: both sides have unique commits.
step: Git compares `B` with `D` and with `E`, combines the changes, and records a merge commit with parents `E` and `D`.
answer: The merge base is `B`; Git makes a three-way merge commit.
@mistakes
- Forgetting which branch is checked out: `git merge feature` merges *into the current branch*, so switch to the receiving branch first.
- Thinking a branch copies files. It is only a pointer, which is why creating and deleting branches is instant.
- Deleting an unmerged branch with `git branch -D` and losing commits that no other branch reaches.
- Starting new work on `main` by accident; run `git status` or `git branch` to check the current branch before editing.

tests:
```python
g = {"A": [], "B": ["A"], "C": ["B"], "D": ["C"], "E": ["B"], "M": ["E", "D"]}
assert ancestors(g, "C") == {"A", "B", "C"}
assert ancestors(g, "A") == {"A"}
```

model:
```python
def ancestors(parents, commit):
    seen = set()
    stack = [commit]
    while stack:
        current = stack.pop()
        if current in seen:
            continue
        seen.add(current)
        stack.extend(parents[current])
    return seen
```
hint: Keep a set of visited commits and a stack of commits still to visit.
hint: Pop a commit, skip it if it was already seen, otherwise add it and push all its parents. A merge commit has two parents, and both must be followed.
solution: This is a graph search following parent links. The `seen` set stops a commit being processed twice (it can be reached along two paths after a merge), and the search ends when no parents remain. The time is linear in the number of commits and edges reached.

model:
```python
def reach(parents, commit):
    seen = set()
    stack = [commit]
    while stack:
        current = stack.pop()
        if current not in seen:
            seen.add(current)
            stack.extend(parents[current])
    return seen


def merge_base(parents, a, b):
    common = reach(parents, a) & reach(parents, b)
    for c in common:
        others = common - {c}
        if all(c not in reach(parents, o) for o in others):
            return c
    return None
```
hint: First compute the set of ancestors of each commit, and intersect the two sets.
hint: The merge base is the common ancestor that no other common ancestor descends from: nobody else in the set can reach it by following parents.
solution: Intersect the two ancestor sets to get all common ancestors. The best one is the one that is not an ancestor of any other common ancestor, because that makes it the most recent. When one commit is an ancestor of the other, the merge base is that commit (a fast-forward case).

tests:

```python
assert can_fast_forward(g, "B", "D") is True
```

model:
```python
def can_fast_forward(parents, current, other):
    seen = set()
    stack = [other]
    while stack:
        commit = stack.pop()
        if commit == current:
            return True
        if commit in seen:
            continue
        seen.add(commit)
        stack.extend(parents[commit])
    return False
```
hint: Walk back from `other` along parent links and look for `current`.
hint: If you reach `current`, return `True`; if the walk ends without meeting it, return `False`.
solution: A fast-forward needs `current` to be an ancestor of `other`, so search the ancestors of `other` for `current`. Moving the branch pointer forward is then enough, with no new commit.
