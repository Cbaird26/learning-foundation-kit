@article
Programs are wrong far more often than they are right on the first try. **Testing** finds bugs; **debugging** locates and removes them; **exceptions** let a program report and handle problems in a controlled way.

### Testing

A **test** runs the code on chosen inputs and compares the result with the expected one. Python's `assert` statement does the comparison: `assert fact(5) == 120` does nothing when true and raises `AssertionError` when false. Choose inputs from the *specification*, not the code:

- **Typical cases** of the common situation.
- **Boundaries**: the smallest and largest legal inputs, and values on either side of every threshold (a grade of 89 and 90).
- **Edge cases**: the empty list or string, one item, duplicates, negatives, zero.
- **Cases a plausible wrong solution gets wrong.**

*Black-box* tests are written from the specification only; *glass-box* tests also use knowledge of the code, for example making sure every branch and loop (zero, one and many passes) runs. Write the tests **before or while** writing the function, and rerun all of them after every change (**regression testing**). The standard library offers `unittest` for organized suites; the idea is the same.

```python
def test_fact():
    assert fact(0) == 1
    assert fact(1) == 1
    assert fact(5) == 120
```

### Exceptions

An **exception** is an object raised when something goes wrong. Common ones: `ValueError` (right type, bad value: `int("abc")`), `TypeError` (`"a" + 1`), `IndexError` (`[1][5]`), `KeyError` (`{}["x"]`), `ZeroDivisionError`, `AssertionError`. An uncaught exception ends the program with a **traceback**: read it from the bottom, where the exception type and message are, upward to the line that caused it.

```python
def parse(s):
    try:
        n = int(s)
    except ValueError:
        return -1
    else:
        return n * 2
    finally:
        print("done")
```

- The `try` block runs first. If it raises, Python looks for a matching `except`.
- `else` runs only if `try` raised nothing.
- `finally` **always** runs, even when a `return` is executed first, so it is the place to release resources.

Catch the **narrowest** exception you can handle. A bare `except:` or `except Exception:` hides bugs. To signal an error yourself, `raise ValueError("age must be positive")`. A function should document which exceptions it raises, as part of its specification. Python style prefers *asking forgiveness* (try, then handle the exception) over checking many conditions first, when the failure is rare.

### Defensive programming and assertions

Use exceptions to reject bad *inputs from outside*; use `assert` for conditions that should be impossible if the program is correct (internal checks, such as a loop invariant). Assertions may be disabled when Python runs with `-O`, so never use them to validate user input.

### Debugging

Debugging is the scientific method:

1. **Reproduce** the failure with the smallest input you can.
2. **Read** the error message and the traceback.
3. **Form a hypothesis** about where and why the value goes wrong.
4. **Test it**: print the values at a key point (or use the `pdb` debugger or an IDE) and compare with what you expected.
5. **Bisect**: check the state halfway through the program; the bug is in the half where it first becomes wrong.
6. **Fix one thing**, rerun all tests, and add a test that would have caught the bug.

Common bug types: off-by-one errors, wrong initial values, aliasing and mutation (week 5), and confusing `=` with `==`. Resist changing code at random.

@example
title: Order of try, except, else and finally
problem: What does this program print?

```python
def parse(s):
    try:
        n = int(s)
    except ValueError:
        return -1
    else:
        return n * 2
    finally:
        print("done")

print(parse("4"))
print(parse("x"))
```
step: `parse("4")`: `int("4")` succeeds, so `except` is skipped and `else` runs, evaluating `return 4 * 2` (the value `8` is ready to be returned).
step: Before the function actually returns, `finally` runs and prints `done`. Then the call returns `8`, which the outer `print` prints.
step: `parse("x")`: `int("x")` raises `ValueError`, so the `except` block returns `-1`. Again `finally` prints `done` first.
step: The outer `print` then prints `-1`.
answer:
```
done
8
done
-1
```

@example
title: Choosing test cases
problem: Choose tests for `second_largest(nums)`, which returns the second largest **distinct** value of a list and raises `ValueError` if there are fewer than two distinct values.
step: Typical case: `[3, 1, 4, 1, 5]` gives `4`.
step: Duplicates of the maximum: `[5, 5, 4]` gives `4`, not `5`. A solution that sorts and takes `[-2]` would fail here.
step: Boundary and error cases: `[2, 2]` and `[7]` have no second distinct value and must raise `ValueError`.
step: Negatives: `[-1, -2]` gives `-2`; this catches code that starts a maximum at `0`.
step: As assertions: `assert second_largest([5, 5, 4]) == 4` and `assert raises(ValueError, second_largest, [2, 2])`.

@mistakes
- Writing only tests that the function obviously passes: no empty input, no boundaries, no duplicates.
- Catching everything with a bare `except:`, which also hides typing mistakes and `KeyboardInterrupt`.
- Putting more code than necessary inside `try`, so an unrelated bug is handled as though it were the expected error.
- Using `assert` to check user input; it can be turned off and its message is not meant for users.

@practice code
prompt: The function below is meant to return the second largest **distinct** value in a list of numbers, and to raise `ValueError` if the list has fewer than two distinct values. It is buggy. Fix it so that it meets the specification.
starter:
```python
def second_largest(nums):
    return sorted(nums)[-2]
```
tests:
```python
assert second_largest([3, 1, 4, 1, 5]) == 4
assert second_largest([5, 5, 4]) == 4
assert second_largest([-1, -2]) == -2
assert second_largest([1, 2, 3]) == 2
assert raises(ValueError, second_largest, [2, 2])
assert raises(ValueError, second_largest, [7])
assert raises(ValueError, second_largest, [])
```
model:
```python
def second_largest(nums):
    if not nums:
        raise ValueError("need at least two distinct values")
    largest = max(nums)
    rest = [n for n in nums if n != largest]
    if not rest:
        raise ValueError("need at least two distinct values")
    return max(rest)
```
hint: Which test fails, and what does `sorted(nums)[-2]` return for `[5, 5, 4]`?
hint: Remove every copy of the largest value, then take the largest of what is left; if nothing is left, raise `ValueError`.
solution: Find the maximum, build the list of values different from it, and return its maximum. An empty input and an input whose values are all equal both leave nothing to return, so raise `ValueError`; `max([])` would otherwise raise `ValueError` itself, but the explicit check keeps the specification clear.

```python
def average(nums):
    pass
```
tests:
```python
assert average([1, 2, 3, 4]) == 2.5
assert average([10]) == 10.0
assert average([-2, 2]) == 0.0
assert average([1.5, 2.5]) == 2.0

```
model:
```python
def average(nums):
    if len(nums) == 0:
        raise ValueError("average of an empty list")

```

@quiz code
prompt: Write `is_palindrome(s)` that returns `True` if the string `s` reads the same forwards and backwards, **recursively** (no loops, no slicing with `[::-1]`, no `reversed`). Compare case-sensitively and consider every character. The empty string and one-character strings are palindromes.
starter:
```python
def is_palindrome(s):
    pass
```
tests:
```python
assert is_palindrome("") is True
assert is_palindrome("a") is True
assert is_palindrome("abba") is True
assert is_palindrome("level") is True
assert is_palindrome("abca") is False
assert is_palindrome("Aba") is False
assert is_palindrome("ab") is False
```
model:
```python
def is_palindrome(s):
    if len(s) <= 1:
        return True
    if s[0] != s[-1]:
        return False
    return is_palindrome(s[1:-1])
```
hint: Base case: strings of length 0 or 1. Recursive case: compare the first and last characters.
solution: If the first and last characters differ, the answer is `False`; otherwise the string is a palindrome exactly when the middle part `s[1:-1]` is. Each call shortens the string by two, so it reaches a base case.
