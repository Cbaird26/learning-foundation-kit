@article
Sorting is the most studied algorithmic problem, and it shows every idea of this course in one place: recurrences, correctness, randomness and lower bounds.

### The algorithms

**Insertion sort** inserts each element into the sorted prefix to its left. It takes $\Theta(n^2)$ time in the worst case (reverse order) but $\Theta(n)$ on an already sorted list, and it is fast on short or nearly sorted lists.

**Merge sort** sorts each half and merges. Time $T(n) = 2T(n/2) + \Theta(n) = \Theta(n \log n)$ in every case, using $\Theta(n)$ extra space. It is **stable**: elements that compare equal keep their original relative order, provided the merge takes from the left half on ties.

**Quicksort** chooses a **pivot**, partitions the list into elements smaller than the pivot and the rest, and recurses on both sides. This in-place version uses the Lomuto partition with a random pivot:

```python
import random

def partition(a, lo, hi):
    """Partition a[lo..hi] around a random pivot; return its final index."""
    k = random.randint(lo, hi)
    a[k], a[hi] = a[hi], a[k]
    pivot = a[hi]
    i = lo
    for j in range(lo, hi):
        if a[j] < pivot:
            a[i], a[j] = a[j], a[i]
            i += 1
    a[i], a[hi] = a[hi], a[i]
    return i

def quicksort_inplace(a, lo=0, hi=None):
    if hi is None:
        hi = len(a) - 1
    if lo < hi:
        p = partition(a, lo, hi)
        quicksort_inplace(a, lo, p - 1)
        quicksort_inplace(a, p + 1, hi)
```

Its time is $T(n) = T(k) + T(n-1-k) + \Theta(n)$ where $k$ is the pivot's rank. If the pivot is always the minimum or maximum (for example the first element of an already sorted list), $T(n) = T(n-1) + \Theta(n) = \Theta(n^2)$. With a **uniformly random** pivot the **expected** number of comparisons is about $2n\ln n \approx 1.39\,n\log_2 n$, so the expected time is $\Theta(n \log n)$ on every input; the randomness is in the algorithm, not in the data. Quicksort is not stable, and this simple partition degrades on many equal keys; a three-way partition (less than, equal to, greater than the pivot) fixes that.

Heapsort sorts in place in $\Theta(n \log n)$ worst-case time using a binary heap; it is mentioned here for completeness.

### The comparison lower bound

A **comparison sort** learns about the input only by asking "is $a_i < a_j$?". Any such algorithm on $n$ distinct elements corresponds to a **decision tree**: each internal node is a comparison, each branch an answer, and each leaf an output permutation. Correctness requires every one of the $n!$ input orderings to reach a leaf where it is sorted, and two different orderings need different leaves. So the tree has at least $n!$ leaves.

A binary tree of height $h$ has at most $2^h$ leaves, so $2^h \ge n!$, and the worst-case number of comparisons is at least
$$h \ge \log_2(n!) \ge \log_2\big((n/2)^{n/2}\big) = \tfrac n2 \log_2 \tfrac n2 = \Omega(n \log n),$$
using $n! \ge (n/2)^{n/2}$ (the top $n/2$ factors of $n!$ are each at least $n/2$). Hence **merge sort is asymptotically optimal** among comparison sorts. For example $\log_2 (5!) = \log_2 120 \approx 6.9$, so sorting 5 items needs at least 7 comparisons in the worst case.

### Beating the bound

**Counting sort** sorts $n$ integers in the range $0, \dots, k-1$ in $\Theta(n + k)$ time by counting occurrences and computing positions. It does not compare keys with each other, so the lower bound does not apply; it uses extra information, that keys are small integers. Radix sort applies a stable counting sort digit by digit.

@example
title: Tracing a partition
problem: Run `partition` on `a = [5, 2, 8, 1, 9, 3]` with `lo = 0`, `hi = 5`, assuming the random choice picks the last element (`k = 5`) as pivot.
step: The pivot is `3`; the swap of `a[5]` with itself changes nothing. Start with `i = 0`.
step: `j = 0`: `5 < 3` is false. `j = 1`: `2 < 3`, swap `a[0]` and `a[1]` to get `[2, 5, 8, 1, 9, 3]`, and `i = 1`.
step: `j = 2`: `8` is not smaller. `j = 3`: `1 < 3`, swap `a[1]` and `a[3]` to get `[2, 1, 8, 5, 9, 3]`, and `i = 2`. `j = 4`: `9` is not smaller.
step: Finally swap `a[i] = a[2]` with the pivot `a[5]`: the list is `[2, 1, 3, 5, 9, 8]` and `partition` returns `2`.
step: Everything left of index 2 is smaller than 3, everything right of it is larger, and `3` is in its final place.
answer: `[2, 1, 3, 5, 9, 8]`, pivot index `2`.

@example
title: Merging two sorted lists
problem: Merge `[2, 5, 9]` and `[1, 5, 7]`, taking from the left list on ties, and count the comparisons.
step: Compare `2` and `1`: take `1`. Compare `2` and `5`: take `2`.
step: Compare `5` (left) and `5` (right): tie, so take the left `5`. Compare `9` and `5`: take the right `5`.
step: Compare `9` and `7`: take `7`. The right list is now empty, so append the remaining `9` without comparing.
step: The result is `[1, 2, 5, 5, 7, 9]` after 5 comparisons. In general merging lists of lengths $m$ and $n$ takes at most $m + n - 1$ comparisons.
answer: `[1, 2, 5, 5, 7, 9]`, 5 comparisons.

@mistakes
- Saying quicksort is $O(n \log n)$ without the qualifier: it is $\Theta(n^2)$ in the worst case and $\Theta(n \log n)$ only in expectation (random pivot) or on average over random inputs.
- Believing "no sorting algorithm beats $n \log n$". The bound holds for comparison sorts; counting and radix sort exploit the structure of integer keys.
- Breaking stability in the merge by taking from the right half on ties.
- Using the lower bound to claim merge sort needs exactly $n\log_2 n$ comparisons. The bound is $\Omega(n \log n)$ and the exact count differs by lower-order terms.

```python
def merge(a, b, key=None):
    if key is None:
        key = lambda x: x
    result = []
    i = j = 0
    while i < len(a) and j < len(b):
        if key(b[j]) < key(a[i]):
            result.append(b[j])
            j += 1
        else:
            result.append(a[i])
            i += 1
    result.extend(a[i:])
    result.extend(b[j:])
    return result
```

```python
def quicksort(a):
    if len(a) <= 1:
        return list(a)
    pivot = a[len(a) // 2]
    less = [x for x in a if x < pivot]
    equal = [x for x in a if x == pivot]

    return quicksort(less) + equal + quicksort(greater)
```

Because `equal` always contains at least the pivot, both recursive lists are strictly shorter, so the recursion terminates, and a list of all-equal elements is finished in one level.

@practice self
prompt: Prove that every comparison-based sorting algorithm needs $\Omega(n \log n)$ comparisons in the worst case. Then explain in two or three sentences why counting sort, which sorts $n$ integers from $\{0, \dots, k-1\}$ in $\Theta(n + k)$ time, does not contradict this.
solution: Model a deterministic comparison sort on $n$ distinct keys as a binary decision tree whose internal nodes are comparisons and whose leaves are outputs. The algorithm must give the correct sorted order for each of the $n!$ input permutations, and two different permutations need different output permutations to be sorted, so they reach different leaves; hence at least $n!$ leaves. A binary tree of height $h$ has at most $2^h$ leaves, so $2^h \ge n!$ and $h \ge \log_2 n!$. Since $n! \ge (n/2)^{n/2}$, we get $h \ge \frac n2\log_2\frac n2 = \Omega(n\log n)$. The worst case of the algorithm is the height of the tree, so it makes $\Omega(n\log n)$ comparisons. Counting sort is not a comparison sort: it uses the key values as array indices, which gives each key $k$ possible outcomes at once rather than two. The decision-tree model does not describe it, so the bound does not apply. When $k$ is $O(n)$ it is linear, but it needs integer keys from a small range.

model:
```python
def merge_sort(a, key=None):
    if key is None:
        key = lambda x: x
    if len(a) <= 1:
        return list(a)
    mid = len(a) // 2
    left = merge_sort(a[:mid], key)
    right = merge_sort(a[mid:], key)
    result = []
    i = j = 0
    while i < len(left) and j < len(right):
        if key(right[j]) < key(left[i]):
            result.append(right[j])
            j += 1
        else:
            result.append(left[i])
            i += 1
    result.extend(left[i:])
    result.extend(right[j:])
    return result
```
hint: Sort each half recursively, then merge the two sorted halves.
hint: In the merge, take from the right half only when its key is strictly smaller. That keeps the sort stable.
solution: Recurse on the two halves and merge with the front-element rule, taking the right element only when its key is strictly smaller than the left's so equal keys stay in their original order. The recurrence is $2T(n/2) + \Theta(n)$, which is $\Theta(n\log n)$.
