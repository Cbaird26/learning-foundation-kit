@article
A dynamic array keeps its elements side by side in one block of memory. A **linked list** keeps each element in its own object, called a **node**, and each node holds a reference to the next one. There is no index arithmetic and no resizing; the structure is held together only by references.

### Nodes and traversal

```python
class Node:
    def __init__(self, value, next=None):
        self.value = value
        self.next = next

# the list 10 -> 20 -> 30
head = Node(10, Node(20, Node(30)))

node = head
while node is not None:
    print(node.value)
    node = node.next
```

The **head** is the reference to the first node, and the last node's `next` is `None`. Traversal follows `next` until it reaches `None`. To read the element at position `i` you must take `i` steps, so indexing is $O(i)$, which is $O(n)$ in the worst case. That is the main weakness compared with an array's $O(1)$ indexing.

### Changing the list

Operations are rewiring of references. Do the steps in an order that never loses a node.

**Insert at the head** is $O(1)$:

```python
def push_front(head, value):
    return Node(value, head)    # the new node points at the old head
```

**Insert after a node you already hold** is $O(1)$: set the new node's `next` to `node.next` first, then set `node.next` to the new node. Doing it in the opposite order would lose the rest of the list.

**Delete after a node you hold** is also $O(1)$: `node.next = node.next.next`. To delete a *given* node in a singly linked list you need its predecessor, and finding that takes $O(n)$.

**Insert at the tail** is $O(n)$ if you only have `head`, because you must walk to the last node. A list object that also stores a `tail` reference makes it $O(1)$. Be careful to keep `tail` correct when the list becomes empty or loses its last node.

### A list object

Real implementations wrap the nodes in a class that stores `head`, `tail` and a `size` counter. Size is maintained on every insert and delete, so `len(list)` is $O(1)$ instead of a traversal.

### Reversal

To reverse a singly linked list in place, walk through it once, redirecting each `next` backward. Keep three references: `prev` (the already reversed part), `node` (the current node) and the saved `next` of the current node. Saving `next` before you overwrite it is the key step.

```python
def reverse(head):
    prev = None
    node = head
    while node is not None:
        nxt = node.next      # save the rest
        node.next = prev     # redirect this node backward
        prev = node          # advance both references
        node = nxt
    return prev              # the old tail is the new head
```

It does $O(n)$ work with $O(1)$ extra space.

### Variants

A **doubly linked list** gives each node `prev` and `next` references, so a node you hold can be deleted in $O(1)$ and the list can be traversed both ways, at the cost of one extra reference per node. A **sentinel** (dummy) node at the front removes the special case of changing the head: inserting and deleting at the front then looks like every other position. A **circular** list links the last node back to the first.

### Linked list or dynamic array?

| Operation | Dynamic array | Singly linked list |
|---|---|---|
| index `i` | $O(1)$ | $O(i)$ |
| insert/delete at front | $O(n)$ | $O(1)$ |
| insert/delete at end | $O(1)$ amortized | $O(1)$ insert with `tail`; delete is $O(n)$ |
| insert/delete after a held node | $O(n)$ | $O(1)$ |
| memory per element | one slot | a node object plus a reference |

On real hardware arrays also benefit from **locality of reference**: neighboring elements share cache lines, so scanning an array is usually much faster than chasing references through a linked list, even when both are $O(n)$. That is why Python programmers reach for `list` first and for linked structures only when constant-time splicing or stable node references matter.

@example
title: Reversing a list by hand
problem: Trace `reverse` on the list `a -> b -> c` (values `"a"`, `"b"`, `"c"`).
step: Start: `prev = None`, `node = a`. Pass 1: save `nxt = b`, set `a.next = None`, then `prev = a` and `node = b`.
step: Pass 2: save `nxt = c`, set `b.next = a`, then `prev = b` and `node = c`.
step: Pass 3: save `nxt = None`, set `c.next = b`, then `prev = c` and `node = None`.
step: The loop ends because `node` is `None`. Return `prev`, which is `c`. The links now read `c -> b -> a -> None`.
answer: The reversed list is `c -> b -> a`, built with 3 passes and no new nodes.

@example
title: Deleting a value with a sentinel
problem: Write `remove_first(head, value)` that removes the first node holding `value` and returns the new head.
step: Removing the head node is a special case, because there is no predecessor to rewire. Create a sentinel `dummy` whose `next` is `head` so every node has a predecessor.
step: Walk with `prev = dummy`, checking `prev.next` each time. Stop when `prev.next` is `None` (value absent) or holds `value`.
step: If the node was found, bypass it with `prev.next = prev.next.next`.
step: Return `dummy.next`, which is the (possibly new) head:

```python
def remove_first(head, value):
    dummy = Node(None, head)
    prev = dummy
    while prev.next is not None and prev.next.value != value:
        prev = prev.next
    if prev.next is not None:
        prev.next = prev.next.next
    return dummy.next
```
step: Cost: one traversal, $O(n)$ time and $O(1)$ extra space.
answer: The function above; it handles removal of the head, of the last node and of a missing value uniformly.

@mistakes
- Overwriting `node.next` before saving the old value, which cuts off the rest of the list.
- Forgetting the special case of changing the head (or the tail, or an empty list) when inserting or deleting.
- Letting `size` or `tail` go stale after a deletion, so later operations act on a node that is no longer in the list.
- Assuming a linked list is faster than an array in practice because inserting is $O(1)$: finding the position costs $O(n)$ unless you already hold the node.

model:
```python
class _Node:
    def __init__(self, value):
        self.value = value
        self.next = None


class LinkedList:
    def __init__(self):
        self._head = None
        self._tail = None
        self._size = 0

    def __len__(self):
        return self._size

    def __iter__(self):
        node = self._head
        while node is not None:
            yield node.value
            node = node.next

    def push_front(self, x):
        node = _Node(x)
        node.next = self._head
        self._head = node
        if self._tail is None:
            self._tail = node
        self._size += 1

    def push_back(self, x):
        node = _Node(x)
        if self._tail is None:
            self._head = node
        else:
            self._tail.next = node
        self._tail = node
        self._size += 1

    def pop_front(self):
        if self._head is None:
            raise IndexError("pop from empty list")
        node = self._head
        self._head = node.next
        if self._head is None:
            self._tail = None
        self._size -= 1
        return node.value
```
hint: Store `_head`, `_tail` and `_size`. An empty list has `_head` and `_tail` both `None`.
hint: When `pop_front` removes the only node, also set `_tail` to `None`; when `push_front` or `push_back` adds to an empty list, the new node is both head and tail.
solution: The two special cases are the empty list and the single-node list. `push_back` links the new node after `_tail` (or makes it the head when empty); `pop_front` clears `_tail` when it removes the last node, so later `push_back` calls start a fresh list. The test that pops everything and then pushes again catches a stale tail.

model:
```python
class Node:
    def __init__(self, value, next=None):
        self.value = value
        self.next = next


def merge_sorted(a, b):
    dummy = Node(None)
    tail = dummy
    while a is not None and b is not None:
        if b.value < a.value:
            tail.next = b
            b = b.next
        else:
            tail.next = a
            a = a.next
        tail = tail.next
    tail.next = a if a is not None else b
    return dummy.next
```
hint: Use a dummy node and a `tail` reference to the end of the merged list so far; compare the two front nodes.
hint: Take `b` only when `b.value < a.value` (so ties favor `a`), relink it to `tail.next`, and advance. When one list runs out, attach the rest of the other.
solution: A sentinel avoids a special case for the first node. Each pass moves the smaller front node onto the merged tail; the strict `<` keeps ties in `a`'s favor. After the loop, one list is empty and the other is attached whole. It runs in $O(m + n)$ time and $O(1)$ extra space, and the identity test checks that nodes were relinked, not copied.

@quiz mc
prompt: A program holds a reference to a node in the middle of a list and must delete that node as quickly as possible. Which structure gives $O(1)$ worst-case deletion of the held node?
choice: A singly linked list, because only the node's `next` needs to change.
choice: A dynamic array, because the node's position is known.
choice*: A doubly linked list, because the node can reach and update its predecessor.
choice: Any linked list that keeps a `tail` reference.
hint: What must change in the node *before* the deleted one?
solution: Unlinking a node requires updating its predecessor's `next`. A doubly linked list stores that predecessor in the node. A singly linked list must search for it in $O(n)$, a `tail` reference does not help in the middle, and a dynamic array shifts later elements.
