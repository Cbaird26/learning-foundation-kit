@article
Last week's analysis said operations cost $\Theta(1 + \alpha)$ expected, where $\alpha = n/m$. A table with a fixed $m$ gets slower and slower as $n$ grows. The fix is the same idea as the dynamic array: when the table becomes too full, build a bigger one.

### The resize policy

Choose a **maximum load factor** $\alpha_{\max}$ (0.75 is a common choice for chaining; Java's `HashMap` uses 0.75, for example). After each insertion of a new key, if $n/m > \alpha_{\max}$, **rehash**: allocate a table with (typically) $2m$ buckets and reinsert every pair, computing its bucket as $h(\text{key}) \bmod 2m$.

A rehash must recompute every bucket index; you cannot copy buckets across unchanged, because the index depends on $m$. A pair that was in bucket 5 of 8 may belong in bucket 5 or bucket 13 of 16.

```python
def rehash(old_buckets, new_size):
    new_buckets = [[] for _ in range(new_size)]
    for bucket in old_buckets:
        for key, value in bucket:
            new_buckets[hash(key) % new_size].append((key, value))
    return new_buckets
```

### Cost of resizing

One resize costs $O(m + n) = O(n)$, since the table has $O(n)$ buckets and $n$ pairs. But the number of buckets doubles each time, exactly as in a dynamic array, so the sizes of the rehashes form a geometric series and $n$ insertions cost $O(n)$ in total. The expected cost of one `put` is therefore $O(1)$ **amortized** (and expected, because chain lengths depend on the hash function). A single unlucky insertion that triggers a rehash is slow, which matters for latency-sensitive programs; some systems resize incrementally, moving a few buckets at a time.

Between resizes, $\alpha \le \alpha_{\max}$, so the expected chain length is below 0.75 plus the item itself, a constant. Growing only is wasteful if many keys are deleted; a table may shrink when $\alpha$ falls well below a lower threshold (for example 0.25 when doubling at 0.75), and the gap between the thresholds prevents resize thrashing.

### Designing the table

**Choosing $m$.** If $m$ is a power of two, `h % m` is a cheap bit mask but uses only the low bits of $h$, so a weak hash function with patterned low bits will cluster. If $m$ is a prime not close to a power of two, all bits of $h$ influence the bucket. Whichever you choose, the hash function should mix its input well.

**Chaining.** Simple, tolerates high $\alpha$, deletion is just removing a pair from a chain. Costs a list object per bucket and pointer chasing.

**Open addressing.** Stores pairs in one array: better cache behavior and less memory per pair, but needs $\alpha < 1$, usually kept below about 0.5 to 0.7, suffers from clustering with linear probing, and needs tombstones for deletion. Python's `dict` is open-addressing with a compact layout: since Python 3.7 the language guarantees that a dict iterates in insertion order. Its keys must be hashable.

**Adversarial inputs.** If an attacker can choose keys that all collide, the table degrades to $O(n)$ per operation and can be used to exhaust a server's CPU (a "hash flooding" denial of service). Defenses are a hash function seeded with a random secret at startup, as Python does for strings, or, in the theory of **universal hashing**, choosing the function at random from a family in which any two distinct keys collide with probability at most $1/m$.

### Beyond the expected case

If $n$ is known to be fixed and the keys are known in advance, **perfect hashing** gives $O(1)$ worst-case lookups. In most programs, the practical advice is to use the built-in `dict` and `set`, to give your own classes consistent `__eq__` and `__hash__`, and to remember what the guarantees really are: expected $O(1)$ with a good hash function, worst case $O(n)$.

@example
title: When does the table resize?
problem: A chaining hash map starts with 4 buckets and doubles when $n/m > 0.75$ after an insertion. Insert 10 distinct keys. After which insertions does it resize, and how many buckets does it end with?
step: With $m = 4$ the limit is $0.75 \cdot 4 = 3$ keys. Insertions 1, 2 and 3 give $n/m = 0.25, 0.5, 0.75$, none above 0.75.
step: Insertion 4 gives $4/4 = 1 > 0.75$, so the table resizes to $m = 8$ (rehashing 4 keys). The limit is now 6 keys.
step: Insertions 5 and 6 keep $n/m \le 0.75$ ($6/8 = 0.75$). Insertion 7 gives $7/8 > 0.75$, so it resizes to $m = 16$ (rehashing 7 keys); the limit is 12.
step: Insertions 8 through 10 fit, since $10/16 = 0.625$.
step: Total pairs reinserted: $4 + 7 = 11$ for 10 insertions, about one extra insertion per key.
answer: It resizes after insertions 4 and 7 and ends with 16 buckets.

@example
title: Rehashing changes the bucket
problem: Keys 3, 11, 5 are in a table with 8 buckets using $h(k) = k$. Where are they after rehashing to 16 buckets?
step: With $m = 8$: $3 \bmod 8 = 3$, $11 \bmod 8 = 3$ (a collision), $5 \bmod 8 = 5$.
step: With $m = 16$: $3 \bmod 16 = 3$, $11 \bmod 16 = 11$, $5 \bmod 16 = 5$.
step: Keys 3 and 11 no longer share a bucket. Growing the table both lowers $\alpha$ and re-spreads the keys.
answer: Buckets 3, 11 and 5 respectively.

@mistakes
- Copying old buckets into the larger table without recomputing each key's index, so lookups probe the wrong bucket and miss existing keys.
- Resizing before the insertion's duplicate check, so updating an existing key grows the table.
- Using the old size in `hash(key) % m` after the buckets list was replaced (or the reverse), leaving the table half rehashed.
- Resizing by a constant number of buckets, which makes the total cost $O(n^2)$, as with dynamic arrays.

model:
```python
class HashMap:
    def __init__(self, buckets=8):
        self._buckets = [[] for _ in range(buckets)]
        self._size = 0

    def __len__(self):
        return self._size

    def num_buckets(self):
        return len(self._buckets)

    def _bucket(self, key):
        return self._buckets[hash(key) % len(self._buckets)]

    def put(self, key, value):
        bucket = self._bucket(key)
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket[i] = (key, value)
                return
        bucket.append((key, value))
        self._size += 1
        if self._size / len(self._buckets) > 0.75:
            self._resize(2 * len(self._buckets))

    def get(self, key, default=None):
        for k, v in self._bucket(key):
            if k == key:
                return v
        return default

    def __contains__(self, key):
        return any(k == key for k, _ in self._bucket(key))

    def remove(self, key):
        bucket = self._bucket(key)
        for i, (k, v) in enumerate(bucket):
            if k == key:
                del bucket[i]
                self._size -= 1
                return v
        raise KeyError(key)

    def _resize(self, new_size):
        new_buckets = [[] for _ in range(new_size)]
        for bucket in self._buckets:
            for k, v in bucket:
                new_buckets[hash(k) % new_size].append((k, v))
        self._buckets = new_buckets
```
hint: Write a helper that returns the bucket (a list) for a key; all of `put`, `get`, `remove` and `__contains__` scan it.
hint: In `put`, scan the bucket for the key first and update in place; only when it is absent append, increment `_size` and check the load factor. In `_resize`, recompute each index from the new size.
solution: Each operation scans one chain. `put` returns early when it updates, so only new keys can trigger the resize check. The resize builds a new bucket list and reinserts every pair with `hash(k) % new_size`. Inserting 100 keys from 8 buckets doubles at 7, 13, 25, 49 and 97 keys, ending with 256 buckets.

model:
```python
def most_common_word(words):
    counts = {}
    for w in words:
        counts[w] = counts.get(w, 0) + 1
    best = None
    best_count = 0
    for w, c in counts.items():
        if c > best_count:
            best = w
            best_count = c
    return best
```
hint: Build the counts first; a dict remembers the order in which keys were first inserted.
hint: Scan the dict in order and replace the best word only when a count is strictly greater, so earlier words win ties.
solution: One pass counts occurrences in expected $O(n)$ time. Iterating the dict visits words in order of first occurrence, and the strict comparison `c > best_count` keeps the earliest word among equals. In `["c", "a", "b", "b", "a"]`, both `a` and `b` appear twice and `a` appeared first among those two.

@quiz mc
prompt: An open-addressing table with linear probing is allowed to fill to a load factor of 0.95 before resizing. What is the most likely consequence?

solution: With few empty slots, runs of occupied slots merge into long clusters, and an unsuccessful search must walk to the end of one, so the expected number of probes grows very large as $\alpha \to 1$. Open-addressing tables therefore resize at a much lower load factor than chaining tables.
