@article
A plain binary search tree can degenerate into a chain, so its operations are $O(n)$ in the worst case. A **self-balancing** binary search tree repairs its own shape after every insertion and deletion so that its height stays $O(\log n)$. The repair uses a local, constant-time operation, the rotation.

### Rotations

A **rotation** changes the shape of a small part of the tree while preserving the BST ordering (the inorder sequence does not change). A **right rotation** at node $y$ with left child $x$ lifts $x$ above $y$: $x$'s right subtree becomes $y$'s left subtree, and $y$ becomes $x$'s right child. A **left rotation** is the mirror image.

```python
def rotate_right(y):
    x = y.left
    y.left = x.right     # x's right subtree moves under y
    x.right = y
    return x             # x is the new root of this subtree

def rotate_left(x):
    y = x.right
    x.right = y.left
    y.left = x
    return y
```

Each rotation changes a constant number of links, so it is $O(1)$. It returns the new subtree root, which the caller stores in the parent's link.

### AVL trees

An **AVL tree** is a BST in which, for every node, the heights of the left and right subtrees differ by at most 1. The **balance factor** of a node is $\text{height}(\text{left}) - \text{height}(\text{right})$ and must be $-1$, $0$ or $+1$.

**Why the height is logarithmic.** Let $N(h)$ be the smallest number of nodes in an AVL tree of height $h$. Such a tree has a root and two subtrees of heights $h-1$ and $h-2$ (the thinnest legal choice), so
$$N(h) = N(h-1) + N(h-2) + 1, \qquad N(0) = 1,\ N(1) = 2.$$
This grows like the Fibonacci numbers, exponentially in $h$: $N(2) = 4$, $N(3) = 7$, $N(4) = 12$, $N(5) = 20$. Hence $n \ge N(h)$ forces $h = O(\log n)$; precisely, $h < 1.4405 \log_2(n + 2)$. Search, insert and delete are $O(\log n)$ in the worst case.

**Inserting.** Insert as in a BST, then walk back up the path updating heights. At the first node whose balance factor becomes $+2$ or $-2$, rotate. There are four cases, named by where the new key went relative to the unbalanced node $z$:

| Case | Shape at $z$ | Fix |
|---|---|---|
| left-left | the left child's left subtree is too tall | right rotation at $z$ |
| right-right | the right child's right subtree is too tall | left rotation at $z$ |
| left-right | the left child's right subtree is too tall | left rotation at $z$'s left child, then right rotation at $z$ |
| right-left | the right child's left subtree is too tall | right rotation at $z$'s right child, then left rotation at $z$ |

After one rotation (single or double) the subtree regains its old height, so an insertion needs at most one such repair. Deletion may need a rotation at every level on the way up, still $O(\log n)$ in total.

### Red-black trees

A **red-black tree** is a BST whose nodes carry a color, subject to five properties:

1. Every node is red or black.
2. The root is black.
3. Every leaf (the `None` positions, treated as nil nodes) is black.
4. A red node has only black children (no two reds in a row).
5. Every path from a node down to its nil descendants contains the same number of black nodes (the node's **black-height**).

**Height bound.** By property 5, a tree of black-height $b$ at the root contains at least $2^b - 1$ nodes, so $b \le \log_2(n+1)$. By property 4, at most every other node on a path is red, so the height is at most $2b$. Hence $h \le 2 \log_2(n + 1)$.

**Insertion** adds the new node as red, then restores the properties: if its parent is red and its uncle is red, recolor and continue upward; if the uncle is black, one or two rotations and a recoloring finish the job. Insertion uses at most two rotations, and all operations are $O(\log n)$ worst case. The ordering rules are simpler to remember through the correspondence with 2-3-4 trees, where a black node with red children represents one multi-key node.

### Which to use?

AVL trees are more strictly balanced (height at most about $1.44 \log_2 n$), so lookups are slightly faster; red-black trees do fewer rotations on updates, which is why they are common in standard libraries (for example C++'s ordered containers and Java's `TreeMap` are typically red-black trees). Python's standard library has no balanced tree or sorted container; sorted sequences are usually kept in a `list` with `bisect`. Other balanced structures include B-trees (the standard for databases and file systems, where a node holds many keys per disk block), treaps, skip lists and splay trees.

@example
title: Fixing a left-right imbalance
problem: Insert 30, then 10, then 20 into an empty AVL tree. What is the final shape?
step: After 30 and 10 the tree is 30 with left child 10 (balanced, balance factor +1). Insert 20: $20 < 30$, then $20 > 10$, so 20 is the right child of 10.
step: Now 30 has a left subtree of height 1 (10 with child 20) and no right subtree: balance factor $1 - (-1) = +2$. The imbalance is left-right: the new key went into the left child's right subtree.
step: A single right rotation at 30 would not help (the tall part is on the inside). First rotate left at 10: 20 rises, with 10 as its left child, so 30 now has the chain 30, 20, 10 to its left.
step: Then rotate right at 30: 20 rises to the root with children 10 and 30.
answer: Root 20 with children 10 and 30, a perfectly balanced tree of height 1.

@example
title: Several AVL insertions
problem: Insert 10, 20, 30, 40, 50 into an empty AVL tree. Give the final tree.
step: Insert 10, then 20 (right of 10). Insert 30: node 10 now has a right chain 20, 30 and balance factor $-2$. This is right-right, so rotate left at 10: the tree is 20 with children 10 and 30.
step: Insert 40 (right of 30). Heights are fine: the root has left height 0 and right height 1.
step: Insert 50 (right of 40). Node 30 has right chain 40, 50 and balance factor $-2$: right-right again, so rotate left at 30: 40 rises with children 30 and 50.
step: The tree is now root 20, left child 10, right child 40 with children 30 and 50. Each node's balance factor is $-1$, $0$ or $+1$ and the height is 2.
answer: Root 20; 10 on the left; 40 on the right with children 30 and 50.

@mistakes
- Rotating in the wrong direction or at the wrong node: a right rotation fixes a too-tall *left-left* shape and is applied at the unbalanced node, not at the new leaf.
- Applying a single rotation to a left-right or right-left case; the inner grandchild stays on the tall side and the tree remains unbalanced.
- Forgetting to update the stored heights after a rotation (children first, then the new root), so later balance factors are wrong.
- Believing all root-to-leaf paths in a red-black tree have the same length. Only the number of black nodes is equal; path lengths may differ by up to a factor of 2.

model:
```python
class Node:
    def __init__(self, key, left=None, right=None):
        self.key = key
        self.left = left
        self.right = right


def is_height_balanced(root):
    def check(node):
        # returns the height, or None if some subtree is unbalanced
        if node is None:
            return -1
        left = check(node.left)
        if left is None:
            return None
        right = check(node.right)
        if right is None:
            return None
        if abs(left - right) > 1:
            return None
        return 1 + max(left, right)

    return check(root) is not None
```
hint: A recursive helper can return the subtree height while checking the condition at each node.
hint: Return `None` (or a flag) as soon as one subtree is unbalanced, and compare `abs(left - right)` with 1 at every node, not just at the root.
solution: The helper computes heights bottom-up and fails as soon as any node has a height difference above 1. The `deep` test has a root with difference 1 but an unbalanced descendant (node 5), so checking the root alone is not enough. The cost is $O(n)$, because each node is visited once.

model:
```python
class Node:
    def __init__(self, key):
        self.key = key
        self.left = None
        self.right = None
        self.height = 0


def height(node):
    return -1 if node is None else node.height


def update(node):
    node.height = 1 + max(height(node.left), height(node.right))


def rotate_right(y):
    x = y.left
    y.left = x.right
    x.right = y
    update(y)
    update(x)
    return x


def rotate_left(x):
    y = x.right
    x.right = y.left
    y.left = x
    update(x)
    update(y)
    return y


def avl_insert(root, key):
    if root is None:
        return Node(key)
    if key < root.key:
        root.left = avl_insert(root.left, key)
    elif key > root.key:
        root.right = avl_insert(root.right, key)
    else:
        return root
    update(root)
    balance = height(root.left) - height(root.right)
    if balance > 1:
        if height(root.left.left) < height(root.left.right):
            root.left = rotate_left(root.left)
        return rotate_right(root)
    if balance < -1:
        if height(root.right.right) < height(root.right.left):
            root.right = rotate_right(root.right)
        return rotate_left(root)
    return root
```
hint: Insert recursively as in a plain BST, then update the node's height and compute its balance factor on the way back up.
hint: If the balance factor is above 1 and the left child leans right, rotate that child left first; then rotate right at the node. The right-heavy case is the mirror image.
solution: After the recursive insertion, recompute the height and the balance factor. A balance above 1 means the left side is too tall: if the left child's right subtree is the taller one (left-right case) rotate the child left first, then rotate right at the node. Below $-1$ is the mirror image. Inserting 1 to 15 in order yields a perfect tree with root 8, which a plain BST would not.
