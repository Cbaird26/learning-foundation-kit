@article
Type `0.1 + 0.2` into Python and it answers `0.30000000000000004`. Is Python broken? No: nearly every machine learning computation runs on **floating-point** numbers, and this answer is exactly what the arithmetic is specified to give. Learning to predict such results is the first skill of numerical computing.

### How a double is stored

Python's `float` is an IEEE 754 **double**: 64 bits, split into 1 sign bit, 11 exponent bits and 52 stored fraction bits. With the implicit leading 1, a double has a 53-bit **significand**. A normal nonzero double equals $\pm\, m \times 2^{k}$ where $m$ is a binary fraction with 53 significant bits. Two consequences matter.

- Only numbers of this form are representable. The decimal $0.1$ is $0.0001100110011\ldots_2$, a repeating binary fraction, so the stored value is the nearest double, $0.1000000000000000055511\ldots$.
- The gap between neighboring doubles grows with the size of the number. In the interval $[2^k, 2^{k+1})$ the spacing is $2^{k-52}$. Near 1 it is $2^{-52} \approx 2.22 \times 10^{-16}$, called **machine epsilon** $\varepsilon$; near $2^{53}$ it is 2, so the double $2^{53}$ plus 1 is not representable.

### The model of rounding

Every basic operation (+, −, ×, ÷, square root) returns the exact result **rounded to the nearest double** (ties go to the one with an even last bit). Write $\mathrm{fl}(\cdot)$ for the rounded result. Then

$$\mathrm{fl}(a \circ b) = (a \circ b)(1 + \delta), \qquad |\delta| \le u = 2^{-53} \approx 1.11 \times 10^{-16},$$

where $u$ is the **unit roundoff**. The **relative error** of an approximation $\hat{x}$ of $x$ is $|\hat{x} - x| / |x|$. Rounding error is relative: each operation is correct to about 16 significant decimal digits, no matter how big the numbers are.

Because each operation rounds, floating-point addition is **not associative**: $(a + b) + c$ and $a + (b + c)$ can differ. It is also why we compare floats with a tolerance, for example `abs(a - b) <= 1e-9 * max(abs(a), abs(b))`, and never with `==`.

### Two ways accuracy is lost

**Absorption.** Adding a small number to a large one can change nothing. At $10^{16}$ the spacing is 2, so $10^{16} + 1$ lands halfway between two doubles, and the tie rounds back to $10^{16}$. Then $(10^{16} + 1) - 10^{16}$ is 0, not 1.

**Cancellation.** Subtracting two nearly equal numbers is exact, but it exposes the rounding errors already in them. Take $x = 10^{-15}$. The sum $1 + x$ must be a multiple of $2^{-52}$, so it becomes $5 \times 2^{-52}$, and $(1 + x) - 1 = 1.1102\ldots \times 10^{-15}$, which is 11% too large. The subtraction itself lost nothing; the damage happened when $1 + x$ was rounded.

### Fighting error: compensated summation

Adding $n$ numbers one at a time can accumulate error proportional to $n u$. **Kahan's compensated summation** keeps a running correction $c$ holding the low-order bits lost by each addition:

```python
def kahan_sum(xs):
    total = 0.0
    comp = 0.0
    for x in xs:
        y = x - comp
        t = total + y
        comp = (t - total) - y
        total = t
    return total

naive = 0.0
for _ in range(10):
    naive += 0.1
print(naive)                   # 0.9999999999999999
print(kahan_sum([0.1] * 10))   # 1.0
```

In exact arithmetic `comp` would always be 0; in floating point it captures what was lost and feeds it into the next addition. (Recent CPython versions already use a compensated algorithm inside the built-in `sum` for floats, but other Pythons do not, so explicit loops are the way to see raw behavior.)

### Fighting error: rearranging formulas

The roots of $a x^2 + b x + c$ are $\frac{-b \pm \sqrt{b^2 - 4ac}}{2a}$. When $b$ is large and positive, $-b + \sqrt{b^2 - 4ac}$ subtracts two nearly equal numbers. The stable fix computes $q = -\tfrac12\big(b + \operatorname{sign}(b)\sqrt{b^2 - 4ac}\big)$, which adds numbers of the same sign, and returns the roots $q/a$ and $c/q$ (their product is $c/a$). The same idea underlies library functions such as `math.log1p(x)`, which computes $\log(1+x)$ accurately for tiny $x$.

### Overflow

Doubles top out near $1.8 \times 10^{308}$: `math.exp(710)` raises an `OverflowError`. Softmax code avoids it by subtracting the maximum score first, a rearrangement of exactly the kind above.

@example
title: Cancellation in a quadratic
problem: Find the smaller-magnitude root of $x^2 + 10^6 x + 1 = 0$ with the textbook formula and with the stable formula, and say which is accurate.
step: The exact small root is about $-1.000000000001 \times 10^{-6}$, since the roots multiply to $c/a = 1$ and the large root is near $-10^6$.
step: Textbook formula: $\sqrt{10^{12} - 4} \approx 999999.999998$. In double precision, $-10^6 + 999999.999998$ cancels, and Python gives about $-1.0000076 \times 10^{-6}$, a relative error near $7.6 \times 10^{-6}$: only five correct digits out of sixteen.
step: Stable formula: $q = -\tfrac12 (10^6 + 999999.999998) \approx -999999.999999$, then the small root is $c/q$, which is about $-1.000000000001 \times 10^{-6}$.
step: Division and a sum of same-sign numbers lose at most a few units of $u$, so the stable answer matches the exact one to about 15 digits.
answer: The stable formula is accurate; the textbook formula loses about eleven digits to cancellation.

@example
title: Spacing of doubles
problem: What is the gap between neighboring doubles near 8, and what does `8.0 + 1e-15` evaluate to?
step: The number 8 is $2^3$, so it lies in $[2^3, 2^4)$, where the spacing is $2^{3-52} = 2^{-49} \approx 1.78 \times 10^{-15}$.
step: A sum is rounded to the nearest double. The value $8 + 10^{-15}$ lies $10^{-15}$ above 8, which is more than half the spacing ($0.89 \times 10^{-15}$), so it rounds up to the next double, $8 + 2^{-49}$.
step: Check: `8.0 + 1e-15 - 8.0` evaluates to $1.7763568394002505 \times 10^{-15}$, not $10^{-15}$.
answer: The spacing is $2^{-49} \approx 1.78 \times 10^{-15}$, and `8.0 + 1e-15` is the next double above 8.

@mistakes
- Comparing floats with `==`: results of different computations differ in the last bits, so use a relative tolerance (and an absolute one when the target may be 0).
- Thinking error is a fixed number like $10^{-16}$: the absolute gap between doubles grows with the magnitude; the relative error bound $u$ is what stays fixed.
- Blaming the subtraction for cancellation: the subtraction is exact; the error comes from the rounded inputs, so the fix is to avoid forming them, not to subtract differently.
- Assuming a longer sum is only slightly less accurate: adding many tiny terms to a large running total can lose every one of them.

model:
```python
import math

def stable_roots(a, b, c):
    """Roots of a*x^2 + b*x + c avoiding cancellation, small |root| first."""
    d = math.sqrt(b * b - 4 * a * c)
    q = -(b + math.copysign(d, b)) / 2
    roots = [q / a, c / q]
    roots.sort(key=abs)
    return (roots[0], roots[1])
```
hint: `math.copysign(d, b)` gives `d` the sign of `b`, so `b + copysign(d, b)` never cancels. Sort the two roots by absolute value.
solution: Adding numbers of the same sign loses nothing, so `q` is accurate, and then `q / a` and `c / q` are both accurate roots (their product is `c / a`). The naive formula gives the small root of the second test with a relative error around 1e-8 or worse, which the tight tolerance rejects.
