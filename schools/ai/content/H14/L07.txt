@article
**Searching** means finding where (or whether) a value occurs in a collection. It is one of the most common jobs in computing, from looking up a contact to finding a word in a dictionary.

### Linear search

The simplest method is to look at the items one by one, from the start, until you find the target or run out of items:

```python
def linear_search(xs, target):
    for i in range(len(xs)):
        if xs[i] == target:
            return i
    return -1
```

It returns the **index** of the first match, or `-1` when the target is absent. (A separate `return -1` after the loop is essential: the function may only give up after checking *every* item.) Python's `target in xs` and `xs.index(target)` do the same scan. In the worst case, the target is last or missing, and the search makes one comparison for each of the $n$ items. Linear search works on any list, sorted or not.

### Binary search

When a list is **sorted**, you can do much better. Think of guessing a number from 1 to 100: you guess 50, are told "higher", and have eliminated half the numbers with one guess. **Binary search** does this with a list. It keeps a range of indexes that could still contain the target, from `lo` to `hi`, and repeatedly looks at the middle item:

```python
def binary_search(xs, target):
    lo = 0
    hi = len(xs) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if xs[mid] == target:
            return mid
        elif xs[mid] < target:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1
```

Each pass compares the target with `xs[mid]` (one **probe**). If the middle item is too small, the target can only be to the right, so `lo = mid + 1`; if it is too big, `hi = mid - 1`. When `lo > hi` the range is empty and the target is not there.

### The precondition

Binary search only works if the list is **sorted** in increasing order. On an unsorted list its eliminations are wrong and it can miss items that are really there. Sorting costs time too (next lesson), so binary search pays off when you search the same data many times.

### How many steps?

Every probe halves the range, so a list of $n$ items needs at most $\lfloor \log_2 n \rfloor + 1$ probes. A list of 1000 items needs at most 10 probes, and a list of a million items needs at most 20, where linear search might need a million comparisons. If the list doubles in size, binary search needs only one more probe.

### Common bugs

- Writing `lo = mid` or `hi = mid` instead of `mid + 1` or `mid - 1`, which can loop forever.
- Starting with `hi = len(xs)` while the loop condition assumes `hi` is a valid index.
- Using binary search on a list that is not sorted.

@example
title: Tracing a binary search
problem: Trace `binary_search([2, 5, 8, 12, 16, 23, 38], 23)`.
step: At the start `lo = 0` and `hi = 6` (the list has 7 items).
step: First pass: `mid = (0 + 6) // 2 = 3`, and `xs[3]` is `12`. Since `12 < 23`, set `lo = 4`.
step: Second pass: `mid = (4 + 6) // 2 = 5`, and `xs[5]` is `23`, which equals the target, so return `5`.
answer: `5`, after 2 probes

@example
title: Counting steps for two searches
problem: How many comparisons do linear search and binary search make to find `38` in `[2, 5, 8, 12, 16, 23, 38]`?
step: Linear search checks the items in order: 2, 5, 8, 12, 16, 23 and 38. That is 7 comparisons, because `38` is the last item.
step: Binary search starts with `lo = 0`, `hi = 6`, `mid = 3` and `xs[3] = 12`. This is too small, so `lo = 4`.
step: Next `mid = 5` and `xs[5] = 23`, again too small, so `lo = 6`.
step: Then `mid = 6` and `xs[6] = 38`, which is the target. That is 3 probes.
step: So here binary search takes 3 comparisons against 7. The gap grows quickly with the size of the list: for a million items the worst cases are about 20 and 1,000,000.

@mistakes
- Putting `return -1` inside the loop, so the search gives up after the first item.
- Using binary search on an unsorted list and trusting the answer.
- Updating with `lo = mid` or `hi = mid`, so the range may stop shrinking and the loop never ends.
- Mixing up the item and its index: the function returns the position, not the value.

tests:
```python
data = [1, 3, 3, 5, 8]
assert first_at_least(data, 3) == 1
assert first_at_least(data, 4) == 3
assert first_at_least(data, 0) == 0
assert first_at_least(data, 9) == 5

```
model:
```python
def first_at_least(xs, limit):
    lo = 0
    hi = len(xs)
    while lo < hi:
        mid = (lo + hi) // 2
        if xs[mid] < limit:
            lo = mid + 1
        else:
            hi = mid
    return lo
```
hint: The answer is a position between 0 and `len(xs)`, so the search range starts as `lo = 0` and `hi = len(xs)`.
hint: If `xs[mid] < limit`, the answer is to the right of `mid`; otherwise `mid` itself could be the answer, so keep it in the range with `hi = mid`.
solution: Keep the invariant that every item before `lo` is smaller than `limit` and every item from `hi` on is at least `limit`. Loop while `lo < hi`: a too-small middle item moves `lo` to `mid + 1`, and otherwise `hi` becomes `mid`. When `lo == hi` that position is the answer, and it equals `len(xs)` when no item is large enough.

@quiz num
prompt: A sorted list has 1000 items. Using the `lo`/`hi` method from this lesson, what is the largest number of probes (items examined) that a binary search can need, for any target, present or absent? Give the number.
answer: 10
check: floor(log2(1000)) + 1
hint: Each probe halves the range, so ask how many times 1000 can be halved before nothing is left; compare $2^{10} = 1024$.
solution: The worst case is $\lfloor \log_2 1000 \rfloor + 1 = 9 + 1 = 10$ probes: the range has at most 1000, 500, 250, 125, 62, 31, 15, 7, 3 and 1 items before the successive probes, so after the tenth probe nothing is left. This matches $2^{10} = 1024 > 1000$.
