@article
Gradient descent as you met it in C12 computes the gradient over the whole data set before every step. With a million examples that is a million forward and backward passes for one small move. But the data set is a sample from a distribution, so a gradient computed on a random handful of examples is already a decent guide. Taking many cheap, noisy steps is usually much faster than taking a few exact ones. That is **stochastic gradient descent** (SGD), the workhorse of deep learning.

### Mini-batches and epochs

Let the loss be an average over $n$ examples, $L(\boldsymbol{\theta}) = \frac{1}{n}\sum_{i=1}^{n} \ell_i(\boldsymbol{\theta})$. A **mini-batch** $\mathcal{B}$ of $B$ examples gives the estimate

$$\mathbf{g}_{\mathcal{B}} = \frac{1}{B}\sum_{i \in \mathcal{B}} \nabla_{\boldsymbol{\theta}}\, \ell_i(\boldsymbol{\theta}), \qquad \boldsymbol{\theta} \leftarrow \boldsymbol{\theta} - \eta\, \mathbf{g}_{\mathcal{B}}.$$

If the batch is a uniformly random sample, $\mathbb{E}[\mathbf{g}_{\mathcal{B}}] = \nabla L(\boldsymbol{\theta})$: the estimate is unbiased, and its variance shrinks roughly like $1/B$. One pass through all the data is an **epoch**. In practice the examples are shuffled at the start of each epoch and cut into consecutive batches, so every example is used exactly once per epoch. With $n$ examples and batch size $B$ there are $\lceil n/B \rceil$ updates per epoch, the last batch being smaller when $B$ does not divide $n$: with $n = 10$ and $B = 4$ the batches have sizes $4, 4, 2$. Batch size 1 is online SGD, and $B = n$ is full-batch gradient descent.

### One epoch by hand

Take a one-input logistic model $p = \sigma(wx + b)$ with binary cross-entropy. Week 2's result gives the gradient per example: $\partial\ell/\partial z = p - y$, so $\partial \ell/\partial w = (p - y)x$ and $\partial \ell/\partial b = p - y$. The data are $(-1, 0), (0, 0), (1, 1), (2, 1)$, with $w = b = 0$, $\eta = 0.5$ and batch size 2 (no shuffling, for reproducibility).

Batch 1 is $\{(-1,0),(0,0)\}$. Every $p = 0.5$, so $g_w = \frac{1}{2}\big(0.5 \cdot (-1) + 0.5 \cdot 0\big) = -0.25$ and $g_b = \frac{1}{2}(0.5 + 0.5) = 0.5$. The update gives $w = 0.125$ and $b = -0.25$.

Batch 2 is $\{(1,1),(2,1)\}$. Now $p_1 = \sigma(0.125 - 0.25) = 0.4688$ and $p_2 = \sigma(0.25 - 0.25) = 0.5$, so $g_w = \frac{1}{2}\big((-0.5312)(1) + (-0.5)(2)\big) = -0.7656$ and $g_b = -0.5156$. The update gives $w = 0.5078$ and $b = 0.0078$. The mean loss over all four points fell from $\log 2 = 0.6931$ to $0.4866$ in one epoch (two updates).

### The learning rate

The step size $\eta$ matters more than any other hyperparameter. Mean loss over the four points after epochs 1, 5, 10 and 20 with full-batch gradient descent:

| $\eta$ | epoch 1 | epoch 5 | epoch 10 | epoch 20 |
|---|---|---|---|---|
| 0.01 | 0.6907 | 0.6809 | 0.6690 | 0.6466 |
| 0.5 | 0.5798 | 0.3751 | 0.2795 | 0.1985 |
| 3.0 | 0.2861 | 0.1438 | 0.0979 | 0.0620 |

A rate that is too small barely moves; too large a rate overshoots the valley and the loss bounces or diverges (on this easy, separable data even 3.0 is still stable, but not on harder problems; the largest stable rate is tied to the curvature of the loss). Mini-batch size changes the picture as well: at $\eta = 0.5$ the mean loss after epoch 5 is 0.1932 for $B = 1$, 0.2705 for $B = 2$ and 0.3751 for $B = 4$. Smaller batches make more updates per epoch, and each is noisier. With a fixed learning rate, the noise keeps the parameters jittering around a minimum instead of settling, which is why practitioners decay the learning rate over training.

### In code

```python
import math

def sigmoid(z):
    return 1 / (1 + math.exp(-z))

def run_epoch(w, b, data, lr, batch_size):
    for i in range(0, len(data), batch_size):
        batch = data[i:i + batch_size]
        gw = sum((sigmoid(w * x + b) - y) * x for x, y in batch) / len(batch)
        gb = sum(sigmoid(w * x + b) - y for x, y in batch) / len(batch)
        w, b = w - lr * gw, b - lr * gb
    return w, b

data = [(-1, 0), (0, 0), (1, 1), (2, 1)]
w = b = 0.0
for epoch in range(1, 3):
    w, b = run_epoch(w, b, data, 0.5, 2)
    print(epoch, round(w, 4), round(b, 4))
```

This prints `1 0.5078 0.0078` and `2 0.8383 -0.0435`. In PyTorch the same structure is a `DataLoader` that shuffles and batches, an optimizer such as `torch.optim.SGD`, and the three calls `loss.backward()`, `optimizer.step()` and `optimizer.zero_grad()` inside the loop.

@example
title: One mini-batch update
problem: A logistic model $p = \sigma(wx + b)$ with binary cross-entropy has $w = 1$, $b = 0$. A mini-batch contains $(2, 1)$ and $(-1, 1)$, and the learning rate is $\eta = 0.5$. Compute the updated $w$ and $b$.
step: Predictions: $p_1 = \sigma(2) = 0.8808$ and $p_2 = \sigma(-1) = 0.2689$.
step: Per-example errors $p - y$: $-0.1192$ and $-0.7311$.
step: Averages: $g_w = \frac{1}{2}\big((-0.1192)(2) + (-0.7311)(-1)\big) = \frac{1}{2}(0.4927) = 0.2464$ and $g_b = \frac{1}{2}(-0.1192 - 0.7311) = -0.4251$.
step: Update: $w = 1 - 0.5 \cdot 0.2464 = 0.8768$ and $b = 0 - 0.5\cdot(-0.4251) = 0.2126$.
answer: $w \approx 0.877$ and $b \approx 0.213$.

@example
title: Counting updates
problem: A data set has $n = 2{,}500$ examples and is trained for 8 epochs with batch size 64. How many parameter updates are made, and what is the size of the last batch of each epoch?
step: Updates per epoch: $\lceil 2500/64 \rceil = \lceil 39.06 \rceil = 40$.
step: Total updates: $8 \times 40 = 320$.
step: The first 39 batches hold $39 \times 64 = 2496$ examples, so the last batch holds $2500 - 2496 = 4$ examples.
answer: 320 updates; the last batch of each epoch has 4 examples.

@mistakes
- Summing the per-example gradients instead of averaging them: the update then scales with the batch size, and a learning rate tuned for one batch size breaks for another.
- Forgetting to shuffle between epochs, so every epoch sees the same batches in the same order and the batches can be correlated with the data's order (for example sorted by class).
- Computing the number of updates per epoch as $n/B$ rounded down: the final partial batch is still used (unless you deliberately drop it).
- Judging the learning rate from one noisy update rather than from the trend of the loss over several epochs.

```python
import random

def make_batches(data, batch_size, rng):
    """Shuffle a copy of data and split it into consecutive batches."""
    items = list(data)
    rng.shuffle(items)
    return [items[i:i + batch_size] for i in range(0, len(items), batch_size)]
```
hint: Copy the list first, shuffle the copy with `rng.shuffle`, then slice it with a step of `batch_size`.
solution: Shuffling a copy leaves the caller's data untouched, and slicing `items[i:i + batch_size]` over `range(0, n, batch_size)` yields full batches followed by one smaller batch when the size does not divide $n$. The test with a fixed seed checks reproducibility without checking any particular order.

model:
```python
import math

def sgd_epoch(w, b, data, lr, batch_size, drop_last=False):
    """One epoch of mini-batch SGD for logistic regression (no shuffling)."""
    for i in range(0, len(data), batch_size):
        batch = data[i:i + batch_size]
        if drop_last and len(batch) < batch_size:
            break
        gw = gb = 0.0
        for x, y in batch:
            err = 1 / (1 + math.exp(-(w * x + b))) - y
            gw += err * x
            gb += err
        w -= lr * gw / len(batch)
        b -= lr * gb / len(batch)
    return w, b
```
hint: Inside the loop over batches, compute the predictions with the current `w` and `b`, average the errors times $x$ and the errors alone, then update both parameters before the next batch.
solution: Each batch updates the parameters, and the next batch uses the updated values; this differs from full-batch descent, which is the first test (batch size 5 equals the whole data set). Dividing by `len(batch)` (not `batch_size`) matters for the partial last batch, and with `drop_last` that batch is skipped altogether.

model:
```python
import math

def train_logistic(data, lr, batch_size, epochs):
    """Mini-batch SGD for one-input logistic regression; returns the loss curve."""
    def sig(z):
        return 1 / (1 + math.exp(-z))

    w = b = 0.0
    losses = []
    for _ in range(epochs):
        for i in range(0, len(data), batch_size):
            batch = data[i:i + batch_size]
            gw = sum((sig(w * x + b) - y) * x for x, y in batch) / len(batch)
            gb = sum(sig(w * x + b) - y for x, y in batch) / len(batch)
            w, b = w - lr * gw, b - lr * gb
        total = 0.0
        for x, y in data:
            p = sig(w * x + b)
            total -= y * math.log(p) + (1 - y) * math.log(1 - p)
        losses.append(total / len(data))
    return w, b, losses
```
hint: Wrap the batch loop from `sgd_epoch` in a loop over epochs, and after each epoch compute the loss on the whole data set with the updated parameters.
solution: The loss is recorded on all the data after the epoch's updates, not on the batches seen during it. With a learning rate of 0 nothing changes and the loss stays at $\log 2$, which is one of the tests.
