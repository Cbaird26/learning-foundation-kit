@article
A search engine is asked for "U.S.A." and a document says "USA"; a spam filter sees "FREE!!!" and "free". To a computer, text is a string of characters, and nothing says which strings count as the same word. Before any model can be trained, we must decide what the basic units are and which spellings to treat alike. This is **text normalization**, and its first step is **tokenization**: splitting a string into a list of **tokens**.

### Tokens and types

Take the sentence "It was the best of times, it was the worst of times." If we lowercase it and treat each word and each punctuation mark as a token, there are 14 **tokens**. Only 9 of them are different: it, was, the, best, of, times, the comma, worst, and the period. The distinct tokens are the **types**, and the set of all types is the **vocabulary** $V$. The **type-token ratio** is $|V| / N$, where $N$ is the number of tokens: here $9/14 \approx 0.643$. Longer texts reuse words, so the ratio falls as the text grows. An empirical regularity (the Herdan–Heaps law) says the vocabulary grows roughly like a power $N^{\beta}$ of the text length with $\beta$ below 1, so a bigger corpus typically contains new types.

### Choices hidden in "split into words"

Splitting on spaces fails quickly: "times," would be a different type from "times". Every rule is a decision, and none is right for all tasks:

| string | possible tokens | issue |
|---|---|---|
| `can't` | `can't` or `ca` + `n't` or `can` + `'` + `t` | contractions |
| `e-mail` | one token or three | hyphens |
| `3.5` | `3.5` or `3` `.` `5` | numbers, decimal points |
| `Mr.` | `Mr.` or `Mr` + `.` | the period is not a sentence end |
| `New York` | two tokens or one | multiword names |

A **regular expression** (a pattern language for strings) lets us write the decisions down. The pattern below keeps a word with an internal apostrophe together, keeps a decimal number together, and makes every other non-space character its own token. The `|` means "or", and the alternatives are tried left to right at each position.

```python
import re

TOKEN = r"[a-z]+(?:'[a-z]+)?|\d+(?:\.\d+)?|[^\sa-z\d]"

def tokenize(text):
    """Lowercase text and return its tokens."""
    return re.findall(TOKEN, text.lower())

tokens = tokenize("It was the best of times, it was the worst of times.")
print(len(tokens), len(set(tokens)), len(set(tokens)) / len(tokens))
```

This prints `14 9 0.6428571428571429`.

### Normalization

After tokenizing we often map variants to one form. **Case folding** lowercases everything. It merges "The" and "the", but it also merges "US" (the country) with "us" (the pronoun), so systems for some tasks keep case. **Stemming** chops suffixes by rules (the Porter stemmer is the classic); it is crude, and it can map different words to one stem or one word to different stems. **Lemmatization** maps each word to its dictionary form ("were" to "be") and needs a lexicon and the word's part of speech. Which steps help depends on the task: topic classification usually benefits, while a task that depends on tense or names may be hurt.

### Sentences

Splitting text into sentences seems easy: cut after `.`, `!` or `?`. But "Dr. Smith left." contains a period that does not end a sentence. A simple fix is to cut only when the next word starts with a capital letter and the word before the period is not a known abbreviation. This works for tidy text and fails on "He moved to Washington D.C. Then he left," where the same rule cannot tell whether the period ends the sentence.

### Why we need fixed rules

The tokenizer is part of the model: the vocabulary, the counts and every later probability depend on it. If training and test text are tokenized differently, the model sees "words" it has never met. Later weeks replace word-level tokens with subword units, which solve the problem of unseen words, but they too must be applied identically at training and test time.

@mistakes
- Counting types as tokens: "the" appearing 5 times is 5 tokens but 1 type. Say which one a question asks for.
- Tokenizing training and test text with different rules, so words that look familiar to a person are unknown to the model.
- Lowercasing and stemming for every task. Merging "US" with "us", or "organization" with "organ", removes information that some tasks need.
- Splitting sentences on every period, which breaks abbreviations and decimal numbers.

model:
```python
ABBREVIATIONS = {"mr.", "mrs.", "dr."}


def split_sentences(text):
    """Split text into sentences using the capital-letter and abbreviation rule."""
    words = text.split()
    sentences = []
    current = []
    for i, word in enumerate(words):
        current.append(word)
        last = i == len(words) - 1
        ends = word[-1] in ".!?" and word.lower() not in ABBREVIATIONS
        if last or (ends and words[i + 1][0].isupper()):
            sentences.append(" ".join(current))
            current = []
    return sentences
```
hint: Walk through the words with an index so that you can look at `words[i + 1]`, and collect words in a list until a boundary is found.
solution: Keep a list of the words of the current sentence. After adding each word, test whether it is the last word, or ends with terminal punctuation, is not an abbreviation, and the next word starts with a capital letter; if so, close the sentence. The test "Mr. Who?" checks that the abbreviation rule stops a split even before a capitalized word.

model:
```python
def light_stem(word):
    """Strip ing, ed or s when at least three letters remain."""
    for suffix in ("ing", "ed", "s"):
        if word.endswith(suffix) and len(word) - len(suffix) >= 3:
            return word[: -len(suffix)]
    return word
```
hint: Loop over the suffixes in order and return as soon as one applies; check the stem length before cutting.
solution: The length condition protects short words such as `sing` and `bus`. The test with `glass` shows the crudeness of rule-based stemming: it cuts the final `s` of a word that is not plural.
