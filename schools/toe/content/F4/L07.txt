@article
Every programmer spends much of their time finding out why a program does not do what they meant. Debugging is a skill with a method, not a matter of luck.

### Three kinds of bug

- A **syntax error** means Python cannot even read the program: a missing colon, an unmatched bracket. Nothing runs.
- A **runtime error** (an *exception*) stops the program part-way and prints a traceback.
- A **logic error** lets the program run to the end and gives a wrong answer. These are the dangerous ones, because nothing warns you.

### Reading a traceback

```
Traceback (most recent call last):
  File "model.py", line 12, in <module>
    result = average(data)
  File "model.py", line 5, in average
    return total / count
ZeroDivisionError: division by zero
```

Read from the **bottom**. The last line gives the exception type and message. The line of code just above it is where Python gave up. Lines further up show who called whom. The mistake may lie in the failing line or in the value that was passed to it, so look at both.

| exception | typical cause |
|---|---|
| `NameError` | a misspelled or undefined name |
| `TypeError` | wrong kind of value, such as `"5" + 3`, or calling something that is not a function |
| `IndexError` | a position outside a list: `v[3]` when `len(v)` is 3 |
| `ValueError` | right type, impossible value: `float("abc")`, `math.sqrt(-1)` |
| `ZeroDivisionError` | dividing by zero |

### A method for logic errors

1. **Reproduce** the failure with the smallest input you can.
2. **Predict** by hand what each step should produce.
3. **Inspect**: print intermediate values and find the first place where reality differs from your prediction.
4. **Change one thing**, then re-run.
5. **Keep** the failing case as a permanent test.

Halving works well: print a value in the middle of the program. If it is already wrong, the bug is in the first half; otherwise it is in the second.

### Assertions

```python
def mean(values):
    assert len(values) > 0, "mean of an empty list"
    return sum(values) / len(values)
```

`assert condition, message` raises `AssertionError` when the condition is false. It is an executable statement of what you believe is true, and it stops the program at the first moment that belief fails, not ten steps later.

### try and except

```python
try:
    x = float(text)
except ValueError:
    x = float("nan")
```

Catch a specific exception that you expect and know how to handle. A bare `except:` hides every error, including your typos, so avoid it.

@example
title: Reading a traceback
problem: This program ends with the error `ZeroDivisionError: division by zero` pointing at the `return` line. Explain why, and fix it.
```python
def mean(values):
    total = 0
    for v in values:
        total += v
    return total / len(values)

data = []
print(mean(data))
```
step: Start at the bottom of the traceback: the type is `ZeroDivisionError`, so some division has a denominator of 0.
step: The failing line is `return total / len(values)`. The only denominator there is `len(values)`.
step: The call passes `data = []`, an empty list, so `len(values)` is 0. The bug is the unchecked input, not the arithmetic.
step: Decide what an empty list should mean. A reasonable fix is to start the function with `assert len(values) > 0, "mean of an empty list"`, which gives a clear message instead of a confusing one.

@example
title: Finding a logic error
problem: This function should return $1^2 + 2^2 + \dots + n^2$. For `sum_squares(3)` we expect 14 but the program prints 5. Find the bug.
```python
def sum_squares(n):
    total = 0
    for k in range(1, n):
        total += k * k
    return total
```
step: Reproduce with the smallest case: `sum_squares(3)` gives 5. Predict by hand: $1 + 4 + 9 = 14$.
step: The wrong answer 5 equals $1 + 4$, so the term $3^2 = 9$ is missing. Put `print(k)` inside the loop to confirm: it shows only 1 and 2.
step: `range(1, n)` stops before `n`. Change it to `range(1, n + 1)`.
step: Re-run: `sum_squares(3)` is now 14. Keep `assert sum_squares(3) == 14` as a permanent test.

@mistakes
- Reading the traceback from the top. Start at the last line, then the line of code just above it.
- Changing several things at once, so you cannot tell which change mattered.
- Writing a bare `except:` that silences every error and hides real bugs.
- Naming a variable after a built-in such as `sum`, `max` or `list`. The built-in is then shadowed and calls to it fail.
- Believing that a program with no error message is correct. Logic errors raise nothing.

v = [1, 2, 3]

@practice mc
prompt: A student writes `f = c * 5 / 9 + 32` to convert Celsius to Fahrenheit. The program runs without any message and prints about 87.6 for `c = 100`, but the correct value is 212. What kind of error is this?
choice*: A logic error: the program runs but the formula is wrong.
choice: A syntax error, because Python cannot read the formula.
choice: A runtime exception, because the result is too large.
choice: No error: Python rounds results, so the answers differ slightly.
hint: Did Python complain, or did it quietly produce a wrong number?

@practice num
prompt: How many times does the `print` call finish successfully before the program stops with an error?
```python
values = [4, 2, 1, 0, 5]
for v in values:
    print(8 / v)
```
answer: 3
check: [4, 2, 1, 0, 5].index(0)
hint: Look for the first value of `v` that makes the division fail.
hint: The values 4, 2 and 1 are fine. What happens at 0?
solution: The loop prints `2.0`, `4.0` and `8.0` for `v = 4, 2, 1`. For `v = 0` the division raises `ZeroDivisionError`, so the program stops. The last element 5 is never reached. The call finished 3 times.

@practice num
prompt: A function meant to compute the mean of a list divides by `len(values) - 1` by mistake. For `values = [2, 4, 9]`, by how much does the buggy result exceed the correct mean?
answer: 2.5
check: (lambda v: sum(v) / (len(v) - 1) - sum(v) / len(v))([2, 4, 9])
hint: Compute the correct mean first, then the buggy one.
hint: The sum is 15. Divide by 3 for the correct mean and by 2 for the buggy one.
solution: The correct mean is $15/3 = 5$. The buggy function returns $15/2 = 7.5$. The difference is $7.5 - 5 = 2.5$.

@practice self
prompt: This function should return the largest number in a list, but a tester reports that it fails on some inputs.
```python
def maximum(values):
    best = 0
    for v in values:
        if v > best:
            best = v
    return best
```
Find an input for which it returns the wrong answer, say what the correct answer would be, explain the bug, and give a corrected version.
hint: Think about what the function returns when every number is negative.
hint: What does `best` start at, and can any item ever beat it?
solution: For `maximum([-3, -1, -2])` the function returns `0` but the correct answer is `-1`. The starting value `best = 0` is larger than every item, so the `if` never fires. A corrected version starts from an actual item:
```python
def maximum(values):
    assert len(values) > 0, "maximum of an empty list"
    best = values[0]
    for v in values:
        if v > best:
            best = v
    return best
```
A good permanent test is `assert maximum([-3, -1, -2]) == -1`.
rubric: The failing input has only negative numbers (or numbers all below the starting value), and the correct answer is stated.
rubric: The explanation names the cause: the starting value 0 is not taken from the data.
rubric: The corrected code initialises best from the first item, or from minus infinity.
rubric: The learner keeps the failing case as a test.

@quiz mc
prompt: What happens when this program runs?
```python
sum = 0
for v in [1, 2, 3]:
    sum += v
print(sum([4, 5]))
```
choice*: `TypeError`, because `sum` is now an integer and cannot be called.
choice: It prints `9`.
choice: `NameError`, because `sum` has not been defined.
choice: It prints `6`.
hint: After the first line, what is the name `sum` attached to?
solution: The assignment `sum = 0` replaces the built-in function with the number 0 (and the loop turns it into 6). Then `sum([4, 5])` tries to call an integer, which raises `TypeError: 'int' object is not callable`.

@quiz num
prompt: What does this program print?
```python
def safe_ratio(a, b):
    try:
        return a / b
    except ZeroDivisionError:
        return -1

print(safe_ratio(6, 3) + safe_ratio(1, 0))
```
answer: 1
check: (lambda r: r(6, 3) + r(1, 0))(lambda a, b: a / b if b != 0 else -1)
hint: Evaluate the two calls separately. Which one raises the exception?
hint: The first call gives 2.0. The second is caught and returns -1.
solution: `safe_ratio(6, 3)` returns `2.0`. In `safe_ratio(1, 0)` the division raises `ZeroDivisionError`, which is caught, so the call returns `-1`. The sum is $2.0 + (-1) = 1.0$.
