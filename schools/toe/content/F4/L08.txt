@article
A **test** is a small program that compares what a function returns with an answer you know is right. Tests turn "it looks fine" into evidence, and they catch the bug you introduce next month.

### Writing tests

```python
def mean(values):
    return sum(values) / len(values)

assert mean([1, 2, 3]) == 2
assert mean([5]) == 5          # boundary: a single item
assert mean([-2, 2]) == 0      # symmetry gives a known answer
```

Good tests come from: values you can work out by hand, boundary cases (zero, one item, the edge of an allowed range), properties that must hold (converting there and back returns the start), and a second, independent method (a formula against a loop). Choose inputs that **cannot hide a bug**: a test with `v = 2` cannot tell `v ** 2` from `v * 2`.

### Floats are inexact

A float has 53 binary digits, about 15 to 16 decimal digits. Most decimal fractions, such as $0.1$, have no finite binary form, so they are rounded:

```python
print(0.1 + 0.2 == 0.3)    # False
print(0.1 + 0.2)           # 0.30000000000000004
```

**Machine epsilon**, `np.finfo(float).eps`, is about $2.2\times 10^{-16}$. It is the gap between $1.0$ and the next float, so it measures relative precision. Rounding errors are tiny, but they accumulate: adding `0.1` ten times gives `0.9999999999999999`. Subtracting nearly equal numbers loses digits, because the leading digits cancel and only the noisy last ones remain: `(1 + 1e-16) - 1` is `0.0`, not `1e-16`.

### Comparing floats

Never test computed floats with `==`. Use a tolerance:

```python
import math
math.isclose(0.1 + 0.2, 0.3)             # True
abs(a - b) <= 1e-9                       # absolute test
math.isclose(a, b, rel_tol=1e-9)         # relative test
```

The **absolute error** of an approximation $\tilde{x}$ to $x$ is $|\tilde{x} - x|$, and the **relative error** is $|\tilde{x} - x| / |x|$. Relative error is the fair measure when sizes vary: an error of $0.001$ is huge for a quantity near $10^{-3}$ and negligible for one near $10^{6}$. Note that `math.isclose` has `abs_tol = 0` by default, so comparing with exactly zero needs `abs_tol=1e-12` or similar. NumPy's `np.isclose` uses different, looser defaults (`rtol=1e-5`, `atol=1e-8`).

### Passing is not proof

A passing test shows only that the function agrees with you on that input. A set of tests that passes means "no bug found so far." Vary the inputs so that different kinds of mistake would show up, and always include a case near each boundary.

@example
title: Testing a conversion with tolerances
problem: Write tests for `to_fahrenheit(c)`, which should return $\tfrac{9}{5}c + 32$.
step: Pick values that are known exactly: $0\,^\circ$C gives $32$, $100\,^\circ$C gives $212$, and $-40$ is the same on both scales. Write `assert to_fahrenheit(0) == 32`, and similarly for the others.
step: Add a case with a non-integer so that float rounding matters, and compare with a tolerance: `assert math.isclose(to_fahrenheit(36.6), 97.88)`.
step: Add a round-trip property: converting to Fahrenheit and back with the inverse function should return the start, again within a tolerance.
step: All five tests together probe different parts of the formula: the offset, the slope, the sign, and rounding. If any one fails, the message shows which.

@example
title: A bug that one test misses
problem: A function `kinetic_energy(m, v)` was meant to return $\tfrac{1}{2}mv^2$ but has the line `return 0.5 * m * v * 2`. A first test uses `m = 1`, `v = 2` and expects 2. Does the test detect the bug? Find a test that does.
step: Evaluate the buggy line for the first test: $0.5 \cdot 1 \cdot 2 \cdot 2 = 2$. The test passes, so it does not detect the bug.
step: The reason is that for $v = 2$ we have $v^2 = 2v$, so the right and wrong formulas agree there. The test input hid the bug.
step: Try `m = 2`, `v = 3`. The correct value is $\tfrac{1}{2} \cdot 2 \cdot 9 = 9$ but the buggy line gives $0.5 \cdot 2 \cdot 3 \cdot 2 = 6$. The assertion fails, and the bug is found.
step: Keep both tests. Better, add a third at a larger speed such as $v = 10$, where the formulas differ greatly.

@mistakes
- Using `==` to compare computed floats. Use `math.isclose` or an explicit tolerance.
- Testing only one typical input, which may coincidentally hide the bug (such as `v = 2` for `v ** 2`).
- Using an absolute tolerance for quantities of very different sizes. Use a relative tolerance.
- Comparing to exactly zero with `math.isclose` and its default `abs_tol` of zero.
- Concluding that code is correct because its tests pass. Tests can only fail to find bugs.

prompt: A calculation should produce $0.3$, but the computed value `x` may carry a tiny rounding error. Which test is the most sensible?
choice*: `assert abs(x - 0.3) < 1e-9`
choice: `assert x == 0.3`
choice: `assert x is 0.3`
choice: `assert str(x) == "0.3"`
hint: Rounding error means `x` can differ from $0.3$ in the last few binary digits.

answer: 4.025e-4
check: abs(22 / 7 - math.pi) / math.pi

@practice num
prompt: Python evaluates each of these four comparisons to `True` or `False`:
```python
0.5 + 0.25 == 0.75
0.1 + 0.2 == 0.3
0.1 * 3 == 0.3
1e16 + 1 == 1e16
```
How many of them are `True`?
answer: 2
check: sum([0.5 + 0.25 == 0.75, 0.1 + 0.2 == 0.3, 0.1 * 3 == 0.3, 1e16 + 1 == 1e16])
hint: Numbers like 0.5 and 0.25 are sums of powers of two and are stored exactly. Numbers like 0.1 and 0.3 are not.
hint: Near $10^{16}$ the gap between neighbouring floats is 2.
solution: The first is `True`, because $0.5$, $0.25$ and $0.75$ are exact in binary. The second and third are `False`, because of rounding error in 0.1, 0.2 and 0.3. The fourth is `True`: at $10^{16}$ adjacent floats are 2 apart, so adding 1 rounds back to $10^{16}$. That makes 2.

prompt: The function `hyp(a, b)` should return $\sqrt{a^2 + b^2}$ but a bug has made it return `(a ** 2 + b) ** 0.5`. For a fixed $a$, for which values $b \ge 0$ would a test give the correct answer anyway, hiding the bug? Give all such values.

@practice self
prompt: A function limits a number to a range:
```python
def clamp(x, lo, hi):
    if x < lo:
        return lo
    if x > hi:
        return lo
    return x
```
One line was altered on purpose. Write a set of `assert` tests (with expected values, for `lo = 0` and `hi = 10`) that would detect the inserted bug. State which test fails, and give the repaired line.
hint: A range limiter has three regions and two boundaries. Test all of them.
hint: Which test would pass for a function that always returned `lo` outside the range?
solution: Tests:
```python
assert clamp(5, 0, 10) == 5      # inside the range
assert clamp(-3, 0, 10) == 0     # below the range
assert clamp(15, 0, 10) == 10    # above the range
assert clamp(0, 0, 10) == 0      # lower boundary
assert clamp(10, 0, 10) == 10    # upper boundary
```
The test `clamp(15, 0, 10) == 10` fails, because the function returns 0 for values above the range. The second `return lo` should be `return hi`. Tests that only use inside or below values would miss the bug.
rubric: The tests cover below, inside and above the range, and at least one boundary, each with an expected value written down in advance.
rubric: The learner identifies the above-range test as the failing one and explains why.
rubric: The repaired line is "return hi" in the branch for x > hi.
rubric: The learner notes that tests using only inside or below inputs would have passed.

@quiz mc
prompt: A function passes five tests that you wrote. What can you conclude?
choice*: It agrees with your expected answers on those five inputs. Other inputs may still fail.
choice: The function is correct for all inputs.
choice: The function is correct as long as the inputs are whole numbers.
choice: Any failure in the future must come from rounding error.
hint: What do the tests actually exercise?
solution: Tests sample a few inputs. They can show that a bug exists, but they cannot show that none exists. More varied tests, especially near boundaries, raise your confidence without proving correctness.

@quiz num
prompt: What is `abs((0.1 + 0.2) - 0.3)` in Python? Give the value in scientific notation.
answer: 5.55e-17
check: abs((0.1 + 0.2) - 0.3)
tol: 1%
hint: The sum prints as `0.30000000000000004`.
hint: Subtract $0.3$ and keep only the leftover digits.
solution: The sum `0.1 + 0.2` is the float just above the float nearest to $0.3$. The two differ by exactly one spacing between neighbouring floats near $0.3$, which is $2^{-54} \approx 5.55 \times 10^{-17}$, a quarter of machine epsilon.
