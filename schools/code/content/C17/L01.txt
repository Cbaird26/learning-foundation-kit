@article
Security is not a feature you add at the end. It is a property of a whole system, and it only has meaning relative to **what you are protecting** and **who you are protecting it from**. A bank vault is secure against a pickpocket and not against a government with a drill. The first job of a defender is therefore to write those two things down.

### Goals

The classic goals are the **CIA triad**:

- **Confidentiality**: only authorized parties can read the data.
- **Integrity**: data and programs are changed only by authorized parties, and tampering is detectable.
- **Availability**: authorized users can use the system when they need it.

Related properties are **authenticity** (a message really comes from who it claims), **non-repudiation** (a sender cannot credibly deny an action) and **accountability** (actions can be traced to a principal through logs).

### Design principles

These recur throughout the course.

- **Least privilege**: give each component and user only the access its task needs. A reporting job that reads one table should not connect as the database administrator.
- **Defense in depth**: use several independent layers, so one failure is not fatal.
- **Fail-safe defaults** (deny by default): when no rule matches, or a check errors, refuse.
- **Complete mediation**: check authorization on every access, on the server, not once at the start.
- **Economy of mechanism**: simpler designs have fewer bugs.
- **Separation of privilege**: require more than one condition for a sensitive action, such as two approvals.
- **Open design** (Kerckhoffs's principle): security must not depend on the design being secret, only on keys.
- **Psychological acceptability**: if the secure path is painful, people route around it.

### Threat modeling

A **threat model** states the assets, the adversary's capabilities and goals, and the assumptions you rely on. A practical method:

1. **Draw the system**: components, data stores and data flows.
2. **Mark trust boundaries**: lines where data crosses between zones of different trust, such as the internet to your web server, or the web server to the database. Every flow across a boundary is part of the **attack surface** and its data must be treated as untrusted.
3. **Enumerate threats** with **STRIDE**: Spoofing (violates authenticity), Tampering (integrity), Repudiation (non-repudiation), Information disclosure (confidentiality), Denial of service (availability), Elevation of privilege (authorization).
4. **Rank** them and choose mitigations.

A simple ranking uses **risk = likelihood × impact**, each on a small scale such as 1 to 5, or expected loss: annualized loss expectancy = annual rate of occurrence × loss per incident.

```python
threats = [("weak admin login", 4, 5), ("verbose error pages", 3, 2)]
for name, likelihood, impact in threats:
    print(name, likelihood * impact)   # 20 and 6
```

Rankings are judgment calls, but writing them down makes the judgment visible and arguable. Mitigations then reduce likelihood (validation, authentication), reduce impact (least privilege, encryption, backups) or transfer risk (insurance). Some risk is accepted knowingly. The OWASP Top 10:2025 list includes **A06 Insecure Design** because flaws found at this stage cannot be patched away by careful coding later.

@example
title: Threat-modeling a photo-sharing app
problem: A web app lets users sign in and upload photos. Browsers talk to a web server, which stores files in object storage and records in a database. List trust boundaries and one STRIDE threat for two flows.
step: Draw the zones: the internet (untrusted browsers), the web server, and the back end (database and storage).
step: Boundary 1 is internet to web server. Every request field, header and uploaded file arrives here and is untrusted. Boundary 2 is web server to back end, where the server's credentials matter.
step: Flow "sign-in request": an attacker who guesses or steals a password performs **Spoofing**. Mitigations: slow password hashing, rate limiting, multi-factor authentication.
step: Flow "photo download by URL": changing an id in the URL to read someone else's photo is **Information disclosure** caused by missing access checks. Mitigation: complete mediation, so the server checks ownership on every request.
step: The server connects to the database as a user that can only read and write the app's tables. If the server is compromised, least privilege limits the damage.
@example
title: Ranking threats by risk
problem: Threats scored as (likelihood, impact): A = (2, 5), B = (4, 3), C = (5, 1), D = (3, 4). Which should be addressed first, and in what order?
step: Compute likelihood × impact for each: A is 10, B is 12, C is 5, D is 12.
step: Sort from largest to smallest. B and D tie at 12.
step: Break the tie by a stated rule. Choosing the higher impact first puts D before B, because a rare severe event may be less tolerable than a frequent mild one.
step: The order is D, B, A, C. Stating the tie-break rule is part of the model.
answer: D, B, A, C
@mistakes
- Treating security as a list of tools instead of starting from assets and adversaries, so the defenses protect the wrong things.
- Relying on secrecy of the design ("nobody knows our URL scheme") instead of on keys and access checks.
- Checking authorization only in the user interface; the server must check every request itself.
- Failing open: when a check throws an error or a rule is missing, the code allows the action.

```python
def risk_rank(threats):
    ordered = sorted(
        threats, key=lambda t: (-(t[1] * t[2]), -t[2], t[0])
    )
    return [t[0] for t in ordered]
```

```python
CATEGORIES = {
    "authenticity": "Spoofing",
    "integrity": "Tampering",
    "non-repudiation": "Repudiation",
    "confidentiality": "Information disclosure",
    "availability": "Denial of service",
    "authorization": "Elevation of privilege",
}


def stride_category(violated):
    if violated not in CATEGORIES:
        raise ValueError(violated)
    return CATEGORIES[violated]
```

solution: Keep the six pairs in a dictionary, raise `ValueError` for unknown keys, and return the mapped value otherwise.

prompt: Write `crossing_flows(flows, trust)`. `trust` is a dict from zone name to an integer trust level (higher is more trusted). Each flow is a tuple `(source_zone, destination_zone, data_name)`. Return the sorted list of `data_name` values for flows that go from a less trusted zone to a more trusted zone, which are the flows whose data must be validated. Flows within a zone or toward a less trusted zone are not included.
starter:
```python
def crossing_flows(flows, trust):
    pass
```
tests:
```python
trust = {"internet": 0, "web": 1, "db": 2}
flows = [
    ("internet", "web", "form"),
    ("web", "db", "query"),
    ("db", "web", "rows"),
    ("web", "web", "log"),
]
assert crossing_flows(flows, trust) == ["form", "query"]
assert crossing_flows([], trust) == []
assert crossing_flows([("db", "internet", "page")], trust) == []
assert crossing_flows(
    [("internet", "db", "z"), ("internet", "web", "a")], trust
) == ["a", "z"]
```
model:
```python
def crossing_flows(flows, trust):
    names = [
        data
        for src, dst, data in flows
        if trust[src] < trust[dst]
    ]
    return sorted(names)
```
hint: A flow qualifies when the source's trust level is strictly lower than the destination's.
hint: Filter with a comprehension over the three-part tuples, then sort the names.
solution: Keep a flow when `trust[src] < trust[dst]` (strict, so same-zone flows are excluded) and return the sorted data names.
