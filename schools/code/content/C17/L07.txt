@article
**Authentication** establishes who is making a request; **authorization** (next lesson) decides what they may do. Authentication uses **factors**: something you **know** (password), something you **have** (a phone, a hardware key) and something you **are** (a fingerprint). **Multi-factor authentication (MFA)** combines factors from different categories, so stealing a password alone is not enough. Failures here are OWASP A07, **Authentication Failures**.

### Current password guidance

NIST SP 800-63B Revision 4 (final, August 2025) reflects what research found about real users:

- Require at least **15 characters** when a password is the only factor, and at least **8** when it is one part of multi-factor authentication. Allow at least **64** characters, and accept any characters, including spaces and Unicode.
- Impose **no composition rules** (such as "one symbol and one digit") and **no forced periodic changes**. Require a change when there is evidence of compromise.
- **Check new passwords against a blocklist** of common and previously compromised passwords.
- Do not use password hints or knowledge-based security questions.
- Allow pasting, so password managers work.
- Limit the rate of failed attempts.

Length contributes most to the number of possibilities. A passphrase of 4 words picked uniformly from a 7776-word list has $4 \log_2 7776 \approx 51.7$ bits of entropy, if the words are picked at random by a machine or dice.

### Storing passwords

Assume the password database will one day be stolen. The goal is that a stolen database does not hand over the passwords.

1. **Never store plaintext or reversible encryption.**
2. **Hash, and hash slowly.** A fast hash such as plain SHA-256 can be computed billions of times per second on commodity hardware, so low-entropy passwords fall quickly. Use a **purpose-built password hashing function** with a tunable cost: **Argon2id** (the usual first choice), **scrypt**, **bcrypt**, or **PBKDF2** when compliance requires it. Tune the work factor so one verification takes tens to hundreds of milliseconds on your servers, and raise it over time.
3. **Salt every password** with a unique, random value (at least 16 bytes) stored beside the hash. The salt is not secret. It guarantees that two users with the same password have different hashes and defeats precomputed tables, so an attacker must attack each account separately.
4. Optionally add a **pepper**: a secret key kept outside the database (for example in a hardware module) and mixed into the hash.
5. Store the algorithm, parameters and salt with the hash (for example `$argon2id$...`) so you can upgrade parameters later: verify with the stored parameters, and rehash on successful login.

Here is a **teaching stand-in** for a slow hash, which iterates SHA-256 with a salt. Real systems should use a vetted Argon2id, scrypt or bcrypt library, not this:

```python
import hashlib

def toy_hash(password: str, salt: bytes, iterations: int) -> str:
    pw = password.encode()
    h = hashlib.sha256(salt + pw).digest()
    for _ in range(iterations - 1):
        h = hashlib.sha256(h + salt + pw).digest()
    return h.hex()
```

On login, recompute with the stored salt and cost and compare in constant time. Return the same generic error for "no such user" and "wrong password", and avoid timing differences that reveal which accounts exist.

### One-time codes and phishing-resistant factors

**TOTP** (RFC 6238) computes a code from a shared secret and the current time step, using HOTP (RFC 4226): take an HMAC of the counter, then apply **dynamic truncation**: the low 4 bits of the last byte give an offset, four bytes there form an integer (top bit cleared), and the code is that integer modulo $10^{\text{digits}}$. Codes can be typed into a fake site, so they are not phishing-resistant. **WebAuthn** and **passkeys** use public-key signatures bound to the real site's origin, so a look-alike site gets nothing usable. Add rate limiting and alerting against **credential stuffing**, in which passwords leaked elsewhere are tried against your site.

@example
title: Validating a password under NIST rules
problem: A site uses passwords as the only factor. Which of these are acceptable new passwords: `Tr0ub4dor&3` (11 characters), `correct horse battery staple` (28 characters), `aaaaaaaaaaaaaaaaaaaa` (20 characters, not in the blocklist)?
step: Length rule: with a password alone the minimum is 15 characters. `Tr0ub4dor&3` has 11, so it is rejected despite mixing symbols; composition does not replace length.
step: `correct horse battery staple` is 28 characters, uses spaces (allowed) and is not on a blocklist, so it is accepted.
step: The third has 20 characters and is not blocklisted, so these rules alone accept it. A practical verifier would also reject repeated characters through the blocklist or a strength estimator.
answer: The 28-character passphrase is accepted; the 11-character one is rejected; the third passes the stated rules.
@example
title: What a salt buys
problem: Two users choose the same password. Compare what an attacker sees in the stolen database without and with per-user salts.
step: Without salts, both rows contain the same hash. The attacker sees the duplicate and one guess cracks both; a precomputed table of common passwords' hashes works for the whole database.
step: With a 16-byte random salt per user, the same password produces different hashes. A guess must be recomputed with each user's salt.
step: The salt does not slow a single guess; the slow function does that. Salts remove sharing and precomputation, the slow hash raises the price of each guess, and a long password makes the search space huge.
answer: Salts make identical passwords hash differently and block precomputed tables.
@mistakes
- Storing passwords with a fast hash such as plain SHA-256 or MD5, even if salted.
- Using one global salt for all users instead of a unique random salt per password.
- Enforcing composition rules and frequent expiry, which push users toward predictable patterns.
- Telling the user whether the username or the password was wrong, and so leaking which accounts exist.

model:
```python
import hashlib


def hash_password(password, salt, iterations):
    pw = password.encode()
    h = hashlib.sha256(salt + pw).digest()
    for _ in range(iterations - 1):
        h = hashlib.sha256(h + salt + pw).digest()
    return h.hex()


def check_password(record, attempt):
    iterations, salt_hex, digest = record.split("$")
    got = hash_password(attempt, bytes.fromhex(salt_hex), int(iterations))
    if len(got) != len(digest):
        return False
    diff = 0
    for x, y in zip(got, digest):
        diff |= ord(x) ^ ord(y)
    return diff == 0
```
hint: `record.split("$")` gives three strings; convert the first to `int` and the second with `bytes.fromhex`.
hint: Recompute with the stored salt and iteration count, then compare the two hex strings character by character, accumulating differences.
solution: Parse the stored cost and salt, recompute the digest for the attempt, and compare to the stored digest with a loop that does not exit early.

model:
```python
def hotp_truncate(digest, digits=6):
    offset = digest[-1] & 0x0F
    chunk = int.from_bytes(digest[offset:offset + 4], "big")
    return (chunk & 0x7FFFFFFF) % 10 ** digits
```
hint: `digest[-1] & 0x0F` gives the offset; slice four bytes from there.
hint: `int.from_bytes(chunk, "big")` converts the four bytes to an integer before masking and taking the remainder.
solution: Dynamic truncation picks a 4-byte window at a data-dependent offset, clears the sign bit and reduces modulo a power of ten. The tests use the published counter 0 and 1 values for the standard test secret.
