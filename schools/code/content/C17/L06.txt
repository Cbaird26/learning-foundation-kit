@article
A **digital signature** scheme has three algorithms: key generation, **sign** (private key, message to signature) and **verify** (public key, message, signature to accept or reject). A valid signature shows that the holder of the private key approved exactly that message, and anyone can check it, so unlike a MAC it gives **non-repudiation**. Practical schemes sign a hash of the message (**hash-and-sign**). Current choices: RSA with PSS padding, ECDSA, and **EdDSA** (Ed25519); the post-quantum standards are ML-DSA (FIPS 204) and SLH-DSA (FIPS 205).

### Certificates and chains of trust

How does a browser know that a public key belongs to `shop.example`? A **certificate** (X.509) is a signed statement that binds a public key to names. It contains the subject's public key, the **subject alternative names** (the hostnames it is valid for), the issuer, a validity period (not-before and not-after dates) and the issuer's signature. A **certificate authority (CA)** issues certificates.

Trust is built as a **chain**: a **leaf** certificate for the site, signed by an **intermediate** CA, signed by a **root** CA whose certificate is already in the client's trust store. A client accepts a chain only if all of these hold:

1. every signature verifies against the next certificate's public key (and the last one chains to a trusted root);
2. every certificate is within its validity period;
3. each issuing certificate is allowed to act as a CA;
4. the leaf's names match the host being contacted: an exact name, or a wildcard such as `*.example.com`, which matches one label (`www.example.com`) but not `example.com` or `a.b.example.com`;
5. the certificate has not been revoked.

**Revocation** is handled by lists (CRLs) and online status checks (OCSP), but is unreliable in practice, so ecosystems also rely on short certificate lifetimes. **Certificate Transparency** logs make every issued certificate publicly auditable, so a mis-issued one can be detected. **Certificate pinning** (accepting only expected keys or certificates) reduces dependence on CAs but creates an outage risk if the pin is not updated.

### TLS 1.3

**TLS 1.3** (RFC 8446) protects HTTPS and many other protocols. It runs over TCP; HTTP/3 uses QUIC (RFC 9000, RFC 9114), which embeds TLS 1.3 for its handshake. A full handshake takes **one round trip**:

1. **ClientHello**: the client's random value, supported cipher suites, protocol versions, and a **key share**, its ephemeral (EC)DHE public value for one or more groups; also the server name (SNI) and the signature algorithms it accepts.
2. **ServerHello**: the chosen cipher suite and the server's key share. Both sides now compute the shared (EC)DHE secret and derive **handshake traffic keys** with a key-derivation function (HKDF). Everything after this point is encrypted.
3. Server flight, encrypted: **EncryptedExtensions**; **Certificate** (the chain); **CertificateVerify**, a signature over a hash of the handshake so far made with the certificate's private key, proving it holds that key; and **Finished**, a MAC over the whole handshake that proves the handshake was not altered.
4. Client: checks the chain and hostname, the CertificateVerify signature and the Finished MAC, then sends its own **Finished** (optionally a client certificate first). Both derive **application traffic keys**, and data flows protected by an AEAD cipher.

TLS 1.3 offers only AEAD cipher suites (such as `TLS_AES_128_GCM_SHA256`, `TLS_AES_256_GCM_SHA384` and `TLS_CHACHA20_POLY1305_SHA256`) and every full handshake uses an ephemeral (EC)DHE key exchange, so those sessions have **forward secrecy** (a resumption that uses only a pre-shared key, without a fresh (EC)DHE exchange, does not). It removed static RSA key transport, CBC mode, compression and renegotiation. **Session resumption** with a pre-shared key is faster; "0-RTT" early data can be **replayed** by an attacker, so it must only carry requests that are safe to repeat.

In code, always use a vetted library with certificate and hostname verification **on**; turning verification off "just for testing" is a classic way to ship a vulnerable client (OWASP A02 Security Misconfiguration).

@example
title: Validating a chain by hand
problem: A client connects to `www.shop.example`. It receives the chain leaf (subject `www.shop.example`, issuer `Shop Issuing CA`), intermediate (subject `Shop Issuing CA`, issuer `Root One`, CA flag true). Its trust store contains `Root One`. Today lies inside every validity period. Accept?
step: Name check: the leaf lists `www.shop.example`, which equals the requested host.
step: Linkage: the leaf's issuer `Shop Issuing CA` equals the intermediate's subject, and the intermediate is allowed to be a CA.
step: Trust anchor: the intermediate's issuer `Root One` is in the trust store, and all dates are valid.
step: Every check passes (and the signatures verify), so the chain is accepted. If the leaf listed only `*.shop.example`, `www.shop.example` would still match, but `shop.example` would not.
answer: Accept
@example
title: Counting round trips
problem: Over TCP, how many round trips pass before the client can send its first encrypted HTTP request with a full TLS 1.3 handshake?
step: TCP's handshake (SYN, SYN-ACK) takes 1 round trip before the client can send data.
step: The TLS 1.3 handshake takes 1 more round trip: ClientHello out, server flight back.
step: After receiving the server flight, the client sends Finished and can immediately send the request.
step: The request is therefore sent after 1 + 1 = 2 round trips.
answer: 2
@mistakes
- Disabling certificate or hostname verification in client code to "make the error go away".
- Checking that a certificate is signed by a trusted CA but not that its names match the host being contacted.
- Assuming the padlock means the site is trustworthy; it shows the connection is encrypted to the named host, not that the host is honest.
- Treating 0-RTT early data as safe for requests that change state.

def hostname_matches(pattern, host):
    pattern = pattern.lower()
    host = host.lower()
    if pattern.startswith("*."):
        suffix = pattern[1:]
        if not host.endswith(suffix):
            return False
        label = host[:-len(suffix)]

model:
```python
def _match(pattern, host):
    pattern = pattern.lower()
    host = host.lower()
    if pattern.startswith("*."):
        suffix = pattern[1:]
        if not host.endswith(suffix):
            return False
        label = host[:-len(suffix)]
        return label != "" and "." not in label
    return pattern == host


def validate_chain(chain, roots, hostname, today):
    if not chain:
        return False
    if not any(_match(p, hostname) for p in chain[0]["san"]):
        return False
    for cert in chain:
        if not cert["not_before"] <= today <= cert["not_after"]:
            return False
    for cert, issuer in zip(chain, chain[1:]):
        if cert["issuer"] != issuer["subject"] or not issuer["is_ca"]:
            return False
    return chain[-1]["issuer"] in roots
```
hint: Work through the rules in order and return `False` as soon as one fails; return `True` only at the end.
hint: `zip(chain, chain[1:])` pairs each certificate with the one that issued it.
solution: Check non-emptiness, then the leaf's name against `hostname`, then every validity period, then each issuer link (and its CA flag), and finally that the last issuer is a trusted root.
