@article
HTTP is stateless, so web applications use a **session**: after login the server issues an identifier, which the browser returns in a **cookie** on every request. Whoever holds the identifier is the user. Two questions follow: which pages may read each other's data, and what can a page make the browser *do* with the cookies it holds?

### The same-origin policy

An **origin** is the triple (scheme, host, port). `https://app.example` and `https://app.example:443` are the same origin (443 is the default for https), while `http://app.example`, `https://api.app.example` and `https://app.example:8443` are each different. The **same-origin policy (SOP)** says that script from one origin may not **read** responses or the DOM of another origin. Without it, any page you visit could read your webmail.

SOP restricts reading, not sending: a page may still cause the browser to send requests to other origins (form posts, images, scripts). That gap is what CSRF uses.

**CORS** (cross-origin resource sharing) lets a server relax the SOP for chosen origins by sending `Access-Control-Allow-Origin`. Rules of thumb: CORS is a controlled relaxation, not a security barrier; never reflect any Origin you receive; the wildcard `*` cannot be combined with credentials, and should not be used for private data; non-simple requests trigger a **preflight** `OPTIONS` request.

### Cross-site request forgery

Suppose `bank.example` transfers money on `POST /transfer` and authenticates with a cookie. If the user is logged in and visits another site, that site's page can make the browser submit a form to `bank.example`. The browser attaches the bank's cookie automatically, so the request looks legitimate. The attacker cannot read the response, but does not need to: the **state change** is the damage. This is **cross-site request forgery (CSRF)**.

Defenses, combined:

- **`SameSite` cookies**: `SameSite=Lax` withholds the cookie on cross-site subrequests and on cross-site POST form submissions, but still sends it on top-level GET navigations (clicking a link); `SameSite=Strict` withholds it on all cross-site requests. Some browsers treat cookies without the attribute as Lax, but behavior varies, so set it explicitly.
- **Anti-CSRF tokens**: a random value, tied to the session, embedded in each form and verified on every state-changing request. A foreign site cannot read it (the SOP), so it cannot include it.
- **Verify `Origin`** (or `Referer`) on state-changing requests, and reject when it is not one of your origins. The `Sec-Fetch-Site` header gives similar information.
- **Never change state on GET**, and require re-authentication for the most sensitive actions.

### Secure sessions

- Make the session identifier **unpredictable**: generated by a cryptographically secure random generator, at least 128 bits, with no meaning inside it.
- Set cookie attributes: **Secure** (only over HTTPS), **HttpOnly** (hidden from JavaScript), **SameSite**, a limited lifetime, and a narrow `Path`/domain; the `__Host-` name prefix enforces some of these.
- **Regenerate the identifier at login** (and privilege changes). Otherwise **session fixation** is possible: an attacker who planted a known identifier before login shares the victim's authenticated session.
- On logout, **invalidate the session on the server**; deleting the cookie in the browser is not enough. Apply idle and absolute timeouts.
- To defend against **clickjacking** (your page loaded invisibly inside another), send `Content-Security-Policy: frame-ancestors 'none'` (or `'self'`).

```python
def session_cookie(name, value, max_age):
    return (f"{name}={value}; Max-Age={max_age}; Path=/; "
            "Secure; HttpOnly; SameSite=Lax")
```

@example
title: Walking through a CSRF defense
problem: A transfer form posts `to` and `amount`. Add a token defense and explain why a forged cross-site request fails.
step: When the server renders the form, it generates a random token, stores it in the user's session and puts it in a hidden field.
step: On `POST /transfer`, the server checks that the submitted token equals the one in the session, and rejects the request otherwise.
step: A forged request from another site carries the victim's cookie, but not the token: the attacker's page cannot read the bank's form (SOP), so it cannot know the value.
step: Add `SameSite=Lax` on the cookie and an `Origin` check as extra layers, and keep the endpoint POST-only.
answer: The forged request lacks the secret token, so it is rejected
@mistakes
- Believing the same-origin policy stops cross-site requests from being sent; it only stops reading the responses.
- Protecting state-changing actions with a cookie alone, with no token, `SameSite` setting or `Origin` check.
- Not regenerating the session identifier at login (session fixation), or only deleting the cookie on logout.
- Configuring CORS to echo back any `Origin` header while allowing credentials.

model:
```python
from urllib.parse import urlsplit

DEFAULT_PORTS = {"http": 80, "https": 443}


def _origin(url):
    parts = urlsplit(url)
    scheme = parts.scheme.lower()
    port = parts.port or DEFAULT_PORTS.get(scheme)
    return (scheme, parts.hostname, port)


def same_origin(url_a, url_b):
    return _origin(url_a) == _origin(url_b)
```
hint: Reduce each URL to a tuple `(scheme, host, port)` and compare the tuples.
hint: Use `parts.port or DEFAULT_PORTS.get(scheme)` to fill in a missing port.
solution: Normalize each URL to `(scheme, host, effective port)`; two URLs share an origin exactly when the tuples are equal. Paths and queries are ignored.

model:
```python
from urllib.parse import urlsplit


def origin_allowed(headers, allowed):
    if "Origin" in headers:
        return headers["Origin"] in allowed
    if "Referer" in headers:
        parts = urlsplit(headers["Referer"])
        return parts.scheme + "://" + parts.netloc in allowed
    return False
```
hint: Check for `Origin` first and decide on it alone when it is there.
hint: The Referer is a full URL; keep only `scheme://netloc` before comparing.
solution: Origin takes priority; Referer is the fallback; absence means reject (fail closed). The last test catches solutions that accept a request because its Referer looks fine while its Origin does not.

```python
import html

def save_comment(conn, user_id, text):
    conn.execute(
        "INSERT INTO comments(user_id, body) VALUES (?, ?)",
        (user_id, text))

def comments_page(conn):
    rows = conn.execute("SELECT body FROM comments").fetchall()
    items = "".join("<li>" + html.escape(r[0]) + "</li>" for r in rows)
    return "<ul>" + items + "</ul>"
```

CSRF: render a random per-session token in the comment form, verify it (in constant time) on every POST that calls `save_comment`, set the session cookie with `SameSite=Lax`, `Secure` and `HttpOnly`, and check the `Origin` header. Take `user_id` from the server-side session, never from the form.
hint: The two functions each write to a different interpreter: a database and a browser.

rubric: Escapes the stored comment on output and labels the flaw stored XSS.
rubric: Adds a token (or Origin check) for the POST and takes the user id from the server-side session.
