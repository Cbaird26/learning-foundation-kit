@article
Encryption hides data but does not stop modification. To detect tampering we need integrity primitives.

### Cryptographic hash functions

A **hash function** $H$ maps arbitrary-length input to a fixed-length digest. SHA-256 gives 256 bits (32 bytes, 64 hex characters); SHA-3 is a separate family. A cryptographic hash should have three properties:

- **Preimage resistance**: given $h$, it is infeasible to find $m$ with $H(m) = h$.
- **Second-preimage resistance**: given $m_1$, it is infeasible to find $m_2 \ne m_1$ with $H(m_2) = H(m_1)$.
- **Collision resistance**: it is infeasible to find any two different inputs with the same digest.

By the **birthday bound**, a collision in an $n$-bit hash is expected after about $2^{n/2}$ hashed values, so collision resistance is at most $n/2$ bits. MD5 and SHA-1 have practical collision attacks and must not be used where collisions matter (signatures, certificates); SHA-256 and SHA-3 are current choices. A hash has no key, so anyone can compute it: it detects accidental change only if the digest itself arrives over a trusted channel.

```python
import hashlib

print(hashlib.sha256(b"abc").hexdigest()[:8])   # ba7816bf
```

### Message authentication codes

A **MAC** takes a secret key and a message and outputs a **tag**. Without the key, an attacker cannot produce a valid tag for a new message. The receiver recomputes the tag and compares. A MAC provides integrity and authenticity between parties who share a key, but not non-repudiation, since either party could have made the tag.

The tempting construction $H(k \,\|\, m)$ is **broken for Merkle-Damgård hashes** such as SHA-256: given the tag of $m$, an attacker can compute a valid tag for $m$ followed by extra data without knowing $k$ (a length-extension weakness). **HMAC** avoids this:

$$\mathrm{HMAC}(K, m) = H\big((K' \oplus \text{opad}) \,\|\, H((K' \oplus \text{ipad}) \,\|\, m)\big)$$

where $K'$ is the key padded with zero bytes to the hash's block size (64 bytes for SHA-256; longer keys are hashed first), `ipad` is the byte `0x36` repeated and `opad` is `0x5c` repeated. In Python, the standard library provides `hmac`; use it in production. Implementing it once shows there is no magic.

### Comparing tags

Compare tags in **constant time**: a naive `==` on bytes may return at the first differing byte, and the running time can leak how many leading bytes matched. Python's `hmac.compare_digest` does this correctly. The idea is to accumulate differences over every byte and decide only at the end.

### Authenticated encryption

Use one primitive that gives confidentiality and integrity together: **AEAD** (authenticated encryption with associated data), such as AES-GCM or ChaCha20-Poly1305. Encryption takes a key, a **nonce** that must be unique per message under one key, the plaintext and optional **associated data** (headers that are authenticated but not encrypted). Decryption returns the plaintext or fails; it never releases data from a message that did not verify. If you must combine primitives yourself, **encrypt-then-MAC** (MAC the ciphertext, verify before decrypting, with independent keys) is the safe order. Reusing a nonce under GCM is catastrophic: it breaks both confidentiality and the authentication key.

### Choosing a primitive

| Need | Use |
|---|---|
| Integrity of a file against corruption, digest obtained securely | Hash (SHA-256) |
| Integrity and authenticity between parties with a shared key | HMAC |
| Confidentiality and integrity of messages | AEAD (AES-GCM, ChaCha20-Poly1305) |
| Storing passwords | Slow, salted password hash (Lesson 7) |
| Proof of origin anyone can verify | Digital signature (Lesson 6) |

@example
title: Why the naive tag fails
problem: A server authenticates requests with tag $= \mathrm{SHA256}(k \,\|\, m)$ where $k$ is secret. Explain the weakness and the fix.
step: SHA-256 processes input block by block, and its final digest is its internal state after the last block.
step: An attacker who knows the tag for $m$ (and the length of $k \,\|\, m$) can resume that state and hash more data, producing a valid tag for $m$ plus padding plus extra data, without knowing $k$.
step: The fix is HMAC, whose outer hash hides the inner state, or a modern MAC. Never design your own keyed hash.
answer: The tag can be extended without the key; use HMAC-SHA-256.
@example
title: Choosing a primitive for two scenarios
problem: (a) A mobile app downloads an update and must be sure it was not corrupted; the expected SHA-256 digest is published on a page served securely. (b) Two services exchange messages that must be secret and tamper-proof.
step: Scenario (a): integrity against corruption with a trusted digest needs only a hash. Compare `sha256(file)` with the published value.
step: Scenario (b) needs confidentiality and integrity, so choose an AEAD such as AES-GCM with a unique nonce per message under each key.
step: A bare hash would not work in (b) because anyone can recompute it after modifying a message, and plain encryption would allow undetected modification.
answer: (a) SHA-256 digest comparison; (b) AEAD
@mistakes
- Using a plain hash as a MAC (`sha256(key + message)`), which allows length extension and offers no real authenticity.
- Comparing tags with `==` when an attacker can measure response time; use a constant-time comparison.
- Repeating a nonce under the same key in GCM or ChaCha20-Poly1305.
- Using MD5 or SHA-1 for new security work because "it still produces a digest".

model:
```python
import hashlib


def hmac_sha256(key, msg):
    block = 64
    if len(key) > block:
        key = hashlib.sha256(key).digest()
    key = key.ljust(block, b"\x00")
    ipad = bytes(b ^ 0x36 for b in key)
    opad = bytes(b ^ 0x5C for b in key)
    inner = hashlib.sha256(ipad + msg).digest()
    return hashlib.sha256(opad + inner).hexdigest()
```
hint: Build the padded key with `ljust(64, b"\x00")` after hashing keys that are too long.
hint: Compute the inner digest as bytes with `.digest()`, then hash `opad + inner` and return `.hexdigest()`.
solution: Normalize the key to 64 bytes, XOR it with the two constant pads, hash the inner message, then hash the outer pad concatenated with the inner digest.

    if len(a) != len(b):
        return False
    diff = 0

    return diff == 0
