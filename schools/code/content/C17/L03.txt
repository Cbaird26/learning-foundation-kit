@article
**Symmetric-key encryption** uses one secret key for both encryption and decryption. Alice and Bob share a key $K$; Alice computes a ciphertext $C = E_K(M)$ and Bob recovers $M = D_K(C)$. By **Kerckhoffs's principle** the algorithm is public and only $K$ is secret. Never design your own cipher: use a vetted one.

### The one-time pad

XOR (`^`) satisfies $(m \oplus k) \oplus k = m$. If $k$ is truly random, as long as the message and used **once**, then $C = M \oplus K$ reveals nothing about $M$ (perfect secrecy). The cost is a key as long as all the data you will ever send, so it is impractical, but it is the model for stream ciphers. Reusing a pad is fatal:

```python
def xor(a: bytes, b: bytes) -> bytes:
    return bytes(x ^ y for x, y in zip(a, b))

# With one key k for two messages, xor(c1, c2) == xor(m1, m2): k cancels.
```

So a ciphertext pair under the same key stream leaks the XOR of the plaintexts, and redundancy in natural language or file formats usually allows recovering both. A defender's rule: **never reuse a keystream**.

### Block ciphers

A **block cipher** is a keyed permutation on fixed-size blocks. **AES** has a 128-bit (16-byte) block and keys of 128, 192 or 256 bits. A secure block cipher behaves like a random permutation to anyone without the key. A block cipher alone only encrypts one block, so we need a **mode of operation** for longer messages.

- **ECB** encrypts every block independently. Equal plaintext blocks give equal ciphertext blocks, so patterns in the data (the outline of an image, repeated records) remain visible. Do not use ECB for data.
- **CBC** XORs each plaintext block with the previous ciphertext block before encrypting. It needs a fresh, **unpredictable IV** (initialization vector) for each message and padding to a multiple of the block size.
- **CTR** (counter mode) encrypts a counter built from a **nonce** and a block number, and XORs the result with the plaintext, turning the block cipher into a stream cipher. It needs no padding and is parallelizable, but a (key, nonce) pair must **never repeat**, or the pad-reuse failure above occurs.

Encryption alone gives confidentiality but no integrity: an attacker who can modify ciphertexts can often change the plaintext in predictable ways (in CTR, flipping a ciphertext bit flips the same plaintext bit). Next lesson adds authentication; modern systems use authenticated modes such as GCM.

### Padding

**PKCS#7 padding** extends a message to a multiple of the block size $b$ by appending $n$ bytes each of value $n$, where $n = b - (\text{len} \bmod b)$. If the length is already a multiple of $b$, a whole block of padding is added, so padding can always be removed unambiguously: read the last byte $n$ and strip $n$ bytes. Padding errors must not be reported in a way that reveals which check failed; padding-oracle bugs have broken real systems, which is another reason to authenticate ciphertexts before decrypting.

### Key sizes

Brute-forcing an $n$-bit key takes about $2^{n-1}$ trials on average. At 128 bits that is far beyond any possible computation, so key size is rarely the weak point: key management, reuse of nonces and missing authentication are.

@example
title: Padding a 20-byte message
problem: Apply PKCS#7 padding with block size 16 to a 20-byte message. How long is the padded message and what do the added bytes look like?
step: $20 \bmod 16 = 4$, so the last block has 4 data bytes and 12 free bytes.
step: $n = 16 - 4 = 12$, so append twelve bytes each equal to `0x0c`.
step: The padded length is $20 + 12 = 32$ bytes, two full blocks.
step: To unpad, read the last byte `0x0c` = 12, check that the last 12 bytes all equal 12, and remove them.
answer: 32 bytes; twelve bytes of 0x0c
@example
title: Why a repeated pad leaks
problem: Two messages are XORed with the same key stream byte `k` at the same position. The plaintext bytes are `H` (0x48) and `W` (0x57). What can an observer compute from the two ciphertext bytes?
step: The ciphertext bytes are $0x48 \oplus k$ and $0x57 \oplus k$.
step: XORing them gives $0x48 \oplus k \oplus 0x57 \oplus k = 0x48 \oplus 0x57$, because $k \oplus k = 0$.
step: $0x48 \oplus 0x57 = 0x1f$, whatever $k$ is. The key has vanished, and the observer learns the XOR of the plaintext bytes.
step: Repeating this at every position gives the XOR of the two whole messages, which structured text rarely survives.
answer: 0x1f, the XOR of the plaintext bytes
@mistakes
- Encrypting data with ECB because it is the default or simplest mode; identical blocks stay identical.
- Reusing a nonce or IV with the same key (counter mode makes this catastrophic; CBC needs unpredictable IVs).
- Assuming encryption provides integrity; without a MAC or an authenticated mode, ciphertexts can be modified.
- Thinking a longer key fixes a mode or nonce mistake: the weakness is in how the cipher is used.

```python
def pkcs7_pad(data, block=16):
    n = block - len(data) % block
    return data + bytes([n]) * n


def pkcs7_unpad(padded, block=16):
    if not padded or len(padded) % block != 0:
        raise ValueError("bad length")
    n = padded[-1]
    if n < 1 or n > block or padded[-n:] != bytes([n]) * n:
        raise ValueError("bad padding")
    return padded[:-n]
```
hint: The pad length is `block - len(data) % block`, which is a full block when the length is already a multiple.
hint: For unpadding, read `padded[-1]`, then compare `padded[-n:]` with `bytes([n]) * n`.
solution: Pad with `n = block - len(data) % block` copies of the byte `n`. When unpadding, validate the length, the last byte and every padding byte before slicing them off.
