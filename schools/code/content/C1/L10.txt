@article
**Inheritance** lets a new class, the **subclass** (or derived class), start from an existing one, the **base class** (or superclass), and add or change behavior. It models an **is-a** relationship: a `Dog` *is an* `Animal`, a savings account *is an* account.

```python
class Animal:
    def __init__(self, name):
        self.name = name

    def speak(self):
        return "..."

    def intro(self):
        return f"{self.name} says {self.speak()}"

class Dog(Animal):
    def speak(self):          # overrides Animal.speak
        return "Woof"
```

`Dog` inherits `__init__` and `intro` unchanged and **overrides** `speak`. Look up of a method starts at the object's own class and moves up to the base classes, so `Dog("Rex").intro()` finds `intro` in `Animal`, and inside it `self.speak()` finds `Dog.speak`, because `self` is a `Dog`. The result is `"Rex says Woof"`.

### Extending with `super()`

A subclass that needs extra state must still initialize the base part. `super()` gives access to the base class:

```python
class Puppy(Dog):
    def __init__(self, name, age):
        super().__init__(name)    # run Animal.__init__
        self.age = age

    def speak(self):
        return super().speak() + "!"   # extend, not replace
```

If you forget `super().__init__(name)`, `self.name` is never set, and the first use of it raises `AttributeError`.

### Polymorphism

Code written against the base class works with any subclass, and each object responds in its own way:

```python
for a in [Animal("Cat"), Dog("Rex"), Puppy("Bit", 1)]:
    print(a.intro())
```

This is **polymorphism**: the same call, different behavior chosen by the actual type of the object. `isinstance(x, Animal)` is true for instances of `Animal` and of all its subclasses; `type(x) is Animal` is true only for exact instances. `issubclass(Dog, Animal)` tests classes.

A base class often defines an interface that subclasses must fill in. A simple way is to raise `NotImplementedError`:

```python
class Shape:
    def area(self):
        raise NotImplementedError("subclasses must define area")
```

The `abc` module (`ABC` and `@abstractmethod`) makes such classes truly abstract so that they cannot be instantiated.

### Method resolution order

With a chain `C(B)`, `B(A)`, a call `super().f()` in `C` runs `B.f`, whose own `super().f()` runs `A.f`. Python computes the lookup order, the **method resolution order** (MRO), also for multiple inheritance (`class D(B, C)`); `D.__mro__` shows it. Prefer single inheritance until you need more.

### Designing hierarchies

Inheritance is a strong coupling: subclasses depend on the base class's details. Guidelines:

- Use inheritance only for real is-a relationships, and keep the hierarchy shallow.
- A subclass must be usable wherever the base class is expected, so it must keep the base class's promises (the **Liskov substitution principle**): do not strengthen preconditions or break postconditions. A `Square` that inherits from a mutable `Rectangle` and forces `width == height` breaks code that sets the width alone.
- Use **composition** (has-a) otherwise: a `Car` *has an* `Engine` object; it is not an engine. Composition is more flexible because the parts can be replaced.

### Exceptions form a hierarchy

Exception classes are ordinary classes: `ValueError` and `KeyError` inherit from `Exception`, and `except Exception` catches all of its subclasses. Define your own to give errors a name:

```python
class InsufficientFundsError(ValueError):
    """Raised when a withdrawal exceeds the balance."""
```

An `except ValueError` clause also catches this error, because it is a `ValueError`.

@example
title: Overriding and super
problem: What does this program print?

```python
class A:
    def f(self):
        return "A"

class B(A):
    def f(self):
        return "B" + super().f()

class C(B):
    pass

print(C().f())
print(B().f())
```
step: `C` defines no `f`, so lookup for `C().f` continues in `B`, where it finds `B.f`.
step: `B.f` returns `"B"` plus `super().f()`. Within `B`, `super()` refers to the next class in the order after `B`, which is `A`, so that call returns `"A"`.
step: Hence `C().f()` is `"BA"`; `B().f()` is the same computation, `"BA"`.
answer:
```
BA
BA
```

@example
title: A small hierarchy with polymorphism
problem: Design `Employee(name, monthly)` with `annual_pay()` and a `Manager` who also receives a yearly bonus.
step: `Employee.annual_pay` is twelve times the monthly salary.
step: A `Manager` is an `Employee` with extra state, so it calls `super().__init__` and stores the bonus.
step: Override `annual_pay` by extending the base result instead of repeating the formula:

```python
class Employee:
    def __init__(self, name, monthly):
        self.name = name
        self.monthly = monthly

    def annual_pay(self):
        return 12 * self.monthly

class Manager(Employee):
    def __init__(self, name, monthly, bonus):
        super().__init__(name, monthly)
        self.bonus = bonus

    def annual_pay(self):
        return super().annual_pay() + self.bonus
```
step: For `Manager("Ada", 1000, 500)` the pay is `12000 + 500 = 12500`. Code that sums `annual_pay()` over a mixed list of employees and managers needs no `if` on the type.

@mistakes
- Forgetting `super().__init__(...)` in a subclass constructor, so the base attributes are missing.
- Using inheritance for a has-a relationship (a `Stack` that inherits from `list` exposes `insert(0, x)` and breaks the stack discipline); use composition.
- Overriding a method with different parameters or weaker guarantees, so code written for the base class breaks.
- Testing types with `type(x) == Base` when `isinstance(x, Base)` is meant, which rejects subclasses.

```python
import math


class Shape:
    def area(self):
        raise NotImplementedError("subclasses must define area")

    def describe(self):
        return f"{type(self).__name__} with area {self.area():.2f}"


class Rect(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height


class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

    def area(self):
        return math.pi * self.radius ** 2
```

@quiz code
prompt: Write a class `InsufficientFundsError` that inherits from `ValueError`; a class `Account(balance=0)` with attribute `balance` and `withdraw(amount)` that raises `InsufficientFundsError` if `amount` exceeds the balance (otherwise subtracts it); and a subclass `SavingsAccount` that overrides `withdraw` so that it also raises `InsufficientFundsError` whenever the withdrawal would leave a balance below the class attribute `MINIMUM = 100`. A failed withdrawal must not change the balance. Reuse the base method through `super()`.
starter:
```python
class InsufficientFundsError(ValueError):
    pass
```
tests:
```python
a = Account(50)
a.withdraw(50)
assert a.balance == 0
assert raises(InsufficientFundsError, a.withdraw, 1)
s = SavingsAccount(300)
s.withdraw(200)
assert s.balance == 100
assert raises(InsufficientFundsError, s.withdraw, 1)
assert s.balance == 100
assert raises(ValueError, s.withdraw, 1)
assert isinstance(s, Account)
assert SavingsAccount.MINIMUM == 100
b = SavingsAccount(1000)
b.withdraw(900)
assert b.balance == 100
```
model:
```python
class InsufficientFundsError(ValueError):
    pass


class Account:
    def __init__(self, balance=0):
        self.balance = balance

    def withdraw(self, amount):
        if amount > self.balance:
            raise InsufficientFundsError("insufficient funds")
        self.balance -= amount


class SavingsAccount(Account):
    MINIMUM = 100

    def withdraw(self, amount):
        if self.balance - amount < self.MINIMUM:
            raise InsufficientFundsError("would go below minimum")
        super().withdraw(amount)
```
hint: Check the extra condition in the subclass first, then delegate to `super().withdraw(amount)`.
solution: `SavingsAccount.withdraw` raises when `balance - amount < MINIMUM` and otherwise calls the base method, which performs its own check and the subtraction. Raising before any change keeps the balance intact, and because the error class inherits from `ValueError`, `except ValueError` catches it too.
