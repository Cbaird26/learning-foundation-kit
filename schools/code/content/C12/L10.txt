@article
A **static type checker** is a program that walks the AST *before* the program runs and decides whether every expression has a consistent type. If it finds a violation, the program is rejected. It is structurally the same as the evaluator: a recursive function over the tree, except that it computes a *type* instead of a *value*.

### Typing rules

We specify a checker with **typing rules**. The judgment $\Gamma \vdash e : T$ reads "in the type environment $\Gamma$, expression $e$ has type $T$". $\Gamma$ maps variable names to types. A rule gives the premises above the line and the conclusion below:

$$\frac{\Gamma \vdash e_1 : \text{int} \qquad \Gamma \vdash e_2 : \text{int}}{\Gamma \vdash e_1 + e_2 : \text{int}} \qquad \frac{\Gamma \vdash c : \text{bool} \quad \Gamma \vdash t : T \quad \Gamma \vdash f : T}{\Gamma \vdash \text{if } c \text{ then } t \text{ else } f : T}$$

For our tiny language (integers and booleans), the rules are:

- A number literal has type `int`, and `true` and `false` have type `bool`.
- A variable has the type recorded for it in $\Gamma$.
- `+`, `-`, `*` take two `int` operands and give `int`; `<` takes two `int` operands and gives `bool`.
- `==` takes two operands of the same type and gives `bool`; `and` takes two `bool` operands and gives `bool`.
- `if c then t else f` needs `c : bool`, and `t` and `f` must have the *same* type, which is the type of the whole expression.
- `let x = v in b` checks `v` to get its type $T$, then checks `b` in $\Gamma$ extended with `x : T`.

Each rule becomes one branch of the function:

```python
def typecheck(node, env):
    kind = node[0]
    if kind == "num":
        return "int"
    if kind == "if":
        if typecheck(node[1], env) != "bool":
            raise TypeError("condition must be bool")
        t = typecheck(node[2], env)
        if typecheck(node[3], env) != t:
            raise TypeError("branches differ")
        return t
    ...
```

The checker runs in time linear in the size of the tree. It is a **conservative** analysis: a **sound** type system never accepts a program that can commit a type error at run time, and this usually means it must reject some programs that would actually run fine. For example `if false then 1 + true else 2` is rejected even though the bad branch never executes, since the checker does not run the program.

### Annotations and inference

In a language with **type annotations**, the programmer writes types and the checker verifies them: `def f(x: int) -> bool`. With **type inference**, the compiler works the types out itself. Many languages mix the two: Rust and Go infer local variable types, TypeScript infers most types it can, and Python tools like mypy infer types of locals from assignments.

The classic algorithm is **Hindley-Milner** inference, used by ML-family languages and Haskell. It introduces a fresh **type variable** (written `'a`, `'b`) for each unknown, collects equalities between types as it walks the tree, and solves them by **unification**: finding a **substitution** (a mapping from type variables to types) that makes two types identical.

Types here include function types, written `T1 -> T2`. Unifying `'a -> bool` with `int -> 'b` forces `'a = int` and `'b = bool`. Unifying `int` with `bool` fails: a type error. Unifying `'a` with `'a -> int` also fails by the **occurs check**: the answer would be an infinite type.

For `fun x -> x + 1`, give `x` the variable `'a`. The rule for `+` requires `'a = int`, and the result is `int`, so the function has type `int -> int`; no annotation was needed. For `fun x -> x`, nothing constrains `'a`, so the type is `'a -> 'a`: the **most general type**, which works for every type. Hindley-Milner also supports **let-polymorphism**, where such a function can be used at several types in the same program.

Inference is fast in practice (nearly linear on real programs, though contrived programs can make the worst case exponential), and it gives you the safety of static types with much less notation. It does not make a language dynamic: every expression still has one static type.

@example
title: Checking an expression
problem: Check `if 1 < 2 then 3 else 4`.
step: The condition `1 < 2` is a `<` node with two `int` operands, so by the `<` rule it has type `bool`.
step: The two branches `3` and `4` both have type `int`, so they agree.
step: The `if` rule gives the whole expression the type of the branches: `int`.
step: Now try `if 1 < 2 then 3 else true`. The branches have types `int` and `bool`, which differ, so the checker raises a type error.
answer: `int`

@example
title: Unifying function types
problem: Unify `'a -> int` with `bool -> 'b`.
step: Both types are function types, so unify their parts pairwise: first the argument types, then the result types.
step: Arguments: `'a` against `bool`. A variable unifies with any type that does not contain it, so record `'a = bool`.
step: Results: `int` against `'b`. Record `'b = int`.
step: Applying the substitution `{'a: bool, 'b: int}` turns both types into `bool -> int`, so they are equal.
answer: The substitution `'a = bool`, `'b = int`; both types become `bool -> int`.

@mistakes
- Letting both branches of an `if` have different types because "only one runs"; a static checker must give the expression one type.
- Forgetting to extend the type environment inside `let`, so the variable is reported undefined in the body.
- Skipping the occurs check, which lets unification build an infinite type.
- Assuming type inference means the language is dynamically typed. The types are still computed before the program runs.

```python
def typecheck(node):
    kind = node[0]
    if kind == "num":
        return "int"
    if kind == "bool":
        return "bool"
    if kind == "bin":
        op = node[1]
        left = typecheck(node[2])
        right = typecheck(node[3])
        if left != "int" or right != "int":
            raise TypeError(f"{op} needs two ints")
        return "bool" if op == "<" else "int"
    if kind == "if":
        if typecheck(node[1]) != "bool":
            raise TypeError("condition must be bool")
        then_type = typecheck(node[2])
        if typecheck(node[3]) != then_type:
            raise TypeError("branches must have the same type")
        return then_type
    raise TypeError(f"unknown node {kind!r}")
```

model:
```python
def typecheck(node, env):
    kind = node[0]
    if kind == "num":
        return "int"
    if kind == "bool":
        return "bool"
    if kind == "var":
        if node[1] not in env:
            raise NameError(f"undefined variable {node[1]!r}")
        return env[node[1]]
    if kind == "let":
        value_type = typecheck(node[2], env)
        inner = dict(env)
        inner[node[1]] = value_type
        return typecheck(node[3], inner)
    if kind == "if":
        if typecheck(node[1], env) != "bool":
            raise TypeError("condition must be bool")
        then_type = typecheck(node[2], env)
        if typecheck(node[3], env) != then_type:
            raise TypeError("branches must have the same type")
        return then_type
    if kind == "bin":
        op = node[1]
        left = typecheck(node[2], env)
        right = typecheck(node[3], env)
        if op in ("+", "-", "*", "<"):
            if left != "int" or right != "int":
                raise TypeError(f"{op} needs two ints")
            return "bool" if op == "<" else "int"
        if op == "==":
            if left != right:
                raise TypeError("== needs operands of one type")
            return "bool"
        if op == "and":
            if left != "bool" or right != "bool":
                raise TypeError("and needs two bools")
            return "bool"
        raise TypeError(f"unknown operator {op!r}")
    raise TypeError(f"unknown node {kind!r}")
```
hint: This is last week's environment idea applied to types: the environment maps names to types instead of values.
hint: For `let`, check the value, copy the environment, add the name with that type and check the body in the copy.
solution: Use a dictionary of types as the environment, extend a copy for `let` so the binding does not leak, and give `==` the rule that both operand types must be equal. Unbound variables raise `NameError`, and all other violations raise `TypeError`.

model:
```python
def _is_var(t):
    return isinstance(t, str) and t.startswith("'")


def _resolve(t, s):
    while _is_var(t) and t in s:
        t = s[t]
    return t


def _occurs(v, t, s):
    t = _resolve(t, s)
    if t == v:
        return True
    if isinstance(t, tuple):
        return _occurs(v, t[1], s) or _occurs(v, t[2], s)
    return False


def unify(a, b, subst=None):
    s = {} if subst is None else dict(subst)

    def go(x, y):
        x = _resolve(x, s)
        y = _resolve(y, s)
        if x == y:
            return
        if _is_var(x):
            if _occurs(x, y, s):
                raise TypeError("infinite type")
            s[x] = y
        elif _is_var(y):
            if _occurs(y, x, s):
                raise TypeError("infinite type")
            s[y] = x
        elif isinstance(x, tuple) and isinstance(y, tuple):
            go(x[1], y[1])
            go(x[2], y[2])
        else:
            raise TypeError(f"cannot unify {x!r} with {y!r}")

    go(a, b)
    return s
```
hint: Handle the cases in order: already equal, a variable on either side, two function types, and anything else is an error.
hint: Before binding a variable, resolve both sides through the substitution so far, and run the occurs check on the type you are about to bind it to.
solution: Resolve both sides using the current substitution, then: equal types need nothing; a variable is bound to the other type after an occurs check; two function types are unified part by part (argument, then result); everything else is a mismatch. Unifying the types `'a -> 'a` and `int -> bool` binds `'a` to `int`, and then `int` against `bool` fails, because the second part is resolved through the first binding.
