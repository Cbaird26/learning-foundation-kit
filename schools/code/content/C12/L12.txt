@article
Every running program needs memory for its data. Two regions matter. The **stack** holds the local variables and return addresses of active function calls; it grows when a function is called and shrinks when it returns, so it is managed automatically. The **heap** holds objects whose lifetime is not tied to one call: anything that outlives the function that created it, such as a closure's environment or a list that is returned. Someone must decide when heap memory can be reused. Languages answer this in three main ways.

### Manual management

In C, you call `malloc` to get heap memory and `free` to give it back. This is fast and predictable, and it puts the burden on the programmer. A forgotten `free` is a **memory leak**; using memory after freeing it is a **dangling pointer** (a use-after-free bug); freeing twice is a **double free**. These bugs are a leading source of security vulnerabilities. Rust keeps manual-style predictability but checks at compile time, through ownership and borrowing rules, that each value has one owner and is freed exactly once, with no garbage collector.

### Reference counting

Give each object a count of the references to it. Storing a reference increments the count; dropping one decrements it; at zero, the object is freed immediately. CPython uses reference counting as its main mechanism, and so does Swift (as automatic reference counting).

Its strengths are that memory is reclaimed promptly and that costs are spread evenly through the run. Its weaknesses are the cost of updating counts on every assignment and, above all, **cycles**. If object `x` refers to `y` and `y` refers to `x`, each has count 1 even when nothing else can reach them, so neither is ever freed. CPython therefore adds a separate **cycle detector** that finds unreachable groups of objects and frees them.

### Tracing garbage collection

A **tracing collector** does not count. When memory runs low it determines which objects are **reachable** and frees all others. The starting points are the **roots**: global variables, the values on the stack and in registers. An object is reachable if it can be found by following references from a root. Anything else is garbage, since the program can no longer get to it.

**Mark-and-sweep** works in two phases:

1. **Mark**: starting from the roots, traverse the reference graph and mark every object visited. (Keep a worklist, and skip objects already marked, so cycles cannot cause an infinite loop.)
2. **Sweep**: scan the whole heap and free every object that is not marked (and clear the marks for the next run).

```python
def mark(heap, roots):
    marked = set()
    work = list(roots)
    while work:
        name = work.pop()
        if name not in marked:
            marked.add(name)
            work.extend(heap[name])
    return marked
```

Marking costs time proportional to the number of *live* objects and their references; the sweep costs time proportional to the size of the *whole heap*. Cycles pose no problem, because reachability only asks whether a root can get there.

Variations improve on the basic scheme. **Compacting** and **copying** collectors move live objects together to remove fragmentation. **Generational** collectors exploit the observation that most objects die young: they collect a small young region often and the old region rarely. Simple collectors **stop the world**, pausing the program during collection; **incremental** and **concurrent** collectors reduce the pauses at the cost of complexity.

### Garbage collection and closures

A closure keeps its captured environment reachable for as long as the closure is reachable; this is why a function returned from `make_counter` can still use `count` after `make_counter` has returned. It also means a long-lived closure, cache or global list can keep large objects alive unintentionally. A garbage collector frees only *unreachable* objects, so a **memory leak** in a managed language usually means an object that is still reachable but no longer needed.

### Modeling a heap

To experiment, represent the heap as a dictionary mapping each object's name to the list of names it refers to, and the roots as a list of names. For `heap = {"a": ["b"], "b": [], "c": ["c"]}` and `roots = ["a"]`, the objects `a` and `b` are reachable, while `c` refers only to itself and is garbage. Reference counting would never free `c`, since it has a count of 1, but a tracing collector would.

@example
title: Mark and sweep by hand
problem: Run mark-and-sweep on `heap = {"a": ["b", "c"], "b": ["a"], "c": [], "d": ["e"], "e": ["d"]}` with `roots = ["b"]`.
step: Mark phase: start the worklist with `b`. Visit `b`, mark it, and add its reference `a`.
step: Visit `a`: mark it and add `b` and `c`. `b` is already marked and is skipped; visit `c`, mark it. The marked set is `{a, b, c}`.
step: Sweep phase: scan all five objects. `a`, `b` and `c` are marked and survive; `d` and `e` are not marked.
step: Free `d` and `e`. They refer to each other (a cycle), but no root reaches them, so they are garbage.
answer: `d` and `e` are freed; `a`, `b` and `c` survive.

@example
title: Reference counting versus a cycle
problem: In the heap `{"a": ["b", "c"], "b": ["a"], "c": [], "d": ["e"], "e": ["d"]}` with `roots = ["b"]`, why does reference counting fail to free `d` and `e`, when nothing else refers to them?
step: Count the references to `d`: the only one is from `e`, so its count is 1. The count of `e` is 1, from `d`.
step: A count of 1 is not zero, so reference counting does not free either object.
step: Nothing outside the pair can reach them, so the program can never use them again: they are leaked.
step: A tracing collector asks a different question (is the object reachable from a root?) and so frees both. CPython combines reference counting with a cycle detector for this reason.
answer: Each has a count of 1 because of the cycle, so neither reaches zero.

@mistakes
- Believing a garbage collector prevents all memory leaks; objects that are still reachable but no longer needed are never freed.
- Thinking reference counting frees cycles. Each member of an unreachable cycle keeps the others alive.
- Forgetting to skip already marked objects during marking, so a cycle makes the loop run forever.
- Mixing up the two phases: marking is proportional to live data, and sweeping to the whole heap.

```python
def mark_sweep(heap, roots):
    marked = set()
    work = list(roots)
    while work:
        name = work.pop()
        if name not in marked:
            marked.add(name)
            work.extend(heap[name])
    garbage = [name for name in heap if name not in marked]
    for name in garbage:

    return sorted(garbage)
```

model:
```python
def refcount_collect(heap, roots):
    counts = {name: 0 for name in heap}
    for r in roots:
        counts[r] += 1
    for refs in heap.values():
        for r in refs:
            counts[r] += 1
    freed = []
    work = [name for name in heap if counts[name] == 0]
    while work:
        name = work.pop()
        freed.append(name)
        for r in heap[name]:
            counts[r] -= 1
            if counts[r] == 0:
                work.append(r)
        del heap[name]
    return sorted(freed)
```
hint: Compute all the counts first, then keep a worklist of objects whose count is 0.
hint: When you free an object, decrement the count of everything it refers to, and add any object that reaches 0 to the worklist.
solution: Compute counts, then free zero-count objects from a worklist. Freeing an object removes its outgoing references, so each target's count drops, possibly freeing a chain. In a cycle each member keeps a count of at least 1, so the cycle survives, which is the weakness of reference counting.
