@article
A name such as `x` has no meaning by itself; it means whatever value it is **bound** to where it is used. An interpreter keeps track of bindings in an **environment**: a mapping from names to values. Evaluating `x + 1` becomes `evaluate(node, env)`, and the variable case is a lookup.

### Environments as chains

Programs have nested regions: a block inside a function inside a module. Each region adds its own bindings and can still see the ones outside. We model this with a **chain of environments**: each environment holds a dictionary and a link to its parent.

```python
class Env:
    def __init__(self, parent=None):
        self.vars = {}
        self.parent = parent

    def define(self, name, value):
        self.vars[name] = value

    def lookup(self, name):
        env = self
        while env is not None:
            if name in env.vars:
                return env.vars[name]
            env = env.parent
        raise NameError(f"undefined variable {name!r}")

    def assign(self, name, value):
        env = self
        while env is not None:
            if name in env.vars:
                env.vars[name] = value
                return
            env = env.parent
        raise NameError(f"undefined variable {name!r}")
```

`define` creates a binding in *this* environment only. `lookup` searches from the innermost environment outwards and uses the first match. `assign` updates an existing binding wherever it is found, and fails if there is none. A lookup takes time proportional to the depth of the chain in the worst case.

### Shadowing

A binding in an inner environment can **shadow** one with the same name outside: the inner name wins inside, and the outer binding is untouched and visible again once the inner region ends. In Python:

```python
x = "outer"

def f():
    x = "inner"
    return x

print(f(), x)   # inner outer
```

### Lexical versus dynamic scope

Which environment is the parent of a function body's environment? Under **lexical (static) scope**, it is the environment where the function was *written*. You can determine what every name refers to by reading the program text. Almost all modern languages, including Python, JavaScript, C and Rust, are lexically scoped. Under **dynamic scope**, it is the environment of the *caller* at run time, so the same text can refer to different variables depending on who called. Some older Lisps and shell languages behave this way. Lexical scope makes programs easier to reason about, and it is what makes closures (next week) work.

### Let expressions

We add two node kinds to the AST: `("var", name)` and `("let", name, value, body)`, which means "evaluate `value`, bind it to `name`, and evaluate `body` with that binding". For example `let x = 5 in x * 2` is `10`. The binding exists only inside the body:

```python
def evaluate(node, env):
    kind = node[0]
    if kind == "num":
        return node[1]
    if kind == "var":
        return env.lookup(node[1])
    if kind == "let":
        value = evaluate(node[2], env)
        inner = Env(env)
        inner.define(node[1], value)
        return evaluate(node[3], inner)
    if kind == "bin":
        ...  # as before, passing env to both recursive calls
```

The key point is that the value is evaluated in the *outer* environment `env`, and the body in a **new child environment**. That is how `let x = 1 in let x = x + 1 in x` gives `2`: the inner `x` is defined from the outer `x`, then shadows it. When the body finishes, the child environment is simply dropped, so there is no cleanup.

Environments also explain **scope rules** in real languages. Python decides whether a name is local to a function at compile time: if a function assigns to `x` anywhere, `x` is local throughout it, and reading it before assignment raises `UnboundLocalError`. The `global` and `nonlocal` statements redirect an assignment to an outer scope. Python's lookup order is summarized by LEGB: Local, Enclosing function, Global (module), Built-in.

@example
title: Looking up through a chain
problem: Given the global environment `{a: 1, b: 2}` and a child `{b: 20, c: 30}` whose parent is the global one, what do `lookup("a")`, `lookup("b")` and `lookup("c")` return in the child?
step: `lookup("a")`: the child has no `a`, so the search moves to the parent and finds `1`.
step: `lookup("b")`: the child has its own `b`, so the search stops there and returns `20`. The parent's `b = 2` is shadowed.
step: `lookup("c")`: found in the child, `30`.
step: `lookup("d")` would search the child and the parent without success and raise `NameError`.
answer: `1`, `20` and `30`.

@example
title: Evaluating nested lets
problem: Evaluate `let x = 3 in let y = x * 2 in x + y`, written as `("let", "x", ("num", 3), ("let", "y", ("bin", "*", ("var", "x"), ("num", 2)), ("bin", "+", ("var", "x"), ("var", "y"))))`.
step: The outer `let` evaluates `3` and creates an environment `E1 = {x: 3}` whose parent is the starting environment.
step: Its body is the inner `let`. It evaluates `x * 2` in `E1`: the lookup finds `x = 3`, so the value is `6`.
step: The inner `let` creates `E2 = {y: 6}` with parent `E1`.
step: The body `x + y` is evaluated in `E2`: `x` is found in the parent `E1` (3) and `y` in `E2` (6), so the result is `9`.
answer: `9`

@mistakes
- Evaluating the `let` value in the new child environment instead of the outer one, so `let x = x + 1` sees the wrong `x`.
- Using one flat dictionary for all variables, so inner bindings overwrite outer ones permanently instead of shadowing them.
- Confusing `define` (create here) with `assign` (update where it already exists).
- Believing a lexically scoped language looks up names in the caller's environment; that is dynamic scope.

@practice code
prompt: Write `evaluate(node, env)` for the nodes `("num", n)`, `("var", name)`, `("let", name, value, body)` and `("bin", op, left, right)` with `op` one of `+`, `-`, `*`. starter:
```python
def evaluate(node, env):

```
tests:
```python
assert evaluate(("num", 4), {}) == 4
assert evaluate(("var", "x"), {"x": 7}) == 7
assert raises(NameError, evaluate, ("var", "y"), {})
let_x = ("let", "x", ("num", 5),
         ("bin", "*", ("var", "x"), ("num", 2)))
assert evaluate(let_x, {}) == 10
shadow = ("let", "x", ("num", 1),
          ("let", "x", ("bin", "+", ("var", "x"), ("num", 1)),
           ("var", "x")))
assert evaluate(shadow, {}) == 2
env = {"x": 100}
outer = ("bin", "+",
         ("let", "x", ("num", 1), ("var", "x")),
         ("var", "x"))

```
model:
```python
def evaluate(node, env):
    kind = node[0]
    if kind == "num":
        return node[1]
    if kind == "var":
        if node[1] not in env:
            raise NameError(f"undefined variable {node[1]!r}")
        return env[node[1]]
    if kind == "let":
        value = evaluate(node[2], env)
        inner = dict(env)
        inner[node[1]] = value
        return evaluate(node[3], inner)
    left = evaluate(node[2], env)
    right = evaluate(node[3], env)
    if node[1] == "+":
        return left + right
    if node[1] == "-":
        return left - right
    return left * right
```
hint: Pass `env` into every recursive call; only `let` changes it.
hint: In `let`, evaluate the value first using the old `env`, then make a copy with `dict(env)`, add the binding and evaluate the body in the copy.
solution: Variables are lookups in `env`. A `let` evaluates its value in the outer `env`, builds a new dictionary with the extra binding and evaluates the body there, which gives shadowing and leaves the caller's `env` unchanged.

model:
```python
def lookup_chain(scopes, name):
    for scope in scopes:
        if name in scope:
            return scope[name]
    raise NameError(f"undefined variable {name!r}")
```
