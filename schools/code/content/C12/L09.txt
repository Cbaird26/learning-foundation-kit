@article
A **type** classifies values: it says which values a variable or expression may have and which operations make sense on them. `int` is the integers with arithmetic; `str` is text with concatenation and slicing. A **type error** is applying an operation to a value of the wrong kind, such as adding a number to a list.

Languages differ on two independent questions, and people often confuse them.

### Static versus dynamic: *when* are types checked?

In a **statically typed** language, types are checked before the program runs (at compile time or by a separate checker). Every expression has a type known from the program text, and a program that violates the rules is rejected. C, Java, Rust, Go and TypeScript work this way.

In a **dynamically typed** language, values carry their types at run time, and operations check them when they execute. Variables have no fixed type; a variable can hold an integer now and a string later. Python, JavaScript, Ruby and Scheme work this way:

```python
x = 5
x = "five"      # fine: the variable has no declared type
x + 1           # TypeError, found only when this line runs
```

Static checking finds a whole class of errors **before** any test runs, documents interfaces and enables optimizations, but it can reject programs that would have run correctly, and it demands more notation. Dynamic typing is flexible and quick to write, but a type error can lurk in a rarely executed branch until it reaches a user. Static typing is not a substitute for tests; it catches the errors that types can express.

### Strong versus weak: *how strictly* are the rules enforced?

These terms are informal, and authors use them differently, but the usual meaning is about **implicit conversion** and whether the type rules can be bypassed. In a **strongly typed** language, an operation applied to the wrong type is an error. In a **weakly typed** one, the language silently converts values (coerces them) or allows reinterpreting memory.

```python
1 + "1"          # Python: TypeError (strong)
```

```javascript
1 + "1"          // JavaScript: the string "11" (the number is coerced)
```

JavaScript silently turns the number into a string. C is weak in a different way: you can cast a pointer to an incompatible type, or read memory as a different type, and the compiler allows it. The result may be undefined behavior.

### The grid

| | Static | Dynamic |
|---|---|---|
| **Strong** | Java, Rust, Haskell | Python, Ruby, Scheme |
| **Weak** | C, C++ (casts, pointers) | JavaScript, PHP |

The placement of weak languages is arguable, because "weak" covers several features. The two axes are independent: Python is **dynamic and strong**.

### Python's details

Python checks at run time and refuses most mixed operations, but its rules have details worth knowing. `"3" * 2` is `"33"` (repetition, not arithmetic). `bool` is a subclass of `int`, so `True + True` is `2` and `isinstance(True, int)` is `True`. Python uses **duck typing**: an object is acceptable if it supports the needed operations, whatever its class ("if it quacks like a duck"). A function that only calls `len(x)` and iterates works on lists, strings and any other sized iterable.

**Type hints** add optional static information:

```python
def area(width: float, height: float) -> float:
    return width * height
```

The interpreter does **not enforce** hints at run time. External checkers such as mypy and pyright read them and report violations before the program runs, which is **gradual typing**: you add static checking to a dynamic language piece by piece. (Python 3.14 evaluates annotations lazily, so a hint can refer to a name defined later in the file.)

### Checking types yourself

A dynamic language implements its checks inside the runtime. In an interpreter this is a few lines: before applying `+`, test the operand types with `isinstance` and raise an error if they are wrong.

```python
def checked_add(a, b):
    if not (isinstance(a, int) and isinstance(b, int)):
        raise TypeError("+ expects two integers")
    return a + b
```

A static checker does the same reasoning without running the program: it computes a type for each expression from the types of its parts. That is next week's topic.

@example
title: Classifying behaviors
problem: For each, say whether it shows static or dynamic checking: (1) a Java compiler rejects `int n = "hi";` (2) Python raises `TypeError` for `[] + 1` when the line executes.
step: In (1) the error is reported by the compiler, before the program runs, from the declared type of `n` and the type of the literal. That is **static** checking.
step: In (2) nothing is reported when the program is loaded. The error appears only when the line runs and the operation finds an incompatible operand. That is **dynamic** checking.
step: Both languages are also *strong* here: neither silently converts the value.
answer: (1) static; (2) dynamic.

@example
title: Coercion in a weakly typed language
problem: In JavaScript, `"5" - 2` is `3`, while `"5" + 2` is `"52"`. What does this show?
step: The operator `-` only makes sense for numbers, so JavaScript converts the string `"5"` to the number 5 and subtracts.
step: The operator `+` is overloaded for strings, so if either operand is a string, the other is converted to a string and the two are joined.
step: In Python both expressions raise `TypeError`: there is no implicit conversion between `str` and `int`.
step: The same source-level operator has different semantics, which makes JavaScript's rules weaker (more implicit) than Python's.
answer: JavaScript coerces silently, so the result depends on implicit conversion rules; Python is stricter.

@mistakes
- Using "strong" and "static" as synonyms. Python is strongly typed but dynamically typed, and C is statically typed but weakly typed.
- Believing Python type hints are enforced when the program runs; they are only checked by external tools.
- Thinking a dynamic language has no types. Values always have types; it is the variables that do not.
- Forgetting that `bool` is a subclass of `int`, so `True` passes an `isinstance(x, int)` check.

@practice code
prompt: Write the decorator factory `typed(*types)`. `typed(int, str)(f)` returns a function that checks that the positional arguments are instances of the given types, in order, and then returns `f(*args)`. If the number of arguments differs from the number of types, or any argument has the wrong type according to `isinstance`, raise `TypeError`. An entry of `types` may also be a tuple of types, as `isinstance` allows, for example `typed((int, float), str)`.
starter:
```python
def typed(*types):
    pass
```
tests:
```python
add = typed(int, int)(lambda a, b: a + b)
assert add(2, 3) == 5
assert raises(TypeError, add, 2, "3")
assert raises(TypeError, add, 2)
assert raises(TypeError, add, 1, 2, 3)
greet = typed(str)(lambda name: "hi " + name)
assert greet("Ann") == "hi Ann"
assert raises(TypeError, greet, 5)
both = typed((int, float), str)(lambda x, s: s * int(x))
assert both(2.0, "ab") == "abab"
assert both(1, "z") == "z"
```
model:
```python
def typed(*types):
    def decorate(f):
        def wrapper(*args):
            if len(args) != len(types):
                raise TypeError("wrong number of arguments")
            for arg, t in zip(args, types):
                if not isinstance(arg, t):
                    raise TypeError(f"expected {t}, got {type(arg)}")
            return f(*args)
        return wrapper
    return decorate
```
hint: `typed(...)` returns a function that takes `f` and returns a new function; that is three nested layers.
hint: In the innermost function, compare `len(args)` with `len(types)`, then check each pair with `zip` and `isinstance`.
solution: This is a dynamic type check written by hand. `isinstance` accepts a tuple of types too, so `(int, float)` works without extra code. The wrapper raises `TypeError` before calling `f` when the arguments do not match.

```python
def weak_add(a, b):
```

prompt: Write `all_of_type(items, t)` that returns `True` if every element of the list `items` is an instance of the type `t` (according to `isinstance`), and `False` otherwise. An empty list gives `True`. Example: `all_of_type([1, 2], int)` is `True`.
starter:
```python
def all_of_type(items, t):
    pass
```
tests:
```python
assert all_of_type([1, 2, 3], int) is True
assert all_of_type([], str) is True
assert all_of_type([1, "2"], int) is False
assert all_of_type(["a", "b"], str) is True
```

model:
```python
def all_of_type(items, t):
    return all(isinstance(item, t) for item in items)
```
hint: The built-in `all` returns `True` for an empty sequence.
hint: Apply `isinstance(item, t)` to every item inside `all(...)`.
solution: `all(isinstance(item, t) for item in items)` does the check and returns `True` for an empty list. Note that `bool` is a subclass of `int`, so a list of booleans counts as a list of ints.
