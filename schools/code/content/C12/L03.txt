@article
A token list is flat, but arithmetic is nested: in `1 + 2 * 3` the product is a part of the sum. The **abstract syntax tree (AST)** records this structure and nothing else. Parentheses, whitespace and punctuation have done their job during parsing, so they do not appear as nodes (that is the "abstract" in the name).

### Representing the tree

In this course an AST node is a tuple whose first element names the kind of node:

```python
("num", 3)                       # the number 3
("neg", node)                    # unary minus
("bin", "+", left, right)        # binary operator
```

The tree for `1 + 2 * 3` is `("bin", "+", ("num", 1), ("bin", "*", ("num", 2), ("num", 3)))`. Reading it from the root, the top operation is `+`, and its right operand is the product.

### Recursive descent

**Recursive-descent parsing** turns a grammar directly into code: one function per nonterminal, and each function calls the functions for the nonterminals in its production. Here is the grammar from last week, with unary minus added:

```text
expr   -> term   ( ("+" | "-") term )*
term   -> factor ( ("*" | "/") factor )*
factor -> NUM | "(" expr ")" | "-" factor
```

The parser keeps a position `pos` into the token list. `peek` looks at the current token without consuming it; `advance` consumes it. Each function parses as much as it can and returns a node:

```python
def parse(tokens):
    pos = 0

    def peek():
        return tokens[pos] if pos < len(tokens) else ("EOF", "")

    def advance():
        nonlocal pos
        tok = peek()
        pos += 1
        return tok

    def expr():
        node = term()
        while peek() in (("OP", "+"), ("OP", "-")):
            op = advance()[1]
            node = ("bin", op, node, term())
        return node

    def term():
        node = factor()
        while peek() in (("OP", "*"), ("OP", "/")):
            op = advance()[1]
            node = ("bin", op, node, factor())
        return node

    def factor():
        kind, text = advance()
        if kind == "NUM":
            return ("num", int(text))
        if kind == "OP" and text == "-":
            return ("neg", factor())
        if kind == "LPAREN":
            node = expr()
            if advance()[0] != "RPAREN":
                raise SyntaxError("expected )")
            return node
        raise SyntaxError(f"unexpected token {text!r}")

    node = expr()
    if peek()[0] != "EOF":
        raise SyntaxError("unexpected trailing tokens")
    return node
```

### Why this gives the right shape

**Precedence** comes from the call structure. `expr` calls `term` for each operand, so products are fully built before `expr` sees a `+`. **Left associativity** comes from the loop: each pass makes the tree built so far the *left* child of a new node. For `10 - 4 - 3` the loop first builds `(10 - 4)` and then `((10 - 4) - 3)`.

Parentheses work because `factor` calls `expr` again: whatever is inside the parentheses is parsed from scratch and returned as a single node, which overrides precedence. Recursion in the grammar becomes recursion in the code, and the Python call stack plays the role of a stack of unfinished constructs.

### Errors

A parser should reject bad input with a clear error rather than guess. The final check above catches leftover tokens such as the `2 3` that follow the `1` in `1 2 3`. Real parsers also report position information; we leave it out for brevity.

Recursive descent is a **top-down** method that decides what to do by looking at the next token, which works for grammars with no left recursion. Writing `expr -> expr "+" term` directly would make `expr` call itself before consuming anything, which never terminates; the loop form above is the standard fix. For the grammars in this course, the parser runs in $O(n)$ time for $n$ tokens.

@example
title: Parsing 1 + 2 * 3 by hand
problem: Show how the parser builds the tree for the tokens of `1 + 2 * 3`.
step: `expr` calls `term`, which calls `factor`. The first token is `NUM 1`, so `factor` returns `("num", 1)`. `term` sees `+`, which is not `*` or `/`, so it returns the node unchanged.
step: Back in `expr`, the next token is `+`. The loop consumes it and calls `term` for the right operand.
step: That `term` gets `("num", 2)` from `factor`, sees `*`, consumes it and calls `factor` again to get `("num", 3)`. It builds `("bin", "*", ("num", 2), ("num", 3))` and returns.
step: `expr` builds `("bin", "+", ("num", 1), <that product>)`. No tokens remain, so the loop ends and the parse is complete.
answer: `("bin", "+", ("num", 1), ("bin", "*", ("num", 2), ("num", 3)))`

@example
title: Associativity from the loop
problem: Why does `8 - 3 - 2` parse as `(8 - 3) - 2`, and what does each loop pass hold?
step: `expr` starts with `node = ("num", 8)`.
step: Pass 1 consumes `-` and the operand 3, producing `node = ("bin", "-", ("num", 8), ("num", 3))`.
step: Pass 2 consumes the second `-` and the operand 2. The old `node` becomes the left child: `("bin", "-", (8 - 3 tree), ("num", 2))`.
step: The tree therefore means `(8 - 3) - 2 = 3`. Had the right operand been parsed recursively by `expr`, the tree would mean `8 - (3 - 2) = 7`.
answer: The loop makes the tree built so far the left child each time, so subtraction is left associative.

@mistakes
- Parsing `expr` as `term "+" expr` (recursing on the right), which makes `+` and `-` right associative and gives `8 - 3 - 2 = 7`.
- Forgetting to consume the closing parenthesis, or never checking that it is present.
- Not checking for leftover tokens after the top-level `expr`, so `1 2` is silently accepted as `1`.
- Putting `+` and `*` at the same grammar level, which loses precedence.

def toks(s):

    for m in re.finditer(r"\d+|[-+*/]|\(|\)", s):

        if t.isdigit():
            out.append(("NUM", t))
        elif t == "(":
