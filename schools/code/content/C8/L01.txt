@article
A computer has a handful of CPU cores, some RAM, a disk and a network card, yet you run dozens of programs at once, each behaving as though it owned the machine. The **operating system (OS)** makes this possible. It is the software that manages the hardware on behalf of programs and gives them a convenient, safe interface to it. The part that is always resident and runs with full hardware privileges is the **kernel**.

### Three roles

- **Virtualizer.** The OS turns one physical resource into many virtual ones: one CPU into many apparent CPUs, and one RAM into a private address space per program.
- **Resource manager.** The OS decides who gets the CPU, which memory frames and which disk blocks, and it must do so efficiently and fairly.
- **Standard library.** The OS exports **system calls** (open, read, fork and so on) so programs need not know the details of each device.

### The process

A **process** is a running program. Its machine state has three parts you should be able to list: its **address space** (the memory it can address: code, static data, heap and stack), its **registers** (including the program counter and stack pointer) and its **open resources** (such as open files). The OS keeps a record for each process, the **process control block (PCB)**, holding the saved registers, state, identifier and so on.

At any moment a process is in one of three basic states:

| state | meaning |
|---|---|
| running | executing instructions on a CPU |
| ready | could run, but the OS has chosen another process |
| blocked | waiting for an event (such as disk I/O) and cannot use the CPU |

The scheduler moves a process ready to running and back; starting an I/O request moves running to blocked; the I/O completing moves blocked to ready (never directly to running).

### Limited direct execution

To be fast, the OS runs a program **directly** on the CPU. To stay in control, the execution is **limited** by two hardware mechanisms.

1. **Privilege modes.** Code runs in **user mode**, where privileged operations (talking to devices, changing page tables, disabling interrupts) are forbidden, or in **kernel mode**, where everything is allowed. A user program that needs a privileged service executes a special **trap** instruction. The hardware raises the privilege level, saves the program's registers on a kernel stack, and jumps to a handler whose address the kernel stored in a **trap table** at boot. A user program cannot choose where the jump lands, which is why the mechanism is safe. A **return-from-trap** instruction lowers the privilege and resumes the program.
2. **The timer interrupt.** Without it, a program stuck in an infinite loop would own the CPU forever. A hardware timer raises an interrupt every few milliseconds; the hardware jumps into the kernel, which may then run the scheduler.

When the kernel decides to run a different process it performs a **context switch**: save the current process's registers into its PCB, load the registers of the next process, and return-from-trap into it. A context switch is pure overhead, so a time slice that is too short wastes CPU time. If a slice is $q$ ms and a switch costs $s$ ms, the fraction of time spent on useful work is $q/(q+s)$.

### A system call, traced

```c
#include <unistd.h>

int main(void) {
    write(1, "hi\n", 3);   /* wrapper in libc: puts number, traps */
    return 0;
}
```

The C library's `write` places the system call number and arguments in registers and executes the trap instruction. In kernel mode the handler looks up the number in a table of system call handlers, performs the write on file descriptor 1 (standard output), and returns the byte count to the user program.

@example
title: Tracing a process through its states
problem: A process starts ready. The scheduler picks it, it starts a disk read, the read finishes, and the scheduler picks it again. Give the state after each event, and say when the CPU could run some other process.
step: Start: the process is `ready`. It can run, but it is not running yet.
step: Event "scheduled": the OS loads its registers and runs it, so the state is `running`.
step: Event "starts a disk read": the process cannot continue until the data arrives, so it moves to `blocked`. This is when the CPU is free to run another process.
step: Event "disk read finishes": an interrupt tells the OS the data is ready, so the process moves to `ready`, not directly to `running`; the scheduler has not yet chosen it.
step: Event "scheduled again": the state is `running`. The full sequence is ready, running, blocked, ready, running.
answer: ready, running, blocked, ready, running

@example
title: The cost of context switching
problem: A time slice is 4.5 ms and one context switch costs 0.5 ms. What fraction of the CPU time is useful work, and how much does it change if the slice is lengthened to 19.5 ms?
step: Useful fraction is $q/(q+s)$, where $q$ is the slice and $s$ the switch cost.
step: For $q = 4.5$ and $s = 0.5$: $4.5/5.0 = 0.9$, so 90% is useful and 10% is overhead.
step: For $q = 19.5$: $19.5/20.0 = 0.975$, so 97.5% is useful.
step: Longer slices cut overhead but make interactive programs wait longer for their turn, so the OS must balance throughput against responsiveness.
answer: 90% and 97.5%

@mistakes
- Believing the blocked state returns directly to running: a process whose I/O completes becomes ready and waits for the scheduler.
- Thinking a system call is an ordinary function call: it changes the privilege level and jumps to an address chosen by the kernel, not by the caller.
- Thinking the OS is constantly running alongside programs: the kernel runs only on traps, interrupts and exceptions (and when it schedules itself).
- Counting the context-switch cost as zero: it is overhead during which no user instruction runs.

tests:
```python
assert final_state([]) == "ready"
assert final_state(["schedule"]) == "running"
assert final_state(["schedule", "io_start", "io_done", "schedule"]) == "running"
assert final_state(["schedule", "deschedule"]) == "ready"

assert raises(ValueError, final_state, ["schedule", "schedule"])
```
model:
```python
TRANSITIONS = {
    ("ready", "schedule"): "running",
    ("running", "deschedule"): "ready",
    ("running", "io_start"): "blocked",
    ("blocked", "io_done"): "ready",
}


def final_state(events):
    state = "ready"
    for event in events:
        if (state, event) not in TRANSITIONS:
            raise ValueError(f"{event!r} not allowed in state {state!r}")
        state = TRANSITIONS[(state, event)]
    return state
```
hint: A dictionary keyed by `(state, event)` pairs makes the allowed moves easy to look up.
hint: Loop over the events, look up the pair, and raise `ValueError` if the pair is not in the dictionary.
solution: Keep the current state, and for each event either move to the state in the transition table or raise `ValueError`. Events such as `io_done` while ready have no entry, so they raise.

@practice self
prompt: Explain why an operating system needs both a trap table and a timer interrupt to implement limited direct execution. What would go wrong without each?
hint: Ask who chooses where a trap jumps, and what brings control back from a looping program.
solution: The trap table is set up by the kernel at boot, in kernel mode, and holds the addresses of the handlers that traps jump to. Because a user program can only trap, not choose the destination, it can request services but cannot run its own code with kernel privileges; without a trap table (or with one the program could change) any program could take over the machine. The timer interrupt guarantees that control returns to the kernel periodically, even if the program never makes a system call. Without it, a program with an infinite loop would keep the CPU forever, and the OS could never switch to another process (cooperative scheduling would depend on every program behaving well).
rubric: States that the kernel installs the trap table at boot and the program cannot choose the jump target, so privileged code runs only at vetted entry points.
rubric: States that the timer interrupt forces control back to the kernel without the program's cooperation.
rubric: Gives the consequence of each missing mechanism (privilege escalation without the trap table; a runaway program monopolizing the CPU without the timer).

@quiz code
prompt: Write `run_interleaved(procs)`. Each element of `procs` is a Python generator standing for a process; each `next()` on it runs the process for one time slice and yields a label. Simulate round-robin: repeatedly take the live processes in list order and call `next()` once on each, appending the yielded label to a result list; a generator that is exhausted is removed. Return the result list.
starter:
```python
def run_interleaved(procs):
    pass
```
tests:
```python
def p(name, n):
    for i in range(n):
        yield f"{name}{i}"

assert run_interleaved([p("A", 2), p("B", 3)]) == ["A0", "B0", "A1", "B1", "B2"]
assert run_interleaved([p("X", 1)]) == ["X0"]
assert run_interleaved([]) == []
assert run_interleaved([p("A", 0), p("B", 2)]) == ["B0", "B1"]
assert run_interleaved([p("A", 1), p("B", 1), p("C", 2)]) == ["A0", "B0", "C0", "C1"]
```
model:
```python
def run_interleaved(procs):
    out = []
    live = list(procs)
    while live:
        still_live = []
        for gen in live:
            try:
                out.append(next(gen))
                still_live.append(gen)
            except StopIteration:
                pass
        live = still_live
    return out
```
hint: One pass over the live list gives each process one slice.
hint: Catch `StopIteration` from `next(gen)` to detect a finished process, and do not keep it for the next pass.
solution: Each outer pass is one round of the round-robin queue. A generator that raises `StopIteration` has terminated, so it is dropped; the others stay in order for the next round.
