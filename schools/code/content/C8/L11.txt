@article
Memory forgets when power is lost; a **file system** gives programs a persistent, named, organized way to store data on a block device. Its design is driven by the physics of the device.

### Hard disk drives

A **hard disk drive (HDD)** has spinning platters; an arm positions a head over a **track**, and the data under the head is read as the platter rotates. The time for one I/O has three parts:

$$T_{I/O} = T_{seek} + T_{rotation} + T_{transfer}.$$

- **Seek:** moving the arm to the right track (several milliseconds for a random seek).
- **Rotational delay:** waiting for the target sector to rotate under the head. On average it is half a rotation. A disk at 7200 RPM turns once in $60/7200 = 8.33$ ms, so the average delay is about 4.17 ms.
- **Transfer:** reading the bytes at the media rate: $T_{transfer} = \text{size}/\text{rate}$.

For small random reads, seek and rotation dominate (around 10 ms per request, so a few hundred small random I/Os per second), while a large **sequential** read pays them once and then streams at the full transfer rate (on the order of 100 MB/s or more). This gap shapes file system design: keep related data close together and issue large I/Os. Disk **schedulers** reorder requests to cut seek time: shortest-seek-time-first picks the nearest track but can starve far requests, while the **elevator (SCAN)** algorithm sweeps the arm in one direction serving requests in order, then reverses.

### Solid-state drives

An **SSD** stores bits in **NAND flash** and has no moving parts, so it has no seek or rotational delay. Its constraints are unusual: flash is read and written in **pages** (a few KB), but a page can only be written after the whole **block** containing it (many pages) has been **erased**, and each block survives a limited number of erase cycles. A **flash translation layer (FTL)** therefore remaps logical addresses to physical pages in a log-structured way, collects garbage from partly stale blocks, and spreads erases evenly (**wear leveling**). Rewriting data in place is expensive; random reads are fast; writes cost more than reads.

### File system structure

A Unix-style file system divides the disk into blocks (commonly 4 KB) arranged as:

- a **superblock** describing the file system (sizes, where the other regions are);
- an **inode bitmap** and a **data bitmap** recording which inodes and data blocks are free;
- the **inode table**, an array of **inodes**;
- the **data region**.

An **inode** (index node) stores everything about a file except its name and contents: type, size, owner, permissions, timestamps, a link count and **pointers** to its data blocks. To support big files without wasting space on small ones, the inode has a few **direct pointers** (for example 12) to data blocks, then a pointer to a **single indirect block** (a block full of pointers), a **double indirect** pointer, and sometimes a **triple indirect** one. With 4 KB blocks and 4-byte pointers, an indirect block holds $4096/4 = 1024$ pointers. The file can then have $12 + 1024 + 1024^2$ blocks without the triple level.

A **directory** is a file whose contents are a list of (name, inode number) pairs. The root directory has a well-known inode number. A **hard link** is another directory entry for the same inode (the link count counts them); a **symbolic link** is a small file containing a path.

### Reading a path

To open `/foo/bar`, the system reads the root directory's inode, then its data to find `foo`'s inode number; reads `foo`'s inode and then its data to find `bar`; and finally reads `bar`'s inode. If each directory fits in one block and nothing is cached, a path with $k$ components costs $1 + 2k$ reads. The cost grows with path depth, which is why file systems cache inodes and directory blocks in memory (the page cache).

@example
title: Disk I/O time
problem: A 7200 RPM disk has an average seek of 4 ms and a transfer rate of 100 MB/s (10^8 bytes per second). Estimate the time for a random 4096-byte read.
step: Rotational delay: half of one rotation, $0.5 \times 60000/7200$ ms $= 4.17$ ms.
step: Transfer: $4096 / 10^8$ s $= 0.04096$ ms.
step: Total: $4 + 4.17 + 0.04 \approx 8.21$ ms.
step: Only about 0.5% of the time is spent transferring data, which is why random small I/O is slow on a disk.
answer: about 8.2 ms

@example
title: Maximum file size of an inode
problem: Block size 1 KB (1024 bytes), 4-byte pointers, 10 direct pointers, one single indirect and one double indirect pointer. What is the maximum file size?
step: Pointers per indirect block: $1024/4 = 256$.
step: Blocks addressed: direct 10; single indirect 256; double indirect $256^2 = 65536$. Total: $10 + 256 + 65536 = 65802$ blocks.
step: Bytes: $65802 \times 1024 = 67{,}381{,}248$, about 64.3 MiB.
answer: 67,381,248 bytes

@mistakes
- Treating an SSD like a disk with no constraints: flash must be erased in blocks before pages are rewritten, so the FTL, not the file system, hides the in-place update.
- Computing the full rotation instead of half a rotation for the average rotational delay.
- Thinking an inode stores the file's name: names live in directory entries, which is why one inode can have several names.
- Forgetting the cost of reading each directory along a path, not just the final file's inode.

tests:
```python
args = (4096, 1024, 12)
assert locate_block(0, *args) == ("direct", 0)
assert locate_block(12 * 4096 - 1, *args) == ("direct", 11)
assert locate_block(12 * 4096, *args) == ("indirect", 0)
assert locate_block((12 + 1023) * 4096, *args) == ("indirect", 1023)

```
model:
```python
def locate_block(offset, block_size, ptrs_per_block, direct):
    b = offset // block_size
    if b < direct:
        return ("direct", b)
    b -= direct
    if b < ptrs_per_block:
        return ("indirect", b)
    b -= ptrs_per_block
    if b < ptrs_per_block * ptrs_per_block:
        return ("double", b // ptrs_per_block, b % ptrs_per_block)
    raise ValueError("offset beyond maximum file size")
```
hint: Subtract the number of blocks covered by each level as you move past it.
solution: Compute the file block number, then peel off levels: direct blocks first, then the single indirect range, then the double indirect range, where division and remainder by `ptrs_per_block` give the two indexes.
