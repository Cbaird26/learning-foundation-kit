@article
The **scheduler** decides which ready process runs next. The mechanism (the context switch) is separate from the **policy** (which job to pick), and the right policy depends on what you want to optimize. Two metrics matter most.

- **Turnaround time** of a job is its completion time minus its arrival time: $T_{turnaround} = T_{completion} - T_{arrival}$. It measures batch performance.
- **Response time** is the time from arrival until the job first runs: $T_{response} = T_{firstrun} - T_{arrival}$. It measures how interactive the system feels.

Fairness (no job starved) often conflicts with both. To begin, assume all jobs arrive at time 0, run to completion without I/O, and have known lengths.

### FIFO

**First in, first out** runs jobs in arrival order. Suppose A, B and C arrive together with lengths 100, 10 and 10 and run in that order. Their completion times are 100, 110 and 120, so the average turnaround is $(100+110+120)/3 = 110$. The short jobs wait behind the long one: the **convoy effect**.

### Shortest job first

**SJF** runs the shortest job first. With the same workload it runs B, C, A, with completions 10, 20 and 120, an average turnaround of 50. When all jobs arrive together, SJF is **optimal** for average turnaround. It needs job lengths in advance, and once jobs arrive at different times it suffers the same convoy problem: if A is already running when B and C arrive, they must wait for A.

### STCF

**Shortest time-to-completion first** (also called preemptive SJF) lets the scheduler preempt the running job whenever a new job arrives with less remaining time than what is left of the current job. If A (length 100) arrives at time 0 and B and C (length 10) arrive at time 10, A runs until 10, B and C run to completion by 30, then A finishes at 120. The turnaround times are 120, 10 and 20, an average of 50.

### Round robin

**Round robin (RR)** runs each job for a fixed **time slice** (quantum), then moves it to the back of the ready queue. RR gives excellent response time: with three jobs and a 1 ms quantum, the jobs first run at 0, 1 and 2 ms. But turnaround is poor, because every job is stretched out. The quantum trades response against context-switch overhead (week 1), and RR is fair but, among policies, is among the worst for average turnaround.

### Multi-level feedback queue

Real systems do not know job lengths. The **multi-level feedback queue (MLFQ)** learns from behavior. It has several queues with different priority levels, and these rules:

1. A job in a higher-priority queue runs before any job in a lower one.
2. Jobs in the same queue run round robin.
3. A new job starts at the highest priority.
4. A job that uses up its time allotment at a level moves down one level; a job that gives up the CPU early (for I/O) stays.
5. After some period, all jobs move back to the top (**priority boost**) so that long jobs do not starve and a job that changes behavior is treated fairly.

Short and interactive jobs finish while still at high priority; long CPU-bound jobs sink. The allotment accounting in rule 4 (rather than counting each slice) stops a program from gaming the scheduler by issuing an I/O just before its slice ends.

### Proportional share

**Lottery scheduling** gives each job tickets; at each slice a random ticket is drawn and its holder runs, so a job with 25% of the tickets gets about 25% of the CPU over time. **Stride scheduling** achieves the same deterministically. Linux's default scheduler for ordinary tasks was the Completely Fair Scheduler (CFS), which tracks virtual runtime; since Linux 6.6 it has been replaced by EEVDF, an earliest-eligible-virtual-deadline-first scheduler.

@mistakes
- Computing turnaround from time 0 instead of from the job's arrival time when jobs arrive later.
- Saying SJF is optimal in general: it is optimal for average turnaround only when all jobs arrive together (and lengths are known).
- Believing a small round-robin quantum always helps: it improves response time, but context-switch overhead grows and turnaround worsens.
- Forgetting that STCF preempts: a short arriving job interrupts a longer running job.

```python
def avg_turnaround(bursts, policy):
    order = sorted(bursts) if policy == "sjf" else list(bursts)
    t = 0
    total = 0
    for b in order:
        t += b
        total += t
    return total / len(order)
```

model:
```python
from collections import deque


def round_robin(bursts, quantum):
    remaining = list(bursts)
    done = [0] * len(bursts)
    queue = deque(range(len(bursts)))
    t = 0
    while queue:
        i = queue.popleft()
        run = min(quantum, remaining[i])
        t += run
        remaining[i] -= run
        if remaining[i] > 0:
            queue.append(i)
        else:
            done[i] = t
    return done
```
hint: Keep a queue of job indexes and a clock `t`.
hint: Pop a job, run it for `min(quantum, remaining)`, advance the clock, then either record its completion time or append it to the back.
solution: Simulate the queue directly. A job that finishes records the current clock as its completion time; an unfinished job goes to the back of the queue. With `[5, 3, 1]` and quantum 2, the finish times are 9, 8 and 5.

@practice self
prompt: An MLFQ scheduler has three queues. A long CPU-bound job and a stream of short interactive jobs share the machine. (a) Explain where each kind of job ends up and why. (b) Explain what could go wrong without a periodic priority boost.
hint: Think about which jobs use up their allotment and which give up the CPU early.
solution: (a) Every job starts in the top queue. The short interactive jobs finish, or give up the CPU for I/O, before using up their allotment, so they stay near the top and receive quick response. The long CPU-bound job uses its full allotment at each level and is demoted until it sits in the bottom queue, where it runs only when no higher queue has work. (b) Without a boost, if interactive jobs keep arriving, the CPU-bound job can starve in the bottom queue. A job that later changes to interactive behavior would also be stuck at low priority. A periodic boost to the top queue guarantees progress and lets the scheduler relearn each job's behavior.
rubric: Says short and interactive jobs stay at high priority because they do not use up their allotment.
rubric: Says the CPU-bound job is demoted to the lowest queue.
rubric: Identifies starvation of low-priority jobs as the problem the boost solves.
rubric: Notes the boost also corrects for jobs that change behavior.

```python
def lottery_winner(tickets, draw):
    counter = 0
    for job, count in enumerate(tickets):
        counter += count
        if draw < counter:
            return job
    raise ValueError("draw out of range")
```
