@article
"It works on my machine" usually means "my machine has a different Python, different libraries and a different operating system from yours." A **container** removes the differences by shipping the application together with its dependencies. An **image** is the packaged, read-only template; a **container** is a running instance of an image. Unlike a virtual machine, a container shares the host's kernel, so it starts in seconds and is much lighter. Docker is the best-known tool, and the image format is an open standard (OCI), so the same image runs on many platforms.

### A Dockerfile for a Python web app

A **Dockerfile** is a recipe: each instruction creates a **layer**, and layers are cached. Here is a Dockerfile for an application whose code is a package `app` served by Gunicorn (listed in `requirements.txt`):

```dockerfile
FROM python:3.13-slim-bookworm

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

RUN useradd --create-home --uid 10001 appuser

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

USER appuser
EXPOSE 8000

HEALTHCHECK --interval=30s --timeout=3s \
    CMD ["python", "-c", "import urllib.request as u; u.urlopen('http://127.0.0.1:8000/health')"]

CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]
```

What each part does and why:

- **`FROM python:3.13-slim-bookworm`** pins the language version and the Debian release; never use `latest`, because it changes under you. For strictly reproducible builds, pin the image digest as well (`python:3.13-slim-bookworm@sha256:...`) and update it deliberately. Newer Python versions and newer Debian releases than `bookworm` exist, so check the official image page and move up on purpose, keeping the same pinning habit.
- **`PYTHONUNBUFFERED=1`** makes logs appear immediately, which matters when you read them from the container's output.
- **`COPY requirements.txt .` before `COPY . .`** is a caching trick: dependency installation is expensive and only changes when `requirements.txt` changes, so it sits in an early layer that is reused when only your code changes.
- **`USER appuser`** runs the process without root, so a bug in the app cannot trivially control the container.
- **`HEALTHCHECK`** lets the runtime test whether the app answers; it uses only the standard library so the image needs no extra tools.
- **`CMD`** in the exec (JSON array) form runs the server as the main process so it receives stop signals.

The app listens on a port taken from configuration and logs to standard output (twelve-factor "port binding" and "logs" factors); the platform decides where those go.

### Keep images small and clean

Add a `.dockerignore` so the build context excludes junk and, importantly, secrets:

```text
.git
.venv
__pycache__/
*.pyc
.env
.pytest_cache/
tests/
```

For compiled dependencies, a **multi-stage build** compiles in a first stage and copies only the result into a slim final stage. Never `COPY .env` and never write secrets with `ENV` or `ARG`, because both stay readable in the image history. Rebuild regularly to pick up security patches in the base image, and scan images for known vulnerabilities (week 10).

### Building and running

```bash
docker build -t toolshare:0.1.0 .
docker run --rm -p 8000:8000 --env-file .env toolshare:0.1.0
```

`-t` names and tags the image with a version, `-p 8000:8000` maps host port to container port (`host:container`), and `--env-file` supplies config at runtime without baking it in. Tag images with the version or the Git commit hash so you always know what is running.

### Docker Compose for local development

**Docker Compose** describes several containers in one file. This `compose.yaml` runs the app with a PostgreSQL database:

```yaml
services:
  web:
    build: .
    ports:
      - "8000:8000"
    env_file: .env
    environment:
      DATABASE_URL: postgresql://app:${DB_PASSWORD}@db:5432/app
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:17-bookworm
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${DB_PASSWORD:?set DB_PASSWORD in your shell or .env}
      POSTGRES_DB: app
    volumes:
      - dbdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 10

volumes:
  dbdata:
```

Start it with `docker compose up --build`. The `${DB_PASSWORD:?...}` form stops with an error if the variable is missing, so there is no default password in the file. The named volume keeps database data when the container is replaced; containers themselves are disposable. Inside Compose, the app reaches the database by the service name `db`, not `localhost`, which is why `web` overrides `DATABASE_URL` from `.env` with a host of `db` and the same password. PostgreSQL has newer major versions than 17; pick a current supported one on purpose.

@example
title: Fixing a slow, fragile Dockerfile
problem: A Dockerfile starts `FROM python:latest`, runs `COPY . .` first, then `pip install -r requirements.txt`, and has no `USER`. Every code edit reinstalls all dependencies. Fix it.
step: Pin the base image: `FROM python:3.13-slim-bookworm`, so builds are repeatable and smaller.
step: Reorder for caching: `COPY requirements.txt .`, then `RUN pip install --no-cache-dir -r requirements.txt`, then `COPY . .`. Now editing code reuses the dependency layer.
step: Add a non-root user with `RUN useradd --create-home --uid 10001 appuser` and `USER appuser` before `CMD`.
step: Add a `.dockerignore` listing `.git`, `.venv` and `.env` so the build context is small and no secret can be copied in.
answer: A pinned base image, dependency layer before the code layer, a non-root user and a `.dockerignore`.

@example
title: Running the container with config
problem: The container exits immediately with `DATABASE_URL is required`. You have a local `.env` file. How do you start it and confirm it works?
step: The error is the app failing fast, which is correct: the container has no environment yet.
step: Supply config at runtime: `docker run --rm -p 8000:8000 --env-file .env toolshare:0.1.0`.
step: Open `http://localhost:8000/health` in a browser, or run `docker ps` and look for `healthy` in the status column after the interval passes.
step: Read logs with `docker logs <container-name>`; they come from standard output, so no log files are involved.
answer: Pass the variables with `--env-file` at run time and verify via the health endpoint and `docker logs`.

@mistakes
- Using `FROM python:latest` or an untagged image, so a rebuild next month silently changes the Python version.
- Copying all files before installing dependencies, which defeats layer caching and slows every build.
- Running as root, or baking secrets into the image with `COPY .env`, `ENV` or `ARG`.
- Treating a container like a server: storing data inside it, instead of in a volume or an external database.

model:
```python
def lint_dockerfile(text):
    problems = []
    unpinned = False
    uses_add = False
    has_user = False
    for raw in text.splitlines():
        line = raw.strip()
        parts = line.split()
        if not parts:
            continue
        word = parts[0].upper()
        if word == "FROM":
            args = [p for p in parts[1:] if not p.startswith("--")]
            image = args[0] if args else ""
            if "@sha256:" not in image:
                name = image.split("/")[-1]
                if ":" not in name or name.endswith(":latest"):
                    unpinned = True
        elif word == "ADD":
            uses_add = True
        elif word == "USER":
            has_user = True
    if unpinned:
        problems.append("unpinned-base")
    if uses_add:
        problems.append("uses-add")
    if not has_user:
        problems.append("runs-as-root")
    return problems
```
hint: Split each line into words; the first word is the instruction.
hint: Look for the tag only in the last path segment, because a registry host can contain a colon for a port.
solution: Walk the lines, recording whether any `FROM` image is unpinned (checking the tag only in the segment after the last `/`), whether `ADD` appears, and whether `USER` appears. Then append the problem names in the required order.

```python
def is_ignored(path, patterns):
    name = path.split("/")[-1]
    for pattern in patterns:
        if pattern.endswith("/"):
            if path.startswith(pattern):
                return True
        elif pattern.startswith("*."):
            if name.endswith(pattern[1:]):
                return True
        elif path == pattern:
            return True
    return False
```
hint: Handle the three pattern kinds in separate branches.
hint: For `*.pyc`, compare the end of the file name with `.pyc` (the pattern without its `*`).
solution: A trailing-slash pattern is a prefix test on the path, a `*.ext` pattern is a suffix test on the file name, and everything else is exact equality. Return `True` on the first match and `False` after the loop.

model:
```python
def parse_port_mapping(text):
    parts = text.split(":")
    if len(parts) != 2:
        raise ValueError("expected host:container")
    numbers = []
    for part in parts:
        if not part.isdigit():
            raise ValueError(f"not a port number: {part!r}")
        number = int(part)
        if not 1 <= number <= 65535:
            raise ValueError(f"port out of range: {number}")
        numbers.append(number)
    return (numbers[0], numbers[1])
```
hint: `text.split(":")` gives the pieces; check how many there are first.
hint: `"".isdigit()` is `False`, which handles an empty part.
solution: Split on `:`, require exactly two parts, require each to be all digits with `isdigit`, convert, and check the range 1 to 65535 before returning the tuple.
