@article
On day one at a new company, the first thing you touch is a repository. A clean one tells you how to run the project in five minutes; a messy one costs you a week. You are about to be the person who sets it up, so do it the way you wish you had found it.

### A repository a stranger can use

Start with these files at the root:

- `README.md`: what the project is, how to run it, how to test it (expand it in week 11).
- `LICENSE`: for public repositories, choose an open-source license deliberately (MIT and Apache 2.0 are permissive; the GPL is copyleft). This is not legal advice; read the license text before choosing.
- `.gitignore`: files that must never be committed: virtual environments, caches, build output, editor files and, above all, secrets such as `.env`.
- A dependency file (`requirements.txt` or `pyproject.toml`) with versions pinned or bounded, so everyone builds the same thing.
- Folders such as `src/` or an app package, `tests/`, and later `docs/`.

```bash
git init -b main
printf '.venv/\n__pycache__/\n.env\n*.pyc\n.pytest_cache/\n' > .gitignore
git add README.md LICENSE .gitignore
git commit -m "chore: initial project skeleton"
```

Check that an ignore rule works with `git check-ignore -v .env`, which prints the rule that matches. If you committed a file by mistake, `git rm --cached .env` removes it from the index without deleting your local copy. Remember that a secret already pushed is compromised even after you delete it (week 5).

### Branching: keep it short-lived

Use **trunk-based development with short-lived branches**: `main` always works, and every change happens on a branch that lives a day or two and merges through a pull request. Name branches by type and topic: `feature/reserve-tool`, `fix/overlap-off-by-one`, `docs/readme-setup`.

```bash
git switch -c feature/reserve-tool
# edit, then
git add -p
git commit -m "feat(reservations): reject overlapping dates"
git push -u origin feature/reserve-tool
```

`git switch -c` creates and switches to a branch (`git checkout -b` does the same). Long-lived branches drift away from `main` and produce painful merges.

### Commit messages

The **Conventional Commits** format makes history readable and enables automatic changelogs:

```text
type(scope): short description in the imperative

Optional body explaining why, not what.
```

Common types are `feat`, `fix`, `docs`, `test`, `refactor`, `chore` and `ci`. A `!` after the type or scope (`feat(api)!: remove v1`) marks a breaking change. Each commit should do one thing and leave the tests passing.

### Pull requests and review

A **pull request (PR)** proposes merging your branch. Keep it small: reviewers can read about 200 to 400 changed lines carefully; beyond that, they skim. A good PR description says what changed, why, how you tested it, and anything you want the reviewer to look at. Attach a PR template to the repository so every PR starts with those headings.

Protect `main` in your hosting service's repository settings: require a pull request, require the CI checks from next week to pass, and (on a team) require one approval. Solo, you can still review your own PR the next morning; you will catch real mistakes.

When reviewing, read in this order:

1. **Does it do what the issue asks?** Compare with the acceptance criteria.
2. **Is it correct?** Edge cases, error handling, off-by-one, concurrency.
3. **Are there tests** that would fail if the code were wrong?
4. **Security:** untrusted input, secrets, access checks.
5. **Clarity:** names, size of functions, comments that explain why.

Give feedback on the code, not the person. Prefer questions ("What happens if `end` is before `start`?") and label preferences as nits so authors know what blocks the merge. Authors: respond to every comment, and do not take review personally.

@example
title: Writing and splitting a commit history
problem: You changed three things: added overlap detection, fixed a typo in the README, and updated a dependency. How should you commit and branch?
step: Group by purpose: one feature, one docs fix and one dependency change. Mixed commits are hard to review and impossible to revert cleanly.
step: Put the overlap feature on `feature/overlap-detection` and commit it as `feat(reservations): reject overlapping dates`.
step: The typo does not need the feature branch: make `docs/readme-typo` from `main` with `docs: fix typo in setup section`, or commit it separately and push it as its own small PR.
step: Put the dependency bump on `chore/bump-framework` with `chore(deps): update web framework to latest patch release`, so a regression can be reverted alone.
answer: Three branches or at least three commits, each with one purpose and a conventional message.

@example
title: Reviewing a pull request diff
problem: A PR adds `SECRET_KEY = "abc123"` to `settings.py`, a 900-line change, and no tests. What do you write?
step: Block on the secret first: a hard-coded key in the repository must be removed and rotated, and read from an environment variable instead.
step: Ask for a split: "This is 900 lines across three concerns; can you split it into smaller PRs so I can review each properly?"
step: Request tests tied to the acceptance criteria and name one missing case, for example overlapping dates.
step: Add a nit separately (a variable name) and say it does not block merge. Close with something specific that was done well.
answer: Block on the secret and the size, ask for tests, and keep nits clearly separate.

@mistakes
- Committing `.env`, a virtual environment or build output, because `.gitignore` was added after the files were tracked.
- Working on one branch for weeks and merging a huge change that nobody can review.
- Writing messages like "fix stuff" or "wip", which make history and changelogs useless.
- Reviewing only style (indentation, naming) and missing tests, access checks and error handling.

Otherwise return `False`.

tests:
```python
assert valid_branch("feature/reserve-tool") is True
assert valid_branch("fix/a1") is True
```

```python
import re

PATTERN = re.compile(r"(feature|fix|chore|docs)/[a-z0-9]+(-[a-z0-9]+)*")


def valid_branch(name):
    return PATTERN.fullmatch(name) is not None
```
hint: A regular expression with `fullmatch` checks the whole string.
hint: A topic is `[a-z0-9]+` followed by zero or more groups of a hyphen and more of the same.

@practice code
prompt: Write `parse_commit(message)` for the first line of a Conventional Commit, `type(scope)!: description`. Return a tuple `(type, scope, breaking, description)`. The scope in parentheses and the `!` are optional: `scope` is `None` when absent and `breaking` is `True` only when `!` is present. The type is lowercase letters. If the line does not match, raise `ValueError`.
starter:
```python
def parse_commit(message):
    pass
```
tests:
```python
assert parse_commit("feat(api): add search") == ("feat", "api", False, "add search")
assert parse_commit("fix: handle empty list") == ("fix", None, False, "handle empty list")
assert parse_commit("feat(api)!: remove v1") == ("feat", "api", True, "remove v1")
assert parse_commit("chore!: drop old python") == ("chore", None, True, "drop old python")
assert raises(ValueError, parse_commit, "fixed stuff")
assert raises(ValueError, parse_commit, "feat:no space")
assert raises(ValueError, parse_commit, "Fix: capital type")
```
model:
```python
def parse_commit(message):
    head, sep, description = message.partition(": ")
    if not sep or not description:
        raise ValueError(f"not a conventional commit: {message!r}")
    breaking = head.endswith("!")
    if breaking:
        head = head[:-1]
    scope = None
    kind = head
    if head.endswith(")"):
        kind, _, rest = head.partition("(")
        scope = rest[:-1]
    if not (kind.isalpha() and kind.islower()):
        raise ValueError(f"bad type in {message!r}")
    return (kind, scope, breaking, description)
```
hint: Split the line at the first `: ` with `str.partition`; the left part holds the type, scope and `!`.
hint: Remove a trailing `!` first, then a trailing `(scope)`; what is left must be lowercase letters.
solution: Partition at `: ` to separate the description, strip a trailing `!` to set `breaking`, split `type(scope)` at the parenthesis, and raise `ValueError` for a missing separator or a type that is not lowercase letters.

```python
def size_label(additions, deletions):
    total = additions + deletions
    if total <= 50:
        return "small"
    if total <= 400:
        return "medium"
    return "large"
```
hint: Add the two numbers first and compare the total.
hint: The boundaries are inclusive: 50 is small and 400 is medium.
solution: Compute `total = additions + deletions` and compare against 50 and 400 with `<=`, so exactly 50 is small and exactly 400 is medium.
