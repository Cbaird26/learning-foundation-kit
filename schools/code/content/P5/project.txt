@project
title: Ship it: a complete deployed application
overview: Plan, build, test, containerize, deploy, monitor, document and demo a small but real application, using everything from this course. You finish with a live (or recorded) system, a public repository with a visible history, and a retrospective that shows what you learned.
goal: Deliver a small application for a named user that is deployed and reachable, built through pull requests with automated checks.
goal: Show a professional delivery path: CI, a container, configuration and secrets handled correctly, a release process with a rollback, and monitoring.
goal: Communicate the work: README, architecture notes, a demo and an honest retrospective.
step: Week 1 to 2, scope and plan. Choose the project using the proposal template in the material below. Write the one-page proposal (problem, user, success criteria, three to six MVP features, non-goals, risks) and turn it into milestones M1 to M5 and a backlog of small issues with acceptance criteria.
step: Week 3 to 4, repository and CI. Create the repository with `.gitignore`, license, README and `.env.example`. Protect `main`, work through short-lived branches and pull requests with conventional commit messages, and add a CI workflow that lints and runs tests with coverage. Write a first vertical slice with tests and merge it only on green.
step: Week 5 to 6, configuration and container. Move all configuration into one validated settings function, keep secrets out of Git and images, and write a Dockerfile (pinned base image, non-root user, cached dependency layer), a `.dockerignore` and a `compose.yaml` that runs the app with its database locally.
step: Week 7 to 8, deploy and release. Choose a hosting option (a platform as a service or a managed container host are good defaults; check current prices and free-tier limits yourself, and never pay to finish this project). Add a health endpoint, deploy the first working version with HTTPS, write the smoke test, and set up a release workflow that promotes one tagged image from staging to production. Rehearse a rollback once.
step: Week 9 to 10, observe and review. Add structured logs, a request ID, an uptime check and one symptom-based alert. Review performance, security (against the OWASP Top 10:2025) and accessibility (against WCAG 2.2) using the review checklist in the material. Fix at least three real findings and record the rest in the backlog.
step: Week 11 to 12, document and present. Finish the README, the architecture notes with at least one ADR, and the runbook. Rehearse and give a five-minute demo (live, or a recording with a live segment), and write the retrospective with owned, dated actions.
step: Week 13, polish and submit. Follow the final checklist in the material, check the repository from a fresh clone, remove secrets and private data, and decide whether to keep the app running or tear it down and replace the link with a recording.

@review
## Week-by-week review

**Weeks 1-2: Scope and plan.** A good capstone has a real user, fits your hours (plan for about 60 percent of them), shows engineering range and can be demoed in five minutes. The proposal states the problem, success criteria, three to six MVP features and explicit non-goals. Milestones are demonstrable states, and the first is a deployed walking skeleton. Issues are small, with testable acceptance criteria and a definition of done. Forecast with velocity: remaining points divided by average velocity, rounded up, and re-forecast weekly.

**Weeks 3-4: Repository and CI.** `.gitignore` before the first commit, short-lived branches, conventional commits, small pull requests, protected `main`. Review in order: does it meet the issue, is it correct, are there tests, is it secure, is it clear. CI runs on every push and pull request on a clean machine, cheap checks first, with read-only permissions, caching and a required status check. Never hide failures with `|| true`; fix or quarantine flaky tests.

**Weeks 5-6: Configuration and containers.** Config comes from the environment, validated once at startup (fail fast). Secrets live in a secrets store, never in the repository, image or logs; a leaked secret is revoked and rotated first. A Dockerfile uses a pinned base image, copies dependency files before code for caching, runs as non-root, and is paired with a `.dockerignore`. An image is a template and a container is a running instance. Compose runs the app and its database locally.

**Weeks 7-8: Deployment and delivery.** Options: platform as a service, managed container host, a virtual machine, serverless or static hosting; check prices and free tiers yourself. Steps: build, configure, migrate, start with a health check, enable HTTPS, smoke test. Retry with capped exponential backoff. Build once and promote the same tagged image; use semantic versioning, feature flags and canary or blue-green releases; roll back by redeploying the previous tag, and use expand and contract for schema changes.

**Weeks 9-10: Observability and review.** Structured logs to standard output, request IDs, no secrets. Golden signals: latency, traffic, errors, saturation; use percentiles. Alert on sustained symptoms, with actionable messages. Review performance (N+1 queries, indexes, pagination), security (OWASP Top 10:2025, parameterized queries, access checks, rate limiting) and accessibility (WCAG 2.2: keyboard, labels, 4.5:1 contrast, 24 by 24 pixel targets).

**Weeks 11-12: Documentation and presentation.** README with a tested quick start, architecture notes, ADRs, a runbook, a changelog. A five-minute demo with a backup recording. A blameless retrospective with owned, dated actions. A portfolio with a resume bullet that states impact, and a plan to tear down or keep paying nothing.

## Most common errors

- A project that is too big or has no real user.
- Estimating with no buffer and leaving deployment to the end.
- Committing `.env`, or believing deleting a leaked key makes it safe.
- `latest` base images, running as root, and baking secrets into images.
- Comparing versions as strings and rebuilding images for production.
- Alerting on causes instead of user-visible symptoms; logging personal data.
- Documentation never tested on a fresh clone, and retrospectives with vague actions.

@exam code
prompt: A release pipeline asks a function to make a decision. Write `release_decision(report)` where `report` is a dict with the keys `"secret_found"` (bool), `"tests_passed"` (bool), `"coverage"` (percent, number), `"version"` and `"current_version"` (strings such as `"1.4.0"`, an optional leading `v` is allowed) and `"error_rate"` (a fraction such as 0.03 measured on the new version, or `None` if the release has not been deployed yet). Check in this order and return the first that applies: `"block: secret"` if a secret was found; `"block: tests"` if the tests did not pass; `"block: coverage"` if coverage is below 80; `"block: version"` if `version` is not strictly newer than `current_version` (compare the numbers, not the text); `"rollback"` if `error_rate` is not `None` and is greater than 0.02; otherwise `"deploy"`.
starter:
```python
def release_decision(report):
    pass
```
tests:
```python
ok = {
    "secret_found": False, "tests_passed": True, "coverage": 85,
    "version": "1.10.0", "current_version": "1.9.3", "error_rate": None,
}
assert release_decision(ok) == "deploy"
assert release_decision({**ok, "secret_found": True, "tests_passed": False}) == "block: secret"
assert release_decision({**ok, "tests_passed": False}) == "block: tests"
assert release_decision({**ok, "coverage": 79.9}) == "block: coverage"
assert release_decision({**ok, "coverage": 80}) == "deploy"
assert release_decision({**ok, "version": "v1.9.3"}) == "block: version"
assert release_decision({**ok, "version": "1.9.10", "current_version": "1.9.9"}) == "deploy"
assert release_decision({**ok, "error_rate": 0.03}) == "rollback"
assert release_decision({**ok, "error_rate": 0.02}) == "deploy"
assert release_decision({**ok, "error_rate": 0.0}) == "deploy"
```
model:
```python
def _parse(version):
    text = version[1:] if version.startswith("v") else version
    return tuple(int(part) for part in text.split("."))


def release_decision(report):
    if report["secret_found"]:
        return "block: secret"
    if not report["tests_passed"]:
        return "block: tests"
    if report["coverage"] < 80:
        return "block: coverage"
    if _parse(report["version"]) <= _parse(report["current_version"]):
        return "block: version"
    rate = report["error_rate"]
    if rate is not None and rate > 0.02:
        return "rollback"
    return "deploy"
```
hint: Write the checks as a chain of `if` statements in exactly the order given; the first match returns.
hint: Convert versions to tuples of ints to compare them; the new version must be strictly greater. Compare `error_rate` with `None` using `is not None`, because 0.0 is a valid rate.
solution: Check the secret, tests and coverage in order, then compare versions as integer tuples (so `1.10.0` is newer than `1.9.3`, and equal versions are blocked), then roll back only if an error rate exists and exceeds 0.02. A rate of exactly 0.02 or 0.0 deploys.

@exam num
prompt: After a deploy, a script polls the health endpoint with exponential backoff. The wait before retry number `i` (starting at 0) is `1 * 2**i` seconds, never more than 10 seconds. There are 6 waits (retries 0 to 5) before the script gives up. What is the total waiting time in seconds?
answer: 35
check: sum(min(10, 1 * 2**i) for i in range(6))
hint: List the waits: 1, 2, 4, 8, then the cap applies.
hint: The fifth and sixth waits would be 16 and 32, but each is limited to 10.
solution: The waits are 1, 2, 4, 8, 10 and 10 seconds, because 16 and 32 are capped at 10. Their sum is 35 seconds.

@exam self
prompt: Incident scenario for a fictional service. At 14:02 you deploy version 1.5.0 of the tool-reservation app (the tests were green). At 14:09 the error rate alert fires at 7 percent. The logs show `column "member_id" does not exist` on every reservation request. The release renamed the column `owner` to `member_id` in a single migration and the code now uses only `member_id`. Write the response: the immediate steps in order (including why a plain code rollback may not be enough), the follow-up fix using expand and contract, what you would add to the pipeline and monitoring so it cannot happen silently again, and a short blameless postmortem summary with two owned, dated actions.
hint: Think about which version of the code works against which schema, and what a smoke test after the migration would have caught.
solution: Immediate steps: (1) Confirm the alert and its cause from the logs and note the start time (14:02 deploy, 14:09 alert). (2) Stop the damage quickly: because the migration renamed the column in one step, the old code (1.4.x) expects `owner` and the new code expects `member_id`, so redeploying the old image alone would fail too. Restore compatibility by adding the old column back (a reversible migration that adds `owner` again and copies the values from `member_id`) or by rolling the schema back with the pre-tested down migration, and then redeploy the previous image tag; if a restore from backup is required, say so and note the data-loss window. (3) Run the smoke test, confirm the error rate falls, and announce the status. Follow-up fix using expand and contract: release A adds `member_id`, writes to both columns and reads from `owner`; a backfill copies existing rows; release B reads from `member_id` while still writing both; release C, after it has been stable, drops `owner`. At each step the previous release still works with the current schema. Prevention: run migrations in staging against a copy of production-like data before every release; add a smoke test that creates and reads a reservation to the release workflow, run after deploying to staging and again to production, failing the release automatically; add a CI check or review rule that flags destructive migrations (drop or rename) and requires an expand-and-contract plan; keep the error-rate alert and link it to the runbook with rollback steps; consider a canary rollout so only a small share of traffic is hit. Postmortem (blameless): the release went out with a breaking schema change and no end-to-end check that exercised the database against the new code, so the failure was found by users' errors, not by the pipeline; impact at least seven minutes of failing reservations (from the 14:02 deploy until service is restored); detected by the alert at 14:09, seven minutes after the deploy. Actions: (1) Add the reservation smoke test to the release workflow; owner Sam Example; due Friday. (2) Write a migration policy and review checklist requiring expand and contract for any rename or drop; owner Sam Example; due next Wednesday.
rubric: The immediate response puts restoring service first, and recognizes that rolling back only the code is insufficient because the schema and the code are incompatible.
rubric: Describes expand and contract correctly across several releases, with the old release working against the current schema at each step.
rubric: Adds specific preventive controls: a post-deploy smoke test, migrations tested before production, and a gate or review for destructive changes.
rubric: The postmortem is blameless, states impact and detection, and has two actions that are specific, owned and dated.
