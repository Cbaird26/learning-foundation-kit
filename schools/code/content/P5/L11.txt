@lesson
title: Documentation and handover
summary: Write a README, architecture notes, decision records and a runbook so that another engineer can run, change and operate your application without you.
objective: Write a README that gets a newcomer from clone to running application quickly.
objective: Record architecture and decisions in short, durable documents, including an architecture decision record.
objective: Produce a runbook and changelog that make the handover safe.
reading: The Twelve-Factor App, the "Codebase" (I) and "Admin processes" (XII) factors, which describe what should be reproducible by anyone who has the repository.

@article
Imagine you are leaving for three weeks and a colleague has to fix a bug at 2 a.m. What do they have? If the answer is "me, on my phone", you have not finished the project. Documentation is part of the product, and it is the part hiring managers read first. Keep it short, accurate and close to the code, so it gets updated with the code. This approach is called **docs as code**: documentation lives in the repository, is reviewed in pull requests and is checked in CI where possible (for example, a link checker).

### The README

The README is the front door. Write it for a reader who has ten minutes. A good order:

1. **What it is:** one paragraph and a screenshot or link to the live demo.
2. **Quick start:** the exact commands to run it locally, tested on a clean machine.
3. **Configuration:** the environment variables, pointing at `.env.example`.
4. **Tests:** how to run them.
5. **Deployment:** where it runs and how a release happens.
6. **Architecture:** a short summary linking to the architecture notes.
7. **Contributing and license:** how to propose changes and what the license is.

```bash
git clone https://example.test/your-name/toolshare.git
cd toolshare
cp .env.example .env
docker compose up --build
# open http://localhost:8000
```

Test the quick start by following it yourself on a fresh clone. Instructions that "work on my machine" are the most common README failure.

### Architecture notes

One or two pages: a **context** sentence (who uses the system), a **diagram** of the main parts and how they talk (browser, web service, database, external services; a simple box-and-arrow picture is enough, and a text description works too), the **data model** (the main tables or entities), and the **request flow** for one important feature, step by step. Add the **deployment view**: what runs where. Diagrams drawn as text (for example in a Mermaid code block, which many hosting sites render) can be reviewed like code.

### Architecture decision records

An **architecture decision record (ADR)** is a short file that captures one significant decision and why. In six months nobody remembers why you chose a relational database or a particular host, and without a record people either relitigate the decision or fear to change it. A standard shape:

```text
# 0003. Use PostgreSQL for storage

Status: Accepted (2026-03-04)

Context: We need transactions to prevent double bookings, and
relational queries for availability.

Decision: Use a managed PostgreSQL database.

Consequences: Good: strong consistency, constraints. Bad: a
schema to migrate; the free tier limits storage.
```

Number the files and keep them in `docs/adr/` with names like `0003-use-postgresql.md`. Never edit an old decision; add a new one that supersedes it. Write ADRs for decisions that are expensive to reverse.

### The runbook

A **runbook** is for the person who is paged. It answers: what is this alert, how do I check it, how do I fix or roll back. Include how to read logs, how to deploy and roll back (week 8), how to restart, how to restore the database, who or what the dependencies are, and a table of known problems with their fix. Write it in plain commands someone half-asleep can follow.

### Changelog and API docs

Keep a **changelog** for users: group changes under Added, Changed, Fixed, Removed for each version, following the Keep a Changelog convention, and generate drafts from Conventional Commit messages (week 3). If your service has an HTTP API, document each endpoint with a request and response example; many frameworks can generate an OpenAPI description to publish.

### Comments versus documents

Comments explain **why**, not what: a comment repeating the code is noise, and docs that are never updated are worse than none. Put every instruction in exactly one place, and link to it elsewhere.

### Handover test

The best test of documentation: give your repository to someone else (or to yourself after a week away) and watch. Wherever they get stuck, the docs are missing something. Fix the docs, not the person.

@example
title: Writing a quick start that works
problem: Your README says "install the dependencies and run the app". A reviewer who tries it on a fresh machine fails. Improve it.
step: Find out what they hit by following your own instructions on a fresh clone: they needed a `.env` file, a database and a port.
step: Write the exact commands: `cp .env.example .env`, `docker compose up --build`, and the URL to open.
step: State prerequisites with versions (Docker, and Python 3.13 if running without Docker) and how to check them, for example `docker --version`.
step: Add what success looks like ("the page shows the tool list") and the first thing to check if it fails, then re-test on a clean clone.
answer: A tested, copy-pasteable quick start with prerequisites, commands, the expected result and a first troubleshooting hint.

@example
title: Recording a decision
problem: You are choosing between a managed database and a SQLite file for a deployed capstone. How do you record the choice?
step: Create `docs/adr/0002-use-managed-postgresql.md` with a status and date.
step: State the context: the app runs in containers that are replaced on every deploy, so a local file would be lost, and two requests must not book the same tool.
step: State the decision and the alternatives considered: a SQLite file on a volume (simple, but fragile when containers move) and a managed PostgreSQL service (strong constraints, free tier limits).
step: List consequences, good and bad, so a future reader sees the cost you accepted and can revisit it when the situation changes.
answer: A short numbered ADR with status, context, decision, alternatives and consequences.

@mistakes
- A README that explains the idea at length but never says how to run the project, or whose instructions were never tested on a clean machine.
- Documentation in a separate wiki that nobody updates, rather than next to the code and reviewed with it.
- Decisions that live only in someone's head or in a chat thread, so they are repeated or reversed by accident.
- Comments that restate the code instead of explaining why it is that way.

prompt: Write `readme_missing(text, required)` where `text` is the contents of a README and `required` is a list of section names. A section is present if some line of `text` consists of one or more `#` characters followed by exactly that name, ignoring case and surrounding spaces (`## Quick Start` satisfies `"quick start"`, but `## Quick start guide` does not). Return the list of missing section names, in the order given in `required`.
starter:
```python
def readme_missing(text, required):
    pass
```
tests:
```python
readme = "# Toolshare\n\nIntro\n\n## Quick start\n...\n### Tests\n"
assert readme_missing(readme, ["quick start", "tests", "deployment"]) == ["deployment"]
assert readme_missing(readme, ["Quick Start"]) == []
assert readme_missing("", ["tests", "license"]) == ["tests", "license"]
assert readme_missing("not a heading: tests", ["tests"]) == ["tests"]
assert readme_missing(readme, []) == []
assert readme_missing("## Quick start guide\n", ["quick start"]) == ["quick start"]
assert readme_missing("##   LICENSE  \n", ["license"]) == []
```
model:
```python
def readme_missing(text, required):
    headings = set()
    for line in text.splitlines():
        stripped = line.strip()
        if stripped.startswith("#"):
            headings.add(stripped.lstrip("#").strip().lower())
    return [name for name in required if name.strip().lower() not in headings]
```
hint: Collect the cleaned heading texts into a set first.
hint: `line.lstrip("#")` removes the leading hash characters; then strip spaces and lowercase.
solution: Gather every line that starts with `#`, remove the hashes and spaces, lowercase it and store it in a set. Return the required names, lowercased and stripped, that are not in the set, preserving the given order.

```python
import re


def adr_filename(number, title):
    slug = re.sub(r"[^a-z0-9]+", "-", title.lower()).strip("-")
    return f"{number:04d}-{slug}.md"
```

hint: `str.strip("-")` removes hyphens from both ends, and `f"{number:04d}"` pads with zeros.
solution: Lowercase the title, use `re.sub(r"[^a-z0-9]+", "-", ...)` so each run of other characters becomes one hyphen, strip hyphens from the ends, and format the number with `04d`.

@quiz code
prompt: Write `changelog_entries(messages)` for a list of Conventional Commit first lines such as `feat(api): add search` or `fix: handle empty list`. Return a dict with exactly the keys `"Added"` and `"Fixed"`: each is the list of descriptions (the text after `: `) of the `feat` commits and the `fix` commits respectively, in the original order. Ignore all other types.
starter:
```python
def changelog_entries(messages):
    pass
```
tests:
```python
msgs = [
    "feat(api): add search",
    "fix: handle empty list",
    "docs: update readme",
    "feat: export csv",
    "fix(db)!: correct index",
    "chore: bump deps",
]
assert changelog_entries(msgs) == {
    "Added": ["add search", "export csv"],
    "Fixed": ["handle empty list", "correct index"],
}
assert changelog_entries([]) == {"Added": [], "Fixed": []}
assert changelog_entries(["docs: x"]) == {"Added": [], "Fixed": []}
assert changelog_entries(["feature: not a type"]) == {"Added": [], "Fixed": []}
```
model:
```python
def changelog_entries(messages):
    result = {"Added": [], "Fixed": []}
    for message in messages:
        head, sep, description = message.partition(": ")
        if not sep:
            continue
        kind = head.rstrip("!").split("(")[0]
        if kind == "feat":
            result["Added"].append(description)
        elif kind == "fix":
            result["Fixed"].append(description)
    return result
```
hint: Split at the first `: `; the left part holds the type, optional scope and optional `!`.
hint: Remove a trailing `!`, then cut off anything from the opening parenthesis.
solution: Partition each message at `: `, reduce the left part to the bare type by dropping a trailing `!` and any `(scope)`, and append the description to `Added` for `feat` or `Fixed` for `fix`. The word `feature` is not the type `feat`, so it is ignored.
