@article
Shipping is not the finish line. Two things remain: showing the work, so other people can see what you built, and learning from it, so the next project is better. Senior engineers do both routinely: they demo at the end of each iteration and hold a retrospective after each project or incident.

### The demo

A demo is a story with a live product in the middle. For five minutes:

1. **The problem (30 seconds):** who has it, and what it costs them. Use the real user from your proposal.
2. **The product (2 minutes):** walk the one path that matters. Use realistic but obviously fictional data, never real people's details. Do not click around; follow a script.
3. **The engineering (1.5 minutes):** one architecture picture, the pipeline (a pull request turning green and a deploy), monitoring (a dashboard or an alert), and one decision you made and why.
4. **Lessons and next steps (1 minute):** what you would do differently and what is next.

Rehearse it with a timer, twice. Prepare for failure: **record a backup video** of the full run and keep a few screenshots, because networks, free-tier apps that sleep, and conference Wi-Fi all fail at the worst time. Start the app a few minutes early so it is warm. Say what you built *and* what does not work yet; honesty about limits earns trust. Expect questions such as "How would it scale?", "How do you handle failures?" and "What would you change?", and prepare short answers using your own numbers from the load, monitoring and security reviews.

### The retrospective

A **retrospective** is a structured look back to improve how you work, not to assign blame. Hold it soon after shipping, while the details are fresh. Common formats are *Start, Stop, Continue* or *Went well, Didn't go well, Ideas*. A **blameless** approach assumes people made reasonable decisions with the information they had, and asks what in the *process* allowed the problem. "I forgot to run the migration" becomes "the deploy did not run the migration automatically."

Use evidence, not feelings: compare the estimate to the actual time (from your backlog), the number of issues finished, incidents and rollbacks, and review findings. Then the most important step: choose **two or three actions**, each **specific, owned and dated** ("add a migration step to the release workflow by Friday"), not wishes ("be more careful"). An action without an owner or a date rarely happens. Review the previous retrospective's actions at the start of the next.

### Writing the retrospective

A useful written version has: a short summary of the outcome versus the plan; what went well (keep doing); what was hard and why, with the underlying cause; the main lesson of each phase (scoping, CI, deployment, monitoring); numbers; and the actions.

### The portfolio

Your project is evidence of what you can do, so make it easy to check:

- A **clear README** with a one-line description, a screenshot or short video, the live link, and the architecture.
- A **clean repository**: meaningful commit history, pull requests with reviews, CI badge, issues and milestones visible.
- A short **write-up** (a page or a blog post): the problem, the key decisions and trade-offs, what went wrong and what you learned.
- A **resume bullet** with an action and a result: "Built and deployed a reservation service (Python, PostgreSQL, Docker) with CI/CD and monitoring; cut double bookings to zero for 40 members" is better than "worked on a web app". Only claim numbers that are true, and be ready to explain every line in an interview.
- Make sure no secrets or private data remain in the history, and use a license.

**Keep it alive or end it cleanly.** Free tiers and trials change, and a dead demo link looks bad. Either keep the app running at no cost, or replace the live link with a recorded demo and delete the cloud resources (app, database, registry images, domain records) so you are never billed unexpectedly. Check your provider's current billing page when you tear it down.

### Talking about it in interviews

Interviewers ask about projects to learn how you think. Prepare a **two-minute story**: situation, your role, what you decided, a problem you hit and how you solved it, and the result. Be ready for "what would you do differently?" with a concrete answer from your retrospective, for example "I would have added monitoring before the first deploy rather than after." Choose a real trade-off: why this host, this database, this test strategy.

@example
title: Timing a demo
problem: Your demo plan is: problem 1 minute, live walkthrough 3 minutes, architecture 2 minutes, pipeline 2 minutes, lessons 1 minute. The slot is five minutes. What do you do?
step: Add up the plan: 1 + 3 + 2 + 2 + 1 = 9 minutes, four minutes over the five-minute slot.
step: Protect the live product, the part that matters most, and cut the rest: shrink the problem to 30 seconds and the walkthrough to 2 minutes.
step: Combine architecture and pipeline into one 1.5-minute segment with a single diagram and a 10-second look at a green pipeline, and keep lessons at 1 minute: 0.5 + 2 + 1.5 + 1 = 5.
step: Rehearse with a timer, and record a backup video of the whole run.
answer: Cut to 30 s problem, 2 min product, 1.5 min engineering, 1 min lessons, and rehearse with a backup recording.

@example
title: Turning a complaint into an action
problem: In the retrospective someone writes "deployments were stressful and we forgot steps". Turn this into something useful.
step: Ask why: steps were remembered from memory and done by hand, so any distraction caused a missed step.
step: Name the root cause as a process gap, not a person: no checklist and no automation for the migration and smoke test.
step: Write specific actions: "Add the migration and smoke-test steps to the release workflow", owner: you, due: Friday; "Add a deployment checklist to the runbook", owner: you, due: Wednesday.
step: Plan how to check: the next release must run with no manual steps; review this at the next retrospective.
answer: Two owned, dated actions that automate and document the steps, with a way to verify them.

@mistakes
- Demoing live without a rehearsal, a backup recording or warmed-up services, then losing the story to a technical failure.
- A retrospective that assigns blame or ends with vague wishes instead of specific, owned, dated actions.
- Resume bullets that list technologies but no impact, or claim numbers you cannot defend.
- Leaving cloud resources running after the course (or a dead link in the portfolio), which can cost money and looks careless.

def agenda_overrun(segments, limit):

@practice code
prompt: Cards from a retrospective are tuples `(category, text, votes)`. Write `retro_summary(cards)` that returns a dict mapping each category to the `text` of its card with the most votes. If two cards in a category have the same top number of votes, the one that appears first wins. A category with no cards does not appear.
starter:
```python
def retro_summary(cards):
    pass
```
tests:
```python
cards = [
    ("went well", "CI caught a bug", 4),
    ("went well", "Deploy was boring", 6),
    ("went wrong", "Forgot migration", 5),
    ("went wrong", "Late security review", 5),
    ("ideas", "Add smoke test", 2),
]
assert retro_summary(cards) == {
    "went well": "Deploy was boring",
    "went wrong": "Forgot migration",
    "ideas": "Add smoke test",
}
assert retro_summary([]) == {}
assert retro_summary([("ideas", "a", 0)]) == {"ideas": "a"}
```
model:
```python
def retro_summary(cards):
    best = {}
    for category, text, votes in cards:
        if category not in best or votes > best[category][1]:
            best[category] = (text, votes)
    return {category: text for category, (text, votes) in best.items()}
```
hint: Remember the best card so far for each category in a dict.
hint: Replace the stored card only when the new one has strictly more votes, so ties keep the first.
solution: Keep a dict from category to `(text, votes)`, replacing an entry only when a card has strictly more votes than the stored one, which makes the first of tied cards win. Finally keep only the texts.

@quiz code
prompt: Action items are dicts with the keys `"action"`, `"owner"` and `"due"`. Write `incomplete_actions(items)` that returns the list of `"action"` texts, in the original order, of the items where the owner or the due date is missing or empty (an empty string or `None`, or the key is absent).
starter:
```python
def incomplete_actions(items):
    pass
```
tests:
```python
items = [
    {"action": "Automate migration", "owner": "Sam", "due": "Fri"},
    {"action": "Be more careful", "owner": "", "due": "Fri"},
    {"action": "Add checklist", "owner": "Sam", "due": None},
    {"action": "Delete resources", "owner": "Sam"},
]
assert incomplete_actions(items) == ["Be more careful", "Add checklist", "Delete resources"]
assert incomplete_actions([]) == []
assert incomplete_actions(items[:1]) == []
```
model:
```python
def incomplete_actions(items):
    return [
        item["action"]
        for item in items
        if not item.get("owner") or not item.get("due")
    ]
```
hint: `item.get("owner")` returns `None` when the key is missing.
hint: An empty string and `None` are both falsy, so `not value` covers both.
solution: Use `dict.get` so missing keys give `None`, and keep an item when either the owner or the due date is falsy; the comprehension preserves the original order.
