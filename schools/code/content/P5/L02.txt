@article
A proposal says *what* and *why*. A plan says *in what order* and *by when*. Without one, you work on whatever feels interesting, discover in week nine that the deployment is unstarted, and arrive at the demo with half a product. A lightweight plan costs an hour and pays back every week.

### Milestones

A **milestone** is a dated, demonstrable state of the product, not a pile of tasks. Good milestones for this course look like this:

| Milestone | Demonstrable outcome |
|---|---|
| M1 Walking skeleton | "Hello" page deployed, CI green |
| M2 First vertical slice | A user can create and list one kind of record |
| M3 MVP feature complete | All MVP features work locally with tests |
| M4 Production ready | Container, monitoring, security and accessibility review done |
| M5 Ship | Demo, documentation, retrospective |

Notice that M1 contains no features at all. Putting the boring path to production first is the single best risk reduction in this course.

### Writing a good issue

An **issue** is a unit of work that one person can finish, ideally in a day or less. If an issue takes more than about two days, split it. Use a template:

```text
Title: Reserve a tool for a date range

Why: Librarians double-book tools in the spreadsheet.

Acceptance criteria:
- [ ] POST /reservations with tool_id, start and end creates a reservation
- [ ] Overlapping reservations for the same tool return 409
- [ ] End before start returns 422
- [ ] Unit tests cover overlap, adjacent ranges and invalid input

Out of scope: email notifications
```

**Acceptance criteria** are testable statements: someone else could read them and say yes or no. "Works well" is not testable; "returns 409 on overlap" is. The **definition of done** is a team-wide checklist applied to every issue: code reviewed and merged, tests pass in CI, documentation updated if behavior changed, deployed to staging.

### The backlog

The **backlog** is the ordered list of everything not yet done. Order it by priority first (what the user needs soonest), then by size (smaller first, because small items finish and give feedback), and keep the top ten items sharp and detailed while the rest stay rough. Re-order weekly. Items that nobody will ever build should be closed, not hoarded.

Use labels sparingly: a type (`feature`, `bug`, `chore`), a priority and a milestone are enough. A board with columns **To do, In progress, In review, Done** is plenty. Limit work in progress: one or two items at a time. Starting five things and finishing none is the classic solo-developer trap.

### Forecasting

Size issues roughly with points (1, 2, 3, 5) or t-shirt sizes. Each week, record how many points you finished: your **velocity** (or throughput). A simple forecast divides the remaining points by your recent average velocity and rounds up:

```python
import math

velocities = [6, 8, 7]
remaining = 40
weeks = math.ceil(remaining / (sum(velocities) / len(velocities)))
print(weeks)   # 6
```

The forecast is a range, not a promise, so report it as "about six weeks, assuming the same pace," and re-forecast every week. If the forecast lands after your deadline, you have a scope conversation, not a pep talk.

### Plan for the invisible work

Add issues for CI, deployment, documentation, the security review and the demo. These are never "just a few minutes", and they are exactly what hiring managers look for in a finished project.

@example
title: Splitting an oversized issue
problem: The backlog contains "Build the reservation system" estimated at three weeks. Make it plannable.
step: Ask what a user can see after each step. The first thing is storing a reservation, then preventing overlaps, then cancelling, then listing.
step: Write one issue each: "Create a reservation", "Reject overlapping reservations", "Cancel a reservation", "List reservations for a tool".
step: Give each acceptance criteria. For overlaps: overlapping returns 409; adjacent ranges (one ends the day another starts) are allowed; tests cover both.
step: Estimate each in points: 3, 3, 2, 2. A three-week blob has become four items of one to two days, each finishable and reviewable.
answer: Four issues of one to two days each with testable acceptance criteria.

@example
title: Forecasting the finish
problem: You have 34 points left. Your last four weeks of velocity were 5, 7, 6 and 6. How many weeks remain, and what do you do if the deadline is five weeks away?
step: The average velocity is (5 + 7 + 6 + 6) / 4 = 6 points per week.
step: Divide: 34 / 6 = 5.67, which rounds up to 6 weeks.
step: The deadline is five weeks away, so you are about one week late at the current pace.
step: Do not simply promise to go faster. Move one or two low-priority issues (about 6 points) out of the MVP and re-forecast: 28 / 6 rounds up to 5 weeks.
answer: Six weeks; cut about 6 points of scope to finish in five.

@mistakes
- Writing issues as vague wishes ("improve the UI") with no acceptance criteria, so nobody can tell when they are done.
- Putting deployment, documentation and review at the end of the plan instead of in the first milestone.
- Letting the backlog grow into hundreds of rough items, which hides what to do next.
- Treating a forecast as a promise instead of re-forecasting with the actual velocity every week.

```python
text = "Intro\n- [x] write model\n- [ ] add tests\n  - [X] docs\n\nnotes"
assert checklist_progress(text) == (2, 3)
assert checklist_progress("") == (0, 0)
assert checklist_progress("- [ ] a\n- [ ] b") == (0, 2)

```
model:
```python
def checklist_progress(text):
    done = 0
    total = 0
    for line in text.splitlines():
        line = line.strip()
        if line.startswith("- [ ]"):
            total += 1
        elif line.startswith(("- [x]", "- [X]")):
            total += 1
            done += 1
    return (done, total)
```
hint: Loop over `text.splitlines()` and strip each line before testing it.
hint: `str.startswith` accepts a tuple of prefixes.
solution: Strip each line, add 1 to `total` for any of the three checkbox prefixes, and also add 1 to `done` for the two checked forms. Indented lines work because of `strip()`.

@practice code
prompt: Write `weeks_remaining(points_left, velocities)` that returns how many whole weeks are needed: the points left divided by the average of the `velocities` list, rounded up. If `points_left` is 0 return 0. If `velocities` is empty, or its average is 0, raise `ValueError`.
starter:
```python
def weeks_remaining(points_left, velocities):
    pass
```
tests:
```python
assert weeks_remaining(34, [5, 7, 6, 6]) == 6
assert weeks_remaining(12, [6]) == 2
assert weeks_remaining(0, [4, 4]) == 0
assert weeks_remaining(1, [10, 10]) == 1
assert raises(ValueError, weeks_remaining, 10, [])
assert raises(ValueError, weeks_remaining, 10, [0, 0])
```
model:
```python
import math


def weeks_remaining(points_left, velocities):
    if not velocities:
        raise ValueError("no velocity data")
    average = sum(velocities) / len(velocities)
    if average == 0:
        raise ValueError("velocity is zero")
    if points_left == 0:
        return 0
    return math.ceil(points_left / average)
```
hint: Validate the velocities before dividing.
hint: Use `math.ceil(points_left / average)` for the rounding up.
solution: Reject empty or zero-average velocity data first, return 0 for no remaining work, and otherwise round the quotient up with `math.ceil`: 34 points at an average of 6 gives 5.67, which is 6 weeks.

@quiz code
prompt: Each issue is a dict with `"id"`, `"priority"` (1 is the most urgent) and `"points"`. Write `order_backlog(issues)` that returns the list of ids ordered by priority (lowest number first), then by points (smaller first), then by id (alphabetical).
starter:
```python
def order_backlog(issues):
    pass
```
tests:
```python
items = [
    {"id": "C", "priority": 2, "points": 1},
    {"id": "A", "priority": 1, "points": 5},
    {"id": "B", "priority": 1, "points": 2},
    {"id": "D", "priority": 2, "points": 1},
]
assert order_backlog(items) == ["B", "A", "C", "D"]
assert order_backlog([]) == []
assert order_backlog([{"id": "X", "priority": 3, "points": 8}]) == ["X"]
assert order_backlog(items[::-1]) == ["B", "A", "C", "D"]
```
model:
```python
def order_backlog(issues):
    ranked = sorted(
        issues, key=lambda i: (i["priority"], i["points"], i["id"])
    )
    return [i["id"] for i in ranked]
```
hint: Tuples compare element by element, so a tuple key sorts by several fields.
hint: Use the key `(priority, points, id)`.
solution: Sort with the key `(priority, points, id)`, which orders by urgency first, then smaller work first, then the id for a stable, predictable result; return only the ids.
