@article
Until your application runs somewhere other than your laptop, it is not a product; it is a demo. The first deployment is also the moment you learn the most, so do it early and do it with something trivial. In this lesson we stay **vendor-neutral**: hosting companies change their consoles, names and prices constantly, so you need the concepts that carry across all of them.

### The main options

| Option | What you manage | Typical fit |
|---|---|---|
| **Platform as a service (PaaS)** | Your code or image and its settings; the platform runs servers, TLS and restarts | Small web apps; fastest path to a URL |
| **Managed container host** | An image, its size, scaling rules and networking | Apps already in containers; moderate control |
| **Virtual machine** you administer | The operating system, updates, a reverse proxy, process supervision | Learning how everything works; full control, most work |
| **Serverless functions or static hosting** | Functions or files only | Static front ends, small event-driven pieces |

For a capstone, a PaaS or a managed container host is usually best, because the time you save goes into the engineering you want to show. **Prices and free tiers change, and some free tiers sleep idle apps or limit hours.** Check the current pricing page and any usage limits yourself, set a spending alert if the provider offers one, and choose an option that costs nothing for your project. You should never need to pay to finish this course; if a provider asks for a card you do not want to give, pick another, or deploy to a local virtual machine or your own computer and document it.

### The deployment steps, in any platform

1. **Build an artifact.** For you, this is the container image from last week, tagged with a version or commit hash. Build it in CI, not on your laptop.
2. **Provide infrastructure.** Create the app service and a **backing service**: a managed database is better than running one yourself, and it is attached by configuration (`DATABASE_URL`).
3. **Set configuration and secrets** in the platform's environment settings or secrets store. Never bake them into the image.
4. **Run database migrations** (schema changes) as a separate, explicit step before or as the new version starts, not by hand on a laptop.
5. **Start the app** and give the platform a **health check**: a URL it calls to decide whether to send traffic and when to restart.
6. **Add a domain name and HTTPS.** Most platforms issue and renew certificates for you. Use TLS everywhere; TLS 1.3 is the current version, and a current platform negotiates it automatically (TLS 1.2 is still widely accepted).
7. **Verify** with a smoke test (below), then write down the steps in the README so anyone can repeat them.

### The health endpoint

A health endpoint answers: "can this instance do its job right now?" Keep it cheap and honest:

```python
from flask import Flask, jsonify

app = Flask(__name__)


@app.get("/health")
def health():
    db_ok = check_database()          # a quick `SELECT 1`
    status = "ok" if db_ok else "degraded"
    code = 200 if db_ok else 503
    return jsonify(status=status, db="ok" if db_ok else "down"), code
```

Return 200 only when the instance can actually serve; a `503` tells the platform to stop sending traffic. Do not expose secrets or version details you would not want public.

### Retries and exponential backoff

After a deploy, things take time: the database accepts connections, the app finishes starting. A client or a deploy script should **retry** instead of giving up at once, but retrying in a tight loop hammers a service that is already struggling. **Exponential backoff** doubles the wait between attempts (1 s, 2 s, 4 s, 8 s) up to a cap, and often adds random **jitter** so many clients do not retry in lockstep. Retry only operations that are safe to repeat, and always give up after a limit.

```python
def backoff_delays(retries, base=1, cap=30):
    return [min(cap, base * 2 ** i) for i in range(retries)]

print(backoff_delays(5))   # [1, 2, 4, 8, 16]
```

### Smoke test

A **smoke test** is the smallest check that the deployed system lives: request the home page and the health URL over HTTPS, create one record and read it back. Run it automatically after every deploy (next week). If it fails, roll back.

title: Waiting for a service to become healthy
problem: After deployment, the health URL returns 503 for about ten seconds while the database warms up. Design a deploy-script wait that is polite and bounded.
step: Poll the health endpoint instead of sleeping a fixed time: succeed as soon as it returns 200.
step: Wait between attempts with exponential backoff: 1, 2, 4, 8 seconds, capped at 10.

@mistakes
- Choosing a hosting option by its marketing instead of reading the current free-tier limits, then discovering the app sleeps or the database expires.
- Setting environment variables by hand in a console and never writing them down, so the next deploy cannot be reproduced.
- Health checks that always return 200, so the platform keeps sending traffic to a broken instance.
- Retrying forever or in a tight loop instead of using a capped backoff with a retry limit.

tests:
```python
results = iter([False, False, True])
slept = []
assert wait_until_healthy(lambda: next(results), 5, slept.append) is True
assert slept == [1, 2]

slept = []
assert wait_until_healthy(lambda: False, 4, slept.append) is False
assert slept == [1, 2, 4]

slept = []
assert wait_until_healthy(lambda: False, 7, slept.append) is False
assert slept == [1, 2, 4, 8, 8, 8]

```
model:
```python
def wait_until_healthy(probe, max_attempts, sleep):
    delay = 1
    for attempt in range(max_attempts):
        if probe():
            return True
        if attempt < max_attempts - 1:
            sleep(delay)
            delay = min(8, delay * 2)
    return False
```
hint: Loop `max_attempts` times; keep a `delay` variable that doubles up to 8.
hint: Only sleep when another attempt will follow, that is when `attempt < max_attempts - 1`.
solution: Try the probe in a loop of `max_attempts` iterations, returning `True` at the first success. After a failure that is not the last attempt, call the injected `sleep(delay)` and double the delay with a cap of 8. With zero attempts the loop never runs and the function returns `False`.

@quiz code
prompt: Write `is_healthy(body)` for the text body of a health endpoint. It returns `True` only if `body` is valid JSON for an object whose `"status"` is the string `"ok"` and every other value in the object is also the string `"ok"`. Return `False` for invalid JSON, for JSON that is not an object, and when `"status"` is missing.
starter:
```python
def is_healthy(body):
    pass
```
tests:
```python
assert is_healthy('{"status": "ok"}') is True
assert is_healthy('{"status": "ok", "db": "ok", "cache": "ok"}') is True
assert is_healthy('{"status": "ok", "db": "down"}') is False
assert is_healthy('{"status": "degraded"}') is False
assert is_healthy('{"db": "ok"}') is False
assert is_healthy('not json') is False
assert is_healthy('["ok"]') is False
assert is_healthy('') is False
```
model:
```python
import json


def is_healthy(body):
    try:
        data = json.loads(body)
    except Exception:
        return False
    if not isinstance(data, dict) or data.get("status") != "ok":
        return False
    return all(value == "ok" for value in data.values())
```
hint: `json.loads` raises an exception for bad input, so wrap it in `try`.
hint: After parsing, check the type, then `status`, then all values.
solution: Parse with `json.loads` inside `try`, return `False` if it raises, require a dict whose `status` is `"ok"`, and finally require that `all` values equal `"ok"`.
