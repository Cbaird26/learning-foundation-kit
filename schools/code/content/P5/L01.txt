@article
Your first week on a new team usually starts with the same question from your lead: "What exactly are we building, for whom, and what are we *not* building?" This course makes you answer it for a project of your own, and then carry that project all the way to production. The most common way capstones fail is not bad code. It is a project that was too big, too vague, or had no real user.

### What makes a good capstone

A good project has five properties:

1. **A real user and a real problem.** Even if the user is you, a friend, or a club. "A habit tracker" is a category; "a tracker my running club uses to log weekly mileage" is a project.
2. **Finishable in your budget.** Count your honest hours per week and multiply by the weeks left. Then plan for roughly 60 percent of that: illness, debugging and surprises always arrive.
3. **Engineering range.** It should need persistence (a database), an HTTP interface, input validation, tests, and at least one decision worth explaining. It does not need machine learning, microservices or a mobile app.
4. **Deployable.** It must run somewhere other than your laptop, on a free or very cheap tier. Check prices and free tiers yourself, because they change; you should never need to pay to finish this course.
5. **Demoable in five minutes.** If you cannot show its value in a short walkthrough, it is too diffuse.

Avoid ideas that need regulated data (health or payment details), real user accounts you cannot protect, scraping sites that forbid it, or anything whose success depends on other people showing up.

### Scoping: problem, users, MVP, non-goals

A **minimum viable product (MVP)** is the smallest version that solves the core problem for one user. Write the proposal on one page:

- **Problem and user:** two sentences.
- **Success criteria:** how you will know it works ("a member can log a run in under 20 seconds").
- **MVP features:** three to six, each phrased as something a user can do.
- **Non-goals:** things you are deliberately leaving out (social features, mobile app, admin dashboard). This list prevents scope creep, because "not now" is easier to say when it is written down.
- **Architecture sketch:** one paragraph or a box-and-arrow diagram in words: browser, web service, database.
- **Risks:** the two or three things most likely to hurt you (an unfamiliar library, a third-party API, deployment).
- **Milestones:** rough dates, which you will refine next week.

### Slice vertically

Build **vertical slices**: one feature through every layer (page, handler, database, test) rather than all the database tables first. A thin slice that works end to end, even ugly, teaches you the deployment path early, which is where the surprises hide.

### Prioritizing and estimating

When features compete for hours, compare **value per hour**: give each feature a value from 1 to 10 for how much the user cares, estimate hours, and rank by value divided by hours. It is crude but beats gut feeling. Estimates are always optimistic, so add a buffer by risk: roughly 25 percent for work you have done before, 50 percent for work that is somewhat new and 100 percent for work in an unfamiliar area.

```python
def padded(hours, multiplier):
    return hours * multiplier

print(padded(8, 1.5))   # 12.0
```

A senior engineer's habit: when someone asks "can you also add...?", the answer is never a flat yes or no. It is "yes, and here is what moves out of the MVP to make room."

@example
title: Cutting an idea down to an MVP
problem: You want to build "a complete running club app" with accounts, a calendar, chat, mileage logs, leaderboards, photo sharing and a mobile app. You have about 60 usable hours. Scope it.
step: Name the core problem in one sentence: members cannot easily see who ran how far this week. Everything else is secondary.
step: Keep only what answers that: add a run (member, date, kilometres), list this week's runs, show the weekly totals per member. Three features.
step: Move the rest to non-goals: chat, photo sharing, calendar, mobile app, accounts with passwords. A single shared club code is enough for the MVP.
step: Check the budget. Rough estimates: add a run 8 h, list runs 6 h, totals 5 h, deployment and CI 12 h, tests and documentation 10 h. That is 41 hours; with a 1.5 buffer it is about 62 hours, right at the limit, so the cut was correct.
answer: Three user-facing features plus delivery work, with chat, photos, calendar, mobile and passwords written as non-goals.

@example
title: Ranking features by value per hour
problem: Features: search (value 6, 12 hours), export to CSV (value 3, 2 hours), tags (value 8, 8 hours). Which order do you build them in?
step: Compute value per hour for each: search 6/12 = 0.5, export 3/2 = 1.5, tags 8/8 = 1.0.
step: Sort from highest to lowest: export (1.5), tags (1.0), search (0.5).
step: Sanity check: export is cheap and useful, so it goes first. Search is expensive for its value, so it falls to the end and is a candidate for the non-goals if hours run out.
answer: Export, then tags, then search.

@mistakes
- Choosing a project because it sounds impressive (a social network, a chat platform) instead of because it has a real user and fits the hours you have.
- Writing features as technologies ("use GraphQL and Redis") instead of as things a user can do.
- Leaving out the non-goals, so every good idea becomes a commitment.
- Estimating with no buffer, then discovering that setup, deployment and debugging took half the time.

tests:
```python
data = [
    {"name": "login", "value": 5, "hours": 10},
    {"name": "list", "value": 8, "hours": 4},
    {"name": "export", "value": 2, "hours": 1},
]
assert rank_features(data) == ["export", "list", "login"]

```
model:
```python
def rank_features(features):
    ranked = sorted(
        features, key=lambda f: (-f["value"] / f["hours"], f["name"])
    )
    return [f["name"] for f in ranked]
```
hint: `sorted` accepts a `key` function that can return a tuple.
hint: Use `(-ratio, name)` so that a larger ratio sorts first and ties fall back to the name.
solution: Sort with the key `(-value / hours, name)`: negating the ratio puts the largest first, and the name breaks ties alphabetically. Then return only the names.

prompt: Write `plan_mvp(features, budget_hours)`. Features are dicts with `"name"`, `"value"` and `"hours"` as before. Consider the features in order of value per hour (highest first, ties alphabetical by name). Take a feature if its hours fit in the budget that remains, otherwise skip it and keep looking at the later ones. Return the chosen names in the order they were taken.
starter:
```python
def plan_mvp(features, budget_hours):
    pass
```
tests:
```python
data = [
    {"name": "a", "value": 12, "hours": 6},
    {"name": "b", "value": 3, "hours": 3},
    {"name": "c", "value": 1, "hours": 2},
]
assert plan_mvp(data, 5) == ["b", "c"]
assert plan_mvp(data, 11) == ["a", "b", "c"]
assert plan_mvp(data, 0) == []
assert plan_mvp([], 10) == []
assert plan_mvp(data, 6) == ["a"]
```
model:
```python
def plan_mvp(features, budget_hours):
    ranked = sorted(
        features, key=lambda f: (-f["value"] / f["hours"], f["name"])
    )
    chosen = []
    remaining = budget_hours
    for feature in ranked:
        if feature["hours"] <= remaining:
            chosen.append(feature["name"])
            remaining -= feature["hours"]
    return chosen
```
hint: Rank first, then walk down the ranking keeping a `remaining` budget.
hint: A feature that does not fit is skipped with no `break`: a cheaper one further down may still fit.
solution: Rank by value per hour, then loop once: if the feature's hours are at most `remaining`, take it and subtract. With a budget of 5, `a` (6 hours) is skipped but `b` and `c` still fit.

@quiz code
prompt: Write `padded_estimate(hours, risk)` that returns the estimate with a buffer, rounded up to a whole number of hours. The risk is `"low"` (multiply by 1.25), `"medium"` (1.5) or `"high"` (2.0). Any other risk value raises `ValueError`.
starter:
```python
def padded_estimate(hours, risk):
    pass
```
tests:
```python
assert padded_estimate(8, "medium") == 12
assert padded_estimate(10, "low") == 13
assert padded_estimate(7, "high") == 14
assert padded_estimate(5, "low") == 7
assert raises(ValueError, padded_estimate, 4, "extreme")
```
model:
```python
import math


def padded_estimate(hours, risk):
    multipliers = {"low": 1.25, "medium": 1.5, "high": 2.0}
    if risk not in multipliers:
        raise ValueError(f"unknown risk: {risk}")
    return math.ceil(hours * multipliers[risk])
```
hint: Keep the multipliers in a dictionary and check the key before using it.
hint: `math.ceil` rounds up; 10 * 1.25 is 12.5, which must become 13.
solution: Look up the multiplier (raising `ValueError` for an unknown risk), multiply, and round up with `math.ceil`, so 12.5 hours becomes 13 and 6.25 becomes 7.
