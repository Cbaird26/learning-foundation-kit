@article
A **process** is a running program: it has its own address space (code, globals, heap, stack), a process ID (**PID**), and a table of open **file descriptors**. A file descriptor is a small non-negative integer naming an open file, pipe or terminal; by convention 0 is standard input, 1 is standard output and 2 is standard error. The `FILE *` streams of week 10 are buffered wrappers around descriptors.

### System calls

A **system call** is a request from your program to the operating system kernel: `open`, `read`, `write`, `close`, `fork`, `execve`, `waitpid`, `pipe`, `dup2`, `_exit`. Library functions such as `printf`, `fopen` and `exit` are built on them (`printf` buffers and eventually calls `write`; `exit` flushes the stdio buffers and then calls `_exit`). The POSIX calls are declared in `<unistd.h>`, `<fcntl.h>` and `<sys/wait.h>`. They report failure by returning `-1` and setting `errno`; check every result and use `perror` to print the reason. They are POSIX, not ISO C, and are not available on every platform.

### fork, exec and wait

- `pid_t fork(void)` creates a new process that is a copy of the caller. It is called once and **returns twice**: `0` in the child, the child's PID in the parent, and `-1` in the parent if it failed. Both processes continue after the call with separate copies of the memory (copy-on-write in practice) and shared open files.
- `int execvp(const char *file, char *const argv[])` **replaces** the current program with a new one, searching `PATH`. `argv[0]` is the program name and the array must end with `NULL`. On success it never returns; it returns `-1` only on failure (command not found), so the next line should report an error and `_exit`.
- `pid_t waitpid(pid_t pid, int *status, int options)` waits for a child to finish and stores its **status**. The macros `WIFEXITED(status)` and `WEXITSTATUS(status)` tell whether it exited normally and with which code (0 to 255); `WIFSIGNALED(status)` and `WTERMSIG(status)` tell whether a signal killed it. A child that has finished but has not been waited for is a **zombie**: it holds a process-table entry until the parent collects its status. A parent that exits first leaves **orphans**, which the system adopts.

```c
pid_t pid = fork();
if (pid < 0) {
    perror("fork");
    return 1;
}
if (pid == 0) {                       /* child */
    char *argv[] = {"ls", "-l", NULL};
    execvp(argv[0], argv);
    perror("execvp");                 /* reached only if exec failed */
    _exit(127);
}
int status;
if (waitpid(pid, &status, 0) < 0) {   /* parent */
    perror("waitpid");
}
else if (WIFEXITED(status)) {
    printf("exit code %d\n", WEXITSTATUS(status));
}
```

`exit` flushes stdio buffers and runs cleanup; `_exit` ends the process immediately. In a child after a failed `exec`, use `_exit` so buffered data that was copied from the parent is not flushed twice. For the same reason, call `fflush(stdout)` before `fork`.

### Redirection and pipes

Descriptors survive `exec`, which is how a shell implements `cmd > out.txt`: in the child, `open` the file (getting, say, descriptor 3), call `dup2(3, 1)` to make descriptor 1 refer to the same file, `close(3)`, then `execvp`. The program writes to "standard output" without knowing it is a file. `pipe(int fds[2])` creates a pipe: bytes written to `fds[1]` can be read from `fds[0]`. For `a | b` the shell creates the pipe, forks twice, makes the first child's descriptor 1 the pipe's write end and the second child's descriptor 0 the read end with `dup2`, closes the unused ends in every process, and waits for both. If a write end stays open somewhere, the reader never sees end of file.

### Structure of a shell

A minimal shell loops: print a prompt, read a line with `fgets`, **tokenize** it into an `argv` array (splitting on whitespace, optionally honoring quotes), handle **built-in commands** itself, otherwise `fork`, `execvp` in the child and `waitpid` in the parent. Commands like `cd` and `exit` must be built in: `chdir` changes the working directory of the process that calls it, so running `cd` in a forked child would leave the shell's own directory unchanged. Free any memory you allocated for the tokens after each command. Real shells also handle signals (such as `Ctrl-C`, which sends `SIGINT` to the foreground processes), job control and environment variables.

@example
title: Counting processes
problem: How many processes exist (counting the original) after `for (int i = 0; i < 3; i++) { fork(); }` has run in every process?
step: Before the loop there is 1 process. Each `fork` doubles the number of processes that execute the rest of the code, because parent and child both continue.
step: After iteration 0 there are 2 processes; both run iteration 1, so after it there are 4; after iteration 2 there are 8.
step: The count is $2^3 = 8$ processes, including the original. (Each child inherits the loop variable's current value, so a child created in iteration 1 only runs iteration 2.)

@example
title: Why cd is a built-in
problem: A shell runs every command with `fork` and `execvp`. Explain why `cd /tmp` typed into it would not work as an external program.
step: `fork` creates a child with a copy of the shell's state, including its current directory.
step: A `cd` program would call `chdir("/tmp")` inside that child, changing only the child's directory.
step: The child then exits. The parent shell's directory is unchanged, so the next command still runs in the old directory.
step: Therefore the shell must call `chdir` itself, in its own process, when it sees `cd`.

@mistakes
- Forgetting that `fork` returns in both processes, so code after it runs twice unless the branches are separated by the return value.
- Not calling `waitpid`, which leaves zombie processes behind.
- Continuing after a failed `execvp` (the child then runs the parent's code); report the error and `_exit`.
- Not terminating the `argv` array with `NULL`.
- Leaving pipe ends open, so a reader waits forever for end of file.
- Printing before `fork` without flushing, so the buffered text appears twice.

model:
```python
def tokenize(line):
    tokens = []
    current = []
    in_quote = False
    started = False
    for ch in line:
        if ch == '"':
            in_quote = not in_quote
            started = True
        elif ch in " \t" and not in_quote:
            if started:
                tokens.append("".join(current))
                current = []
                started = False
        else:
            current.append(ch)
            started = True
    if started:
        tokens.append("".join(current))
    return tokens
```
hint: Scan one character at a time, keeping the current argument, a flag for being inside quotes, and a flag for whether an argument has started.
hint: A quote toggles the flag (and starts an argument even if it stays empty); a space or tab outside quotes ends the current argument if one has started; any other character is appended.
solution: This is the state machine a small shell uses: the `started` flag is what distinguishes the empty argument `""` from the gap between arguments, and it also stops runs of spaces from creating empty tokens. In C, the same loop would write into a buffer and record the start of each token in an `argv` array.

model:
```python
def split_pipeline(tokens):
    if not tokens:
        return []
    commands = [[]]
    for tok in tokens:
        if tok == "|":
            if not commands[-1]:
                raise ValueError("empty command")
            commands.append([])
        else:
            commands[-1].append(tok)
    if not commands[-1]:
        raise ValueError("empty command")
    return commands
```
hint: Start a new command list each time you see `"|"`.
hint: Before starting a new command, and at the end, check that the command you are leaving is not empty.
solution: Each pipe token closes the current command, which must contain at least one token, and opens the next. Checking the last command after the loop catches a trailing `|`. A real shell would then create `len(commands) - 1` pipes and fork one child per command.
