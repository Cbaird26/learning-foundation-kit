@article
Test-driven development (TDD) is a way of writing code in which the test comes first. It sounds backwards until you try it: you write down, as an executable example, what the code should do, watch it fail, and only then write the code. The result is code that is always covered by a test that you have seen fail for the right reason.

### The cycle: red, green, refactor

1. **Red.** Write one small test for behavior that does not exist yet. Run it and confirm it **fails**, and fails for the reason you expect (a missing function, or a wrong value), not because of a typo.
2. **Green.** Write the **simplest** code that makes the test pass. Not the best code, not the general code: the simplest. Run all tests; they are green.
3. **Refactor.** With a green suite as your safety net, clean up duplication and names in both the code and the tests. Behavior must not change, so the tests must stay green.

Then pick the next small behavior and repeat. A cycle takes minutes, not hours. If you are stuck in red for half an hour, the step was too big: delete the test and write a smaller one.

### Why watching the test fail matters

A test that has never failed has not proved it can. A forgotten assert, a test function the runner never collects, or an expectation that matches the wrong value all produce a green result that means nothing. Seeing red first proves the test is wired up and sensitive to the behavior you are about to add.

### Small steps and "fake it"

Early green steps can look silly. If the first test asks `shipping_cost(0)` to be `0`, the simplest passing code is `return 0`. That is intentional. The next test (`shipping_cost(1)` is `5`) forces the code to become conditional, and the third test forces a real rule. This is called **triangulation**: each new example forces the code to generalize only as far as the examples demand. When the right implementation is obvious, you may write it directly (an "obvious implementation"), but drop back to tiny steps the moment a test surprises you.

### Choosing the next test

Start with the simplest case (empty input, zero, one item), then add the next simplest behavior, then edge cases and errors. Keep a short to-do list beside you: when you think of a case you are not ready for, write it down instead of coding it. Each test should fail for exactly one reason, so one new test requires one small code change.

### What TDD gives you

It gives a **design pressure**: to test a function you must be able to call it with plain inputs, so your code tends toward small functions with explicit dependencies. It gives a **fast feedback loop** and a living specification. It also prevents the common failure of writing tests afterwards that only repeat what the code already does, including its bugs.

### Where TDD is weaker

TDD is not a religion. It works best for logic with clear inputs and outputs: business rules, parsers, algorithms, data transformations. It is awkward for exploratory work where you do not yet know what you are building (a "spike": write throwaway code to learn, then delete it and rebuild test-first), for pure user-interface layout, and for glue code whose only job is calling a library. For bugs, a close cousin applies: first write a failing test that reproduces the bug, then fix it. That single habit is worth adopting even if you never do full TDD.

### A note on tools

In a real project you run the suite with `pytest` after every small change, usually through a file watcher or your editor's test runner, so red-or-green feedback arrives within a second or two. Commit on green. A history of small green commits makes review easy and lets you revert one step without losing others.

@example
title: One feature in three cycles
problem: Build `ticket_price(age)`: children under 5 are free, ages 5 to 64 pay 10, and ages 65 and over pay 6. Show the red-green-refactor steps.
step: **Red 1.** The simplest test: `assert ticket_price(3) == 0`. It fails with `NameError` because the function does not exist, which is the expected reason.
step: **Green 1.** The simplest code that passes:

```python
def ticket_price(age):
    return 0
```
step: **Red 2.** `assert ticket_price(30) == 10` fails (`0 != 10`). **Green 2.** Now the code must branch:

```python
def ticket_price(age):
    if age < 5:
        return 0
    return 10
```
step: **Red 3.** `assert ticket_price(65) == 6` fails (`10 != 6`). **Green 3:** add `if age >= 65: return 6` before the final line. Add boundary tests for 4, 5 and 64 as well; they already pass, which is fine, because they document the boundaries.
step: **Refactor.** Name the numbers (`CHILD_LIMIT = 5`, `SENIOR_AGE = 65`) and run all tests again. They stay green, so behavior did not change.
answer: Three cycles, each forced by one failing test, followed by a refactor that keeps the suite green.

@example
title: Reproduce the bug first
problem: A user reports that `ticket_price(65)` returns `10`. What is the TDD-style response?
step: Write the failing test first: `def test_age_65_gets_senior_price(): assert ticket_price(65) == 6`.
step: Run it. It fails with `10 != 6`, which proves the test reproduces the report.
step: Fix the code (use `>=`, not `>`), run the whole suite, and see all tests pass.
step: Commit the test and the fix together. The bug can never silently return.
answer: Failing test first, then the smallest fix, then a green suite.

@mistakes
- Writing several tests (or all the code) before running anything, which defeats the fast feedback that makes TDD work.
- Never seeing the test fail, so a test that cannot fail goes unnoticed.
- Writing a clever, general implementation in the green step instead of the simplest code that passes.
- Skipping the refactor step, so the code and the tests slowly fill with duplication.

@practice code
prompt: Build `is_valid_username(name)` the TDD way. The rules, which your tests will check: 3 to 12 characters long, only ASCII letters, digits and underscores, and it must start with a letter. Return `True` or `False`.
starter:
```python
def is_valid_username(name):
    pass
```
tests:
```python
assert is_valid_username("abc") is True
assert is_valid_username("ab") is False
assert is_valid_username("a" * 12) is True
assert is_valid_username("a" * 13) is False
assert is_valid_username("1abc") is False
assert is_valid_username("ab_c1") is True
assert is_valid_username("ab-c") is False
assert is_valid_username("_abc") is False
assert is_valid_username("ab\u00e9") is False
assert is_valid_username("") is False
```
model:
```python
def is_valid_username(name):
    if not 3 <= len(name) <= 12:
        return False
    if not (name[0].isascii() and name[0].isalpha()):
        return False
    for ch in name:
        if not (ch.isascii() and (ch.isalnum() or ch == "_")):
            return False
    return True
```
hint: Add one rule at a time, the way a TDD session would: length, then first character, then allowed characters.
hint: Check the length first, so `name[0]` is never evaluated for an empty string. Use `isascii()` so letters such as accented ones are rejected.
solution: Test the length range first (which also protects `name[0]`), then require an ASCII letter at the start, then scan every character for letters, digits or underscore. Each rule matches one group of tests, which is how the rules would have arrived in red-green cycles: length, first character, then allowed characters.

@quiz code
prompt: Write a class `RunningAverage` with `add(value)` that records a number, and `average()` that returns the mean of everything added so far as a float. It has a `count` attribute that starts at `0` and counts the added values. Calling `average()` before anything has been added raises `ValueError`.
starter:
```python
class RunningAverage:
    pass
```
tests:
```python
r = RunningAverage()
assert r.count == 0
assert raises(ValueError, r.average)
r.add(4)
assert r.average() == 4.0
r.add(6)
assert r.average() == 5.0
assert r.count == 2
r.add(-5)
assert r.average() == 5 / 3
other = RunningAverage()
assert other.count == 0
```
model:
```python
class RunningAverage:
    def __init__(self):
        self.count = 0
        self._total = 0

    def add(self, value):
        self._total += value
        self.count += 1

    def average(self):
        if self.count == 0:
            raise ValueError("no values added")
        return self._total / self.count
```
hint: You only need to remember a running total and a count, not every value.
hint: Raise `ValueError` in `average` when `count` is 0; store the state in `__init__` so each instance starts fresh.
solution: Keep `count` and a private `_total`, update both in `add`, and divide in `average` after checking for an empty instance. The last check confirms that state belongs to each instance, not to the class.
