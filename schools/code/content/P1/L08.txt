@article
You have written tests. How good are they? Two tools give two different answers. **Coverage** tells you which code your tests *ran*. **Mutation testing** tells you whether your tests would *notice* if that code were wrong. The gap between the two is the subject of this lesson.

### Measuring coverage

With the `coverage` package, or its pytest plugin, you run the suite and get a report:

```bash
pip install pytest pytest-cov
pytest --cov=mypackage --cov-branch --cov-report=term-missing
```

The report lists, per file, the percentage of code executed and the **line numbers that never ran**. `term-missing` shows those numbers, which is the useful part: each missed line is a question ("is this code dead, or untested?"). `--cov-report=html` writes a browsable page that highlights them.

There are several kinds:

- **Line (statement) coverage**: the share of executable statements that ran at least once.
- **Branch coverage**: also tracks whether each `if` took *both* directions, and each loop both ran and exited. Turn it on (`--cov-branch`), because line coverage can be 100% while one side of an `if` never executed.
- **Diff coverage**: coverage of only the lines changed in a pull request. This is often the most useful number in review.

```python
def label(n):
    result = "small"
    if n > 10:
        result = "big"
    return result
```

The single test `label(50) == "big"` runs every line (100% line coverage), but the case where the `if` is false never ran. Branch coverage reports it as incomplete.

### What coverage cannot tell you

Coverage proves code *ran*, not that anything *checked* it. This test gives 100% coverage and verifies nothing:

```python
def test_label():
    label(50)
```

Coverage also cannot see missing code (a case you forgot to handle has no lines to be uncovered) and says nothing about whether the right values were asserted. This is why a coverage **target** gets gamed: once a number becomes the goal, people write assertion-free tests to reach it. That is **Goodhart's law**: when a measure becomes a target, it stops being a good measure.

### Using coverage well

Use it as a **flashlight**, not a score. Look at the *uncovered* lines and decide for each: write a test, delete the dead code, or mark it as deliberately excluded (`# pragma: no cover`, sparingly). A sensible policy is a floor in CI (for example `--cov-fail-under=80`, or a rule that new code must be covered) combined with human judgment in review. Low coverage in critical code (payments, permissions) is a stronger signal than a high overall percentage.

### Mutation testing: testing your tests

Mutation testing asks: *if I introduce a small bug, does a test fail?* A tool makes many **mutants**, copies of your code with one small change each: `>` becomes `>=`, `+` becomes `-`, `True` becomes `False`, a `return x` becomes `return None`. It runs your tests against each mutant. If some test fails, the mutant is **killed** (good). If all tests pass, the mutant **survived**: your tests cannot tell the buggy code from the correct code.

$$\text{mutation score} = \frac{\text{killed mutants}}{\text{total mutants}}$$

In Python, tools such as **mutmut** and **Cosmic Ray** do this; you typically point them at one module and its tests, since they run the suite many times and are slow. Each survivor is a concrete to-do: either a missing assertion, a missing boundary test, or an *equivalent mutant* (a change that does not alter behavior, which cannot be killed and is ignored).

### A worked intuition

Take `is_adult(age): return age >= 18`. A mutation tool changes `>=` to `>`. If your only tests are `is_adult(10)` and `is_adult(30)`, both versions give the same answers, so the mutant survives. The surviving mutant says: "you never tested age 18." That is exactly the boundary advice from the edge-case lesson, now found by a machine.

### Practical limits

Mutation testing is expensive, so run it on important modules, on a schedule or on changed files, not on every commit. Combine the tools: coverage finds code that no test touches, mutation testing finds code that tests touch but do not check, and reviewers find what neither can: missing requirements.

@example
title: Reading a coverage report
problem: The report for `grade` shows 83% (5 of 6 statements) and `term-missing` lists line 5. What does that tell you and what do you do?

```python
def grade(score):
    if score >= 90:
        return "A"
    if score >= 50:
        return "pass"      # line 5
    return "fail"
```
step: Line 5 never ran: no test passed a score from 50 to 89.
step: Decide what the line deserves: it is real logic, so it needs a test, not an exclusion.
step: Add `assert grade(70) == "pass"`, plus the boundaries `grade(50)`, `grade(49)`, `grade(90)` and `grade(89)`.
step: Rerun with `--cov-branch`: now both directions of each `if` have run. Coverage is 100%, and the boundary tests also protect against `>=` versus `>` mistakes.
answer: The missed line led to a real test and to boundary tests that coverage alone would not have demanded.

@example
title: A surviving mutant
problem: `is_adult(age)` returns `age >= 18`; the tests are `is_adult(10) is False` and `is_adult(30) is True`. A mutation tool reports that the mutant `age > 18` survived. What now?
step: Both tests give the same answer for original and mutant, since 10 and 30 are far from 18, so nothing fails.
step: The survivor is useful information: a boundary is untested.
step: Add `assert is_adult(18) is True` (and `is_adult(17) is False`). Against the mutant, 18 gives `False`, so a test now fails and the mutant is killed.
step: Rerun the tool: the mutant is reported as killed and the mutation score for this function rises.
answer: Add the boundary tests at 17 and 18; the surviving mutant exposed the missing case.

@mistakes
- Chasing 100% line coverage and writing tests without assertions, which satisfies the number and checks nothing.
- Trusting line coverage when branch coverage would show an untested `else` or an untested loop exit.
- Treating a missed line as an automatic task to test it, instead of asking whether the code is dead and should be deleted.
- Running mutation testing across the entire project on every commit, when it is slow and best aimed at important modules.

@quiz code
prompt: Write `mutation_score(cases, mutants)`. `cases` is a list of `(args, expected)` pairs, where `args` is a tuple. `mutants` is a list of functions. A mutant is **killed** if for at least one case it returns a value different from `expected`, or raises an exception. Return the fraction of mutants killed as a float (`killed / len(mutants)`). If there are no mutants, return `1.0`.
starter:
```python
def mutation_score(cases, mutants):
    pass
```
tests:
```python
def is_adult(age):
    return age >= 18

m_gt = lambda age: age > 18
m_always = lambda age: True
m_crash = lambda age: age.missing

weak = [((10,), False), ((30,), True)]
strong = [((10,), False), ((17,), False), ((18,), True), ((30,), True)]

assert mutation_score(weak, [m_gt]) == 0.0
assert mutation_score(strong, [m_gt]) == 1.0
assert mutation_score(weak, [m_gt, m_always, m_crash]) == 2 / 3
assert mutation_score(strong, []) == 1.0
assert mutation_score([], [m_always]) == 0.0
```
model:
```python
def mutation_score(cases, mutants):
    if not mutants:
        return 1.0
    killed = 0
    for mutant in mutants:
        for args, expected in cases:
            try:
                got = mutant(*args)
            except Exception:
                killed += 1
                break
            if got != expected:
                killed += 1
                break
    return killed / len(mutants)
```
hint: For each mutant, check the cases one by one and stop at the first case that exposes it.
hint: An exception counts as a kill; use `try`/`except Exception` and `break` after counting, so a mutant is counted once.
solution: Loop over mutants; for each, run the cases until one returns the wrong value or raises, count the mutant once and `break`. Return `killed / len(mutants)`, with `1.0` for an empty mutant list. With no cases nothing can be killed, so the score is 0.0, which is why a suite with no tests has a mutation score of zero.
