@article
On your first week at a company you will be asked to change code you did not write. The question that decides whether that is a calm task or a stressful one is simple: *how will I know I did not break something?* Automated tests are the answer. A test is a small program that runs your code with a chosen input and checks the result, so a machine can repeat in seconds what a person would repeat in an afternoon.

### What tests actually buy you

Tests do four jobs. They **catch regressions**, bugs that return after a change. They **document behavior**: a test named `test_expired_coupon_is_rejected` is a sentence about the system that cannot go out of date without turning red. They **enable refactoring**, because you can restructure code and know within seconds whether behavior survived. And they **shape design**: code that is hard to test is usually code with hidden dependencies, and the pain you feel writing the test is useful feedback.

Tests also cost something: time to write, time to run, and time to maintain when the code changes. Good testing is not "more tests", it is the right tests for the lowest total cost.

### The three levels

Classify a test by **how much of the system it exercises**.

- A **unit test** runs one small piece (a function or a class) in isolation, in memory, with no network, database, disk or clock. It takes microseconds to milliseconds.
- An **integration test** runs several pieces together, or a piece together with a real dependency: your repository class against a real database, your HTTP handler through the framework's test client. It takes tens of milliseconds to seconds.
- An **end-to-end (E2E) test** drives the whole deployed system the way a user does, for example a browser script that logs in and buys something. It takes seconds to minutes, and it fails for reasons that have nothing to do with your change: a slow page, a flaky third-party service, a stale test account.

Teams argue about the exact boundaries, and some add "component" or "contract" tests between the levels. What matters is that you can say what each test touches and what it costs.

### The testing pyramid

The **testing pyramid** is a rule of thumb: write **many unit tests, fewer integration tests, and very few E2E tests**. The reasons are economic.

| Level | Speed | Failure tells you | Stability |
|---|---|---|---|
| Unit | very fast | exactly which function is wrong | very stable |
| Integration | medium | which seam between parts is wrong | mostly stable |
| E2E | slow | "something is broken somewhere" | often flaky |

A suite that inverts the pyramid (the "ice cream cone") is slow, so people stop running it, and flaky, so people stop trusting it. A failing unit test points at a few lines; a failing E2E test starts an investigation. Put most of your logic checks at the bottom, then use a handful of higher-level tests to prove the pieces are wired together.

### Reading a test: arrange, act, assert

Almost every test has three parts: **arrange** the inputs, **act** by calling the code, **assert** on the outcome.

```python
def apply_discount(price, percent):
    return round(price * (1 - percent / 100), 2)


def test_ten_percent_off():
    price = 80.0                           # arrange
    result = apply_discount(price, 10)     # act
    assert result == 72.0                  # assert
```

When `assert` fails it raises `AssertionError`, and the test runner reports the test as failed. If the code raises any other exception, some runners (`unittest`, for example) report an **error** instead of a failure, which usually means the test or its setup is broken rather than the behavior; pytest marks both as failed and reserves "error" for problems in fixtures and setup.

### What to remember for the job

Tests are only valuable if they are **fast, deterministic and independent**. A test that passes only on Tuesdays, or only after another test ran first, is worse than no test because it trains the team to ignore red builds. Keep each test about one behavior, name it after that behavior, and run the fast ones on every save and every commit.

@example
title: Choosing the level for each check
problem: A pull request adds a "coupon code" feature to a shop. It validates the code (not expired, not used up), computes the discounted total, stores the redemption in a database, and shows the new total on the checkout page. Which level should check each part?
step: Validity rules and the discount arithmetic are pure logic: given a coupon and a date, return accepted or rejected, and compute a number. These are **unit tests**, and there should be many (expired, used up, exactly at the limit, zero percent, 100 percent).
step: Saving the redemption touches a real database table with constraints. Write a few **integration tests** that use a test database: a redemption is stored once, and a second redemption of a one-use coupon is refused by the constraint.
step: The checkout page showing the new total depends on templates, the framework and the browser. Write **one E2E test** for the happy path: add an item, enter a valid code, see the reduced total.
step: The pyramid result is roughly 15 unit tests, 3 integration tests and 1 E2E test. If the E2E test fails you know the wiring is wrong; the unit tests already told you the logic is right.
answer: Many unit tests for rules and arithmetic, a few integration tests for the database, one E2E test for the checkout flow.

@example
title: A test is just a program that can fail
problem: What does this script print, and what does that tell you about how test runners work?

```python
def double(x):
    return x * 2


try:
    assert double(3) == 7
    print("passed")
except AssertionError:
    print("failed")
```
step: `double(3)` returns `6`.
step: The assertion `6 == 7` is false, so `assert` raises `AssertionError` before `print("passed")` runs.
step: The `except AssertionError` branch catches it and prints `failed`.
step: A test runner does exactly this for every test function: call it, catch `AssertionError` (failure) or any other exception (an error in `unittest`; pytest also reports it as a failed test), and keep going so one bad test does not hide the others.
answer: It prints `failed`.

@mistakes
- Writing mostly E2E tests because they "test everything": the suite becomes slow and flaky and people stop running it.
- Calling a test a unit test while it quietly hits the network, the disk or the real clock, which makes it slow and non-deterministic.
- Treating a green suite as proof of correctness: tests show the cases you checked, not the cases you did not think of.
- Writing tests that depend on each other's order or leftover state, so they pass alone and fail together (or the reverse).

tests:
```python
def square(x):
    return x * x

assert check_cases(square, [((2,), 4), ((0,), 0)]) == []
assert check_cases(square, [((2,), 4), ((3,), 6), ((0,), 0)]) == [((3,), 6, 9)]
assert check_cases(square, []) == []
```

model:
```python
def check_cases(func, cases):
    failures = []
    for args, expected in cases:
        got = func(*args)
        if got != expected:
            failures.append((args, expected, got))
    return failures
```
hint: Loop over the cases and unpack each pair into `args` and `expected`.
hint: Call `func(*args)`, compare with `expected`, and append a tuple to a result list only when they differ.
solution: Build a `failures` list, call the function with the unpacked arguments for each case, and record `(args, expected, got)` when the result differs from the expectation. Returning the list after the loop means one failing case never hides the others, which is how real runners behave.

@quiz code
prompt: Write `run_all(tests)`, where `tests` is a dict mapping a test name to a function that takes no arguments. Call every function. A test **fails** if calling it raises any exception. Return the names of the failing tests as a sorted list, and keep running after a failure.
starter:
```python
def run_all(tests):
    pass
```
tests:
```python
def ok():
    assert 1 + 1 == 2

def bad():
    assert 1 + 1 == 3

def boom():
    return {}["missing"]

assert run_all({"a": ok, "b": bad, "c": boom}) == ["b", "c"]
assert run_all({}) == []
assert run_all({"z": ok}) == []
assert run_all({"y": bad, "x": bad, "w": ok}) == ["x", "y"]
```
model:
```python
def run_all(tests):
    failed = []
    for name, test in tests.items():
        try:
            test()
        except Exception:
            failed.append(name)
    return sorted(failed)
```
hint: Wrap each call in `try` and `except`, so one failure does not stop the loop.
hint: Append the name in the `except` branch, and sort the list when you return it.
solution: Loop over `tests.items()`, call each function inside `try`, record the name in `except Exception`, and return `sorted(failed)`. Catching the exception per test is the key idea: it is why one failing test never prevents the others from running.
