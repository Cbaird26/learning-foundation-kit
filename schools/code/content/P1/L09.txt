@article
Code is read far more often than it is written. In a team, the person reading your function next quarter will usually be you with no memory of it, or a colleague under time pressure during an incident. Readable code is not decoration: it directly lowers the cost of every future change and the chance of a bug. Most of readability comes from a few habits.

### Names carry the meaning

A name is a tiny comment that cannot go stale. Prefer names that say **what a thing is or does** in the domain:

```python
# unclear
def calc(d, r):
    return d * r / 100


# clear
def discount_amount(price, percent):
    return price * percent / 100
```

Python conventions (PEP 8): `snake_case` for functions, variables and modules; `PascalCase` for classes; `UPPER_SNAKE_CASE` for constants; a leading underscore for "internal". Name booleans like questions (`is_valid`, `has_items`), functions as verbs (`parse_date`, `send_receipt`), and values as nouns (`order_total`). Avoid single letters except in tiny scopes (`i` in a loop, `x` in a lambda), avoid abbreviations nobody else knows, and do not put the type in the name (`user_list` is better as `users`). Use the same word for the same concept everywhere: do not mix `customer`, `client` and `user` for one idea.

### Functions: one job, few parameters

A good function does **one thing** at one level of abstraction, and its name says what. Signs a function is too big: you need "and" to describe it, it has many nested blocks, or you cannot see it on one screen. Split it into smaller functions with their own names; the names then become the outline of the code.

Keep parameter lists short (more than three or four is a smell; group related values into an object or dataclass). Avoid **flag arguments** that make a function do two different things (`save(user, send_email=True)`): write two functions or make the caller do the second step. Prefer returning a value over modifying an argument, and avoid hidden side effects.

### Early returns flatten the logic

Deep nesting forces the reader to hold many conditions in their head. Handle the unusual cases first with **guard clauses**, then write the main path unindented:

```python
# nested
def shipping_label(order):
    if order is not None:
        if order.items:
            return f"Ship {len(order.items)} items"
        else:
            return "Nothing to ship"
    else:
        return "No order"


# guard clauses
def shipping_label(order):
    if order is None:
        return "No order"
    if not order.items:
        return "Nothing to ship"
    return f"Ship {len(order.items)} items"
```

### No magic numbers, and useful comments

A bare `if age >= 65:` makes the reader guess; `SENIOR_AGE = 65` documents it and gives one place to change. Comments should explain **why**, not repeat **what**. `# add one to count` is noise; `# the API counts from 1, so convert to a zero-based index` is useful. If you feel the need to write a comment explaining a confusing block, first try to make the block clear by renaming or extracting. Write **docstrings** for public functions: one summary line, then parameters, return value and raised exceptions when they are not obvious.

### Avoid cleverness and duplication

A readable loop beats a three-level nested comprehension. Use comprehensions for simple transformations and filters; switch to a loop when you need a second `if` plus a nested `for`. Remove copy-pasted code, but wait for the *third* occurrence before abstracting (the "rule of three"), because a wrong abstraction is harder to undo than a little duplication.

### Let tools enforce style

Style arguments waste review time, so automate them. A **formatter** (`ruff format` or `black`) rewrites code to one consistent layout, so layout is never discussed. A **linter** (`ruff check`, `flake8` or `pylint`) finds unused imports and undefined names by default, and with more rule sets enabled mutable default arguments, overly complex functions and many other bug patterns. Configure them once in `pyproject.toml`, run them in your editor and in CI, and optionally on each commit through `pre-commit` hooks. The line length limit is a setting (PEP 8 says 79; many teams choose 88 or 100). The rule: automated tools decide formatting, humans decide meaning.

### A quick readability check

Read your function aloud as if explaining it to a colleague. If you stumble, rename, extract or simplify. Then ask: can a new teammate predict what it does from the name alone, and can a test be written for it without a long setup?

@example
title: Cleaning up a confusing function
problem: Improve this function without changing what it does.

```python
def f(l, t):
    r = []
    for i in l:
        if i[1] > t:
            if i[2] == True:
                r.append(i[0])
    return r
```
step: Understand it first: `l` is a list of triples; it keeps the first item of each triple whose second item is above `t` and whose third item is true.
step: Name the data. The triples are `(name, score, active)` and `t` is a threshold: `def active_names_above(students, threshold)`.
step: Unpack in the loop and remove the nesting and the comparison with `True`:

```python
def active_names_above(students, threshold):
    names = []
    for name, score, active in students:
        if score > threshold and active:
            names.append(name)
    return names
```
step: Optionally write it as a comprehension (`[name for name, score, active in students if score > threshold and active]`), because it is a simple filter. Behavior is identical; only the clarity changed, which is exactly what a test suite should confirm.
answer: Descriptive names, tuple unpacking and a combined condition give the same behavior with far less to decode.

@example
title: Naming a constant and flattening a function
problem: Rewrite `def pay(h, r): if h > 40: return 40 * r + (h - 40) * r * 1.5 else: return h * r` so the rules are visible.
step: Name the parameters (`hours`, `rate`) and the two rules (`REGULAR_HOURS = 40`, `OVERTIME_MULTIPLIER = 1.5`).
step: Use a guard clause for the simple case, so the main path stays flat.
step: Result:

```python
REGULAR_HOURS = 40
OVERTIME_MULTIPLIER = 1.5


def weekly_pay(hours, rate):
    if hours <= REGULAR_HOURS:
        return hours * rate
    overtime = hours - REGULAR_HOURS
    return REGULAR_HOURS * rate + overtime * rate * OVERTIME_MULTIPLIER
```
step: Check with a calculation: 45 hours at rate 10 is `400 + 5 * 10 * 1.5 = 475`, the same as the original.
answer: Named constants and a named intermediate value turn a cryptic formula into the stated payroll rule.

@mistakes
- Naming things `data`, `temp`, `x2` or `handle_stuff`, so every reader must read the body to learn what a value is.
- Adding a boolean flag parameter that switches a function between two behaviors instead of splitting it in two.
- Comments that restate the code (`i += 1  # increment i`) while the real reason for a decision is never written down.
- Arguing about quotes and spacing in review instead of letting a formatter decide.

@practice self
prompt: Review this function as you would in a pull request. List at least four readability problems and rewrite it.

```python
def proc(d, f=False):
    # loop through d
    out = []
    for x in d:
        if x is not None:
            if f:
                out.append(x.strip().lower())
            else:
                out.append(x.strip())
    return out
```
hint: Look at the names, the flag parameter, the nesting and the comment.
solution: Problems: the names `proc`, `d`, `f` and `x` hide the purpose; `f` is a flag argument that makes one function do two jobs; the nesting is three levels deep for a simple filter; the comment `# loop through d` repeats the code; there is no docstring, and the behavior for `None` entries (they are skipped) is not stated anywhere. Rewrite as two small functions or use a transformation the caller passes:

```python
def clean_names(raw_names):
    """Return the non-None names with surrounding whitespace removed."""
    return [name.strip() for name in raw_names if name is not None]


def clean_names_lowercase(raw_names):
    """Like clean_names, but also lowercases each name."""
    return [name.lower() for name in clean_names(raw_names)]
```
The flag is gone, each function has one job and a docstring, the `None` rule is documented, and a test can target each behavior separately.
rubric: Identifies at least four distinct problems (unclear names, the flag argument, deep nesting, a comment that repeats the code, missing docstring).
rubric: The rewrite removes the flag by splitting responsibilities or otherwise making each function do one thing.
rubric: The rewrite has descriptive names, no unnecessary nesting and documents the behavior for `None` entries.

@quiz code
prompt: Write `weekly_pay(hours, rate)`: the first 40 hours are paid at `rate`, and hours beyond 40 are paid at 1.5 times `rate`. Use named constants for the 40 and the 1.5, and a guard clause for the case without overtime. Negative `hours` raise `ValueError`.
starter:
```python
def weekly_pay(hours, rate):
    pass
```
tests:
```python
assert weekly_pay(0, 10) == 0
assert weekly_pay(40, 10) == 400
assert weekly_pay(45, 10) == 475
assert weekly_pay(30, 12.5) == 375
assert weekly_pay(41, 20) == 830
assert raises(ValueError, weekly_pay, -1, 10)
```
model:
```python
REGULAR_HOURS = 40
OVERTIME_MULTIPLIER = 1.5


def weekly_pay(hours, rate):
    if hours < 0:
        raise ValueError("hours must not be negative")
    if hours <= REGULAR_HOURS:
        return hours * rate
    overtime_hours = hours - REGULAR_HOURS
    return REGULAR_HOURS * rate + overtime_hours * rate * OVERTIME_MULTIPLIER
```
hint: Validate first, then handle the no-overtime case with an early return.
hint: Overtime pay is `(hours - 40) * rate * 1.5`; add the 40 regular hours at the normal rate.
solution: Reject negative hours, return `hours * rate` when there is no overtime, and otherwise add the regular pay to the overtime pay computed from the named constants. The test at exactly 40 hours checks the boundary between the two branches.
