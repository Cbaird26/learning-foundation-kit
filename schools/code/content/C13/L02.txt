@article
Most failed projects do not fail because the code was badly written. They fail because the team built the wrong thing, or nobody could tell whether they had built the right thing. **Requirements engineering** is the work of finding out what the software must do and writing it down so it can be agreed, built and verified.

### Functional and non-functional requirements

A **functional requirement** states behavior: "The system sends a confirmation email when an order is placed." A **non-functional requirement** (quality attribute) states how well: performance, availability, security, usability, accessibility, maintainability. A requirement is only useful if you can tell when it is met, so non-functional ones must be made measurable:

| Vague | Testable |
|---|---|
| "The site should be fast." | "95% of search requests complete in under 300 ms with 500 concurrent users." |
| "It must be secure." | "Passwords are stored salted and hashed; accounts lock for 15 minutes after 5 failed sign-ins." |
| "Easy to use." | "A new user completes checkout in under 3 minutes without help in a usability test with 8 people." |

**Elicitation** techniques include interviews, observation of real work, questionnaires, studying existing systems and prototypes. Requirements also conflict (security versus convenience), so someone must negotiate priorities. Constraints (a deadline, a mandated database) are requirements too.

### User stories

Agile teams usually capture functional requirements as **user stories**: short statements from the viewpoint of a user.

```text
As a <role>, I want <goal> so that <benefit>.
```

For example: "As a shopper, I want to save items for later so that I can buy them when I get paid." The story is a reminder to have a conversation, not a full specification. The "so that" clause matters: it exposes the real need, which sometimes has a cheaper solution than the stated goal.

Good stories satisfy **INVEST**:

- **I**ndependent: can be scheduled in any order where possible.
- **N**egotiable: details are discussed, not fixed in the text.
- **V**aluable to a user or customer.
- **E**stimable: the team understands it well enough to size it.
- **S**mall: finishable within one iteration.
- **T**estable: you can say when it is done.

"As an admin, I want a better dashboard" fails Testable and Small. An **epic** is a story too large for one iteration, to be split into smaller stories that each deliver value (split by workflow step or data variation, not by technical layer).

### Acceptance criteria

**Acceptance criteria** are the conditions under which a story is accepted. A popular format is **Given-When-Then**:

```text
Given a cart with a total of 50.00 or more
When the shopper views the shipping cost
Then the shipping cost is 0.00
```

Each scenario names a starting state, one action and an observable outcome. Several scenarios per story should cover the typical path and the boundaries. Because they are precise, they can become automated tests directly:

```python
def shipping_cents(total_cents):
    return 0 if total_cents >= 5000 else 499

assert shipping_cents(5000) == 0      # the boundary itself
assert shipping_cents(4999) == 499    # just below it
```

Writing the criteria before the code is the cheapest way to find ambiguity: you cannot write the boundary assert without deciding what exactly happens at 50.00.

@example
title: Improving a vague story
problem: Improve the story "As a user, I want a faster search" so that it satisfies INVEST, and write two Given-When-Then criteria.
step: Identify who the user is and what the benefit is. "User" is too general; say shopper. The benefit is finding a product without giving up.
step: Make it testable by naming a measurable target: "results appear in under 1 second for catalog searches".
step: Rewrite: "As a shopper, I want search results to appear in under 1 second so that I do not abandon the site while looking for a product."
step: Criterion 1: Given a catalog of 10,000 products, When the shopper searches for "lamp", Then results are displayed in under 1 second.
step: Criterion 2: Given a search term that matches no product, When the shopper searches, Then a "no results" message appears in under 1 second.
answer: A role-specific story with a measurable benefit and two scenarios covering the typical and the empty case.

@example
title: From acceptance criteria to an executable check
problem: Criteria: orders of 50.00 or more ship free; smaller orders cost 4.99. Write `shipping_cents(total_cents)` and the asserts that cover the boundary.
step: Work in integer cents (5000 and 499) to avoid floating-point rounding in money.
step: The criterion "50.00 or more" is `total_cents >= 5000`, so 5000 itself ships free.
step: Implement it as a conditional expression:

```python
def shipping_cents(total_cents):
    return 0 if total_cents >= 5000 else 499
```
step: Test the boundary and its neighbor: `shipping_cents(5000) == 0` and `shipping_cents(4999) == 499`. A solution using `>` instead of `>=` would fail the first.
answer: Free at 5000 cents and above, 499 below.

@mistakes
- Writing stories that describe a solution ("I want a dropdown") instead of a need and its benefit.
- Leaving out "so that", which hides the reason and prevents cheaper alternatives.
- Writing acceptance criteria that cannot fail ("the page should look good") instead of observable outcomes.
- Splitting an epic by technical layer ("the database part", "the UI part"), which delivers no user value until all parts exist.

model:
```python
def parse_story(text):
    if text.startswith("As an "):
        rest = text[len("As an "):]
    elif text.startswith("As a "):
        rest = text[len("As a "):]
    else:
        raise ValueError("story must start with 'As a'")
    if ", I want " not in rest:
        raise ValueError("story needs ', I want '")
    role, rest = rest.split(", I want ", 1)
    rest = rest.rstrip(".")
    if " so that " in rest:
        goal, benefit = rest.split(" so that ", 1)
    else:
        goal, benefit = rest, None
    return {"role": role, "goal": goal, "benefit": benefit}
```
hint: Strip the prefix first, then split on `", I want "`, then on `" so that "` with `split(sep, 1)`.
hint: Remove the final period from the rest of the text before splitting on `so that`.
solution: Check the prefix (try `As an ` before `As a `, though neither is a prefix of the other here), split on `", I want "` once, strip the trailing period, then split on `" so that "` once if present; otherwise the benefit is `None`.

model:
```python
def is_valid_story(text):
    if not (text.startswith("As a ") or text.startswith("As an ")):
        return False
    i = text.find(", I want ")
    if i == -1:
        return False
    return text.find(" so that ", i + len(", I want ")) != -1
```
hint: Find `, I want ` first, then search for ` so that ` only after that position.
solution: Check the prefix, locate `, I want `, then use `find` with a start index just past it to require ` so that ` afterwards. This rejects stories whose parts are out of order.
