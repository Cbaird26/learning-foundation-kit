@article
Code explains *how*; documentation explains *what it is for, how to use it, and why it is this way*. The reader may be a new teammate, a user of your library, or you in six months. Documentation that is out of date is worse than none, so the aim is not more documents but **the right documents, close to the code, kept up to date**.

### Kinds of documentation

| Kind | Audience | Content |
|---|---|---|
| README | anyone meeting the project | what it is, install, a quick example, how to run tests, how to contribute |
| API reference / docstrings | users of the code | each public function: purpose, parameters, return value, errors, example |
| Design document | reviewers and future maintainers | goals, non-goals, options considered, chosen design |
| Architecture decision record (ADR) | future maintainers | one decision: context, decision, consequences |
| Runbook | on-call engineers | steps to diagnose and fix a known failure |
| Changelog / release notes | users and operators | what changed in each release |

**Comments** should say *why*, not repeat *what* the code obviously does: `i += 1  # increment i` is noise, while `# The API returns UTC; convert before comparing` is knowledge. Treat docs like code: store them in version control, review them in pull requests, and update them in the same change as the code they describe. In Python, a **docstring** documents a public function:

```python
def clamp(value, low, high):
    """Return value limited to the range [low, high].

    Raises ValueError if low is greater than high.
    """
    if low > high:
        raise ValueError("low must not exceed high")
    return max(low, min(value, high))
```

### Recording decisions

An **ADR** is a short document, one per significant decision, kept in the repository. A common layout: *Title*, *Status* (proposed, accepted, superseded), *Context* (the forces and constraints), *Decision* (what we chose), *Consequences* (good and bad results, including costs we accept). ADRs are never edited to hide history; a later decision *supersedes* an earlier one. They answer the question every new maintainer asks: "why on earth did they do it this way?"

### Versioning and changelogs

**Semantic Versioning** (SemVer 2.0.0) numbers releases `MAJOR.MINOR.PATCH`. Increment **MAJOR** for incompatible API changes, **MINOR** for backward-compatible new functionality, and **PATCH** for backward-compatible bug fixes; raising a higher number resets the lower ones to zero (`1.4.7` to `2.0.0`). A **changelog** lists notable changes per version for humans, grouped under headings such as Added, Changed, Deprecated, Removed, Fixed and Security, newest first.

### Professional ethics

Software affects people's safety, money, privacy and opportunities, so engineers carry professional responsibilities. The **ACM Code of Ethics and Professional Conduct** (2018) lists principles including: contribute to society and to human well-being; avoid harm; be honest and trustworthy; be fair and take action not to discriminate; respect the work required to produce new ideas and software; respect privacy; honor confidentiality; and, for professionals, perform work only in areas of competence, give comprehensive and thorough evaluations of systems and their risks, and design and implement systems that are robustly and usably secure. The joint ACM/IEEE-CS **Software Engineering Code of Ethics** organizes similar duties around the public, client and employer, product, judgment, management, profession, colleagues and self. Codes do not give mechanical answers; they give a vocabulary for weighing duties when they conflict, and the public interest comes first.

Practical consequences: estimate and report risks honestly; do not ship known safety or security defects silently; collect only the personal data you need and protect it; design for accessibility (WCAG 2.2); run **blameless postmortems** after incidents; take responsibility for code you submit, including code produced with the help of AI tools, which you must review, test and check for licensing and security problems like any other code.

### Licenses (not legal advice)

Code without a license is, by default, under copyright with all rights reserved to its author; others may not legally reuse it. **Permissive** licenses (MIT, BSD, Apache 2.0) allow use, modification and redistribution with few conditions, mainly keeping the copyright notice (Apache 2.0 also includes an explicit patent grant). **Copyleft** licenses such as the GNU General Public License (GPL) require that distributed derivative works be released under the same license terms with source available. Always read the license before depending on code, track the licenses of your dependencies, and ask a lawyer for legal questions.

@example
title: Deciding the next version number
problem: The current release is `2.3.4`. Choose the next version for (a) a bug fix that changes no interface; (b) a new optional function; (c) renaming an existing public function without keeping the old name.
step: (a) A backward-compatible bug fix is a PATCH change, so `2.3.5`.
step: (b) New backward-compatible functionality is a MINOR change; reset the patch to zero: `2.4.0`.
step: (c) Removing or renaming a public function breaks existing callers, an incompatible change, so MAJOR: `3.0.0`, with minor and patch reset.
step: Record each in the changelog under Fixed, Added and Changed or Removed, so users can decide whether upgrading is safe.
answer: (a) 2.3.5, (b) 2.4.0, (c) 3.0.0.

@example
title: Writing an architecture decision record
problem: A team chooses PostgreSQL over a document database for its orders service. Write the ADR.
step: Title and status: "ADR 7: Use PostgreSQL for the orders service. Status: accepted."
step: Context: orders have strict relationships (customers, items, payments), need transactions across tables, and the team already operates PostgreSQL.
step: Decision: store orders in PostgreSQL with a relational schema, and use migrations in version control.
step: Consequences: good: transactions, mature tooling, no new system to operate. Bad: schema changes need migrations, and very high write volume would later need partitioning or another store. Alternatives considered: a document database (rejected for transactional needs).
answer: A one-page ADR with title, status, context, decision and consequences, including the costs accepted.

@mistakes
- Writing comments that restate the code ("add 1 to total") instead of explaining the reason.
- Keeping documentation separate from the code, so it is not updated in the same change and goes stale.
- Reading "no license" as "free to use"; without a license the default is that reuse is not permitted.
- Bumping only the patch number for a change that breaks existing users, which hides the incompatibility.

Raise `ValueError` for anything else (wrong number of parts, letters, empty parts, leading zeros, pre-release suffixes such as `"1.2.3-beta"`).

```python

```
tests:
```python
assert parse_version("1.12.3") == (1, 12, 3)
assert parse_version("0.0.0") == (0, 0, 0)
assert parse_version("10.20.30") == (10, 20, 30)
assert raises(ValueError, parse_version, "1.2")
assert raises(ValueError, parse_version, "1.2.3.4")
assert raises(ValueError, parse_version, "1.02.3")

assert raises(ValueError, parse_version, "1.2.3-beta")
```
model:
```python
def parse_version(text):
    parts = text.split(".")
    if len(parts) != 3:
        raise ValueError("need MAJOR.MINOR.PATCH")
    numbers = []
    for part in parts:
        if not part or not part.isascii() or not part.isdigit():
            raise ValueError(f"bad version part: {part!r}")
        if len(part) > 1 and part.startswith("0"):
            raise ValueError("leading zero")
        numbers.append(int(part))
    return tuple(numbers)
```
hint: Split on `"."` and check that there are exactly three parts.
hint: For each part check `isdigit()` and that a part longer than one character does not start with `"0"`.
solution: Split into three parts, validate each (non-empty, ASCII digits, no leading zero), convert with `int` and return a tuple. A suffix such as `-beta` makes the last part contain a non-digit, so it is rejected.

@practice code
prompt: Write `bump_version(version, part)` that returns the next semantic version string. `part` is `"major"`, `"minor"` or `"patch"`: bumping major adds 1 to the major number and resets minor and patch to 0; bumping minor adds 1 to minor and resets patch to 0; bumping patch adds 1 to patch. Example: `bump_version("2.3.4", "minor")` is `"2.4.0"`. Raise `ValueError` if `part` is anything else, or if `version` is not three dot-separated non-negative integers (you may use `int()` on each part, but there must be exactly three parts and no part may be negative).
starter:
```python
def bump_version(version, part):
    pass
```
tests:
```python
assert bump_version("2.3.4", "patch") == "2.3.5"
assert bump_version("2.3.4", "minor") == "2.4.0"
assert bump_version("2.3.4", "major") == "3.0.0"
assert bump_version("0.0.9", "patch") == "0.0.10"
assert bump_version("1.9.9", "minor") == "1.10.0"
assert raises(ValueError, bump_version, "1.2.3", "build")
assert raises(ValueError, bump_version, "1.2", "patch")
assert raises(ValueError, bump_version, "a.b.c", "patch")
assert raises(ValueError, bump_version, "1.-2.3", "patch")
```
model:
```python
def bump_version(version, part):
    pieces = version.split(".")
    if len(pieces) != 3:
        raise ValueError("need MAJOR.MINOR.PATCH")
    major, minor, patch = (int(p) for p in pieces)
    if min(major, minor, patch) < 0:
        raise ValueError("negative part")
    if part == "major":
        major, minor, patch = major + 1, 0, 0
    elif part == "minor":
        minor, patch = minor + 1, 0
    elif part == "patch":
        patch += 1
    else:
        raise ValueError(f"unknown part: {part!r}")
    return f"{major}.{minor}.{patch}"
```
hint: Convert the three pieces to integers first, then apply the rule for the chosen part.
hint: Remember that bumping a higher number resets all lower ones to zero.
solution: Split into exactly three integers (`int` raises `ValueError` itself for letters), apply the reset rules for each part, and join the numbers with dots. Numbers are compared and incremented as integers, so `1.9.9` minor becomes `1.10.0`, not `1.9.10`.

assert satisfies_caret("1.2.3", "1.2.3")
assert satisfies_caret("1.10.0", "1.9.0")

model:
```python
def satisfies_caret(version, base):
    v = tuple(int(p) for p in version.split("."))
    b = tuple(int(p) for p in base.split("."))
    if b[0] == 0:
        raise ValueError("major version 0 is not supported")
    return v >= b and v[0] == b[0]
```
hint: Convert each string to a tuple of integers; tuples compare element by element.
solution: Turn both versions into integer tuples so that `1.10.0 > 1.9.0` compares correctly, require `v >= b`, and require the same major number. Comparing strings would wrongly rank `"1.10.0"` below `"1.9.0"`.
