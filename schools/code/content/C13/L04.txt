@article
A design that lives only in one person's head cannot be reviewed. The **Unified Modeling Language (UML)** is a standard graphical notation for describing software designs. You rarely draw every diagram a tool can produce. Teams sketch two kinds again and again: a **class diagram** for *structure* (what exists and how it is related) and a **sequence diagram** for *behavior over time* (who calls whom, in what order). Treat diagrams as communication, not decoration: draw only what a reader needs and say which question each answers.

### Class diagrams

A class is a box with three compartments: name, attributes, operations. Visibility prefixes are `+` public, `-` private, `#` protected.

```text
+---------------------+
| Order               |
+---------------------+
| - id: int           |
| - status: String    |
+---------------------+
| + total(): Money    |
| + cancel(): void    |
+---------------------+
```

Lines between boxes are **relationships**:

| Relationship | Meaning | Notation |
|---|---|---|
| Association | one class knows or uses another over time | plain line, often with a role name |
| Aggregation | "has-a", the part can exist alone | line with a hollow diamond at the whole |
| Composition | "owns", the part's life ends with the whole | line with a filled diamond at the whole |
| Inheritance (generalization) | "is-a" | solid line with a hollow triangle at the superclass |
| Realization | a class implements an interface | dashed line with a hollow triangle at the interface |
| Dependency | one class uses another briefly (a parameter, a local variable) | dashed line with an open arrowhead |

**Multiplicity** at a line end says how many instances take part: `1` exactly one, `0..1` optional, `*` or `0..*` any number, `1..*` at least one. "One `Order` has `1..*` `OrderLine` objects" is written with `1` at the Order end and `1..*` at the OrderLine end. Because order lines do not exist without their order, this is composition.

In code, an association usually becomes an attribute, inheritance becomes a subclass, and realization becomes a class implementing an abstract base class or protocol:

```python
class Order:
    def __init__(self):
        self._lines = []          # composition: Order owns its lines

    def add_line(self, product, qty):
        self._lines.append(OrderLine(product, qty))
```

### Sequence diagrams

A sequence diagram shows **participants** (objects or components) as **lifelines** running down the page, and **messages** as horizontal arrows ordered from top to bottom. A solid arrow is a call; a dashed arrow is a return. Time flows downward; nothing is implied by horizontal distance. A text form that many tools accept looks like this:

```text
Shopper -> Cart: addItem(book)
Cart -> Catalog: price(book)
Catalog --> Cart: 12.00
Cart --> Shopper: total 12.00
```

Each line is `sender -> receiver: message`, with `-->` for a return. **Combined fragments** add control flow: `alt` (alternatives, like if/else), `opt` (optional), `loop` (repetition). Use them sparingly; a diagram that must show every branch is usually too detailed.

### Choosing what to draw

Draw a class diagram when the question is "what are the parts and who owns what?" and a sequence diagram when it is "what happens, in what order, when the user does X?" Draw one sequence diagram per use case or scenario, derived from a user story. If a sequence diagram needs a message that no class diagram operation supports, one of the two is wrong; checking them against each other is the main benefit of drawing both.

@example
title: From a story to a class diagram
problem: Story: "As a library member, I want to borrow a book so that I can read it at home." Sketch the classes and relationships.
step: Find the nouns: Member, Book, Loan. These are candidate classes.
step: A `Loan` links one `Member` to one `Book` and has a due date. Make it a class with attributes `dueDate` and `returnedOn`.
step: Relationships with multiplicity: a Member has `0..*` Loans; each Loan belongs to exactly `1` Member; each Loan is for exactly `1` Book; a Book has `0..*` Loans over time.
step: Add operations from the verbs: `Member.borrow(book)`, `Loan.isOverdue(today)`, `Loan.markReturned(date)`.
step: Check the lifetimes: a Loan record has no meaning without its Member, but a Member exists without loans, so use a plain association (or aggregation), not composition, unless loans are deleted with the member.
answer: Member 1 --- 0..* Loan 0..* --- 1 Book, with the operations above.

@example
title: A sequence diagram for borrowing a book
problem: Draw the message sequence for `borrow(book)`, including the case where the book is already on loan.
step: Participants: Member, Library, Book, Loan.
step: First message: `Member -> Library: borrow(book)`. The library asks the book `Library -> Book: isAvailable()` and the book returns `Book --> Library: true`.
step: In the available branch, `Library -> Loan: create(member, book, dueDate)` follows, and `Library --> Member: loan`.
step: Wrap the choice in an `alt` fragment: [available] creates the loan; [else] `Library --> Member: error("on loan")`.
step: Check against the class diagram: `isAvailable` must be an operation of `Book`, and `Loan` must have a way to be created with the three arguments.
answer: Member calls Library, which queries Book and, only when available, creates a Loan; otherwise it returns an error.

@mistakes
- Using inheritance where "has-a" is meant (for example, `Car` extends `Engine`); inheritance means "is-a".
- Reading or drawing the diamond at the wrong end: it always sits at the whole, not at the part.
- Making diagrams too detailed to read; showing every attribute of every class instead of what the discussion needs.
- Drawing a sequence diagram whose messages do not correspond to operations on the class diagram, so the two models disagree.

@practice code
prompt: A sequence diagram is stored as a list of messages, each a tuple `(sender, receiver, text)`. Write `participants(messages)` that returns the list of distinct participant names in order of first appearance, reading the sender before the receiver within each message. Example: `[("A", "B", "x"), ("B", "C", "y"), ("C", "A", "z")]` gives `["A", "B", "C"]`. An empty list gives `[]`.
starter:
```python
def participants(messages):
    pass
```
tests:
```python
msgs = [("A", "B", "x"), ("B", "C", "y"), ("C", "A", "z")]
assert participants(msgs) == ["A", "B", "C"]
assert participants([]) == []
assert participants([("Cart", "Cart", "recalc")]) == ["Cart"]
assert participants([("B", "A", "m"), ("A", "C", "n")]) == ["B", "A", "C"]
```
model:
```python
def participants(messages):
    seen = []
    for sender, receiver, _ in messages:
        for name in (sender, receiver):
            if name not in seen:
                seen.append(name)
    return seen
```
hint: Keep a list of names already seen and append a name only the first time.
solution: Loop through the messages, and for each handle the sender and then the receiver, appending a name to `seen` only if it is not already there. Using a list (not a set) preserves the order of first appearance.

@practice code
prompt: Write `render_sequence(messages)` that turns a list of `(sender, receiver, text)` tuples into diagram text, one line per message in the form `sender -> receiver: text`, joined with newline characters and with no trailing newline. If the text starts with `return `, draw it as a return instead: `sender --> receiver: ` followed by the text with the leading `return ` removed. An empty list returns the empty string. Example: `[("A", "B", "go"), ("B", "A", "return ok")]` gives `"A -> B: go\nB --> A: ok"`.
starter:
```python
def render_sequence(messages):
    pass
```
tests:
```python
assert render_sequence([("A", "B", "go")]) == "A -> B: go"
assert render_sequence([("A", "B", "go"), ("B", "A", "return ok")]) == (
    "A -> B: go\nB --> A: ok")
assert render_sequence([]) == ""
assert render_sequence([("X", "Y", "returns")]) == "X -> Y: returns"
```
model:
```python
def render_sequence(messages):
    lines = []
    for sender, receiver, text in messages:
        if text.startswith("return "):
            lines.append(f"{sender} --> {receiver}: {text[len('return '):]}")
        else:
            lines.append(f"{sender} -> {receiver}: {text}")
    return "\n".join(lines)
```
hint: Build a list of lines and join it at the end with `"\n".join(...)`.
hint: The prefix to test for is `"return "` with a trailing space, so `"returns"` is not a return.
solution: Build one line per message, choosing the dashed arrow when the text starts with `return ` (with the space) and stripping that prefix; join with newlines. The trailing space in the prefix keeps `returns` as an ordinary call.

rubric: The sequence shows messages in order with returns, and each message matches an operation in the class diagram.
rubric: The expired-code scenario is shown as an alternative branch with its own outcome.
