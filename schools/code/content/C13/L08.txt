@article
You can never test every input: a function taking one 32-bit integer already has over four billion. **Test design** techniques pick a small set of inputs likely to expose defects. They are *black-box* techniques: you derive tests from the specification, without looking at the code, so the tests stay valid when the implementation changes.

### Equivalence partitioning

An **equivalence class** is a set of inputs that the specification treats the same way, so that if the program is correct (or wrong) for one member, it very probably is for all. Partition the input domain into classes and test **one representative of each class**, including *invalid* classes. Suppose a form accepts an age from 18 to 65 inclusive. The classes are: below 18 (invalid), 18 to 65 (valid), above 65 (invalid), and non-numeric input (invalid). Four tests, such as 10, 40, 80 and `"abc"`, cover the classes.

### Boundary value analysis

Defects cluster at boundaries: `<` written for `<=`, an off-by-one in a loop. **Boundary value analysis** tests each boundary exactly and just beside it. For the range 18 to 65 the boundary values are 17, 18, 65 and 66: the last invalid value below, the first and last valid values, and the first invalid value above. For discrete inputs "just beside" means the adjacent value (for whole grams, one gram). Combine both techniques: representatives from the interior of each class plus values at every boundary.

### Decision tables

When the output depends on a combination of conditions, list the combinations in a **decision table**: conditions as rows, rules as columns, and the resulting action at the bottom. For a login: conditions are "credentials valid" and "account locked"; there are four combinations, and the table shows that a locked account must be refused even with correct credentials, a rule easy to forget. With *n* independent true/false conditions there are $2^n$ combinations, so for many conditions teams select a subset (for example, pairwise testing covers every pair of values).

### State-transition and error guessing

For systems with memory (an order that goes from new to paid to shipped), draw the states and transitions, then test every valid transition and several invalid ones (shipping an unpaid order). **Error guessing** adds tests from experience: empty strings, `None`, very long input, duplicates, Unicode, leap days, negative numbers.

### From specification to test table

Write the cases as a table of input, expected output and the class or boundary each tests. Here is one for a function `shipping_band(weight_g)` with these rules: weights 1 to 1000 g cost 5, 1001 to 10000 g cost 8, 10001 to 30000 g cost 15, and any weight below 1 or above 30000 is invalid.

| Test | Input (g) | Expected | Reason |
|---|---|---|---|
| 1 | 0 | error | below the valid range |
| 2 | 1 | 5 | lowest valid weight |
| 3 | 500 | 5 | interior of first band |
| 4 | 1000 | 5 | upper bound of first band |
| 5 | 1001 | 8 | lower bound of second band |
| 6 | 10000 | 8 | upper bound of second band |
| 7 | 10001 | 15 | lower bound of third band |
| 8 | 30000 | 15 | highest valid weight |
| 9 | 30001 | error | above the valid range |

Notice that every expected value comes from the specification, never from running the code. In Python these become assertions, with `raises` or `pytest.raises`-style checks for errors. Finally, a technique to remember when the domain is huge: **property-based testing** generates many random inputs and checks properties that must always hold, such as "sorting twice gives the same result as sorting once".

@example
title: Boundary tests for a shipping rule
problem: Using the weight rules from the article (1 to 1000 g costs 5, 1001 to 10000 g costs 8, 10001 to 30000 g costs 15, otherwise invalid), list a boundary-value test set.
step: Find the boundaries between classes: 0|1 (invalid to first band), 1000|1001, 10000|10001 and 30000|30001.
step: Test both sides of each boundary, so the values are 0, 1, 1000, 1001, 10000, 10001, 30000 and 30001: eight values.
step: Add one interior representative for each band if desired, such as 500, 5000 and 20000.
step: Write the expected result from the specification: 0 is invalid, 1 and 1000 cost 5, 1001 and 10000 cost 8, 10001 and 30000 cost 15, 30001 is invalid.
answer: The eight boundary values 0, 1, 1000, 1001, 10000, 10001, 30000, 30001 (plus optional interior values).

@example
title: A boundary test catches an off-by-one
problem: A developer wrote `def is_adult(age): return age > 18`, but the specification says people aged 18 or over are adults. Which test reveals the bug?
step: The boundary of the specification is 18, so test 17, 18 and 19.
step: Expected by the specification: `is_adult(17)` is `False`, `is_adult(18)` is `True`, `is_adult(19)` is `True`.
step: The code gives `False` for 17 (correct), `False` for 18 (wrong) and `True` for 19 (correct).
step: Only the test at exactly 18 fails. A test set with just 10 and 40 (one value per class) would have missed the bug, which is why boundaries need their own tests.
answer: `is_adult(18)` returns `False` but should return `True`; the fix is `age >= 18`.

@mistakes
- Testing only "typical" values from the middle of each range and missing the boundaries where defects cluster.
- Forgetting the invalid classes (negative numbers, empty input, `None`, wrong type) and testing only valid input.
- Deriving the expected output by running the code under test, which makes a wrong implementation pass its own test.
- Testing many members of the same equivalence class, which costs time and adds no new information.

@practice code
prompt: Write `classify_triangle(a, b, c)` for three side lengths (numbers). Return `"invalid"` if any side is zero or negative, or if the sides violate the triangle inequality, meaning the sum of the two shorter sides is not strictly greater than the longest (a degenerate triangle such as 1, 2, 3 is invalid). Otherwise return `"equilateral"` if all three sides are equal, `"isosceles"` if exactly two are equal, and `"scalene"` if all differ.
starter:
```python
def classify_triangle(a, b, c):
    pass
```
tests:
```python
assert classify_triangle(3, 3, 3) == "equilateral"
assert classify_triangle(3, 3, 5) == "isosceles"
assert classify_triangle(3, 4, 5) == "scalene"
assert classify_triangle(1, 2, 3) == "invalid"
assert classify_triangle(0, 4, 4) == "invalid"
assert classify_triangle(-1, 2, 2) == "invalid"
assert classify_triangle(2, 3, 6) == "invalid"
assert classify_triangle(5, 5, 9) == "isosceles"
assert classify_triangle(5, 9, 5) == "isosceles"
```
model:
```python
def classify_triangle(a, b, c):
    if a <= 0 or b <= 0 or c <= 0:
        return "invalid"
    x, y, z = sorted((a, b, c))
    if x + y <= z:
        return "invalid"
    if x == z:
        return "equilateral"
    if x == y or y == z:
        return "isosceles"
    return "scalene"
```
hint: Sort the sides so the longest is last, then test the triangle inequality on the sorted values.
hint: Check validity first; after sorting, all equal means `x == z`, and two equal means `x == y` or `y == z`.
solution: Reject non-positive sides, sort, and reject when the two shorter sides do not sum to more than the longest (so 1, 2, 3 is invalid). Then classify by how many sides are equal. Sorting makes the isosceles test independent of argument order.

@practice code
prompt: Specification: `grade(score)` takes an integer exam score from 0 to 100 inclusive and returns a letter: `"A"` for 90 to 100, `"B"` for 80 to 89, `"C"` for 70 to 79, `"D"` for 60 to 69, `"F"` for 0 to 59. Any score below 0 or above 100 raises `ValueError`. Implement it.
starter:
```python
def grade(score):
    pass
```
tests:
```python
assert grade(100) == "A"
assert grade(90) == "A"
assert grade(89) == "B"
assert grade(80) == "B"
assert grade(79) == "C"
assert grade(70) == "C"
assert grade(69) == "D"
assert grade(60) == "D"
assert grade(59) == "F"
assert grade(0) == "F"
assert raises(ValueError, grade, -1)
assert raises(ValueError, grade, 101)
```
model:
```python
def grade(score):
    if score < 0 or score > 100:
        raise ValueError("score must be between 0 and 100")
    if score >= 90:
        return "A"
    if score >= 80:
        return "B"
    if score >= 70:
        return "C"
    if score >= 60:
        return "D"
    return "F"
```
hint: Validate the range first, then test the thresholds from the highest down using `>=`.
solution: Raise `ValueError` outside 0 to 100, then check `>= 90`, `>= 80`, `>= 70` and `>= 60` in that order and return `"F"` otherwise. The tests sit on both sides of every threshold, which is where `>` versus `>=` mistakes show.

@practice self
prompt: Specification: `password_ok(pw)` returns `True` if the password has at least 15 characters and at most 128 characters, and is not in a supplied blocklist of common passwords; otherwise `False`. Design a table of test cases (input, expected result, reason) using equivalence classes and boundary values. Include at least eight cases.
solution: Classes: too short (below 15), valid length (15 to 128) and not blocklisted, too long (above 128), blocklisted (even when the length is valid), plus edge inputs. Cases: (1) a 14-character password: False, just below the lower bound. (2) A 15-character password not on the blocklist: True, lower bound. (3) A 16-character password: True, just above the bound. (4) A 40-character password: True, interior of the valid class. (5) A 128-character password: True, upper bound. (6) A 129-character password: False, just above the upper bound. (7) An empty string: False, error-guessing edge. (8) A 15-or-more-character password that is on the blocklist: False, blocklist class independent of length. (9) A 20-character password with spaces and Unicode characters: True, there are no composition rules. Expected values come from the specification.
rubric: Includes the boundary values 14, 15, 128 and 129 characters with the correct expected results.
rubric: Includes a blocklisted case whose length is otherwise valid, showing a second independent condition.
rubric: Includes at least one error-guessing case such as the empty string or unusual characters.
rubric: Each case states its reason, and expected outputs are derived from the specification.
hint: There are two conditions, length and blocklist; make a case for each combination, then add boundaries.

```python
def ticket_price(age):
    if age < 0 or age > 120:
        raise ValueError("age out of range")
    if age <= 2:
        return 0
    if age <= 12:
        return 8
    if age <= 64:
        return 15
    return 10
```

solution: Reject ages outside 0 to 120, then test the upper bounds 2, 12 and 64 with `<=` in increasing order; everything left is 65 to 120. The tests probe both sides of each boundary.
