@article
**Code review** means that someone other than the author examines a change before it is merged. Its benefits go beyond catching bugs: it spreads knowledge of the codebase, keeps style and design consistent, teaches both author and reviewer, and creates a shared sense of ownership. Review complements testing rather than replacing it: reviewers catch kinds of problems tests cannot, especially design flaws, unclear code and missing tests.

### The author's job

Review quality starts before the reviewer opens the change. A good author:

- keeps the change **small and focused**: one logical change that a reviewer can understand in under an hour. Large changes get shallow reviews, because attention falls as size rises.
- writes a **description** that says what changed, why, and how it was tested, and links the story or issue.
- runs the tests, the linter and the formatter first, so reviewers do not spend time on what machines check.
- reviews their own diff before asking for others.
- responds to every comment, either by changing the code or by explaining; and does not take comments personally, since the review is about the code.

### The reviewer's job

Read the description first, then the tests (they state the intended behavior), then the code. A useful checklist:

1. **Correctness**: does it do what the story asks? Edge cases: empty input, `None`, boundaries, error paths, concurrency?
2. **Design**: does it fit the existing structure? Is it in the right module, with low coupling and no duplication?
3. **Tests**: do tests exist for new behavior and for the bug being fixed? Would they fail if the code were wrong?
4. **Readability**: names, comments that explain *why*, small functions. Could a new teammate understand it?
5. **Security and privacy**: is input validated, are queries parameterized, are secrets and personal data protected?
6. **Operations**: logging, error handling, performance in the hot path, backward compatibility of data and APIs.

Approve when the change improves the overall health of the codebase, even if it is not how you would have written it. Perfection is not the bar; do not block on matters of personal preference.

### Writing comments

Be specific, explain the reason, and suggest a direction. Compare:

```text
Bad:  "This is wrong."
Good: "If `items` is empty this raises ZeroDivisionError on line 12.
       Could we return 0.0 in that case, and add a test for it?"
```

Comment on the code, not the person ("this function" rather than "you"). Ask questions when unsure ("What happens if the file is missing?"). Mark the weight of each comment: a prefix such as `nit:` for minor optional points and `blocking:` for must-fix issues makes the author's job clear. Praise good work too.

### Automate and speed up

Humans should not argue about formatting. Use formatters and linters, and run tests and static analysis in **continuous integration** so every pull request gets the same automated checks. Respond to review requests promptly: slow reviews push authors to make bigger, riskier changes. Reviewers can read changes as a unified **diff**, in which lines beginning with `+` were added and lines beginning with `-` were removed, with `+++` and `---` marking the file headers.

@example
title: Reviewing a small change
problem: A pull request adds this function. Write the review comments you would leave.

```python
def average(items):
    total = 0
    for i in range(len(items)):
        total = total + items[i]
    return total / len(items)
```
step: Correctness first: for an empty list, `len(items)` is 0 and the division raises `ZeroDivisionError`. This is a blocking issue unless callers guarantee non-empty input; ask which behavior is intended.
step: Tests: the description mentions none. Ask for tests for an empty list, a single item and negative numbers.
step: Readability (a nit): `for item in items:` is simpler than indexing, and `sum(items)` expresses the intent directly. Mark this `nit:`.
step: Write the comments as specific and actionable: "blocking: `average([])` raises ZeroDivisionError. Should it return 0.0 or raise ValueError? Please decide and add a test."
step: End with a positive note about what is good (clear name, small function) so the review is balanced.
answer: One blocking comment (empty list), one request for tests, one nit about `sum`, plus encouragement.

@example
title: Counting changes in a diff
problem: How many lines were added and how many removed in this diff hunk?

```text
--- a/app.py
+++ b/app.py
@@ -1,4 +1,4 @@
 def greet(name):
-    return "Hello " + name
+    return f"Hello, {name}!"

 print(greet("Sam"))
```
step: Ignore the file header lines `---` and `+++` and the hunk header starting with `@@`; they are not content changes.
step: Lines starting with a space (`def greet`, the blank line, and `print`) are unchanged context.
step: One line starts with `-` (the old return), so one line was removed.
step: One line starts with `+` (the new return), so one line was added.
answer: 1 line added, 1 line removed.

@mistakes
- Submitting a huge pull request mixing a feature, a refactor and formatting changes, which no one can review well.
- Giving vague or personal comments ("sloppy", "why would you do this?") instead of specific, actionable ones about the code.
- Blocking a change over personal style preferences that a formatter or the team style guide does not require.
- Skimming the diff without reading the tests or running the change, so the reviewer approves what they did not examine.

@practice code
prompt: Write `diff_stats(diff_text)` that counts changes in a unified diff given as one string. Return a tuple `(added, removed)`. A line counts as added if it starts with `+` but not `+++`, and removed if it starts with `-` but not `---`. Lines starting with a space, `@@`, or anything else are ignored. An empty string gives `(0, 0)`.
starter:
```python
def diff_stats(diff_text):
    pass
```
tests:
```python
d = "--- a/x.py\n+++ b/x.py\n@@ -1,2 +1,3 @@\n a\n-b\n+c\n+d\n"
assert diff_stats(d) == (2, 1)
assert diff_stats("") == (0, 0)
assert diff_stats(" context only\n more context\n") == (0, 0)
assert diff_stats("+one\n+two\n+three") == (3, 0)
assert diff_stats("-a\n--- header\n+++ header\n") == (0, 1)
```
model:
```python
def diff_stats(diff_text):
    added = 0
    removed = 0
    for line in diff_text.splitlines():
        if line.startswith("+") and not line.startswith("+++"):
            added += 1
        elif line.startswith("-") and not line.startswith("---"):
            removed += 1
    return added, removed
```
hint: Use `diff_text.splitlines()` and test each line with `startswith`.
hint: Exclude the header lines by checking for `+++` and `---` before counting.
solution: Loop over the lines, increment `added` for a line starting with `+` that is not a `+++` header, and `removed` for one starting with `-` that is not a `---` header. Everything else is context.

@practice text
prompt: A reviewer reads this function, meant to return the last `n` items of a list. Type the exact output of the program, which shows a bug the reviewer should catch.

```python
def last_n(items, n):
    return items[-n:]

print(last_n([1, 2, 3, 4], 2))
print(last_n([1, 2, 3, 4], 0))
```
answer:
```
[3, 4]
[1, 2, 3, 4]
```
check: run("def last_n(items, n):\n    return items[-n:]\n\nprint(last_n([1, 2, 3, 4], 2))\nprint(last_n([1, 2, 3, 4], 0))\n")
hint: Evaluate `items[-0:]`, remembering that `-0` is just `0`.
solution: `items[-0:]` is `items[0:]`, the whole list, so asking for zero items returns everything. A review comment should flag the edge case `n = 0` and request a test (a fix is `items[len(items) - n:]` when `n <= len(items)`, with clear handling of larger `n`).

@practice self
prompt: Review this pull request. Its description says only "add discount feature". Write at least four review comments, labelling each blocking or nit, and say whether you would approve it.

```python
def apply_discount(price, percent):
    # percent is like 10 for 10 percent
    new_price = price - price * percent / 100
    print("discounted price is", new_price)
    return new_price
```
solution: 1. blocking: no validation. `percent` of 150 or -20 gives a negative price or a price increase; define valid range (0 to 100) and raise `ValueError`. 2. blocking: no tests; ask for tests for 0 percent, 100 percent and an out-of-range value. 3. blocking: money in floating point accumulates rounding error; use integer cents or `Decimal`, and decide the rounding rule. 4. nit: the `print` mixes output with logic; remove it or use logging, so callers decide what to show. 5. The description does not say why or how it was tested; ask for a story link and for the rounding behavior to be documented. Decision: request changes, with thanks for the clear name and the explanatory comment.
rubric: Finds the missing input validation (range of `percent`) and names the consequence.
rubric: Asks for tests and notes the missing description.
rubric: Raises at least one further real issue (floating-point money, `print` in a function, rounding rule).
rubric: Labels comments as blocking or nit, writes them politely and specifically, and gives a decision.
hint: Try the inputs 0, 100, 150 and -20, and ask what could go wrong with money.

@quiz code
prompt: Write `size_category(added, removed)` for a pull-request bot: let `changed = added + removed`. Return `"small"` if `changed <= 50`, `"medium"` if `changed <= 400`, and `"large"` otherwise. Raise `ValueError` if either argument is negative.
starter:
```python
def size_category(added, removed):
    pass
```
tests:
```python
assert size_category(10, 5) == "small"
assert size_category(30, 20) == "small"
assert size_category(30, 21) == "medium"
assert size_category(400, 0) == "medium"
assert size_category(300, 101) == "large"
assert raises(ValueError, size_category, -1, 5)
assert raises(ValueError, size_category, 5, -1)
```
model:
```python
def size_category(added, removed):
    if added < 0 or removed < 0:
        raise ValueError("counts must not be negative")
    changed = added + removed
    if changed <= 50:
        return "small"
    if changed <= 400:
        return "medium"
    return "large"
```
hint: Sum the two counts and compare the total with 50 and 400, using `<=`.
solution: Validate first, compute `changed`, then test the thresholds in increasing order with `<=` so that exactly 50 is small and exactly 400 is medium.
