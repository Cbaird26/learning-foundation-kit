@article
Software design is the art of deciding *where code lives*. Requirements say what the system must do; design divides it into parts so that people can understand, change and test each part without understanding all the others. Since maintenance dominates the cost of software, the best design is the one whose likely changes touch the fewest places.

### Abstraction and information hiding

An **abstraction** presents what something does and omits how. A **module** (a function, class, package or service) has an **interface** (what callers may use) and an **implementation** (everything else). **Information hiding** means a module keeps its design decisions, such as its data layout or algorithm, private behind the interface. If callers depend only on the interface, the implementation can change without breaking them.

```python
class Account:
    def __init__(self, balance=0):
        self._balance = balance      # leading underscore: internal detail

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        self._balance += amount
```

Callers cannot set the balance to an arbitrary value by accident, and the class could later store a list of transactions instead, with no change for callers. (Python marks internals by convention, with `_name`, rather than enforcing privacy.)

### Cohesion and coupling

**Cohesion** is how strongly the parts of one module belong together. A `PriceCalculator` that only calculates prices is cohesive; a `Utils` class mixing date parsing, email and tax rules is not. **Coupling** is how much one module depends on the internals of another. The goal is **high cohesion and low coupling**: changes stay local. Signs of tight coupling are reaching into another object's fields, sharing global variables, and one class constructing the concrete classes it uses.

### SOLID

Five widely taught principles for object-oriented design:

- **S**ingle responsibility: a class should have one reason to change.
- **O**pen/closed: open for extension, closed for modification; add behavior by adding code, not by editing tested code.
- **L**iskov substitution: a subclass must be usable wherever its base class is expected without surprising the caller.
- **I**nterface segregation: prefer several small interfaces to one large one, so clients depend only on what they use.
- **D**ependency inversion: high-level modules should depend on abstractions, not on concrete low-level modules.

These are heuristics, not laws; they can be over-applied into needless layers. Also prefer **composition over inheritance**: build behavior by holding other objects rather than extending a class just to reuse code.

### Dependency injection

A class that creates its own collaborator is hard to change and hard to test:

```python
class Checkout:
    def __init__(self):
        self.gateway = RealPaymentGateway()   # hard-wired
```

With **dependency injection** the collaborator is passed in:

```python
class Checkout:
    def __init__(self, gateway):
        self.gateway = gateway                # any object with charge()

    def pay(self, cents):
        return "paid" if self.gateway.charge(cents) else "declined"
```

Production code passes the real gateway; a test passes a simple fake. This applies the dependency-inversion principle: `Checkout` depends on "something with a `charge` method", not on a particular payment company.

@example
title: Spotting a single-responsibility violation
problem: A class `Invoice` calculates totals, formats a PDF and sends it by email. Why is this a design problem, and how would you divide it?
step: List the reasons the class might change: the tax rules change (calculation), the layout changes (formatting), the mail provider changes (delivery). That is three reasons to change.
step: A class with three reasons to change violates single responsibility and has low cohesion: a layout tweak risks breaking tax logic.
step: Split it into `InvoiceCalculator` (totals), `InvoiceFormatter` (layout) and `InvoiceMailer` (delivery), each with a small interface.
step: Add a small coordinating function that calls the three in order. Each part can now be tested and replaced alone.
answer: Split into calculator, formatter and mailer, one reason to change each.

@example
title: Testing with an injected fake
problem: Using the injected `Checkout` above, show how a test can check that a declined card is reported, without a real payment service.
step: Write a fake with the same `charge` method that records its calls and returns a chosen result:

```python
class FakeGateway:
    def __init__(self, ok):
        self.ok = ok
        self.charged = []

    def charge(self, cents):
        self.charged.append(cents)
        return self.ok
```
step: Build `Checkout(FakeGateway(False))` and call `pay(500)`. The fake returns `False`, so `pay` returns `"declined"`.
step: Inspect the fake's `charged` list to confirm `charge` was called exactly once with `500`.
step: Nothing was charged and no network was used, yet the test exercised the real `Checkout` logic.
answer: `"declined"`, and `charged == [500]`.

@mistakes
- Confusing cohesion with coupling: cohesion is about the inside of a module, coupling about the connections between modules.
- Using inheritance only to reuse code, which creates a subclass that cannot honor the base class's contract (a Liskov violation).
- Creating concrete collaborators inside a class (`self.db = Database()`), which makes it impossible to substitute them in tests.
- Over-applying principles by adding interfaces and layers for changes that will never happen.

@quiz code
prompt: Write a class `Account` with a constructor `Account(balance=0)`, a read-only property `balance`, a method `deposit(amount)` and a method `withdraw(amount)`. Both methods raise `ValueError` if `amount` is zero or negative; `withdraw` also raises `ValueError` if `amount` exceeds the balance (and then leaves the balance unchanged). Assigning to `balance` directly must raise `AttributeError`.
starter:
```python
class Account:
    pass
```
tests:
```python
a = Account(100)
a.deposit(50)
assert a.balance == 150
a.withdraw(30)
assert a.balance == 120
assert Account().balance == 0
assert raises(ValueError, a.withdraw, 500)
assert a.balance == 120
assert raises(ValueError, a.deposit, 0)
assert raises(ValueError, a.withdraw, -5)
assert raises(AttributeError, setattr, a, "balance", 1)
```
model:
```python
class Account:
    def __init__(self, balance=0):
        self._balance = balance

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        self._balance += amount

    def withdraw(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        if amount > self._balance:
            raise ValueError("insufficient funds")
        self._balance -= amount
```
hint: Keep the balance in `self._balance` and expose it only through a property without a setter.
hint: Validate the amount before changing the balance, so a failed call leaves the state unchanged.
solution: The leading underscore marks the field as internal, and a property with no setter makes `account.balance = 1` raise `AttributeError`. Each method validates first and mutates last, so an invalid call changes nothing.
