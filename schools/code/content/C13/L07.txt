@article
**Verification** asks "did we build the product right?" (does the code meet its specification); **validation** asks "did we build the right product?" (does it meet the users' needs). Testing mainly serves verification, and acceptance criteria connect it to validation. A test is code that runs other code and reports pass or fail, so it keeps checking long after its author has moved on. The value of a test suite is **confidence to change code**: if the suite is trustworthy, you can refactor or add features and learn within minutes whether you broke something.

### Levels of tests

- A **unit test** exercises one small unit (a function or class) in isolation, with its collaborators replaced. It is fast (milliseconds) and points directly at the faulty code.
- An **integration test** checks that several units or components work together: your code with a real database, a queue, or a service boundary. It finds interface mistakes unit tests cannot, but is slower and harder to diagnose.
- A **system test** (end-to-end test) runs the whole deployed system through its external interface, such as a browser driving the web application. It gives the most realism, and is the slowest and most fragile.
- An **acceptance test** checks a requirement from the customer's viewpoint, often written from a story's Given-When-Then criteria; it can be implemented as a system test.

### The test pyramid

Because lower-level tests are faster, cheaper and more precise, a healthy suite looks like a pyramid: **many unit tests, fewer integration tests, and few end-to-end tests**. An inverted pyramid (mostly slow end-to-end tests) gives slow feedback, many false failures and hard debugging. Some organizations classify tests by size (small: one process, no network; medium: one machine; large: many machines) rather than by what they cover. The exact ratio, say 70/20/10, is a rule of thumb, not a law.

### Test doubles

To isolate a unit you replace its collaborators with **test doubles**: a **stub** returns canned answers; a **fake** is a simplified working implementation (an in-memory database); a **mock** records calls so the test can verify interactions. Prefer fakes and real objects where practical: tests that verify exactly which internal methods were called break whenever the implementation changes, even when behavior is correct. Test *behavior* (observable results), not implementation.

```python
import unittest


def add_tax(cents, percent):
    return cents + round(cents * percent / 100)


class AddTaxTest(unittest.TestCase):
    def test_adds_percentage(self):
        self.assertEqual(add_tax(1000, 20), 1200)

    def test_zero_rate_changes_nothing(self):
        self.assertEqual(add_tax(1000, 0), 1000)


if __name__ == "__main__":
    unittest.main()
```

Run it with `python -m unittest` (or `python -m unittest -v` for names). Name tests for the behavior they check, and keep each test short, with one reason to fail.

### Reliability and coverage

A **flaky test** passes and fails on the same code (because of timing, random data, shared state or the network). Flaky tests destroy trust: people learn to ignore red builds. Fix or delete them. A **regression test** is written when a bug is found, to fail before the fix and pass after, so the bug cannot return silently. **Code coverage** reports which lines (or branches) ran during tests. Low coverage shows untested code, but high coverage does not show good tests: a test that runs a line without asserting anything adds coverage and no safety. Use coverage to find gaps, never as the goal. **Test-driven development** (TDD) writes a failing test first, then the code, then refactors.

@example
title: Choosing test levels for a feature
problem: A shopping site adds "apply discount code". Decide which tests to write and at which level.
step: The pricing rule (10% off, never below zero, expired codes rejected) is pure logic: cover it with many fast unit tests, including boundaries.
step: Code lookup uses a database: write a few integration tests with a real test database to verify the query and the mapping work.
step: The whole flow (enter code in the browser, see the new total) is the acceptance criterion: write one or two end-to-end tests for the happy path and the expired code.
step: Result: many unit tests, a handful of integration tests, two system tests, a pyramid. Each failure is easy to locate because most tests are small.
answer: Unit tests for the rule, integration tests for the database, two end-to-end tests for the flow.

@example
title: Isolating a unit with a mock
problem: `greet_user(client, user_id)` should return `"Hello, <name>!"` using `client.get_user(user_id)`, which returns a dict with a `"name"` key. Write the function and a test that needs no real client.
step: Write the function so the client is a parameter (injected):

```python
def greet_user(client, user_id):
    user = client.get_user(user_id)
    return f"Hello, {user['name']}!"
```
step: In the test, create a mock client and set what `get_user` returns:

```python
from unittest.mock import Mock

client = Mock()
client.get_user.return_value = {"name": "Ada"}
```
step: Call `greet_user(client, 7)` and assert the result is `"Hello, Ada!"`.
step: Optionally check that the interaction happened once: `client.get_user.call_count == 1`. Do this sparingly; the result is the behavior that matters.
answer: `"Hello, Ada!"`, with no network or real client.

@mistakes
- Writing mostly slow end-to-end tests, so feedback takes an hour and failures are hard to diagnose.
- Treating 100% code coverage as proof of quality although tests can run code without asserting anything.
- Over-mocking: asserting on internal calls so every refactoring breaks tests even though behavior is unchanged.
- Leaving flaky tests in the suite, which teaches the team to ignore failures.

@quiz code
prompt: Write `retry(func, attempts)` that calls `func()` with no arguments up to `attempts` times. It returns the first value `func` returns. If `func` raises an exception, try again; if the last attempt also raises, let that exception propagate. Raise `ValueError` if `attempts` is less than 1.
starter:
```python
def retry(func, attempts):
    pass
```
tests:
```python
calls = []


def flaky():
    calls.append(1)
    if len(calls) < 3:
        raise RuntimeError("temporary")
    return "ok"


assert retry(flaky, 5) == "ok"
assert len(calls) == 3
assert retry(lambda: 5, 1) == 5
count = []


def always_fails():
    count.append(1)
    raise KeyError("x")


assert raises(KeyError, retry, always_fails, 2)
assert len(count) == 2
assert raises(ValueError, retry, lambda: 1, 0)
```
model:
```python
def retry(func, attempts):
    if attempts < 1:
        raise ValueError("attempts must be at least 1")
    for attempt in range(attempts):
        try:
            return func()
        except Exception:
            if attempt == attempts - 1:
                raise
```
hint: Loop `attempts` times; return inside `try`, and re-raise only on the last attempt.
solution: Validate `attempts`, then loop. A successful call returns immediately; a failure is swallowed unless it was the last attempt, in which case a bare `raise` re-raises that same exception.
