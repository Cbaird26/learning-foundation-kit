@article
Plan-driven processes assume that you can specify the product in advance. Many products cannot be specified that way: users discover what they want by using early versions. **Agile** methods respond with short cycles of building, showing and adjusting. The 2001 **Agile Manifesto** states four values, valuing the items on the left more than those on the right (while still valuing the right):

- individuals and interactions over processes and tools
- working software over comprehensive documentation
- customer collaboration over contract negotiation
- responding to change over following a plan

Agile is a family of methods (Scrum, Kanban, Extreme Programming and others) built on these values, not a single process. Common engineering practices that go with it include continuous integration, automated tests, pair programming and frequent releases.

### Scrum

**Scrum** is a lightweight framework for a small team to deliver value in fixed-length iterations called **Sprints**. As described in the 2020 Scrum Guide:

- **Accountabilities**: the **Product Owner** is accountable for maximizing the value of the product and for managing the **Product Backlog** (the ordered list of what might be built); the **Scrum Master** is accountable for establishing Scrum and helping the team improve; the **Developers** are accountable for creating a usable **Increment** each Sprint. Together they form one Scrum Team, usually ten or fewer people.
- **Events**: the **Sprint** itself (one month or less, with a fixed length), **Sprint Planning** (why is this Sprint valuable, what can be done, how will it be done), the **Daily Scrum** (a 15-minute event for Developers to inspect progress toward the Sprint Goal and adapt the plan), the **Sprint Review** (inspect the Increment with stakeholders and adapt the Product Backlog) and the **Sprint Retrospective** (the team inspects its own way of working and plans improvements).
- **Artifacts**, each with a commitment: the Product Backlog (commitment: the **Product Goal**), the **Sprint Backlog** (the Sprint Goal, the chosen items and the plan to deliver them) and the **Increment** (the **Definition of Done**, a shared statement of what "finished" means, such as "reviewed, tested, documented and deployed to staging").

Scrum rests on *empiricism*: transparency, inspection and adaptation. Work that does not meet the Definition of Done is not part of the Increment.

### Kanban

**Kanban** (as used in software) manages a continuous flow of work rather than fixed iterations. Its core practices: **visualize** the workflow on a board with columns such as To Do, In Progress, Review and Done; **limit work in progress (WIP)** per column; **manage flow** by measuring how long items take and removing blockers; make policies explicit; and improve incrementally. A WIP limit forces the team to finish work before starting more, which exposes bottlenecks: if Review is full, developers help review instead of pulling new items.

Key measures: **lead time** (from the request to delivery), **cycle time** (from starting work to delivery) and **throughput** (items completed per time unit). They are linked by **Little's Law**, which for a stable system says

$$\text{average lead time} = \frac{\text{average WIP}}{\text{average throughput}}.$$

Here WIP counts the items inside the part of the workflow you measure: every item from request to delivery for lead time, or only the items already started for cycle time. With 12 items between request and delivery and a throughput of 3 items per day, the average lead time is 4 days; to shorten lead time, reduce WIP or increase throughput. A **cumulative flow diagram** plots the count of items in each state over time and shows bottlenecks as widening bands.

### Scrum or Kanban?

Scrum suits product development where a team can commit to a goal for a few weeks and benefits from a regular rhythm of planning, review and retrospective. Kanban suits work that arrives unpredictably and must be handled continuously, such as support and operations, and it can be adopted without changing roles. Many teams combine them ("Scrumban"). Neither is magic: agile practices fail when they become rituals without feedback, when the Definition of Done is ignored, or when "agile" is used as an excuse for no planning or no documentation.

@example
title: Applying a WIP limit
problem: A Kanban board has the columns To Do, Doing (WIP limit 2) and Done. Doing already holds items C and D, and the developer wants to pull item A from To Do. What should happen?
step: Check the limit: Doing has 2 items and the limit is 2, so it is full.
step: The WIP rule says no new item may enter Doing until one leaves, so A stays in To Do.
step: The developer instead helps finish C or D (pairing, reviewing or unblocking it), so the item moves to Done.
step: Now Doing has 1 item and A can be pulled, and Doing has 2 again.
step: The limit did its job: it directed effort to finishing, not starting, which shortens lead time (Little's Law: lower WIP gives lower lead time at the same throughput).
answer: A may not move until a Doing item finishes.

@example
title: Mapping a team's week onto Scrum events
problem: A team runs two-week Sprints. Name the event for each activity: (a) planning what to build and how; (b) a 15-minute daily check; (c) showing the working Increment to stakeholders; (d) discussing how to improve the team's collaboration.
step: (a) deciding why the Sprint is valuable, which items to select and how to do them is Sprint Planning at the start.
step: (b) the 15-minute daily inspection of progress toward the Sprint Goal is the Daily Scrum.
step: (c) inspecting the Increment with stakeholders and adapting the Product Backlog is the Sprint Review.
step: (d) inspecting the team's own way of working and agreeing improvements is the Sprint Retrospective, held after the Review and before the next Sprint.
answer: (a) Sprint Planning, (b) Daily Scrum, (c) Sprint Review, (d) Sprint Retrospective.

@mistakes
- Treating the Daily Scrum as a status report to the manager instead of the Developers' planning meeting for the next day's work.
- Calling work "done" without the shared Definition of Done, so the Increment contains unfinished work.
- Setting a WIP limit and then ignoring it whenever the team is busy, which removes its benefit.
- Using "agile" as a reason to skip design, documentation or planning; agile favors adequate documentation and continuous planning, not none.

@practice code
prompt: A Kanban board is a dict mapping column names to lists of card names, for example `{"todo": ["a", "b"], "doing": ["c"], "done": []}`. Write `move_card(board, card, to_col, wip)` that moves `card` from its current column to the end of the `to_col` list, modifying `board` in place and returning `None`. `wip` is a dict mapping column names to WIP limits; a column missing from `wip` has no limit. Raise `ValueError` if the card is not on the board, if `to_col` is not a column of the board, or if the move would put more cards in `to_col` than its limit allows (in these cases the board must be left unchanged). If the card is already in `to_col`, do nothing.
starter:
```python
def move_card(board, card, to_col, wip):
    pass
```
tests:
```python
board = {"todo": ["a", "b"], "doing": ["c"], "done": []}
wip = {"doing": 2}
move_card(board, "a", "doing", wip)
assert board["doing"] == ["c", "a"]
assert board["todo"] == ["b"]
assert raises(ValueError, move_card, board, "b", "doing", wip)
assert board["todo"] == ["b"]
assert board["doing"] == ["c", "a"]
move_card(board, "a", "done", wip)
assert board["done"] == ["a"]
assert board["doing"] == ["c"]
assert raises(ValueError, move_card, board, "zzz", "done", wip)
assert raises(ValueError, move_card, board, "b", "nowhere", wip)
move_card(board, "b", "todo", wip)
assert board["todo"] == ["b"]
```
model:
```python
def move_card(board, card, to_col, wip):
    source = None
    for col, cards in board.items():
        if card in cards:
            source = col
            break
    if source is None:
        raise ValueError("no such card")
    if to_col not in board:
        raise ValueError("no such column")
    if source == to_col:
        return None
    limit = wip.get(to_col)
    if limit is not None and len(board[to_col]) >= limit:
        raise ValueError("WIP limit reached")
    board[source].remove(card)
    board[to_col].append(card)
    return None
```
hint: First find which column holds the card; then validate everything before changing the board.
hint: The move is blocked when the target already has `limit` cards, so test `len(board[to_col]) >= limit`.
solution: Locate the source column, validate the card, the target column and the WIP limit, return early when source and target are the same, and only then remove and append. Validating before mutating keeps the board unchanged on every error.

model:
```python
def wip_violations(board, wip):
    bad = []
    for col, limit in wip.items():
        if col in board and len(board[col]) > limit:
            bad.append(col)
    return sorted(bad)
```
hint: Loop over the limits, skip columns not on the board, and compare `len(board[col])` with the limit.
solution: For each limit, ignore unknown columns, and collect the column when its card count is strictly greater than the limit (equal to the limit is allowed). Sort the result for a deterministic order.
