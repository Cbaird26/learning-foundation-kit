@article
Version control records every change to a project so that people can work in parallel, undo mistakes and answer "who changed this and why?". A team's **workflow** is the agreement on how changes flow from one developer's computer into the shared line of development. Choosing it well keeps integration cheap and the main branch always working.

### The commit graph

In Git, a **commit** is an immutable snapshot with a message and links to its **parent** commit(s). Commits therefore form a **directed acyclic graph**. A **branch** is only a named pointer to one commit; it moves forward when you commit while on it. `HEAD` says which branch (or commit) you are on. Because branches are cheap pointers, creating one costs nothing:

```bash
git switch -c fix-login        # create a branch and switch to it
git add login.py
git commit -m "Reject empty passwords at sign-in"
git push -u origin fix-login   # publish the branch and track it
```

(`git switch` and `git restore` were introduced as clearer alternatives to the overloaded `git checkout`; `git checkout -b fix-login` still works. New repositories commonly name the default branch `main`.)

### Common workflows

- **Centralized**: everyone commits directly to one shared branch. Simple, but unreviewed and unstable changes land immediately.
- **Feature branch with pull requests**: each change lives on a short-lived branch; a **pull request** (or merge request) asks for review and automated checks before it merges into `main`. This is the most common arrangement.
- **Trunk-based development**: everyone integrates into `main` (the trunk) at least daily, in small changes, using very short-lived branches or none. Unfinished work stays hidden behind **feature flags**. It needs strong automated tests and continuous integration, and it avoids painful long-lived merges.
- **Forking workflow**: contributors copy the repository (a fork), push to their copy and open a pull request to the original. Typical for open-source projects where contributors have no write access.
- **Gitflow**-style models use long-lived `develop` and `release` branches. They fit products with scheduled, versioned releases, but add merging overhead.

The longer a branch lives, the more it diverges and the harder the eventual merge. Whatever the workflow, keep changes small and integrate often.

### Integrating: merge, rebase, squash

Suppose `main` has commits A-B-C and your branch left from B with commits D and E.

- **Merge** (`git merge`) creates a new **merge commit** with two parents (C and E). History is preserved exactly as it happened. If `main` has not moved, Git can simply move the pointer forward, a **fast-forward**, and make no merge commit (`--no-ff` forces one).
- **Rebase** (`git rebase main`) replays D and E on top of C as *new* commits D' and E'. History becomes linear, but the commits are rewritten (new identifiers). Never rebase commits that others have already pulled; if you must update your own pushed branch afterwards, use `git push --force-with-lease`, which refuses to overwrite work you have not seen.
- **Squash** (`git merge --squash`, or the pull-request button of the same name) combines all of a branch's changes into one commit on `main`, giving a tidy history at the cost of the branch's individual steps.

### Conflicts and good commits

A **conflict** occurs when both sides changed the same lines. Git marks the file with `<<<<<<<`, `=======` and `>>>>>>>`; you edit it to the intended result, `git add` the file and continue (`git commit`, or `git rebase --continue`). Good commits are small, do one thing, and have a message that says *why*: an imperative summary line under about 50 characters, then a blank line and a body when needed.

@example
title: Merge versus rebase on the same history
problem: `main` has A-B-C. Branch `feature` left from B and has D and E. Show the history after integrating `feature` by merge and by rebase.
step: Before integrating, `main` points to C and `feature` points to E; their common ancestor (merge base) is B.
step: By merge: Git creates commit M with parents C and E and moves `main` to M. The graph keeps the fork and the join; D and E keep their identifiers.
step: By rebase (run on `feature`): Git replays D and E on top of C, creating D' and E'. `feature` now points to E', directly after C.
step: A fast-forward merge of `main` to E' then gives the linear history A-B-C-D'-E' with no merge commit.
step: Trade-off: merge preserves the true history and is safe on shared branches; rebase gives linear history but rewrites commits, so use it only on commits that are yours alone.
answer: Merge: A-B-C-M with D, E joined in. Rebase: A-B-C-D'-E'.

@example
title: Resolving a merge conflict
problem: Merging `main` into your branch leaves this in `greeting.py`. What do you do?

```text
<<<<<<< HEAD
GREETING = "Hello"
=======
GREETING = "Hi there"
>>>>>>> main
```
step: The section between `<<<<<<< HEAD` and `=======` is your branch's version; the section up to `>>>>>>> main` is the incoming one.
step: Decide the intended result with the other author if needed. Suppose you keep the incoming wording.
step: Edit the file to contain only `GREETING = "Hi there"`, deleting all three marker lines.
step: Run the tests, then `git add greeting.py` and finish with `git commit` (or `git merge --continue`).
answer: The file ends with the single line `GREETING = "Hi there"`, staged and committed.

@mistakes
- Rebasing commits that teammates have already pulled, which forces them to repair their histories.
- Leaving long-lived branches unmerged for weeks, so the final merge becomes a large and risky conflict.
- Committing conflict markers, or a half-resolved file, because the tests were not run before `git add`.
- Writing messages such as "fix stuff" that say neither what nor why changed.

@practice code
prompt: A repository history is a dict `parents` mapping each commit name to the list of its parent commit names (empty for a root commit). Write `merge_base(parents, a, b)`: return the best common ancestor of commits `a` and `b`. A commit counts as an ancestor of itself. Among all common ancestors, return the one that is not an ancestor of any other common ancestor; if there is none because the commits share no history, return `None`. In the tests the answer is unique.
starter:
```python
def merge_base(parents, a, b):
    pass
```
tests:
```python
parents = {"A": [], "B": ["A"], "C": ["B"], "D": ["B"], "E": ["C", "D"]}
assert merge_base(parents, "C", "D") == "B"
assert merge_base(parents, "E", "C") == "C"
assert merge_base(parents, "C", "C") == "C"
assert merge_base(parents, "D", "A") == "A"
other = {"X": [], "Y": ["X"], "P": [], "Q": ["P"]}
assert merge_base(other, "Y", "Q") is None
```
model:
```python
def ancestors(parents, commit):
    seen = {commit}
    stack = [commit]
    while stack:
        for p in parents[stack.pop()]:
            if p not in seen:
                seen.add(p)
                stack.append(p)
    return seen


def merge_base(parents, a, b):
    common = ancestors(parents, a) & ancestors(parents, b)
    best = [c for c in common
            if not any(c != d and c in ancestors(parents, d)
                       for d in common)]
    return sorted(best)[0] if best else None
```
hint: First write a helper that returns the set of all ancestors of a commit, including the commit itself.
hint: Intersect the two ancestor sets, then keep the member that no other member descends from.
solution: Compute each commit's ancestor set with a graph traversal, intersect them, and discard any common ancestor that is itself an ancestor of another common ancestor; the remaining one is the merge base. An empty intersection gives `None`.

@quiz code
prompt: Using the same `parents` dict convention (commit name to list of parent names), write `is_fast_forward(parents, current, target)` returning `True` when `current` is a proper ancestor of `target` (so moving a branch from `current` to `target` is a fast-forward), and `False` otherwise, including when they are the same commit.
starter:
```python
def is_fast_forward(parents, current, target):
    pass
```
tests:
```python
parents = {"A": [], "B": ["A"], "C": ["B"], "D": ["B"], "E": ["C", "D"]}
assert is_fast_forward(parents, "C", "E")
assert is_fast_forward(parents, "A", "E")
assert not is_fast_forward(parents, "D", "C")
assert not is_fast_forward(parents, "C", "C")
assert not is_fast_forward(parents, "E", "A")
```
model:
```python
def is_fast_forward(parents, current, target):
    if current == target:
        return False
    stack = [target]
    seen = {target}
    while stack:
        for p in parents[stack.pop()]:
            if p == current:
                return True
            if p not in seen:
                seen.add(p)
                stack.append(p)
    return False
```
hint: Walk backward from `target` through parents and see whether you reach `current`.
solution: Traverse the ancestors of `target` with a stack and a `seen` set; if `current` appears, it is a proper ancestor, so the move is a fast-forward. The explicit `current == target` check handles the same-commit case.
