@article
Software is never finished while it is used. **Maintenance** is everything done to software after its first delivery, and it usually consumes most of the lifetime cost. It comes in four kinds:

- **Corrective**: fixing defects found in use.
- **Adaptive**: changing software because its environment changed (a new operating system, a new tax law, an API that is retired).
- **Perfective**: adding features or improving performance and usability.
- **Preventive**: improving structure so that future changes are cheaper, which is where refactoring belongs.

Code is read far more often than it is written, so maintainability is a design goal from the start.

### Code smells

A **code smell** is a surface sign that the design may have a deeper problem. A smell is not a bug, since the code works, but it makes change risky. Common smells and their usual remedies:

| Smell | Symptom | Typical refactoring |
|---|---|---|
| Long function | does several things; needs comments to separate sections | Extract function |
| Duplicated code | the same logic copied in several places | Extract function, then reuse |
| Large class | many fields and responsibilities | Extract class |
| Long parameter list | five or more related parameters | Introduce parameter object |
| Magic number | unexplained literal such as `0.0825` | Replace with a named constant |
| Deep nesting | many levels of `if` | Guard clauses (early return) |
| Feature envy | a method uses another object's data more than its own | Move method |
| Primitive obsession | strings or ints stand for rich concepts | Introduce a small type |

### Refactoring

**Refactoring** is changing the internal structure of code *without changing its observable behavior*. It is not rewriting, and it is not adding features (do those in separate steps, ideally in separate commits). The discipline that makes it safe:

1. **Have tests** that pin down current behavior. If none exist, write **characterization tests**: call the code with a range of inputs, record what it does now (even if odd) and assert that. They protect you while you restructure.
2. Make **one small change** (rename, extract, move), run the tests, and commit. If the tests fail, undo the step instead of debugging a large change.
3. Keep the **interface** the same for callers during the step, or update all callers in the same change.
4. Stop when the code is clear enough for the change you came to make.

A deeply nested function and its guard-clause form show a typical refactoring:

```python
# before
def label(n):
    if n is not None:
        if n >= 0:
            return "ok"
        else:
            return "negative"
    else:
        return "missing"

# after: same behavior, guard clauses
def label(n):
    if n is None:
        return "missing"
    if n < 0:
        return "negative"
    return "ok"
```

### Technical debt

**Technical debt** is a metaphor: a shortcut that speeds delivery now (a quick hack, a skipped test, outdated documentation) is like a loan. You may repay the **principal** later by fixing it, but until then you pay **interest**: every change in that area is slower and riskier. Debt can be *deliberate and prudent* ("ship the prototype, clean up before launch"), or *inadvertent* (we did not know better then). Debt is acceptable when taken knowingly, recorded (in the backlog, with a link to the code) and repaid before the interest outgrows the benefit. Unrecorded debt compounds silently until each feature takes many times as long as it should.

Ways to manage it: reserve a share of each sprint for cleanup; follow the **boy scout rule** (leave code a little cleaner than you found it); refactor in the area you are about to change, not everywhere at once; track smells with static analysis and review comments; and for replacing a whole legacy system, migrate gradually (route one feature at a time to the new code) rather than rewriting everything in one risky release.

@example
title: Refactoring nested conditionals with guard clauses
problem: Refactor `access` so it behaves identically but is easier to read.

```python
def access(user):
    if user is not None:
        if user["active"]:
            if user["admin"]:
                return "admin"
            else:
                return "user"
        else:
            return "suspended"
    else:
        return "anonymous"
```
step: Pin down behavior with characterization tests: `None` gives `"anonymous"`; an inactive user gives `"suspended"` (even if admin); an active admin gives `"admin"`; an active non-admin gives `"user"`.
step: Handle the first exceptional case with a guard: `if user is None: return "anonymous"`. Run the tests.
step: Add the next guard: `if not user["active"]: return "suspended"`. Run the tests.
step: What remains is the normal path, and the `if user["admin"]` check becomes the last two lines:

```python
def access(user):
    if user is None:
        return "anonymous"
    if not user["active"]:
        return "suspended"
    return "admin" if user["admin"] else "user"
```
step: Re-run the tests, commit with a message such as "Refactor access() with guard clauses; no behavior change".
answer: Three guards and a final conditional expression with identical behavior.

@mistakes
- Mixing refactoring with feature work in one change, so a failing test cannot be traced to its cause.
- Refactoring without tests, which makes it impossible to know whether behavior changed.
- Making a huge refactoring in one step instead of many small, tested steps.
- Treating all technical debt as bad, or never recording the debt deliberately taken, so no one repays it.

    "regular": [(5, 10), (2, 5), (0, 0)],
    "premium": [(5, 20), (0, 15)],

```python

    sign = "-" if cents < 0 else ""
    dollars, rest = divmod(abs(cents), 100)
    return f"{sign}${dollars}.{rest:02d}"

```python
def process(o):
    t = 0
    for i in o["items"]:
        t = t + i["price"] * i["qty"]
    if o["country"] == "US":

Characterization tests first: US, DE, another country, an empty cart. Commit message: "Refactor order total: name tax rates, extract subtotal; no behavior change". Changelog note: "Internal: order total calculation restructured (tax rates in a table). No change to results." The table also makes a new country a one-line change.

rubric: The rewritten code keeps behavior, including the default of no tax for unknown countries, and mentions characterization tests before refactoring.
rubric: The commit message states what changed and says that behavior is unchanged.
