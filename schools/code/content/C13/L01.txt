@article
A program that one person writes in an afternoon to answer one question is *programming*. A payroll system that dozens of people change for fifteen years while thousands of employees depend on it is *software engineering*. The difference is not the language or the cleverness of the code. It is that three things grow at once: **time** (the code outlives its authors and its original requirements), **scale** (more code, more users, more data) and **people** (many contributors who must coordinate). Software engineering is the application of systematic, disciplined, measurable approaches to developing, operating and maintaining software, so that it keeps working as time, scale and team size grow.

### The software life cycle

Every successful product passes through the same kinds of activity, whatever the process is called:

| Activity | Question it answers | Typical output |
|---|---|---|
| Requirements | What problem must the software solve, for whom? | Stories, specifications, acceptance criteria |
| Design | How will it be structured? | Architecture, interfaces, diagrams |
| Implementation | How do we write it? | Source code, reviews |
| Verification | Does it do what was required? | Tests, inspections, test reports |
| Deployment | How does it reach users? | Releases, pipelines, configuration |
| Maintenance | How do we keep it useful? | Fixes, enhancements, refactoring |

Maintenance is not an afterthought. For most products, far more effort goes into changing existing code than into writing the first version, so decisions made early are judged by how cheaply they let the code change later.

### Process models

A **process model** says how those activities are ordered and repeated.

- **Waterfall** performs each activity once, in sequence, with a review between phases. It suits work where requirements are stable and well understood, or where regulation demands documented evidence at each gate, such as some safety-critical systems. Its weakness: a mistake in requirements is discovered only at verification, when it is expensive to fix.
- **Iterative and incremental** development repeats the cycle in short rounds. Each round produces a working increment that real users or stakeholders can react to. Feedback arrives early, so wrong assumptions are corrected while they are cheap.
- **Spiral** adds explicit risk analysis at the start of every iteration; the riskiest parts are tackled first.
- **Agile** methods (week 9) are iterative processes that value working software, collaboration and responding to change, usually in cycles of one to four weeks.
- **DevOps** practices, such as continuous integration and continuous delivery, automate build, test and release so that deployment is routine rather than an event.

No model is "correct" in general. You pick one by asking where the largest risk lies: in *what* to build (favor iteration and feedback), in *whether it is safe* (favor documented gates and heavy verification), or in *how to ship it reliably* (favor automation).

### Why defects get cheaper to fix early

A defect found while writing a requirement costs a conversation. The same defect found in production may cost an outage, a data repair and lost trust, because by then code, tests, documentation and user habits all depend on it. This is why engineering practice moves checks earlier: reviews, automated tests on every change, and short feedback loops. A simple measure used to track quality is **defect density**, defects per thousand lines of code (KLOC):

```python
def defect_density(defects, lines):
    return defects / (lines / 1000)

print(defect_density(7, 2500))  # 2.8
```

Metrics like this are signals, not goals: a team that is rewarded for a low number can game it by not looking for defects.

@example
title: Choosing a process for a project
problem: A team will build a mobile app for a start-up that has not yet found its customers. A second team will build the control software for an infusion pump, to be certified by a regulator. Which process model fits each, and why?
step: Find the dominant risk of each project. For the start-up, the risk is building something nobody wants: the requirements are unknown and will change.
step: Unknown, changing requirements favor an iterative, agile process: release a small increment, observe real use, adjust the next iteration.
step: For the pump, the dominant risk is harm to patients, and the regulator expects evidence: documented requirements, design reviews and traceable verification.
step: That favors a plan-driven process with gates (waterfall or a V-model) and heavy verification, although even this team may build and test increments internally.
step: State the conclusion with its condition: iterative for the start-up because requirements are unstable; plan-driven for the pump because safety and certification demand documented evidence at each gate.
answer: Start-up: iterative/agile. Pump: plan-driven with gated verification.

@example
title: Computing defect density
problem: A release has 2500 lines of code and 7 defects were found in it. What is the defect density per KLOC, and what does Python print for `defect_density(7, 2500)`?
step: Convert lines to thousands of lines: `2500 / 1000 = 2.5` KLOC.
step: Divide defects by KLOC: `7 / 2.5 = 2.8`.
step: In code, `defects / (lines / 1000)` performs exactly those two operations, so `defect_density(7, 2500)` returns `2.8`.
step: Interpret it carefully: the number compares releases of similar scope; it does not say which defects matter most.
answer: 2.8 defects per KLOC

@mistakes
- Treating software engineering as "programming with more paperwork" instead of managing change over time, scale and people.
- Believing waterfall is always wrong or agile is always right; the choice depends on the project's risks and constraints.
- Counting only the first release as the cost of a system and forgetting that maintenance usually dominates the total effort.
- Using a metric such as defect density as a target to be minimized rather than a signal to be interpreted.

Write `next_phase(phase)` that returns the phase that follows `phase`, returns `None` for `"maintenance"` (the last phase), and raises `ValueError` for any string that is not a phase name.
starter:
```python
PHASES = ["requirements", "design", "implementation",
          "verification", "deployment", "maintenance"]


def next_phase(phase):
    pass
```
tests:
```python
assert next_phase("requirements") == "design"
assert next_phase("verification") == "deployment"
assert next_phase("deployment") == "maintenance"
assert next_phase("maintenance") is None
assert raises(ValueError, next_phase, "testing")
```
model:
```python
PHASES = ["requirements", "design", "implementation",
          "verification", "deployment", "maintenance"]


def next_phase(phase):
    if phase not in PHASES:
        raise ValueError(f"unknown phase: {phase}")
    i = PHASES.index(phase)
    if i == len(PHASES) - 1:
        return None
    return PHASES[i + 1]
```
hint: `PHASES.index(phase)` gives the position of a phase in the list.
hint: The last phase has no successor; check for it before adding 1 to the index.
solution: Check membership first so unknown names raise `ValueError`, find the index, return `None` when it is the last index, and otherwise return the element at `index + 1`.
