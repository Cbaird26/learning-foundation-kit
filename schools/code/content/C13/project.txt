### Week by week

**Weeks 1 and 2: process and requirements.** Software engineering is programming integrated over time, scale and people. The life cycle activities are requirements, design, implementation, verification, deployment and maintenance. Waterfall runs them once with gates; iterative and agile processes repeat them in short cycles; choose by the dominant risk. Requirements are functional or non-functional, and must be testable. A user story is *As a role, I want a goal so that a benefit*; check it against INVEST; attach Given-When-Then criteria.

**Weeks 3 and 4: design and UML.** Aim for high cohesion and low coupling, with information hiding. SOLID: single responsibility, open/closed, Liskov substitution, interface segregation, dependency inversion. Inject dependencies instead of creating them. Class diagrams show structure (association, aggregation, composition, inheritance, realization, dependency, multiplicity); sequence diagrams show messages over time, with returns and `alt` fragments.

**Weeks 5 and 6: Git and review.** Commits form a graph and branches are pointers. Compare feature branches with pull requests, trunk-based development and forking. Merge preserves history, rebase rewrites it (never rebase shared commits), squash condenses. Review small changes against a checklist; write specific, kind, labelled comments; automate formatting and linting.

**Weeks 7 and 8: testing.** Many unit tests, fewer integration tests, few end-to-end tests. Use stubs, fakes and mocks to isolate units; avoid flaky tests; coverage finds gaps and does not prove quality. Derive tests from the specification: equivalence classes (one representative each, including invalid), boundary values (just below, on, and just above each edge), decision tables for combined conditions.

**Weeks 9 and 10: agile and planning.** The four Agile Manifesto values; Scrum's three accountabilities, five events and three artifacts with the Definition of Done; Kanban's visualization and WIP limits; Little's Law, lead time = WIP / throughput. Estimates are ranges, not promises; points are relative; PERT is $(o + 4m + p)/6$; forecast sprints as $\lceil B/v \rceil$; capacity is people times days times productive hours, minus absences; leave a buffer.

**Weeks 11 and 12: maintenance, documentation, ethics.** Maintenance is corrective, adaptive, perfective or preventive. Refactor in small tested steps without changing behavior; use characterization tests when none exist. Technical debt has principal and interest and should be recorded. Documentation lives next to code; ADRs record decisions; SemVer: major for breaking, minor for new compatible features, patch for fixes. Apply the ACM Code of Ethics; know permissive versus copyleft licenses (not legal advice).

### Common errors

Treating estimates as promises; writing stories as solutions; forgetting invalid equivalence classes; testing the middle of a range but not its edges; deriving expected values from the code being tested; rebasing shared history; mixing refactoring with feature work; using `>` for `>=` at a boundary; counting unfinished stories in velocity; forgetting that SemVer resets lower numbers.

@exam code
prompt: In the room-booking project, bookings for one room on one day are stored as a list of `(start, end)` integer pairs, where each booking is the half-open interval from `start` up to but not including `end`. Write `has_conflict(existing, start, end)` returning `True` if a new request from `start` to `end` overlaps any booking in `existing`, and `False` otherwise. Bookings that only touch (one ends exactly when the other starts) do not conflict. Raise `ValueError` unless `0 <= start < end <= 24`. Do not modify `existing`.
starter:
```python
def has_conflict(existing, start, end):
    pass
```
tests:
```python
booked = [(9, 11), (14, 15)]
assert has_conflict(booked, 10, 12)
assert has_conflict(booked, 8, 10)
assert has_conflict(booked, 9, 11)
assert has_conflict(booked, 8, 20)
assert not has_conflict(booked, 11, 14)
assert not has_conflict(booked, 7, 9)
assert not has_conflict([], 0, 24)
assert has_conflict([(0, 24)], 23, 24)
assert raises(ValueError, has_conflict, booked, 5, 5)
assert raises(ValueError, has_conflict, booked, 20, 25)
assert booked == [(9, 11), (14, 15)]
```
model:
```python
def has_conflict(existing, start, end):
    if not (0 <= start < end <= 24):
        raise ValueError("need 0 <= start < end <= 24")
    for s, e in existing:
        if start < e and s < end:
            return True
    return False
```
hint: Two half-open intervals overlap exactly when each one starts before the other ends.
hint: Use strict comparisons so that touching intervals do not count: `start < e and s < end`.
solution: Validate the request, then compare it with every existing booking using the overlap rule `start < e and s < end`. Strict inequalities make touching intervals non-conflicting, and nothing in `existing` is modified.

@exam num
prompt: A team has a backlog of 90 story points and its last three sprints had velocities of 18, 22 and 20. Using the average velocity and rounding up to a whole number of sprints, how many sprints does it forecast? (Then think about what range you would report; give only the number.)
answer: 5
check: -(-90 * 3 // (18 + 22 + 20))
hint: The average velocity is the sum of the three velocities divided by three.
solution: The average velocity is `(18 + 22 + 20) / 3 = 20`. `90 / 20 = 4.5`, rounded up to 5 sprints. With the slowest sprint (18) the forecast is `90 / 18 = 5`, and with the fastest (22) it is `90 / 22 = 4.09`, which rounds up to 5, so the range is also 5 sprints.
