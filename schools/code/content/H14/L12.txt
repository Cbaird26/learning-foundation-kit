@article
A 10-line program can be written straight from your head. A 150-line program cannot: without a plan you end up with tangled code that is hard to test and harder to fix. The skills in this lesson are what turn the individual tools of the course (functions, lists, dictionaries, files, tests) into a working larger program.

### Step 1: Say what the program must do

Write a few sentences about the **inputs** (a text file, user typing, a list), the **outputs** (a report, a file, a number) and the **rules** in between. Then add concrete examples with the exact answer expected. Examples are the seeds of your tests.

### Step 2: Choose the data

Decide how information will be stored while the program runs, using the structures you know: a list of dictionaries for records, a dictionary of totals per category, a set of unique values. Then write what a single record looks like, for example `("pens", "office", 12.5)` for (item, category, amount).

### Step 3: Break it into functions

**Top-down design:** start with the whole task in one line and split it into the main steps; split each step further until every piece is small enough to write in a few lines and name clearly. For a spending report you might get:

1. `parse_record(line)`: one text line to one record;
2. `load_records(lines)`: all lines to a list of records, skipping bad lines;
3. `summarize(records)`: records to a dictionary of totals per category;
4. `format_report(totals)`: totals to the text of the report;
5. `main()`: read the data, call the functions above, print the report.

Write down each function's **signature** (name and parameters), what it returns, and one example. This list is your outline.

### Separate input, processing and output

Functions that compute and *return* values are easy to test with `assert`. Functions that read the keyboard, open files or print are awkward to test. So keep these parts thin and put the real work into functions that take data and return data. A typical shape:

```python
def parse_line(line):
    name, score = line.split(",")
    return name.strip(), int(score)

def load(lines):
    return [parse_line(line) for line in lines if line.strip()]

def average(records):
    return sum(score for _, score in records) / len(records)

def report(records):
    return f"{len(records)} students, average {average(records):.1f}"

def main():
    lines = ["ana, 90", "ben, 72", "", "cy, 81"]
    print(report(load(lines)))

if __name__ == "__main__":
    main()
```

The last two lines run `main()` only when the file is run directly, not when another file imports it, which lets you import the functions into a test file.

### Step 4: Build in small steps

1. Write each function as a **stub** (`def summarize(records): pass`) so the whole structure exists and runs.
2. Take the functions one at a time. Write its tests first, then the code, and run all the tests after every change.
3. Connect the pieces in `main()` only when each piece works.
4. When something fails, you know the culprit is the last thing you changed.

Add a function whenever you see the same code twice or a block you can describe by a name. Keep each function short enough to read at a glance.

### Planning documents

For your own projects, a one-page plan (requirements, data, function list with signatures, test list, order of work) saves hours. In teams this is the first thing reviewed, because errors in a plan are far cheaper to fix than errors in finished code.

@mistakes
- Starting to type code before writing down the inputs, outputs and examples.
- Mixing input, computing and printing in one long function, which makes it impossible to test with `assert`.
- Writing all the code first and testing at the end, so a failure could be anywhere.
- Copy-pasting a block of code instead of turning it into a function with a parameter.

@practice text
prompt: What does this program print? Type the output exactly.

```python
def tidy(line):
    return line.strip().lower()

def parse(lines):
    return [tidy(line) for line in lines if tidy(line)]

print(parse(["  A ", "", "b", "   "]))
```
answer: ['a', 'b']
check: run("def tidy(line):\n    return line.strip().lower()\n\ndef parse(lines):\n    return [tidy(line) for line in lines if tidy(line)]\n\nprint(parse(['  A ', '', 'b', '   ']))\n")
hint: An empty string counts as false in the `if` of a comprehension.
solution: `tidy("  A ")` is `"a"`, `tidy("")` and `tidy("   ")` are empty strings, which are false and filtered out, and `tidy("b")` is `"b"`. The result is the list `['a', 'b']`.

@practice code
prompt: Write `parse_record(line)` for lines of the form `item,category,amount`. Return a tuple `(item, category, amount)` where item and category have surrounding spaces removed and `amount` is a float. For example `parse_record("pens, office, 12.50")` is `("pens", "office", 12.5)`. If the line does not have exactly three comma-separated fields, or the amount is not a number, raise `ValueError`.
starter:
```python
def parse_record(line):
    pass
```
tests:
```python
assert parse_record("pens, office, 12.50") == ("pens", "office", 12.5)
assert parse_record("ink,office,7") == ("ink", "office", 7.0)
assert parse_record(" tea , food , 3.25 ") == ("tea", "food", 3.25)
assert raises(ValueError, parse_record, "pens,office")
assert raises(ValueError, parse_record, "a,b,c,4")
assert raises(ValueError, parse_record, "pens,office,lots")
assert raises(ValueError, parse_record, "")
```
model:
```python
def parse_record(line):
    parts = line.split(",")
    if len(parts) != 3:
        raise ValueError("expected three fields")
    item = parts[0].strip()
    category = parts[1].strip()
    amount = float(parts[2])
    return (item, category, amount)
```
hint: Split at the commas and check how many parts you got before using them.
hint: Raise `ValueError` yourself when `len(parts) != 3`; `float(...)` raises `ValueError` by itself for text that is not a number.
solution: Split the line, raise `ValueError` unless there are exactly three parts, strip the first two, and convert the third with `float`. The empty string splits into one part, so it is rejected by the length check, and a non-number makes `float` raise `ValueError`.

@practice code
prompt: Write `summarize(records)` where `records` is a list of `(item, category, amount)` tuples. Return a dictionary mapping each category to the total of its amounts. An empty list gives `{}`.
starter:
```python
def summarize(records):
    pass
```
tests:
```python
records = [("pens", "office", 12.5), ("tea", "food", 3.0), ("ink", "office", 7.5)]
assert summarize(records) == {"office": 20.0, "food": 3.0}
assert summarize([]) == {}
assert summarize([("a", "x", 1.5)]) == {"x": 1.5}
assert summarize([("a", "x", 2.0), ("b", "x", -0.5)]) == {"x": 1.5}
```
model:
```python
def summarize(records):
    totals = {}
    for item, category, amount in records:
        totals[category] = totals.get(category, 0) + amount
    return totals
```
hint: This is the counting pattern, adding the amount instead of 1.
hint: Unpack each tuple in the `for` line, and use `totals.get(category, 0) + amount`.
solution: Use a dictionary of totals: for each record, add its amount to the total of its category, starting from `0` for a new category. The item name is not needed for the totals.

@quiz code
prompt: Write `format_report(totals)` where `totals` is a dictionary mapping category names to float totals. Return the report as one string with one line per category, in alphabetical order of the category, each line formatted as `category: amount` with the amount shown with exactly two decimals. Lines are separated by a newline character and there is no newline at the end. An empty dictionary gives `""`.
starter:
```python
def format_report(totals):
    pass
```
tests:
```python
assert format_report({"b": 2.5, "a": 10}) == "a: 10.00\nb: 2.50"
assert format_report({}) == ""
assert format_report({"food": 3.256}) == "food: 3.26"
assert format_report({"z": 1, "y": 0.5, "x": 0}) == "x: 0.00\ny: 0.50\nz: 1.00"
```
model:
```python
def format_report(totals):
    lines = []
    for category in sorted(totals):
        lines.append(f"{category}: {totals[category]:.2f}")
    return "\n".join(lines)
```
hint: Build a list of lines, one per category, in sorted order of the keys.
hint: `f"{amount:.2f}"` shows two decimals, and `"\n".join(lines)` puts newlines only between lines.
solution: Loop over `sorted(totals)` to get the categories in alphabetical order, format each line with `:.2f`, and join the lines with `"\n"`. Joining puts no newline after the last line, and an empty dictionary produces an empty list of lines and so the empty string.

@quiz mc
prompt: You are building a 150-line program made of eight functions. Which approach to building it is best?
choice: Write all eight functions, then run the program once at the end and fix whatever fails.
choice*: Create stubs for all functions, then write and test one function at a time, running the tests after every change.

hint: Which approach tells you quickly which change caused a failure?
solution: Writing and testing one function at a time means that when a test fails, the cause is almost certainly the last change. Testing only at the end makes bugs hard to locate, and a single big `main()` is hard to test.
