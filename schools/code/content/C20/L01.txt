@article
The web is a system of **clients** (usually browsers) that request **resources** from **servers**, which reply with responses. Every step follows a published protocol, so any browser can talk to any server. This week gives you the map you will use for the rest of the course.

### From URL to page

Typing `https://docs.example.org/guide/intro.html?lang=en#install` starts a chain of events:

1. The browser **parses the URL**: scheme `https`, host `docs.example.org`, port 443 (the default for `https`; `http` defaults to 80), path `/guide/intro.html`, query `lang=en`, fragment `install`.
2. **DNS** turns the host name into an IP address.
3. The browser opens a **TCP** connection (or, for HTTP/3, a **QUIC** connection over UDP) and, for `https`, performs a **TLS** handshake (TLS 1.3, RFC 8446, is the current version) that authenticates the server and encrypts the traffic.
4. The browser sends an **HTTP request**.
5. The server sends an **HTTP response**; the browser starts parsing it while it arrives.

The **fragment** (`#install`) never leaves the browser: it tells the browser which part of the page to scroll to or which element to focus. Everything else is used to build the request.

### HTTP messages

HTTP is a text-based request/response protocol (HTTP/1.1 is plain text; HTTP/2 and HTTP/3 carry the same semantics in a binary framing, described in RFC 9110 for semantics, RFC 9114 for HTTP/3 and RFC 9000 for QUIC). An HTTP/1.1 request is a start line, headers, an empty line and an optional body, with lines ending in `CRLF`:

```http
GET /guide/intro.html?lang=en HTTP/1.1
Host: docs.example.org
Accept: text/html
```

The reply has a status line, headers, an empty line and a body:

```http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Content-Length: 1256

<!doctype html>...
```

`Host` tells a server that serves several sites which one you mean. `Content-Type` says how to interpret the body, and `Content-Length` is its size in **bytes**.

### Methods and status codes

| Method | Meaning | Safe | Idempotent |
|---|---|---|---|
| `GET` | read a resource | yes | yes |
| `POST` | submit data, create | no | no |
| `PUT` | replace a resource | no | yes |
| `PATCH` | partially modify | no | not guaranteed |
| `DELETE` | remove | no | yes |

*Safe* means the request is not supposed to change server state; *idempotent* means repeating it has the same effect as sending it once. Status codes are grouped by first digit: **1xx** informational, **2xx** success (`200 OK`, `201 Created`, `204 No Content`), **3xx** redirection (`301`/`308` permanent, `302`/`307` temporary, `304 Not Modified`), **4xx** client error (`400`, `401`, `403`, `404`, `405`, `409`, `429`) and **5xx** server error (`500`, `503`). `307` and `308` keep the original method on the redirect; historically `301` and `302` let browsers change `POST` into `GET`.

### Statelessness

Each request is understood on its own. Anything that must persist between requests, such as "this user is signed in", is carried by **cookies** or tokens that the client sends back each time. You will build exactly that in week 11.

### What the browser does with the response

The browser parses the HTML into the **DOM** (a tree of elements), fetches linked CSS and parses it into the **CSSOM**, combines them into a render tree, computes **layout** (sizes and positions), and **paints** pixels. Scripts can change the DOM and trigger layout and paint again. Linked images, stylesheets and scripts are separate HTTP requests.

Python's `urllib.parse` module (`urlsplit`, `parse_qs`, `urljoin`) parses URLs exactly as this lesson describes, and it runs in the browser exercises.

@example
title: Dissecting a URL
problem: Name the parts of `https://docs.example.org/guide/intro.html?lang=en&v=2#install`, and say which parts the server receives.
step: The scheme is `https`, so the connection uses TLS and the default port is 443.
step: The host is `docs.example.org`; it is resolved with DNS and sent in the `Host` header.
step: The path is `/guide/intro.html`; the query string is `lang=en&v=2`, which is two `name=value` pairs joined by `&`.
step: The fragment is `install`. The request line becomes `GET /guide/intro.html?lang=en&v=2 HTTP/1.1`, so the fragment is not in it.
answer: The server receives the host, path and query; the fragment stays in the browser.

@example
title: Parsing a request line in Python
problem: Given `"GET /search?q=web HTTP/1.1"`, extract the method, the path and the query values.
step: The request line has three space-separated fields, so `method, target, version = line.split(" ")` gives `"GET"`, `"/search?q=web"` and `"HTTP/1.1"`.
step: Split the target into its parts with `urlsplit(target)`. Its `.path` is `/search` and its `.query` is `q=web`.
step: Decode the query with `parse_qs`, which returns a dictionary whose values are lists, because a name may repeat:

```python
from urllib.parse import urlsplit, parse_qs

line = "GET /search?q=web HTTP/1.1"
method, target, version = line.split(" ")
parts = urlsplit(target)
print(method, parts.path, parse_qs(parts.query))
```
step: This prints `GET /search {'q': ['web']}`.

@mistakes
- Believing the fragment (`#section`) is sent to the server; it is handled only by the browser.
- Using `301` or `302` when the method must be preserved on a redirect; `307` and `308` guarantee that.
- Computing `Content-Length` as the number of characters instead of the number of bytes, which differs for non-ASCII text in UTF-8.
- Calling `POST` idempotent or `GET` unsafe: repeating a `POST` may create two records, while `GET` must not change state.

model:
```python
from urllib.parse import urlsplit, parse_qs


def parse_request(raw):
    head = raw.split("\r\n\r\n", 1)[0]
    lines = head.split("\r\n")
    method, target, _version = lines[0].split(" ")
    headers = {}
    for line in lines[1:]:
        name, _, value = line.partition(":")
        headers[name.strip().lower()] = value.strip()
    parts = urlsplit(target)
    return method, parts.path, parse_qs(parts.query), headers
```
hint: Cut the header block off at the first blank line (`"\r\n\r\n"`), then split it into lines.
hint: `str.partition(":")` splits at the first colon only, which matters for values that contain colons.
solution: Split off the head, take the first line apart into method and target, use `urlsplit` and `parse_qs` on the target, and build the header dictionary with `partition(":")`, `strip()` and `lower()`. Because `partition` splits at the first colon, the value `a:b` survives intact.

```python
def status_class(code):
    names = {
        1: "informational",
        2: "success",
        3: "redirection",
        4: "client error",
        5: "server error",
    }
    if not 100 <= code <= 599:
        raise ValueError(f"not an HTTP status code: {code}")
    return names[code // 100]
```
hint: The class is determined by the hundreds digit, which integer division by 100 gives you.

prompt: Write `build_response(status, body)` that returns a complete HTTP/1.1 response as a `str`. The status line is `HTTP/1.1 <status> <reason>`, where the supported statuses are `200` (`OK`), `404` (`Not Found`) and `500` (`Internal Server Error`); any other status raises `ValueError`. After the status line come exactly two headers in this order: `Content-Type: text/plain; charset=utf-8` and `Content-Length: <n>`, where `n` is the length of `body` encoded as UTF-8 **in bytes**. Every line ends with `"\r\n"`, a blank line follows the headers, then the body.
starter:
```python
def build_response(status, body):
    pass
```
tests:
```python
assert build_response(200, "hi") == (
    "HTTP/1.1 200 OK\r\n"
    "Content-Type: text/plain; charset=utf-8\r\n"
    "Content-Length: 2\r\n\r\nhi")
assert build_response(404, "") == (
    "HTTP/1.1 404 Not Found\r\n"
    "Content-Type: text/plain; charset=utf-8\r\n"
    "Content-Length: 0\r\n\r\n")
assert build_response(500, "café").endswith(
    "Content-Length: 5\r\n\r\ncafé")
assert raises(ValueError, build_response, 418, "x")
```
model:
```python
REASONS = {200: "OK", 404: "Not Found", 500: "Internal Server Error"}


def build_response(status, body):
    if status not in REASONS:
        raise ValueError(f"unsupported status: {status}")
    size = len(body.encode("utf-8"))
    return (
        f"HTTP/1.1 {status} {REASONS[status]}\r\n"
        "Content-Type: text/plain; charset=utf-8\r\n"
        f"Content-Length: {size}\r\n"
        "\r\n"
        f"{body}"
    )
```
hint: A dictionary from status code to reason phrase handles both the lookup and the unsupported case.
hint: `len(body)` counts characters; encode first with `body.encode("utf-8")` to count bytes.
solution: Look up the reason phrase (raise `ValueError` if missing), compute the byte length from the UTF-8 encoding, and join the lines with `"\r\n"`. The test with `café` checks that `é` takes two bytes, so the length is 5, not 4.
