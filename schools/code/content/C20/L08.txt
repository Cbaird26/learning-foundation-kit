@article
An **API** (application programming interface) lets programs, not people, use a service. A **web API** is used over HTTP. Most modern web APIs follow the **REST** style (representational state transfer): the server exposes **resources**, each identified by a URL, and clients act on them with the standard HTTP methods, exchanging **representations** of the resource, almost always JSON.

### JSON

**JSON** (JavaScript Object Notation, RFC 8259) is a text format with exactly these values: objects `{"name": "Ada"}` (keys are strings in double quotes), arrays `[1, 2, 3]`, strings (double quotes only), numbers, `true`, `false` and `null`.

```json
{
  "id": 7,
  "title": "Dune",
  "tags": ["fiction", "classic"],
  "rating": 4.5,
  "series": null,
  "available": true
}
```

There are no comments, no trailing commas, no single quotes and no `undefined`, `NaN` or functions. In JavaScript, `JSON.stringify(value)` produces the text and `JSON.parse(text)` reads it (throwing a `SyntaxError` for invalid input). In Python, `json.dumps` and `json.loads` do the same, mapping `null`, `true`, `false` to `None`, `True`, `False`. Send it with the header `Content-Type: application/json`.

### Designing resources

Use **nouns** in URLs for collections and items, and let the **method** express the action:

| Request | Meaning | Typical success status |
|---|---|---|
| `GET /books` | list books | `200 OK` |
| `GET /books/7` | read one | `200 OK` |
| `POST /books` | create | `201 Created`, with a `Location` header |
| `PUT /books/7` | replace entirely | `200` or `204` |
| `PATCH /books/7` | change some fields | `200` or `204` |
| `DELETE /books/7` | remove | `204 No Content` |

Conventions that make an API predictable: plural nouns (`/books`, not `/getBook`); filters and sorting in the query string (`/books?author=herbert&sort=title`); versioning in the path or a header (`/v1/books`); `GET` never changes data; `PUT` and `DELETE` are idempotent, so a client may safely retry them after a timeout, whereas retrying `POST` may create duplicates unless the API supports idempotency keys.

### Status codes for errors

Return a code that tells the client what to do next: `400` for a malformed request, `401` when authentication is missing or failed, `403` when the user is known but not allowed, `404` for an unknown resource, `405` when the method is not supported on that URL (with an `Allow` header), `409` for a conflict (such as a duplicate), `422` for well-formed but semantically invalid data, `429` for too many requests (often with `Retry-After`) and `500` or `503` for server faults. Give a machine-readable body, for example the **problem details** format of RFC 9457 (`application/problem+json`), or at least `{"error": "title required"}`. Never include stack traces or internal details.

### Pagination

Returning every row is slow and risky, so collections are paged. **Offset pagination** uses `?page=2&per_page=10` (or `limit` and `offset`): item $i$ (counting from 0) of page $p$ (counting from 1) is at index $(p-1)\cdot\text{per\_page} + i$, and the number of pages is $\lceil \text{total}/\text{per\_page} \rceil$. **Cursor pagination** (`?after=<token>`) stays stable when rows are inserted while a client is paging and scales better on large tables.

### JSON Merge Patch

`PATCH` bodies are often a **JSON Merge Patch** (RFC 7396): the patch is merged into the target; a member whose value is `null` deletes that key, an object member is merged recursively, and any other value replaces the old one.

### Consuming a public API

```javascript
async function showBooks(list) {
  const response = await fetch("https://api.example.com/v1/books?limit=5");
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}`);
  }
  const books = await response.json();
  list.replaceChildren();
  for (const book of books) {
    const li = document.createElement("li");
    li.textContent = `${book.title} by ${book.author}`;
    list.append(li);
  }
}
```

Read the API's documentation for its base URL, authentication, rate limits and terms. Treat the data as untrusted: insert it with `textContent`, never `innerHTML`. **Never put a secret API key in front-end JavaScript**, because every visitor can read it; call the API from your own server instead (week 9). Give the user a loading state, an error state and an empty state, and announce updates to assistive technology, for example by placing status text in an element with `role="status"`.

@example
title: Designing an API for a reading list
problem: Design the requests for a reading tracker: list a user's books, add one, mark book 7 as finished, and remove book 7.
step: The resource is a book, so the collection is `/books`. Listing is `GET /books`, with `200 OK` and a JSON array.
step: Adding is `POST /books` with body `{"title": "Dune"}`. The server answers `201 Created`, a `Location: /books/7` header and the new book as JSON.
step: Marking as finished changes one field, so use `PATCH /books/7` with `{"finished": true}`. `PUT` would require sending the whole book.
step: Removing is `DELETE /books/7`; the server replies `204 No Content`, and a second `DELETE` returns `404` (the final state is the same, so the method is idempotent).

@example
title: Applying a merge patch
problem: Apply the patch `{"a": "z", "c": {"f": null}}` to `{"a": "b", "c": {"d": "e", "f": "g"}}`.
step: Key `a` has a non-object value in the patch, so it replaces the old one: `"a": "z"`.
step: Key `c` is an object in both, so merge it recursively.
step: Inside `c`, the patch sets `f` to `null`, which deletes `f`; `d` is untouched.
step: The result is `{"a": "z", "c": {"d": "e"}}`.
answer: `{"a": "z", "c": {"d": "e"}}`

@mistakes
- Putting verbs in URLs (`/deleteBook?id=7`) or changing data with `GET`, which breaks caching and safety.
- Returning `200` with an error message in the body, so clients and tools cannot detect failure from the status.
- Writing invalid JSON by hand: single quotes, trailing commas or comments.
- Embedding a secret API key in client-side code, or inserting API data with `innerHTML`.

model:
```python
import math


def paginate(items, page, per_page):
    if page < 1 or per_page < 1:
        raise ValueError("page and per_page must be at least 1")
    start = (page - 1) * per_page
    return {
        "items": items[start:start + per_page],
        "page": page,
        "per_page": per_page,
        "total": len(items),
        "pages": math.ceil(len(items) / per_page),
    }
```
hint: Page $p$ starts at index $(p-1) \cdot \text{per\_page}$.
hint: Slicing past the end of a list gives an empty list, and `math.ceil(total / per_page)` gives the number of pages.
solution: Validate the arguments, slice from `(page - 1) * per_page` for `per_page` items, and compute the page count with `math.ceil`. Python slices never raise on a start beyond the end, which gives the empty last page for free.

model:
```python
def api(books, method, path, body=None):
    not_found = (404, {"error": "not found"})
    if path == "/books":
        if method == "GET":
            return 200, list(books)
        if method == "POST":
            title = body.get("title") if isinstance(body, dict) else None
            if not isinstance(title, str) or not title.strip():
                return 400, {"error": "title required"}
            new_id = max((b["id"] for b in books), default=0) + 1
            book = {"id": new_id, "title": title.strip()}
            books.append(book)
            return 201, book
        return 405, {"error": "method not allowed"}
    prefix = "/books/"
    digits = path[len(prefix):]
    if not path.startswith(prefix) or not digits.isdigit():
        return not_found
    if method not in ("GET", "DELETE"):
        return 405, {"error": "method not allowed"}
    book_id = int(digits)
    for book in books:
        if book["id"] == book_id:
            if method == "GET":
                return 200, book
            books.remove(book)
            return 204, None
    return not_found
```
hint: Handle the exact path `/books` first, then check that the path starts with `/books/` and that the rest is made of digits (`str.isdigit()`).
hint: Validate the `POST` body step by step: is it a dictionary, is the title a string, is it non-empty after `strip()`?
solution: Route by path, then by method, returning `405` for a known path with an unsupported method before any lookup. For `POST`, validate the body defensively (it may be `None`), compute the next id and append the book. For items, search the list for the id: `GET` returns the book, `DELETE` removes it, and a missing id falls through to the `404`.

tests:

```python
target = {"a": "b", "c": {"d": "e", "f": "g"}}
patch = {"a": "z", "c": {"f": None}}
assert merge_patch(target, patch) == {"a": "z", "c": {"d": "e"}}

```
model:
```python
def merge_patch(target, patch):
    if not isinstance(patch, dict):
        return patch
    result = dict(target) if isinstance(target, dict) else {}
    for key, value in patch.items():
        if value is None:
            result.pop(key, None)
        else:
            result[key] = merge_patch(result.get(key), value)
    return result
```
hint: The function is recursive: a patch value that is a dictionary is merged into the target's value at that key.
hint: Copy the target with `dict(target)` first, and use `result.pop(key, None)` to delete a key that may be missing.
solution: A non-dictionary patch replaces the target outright. For a dictionary patch, copy the target, delete keys whose patch value is `None`, and set the others to the recursive merge. Because the result is a new dictionary at every level that is touched, the original `target` is not changed.
