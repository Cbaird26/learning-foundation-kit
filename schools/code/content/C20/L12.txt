@article
A web application is only finished when you can show that it works and can run it for other people. This week covers both: **testing** (how you know) and **deployment** (how you ship).

### Levels of testing

- **Unit tests** check one function in isolation (a validator, a price calculation). They are fast and numerous.
- **Integration tests** exercise several parts together, for instance an HTTP request through routing, the view and a real (temporary) database.
- **End-to-end tests** drive a real browser through whole user journeys (sign in, add a book, see it listed). They are the most realistic, slowest and most fragile, so keep few.

The usual advice (the "test pyramid") is many unit tests, fewer integration tests and a handful of end-to-end tests. Tests must be **independent** (each starts from a clean state, so a failing test never depends on another) and **deterministic** (no dependence on the clock, random numbers or the network). To test code that calls something external, **inject the dependency** (pass the function as a parameter) and give the test a fake one; Python's `unittest.mock` can also replace objects temporarily.

### Testing Flask

Flask provides a test client that sends requests to the app in-process, with no server and no network:

```python
import pytest
from app import create_app


@pytest.fixture
def client(tmp_path):
    app = create_app({"TESTING": True, "DATABASE": str(tmp_path / "test.db")})
    with app.test_client() as client:
        yield client


def test_create_book_requires_title(client):
    response = client.post("/api/books", json={"title": ""})
    assert response.status_code == 400
    assert "error" in response.get_json()


def test_create_then_list(client):
    client.post("/api/books", json={"title": "Dune"})
    titles = [b["title"] for b in client.get("/api/books").get_json()]
    assert titles == ["Dune"]
```

A **fixture** builds a fresh app and a temporary database for every test. (`pytest` is the most popular test runner; the standard library's `unittest` does the same job with classes.) Test the unhappy paths as much as the happy ones: invalid input, missing authentication, someone else's data. Measure **coverage** to find untested code, but remember that coverage shows what code ran, not that it was checked, and that a passing suite does not prove the absence of bugs. Run the tests automatically on every push with **continuous integration** (CI).

### Fixing a security bug with a test

A bug report says: after sign-in, `/login?next=...` sends users to any address, so a phishing link such as `/login?next=https://evil.example/` makes your real login page redirect to another site (an **open redirect**). The disciplined way to fix it:

1. Write a test that reproduces the problem and **fails**.
2. Fix the code until the test passes.
3. Keep the test as a **regression test** so the bug cannot return.

```python
# VULNERABLE: redirects to whatever the query string says
return redirect(request.args.get("next", "/"))

# FIXED: only a path on this site is allowed
target = request.args.get("next", "")
return redirect(target if is_safe_redirect(target) else url_for("home"))
```

The check accepts only a string that starts with a single `/` (not `//`, which means "another host", and not `/\`, which browsers treat the same way) and contains no control characters (browsers silently strip tabs and newlines in URLs). Test accessibility too: automated checkers find only a fraction of problems, so also tab through the page with the keyboard, zoom to 200% and try a screen reader.

### Configuration

Code is the same everywhere; **configuration** (secret keys, database URL, debug flag, port) differs between laptop, test and production, and secrets must never be committed to version control. Read them from **environment variables** at startup, give safe defaults for non-secrets, and **fail fast** if a required one is missing. Add a **health check** route (`/healthz`) that returns `200` when the app and its database work and `503` otherwise, so load balancers and orchestrators know when to restart or stop sending traffic.

### Deploying

A typical production setup:

1. **Dependencies** are pinned in `requirements.txt` and installed in a clean environment (or image).
2. A **WSGI server** such as Gunicorn runs the app with several worker processes: `gunicorn --bind 0.0.0.0:8000 app:app`.
3. A **reverse proxy** (nginx, Caddy or a cloud load balancer) accepts public traffic, terminates **TLS** with a certificate (obtained automatically through the ACME protocol, for instance), serves static files and forwards requests to Gunicorn. Redirect HTTP to HTTPS and send `Strict-Transport-Security`.
4. A **database server** (such as PostgreSQL) replaces a local SQLite file when several machines or heavy writes are involved; schema changes are applied by versioned **migrations**, and backups are tested by restoring them.
5. Logs go to standard output, where the platform collects them; log events, not secrets or passwords.

A **container** packages the app and its dependencies:

```dockerfile
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN useradd --create-home appuser
USER appuser
EXPOSE 8000
CMD ["gunicorn", "--bind", "0.0.0.0:8000", "app:app"]
```

Before launch, run the checklist: debug off, a strong `SECRET_KEY` from the environment, HTTPS only, secure cookies, passwords hashed, dependencies up to date, tests green, errors that show users a plain message while logging details privately, and a way to roll back.

@example
title: Test first, then fix
problem: Show how to fix the open redirect in a login view with a regression test.
step: Write the test: `client.post("/login?next=https://evil.example/", data=VALID)` must answer `303` with a `Location` header that does not start with `https://evil.example`.
step: Run it: it fails, which proves that the test really detects the bug.
step: Add `is_safe_redirect(target)` and use it in the view, falling back to the home page when it returns `False`.
step: Run the whole suite. The new test passes, and it stays in the suite, so a later refactoring cannot silently bring the bug back.

@example
title: Reading configuration from the environment
problem: Load `DEBUG` and `PORT` from environment variables, with safe defaults.
step: `DEBUG` is dangerous when wrongly on, so the default is off, and only clear "yes" values turn it on: `os.environ.get("DEBUG", "").lower() in {"1", "true", "yes", "on"}`.
step: `PORT` needs conversion and a range check: `port = int(os.environ.get("PORT", "8000"))`; `int` raises `ValueError` for text, and you add a check that `1 <= port <= 65535`.
step: A required secret has no default: `os.environ["SECRET_KEY"]` raises `KeyError` at startup if it is missing, so the app refuses to start without it.
step: The same code now runs on a laptop and in production, with only the environment changing.

@mistakes
- Writing tests that depend on each other's data, the clock or the network, so that they fail randomly.
- Fixing a bug without a test that fails first, so that nobody knows the fix works or that it stays fixed.
- Committing secrets or `.env` files with real keys to the repository, or leaving debug mode on in production.
- Exposing Flask's development server directly to the internet, with no TLS.

model:
```python
def load_config(env):
    secret = env.get("SECRET_KEY", "")
    if len(secret) < 32:
        raise RuntimeError("SECRET_KEY must be set and at least 32 characters")
    debug = env.get("DEBUG", "").strip().lower() in {"1", "true", "yes", "on"}
    port = int(env.get("PORT", "8000"))
    if not 1 <= port <= 65535:
        raise ValueError(f"PORT out of range: {port}")
    return {
        "SECRET_KEY": secret,
        "DEBUG": debug,
        "PORT": port,
        "DATABASE_URL": env.get("DATABASE_URL", "sqlite:///app.db"),
    }
```
hint: Treat a missing secret like an empty one, with `env.get("SECRET_KEY", "")`, and check the length.
hint: `int(...)` already raises `ValueError` for text such as `"abc"`; add your own check for the range.
solution: Validate the required secret first (fail fast), turn the debug text into a boolean through a set of accepted spellings, convert and range-check the port, and fill defaults for non-secret settings.

Return a tuple `(status, payload)`: if all checks pass, `(200, {"status": "ok", "checks": {...}})`, otherwise `(503, {"status": "unavailable", "checks": {...}})`, where the `"checks"` dictionary maps each name to `"ok"` or `"fail"`. ```
tests:
```python
def db_ok():
    return True


def db_down():
    raise ConnectionError("password for db is hunter2")


assert health({"db": db_ok}) == (
    200, {"status": "ok", "checks": {"db": "ok"}})
status, payload = health({"db": db_down, "cache": lambda: True})
assert status == 503
assert payload == {"status": "unavailable",
                   "checks": {"db": "fail", "cache": "ok"}}
assert "hunter2" not in str(payload)
```

model:
```python
def health(checks):
    results = {}
    for name, check in checks.items():
        try:
            passed = bool(check())
        except Exception:
            passed = False
        results[name] = "ok" if passed else "fail"
    healthy = all(value == "ok" for value in results.values())
    if healthy:
        return 200, {"status": "ok", "checks": results}
    return 503, {"status": "unavailable", "checks": results}
```
hint: Run every check inside `try`/`except Exception`, so one failure cannot stop the others from running.
hint: Build the `"checks"` dictionary first, then decide the status from it with `all(...)`.
solution: For each check record `"ok"` or `"fail"` (an exception counts as a failure and its message is deliberately dropped), then return 200 only when every entry is `"ok"`. `all([])` is `True`, which gives the required result for no checks.

@practice code
prompt: A login view redirects to the address in the `next` query parameter. Fix the open-redirect bug by writing `is_safe_redirect(target)`, which returns `True` only for a path on the same site: the string must start with `"/"`, its second character (if any) must not be `"/"` or `"\\"` (a backslash), it must contain no control characters (any character with a code below 32, such as a tab or a newline), and `urllib.parse.urlsplit(target)` must have an empty scheme and an empty network location. Anything else, including the empty string, returns `False`.

tests:
```python
assert is_safe_redirect("/dashboard") is True
assert is_safe_redirect("/") is True
assert is_safe_redirect("/books?page=2") is True
assert is_safe_redirect("https://evil.example/") is False
assert is_safe_redirect("//evil.example/x") is False
assert is_safe_redirect("/\\evil.example") is False
assert is_safe_redirect("/\t/evil.example") is False
assert is_safe_redirect("/ok\nSet-Cookie: x=1") is False
assert is_safe_redirect("dashboard") is False
assert is_safe_redirect("") is False

```
model:
```python
from urllib.parse import urlsplit


def is_safe_redirect(target):
    if not target.startswith("/"):
        return False
    if len(target) > 1 and target[1] in "/\\":
        return False
    if any(ord(ch) < 32 for ch in target):
        return False
    parts = urlsplit(target)
    return parts.scheme == "" and parts.netloc == ""
```
hint: Reject early: first the strings that do not begin with `/`, then those whose second character is `/` or a backslash.
hint: `any(ord(ch) < 32 for ch in target)` detects tabs, newlines and other control characters.
solution: A site-relative path begins with a single slash. A second slash or backslash makes the browser read it as another host, control characters can be stripped by browsers to produce one, and `urlsplit` provides a final check that no scheme or host is present. Anything that fails a check falls back to a safe default page.

model:
```python
def load_name(fetch, user_id):
    status, data = fetch(f"/api/users/{user_id}")
    if status == 200:
        return data["name"]
    if status == 404:
        return None
    raise RuntimeError(f"unexpected status {status}")
```

hint: Build the path with an f-string: `f"/api/users/{user_id}"`.
