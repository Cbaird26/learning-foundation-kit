material: ## Specification

Users register and sign in. Each user sees and changes only their own books. A book has a title (required, at most 200 characters), an author (optional), a status (`to-read`, `reading` or `finished`) and an optional rating from 1 to 5.

| Method and path | Purpose | Success | Errors |
|---|---|---|---|
| `POST /api/register` | create a user (`username`, `password` in JSON) | `201` | `400` invalid, `409` name taken |
| `POST /api/login` | sign in, start a session | `200` | `401` wrong name or password |
| `POST /api/logout` | end the session | `204` | |
| `GET /api/books` | the signed-in user's books, optional `?status=` filter | `200` | `401` |
| `POST /api/books` | add a book | `201` with the book | `400` invalid, `401` |
| `PATCH /api/books/<id>` | change `title`, `author`, `status` or `rating` | `200` | `400`, `401`, `404` |
| `DELETE /api/books/<id>` | remove a book | `204` | `401`, `404` |
| `GET /healthz` | health check | `200` | `503` |

A book that belongs to another user must answer `404`, exactly as if it did not exist. Errors are JSON of the form `{"error": "message"}`.
material: ## Database schema

```sql
CREATE TABLE users (
    id INTEGER PRIMARY KEY,
    username TEXT NOT NULL UNIQUE,
    pw_hash TEXT NOT NULL
);

CREATE TABLE books (
    id INTEGER PRIMARY KEY,
    owner_id INTEGER NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    title TEXT NOT NULL,
    author TEXT NOT NULL DEFAULT '',
    status TEXT NOT NULL DEFAULT 'to-read'
        CHECK (status IN ('to-read', 'reading', 'finished')),
    rating INTEGER CHECK (rating BETWEEN 1 AND 5)
);
```

Remember `PRAGMA foreign_keys = ON` on every SQLite connection.

material: ## Accessibility checklist (copy it into your README and mark each line)

- Every page has `lang`, a unique `title`, one `h1` and a logical heading outline.
- Landmarks are used: `header`, `nav`, `main`, `footer`.
- Every form control has a visible `label`; errors are text, not only color, and are announced (`role="alert"` or `role="status"`).
- Everything works with the keyboard alone, with a visible focus indicator, and targets are at least 24 by 24 CSS pixels.
- Text contrast is at least 4.5:1 (3:1 for large text), checked with a tool or a calculation.
- The layout works at 320 CSS pixels wide and at 200 percent zoom.
- Images have meaningful `alt` text, or `alt=""` when decorative.
material: ## Security checklist (copy it into your README and mark each line)

- Passwords are stored with a salted slow hash; the policy follows NIST SP 800-63B Revision 4.
- Every SQL statement uses placeholders; every template value is escaped; no `innerHTML` with user data.
- Every books query filters by the signed-in user; there is a test for it.
- Session cookie is `HttpOnly`, `Secure` and `SameSite=Lax`; the session is renewed at login and cleared at logout.
- State-changing requests are `POST`, `PATCH` or `DELETE`, and a CSRF defense is in place (`SameSite` plus a token or an `Origin` check).
- `SECRET_KEY` and other secrets come from the environment and are not in the repository; debug mode is off in production.
- Error responses contain no stack traces; login errors do not reveal whether a user exists.
- Dependencies are pinned and have been checked for known vulnerabilities.

@review
## Week-by-week review

**Week 1, HTTP.** A URL has scheme, host, port, path, query and fragment; the fragment stays in the browser. HTTP is a stateless request/response protocol: methods (`GET` safe and idempotent, `POST` neither, `PUT` and `DELETE` idempotent), status classes 1xx to 5xx, headers such as `Host`, `Content-Type` and `Content-Length` (bytes). TLS 1.3 secures `https`; HTTP/3 runs over QUIC.

**Week 2, HTML.** Semantic elements and landmarks, one `h1`, no skipped heading levels, `alt` text (empty for decoration), labels tied to controls, buttons for actions and links for navigation, native elements before ARIA, WCAG 2.2 AA contrast of 4.5:1 and 3:1 and the contrast-ratio formula.

**Week 3, CSS.** Selector types, specificity as $(a,b,c)$, the cascade (importance, layers, specificity, order), inheritance, the box model, `content-box` versus `border-box`, `rem` and `em`.

**Week 4, layout.** Flexbox (main and cross axis, grow, shrink, basis), grid (`fr`, `repeat`, `minmax`, `auto-fill`), the viewport meta tag, mobile-first `min-width` queries, fluid sizing.

**Week 5, JavaScript.** `let` and `const`, `===`, truthiness, closures, `map`, `filter`, `reduce`, destructuring, the default string sort of `sort()`.

**Week 6, DOM.** Selecting and changing elements, `textContent` versus `innerHTML`, event phases, `preventDefault`, `stopPropagation`, delegation, state kept separate from the page.

**Week 7, async.** Single thread and event loop, microtasks before timers, promises, `async`/`await`, `fetch` resolving on `404` (check `response.ok`), `Promise.all` and `allSettled`.

**Week 8, REST and JSON.** Resources and methods, status codes for success and failure, JSON syntax rules, pagination, merge patch, never a secret key in front-end code.

**Week 9, Flask.** Routes and converters, `request`, responses and `abort`, WSGI, Gunicorn instead of the development server, no debug mode in production.

**Week 10, data and forms.** Parameterized SQL, `commit`, Jinja2 autoescaping, server-side validation, Post/Redirect/Get.

**Week 11, security.** Salted slow password hashes, NIST SP 800-63B Revision 4 policy, sessions and cookie attributes, access control on every request, XSS, CSRF, injection, the OWASP Top 10:2025.

**Week 12, testing and deployment.** Unit, integration and end-to-end tests, the Flask test client, regression tests, configuration from the environment, health checks, reverse proxy and TLS, containers, a launch checklist.

## Common errors

Forgetting `response.ok` after `fetch`; using `innerHTML` for user data; building SQL by concatenation; checking that a user is signed in but not that the object is theirs; relying on browser validation alone; forgetting the viewport meta tag; counting characters instead of bytes for `Content-Length`; leaving debug mode on.

@exam code
prompt: Write `serve(raw, books)`, a miniature web server for one resource, working on raw HTTP/1.1 text. `raw` is a request: a request line `METHOD PATH HTTP/1.1`, header lines, a blank line and an optional body, all separated by `"\r\n"`. `books` is a list of dictionaries `{"id": int, "title": str}` which `serve` may modify. Routes: `GET /books` returns status 200 and the list as JSON; `POST /books` reads the body as JSON, which must be a dictionary with a `"title"` that is a non-empty string after stripping; then it appends `{"id": largest id plus one (1 if empty), "title": stripped title}` and returns status 201 and that book. An invalid body (not JSON, not a dictionary, or a bad title) gives status 400 and `{"error": "title required"}`. Any other path (ignoring a query string after `?`) gives 404 and `{"error": "not found"}`; a known path with another method gives 405 and `{"error": "method not allowed"}`. The result is a response string: the status line `HTTP/1.1 <code> <reason>` (reasons `OK`, `Created`, `Bad Request`, `Not Found`, `Method Not Allowed`), then the headers `Content-Type: application/json` and `Content-Length: <n>` (the body's length in bytes), a blank line and the body, which is `json.dumps(payload, ensure_ascii=False)` (so a title such as `Café` keeps its `é`, and the length in bytes can differ from the number of characters). Lines end with `"\r\n"`.

model:
```python
import json

REASONS = {
    200: "OK",
    201: "Created",
    400: "Bad Request",
    404: "Not Found",
    405: "Method Not Allowed",
}


def respond(status, payload):
    body = json.dumps(payload, ensure_ascii=False)
    return (
        f"HTTP/1.1 {status} {REASONS[status]}\r\n"
        "Content-Type: application/json\r\n"
        f"Content-Length: {len(body.encode('utf-8'))}\r\n"
        "\r\n"
        f"{body}"
    )


def serve(raw, books):
    head, _, body = raw.partition("\r\n\r\n")
    method, target, _version = head.split("\r\n")[0].split(" ")
    path = target.split("?")[0]
    if path != "/books":
        return respond(404, {"error": "not found"})
    if method == "GET":
        return respond(200, list(books))
    if method != "POST":
        return respond(405, {"error": "method not allowed"})
    try:
        data = json.loads(body)
    except Exception:
        data = None
    title = data.get("title") if isinstance(data, dict) else None
    if not isinstance(title, str) or not title.strip():
        return respond(400, {"error": "title required"})
    new_id = max((b["id"] for b in books), default=0) + 1
    book = {"id": new_id, "title": title.strip()}
    books.append(book)
    return respond(201, book)
```
hint: Split the request at the first blank line with `partition("\r\n\r\n")`, and take method and path from the first line.
hint: Write a helper that turns a status and a payload into the full response text, so every branch can reuse it; compute the byte length from the UTF-8 encoding of the body.
solution: Parse the head and body, route by path (404), then by method (200, 405 or the `POST` branch). For `POST`, a broken JSON body is caught and treated like any other invalid body, so every bad input leads to the same `400`. The helper builds the status line, the two headers (with a byte-based length) and the body.

hint: First find how many columns of at least 250px fit with the 30px gaps: $n$ columns need $250n + 30(n-1) \le 1200$.
hint: The free space after the gaps is shared equally by the `1fr` maximum, so each column is $(1200 - 30(n-1))/n$ pixels wide.
solution: Four columns need $4\cdot 250 + 3\cdot 30 = 1090 \le 1200$ pixels, while five need $1370 > 1200$, so there are 4 columns. The gaps use $3 \cdot 30 = 90$ pixels, leaving $1110$ pixels, so each column is $1110/4 = 277.5$ pixels wide.
