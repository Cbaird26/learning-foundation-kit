@article
Git is **distributed**: every clone has the full history, and any clone can exchange commits with another. In practice teams designate one shared repository on a hosting service such as GitHub, GitLab or Bitbucket, and everyone synchronizes with it.

### Remotes

A **remote** is a named URL of another copy of the repository. `git clone URL` copies a repository, and it names the source `origin`. `git remote -v` lists remotes and `git remote add origin URL` adds one. A URL is either HTTPS (`https://github.com/owner/repo.git`) or SSH (`git@github.com:owner/repo.git`); SSH uses a key pair so you do not type a password.

For each branch on a remote, your repository keeps a **remote-tracking branch** such as `origin/main`: a read-only bookmark recording where that branch was the last time you talked to the remote. Your own `main` is a separate, local branch and may be ahead of, behind, or diverged from `origin/main`.

### Synchronizing

- `git fetch` downloads new commits and updates `origin/main` and other remote-tracking branches. It **never changes your local branches or files**, so it is always safe.
- `git merge origin/main` (or `git rebase origin/main`) then integrates the fetched work into your current branch.
- `git pull` is `git fetch` followed by a merge into the current branch; `git pull --rebase` fetches and rebases instead.
- `git push origin main` uploads your commits and moves the remote's `main`. The push is rejected as "non-fast-forward" if the remote has commits you lack: fetch, integrate, then push again. Never solve that by force-pushing a shared branch.
- `git push -u origin feature` pushes a new branch and sets its **upstream**, so later `git push` and `git pull` need no arguments, and `git status` reports how many commits you are ahead or behind (`git status -sb` shows `[ahead 2, behind 1]`).

`git branch -vv` shows each local branch with its upstream, and `git log origin/main..main` lists the commits you have not pushed.

### Pull requests

A **pull request** (PR; a "merge request" on GitLab) is a proposal to merge one branch into another, with a discussion page attached. It is a feature of the hosting service, not of Git itself. The common workflow is:

1. Update `main` (`git switch main`, `git pull`), then create a branch (`git switch -c fix-parser`).
2. Commit your work and push it (`git push -u origin fix-parser`).
3. Open a pull request from `fix-parser` into `main`. Write a title and a description that says *what* changed, *why*, how you tested it, and what a reviewer should look at.
4. Automated checks (**continuous integration**, CI) run the tests and linters on the branch. Reviewers comment on lines; you answer, push more commits to the same branch (the PR updates automatically), and request another look.
5. When approved and green, a maintainer merges it. Hosting services usually offer three styles: a merge commit, **squash and merge** (all the PR's commits become one) and **rebase and merge** (commits are replayed linearly).
6. Delete the branch and update your local `main`.

When working on someone else's project you usually **fork** it (your own server-side copy), push branches to your fork, and open the PR from the fork to the original ("upstream") repository. Good PRs are small, focused and self-explanatory: a 2000-line PR is hard to review well. When you review, comment on the code, not the person, be specific, and say which points are blocking and which are suggestions.

@example
title: A rejected push
problem: `git push origin main` fails with "rejected ... (fetch first)". Your local `main` has one new commit. What happened and what should you do?
step: Someone else pushed a commit to `origin/main` after your last fetch, so the remote has a commit you lack. Your `main` and the remote have diverged.
step: Run `git pull --rebase` (or `git fetch` and then `git rebase origin/main`) to replay your commit on top of theirs.
step: Resolve any conflicts, run the tests, then `git push origin main`, which is now a fast-forward for the remote.
step: Do not use `git push --force` on a shared branch: it would delete their commit from the remote.
answer: The remote has new commits; integrate with `git pull --rebase` (or a merge) and push again.
@mistakes
- Thinking `git fetch` changes your files. It only updates remote-tracking branches such as `origin/main`.
- Force-pushing a shared branch to "fix" a rejected push, which discards teammates' commits.
- Opening huge, unfocused pull requests, or leaving the description empty so reviewers must guess what changed and why.
- Committing directly to `main` instead of a branch, so changes cannot be reviewed first.

```python
def parse_remote(url):
    if url.startswith("git@"):
        path = url.split(":", 1)[1]
    else:
        path = url.split("://", 1)[1].split("/", 1)[1]
    if path.endswith(".git"):
        path = path[:-4]
    owner, repo = path.split("/")
    return (owner, repo)
```

Example: if `local` has two commits that `remote` lacks and `remote` has one that `local` lacks, the result is `(2, 1)`.
starter:
```python
def ahead_behind(parents, local, remote):
    pass
```
tests:
```python
g = {"A": [], "B": ["A"], "C": ["B"], "D": ["C"], "R": ["B"]}
assert ahead_behind(g, "D", "R") == (2, 1)
assert ahead_behind(g, "D", "B") == (2, 0)
assert ahead_behind(g, "B", "D") == (0, 2)
assert ahead_behind(g, "C", "C") == (0, 0)
```
model:
```python
def reach(parents, commit):
    seen = set()
    stack = [commit]
    while stack:
        current = stack.pop()
        if current not in seen:
            seen.add(current)
            stack.extend(parents[current])
    return seen


def ahead_behind(parents, local, remote):
    mine = reach(parents, local)
    theirs = reach(parents, remote)
    return (len(mine - theirs), len(theirs - mine))
```
hint: Compute the set of commits reachable from each tip.
hint: `ahead` is the size of the set difference `mine - theirs`; `behind` is `theirs - mine`.
solution: Collect all ancestors of each tip (a tip counts as its own ancestor), then count the commits in each set but not in the other. These are the numbers shown by `git status` as "ahead" and "behind".

```python
def remote_status(ahead, behind):
    if ahead > 0 and behind > 0:
        return "diverged: pull --rebase, then push"
    if ahead > 0:
        return "push"
    if behind > 0:
        return "pull"
    return "up to date"
```
