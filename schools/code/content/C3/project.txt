material: **Specification of `logstat`.** The input is a text log in which every line has the form `DATE TIME LEVEL message`, for example the sample below. Fields are separated by single spaces and the message may contain spaces. Lines with fewer than three fields are ignored. The function `summarize(text, n)` returns the text that the tool prints, as one string whose lines end in a newline. First it prints one line `LEVEL COUNT` for each level that occurs, in the order `DEBUG`, `INFO`, `WARNING`, `ERROR`, `CRITICAL` (levels with a count of zero and unknown level names are not printed). If at least one `ERROR` line exists, it then prints the line `Top errors:` followed by at most `n` lines `COUNT MESSAGE`, one for each distinct error message, ordered by count from largest to smallest with ties in alphabetical order of the message. The command `python logstat.py [-n N] LOGFILE` (default `N` is 3) prints that text and exits with status 0. It exits with status 2 and prints a usage message to standard error if the file name is missing or the file cannot be read.

## Week-by-week key ideas

1. **The shell.** A path is absolute (starts with `/`) or relative; `.`, `..` and `~` are shortcuts. `mkdir -p`, `cp -r`, `mv` and `rm -r` manage files, and `rm` has no undo. Globs (`*`, `?`) are expanded by the shell before the command runs; quote names with spaces.
2. **Permissions, processes, environment.** Read `rwxr-xr--` as octal `754` (r=4, w=2, x=1). `chmod` changes modes; the umask removes bits from new files. `&`, `jobs`, `kill` (SIGTERM by default) and exit statuses (`0` is success, `$?`) control processes. Exported variables are inherited by children; `PATH` lists where programs are searched.
3. **Pipes and text tools.** Streams are stdin, stdout and stderr; `>`, `>>`, `<`, `2>`, `2>&1` and `|` connect them. `sort | uniq -c | sort -rn | head` is the frequency idiom; `uniq` needs sorted input; `sort -n` for numbers.
4. **Shell scripting.** Shebang, `$1`, `$#`, `"$@"`, `$(...)`, `if [ ... ]`, loops, functions, `set -euo pipefail`. Quote every expansion. Know when to switch to Python.
5. **Git basics.** Working tree, index and repository. A commit is a snapshot with a parent, named by a hash. `add`, `commit`, `status`, `diff`, `diff --staged`, `restore`, `revert`, `.gitignore`.
6. **Branches and merging.** A branch is a pointer. Fast-forward when one tip is an ancestor of the other; otherwise a three-way merge from the merge base creates a commit with two parents.
7. **Conflicts and rebase.** Edit the markers away, `git add`, commit; `git merge --abort` to give up. Rebase replays commits with new hashes; never rebase shared history; `--force-with-lease` after rewriting your own branch.
8. **Remotes and pull requests.** `fetch` updates remote-tracking branches only; `pull` is fetch plus merge or rebase; `push -u` sets the upstream. A pull request is a reviewed proposal built on a branch.
9. **Debugging.** Reproduce, minimize, hypothesize, test, fix, add a regression test. `breakpoint()` and `pdb` commands (`n`, `s`, `c`, `p`, `w`). Logging levels (`DEBUG` 10 up to `CRITICAL` 50; default `WARNING`). `git bisect` is binary search.
10. **Profiling.** Measure first. `timeit`, `cProfile` (`tottime` versus `cumtime`), better algorithms and caching first, and Amdahl's law: speedup $=1/((1-p)+p/s)$.
11. **Environments and dependencies.** `python3 -m venv .venv`, activate, `python -m pip`, pin with `pip freeze`, never commit `.venv`. Specifiers `==`, `>=,<`, `~=`; numeric version comparison; supply-chain risks.
12. **Editors, docs, make.** Vim modes (`i`, `Esc`, `:wq`, `:q!`); read the error and the reference; make rebuilds when a prerequisite is newer; `.PHONY`, `$@`, `$<`, `$^`.

## Common errors

Unquoted variables; `>` instead of `>>`; `uniq` without `sort`; committing without staging a file; merging into the wrong branch; leaving conflict markers in a file; force-pushing a shared branch; optimizing before measuring; comparing versions as text; spaces instead of a tab in a Makefile recipe.

prompt: Write `error_report(text, n)` for a log whose lines have the form `DATE TIME LEVEL message` (the message may contain spaces). Ignore lines with fewer than three whitespace-separated fields and lines whose level is not exactly `ERROR`, and lines with level `ERROR` but no message. Return a list of at most `n` tuples `(count, message)`, one for each distinct error message (the message is everything after the level, with single spaces between words as in the line), ordered by count from largest to smallest, ties in alphabetical order of the message. Example: a log with `ERROR disk full` twice and `ERROR timeout` once gives `[(2, "disk full"), (1, "timeout")]` for `n = 3`.
starter:
```python
def error_report(text, n):
    pass
```
tests:
```python
log = """2026-03-02 10:15:01 INFO server started
2026-03-02 10:17:02 ERROR disk full
2026-03-02 10:17:45 ERROR timeout
2026-03-02 10:19:00 ERROR disk full
2026-03-02 10:19:30 WARNING ERROR in text
"""
assert error_report(log, 3) == [(2, "disk full"), (1, "timeout")]
assert error_report(log, 1) == [(2, "disk full")]
assert error_report("", 5) == []
assert error_report("d t ERROR b\nd t ERROR a\n", 2) == [(1, "a"), (1, "b")]
assert error_report("x y\nd t ERROR\n", 2) == []
assert error_report("d t ERROR a b\nd t ERROR a b\n", 0) == []
```
model:
```python
def error_report(text, n):
    counts = {}
    for line in text.splitlines():
        fields = line.split()
        if len(fields) < 4 or fields[2] != "ERROR":
            continue
        message = " ".join(fields[3:])
        counts[message] = counts.get(message, 0) + 1
    ranked = sorted(((c, m) for m, c in counts.items()),
                    key=lambda pair: (-pair[0], pair[1]))
    return ranked[:n]
```
hint: Split each line into fields; the level is field 2 (counting from 0) and the message is everything after it.
hint: Count messages in a dictionary, sort with the key `(-count, message)`, and slice the first `n` items. A line with no message has fewer than four fields.
solution: This is the shell idiom `grep ' ERROR ' | cut -f4- | sort | uniq -c | sort -rn | head -n N` written in Python, with a deterministic tie-break. Lines without a message are skipped, and slicing with `[:n]` returns an empty list when `n` is 0.
@exam num
prompt: A regression was introduced somewhere in a range of 1000 consecutive commits, the first commit is known to be good and the last is known to be bad. Using `git bisect` (binary search), what is the largest number of commits you must build and test to identify the first bad commit, assuming the range is searched as efficiently as possible?
answer: 10
check: ceil(log2(1000))
hint: Each test halves the number of candidates.
solution: Binary search over 1000 candidates needs at most $\lceil \log_2 1000 \rceil = 10$ tests, since $2^{10} = 1024 \ge 1000$ and $2^9 = 512 < 1000$.

solution: Run `git fetch origin`, then update the branch. Because `feature/export` is my own branch and I have not shared it (or have agreed to rewrite it), I can rebase: `git rebase origin/main`. After a rebase I update the pull request with `git push --force-with-lease`, which only overwrites my own earlier push. If a test now fails, I start `git bisect start`, mark the current commit `git bisect bad` and a commit where the tests passed `git bisect good <hash>`, and let `git bisect run make test` find the first bad commit, then `git bisect reset`.
