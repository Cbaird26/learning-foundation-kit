@article
Your editor is where you spend most of your working day, and a few hours spent learning it pay off for years. This final tools lesson covers editors, the art of finding answers, and automating routine commands.

### Editors

An **IDE** (integrated development environment) such as VS Code or PyCharm combines an editor with a debugger, a terminal, version control and a **language server**, a background process that supplies completion, go-to-definition, rename-everywhere and live error checking. Learn the shortcuts for the things you do hundreds of times a day: open a file by name, search the project, jump to a definition, find all references, rename a symbol, run the tests, and start the debugger with a breakpoint. Configure a **formatter** and a **linter** to run on save so style is never debated in code review.

**Vim** is a terminal editor found on almost every server, so a minimum of it is worth knowing for editing over SSH. It is **modal**: the same key does different things in different modes. You start in **normal mode**, where keys are commands. `i` enters **insert mode** for typing text and `Esc` returns to normal mode. Useful normal-mode commands: `h j k l` move left, down, up, right; `w` and `b` move by word; `0` and `$` go to line start and end; `x` deletes a character; `dd` deletes (cuts) a line; `yy` copies a line; `p` pastes; `u` undoes; `/text` searches. Commands starting with `:` act on files: `:w` saves, `:q` quits, `:wq` does both, and `:q!` quits **without saving**. If you are stuck, press `Esc` a few times, then type `:q!`.

### Finding answers

- Commands: `man name` (the manual page), `name --help`, and `type name` to see what a name is.
- Python: `help(str.split)` in the interpreter, `python3 -m pydoc name`, docstrings, and the official documentation. The standard-library reference tells you precisely what a function does; a **tutorial** teaches the idea. Use a tutorial to learn something new and the reference to check a detail.
- Error messages: read the whole message and the last lines of a traceback, then search the **exact message** (without your file names) together with the tool's name. Prefer official documentation and the project's issue tracker to anonymous snippets. Never paste secrets or private code into public forums.
- Source code: for open-source libraries, reading the function you call is often the fastest way to learn what it really does.

When you ask a person for help, give the goal, what you ran, the exact error, and what you already tried: a **minimal reproducible example** gets answers fast.

### Automating with make

`make` runs commands described in a file named `Makefile`, rebuilding only what is out of date. A **rule** has a target, its prerequisites and a recipe:

```make
VENV = .venv

.PHONY: setup test clean

setup: requirements.txt
	python3 -m venv $(VENV)
	$(VENV)/bin/python -m pip install -r requirements.txt

test:
	$(VENV)/bin/python -m unittest discover -s tests

clean:
	rm -rf $(VENV) __pycache__
```

Each recipe line must start with a **tab character** (not spaces); any other leading whitespace is a syntax error ("missing separator"), so set your editor to insert a real tab in Makefiles. The make that ships with macOS is an old GNU Make 3.81, so stick to these classic features. `make test` runs the `test` rule. With no argument, `make` builds the **first** target in the file.

**When does make rebuild?** A target that is a file is rebuilt if it does not exist or if any prerequisite has a **modification time newer** than the target. That is how `make` recompiles only the changed sources of a C program. Targets that are *actions* rather than files (`test`, `clean`) should be declared `.PHONY`, so they always run even if a file with that name exists. `make -n` prints the commands without running them.

Variables are set with `NAME = value` and used as `$(NAME)`. Inside a recipe, **automatic variables** give the rule's pieces: `$@` is the target, `$<` is the first prerequisite and `$^` is all prerequisites. A **pattern rule** such as `%.o: %.c` describes how to build any `.o` file from the `.c` file with the same stem, and `make -j4` runs independent recipes in parallel. Each recipe line runs in its own shell, so `cd dir` on one line does not affect the next line; join commands with `&&` on one line when needed.

For Python projects, a Makefile is a convenient front door: `make setup`, `make test`, `make lint` document and standardize how everyone runs the project. Other tools (`just`, `npm` scripts, `tox`) do similar jobs, but `make` is everywhere.

@example
title: Reading a Makefile
problem: Given the rules below, what runs when you type `make app`, if `main.c` was edited a minute ago and `util.c` was not edited?

```make
app: main.o util.o
	cc -o app main.o util.o
main.o: main.c
	cc -c main.c
util.o: util.c
	cc -c util.c
```
step: To build `app`, make first checks its prerequisites `main.o` and `util.o`, recursively.
step: `main.c` is newer than `main.o`, so `main.o` is out of date and `cc -c main.c` runs.
step: `util.c` is older than `util.o`, so `util.o` is up to date and its recipe is skipped.
step: `main.o` was just rebuilt, so `app` is out of date and `cc -o app main.o util.o` runs. Two commands run in total.
answer: `cc -c main.c` then `cc -o app main.o util.o`
@example
title: Automatic variables
problem: Write one pattern rule that compiles any `NAME.c` into `NAME.o`, using automatic variables instead of repeating file names.
step: The target pattern is `%.o` and the prerequisite pattern is `%.c`: the `%` matches the same stem in both.
step: In the recipe, `$<` is the first prerequisite (the `.c` file) and `$@` is the target (the `.o` file).
step: The rule is:

```make
%.o: %.c
	cc -c $< -o $@
```
step: For the target `main.o` this expands to `cc -c main.c -o main.o`.
answer: `%.o: %.c` with the recipe `cc -c $< -o $@`
@mistakes
- Indenting recipe lines with spaces in a normal Makefile (it needs a tab), which causes the error "missing separator".
- Forgetting `.PHONY` on `test` or `clean`, so a file or directory of that name makes `make` say the target is up to date.
- Expecting `cd` to carry over to the next recipe line, when each line is a separate shell.
- Searching for an answer without reading the error message first, or pasting secrets into a public question.

tests:
```python
r = {"app": ["main.o", "util.o"], "main.o": ["main.c", "util.h"],
     "util.o": ["util.c", "util.h"]}
assert build_order(r, "app") == ["main.o", "util.o", "app"]
r2 = {"all": ["a", "b"], "a": ["c"], "b": ["c"], "c": []}
```

model:
```python
def build_order(rules, target):
    order = []
    seen = set()

    def visit(name):
        if name in seen or name not in rules:
            return
        seen.add(name)
        for prereq in rules[name]:
            visit(prereq)
        order.append(name)

    visit(target)
    return order
```
hint: Use a depth-first search that appends a target to the result after visiting its prerequisites.
hint: Keep a `seen` set so a shared prerequisite is built once, and ignore names that are not in `rules`.
solution: A post-order depth-first traversal lists every prerequisite before the target that needs it. The `seen` set avoids building a shared prerequisite twice, and names missing from `rules` are plain source files. Time is linear in the number of rules and prerequisite entries.

tests:
```python
assert expand_recipe("cc -o $@ $^", "app", ["a.o", "b.o"]) == "cc -o app a.o b.o"
assert expand_recipe("cc -c $< -o $@", "main.o", ["main.c", "util.h"]) == "cc -c main.c -o main.o"
```

model:
```python
def expand_recipe(command, target, prereqs):
    first = prereqs[0] if prereqs else ""
    result = command.replace("$@", target)
    result = result.replace("$<", first)
    result = result.replace("$^", " ".join(prereqs))
    return result
```
hint: Use `str.replace` once for each of the three variables.
hint: Compute the value of `$<` first: the first prerequisite if the list is not empty, otherwise `""`.
solution: Each automatic variable is a simple textual substitution: the target, the first prerequisite, and the space-joined prerequisites. The empty-list case gives an empty string for `$<` and `$^`.
