@article
**Planning** is the problem of finding a sequence of actions that achieves a goal. Search on an unstructured state space (weeks 2 and 3) cannot exploit what an action means. A planning language represents states and actions with logic, so an algorithm can look inside actions and derive good heuristics automatically.

### Classical planning and STRIPS

**Classical planning** assumes a fully observable, deterministic, static, discrete environment. In the **STRIPS** style, a **state** is a set of ground **fluents** (facts that can change), for example `{at_A, pkg_A}`. The **closed-world assumption** says that any fluent not in the set is false. A **goal** is a set of fluents that must all hold. An **action** has:

- **preconditions**: fluents that must be in the state for the action to be applicable;
- an **add list**: fluents that become true;
- a **delete list**: fluents that become false.

If $\text{pre}(a) \subseteq s$, then
$$\text{result}(s, a) = (s \setminus \text{del}(a)) \cup \text{add}(a).$$
The delete list is applied first, so a fluent that is in both lists ends up true. This answers the **frame problem** in the simplest way: everything not mentioned by the action stays as it was. The standard language is **PDDL**, which writes **action schemas** with variables, such as $\text{Fly}(p, a, b)$, that expand into ground actions. A schema over $P$ planes and $A$ airports with $a \ne b$ has $P \cdot A \cdot (A - 1)$ ground actions.

### Progression and regression

**Forward (progression) search** starts at the initial state and applies applicable actions until a state satisfies the goal. Any of the search algorithms of earlier weeks work, for example breadth-first search for a shortest plan or A* with a heuristic.

**Backward (regression) search** starts from the goal: for a **relevant** action (one that adds some goal fluent and deletes no goal fluent), the regressed goal is $(g \setminus \text{add}(a)) \cup \text{pre}(a)$. It often has a smaller branching factor, but it searches over goal descriptions.

### Heuristics from relaxation

An informative heuristic comes from a **relaxed problem**. The **delete relaxation** ignores the delete lists, so fluents once true stay true. Its optimal plan length $h^+$ is admissible. A cheap related estimate builds **layers** as in a **planning graph**: layer 0 is the initial state; each next layer adds the effects of every action whose preconditions are all present. The first layer that contains all the goal fluents is a lower bound on the plan length (the **max** heuristic), so it is admissible. If the goal never appears, the problem is unsolvable. Heuristics such as FF, built from a relaxed plan, are not admissible but guide planners well. The **GraphPlan** algorithm extends the planning graph with **mutex** (mutually exclusive) links and extracts a plan from it.

### Other planning formalisms

**Partial-order planning** searches the space of plans and leaves the order of independent actions unspecified until needed. **Hierarchical task network (HTN)** planning decomposes high-level tasks into subtasks using domain knowledge. **SAT-based** planning encodes "is there a plan of length $k$?" as a satisfiability problem. Real systems relax the classical assumptions with probabilities (next week's topics), partial observability and continuous time.

@example
title: A STRIPS action and its effect
problem: The schema $\text{Fly}(p, a, b)$ has preconditions $\text{At}(p, a)$ and $\text{Plane}(p)$, add list $\{\text{At}(p, b)\}$ and delete list $\{\text{At}(p, a)\}$. In the state $\{\text{At}(P1, SFO), \text{Plane}(P1)\}$, apply $\text{Fly}(P1, SFO, JFK)$.
step: Ground the schema: preconditions $\{\text{At}(P1, SFO), \text{Plane}(P1)\}$, add $\{\text{At}(P1, JFK)\}$, delete $\{\text{At}(P1, SFO)\}$.
step: Check applicability: both preconditions are in the state, so the action is applicable.
step: Delete first: $\{\text{At}(P1, SFO), \text{Plane}(P1)\} \setminus \{\text{At}(P1, SFO)\} = \{\text{Plane}(P1)\}$.
step: Then add: the new state is $\{\text{Plane}(P1), \text{At}(P1, JFK)\}$. Plane(P1) was not mentioned in the effects, so it is unchanged.
answer: $\{\text{Plane}(P1), \text{At}(P1, JFK)\}$.

@example
title: Counting planning-graph layers
problem: Actions: `boil` needs `water, kettle` and adds `hot`; `steep` needs `hot, teabag` and adds `tea`. The initial state is `{water, kettle, teabag}` and the goal is `{tea}`. How many layers does the delete-relaxation estimate give?
step: Layer 0 is the initial state `{water, kettle, teabag}`.
step: Layer 1: `boil` is applicable (its preconditions are in layer 0), so `hot` is added. `steep` is not yet applicable. The layer is `{water, kettle, teabag, hot}`.
step: Layer 2: `steep` is now applicable and adds `tea`. The goal `{tea}` is contained in layer 2.
answer: 2 layers, which equals the length of the only plan (`boil`, then `steep`).

@mistakes
- Applying the add list before the delete list, which wrongly removes a fluent that the action also adds.
- Forgetting the closed-world assumption: a fluent that is absent from the state is false, not unknown.
- Assuming the delete-relaxation estimate is exact: ignoring deletes can make the estimate smaller than the true plan length (but never larger, for the layer count).
- Counting ground actions of $\text{Fly}(p, a, b)$ with $a = b$ allowed, when the schema requires different airports.

```python
from collections import deque


def plan(initial, goal, actions):
    start = frozenset(initial)
    goal = frozenset(goal)
    parent = {start: None}
    frontier = deque([start])
    while frontier:
        state = frontier.popleft()
        if goal <= state:
            steps = []
            while parent[state] is not None:
                state, name = parent[state]
                steps.append(name)
            return steps[::-1]
        for name in sorted(actions):
            act = actions[name]
            current = set(state)
            if act["pre"] <= current:
                nxt = frozenset((current - act["del"]) | act["add"])
                if nxt not in parent:
                    parent[nxt] = (state, name)
                    frontier.append(nxt)
    return None
```
hint: Store for each reached state the pair `(previous state, action name)` so the plan can be rebuilt.
hint: Test the goal when a state is removed from the queue, and apply every action whose preconditions hold, in sorted name order.
solution: Breadth-first search on the state space, with states as frozensets so that they can be dictionary keys. The first goal state removed from the queue is at the smallest depth, so the rebuilt plan is shortest. A `None` return means the queue emptied without reaching the goal.

model:
```python
def relaxed_layers(initial, goal, actions):
    layer = set(initial)
    goal = set(goal)
    index = 0
    while True:
        if goal <= layer:
            return index
        new = set(layer)
        for act in actions.values():
            if act["pre"] <= layer:
                new |= act["add"]
        if new == layer:
            return None
        layer = new
        index += 1
```
hint: Keep the current layer as a set and build the next one from the same previous layer, not from the one you are still building.
hint: Stop with `None` when a new layer equals the previous one, because nothing more can ever be added.
solution: Each iteration adds the effects of every currently applicable action at once, so the layer index counts parallel steps. In the logistics example `at_B` and `in_truck` appear in layer 1, which makes `unload_B` applicable and gives `pkg_B` in layer 2, an estimate of 2 against a real plan length of 3.
