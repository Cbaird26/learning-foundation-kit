@article
A **consistency model** is a contract between a replicated data store and its clients: it says which results of reads and writes are allowed when operations overlap and replicas disagree. Stronger models are easier to program against but cost latency and availability.

Operations are described by an **invocation** time and a **response** time; two operations are **concurrent** if their intervals overlap. A **history** is the list of operations with their intervals and results. Below, a register $x$ starts at 0.

### The models

**Linearizability** (strong consistency). Every operation appears to take effect atomically at one instant between its invocation and its response, and the resulting order obeys real time: if operation $A$ responds before $B$ is invoked, $A$ is ordered before $B$. Formally, there must be a total order of all operations that (1) respects real-time precedence and (2) is a legal sequential execution (each read returns the latest preceding write). A read that starts after a write completed must therefore see that write or a later one.

**Sequential consistency.** There is a total order of all operations that is a legal sequential execution and respects each *process's program order*, but it need **not** respect real time across processes. Every linearizable history is sequentially consistent, not conversely.

**Causal consistency.** Writes that are causally related (the happened-before relation of Lesson 3: a process reads a value and then writes, or writes after earlier writes in its own session) must be seen in the same order by everyone. Concurrent writes may be seen in different orders by different processes.

**Eventual consistency.** If no new writes occur, all replicas eventually converge to the same value. It says nothing about what reads return in the meantime; it is the weakest of these models and the cheapest to provide.

Strength: linearizable $\Rightarrow$ sequential $\Rightarrow$ causal $\Rightarrow$ eventual (each implies the next).

### Session guarantees

Weaker stores often add per-client guarantees:

- **Read-your-writes:** a client's read reflects its own earlier writes.
- **Monotonic reads:** once a client has seen a value, it never later sees an older one.
- **Monotonic writes:** a client's writes are applied in the order issued.
- **Writes-follow-reads:** a write is ordered after the writes whose values the client read.

```python
def monotonic_reads_ok(versions):
    return all(a <= b for a, b in zip(versions, versions[1:]))
```

### Checking a history

To test linearizability of a small history, search for an order: repeatedly choose an operation that no other remaining operation must precede (no remaining operation *responded before it was invoked*), check that a read returns the current value, apply writes, and recurse. The problem is NP-complete in general, but checkers work well in practice for realistic histories.

### Why weaker models exist

Linearizability needs coordination on every operation, which costs round trips across replicas, and a minority partition cannot serve requests (Lesson 8). Geo-replicated and highly available stores choose weaker models to answer from the nearest replica with low latency, then reconcile later (with last-write-wins, vector clocks, or merge functions such as CRDTs). Applications then have to tolerate stale reads and conflicts.

@example
title: Is the history linearizable?
problem: A register starts at 0. Client A writes 1 during the interval [0, 5]. Client B reads during [1, 2] and gets 0. Client C reads during [3, 4] and gets 1. Is the history linearizable?
step: A's write overlaps both reads, so it may be ordered before or after either of them. The reads do not overlap each other: B's read (ends at 2) precedes C's read (starts at 3).
step: Try the order: B's read (returns 0), then the write of 1, then C's read (returns 1). The order respects real time (B before C) and each read returns the latest preceding write (initial 0, then 1).
step: Since a legal order exists, the history is linearizable.
step: If C had read 0 instead, we would need the write after both reads; but then C reads 0 after B read 0 with the write still pending, which is also legal. A violation would be B reading 1 and then C reading 0, because after a read returns 1 the write must already have taken effect.
answer: linearizable

@example
title: Sequential but not linearizable
problem: Client A writes x=1 during [0, 2]. After A's write completed, client B reads x during [3, 4] and gets 0. Which models allow this?
step: Linearizability: A's write finished (time 2) before B's read started (time 3), so any linearization places the write first, and the read must return 1. The history is not linearizable.
step: Sequential consistency: only program order per process must be respected. Order B's read first (returns the initial 0), then A's write. Each process's own order is preserved, so it is sequentially consistent.
step: Causal consistency: no causal link between the write and the read, so it is allowed; eventual consistency allows it too.
answer: sequential, causal and eventual allow it; linearizable does not

@mistakes
- Confusing linearizability with sequential consistency: only the first respects real-time order across clients.
- Thinking eventual consistency promises anything about reads before convergence.
- Treating concurrent operations as "must be ordered by start time"; concurrent operations may take effect in either order.
- Assuming a store that guarantees read-your-writes is also monotonic or causal; session guarantees are separate.

model:
```python
def linearizable(history):
    def search(remaining, state):
        if not remaining:
            return True
        for i, (s, e, kind, v) in enumerate(remaining):
            blocked = any(o[1] < s for j, o in enumerate(remaining)
                          if j != i)
            if blocked:
                continue
            if kind == "r" and v != state:
                continue
            new_state = v if kind == "w" else state
            rest = remaining[:i] + remaining[i + 1:]
            if search(rest, new_state):
                return True
        return False

    return search(list(history), 0)
```
hint: Build the order one operation at a time with recursion, tracking the register's current value.
hint: An operation may go next only if no other remaining operation ended before it started. A read may go next only if its value equals the current state; a write changes the state. Try every allowed choice and backtrack.
solution: Backtracking search: at each step pick any remaining operation that nothing else must precede, check reads against the current value, update the state on writes, and recurse. If some branch consumes all operations, a legal order exists. The search is exponential in the worst case, fine for histories of a few operations.

def read_your_writes_ok(ops):
    last_write = 0
    for kind, version in ops:
        if kind == "w":
            last_write = version
        elif version < last_write:
            return False
    return True
