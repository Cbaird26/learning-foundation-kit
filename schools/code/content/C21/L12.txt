### Containers

A **container** is an ordinary process (or group of processes) on a Linux host, given an isolated view of the system. Two kernel features do the work: **namespaces** limit what the process can *see* (its own process IDs, network interfaces, mount points, hostname, users) and **control groups (cgroups)** limit what it can *use* (CPU, memory, I/O). Unlike a virtual machine, a container does **not** run its own kernel: all containers on a host share the host kernel. They therefore start in milliseconds to seconds and use little memory, but provide weaker isolation than a VM's hypervisor boundary, so a kernel vulnerability can affect every container on the host.

A container runs from an **image**, an immutable stack of read-only **layers** (file system changes) plus metadata. Layers are shared and cached, so images that build on a common base download and store the base once. Images are built from a recipe such as a Dockerfile and stored in a **registry**:

```text
FROM python:3.13-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["python", "app.py"]
```

Copying the dependency file and installing before copying the source lets the build cache reuse the slow install layer when only code changes. Containers should be **immutable and disposable**: configuration comes from the environment, state lives outside in volumes or services.

### Orchestration with Kubernetes

Running thousands of containers needs an **orchestrator** to place, restart, scale and connect them. In Kubernetes the **control plane** has an API server, a store of cluster state (etcd, which itself uses Raft, Lesson 7), a **scheduler** that assigns Pods to nodes, and **controllers**. Each worker **node** runs a kubelet and a container runtime.

- A **Pod** is the smallest deployable unit: one or more containers sharing a network namespace and volumes. Pods are mortal and get new IP addresses when recreated.
- A **Deployment** declares a desired number of replicas of a Pod template. It manages **ReplicaSets**, which manage the Pods, and performs **rolling updates** (replace Pods gradually) and rollbacks.
- A **Service** gives a set of Pods (chosen by labels) a stable virtual IP and DNS name and load-balances across the *ready* Pods.
- **Probes** report health: a **liveness** probe failure makes the kubelet restart the container; a **readiness** probe failure removes the Pod from Service endpoints; a **startup** probe protects slow starters.

```text
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
        - name: web
          image: example/web:1.4
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /ready
              port: 8080
```

The central idea is **declarative desired state** with a **reconciliation loop**: controllers repeatedly compare desired state (3 replicas) with observed state (2 running) and act to close the gap (start one). The loop makes the system self-healing and idempotent: running it again changes nothing once the states match. The Horizontal Pod Autoscaler uses the formula of Lesson 11 to change the replica count.

```python
def reconcile(desired, running):
    if len(running) < desired:
        return {"create": desired - len(running), "delete": []}
    return {"create": 0, "delete": running[desired:]}
```

### Observability

**Observability** is the ability to understand a system's internal state from its outputs. The three classic signals are **metrics** (numeric time series, cheap to store, good for dashboards and alerts), **logs** (timestamped event records, best structured as JSON) and **traces** (the path of one request through many services; a **trace ID** is propagated in request headers and each service records a **span**).

Four **golden signals** to watch for a service: **latency**, **traffic**, **errors** and **saturation**. Report latency as **percentiles** rather than averages: the 99th percentile (p99) is the value that 99% of requests are at or below, and averages hide the slow tail. By the nearest-rank method, the $p$-th percentile of $n$ sorted values is the value at rank $\lceil p n / 100 \rceil$.

A **service level indicator (SLI)** is a measurement (fraction of requests under 300 ms), a **service level objective (SLO)** a target for it (99.9% over 30 days), and the **error budget** is what the SLO permits to fail: $(1 - \text{SLO}) \times \text{period}$. Teams spend the budget on releases and risk, and slow down when it is used up. Alerts should fire on symptoms users feel, not on every internal cause.

@example
title: Percentile by nearest rank
problem: Ten request latencies in milliseconds are 12, 15, 11, 90, 14, 13, 16, 12, 400, 18. What are the median (p50) and p90 by the nearest-rank method, and why does the average mislead?
step: Sort: 11, 12, 12, 13, 14, 15, 16, 18, 90, 400.
step: p50: rank $\lceil 50 \times 10 / 100 \rceil = 5$, the 5th value is 14 ms.
step: p90: rank $\lceil 90 \times 10 / 100 \rceil = 9$, the 9th value is 90 ms.
step: The mean is $(11+12+12+13+14+15+16+18+90+400)/10 = 60.1$ ms, which is neither what a typical user sees (14) nor what the slow tail sees (90 to 400). Percentiles describe both.
answer: p50 = 14 ms, p90 = 90 ms

@example
title: One reconciliation step
problem: A Deployment wants 3 replicas. Observed running Pods: `web-a`, `web-b`, `web-c`, `web-d` (4 Pods, after a manual change). What does the controller do, and what if `web-c` then crashes?
step: Desired 3, observed 4: one surplus. The controller deletes one Pod (in the model `reconcile(3, [...])`, the last one in the list, `web-d`).
step: Now 3 are running and the states match; the next pass of the loop does nothing.
step: When `web-c` crashes, observed becomes 2 against desired 3. The controller creates one new Pod. The Deployment converges back to 3 without human action.
answer: delete web-d; later create one Pod

@mistakes
- Believing a container has its own kernel like a VM; containers share the host kernel, so isolation is weaker.
- Using the average latency for a service level objective instead of a percentile, hiding the slow tail.
- Treating Pods as permanent: their names and IPs change, which is why clients use a Service.
- Confusing liveness with readiness: a failing liveness probe restarts the container, a failing readiness probe only removes the Pod from load balancing.

@quiz code
prompt: Write `first_fit(pods, nodes)` for a simple scheduler. `pods` is a list of CPU requests (integers) and `nodes` is a list of free CPU capacities (integers). Process the pods in order and place each on the first node (lowest index) whose remaining capacity is at least the pod's request, reducing that node's remaining capacity. Return a list with, for each pod, the index of its node, or `None` if no node fits (that pod stays pending and uses no capacity). Do not modify the `nodes` argument.
starter:
```python
def first_fit(pods, nodes):
    pass
```
tests:
```python
assert first_fit([2, 3, 1], [4, 4]) == [0, 1, 0]
assert first_fit([5], [4, 4]) == [None]
assert first_fit([], [1]) == []
assert first_fit([4, 4, 1], [4, 4]) == [0, 1, None]
free = [4, 4]
assert first_fit([2, 2, 2], free) == [0, 0, 1]
assert free == [4, 4]
```
model:
```python
def first_fit(pods, nodes):
    remaining = list(nodes)
    placement = []
    for request in pods:
        chosen = None
        for i, free in enumerate(remaining):
            if free >= request:
                chosen = i
                remaining[i] -= request
                break
        placement.append(chosen)
    return placement
```
hint: Work on a copy of the capacities so the argument is unchanged.
hint: For each pod scan the nodes in order, take the first with enough room, subtract the request, and record the index (or `None`).
solution: A copy of `nodes` tracks remaining capacity. Each pod goes to the first node that fits, which is the first-fit heuristic; real schedulers also score nodes by other factors. A pod that fits nowhere is recorded as `None` and consumes nothing.
