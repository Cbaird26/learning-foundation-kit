@article
Replication copies the same data to several nodes. **Partitioning** (also called **sharding**) is the opposite: it splits a dataset so that each node holds only a portion, which lets storage and traffic scale beyond one machine. Real systems combine both: each partition is replicated.

### Partitioning strategies

**Range partitioning** assigns contiguous key ranges to partitions (for example keys `A` to `F` on shard 1). Range queries are efficient because neighbouring keys live together, but sequential keys (timestamps, auto-increment ids) create a **hot spot**, since all new writes land in the last range. Partitions can be split when they grow.

**Hash partitioning** applies a hash function to the key and assigns by hash value. It spreads load evenly and avoids sequential hot spots, but range queries must contact every partition. Even hash partitioning cannot fix a single **hot key** that receives a large share of traffic; that needs caching or splitting the key.

### The problem with `hash(key) mod N`

Suppose key $k$ lives on node $k \bmod N$. When a node is added, $N$ becomes $N+1$, and for most keys $k \bmod N \ne k \bmod (N+1)$. About a fraction $N/(N+1)$ of all keys move, which causes a storm of data transfer and cache misses exactly when the cluster is under change.

### Consistent hashing

**Consistent hashing** hashes both nodes and keys onto the same circular space, the **hash ring** (for example integers 0 to $2^{32}-1$ that wrap around). A key is stored on the first node found going **clockwise** from the key's position (at or after it, wrapping past the top back to 0).

When a node joins, it takes over only the keys between its predecessor and itself, which come from its successor: on average **$K/N$ of $K$ keys move** (not almost all). When a node leaves, its keys go to its successor. Plain consistent hashing can distribute unevenly because a few random points divide the circle unequally, so each physical node is given many positions, called **virtual nodes** (vnodes). Vnodes smooth the load and let a more powerful machine take more vnodes; when a node fails, its load is spread over many others rather than dumped on one successor.

```python
def owner(positions, h):
    """positions: dict node -> ring position; h: key hash."""
    ahead = [(p, n) for n, p in positions.items() if p >= h]
    return min(ahead)[1] if ahead else min((p, n) for n, p in positions.items())[1]
```

### Replication on the ring

To keep $r$ copies, store the key on its owner and the next $r - 1$ **distinct physical nodes** clockwise (the **preference list**). With vnodes, skip positions that belong to a node already chosen. A coordinator can then use quorum reads and writes (Lesson 5) over that list, and a failed node's data can be repaired from its successors. Consistent hashing, vnodes, quorums, vector-clock-style versions and anti-entropy together describe the design of Dynamo-style stores.

Other approaches to the same problem include **rendezvous hashing** (each key goes to the node with the highest hash of the pair key and node) and a **directory service** that maps ranges to nodes explicitly, as in distributed file systems with a metadata server plus chunk servers. A directory gives full control over placement but the directory itself must be replicated and kept consistent.

@example
title: Lookups on a ring
problem: A ring has positions 0 to 99. Nodes: A at 10, B at 40, C at 70. Where do keys with hashes 55, 95 and 10 go? What happens when D joins at position 50?
step: Key 55: the first node at or after 55 clockwise is C (70).
step: Key 95: nothing at or after 95, so wrap around to the smallest position: A (10).
step: Key 10: a node at exactly 10 is at or after the key, so A owns it.
step: D joins at 50. It takes keys in the range (40, 50] from C, its successor. Keys 55 (still C), 95 (still A) and 10 (still A) are unchanged; only keys with hashes 41 to 50 move.
answer: 55 goes to C, 95 goes to A, 10 goes to A; D takes only keys 41 to 50 from C

@example
title: Moving keys with modulo hashing
problem: Keys 0 to 11 are placed by `k mod 3`. A fourth node is added and placement becomes `k mod 4`. How many of the 12 keys change node?
step: Compare `k mod 3` and `k mod 4` for each key: keys 0, 1 and 2 give identical values.
step: Key 3: 0 versus 3, moves. Key 4: 1 versus 0, moves. Key 5: 2 versus 1, moves.
step: Keys 6, 7, 8, 9, 10 and 11 give 0 versus 2, 1 versus 3, 2 versus 0, 0 versus 1, 1 versus 2, 2 versus 3: all differ.
step: Only keys 0, 1 and 2 stay, so 9 of 12 keys (75%) move. A consistent-hashing ring would move about $12/4 = 3$ keys on average.
answer: 9 keys

@mistakes
- Using `hash(key) mod N` for a cluster that changes size, which remaps most keys.
- Forgetting the wrap-around case, where a key beyond the last node goes to the first node.
- Choosing the next $r-1$ *positions* instead of the next distinct *physical nodes* as replicas, so two copies land on the same machine.
- Assuming hash partitioning supports efficient range scans or removes the hot-key problem.

```python
def owner(positions, h):
    best = None
    for node, pos in positions.items():
        if pos >= h and (best is None or pos < positions[best]):
            best = node
    if best is not None:
        return best
    return min(positions, key=positions.get)
```

model:
```python
def replicas_for(positions, h, r):
    ordered = sorted(positions, key=positions.get)
    start = 0
    for i, node in enumerate(ordered):
        if positions[node] >= h:
            start = i
            break
    else:
        start = 0
    return [ordered[(start + k) % len(ordered)] for k in range(r)]
```
hint: Sort the nodes by position first; then the preference list is a run of consecutive nodes in that order.
hint: Find the index of the first node with position `>= h` (or 0 if there is none), then take `r` nodes from there using `% len(ordered)` to wrap around.
solution: With the nodes in ring order, the owner is the first node at or after the key, and the other replicas are the following nodes, wrapping at the end. With one position per node the nodes are already distinct physical machines.

@quiz mc
prompt: What is the main purpose of giving each physical node many virtual nodes on a consistent hash ring?
choice: To reduce the number of physical nodes needed
choice: To make range queries efficient
choice*: To even out the load and spread a failed node's keys over many nodes

solution: Many positions per node average out the random arc sizes, so load is more even, a bigger machine can hold more vnodes, and when a node fails its keys scatter over many successors instead of overloading one. Vnodes do not help range queries or replace replication.
