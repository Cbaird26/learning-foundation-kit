@article
**Replication** keeps copies of the same data or service on several machines. It serves three goals: **availability** (the service survives crashes), **performance** (reads served by nearby or many replicas), and **durability** (data survives the loss of a disk or a site). The price is the central problem of the next lessons: keeping the copies consistent while messages are delayed or lost and nodes crash.

### Primary-backup

One replica, the **primary**, accepts all writes and forwards them to the **backups**. Clients may read from the primary only, or from backups too.

- **Synchronous** replication: the primary acknowledges a write only after the backups confirmed it. A failover loses no acknowledged write, but writes are slower and block if a backup is unreachable.
- **Asynchronous** replication: the primary acknowledges immediately and ships changes later. Writes are fast, but a primary crash can **lose acknowledged writes**, and backups show **replication lag** (stale reads).

Failover raises its own questions: who decides the primary is dead (a timeout may be wrong), and how do you prevent two nodes from both acting as primary (**split brain**)? Consensus (Lesson 7) is the clean answer.

### State machine replication

A service is a deterministic **state machine**: its state is a function of the sequence of commands applied. If every replica starts in the same state and applies the **same commands in the same order**, all replicas stay identical. The hard part is agreeing on the order, which is exactly what a consensus-based replicated log (Paxos, Raft) provides. Commands must be deterministic: no local clocks, no random numbers, no reading of external state during execution.

```python
def apply_log(log):
    state = {}
    for entry in log:
        if entry[0] == "set":
            state[entry[1]] = entry[2]
        else:
            state.pop(entry[1], None)
    return state
```

### Chain replication

Replicas form a chain. Writes enter at the **head** and propagate along the chain; the write is acknowledged when the **tail** has it, and reads are served by the tail. Because the tail has only fully replicated writes, reads are strongly consistent, and the work is spread across nodes.

### Quorum replication

With $N$ replicas, a write must be acknowledged by $W$ replicas and a read must contact $R$ replicas. If

$$R + W > N,$$

then every read quorum overlaps every write quorum in at least one replica, so a read contacts at least one replica holding the latest acknowledged write. Each stored value carries a **version** (a number, timestamp or vector clock) so the reader returns the value with the highest version. With $R + W \le N$ a read may miss the latest write.

Typical choices for $N = 3$: $W=2, R=2$ (balanced, tolerates one failure for both); $W=3, R=1$ (fast reads, writes need all replicas); $W=1, R=3$ (fast writes). Quorum systems with $R+W>N$ are not automatically linearizable: concurrent writes, failed writes that landed on some replicas, and **sloppy quorums** (using substitute nodes during failures) can still expose stale or conflicting values, which is why repair mechanisms exist: **read repair** (the reader updates stale replicas it noticed) and **anti-entropy** (background comparison of replicas).

Replicas can tolerate $N - W$ failures for writes and $N - R$ for reads.

@example
title: Replication lag in asynchronous primary-backup
problem: A primary acknowledges writes immediately and ships each write to its backup one step later. The client writes x=1, then x=2, then the primary crashes before shipping the second write, and the backup is promoted. What does a client read, and what was lost?
step: After `write(x, 1)` the primary replies to the client and sends the update to the backup, which applies it: backup x is 1.
step: After `write(x, 2)` the primary replies immediately. It crashes before the update leaves.
step: The backup is promoted. Its state still has x=1.
step: A read returns 1. The acknowledged write x=2 is lost. Synchronous replication would not have acknowledged x=2 until the backup had it.
answer: reads 1; the acknowledged write x=2 is lost

@example
title: Choosing quorum sizes
problem: With N = 5, writes use W = 4. What is the smallest R that guarantees reads see the latest acknowledged write, and how many replica failures can reads and writes each tolerate?
step: We need $R + W > N$, so $R + 4 > 5$ and $R \ge 2$. The smallest is 2.
step: Writes tolerate $N - W = 5 - 4 = 1$ failed replica.
step: Reads tolerate $N - R = 5 - 2 = 3$ failed replicas.
step: This configuration favors reads at the cost of fragile writes; $W = 3, R = 3$ balances both at two tolerated failures each.

@mistakes
- Assuming asynchronous replication never loses acknowledged writes after a primary failure.
- Applying non-deterministic commands (current time, random values) on each replica of a state machine, so replicas diverge.
- Believing $R + W > N$ alone makes a quorum store linearizable; concurrent writes and sloppy quorums break that.
- Computing failure tolerance from the wrong quorum: writes tolerate $N - W$ failures and reads $N - R$.

def quorum_read(responses):
    return max(responses, key=lambda r: r[0])[1]

def min_read_quorum(n, w):

@quiz ms
prompt: Which statements about replication are true?
choice*: Synchronous primary-backup replication does not lose acknowledged writes when the primary fails (assuming at most the primary fails).
