@article
**Batch processing** reads a large bounded input, computes, and writes a result; **stream processing** handles an unbounded, continuously arriving input. Both are programmed as dataflows that a framework runs on many machines and recovers when some fail.

### The MapReduce model

A job is defined by two user functions:

- `map(record)` emits zero or more intermediate **(key, value)** pairs.
- `reduce(key, values)` receives one key with *all* its values and emits a result.

The framework does the rest in three phases:

1. **Map:** the input is split into chunks and each chunk is processed by a map task, preferably on a machine that stores that chunk (**data locality**).
2. **Shuffle:** intermediate pairs are partitioned by key (commonly `hash(key) mod R` for $R$ reduce tasks), transferred across the network and sorted or grouped by key, so each key's values arrive together at one reducer.
3. **Reduce:** each reduce task applies `reduce` to every key it owns and writes output.

```python
def mapreduce(docs, map_fn, reduce_fn):
    groups = {}
    for doc in docs:
        for key, value in map_fn(doc):
            groups.setdefault(key, []).append(value)   # the shuffle
    return {k: reduce_fn(k, vs) for k, vs in groups.items()}

def wc_map(doc):
    return [(w.lower(), 1) for w in doc.split()]

def wc_reduce(key, values):
    return sum(values)
```

This single-process driver captures the semantics; a real framework runs the loop on thousands of machines.

### Making it practical

- **Fault tolerance by re-execution.** Map and reduce functions are deterministic and tasks have no side effects other than writing their own output, so if a worker dies the master simply runs the task again elsewhere. Map output is stored on the mapper's local disk, reduce output in the distributed file system. Slow workers (**stragglers**) are handled by **speculative execution**: launch a duplicate and take whichever finishes first.
- **Combiner.** A combiner is a local, map-side reduce that pre-aggregates pairs before the shuffle (for word count, summing counts per word on each mapper), cutting network traffic. It is valid when the reduce operation is associative and commutative.
- **Skew.** If one key has far more values than others (a very common word), one reducer becomes the bottleneck; remedies include splitting the key or combiners.
- **Limitations.** Each MapReduce stage writes to disk and the model fits multi-stage and iterative algorithms poorly. Later dataflow engines express a job as a **directed acyclic graph** of operators, keep intermediate data in memory where possible, and record **lineage** (how a dataset was computed from others) so lost partitions can be recomputed.

### Stream processing

A stream processor consumes events continuously (often from a log or message queue) and keeps state. Key ideas:

- **Event time** is when the event happened; **processing time** is when the system sees it. Events arrive late and out of order, so correct results use event time.
- A **window** groups events: **tumbling** windows are fixed-size and disjoint (every minute on the minute), **sliding** windows overlap, **session** windows close after a gap of inactivity.
- A **watermark** is the system's estimate that no events older than some event time are still coming. When the watermark passes a window's end, the window can be emitted; later arrivals are *late data*, which are dropped, handled separately, or trigger an update.
- **Fault tolerance** comes from periodically **checkpointing** operator state together with the input offsets; after a failure the job rewinds to the checkpoint and replays. Combined with idempotent or transactional output, the *effect* on results is exactly-once (Lesson 2).

@mistakes
- Forgetting that `reduce` receives all values of one key together; the framework, not the user, groups them.
- Using a combiner for an operation that is not associative and commutative, such as computing an average from partial averages.
- Mixing up event time and processing time, so late events end up in the wrong window.
- Writing map or reduce functions with side effects or randomness, which breaks safe re-execution.

```python
def tumbling_counts(events, size):
    windows = {}
    for t, key in events:
        start = (t // size) * size
        counts = windows.setdefault(start, {})
        counts[key] = counts.get(key, 0) + 1
    return windows
```
hint: Compute each event's window start first, then update a counter for that window and key.
hint: Use `windows.setdefault(start, {})` to get the inner dict and `counts.get(key, 0) + 1` to count.
solution: Integer division maps each timestamp to its window start; a dict of dicts accumulates the counts. An event exactly on a boundary (timestamp 5 with size 5) starts the next window, because windows are half-open `[start, start + size)`.
