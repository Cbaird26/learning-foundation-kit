@article
Machines in a distributed system communicate only by sending messages. Two styles dominate: **remote procedure call** (RPC), which makes a remote request look like a function call, and **message passing**, in which components exchange messages through channels or queues.

### Remote procedure call

An RPC lets a client call `get_user(42)` as if it were local. A **client stub** (generated from an interface definition) **marshals** the arguments into bytes (serialization, for example JSON or Protocol Buffers), sends a request message over the network, and blocks. The server's **skeleton** unmarshals the request, calls the real procedure, and marshals the result into a reply. Modern frameworks such as gRPC follow this model.

RPC hides the network but cannot hide its failures. A local call either returns or the program dies; a remote call can also **time out** with an unknown outcome (Lesson 1). Good RPC systems therefore expose **deadlines**, error codes and retry policies instead of pretending calls are local. Other differences: arguments are passed by value (pointers are meaningless on another machine), latency is orders of magnitude higher, and the two sides may run different versions of the code, so message formats need a compatibility plan (adding optional fields, never reusing field numbers).

### Call semantics

What does the caller know when the call returns or fails?

- **At-most-once**: the procedure runs zero or one times. The client does not retry, or the server filters duplicates. A timeout leaves the outcome unknown.
- **At-least-once**: the client retries until it gets a reply, so the procedure runs one or more times. Safe only for idempotent operations.
- **Exactly-once** delivery is impossible in general over an unreliable network, because the sender cannot know whether a lost acknowledgment means the message was received. What systems achieve is **effectively-once processing**: at-least-once delivery plus **deduplication** on the receiver, using a unique request ID.

```python
class DedupServer:
    def __init__(self):
        self.balance = 0
        self.done = {}             # request id -> cached reply

    def deposit(self, req_id, amount):
        if req_id in self.done:    # duplicate: replay the stored reply
            return self.done[req_id]
        self.balance += amount
        self.done[req_id] = self.balance
        return self.balance
```

The reply is cached so a retry gets the same answer. The server must eventually discard old IDs (for instance with per-client sequence numbers or an expiry window), which bounds the guarantee.

### Message passing and queues

In **synchronous** communication the sender waits for a reply (RPC, HTTP request/response). In **asynchronous** communication the sender continues after handing the message to a channel. A **message queue** (a broker) stores messages durably, which *decouples* sender and receiver in time: the consumer may be down when the message is sent. Consumers acknowledge a message after processing it; if no acknowledgment arrives, the broker redelivers, giving at-least-once delivery. A consumer that crashes after processing but before acknowledging will see the message again, so consumers should be idempotent.

In **publish-subscribe**, publishers send to a *topic* and the system delivers each message to every subscriber of that topic; the publisher does not know who the subscribers are. A queue with competing consumers instead delivers each message to *one* consumer, sharing the work.

Ordering is a design choice: a single queue or partition can preserve order, but order across many partitions is generally not guaranteed.

@example
title: A lost reply with and without deduplication
problem: A client sends `deposit(req_id="r1", amount=10)` to a server whose balance is 0. The reply is lost and the client retries the same request. What balance results with the `DedupServer` above, and what would it be without the `done` table?
step: First arrival: `"r1"` is not in `done`, so the balance becomes 10 and `done["r1"] = 10`. The reply is lost in transit.
step: The client times out and resends the same ID `"r1"`.
step: Second arrival: `"r1"` is in `done`, so the server returns the cached 10 without touching the balance. The balance stays 10.
step: Without the table, the second arrival would add 10 again, giving 20: at-least-once delivery would become at-least-once execution.
answer: 10 with deduplication, 20 without

@example
title: Choosing a semantics
problem: Which call semantics fit (a) "charge the customer's card" and (b) "read the current temperature"?
step: (b) is a read with no side effects, so it is idempotent. At-least-once with retries is fine.
step: (a) has an external side effect that must not happen twice. Use a unique charge ID and have the payment service deduplicate on it, giving effectively-once processing.
step: Plain at-most-once (never retry) is also possible for (a), but the client then may not know whether the charge happened. The ID makes retrying safe.

@mistakes
- Believing RPC makes a remote call equivalent to a local one; it adds latency, partial failure and version skew.
- Claiming a network can provide exactly-once delivery; the realistic goal is effectively-once processing with deduplication.
- Retrying a non-idempotent call without a request ID.
- Acknowledging a queue message before processing it, so a crash after the acknowledgment loses the work.

```python
def send_with_retry(send, msg, max_tries):
    for _ in range(max_tries):
        reply = send(msg)
        if reply is not None:

    raise TimeoutError("no reply")
```

solution: A bounded loop that returns the first non-`None` reply and raises after the loop gives the required behavior. With `max_tries = 0` the loop never runs, so the error is raised immediately.

```python
import json

def encode_call(method, args):
    return json.dumps({"method": method, "args": args},
                      sort_keys=True, separators=(",", ":"))

def decode_call(text):
    d = json.loads(text)
    return d["method"], d["args"]
```

hint: Build the dict with both keys, pass the two keyword arguments, and in `decode_call` return a tuple.
solution: `encode_call` marshals a dict with `json.dumps` using sorted keys and compact separators, so the text is deterministic. `decode_call` unmarshals with `json.loads` and returns `(d["method"], d["args"])`.
