@article
The single-cycle processor is slow because each instruction occupies the whole datapath for one long cycle. **Pipelining** divides instruction execution into stages and overlaps different instructions in different stages, exactly as a laundry with a washer and a dryer starts the second load while the first is drying.

### The five-stage pipeline

The classic RISC pipeline has five stages:

1. **IF**: instruction fetch (read instruction memory at the PC).
2. **ID**: instruction decode and register read (and sign-extend the immediate).
3. **EX**: execute (ALU operation or address calculation; branches are resolved here in the simplest design).
4. **MEM**: data memory access (loads and stores).
5. **WB**: write back the result to the register file.

Between stages sit **pipeline registers** (IF/ID, ID/EX, EX/MEM, MEM/WB) that hold everything the next stage needs, so each stage works on a different instruction in each cycle. The clock period is set by the slowest stage (plus register overhead), not by the whole instruction.

An ideal pipeline with $k$ stages finishes $n$ instructions in $k+n-1$ cycles: the first instruction takes $k$ cycles to emerge and then one instruction completes per cycle. The **latency** of one instruction is not shorter (it is even slightly longer because of register overhead); the **throughput** approaches one instruction per cycle, up to $k$ times better than an unpipelined design with the same logic.

A **pipeline diagram** shows time across and instructions down:

```text
            1   2   3   4   5   6
add x1,..   IF  ID  EX  MEM WB
sub x4,..       IF  ID  EX  MEM WB
```

### Hazards

A **hazard** is a situation that prevents the next instruction from executing in its clock cycle.

- **Structural hazard**: two instructions need the same hardware at once. With one memory shared by instructions and data, a load in MEM would collide with a fetch in IF; the fix is separate instruction and data memories (or caches). The register file is written in WB and read in ID in the same cycle, which works by writing in the first half of the cycle and reading in the second.
- **Data hazard**: an instruction needs a result that an earlier instruction has not yet written. The kind that matters in this pipeline is read-after-write (RAW): `add x1, x2, x3` followed by `sub x4, x1, x5`.
- **Control hazard**: the next instruction to fetch is unknown until a branch resolves.

### Resolving data hazards

The simplest fix is a **stall** (a **bubble**): hold the dependent instruction in ID until the value is in the register file. Without forwarding, a dependent instruction one slot behind needs two stalls, and one two slots behind needs one.

**Forwarding** (bypassing) is better: the result already exists at the end of EX, so extra multiplexers route it from the EX/MEM register, or from the MEM/WB register, directly to the ALU inputs of the instruction that needs it. With forwarding, ALU-to-ALU dependences cost no stall at all. The exception is the **load-use hazard**: a load's data is not available until the end of MEM, so an instruction that uses it in the very next slot must stall **one** cycle even with forwarding. A compiler can often fill that slot with an independent instruction.

### Resolving control hazards

Do not wait: assume the branch is **not taken** and keep fetching sequentially. If the branch turns out to be taken, **flush** the wrongly fetched instructions (turn them into bubbles) and fetch from the target; this costs several cycles, the **branch penalty**. Real processors use **branch prediction**: a table of 2-bit saturating counters per branch predicts the direction, and accuracy above 90% is common, which makes the average penalty small.

### Limits

Pipelining improves throughput, not latency; deeper pipelines have faster clocks but larger penalties on every hazard and misprediction. The achieved **CPI** is $1+$ stall cycles per instruction.

@example
title: Forwarding removes the stall
problem: Draw the pipeline diagram for `add x1, x2, x3` followed by `sub x4, x1, x5` with forwarding. How many cycles in total, and how many stalls?
step: The `add` computes `x1` in EX during cycle 3. With forwarding, the value moves from the EX/MEM register to the ALU input in cycle 4, exactly when `sub` is in EX.
step: So `sub` need not wait: it follows one cycle behind with no bubble.

```text
            1   2   3   4   5   6
add x1,..   IF  ID  EX  MEM WB
sub x4,..       IF  ID  EX  MEM WB
```
step: Two instructions on a 5-stage pipeline take $5+2-1=6$ cycles, so there are 0 stalls.
answer: 6 cycles, no stalls (forwarding from EX/MEM to EX)

@example
title: A load-use stall
problem: Draw the pipeline diagram, with forwarding, for `lw x1, 0(x2)` followed by `add x3, x1, x4`.
step: The loaded value is available only at the end of MEM (cycle 4 for the load).
step: The `add` would reach EX in cycle 4, one cycle too early, so it stays in ID for one extra cycle (a stall, marked `s`) and enters EX in cycle 5.
step: In cycle 5 the value is forwarded from the MEM/WB register to the ALU input.

```text
            1   2   3   4   5   6   7
lw  x1,..   IF  ID  EX  MEM WB
add x3,..       IF  ID  s   EX  MEM WB
```
step: The total is 7 cycles for two instructions: $6$ for the ideal case plus 1 stall.
answer: 7 cycles with one stall

@mistakes
- Saying a pipeline makes each instruction run faster; it improves throughput, while the latency of a single instruction stays the same or grows.
- Forgetting the load-use stall: forwarding cannot send data back in time from the end of MEM.
- Counting $n \times k$ cycles for $n$ instructions on a $k$-stage pipeline instead of $k+n-1$ (plus stalls).
- Forwarding from the wrong stage, or from an instruction whose destination is `x0`.

```python
def stalls_no_forwarding(prog):
    wb_cycle = {}
    prev_id = 1
    for rd, rs1, rs2 in prog:
        cycle = prev_id + 1
        for src in (rs1, rs2):
            if src in wb_cycle:
                cycle = max(cycle, wb_cycle[src])
        prev_id = cycle
        if rd:
            wb_cycle[rd] = cycle + 3
    return prev_id - (len(prog) + 1)
```
hint: Track the ID cycle of each instruction: at least `previous + 1`, and not before the WB cycle of the producer of any register it reads.
hint: Record `wb_cycle[rd] = id_cycle + 3` when an instruction with a non-zero `rd` is placed. Stalls are the last ID cycle minus the stall-free value `len(prog) + 1`.
solution: Each instruction enters ID as soon as the pipeline allows and all its source values have been written back; a producer in ID at cycle `c` writes back in `c + 3`. Without stalls the last instruction would be in ID at cycle `len(prog) + 1`; every cycle beyond that is a stall. A dependent instruction directly behind its producer waits 2 cycles; one slot further, 1 cycle.

```python
def load_use_stalls(prog):
    count = 0
    for i in range(len(prog) - 1):
        op, rd, _rs1, _rs2 = prog[i]
        if op == "lw" and rd:
            nxt = prog[i + 1]
            if rd in (nxt[2], nxt[3]):
                count += 1
    return count
```

model:
```python
def forwarding_for(prog, i, reg):
    if reg == 0:
        return "none"
    if i >= 1 and prog[i - 1][0] == reg:
        return "EX/MEM"
    if i >= 2 and prog[i - 2][0] == reg:
        return "MEM/WB"
    return "none"
```
hint: Check the closest earlier instruction first, then the one before it.
hint: Guard the indexes: `i >= 1` before looking at `prog[i - 1]`, and `i >= 2` before `prog[i - 2]`.
solution: The most recent writer holds the newest value, so test `prog[i - 1]` first (EX/MEM), then `prog[i - 2]` (MEM/WB), else the register file already has the value. Register 0 is constant zero and is never forwarded.
