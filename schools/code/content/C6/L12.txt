@article
"Fast" is ambiguous. **Response time** (execution time) is how long one task takes; **throughput** is how many tasks complete per unit time. This lesson concentrates on the execution time of a single program, and on the equation that explains where it comes from.

### The performance equation

$$\text{CPU time}=\text{instruction count}\times\text{CPI}\times\text{clock period}=\frac{\text{IC}\times\text{CPI}}{f}$$

where **CPI** is the average number of clock cycles per instruction and $f$ is the clock frequency. Each factor has different owners:

- **Instruction count (IC)**: set by the algorithm, the programming language, the compiler and the ISA.
- **CPI**: set by the microarchitecture (pipelining, hazards, caches) and by the instruction mix.
- **Clock period**: set by the circuit technology and the depth of the logic between registers.

Improving one factor at the expense of another may not help. If a program has instruction classes with fractions $p_i$ and CPIs $c_i$, then $\text{CPI}=\sum_i p_i c_i$. With a memory system, the stall cycles add to the CPI: if 30% of instructions access memory with a 5% miss rate and a 40-cycle penalty, the memory stalls add $0.3\times0.05\times40=0.6$ cycles per instruction to the base CPI.

### Misleading metrics

**Clock rate** alone says nothing: a machine with a higher frequency and a higher CPI can be slower. **MIPS** (millions of instructions per second) is also misleading, because different ISAs and compilers need different numbers of instructions for the same work, and a faster program can even have a lower MIPS rating. The only reliable measure is the time to run **real programs**: **benchmark suites** such as SPEC run a collection of representative programs. To summarize normalized results ("machine A is 2.0 times faster on program 1, 0.5 times on program 2") the **geometric mean** is used, because it gives the same ranking whichever machine is chosen as the reference. Execution times themselves are summarized with the arithmetic mean.

### Amdahl's law

Speeding up one part of a task limits the overall gain. If a fraction $f$ of the original execution time is improved by a factor $s$, then

$$\text{speedup}=\frac{1}{(1-f)+f/s}.$$

Even an infinite speedup of that part gives at most $1/(1-f)$: if 90% of the time is improved without limit, the overall speedup cannot exceed 10. The same law governs **multicore** scaling: the serial fraction of a program limits the benefit of adding cores. The practical lesson is to optimize the part that dominates the profile first, and to measure before and after.

### Power and the limits of scaling

Dynamic power of a chip is proportional to $\alpha C V^2 f$ (activity, capacitance, voltage squared and frequency). Frequency growth stalled in the mid-2000s because chips could not dissipate the heat; this "power wall" is why performance growth moved to **multiple cores**, wider **superscalar** execution (several instructions per cycle), **SIMD** (one instruction on many data) and specialized accelerators. Lowering voltage helps quadratically, which is why lower-frequency designs are more energy-efficient.

### Measuring honestly

Run the same inputs on each configuration, repeat the measurement several times and report the spread, separate startup effects from steady state, and use hardware counters (for instance with Linux `perf stat`) to see instructions, cycles and cache misses rather than guessing. A simulator such as the cache model you wrote last week gives hit rate and AMAT for a given trace and lets you try alternatives cheaply.

@example
title: Comparing two machines
problem: Machine A runs at 2 GHz with CPI 1.5, and machine B at 3 GHz with CPI 2.5, on the same program of $10^9$ instructions. Which is faster, and by what factor?
step: $T_A = 10^9\times1.5/(2\times10^9) = 0.75$ s.
step: $T_B = 10^9\times2.5/(3\times10^9) = 0.8\overline{3}$ s.
step: The ratio is $T_B/T_A = 0.8333/0.75 = 1.111$.
answer: A is faster, by a factor of about 1.11, despite its lower clock rate

@example
title: Amdahl's law in action
problem: A program takes 100 s, of which 70 s are spent in one loop. A new implementation runs that loop 5 times faster. What are the new run time and the overall speedup?
step: The loop now takes $70/5=14$ s; the other $30$ s are unchanged.
step: The new run time is $14+30=44$ s.
step: The speedup is $100/44\approx2.27$, matching the formula $1/(0.3+0.7/5)=1/0.44$.
step: Even with an infinite speedup of the loop, the time would stay at 30 s, a limit of $100/30\approx3.33$.
answer: 44 s and a speedup of about 2.27

@mistakes
- Judging performance by clock rate or MIPS alone.
- Applying Amdahl's law with the fraction of the *improved* time instead of the fraction of the *original* time.
- Averaging speedup ratios with the arithmetic mean instead of the geometric mean.
- Adding the memory stall cycles to the wrong quantity: they add to CPI per instruction, so multiply the miss rate by the memory accesses per instruction first.

starter:

tests:
```python
rate, amat = cache_stats([0, 4, 16, 64, 0], 16, 4, 1, 100)
assert abs(rate - 0.2) < 1e-9
assert abs(amat - 81.0) < 1e-9
rate, amat = cache_stats(list(range(0, 64, 4)), 16, 4, 2, 40)
assert abs(rate - 0.75) < 1e-9
assert abs(amat - 12.0) < 1e-9
rate, amat = cache_stats([8, 8, 8, 8], 16, 2, 1, 50)
assert abs(rate - 0.75) < 1e-9
assert abs(amat - 13.5) < 1e-9
```
model:
```python
def cache_stats(trace, block_size, num_sets, hit_time, miss_penalty):
    tags = [None] * num_sets
    hits = 0
    for addr in trace:
        block = addr // block_size
        index = block % num_sets
        tag = block // num_sets
        if tags[index] == tag:
            hits += 1
        else:
            tags[index] = tag
    hit_rate = hits / len(trace)
    return hit_rate, hit_time + (1 - hit_rate) * miss_penalty
```
hint: Simulate as in a direct-mapped cache: one stored tag per set, counting hits.
hint: After the loop, the hit rate is `hits / len(trace)`; then apply the AMAT formula.
solution: Count the hits with a tag array indexed by set, divide by the number of accesses, and plug the miss rate into $\text{AMAT}=t_{hit}+m\cdot p$. For the first trace there is 1 hit in 5 accesses, so $1+0.8\times100=81$.

```python
def weighted_cpi(mix):
```

hint: Each class contributes its fraction of the instructions times its cycles per instruction.
