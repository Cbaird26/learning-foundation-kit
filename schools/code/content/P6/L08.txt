@article
Almost every product you will work on depends on open-source software, and many employers expect you to contribute to it. Contributing is also one of the best ways to learn from strangers' code. **This lesson gives general information about licenses, not legal advice; for real decisions, ask your company's legal team.** Projects and people below are **fictional**.

### Contributing the way maintainers expect

Maintainers are usually volunteers or a small team with limited time, so be easy to help:

1. **Choose a project you use.** You already understand its purpose.
2. **Read the guidelines**: `README`, `CONTRIBUTING`, the **code of conduct**, and the issue templates. Follow the project's style and test commands.
3. **Start small**: documentation fixes, reproducible bug reports and issues labeled for newcomers (often "good first issue").
4. **Discuss before large changes.** Open an issue or discussion describing the problem and your plan, and wait for a maintainer's response; surprise 2,000-line pull requests are usually closed.
5. **Fork, branch, change, test.** Keep the pull request (PR) focused on one thing, add tests and docs, and write a clear description linking the issue.
6. **Respond to review** politely and promptly. Disagreement is normal; explain your reasoning, accept the maintainers' final decision on their project, and do not take review personally.
7. **Be patient.** A silent PR is usually a busy maintainer. A single polite reminder after a couple of weeks is fine.

Some projects require a **Developer Certificate of Origin (DCO)** sign-off (`git commit -s` adds a `Signed-off-by` line) or a **contributor license agreement (CLA)**. Report security vulnerabilities **privately** using the project's `SECURITY` policy, never in a public issue. If your employer owns work you do, check your employment terms before contributing.

### Why licenses matter

Code with **no license** is, by default, under copyright with all rights reserved: you may read it but have no general permission to copy, modify or redistribute it. An open-source license grants those permissions with conditions. Identify licenses with **SPDX identifiers** such as `MIT` or `Apache-2.0`, and combine them with `OR` (the user chooses) and `AND` (all apply), for example `MIT OR Apache-2.0`. The GNU licenses have versioned identifiers: SPDX now prefers `GPL-3.0-only` and `GPL-3.0-or-later` (likewise for LGPL and AGPL) over the older `GPL-3.0`, which this lesson uses as a short name.

### The main licenses

| License | Kind | What you must do when you distribute | Patents |
|---|---|---|---|
| MIT | Permissive | Keep the copyright and permission notice | No express patent grant |
| BSD-2-Clause, BSD-3-Clause | Permissive | Keep the notices; the 3-clause version also forbids using the authors' names to endorse your product | No express patent grant |
| Apache-2.0 | Permissive | Keep notices (including a NOTICE file if present), state significant changes | Express patent license from contributors; it ends for a user who sues claiming the work infringes a patent |
| MPL-2.0 | Weak, file-level copyleft | Share source of modified MPL-covered files under MPL; other files in a larger work can have other terms | Express patent grant |
| LGPL-3.0 | Weak copyleft for libraries | Keep the library (and changes to it) under LGPL; an application can use it if users can replace the library and notices are kept | GPL-3.0 patent terms apply |
| GPL-3.0 | Strong copyleft | When you distribute a work based on GPL code, provide its corresponding source under GPL-3.0 | Express patent license; installation-information rules for consumer devices |
| AGPL-3.0 | Strong copyleft plus network clause | Everything GPL-3.0 requires, and if you modify it and users interact with it over a network, offer them the source | Same family as GPL-3.0 |

Key ideas:

- **Permissive** licenses let you use the code in closed-source products if you keep the notices.
- **Copyleft** licenses require derived works that you *distribute* to carry the same freedoms. The GPL's obligations trigger on distribution, so using GPL software privately, or running it on your own servers without giving it to others, does not trigger them; the **AGPL** closes that gap for network services.
- **Scope varies**: MPL covers files, LGPL covers the library boundary, GPL covers the whole combined work.
- **Compatibility is directional.** Apache-2.0 code can be included in a GPL-3.0 project, but GPL-3.0 code cannot go into an Apache-2.0 project and stay Apache-2.0. Apache-2.0 is not compatible with GPL-2.0-only.
- **Dual licensing** (for example a project offered under GPL or a commercial license) is a business choice the copyright holder can make.
- **Public-domain-style dedications** such as CC0 give up copyright interests, but CC0 expressly does not license patents.

Companies keep a list of approved licenses and scan dependencies automatically. Learn your company's policy before adding a dependency.

### Supply chain basics

Every dependency is code you are responsible for: check maintenance, license and security record, pin versions, and keep a software bill of materials (SBOM) when your company requires one.

@example
title: Choosing whether you can use a dependency
problem: Your fictional company ships a closed-source desktop app. A library `fastgrid` is licensed under GPL-3.0. May the team link it into the app and distribute the app?
step: Identify the license: GPL-3.0 is strong copyleft, triggered by distribution of a work based on the library.
step: The app would be distributed to customers and would be combined with the library, so the combined work would have to be offered under GPL-3.0 with source, which conflicts with a closed-source plan.
step: Options: find a permissively licensed or LGPL alternative, buy a commercial license if the copyright holders offer one, or keep the library on your own servers without distributing it (check with legal; if the license were AGPL, network use would also trigger obligations).
step: Ask the legal team before deciding; this is general information, not legal advice.
answer: Not without accepting GPL obligations for the whole app; use an alternative, a commercial license, or get legal advice.

@example
title: A focused first contribution
problem: You notice the fictional `tinyparse` README shows a function that was renamed. How do you contribute a fix?
step: Read `CONTRIBUTING` and check for an existing issue about the README.
step: Fork the repository, create a branch such as `fix-readme-rename`, and fix only that example (run the example to confirm it works).
step: Commit with a clear message (with `-s` if the project requires sign-off) and open a PR that says what was wrong and links the issue.
step: Respond to the maintainers' feedback and update the PR. A small, correct documentation fix is an excellent first contribution.
answer: Read the guidelines, make a small tested fix on a branch, open a focused PR and respond to review.

@mistakes
- Assuming code on a public repository with no license file is free to reuse; with no license, default copyright applies.
- Believing copyleft is triggered by merely running the software; GPL-style obligations attach to distribution (and, for the AGPL, to network interaction with a modified version).
- Opening a huge unannounced pull request instead of discussing the plan first.
- Reporting a security vulnerability in a public issue instead of using the private reporting channel.

@practice code
prompt: Here is a simplified, illustrative teaching table `compat` mapping each dependency license to the set of project licenses it may be used in. Write `blocked_dependencies(compat, deps, project_license)` where `deps` is a dict of package name to license. Return a sorted list of package names that are **not** allowed: either the package's license is not in `compat` at all (unknown), or `project_license` is not in its allowed set. This is a teaching exercise, not legal advice.
starter:
```python
def blocked_dependencies(compat, deps, project_license):
    pass
```
tests:
```python
ALL = {"MIT", "Apache-2.0", "GPL-3.0", "AGPL-3.0", "Proprietary"}
compat = {
    "MIT": ALL,
    "Apache-2.0": ALL,
    "GPL-3.0": {"GPL-3.0", "AGPL-3.0"},
    "AGPL-3.0": {"AGPL-3.0"},
}
deps = {"fmt": "MIT", "net": "Apache-2.0", "grid": "GPL-3.0", "odd": "Custom-1.0"}
assert blocked_dependencies(compat, deps, "Proprietary") == ["grid", "odd"]
assert blocked_dependencies(compat, deps, "GPL-3.0") == ["odd"]
assert blocked_dependencies(compat, {"web": "AGPL-3.0"}, "GPL-3.0") == ["web"]
assert blocked_dependencies(compat, {"web": "AGPL-3.0"}, "AGPL-3.0") == []
assert blocked_dependencies(compat, {}, "MIT") == []
```
model:
```python
def blocked_dependencies(compat, deps, project_license):
    blocked = []
    for package, license_id in deps.items():
        allowed = compat.get(license_id)
        if allowed is None or project_license not in allowed:
            blocked.append(package)
    return sorted(blocked)
```
hint: `compat.get(license_id)` returns `None` for an unknown license.
hint: A package is blocked when its license is unknown or the project license is not in the allowed set.
solution: Look up each dependency's allowed project licenses; treat a missing entry as blocked (unknown licenses need review), and also block when the project license is not allowed. Sort the names.

@practice code
prompt: SPDX expressions combine licenses with `OR` (alternatives) and `AND` (all required); `AND` binds tighter than `OR`. Write `spdx_alternatives(expr)` for expressions without parentheses. It returns a list of alternatives, each alternative a list of license ids that all apply. For example `"MIT OR Apache-2.0"` gives `[["MIT"], ["Apache-2.0"]]` and `"A AND B OR C"` gives `[["A", "B"], ["C"]]`. Words are separated by single spaces.
starter:
```python
def spdx_alternatives(expr):
    pass
```
tests:
```python
assert spdx_alternatives("MIT") == [["MIT"]]
assert spdx_alternatives("MIT OR Apache-2.0") == [["MIT"], ["Apache-2.0"]]
assert spdx_alternatives("GPL-3.0-only AND MIT") == [["GPL-3.0-only", "MIT"]]
assert spdx_alternatives("A AND B OR C") == [["A", "B"], ["C"]]
assert spdx_alternatives("A OR B AND C OR D") == [["A"], ["B", "C"], ["D"]]
```
model:
```python
def spdx_alternatives(expr):
    return [part.split(" AND ") for part in expr.split(" OR ")]
```
hint: Split on `" OR "` first, because `AND` binds tighter.
hint: Then split each piece on `" AND "`.
solution: Splitting first on `OR` and then each part on `AND` follows operator precedence: each `OR` piece is one alternative whose `AND`-separated licenses all apply.

@practice self
prompt: Deliverable: write a postmortem for a supplied incident. All names and numbers are fictional. The open-source library `tinyparse` (parses dates and durations) is maintained by three volunteers. On Tuesday at 14:00 UTC an automated release pipeline published version 2.4.0 after pull request 381 (a change to default timezone handling) was merged with one approval. The change made naive timestamps default to the machine's local timezone instead of UTC. CI runs in UTC, so tests passed, and the changelog described the change as an internal cleanup. At 14:40 users began opening issues saying their applications produced wrong dates; the maintainers had no alert on issue volume and a maintainer saw the first issues at 15:30. At 15:50 the team decided to yank 2.4.0 from the registry, which completed at 16:10, and at 16:45 version 2.4.1 restored the old behavior. About 1,200 downloads of 2.4.0 occurred. Write a blameless postmortem with summary and impact, timeline, contributing factors, what went well and poorly, and at least four action items with owners (use maintainer roles) and dates (relative, like "within 2 weeks").
hint: Use the facts supplied. Describe system conditions: CI timezone, review process, changelog, release automation, alerting.
hint: Do not name the approving reviewer or the PR author as the cause.
solution: Summary and impact: tinyparse 2.4.0 changed the default for naive timestamps from UTC to local time, which silently altered results for applications on non-UTC machines. It was available for 2 hours and 10 minutes (14:00 to 16:10 UTC, until yanked) and about 1,200 downloads occurred. Users received wrong dates; no data loss in the library itself, but downstream data may need correction.

Timeline (UTC): 14:00 2.4.0 published automatically; 14:40 first user issues report wrong dates; 15:30 a maintainer notices the issues; 15:50 maintainers decide to yank; 16:10 yank completes; 16:45 2.4.1 restores the previous default; later, an announcement and a fix guide are posted.

Contributing factors: (1) A behavior change shipped as a patch-level-looking cleanup because nothing in the process flags changes to defaults; the changelog called it internal. (2) Tests ran only in UTC, so the difference between UTC and local time was invisible. (3) The change had a single reviewer and the review checklist has no item for behavior changes in public defaults. (4) The release pipeline publishes on merge with no delay, canary or pre-release step. (5) There was no alert on issue volume, so detection depended on a maintainer happening to look; with volunteers across time zones that took 50 minutes after the first report. (6) Yank and revert steps were not documented, so the decision and execution took 40 minutes.

What went well: users reported quickly with clear examples; the yank and the revert were effective; communication in the issue tracker was clear and polite. What went poorly: detection, rollout safety and documentation. Where we got lucky: the bug did not corrupt stored data inside the library, and the release was short-lived.

Action items: (a) Add CI jobs that run the tests under at least two non-UTC timezones; owner: test maintainer; within 2 weeks. (b) Add a review checklist item and a pull request template question: "Does this change any default or public behavior?"; require a second approval for such changes; owner: lead maintainer; within 1 week. (c) Change the release pipeline to publish a release candidate first and wait 24 hours for feedback before the final release; owner: release maintainer; within 4 weeks. (d) Add a notification to the maintainers' chat when more than 5 issues open within an hour, and write a short yank and revert runbook; owner: infrastructure maintainer; within 2 weeks. (e) Review in 30 days that (a) to (d) are complete.
rubric: Summary and impact use the supplied facts (duration, downloads, effect) accurately.
rubric: Timeline is in order with the supplied times and does not invent contradictory events.
rubric: Contributing factors are systemic (CI timezone, review, changelog, release automation, alerting) and are not blame on a person.
rubric: Action items are specific, tied to factors, and each has an owner role and a due date.

@quiz code
prompt: Write `license_counts(packages)` where `packages` is a list of `(name, license)` pairs. Return a dict mapping each license to the number of packages that use it. A license value that is `None` or an empty string counts under the key `"UNKNOWN"`.
starter:
```python
def license_counts(packages):
    pass
```
tests:
```python
pk = [("a", "MIT"), ("b", "MIT"), ("c", "GPL-3.0"), ("d", None), ("e", "")]
assert license_counts(pk) == {"MIT": 2, "GPL-3.0": 1, "UNKNOWN": 2}
assert license_counts([]) == {}
assert license_counts([("x", "Apache-2.0")]) == {"Apache-2.0": 1}
```
model:
```python
def license_counts(packages):
    counts = {}
    for _name, license_id in packages:
        key = license_id or "UNKNOWN"
        counts[key] = counts.get(key, 0) + 1
    return counts
```
hint: `license_id or "UNKNOWN"` handles both `None` and the empty string.
hint: Use `dict.get(key, 0) + 1` to count.
solution: Normalize missing licenses to `"UNKNOWN"` and count occurrences in a dict. The unknown bucket is what a license review would look at first.
