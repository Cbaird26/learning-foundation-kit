@article
Most engineering problems that go wrong slowly go wrong through communication: a blocker nobody mentioned, a meeting with no decision, a question asked three days too late. The scenarios below are **fictional**.

### Status updates

A good status update takes a reader under a minute and answers four things: **what is done, what is next, what is at risk or blocked, and what you need from the reader.** Lead with the conclusion ("on track" or "slipping by three days"), not the story. Be specific: "The export endpoint is merged and deployed to staging; load testing starts Tuesday" beats "Making progress on exports." Report bad news early: a slip announced on day two is a planning problem; the same slip announced on the deadline is a trust problem. Be honest about uncertainty ("70 percent confident we make Friday; the risk is the vendor API").

A tidy format for a written update:

```text
Done: ...
In progress: ...
Blocked / at risk: ...
Need from you: ...
```

### Meetings

Meetings are expensive: a one-hour meeting with eight people costs eight hours of work. Before you call or accept one, ask what decision or outcome it exists to produce. Good meetings have an **agenda** sent in advance, a **facilitator**, a **note-taker**, and end with **decisions and action items, each with an owner and date**. If a meeting is only information transfer, a short written update is usually better. When you attend: arrive prepared (read the document first), speak concisely, and when you disagree say what concern you have and what evidence would change your mind. Remote and hybrid meetings need extra care: invite everyone to speak, put decisions in writing, and share notes with people who were not there.

Regular meetings you will meet: **stand-up** (short sync on progress and blockers), **one-on-one** with your manager (your meeting: bring topics and career questions), **planning**, **design review**, **retrospective** and **incident review**.

### Written, asynchronous communication

Chat is for quick coordination; documents and tickets are for decisions that must be found later. Write messages that survive being read cold: include the link, the goal and the question in one message instead of "hey" followed by silence. Summarize long threads with the decision at the top. When a conversation goes in circles over text, switch to a call and then write down the outcome.

### Asking for help

Struggling silently feels safe and is expensive. A useful rule is to **timebox** your own effort (for example 30 to 60 minutes on something that blocks you, adjusted to the problem), then ask. A good question contains:

1. **The goal** you are trying to reach.
2. **What you tried** and what happened (commands, errors, links).
3. **What you suspect**, and what you have already ruled out.
4. **A specific ask**: "Can you point me to who owns the billing service?" rather than "Can you help?"

Make it easy to answer: paste text, not screenshots of text; give a minimal reproduction. Say thank you and, when you solve it, post the answer so the next person finds it. Asking questions is normal and expected for new hires; hiding confusion is the real risk.

### Giving and receiving feedback in review

In code and design review, comment on the work, not the person: "This query runs once per row, which may be slow for large orders; could we batch it?" Distinguish blocking issues from preferences ("nit:"). When you receive comments, assume good intent, ask if unclear, and thank reviewers.

@example
title: A good request for help
problem: You are blocked by a failing CI job on your first PR. Draft the message to your team channel.
step: State the goal: "I am trying to get PR 482 (adds retry logic to the sync job) green."
step: Say what you tried: "The test `test_retry_backoff` fails in CI with a timeout but passes locally; I rebuilt with a clean cache and compared Python versions (3.13 both)."
step: Give your hypothesis and ruled-out causes: "I suspect CI machines are slower and the 1 second timeout is too tight."
step: Make a specific ask and include the link: "Does anyone know whether CI has a standard way to scale timeouts? Log: (link)."
answer: Goal, what you tried, hypothesis and a specific question with a link; much faster to answer than "CI is broken, help."

@mistakes
- Hiding a slipping deadline until the last day; report risks early and with options.
- Calling a meeting with no agenda, no decision to make and no notes afterward.
- Asking "can anyone help?" with no context, so nobody can tell what is wrong or whether it is theirs.
- Posting a screenshot of an error instead of copyable text, or never reporting back what fixed it.

starter:
```python
def format_status(items):
    pass
```
tests:
```python
items = [("doing", "load test"), ("done", "CSV export"), ("done", "docs")]
assert format_status(items) == "Done:\n- CSV export\n- docs\n\nIn progress:\n- load test"
assert format_status([("blocked", "vendor key")]) == "Blocked:\n- vendor key"
assert format_status([]) == ""
all3 = [("blocked", "b"), ("doing", "d"), ("done", "x")]

```
model:
```python
def format_status(items):
    titles = [("done", "Done"), ("doing", "In progress"),
              ("blocked", "Blocked")]
    groups = []
    for state, title in titles:
        lines = [f"- {text}" for s, text in items if s == state]
        if lines:
            groups.append(title + ":\n" + "\n".join(lines))
    return "\n\n".join(groups)
```
hint: Loop over the states in output order, not over the items.
hint: Build each group as a string, skip empty ones, and join groups with `"\n\n"`.
solution: Iterate over the three states in the required order, collect the item lines for each, and build a group only when there are lines. Joining the groups with a blank line gives no trailing newline.

@practice self
prompt: Deliverable: write a one-page design document (about 300 to 500 words) for this fictional problem. Fernwood Freight's public tracking API (about 400 customers) slowed down on three days last month when one customer's script sent about 200 requests per second; p95 latency rose from 120 ms to 900 ms for everyone. The team wants to add per-API-key rate limiting. Constraints: it must ship in one sprint, customers must get a clear error and a hint on when to retry, and the system runs three API instances behind a load balancer with a shared Redis cache. Include title and status, context and problem, goals and non-goals, the proposal, at least two alternatives considered, risks and open questions, and how you will roll it out and test it.
hint: Decide the algorithm and limit values, but justify them and mark them as starting points.
hint: Think about what happens when Redis is unavailable (fail open or closed) and how to roll out without surprising customers.
solution: Example answer.

Design doc: Per-API-key rate limiting for the tracking API. Author: (you). Status: Draft for review.

Context and problem: On three days last month a single API key sent about 200 requests per second, raising p95 latency from 120 ms to 900 ms for all 400 customers. There is no limit today, so any client can degrade the others.

Goals: (1) one client cannot push p95 latency of others above 250 ms; (2) over-limit clients receive HTTP 429 with a `Retry-After` header; (3) ship in one sprint. Non-goals: per-endpoint limits, billing-based quotas and a customer dashboard in this version.

Proposal: A token-bucket limiter keyed by API key, with state in the shared Redis so all three instances agree. Default 60 requests per minute with bursts of 20 (starting values, tunable per key). Each request atomically takes a token; if none are left, return 429 with `Retry-After` set to the seconds until the next token and a JSON body explaining the limit. Log and count every rejection per key for dashboards.

Alternatives: (a) Limit at the load balancer by IP: no code changes, but customers share IPs behind proxies and it cannot distinguish keys. (b) A fixed-window counter in Redis: simpler, but allows double bursts at window edges. (c) Per-instance in-memory limits: no Redis dependency, but the effective limit is multiplied by the number of instances and varies with load balancing.

Risks and open questions: If Redis is down, do we fail open (allow traffic) or closed? Proposal: fail open and alert, because availability matters more than limiting for this API. Some legitimate customers may exceed 60 per minute: open question whether to grandfather the top ten by raising their limits first.

Rollout and testing: Ship in log-only mode for one week to see who would be limited, contact heavy users, then enforce. Unit-test the bucket logic with fake time, load-test with the 200 requests per second pattern in staging, and add an alert on the rejection rate.
rubric: Problem statement uses the supplied evidence and states a measurable goal.
rubric: Has explicit non-goals and at least two real alternatives with reasons for rejecting them.
rubric: Proposal is concrete (algorithm, key, limit values marked as tunable, error behavior with 429 and Retry-After) and fits the constraints.
rubric: Identifies risks (for example Redis failure or legitimate heavy users) and a rollout and test plan, in about one page.

@quiz code
prompt: Write `overdue_blockers(blockers, today, max_days)` where `blockers` is a list of `(name, raised)` pairs with `raised` an ISO date string `"YYYY-MM-DD"`, and `today` is an ISO date string. Return the names of blockers that have been open **more than** `max_days` days, oldest first (ties broken alphabetically by name).
starter:
```python
def overdue_blockers(blockers, today, max_days):
    pass
```
tests:
```python
b = [("A", "2026-05-15"), ("B", "2026-05-17"), ("C", "2026-05-10")]
assert overdue_blockers(b, "2026-05-20", 3) == ["C", "A"]
b2 = b + [("D", "2026-05-15")]
assert overdue_blockers(b2, "2026-05-20", 3) == ["C", "A", "D"]
assert overdue_blockers(b, "2026-05-20", 10) == []
assert overdue_blockers([], "2026-05-20", 1) == []
```
model:
```python
from datetime import date


def overdue_blockers(blockers, today, max_days):
    now = date.fromisoformat(today)
    late = []
    for name, raised in blockers:
        age = (now - date.fromisoformat(raised)).days
        if age > max_days:
            late.append((-age, name))
    return [name for _, name in sorted(late)]
```
hint: Compute each blocker's age in days with `date.fromisoformat`.
hint: Sort by oldest first by sorting on `(-age, name)`.
solution: Compute age, keep those strictly greater than `max_days`, and sort by negative age (oldest first) then name. The second test checks the alphabetical tie-break, and the third checks that exactly `max_days` is not overdue.
