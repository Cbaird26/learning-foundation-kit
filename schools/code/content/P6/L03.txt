@article
Code explains *how*. Writing explains *what, why and what else we considered*. Engineers who write well get their ideas adopted, onboard others faster and avoid re-arguing old decisions. The people and projects below are **fictional**.

### Know the reader

Before writing a word, answer: who reads this, what do they already know, and what do I want them to do afterward (approve, review, run it, decide)? A design document for senior reviewers can skip the basics; a README for a stranger cannot. Put the point first: the first paragraph should let a busy reader decide whether to keep reading.

### The design document

A **design document** (design doc, RFC, tech spec) is written *before* building a non-trivial change, to think clearly, get feedback while changes are cheap, and record why a decision was made. Companies use different templates, but good ones share these parts:

| Section | Answers |
|---|---|
| Title, authors, status, date | Who, and is it a draft, in review or approved? |
| Context and problem | What hurts today, for whom, with evidence? |
| Goals and non-goals | What must be true after? What are we deliberately *not* doing? |
| Proposal | What will we build? Include a small diagram or example |
| Alternatives considered | What else could work, and why not? |
| Risks and open questions | What could go wrong? What do we not know yet? |
| Rollout, testing, security and privacy | How do we ship and verify it safely? |

**Non-goals** are underrated: "We will not support per-endpoint limits in v1" prevents scope creep and shows you thought about it. **Alternatives** are essential: a proposal with no alternatives usually means the author has not explored enough, and reviewers will ask. Keep the document to about one to three pages; a longer one is rarely read. For decisions that outlive the document, teams keep short **architecture decision records (ADRs)**: context, decision, consequences.

### The README

The README is the front door of a repository. A new reader should be able to answer, in order: *What is this? Why would I use it? How do I install and run it? How do I use it? How do I get help or contribute? What is the license?* A solid skeleton:

```markdown
# project-name
One sentence: what it does and for whom.

## Install
## Usage
## Configuration
## Contributing
## License
```

Make the quick start **copy-pasteable** and test it on a clean machine; a README whose commands no longer work is worse than none. Document the version of the language or tools you require. Link to deeper docs rather than inlining everything.

### Habits that make writing clear

- Use short sentences and the active voice: "The scheduler retries three times" beats "Retries are performed."
- Define a term once, and then use it consistently. Do not call the same thing a *job*, a *task* and a *work item*.
- Prefer a concrete example to an abstract claim: show a sample request and response.
- Use headings, lists and tables so readers can scan; use a diagram when relationships matter.
- Say what you are unsure about. "Open question: do we need to keep logs for 30 days?" is honest and invites help.
- Keep documents next to the code (in the repository, reviewed like code) so they change together.

### Review your writing

Read it aloud, cut every sentence that does not help the reader act, and ask a colleague outside your team to find the first confusing sentence. Then fix that sentence.

@example
title: Sharpening a problem statement
problem: A draft design doc (fictional) says: "The tracking API is bad and slow sometimes, so we should add rate limiting." Rewrite the problem statement.
step: Replace vague words with evidence. What does "slow" mean, and when? Suppose logs show p95 latency rose from 120 ms to 900 ms on 3 days last month.
step: Name the cause and the affected people: one customer's script sent about 200 requests per second, and other customers saw the slowdown.
step: Say what is at stake and how you will know it is fixed.
step: Write it: "On three days last month, one API key sent about 200 requests per second, raising p95 latency for all customers from 120 ms to 900 ms. We want a limit per API key so one client cannot degrade the others. Success: p95 stays below 250 ms under the same load."
answer: A problem statement that has numbers, a cause, who is affected and a measurable success condition.

@example
title: Checking a README for the essentials
problem: A README (fictional) for `route-planner` has sections Overview, Features and Credits. A new teammate cannot run the project. What is missing?
step: Compare with the reader's questions: what it is (Overview, present), how to install, how to run, how to contribute, the license.
step: Install and Usage are missing, so nobody can start. License is missing, so reuse is legally unclear.
step: Add Install and Usage sections with commands you have tested on a clean machine, plus Contributing and License.
answer: Add Install, Usage, Contributing and License sections, with a tested quick start.

@mistakes
- Starting with history or background and burying the actual proposal on page three.
- Listing no alternatives or non-goals, which hides trade-offs and invites scope creep in review.
- Leaving a README quick start untested so the commands no longer work.
- Using the same word for different things (or two words for one thing), which forces readers to guess.

@practice code
prompt: Write `missing_sections(readme, required)` that returns the list of names from `required` (in the order given) that do **not** appear as a Markdown heading in the text `readme`. A heading is a line that starts with one or more `#` characters followed by a space; compare the heading text case-insensitively, ignoring surrounding spaces. Lines inside fenced code blocks (between lines starting with three backticks) are not headings, even if they start with `#`.
starter:
```python
def missing_sections(readme, required):
    pass
```
tests:
```python
text = "# Tool\n\n## Install\nrun it\n\n## License\nMIT\n"
assert missing_sections(text, ["Install", "License"]) == []
assert missing_sections(text, ["Install", "Usage", "License"]) == ["Usage"]
assert missing_sections(text, ["install", "LICENSE"]) == []
fenced = "# T\n```bash\n# Usage\necho hi\n```\n## License\n"
assert missing_sections(fenced, ["Usage", "License"]) == ["Usage"]
assert missing_sections("", ["Install"]) == ["Install"]
assert missing_sections("#Usage\n", ["Usage"]) == ["Usage"]
```
model:
```python
def missing_sections(readme, required):
    found = set()
    in_fence = False
    for line in readme.splitlines():
        if line.startswith("```"):
            in_fence = not in_fence
        elif not in_fence and line.startswith("#"):
            title = line.lstrip("#")
            if title.startswith(" "):
                found.add(title.strip().lower())
    return [name for name in required if name.lower() not in found]
```
hint: Track whether you are inside a code fence; toggle on each line that starts with three backticks.
hint: Collect lowercase heading titles in a set, then keep the required names whose lowercase form is not in it.
solution: Scan the lines, toggling a fence flag, and for lines outside fences that start with `#` and then a space, record the lowercase title. Return the required names that were not found, preserving order. The fenced test catches solutions that treat a shell comment as a heading.

@practice code
prompt: A design doc for a one-page review should take a few minutes to read. Write `reading_minutes(text, wpm=200)` that returns the estimated reading time in whole minutes, rounded **up**, based on the number of whitespace-separated words. Text with no words returns `0`.
starter:
```python
def reading_minutes(text, wpm=200):
    pass
```
tests:
```python
assert reading_minutes("") == 0
assert reading_minutes("   \n  ") == 0
assert reading_minutes("word " * 200) == 1
assert reading_minutes("word " * 201) == 2
assert reading_minutes("word " * 600, wpm=300) == 2
assert reading_minutes("hello") == 1
```
model:
```python
def reading_minutes(text, wpm=200):
    words = len(text.split())
    return -(-words // wpm)
```
hint: `text.split()` with no arguments splits on any whitespace and ignores extra spaces.
hint: Round up with ceiling division: `-(-words // wpm)`, or use `math.ceil`.
solution: Count words with `split()`, then divide by `wpm` rounding up. Zero words gives `0`, one word gives `1`, and exactly 200 words fits in one minute.

"Notifications for order updates are delayed by more than five minutes for about 8 percent of orders (measured over the last 30 days), and support receives roughly 40 tickets a week about missing updates. @quiz code
prompt: Design docs often end with a checklist of open questions written as Markdown task items: a line like `- [ ] Do we keep logs for 30 days?` is unanswered and `- [x] Use Postgres` is resolved. Write `open_questions(doc)` that returns, in order, the text of every unchecked item (the text after `- [ ] `, with surrounding spaces removed). Lines may be indented with spaces. Ignore all other lines, including checked items.
starter:
```python
def open_questions(doc):
    pass
```
tests:
```python
doc = "## Open questions\n- [ ] Keep logs 30 days?\n- [x] Use Postgres\n- [ ]  Who owns alerts?  \n"
assert open_questions(doc) == ["Keep logs 30 days?", "Who owns alerts?"]
assert open_questions("") == []
assert open_questions("  - [ ] indented\n- [X] done\nplain text\n") == ["indented"]
assert open_questions("- [x] a\n- [x] b\n") == []
```
model:
```python
def open_questions(doc):
    questions = []
    for line in doc.splitlines():
        stripped = line.strip()
        if stripped.startswith("- [ ]"):
            questions.append(stripped[len("- [ ]"):].strip())
    return questions
```
hint: Strip each line, then test `startswith("- [ ]")`.
hint: Slice off the five-character prefix and strip again for the question text.
solution: Strip leading spaces, select lines that start with the unchecked marker `- [ ]`, and return the remaining text trimmed. Checked items start with `- [x]` or `- [X]`, so they do not match.
