@article
Your degree or bootcamp gave you a foundation. Tools, frameworks and practices will change many times in your career; the skill that lasts is learning efficiently. The people in the examples below are **fictional**.

### Learning that works

- **Prefer fundamentals over fashion.** Data structures, networks, databases, operating systems, testing and design principles transfer across tools. Learn a new framework by mapping it to concepts you know.
- **Learn by doing.** Build a small project that is just beyond your comfort zone; read the error messages; fix them. Reading alone creates an illusion of understanding.
- **Deliberate practice**: work at the edge of your ability, get fast feedback and repeat the hard parts. Fifteen focused minutes beat an hour of passive scrolling.
- **Read real code**: open-source projects, the standard library, your colleagues' pull requests. Notice naming, structure and tests, and ask why.
- **Read primary sources**: official documentation, RFCs, design docs and papers; summaries can be wrong or stale.
- **Spaced repetition**: review material at growing intervals (a day, two days, four, and so on) so it sticks. A simple version is the **Leitner system**: flashcards live in boxes; a correct answer moves a card up a box (reviewed less often), a wrong answer sends it back to box 1.
- **Teach**: writing a short explanation, giving a lunch talk or answering a question reveals gaps in your understanding.
- **Use AI coding assistants as a tool, not a substitute for understanding.** Language models can produce plausible but wrong code and explanations stated with confidence. Read what they produce, test it, check licenses and security, and never share confidential data with tools your employer has not approved. If you cannot explain code you ship, you do not own it yet.
- **Make time**: schedule a small, regular slot (even one hour a week is a good start; the amount is personal and illustrative) and protect it. Consistency matters more than intensity, and rest prevents burnout.

Certifications, courses and conferences can help, but their value varies by field and employer; prefer visible work you can show and discuss.

### Being mentored

A mentor is someone with more experience who helps you grow. To use one well: **bring an agenda** to each meeting; **ask specific questions** ("How would you approach splitting this service?"); **report back** on what you tried; and **thank them**. You can have several mentors for different things (technical, career, communication), and mentoring can be peer-to-peer or formal. Ask your manager about programs, but also invite a person whose work you admire for a single coffee conversation.

### Mentoring others

You do not have to be senior to mentor: someone a few months behind you needs what you recently learned. Good mentoring is mostly **listening and asking questions** rather than telling: "What have you tried?" "What do you expect to happen?" Share context (why we do it this way), pair with them on real tasks, and **let them struggle productively** for a bit before helping. Use code review as teaching: explain the reason behind a request, link to resources, and praise good decisions. Give credit publicly. Write down what you explain twice: it becomes onboarding documentation.

### Giving feedback: situation, behavior, impact

The **situation-behavior-impact (SBI)** model keeps feedback specific and non-judgmental:

- **Situation**: when and where ("In Tuesday's design review...")
- **Behavior**: what you observed, not your interpretation ("you answered questions with 'that is how it works' and did not show the data")
- **Impact**: the effect it had ("so the reviewers could not tell which risks you had checked, and the discussion ran long")

Then ask for their view and agree on a next step. Give feedback soon, privately for critical points, and include positive feedback that is just as specific. Receive feedback by listening, asking for examples and thanking the person; you decide what to act on afterward. Psychological safety (people feel safe to admit mistakes and ask questions) is built by teammates, especially senior ones, who respond to mistakes with curiosity.

### Your one-year growth plan

Write down a plan and revisit it. A useful format:

1. **Where I am now**: strengths, gaps and how I know (feedback, work).
2. **Two or three goals** for the year, each with a **measure** and a **due date**, tied to why it matters.
3. **Quarterly milestones**: what will be true at the end of each quarter.
4. **Learning actions**: books, projects, courses, shadowing, with scheduled time.
5. **Support needed**: a mentor, a project, feedback from a named person.
6. **Risks** and how you will handle them; **review dates** (for example the end of each quarter).

Share the plan with your manager so they can help with scope and opportunities.

@mistakes
- Treating learning as occasional binge sessions rather than a small regular habit.
- Copying AI-generated code or tutorials you cannot explain, then being unable to debug them.
- Giving vague or personal feedback ("you are sloppy") instead of specific behavior and its impact.
- Writing a growth plan with no measures, dates or review points, then forgetting it.

prompt: Write `next_box(box, correct, max_box=5)` for a Leitner flashcard system. A correct answer moves the card up one box but never above `max_box`; a wrong answer sends it back to box `1`. Return the new box number.
starter:
```python
def next_box(box, correct, max_box=5):
    pass
```
tests:
```python
assert next_box(2, True) == 3
assert next_box(5, True) == 5
assert next_box(3, False) == 1
assert next_box(1, False) == 1
assert next_box(3, True, max_box=3) == 3
```
model:
```python
def next_box(box, correct, max_box=5):
    if correct:
        return min(box + 1, max_box)
    return 1
```
hint: Use `min` to cap the box at `max_box`.
hint: A wrong answer always returns 1, whatever the current box.
solution: Add one and cap with `min` when correct; return `1` otherwise. The `max_box=3` test checks that the cap is a parameter, not a constant `5`.

@practice code
prompt: Cards are reviewed after an interval that depends on their box: box 1 after 1 day, box 2 after 2, box 3 after 4, box 4 after 8 and box 5 after 16 days. Write `due_cards(cards, today)` where `cards` is a list of `(name, box, last_reviewed)` with `last_reviewed` an ISO date string, and `today` an ISO date string. Return a sorted list of the names of cards that are due: those for which the days since `last_reviewed` are **at least** the interval for their box.
starter:
```python
from datetime import date

INTERVALS = {1: 1, 2: 2, 3: 4, 4: 8, 5: 16}


def due_cards(cards, today):
    pass
```
tests:
```python
cards = [
    ("sql joins", 1, "2026-03-01"),
    ("big o", 3, "2026-03-01"),
    ("tcp", 5, "2026-02-17"),
    ("regex", 4, "2026-03-05"),
]
assert due_cards(cards, "2026-03-05") == ["big o", "sql joins", "tcp"]
assert due_cards(cards, "2026-03-01") == []
assert due_cards(cards, "2026-03-13") == ["big o", "regex", "sql joins", "tcp"]
assert due_cards([], "2026-03-05") == []
```
model:
```python
from datetime import date

INTERVALS = {1: 1, 2: 2, 3: 4, 4: 8, 5: 16}


def due_cards(cards, today):
    now = date.fromisoformat(today)
    due = []
    for name, box, last in cards:
        elapsed = (now - date.fromisoformat(last)).days
        if elapsed >= INTERVALS[box]:
            due.append(name)
    return sorted(due)
```
hint: Compute the days since the last review with `date.fromisoformat`.
hint: Compare with `INTERVALS[box]` using `>=`, then sort the names.
solution: For each card compute the elapsed days and test against its box interval, using `>=` so a card is due exactly when the interval has passed. Sorting at the end gives alphabetical order. The `regex` card in box 4 becomes due only 8 days after 2026-03-05.

@quiz code
prompt: Write `longest_streak(dates)` that takes a list of ISO date strings (`"YYYY-MM-DD"`) on which you studied, possibly unsorted and with duplicates, and returns the length of the longest run of **consecutive calendar days**. An empty list returns `0`.
starter:
```python
from datetime import date, timedelta


def longest_streak(dates):
    pass
```
tests:
```python
assert longest_streak([]) == 0
assert longest_streak(["2026-03-01"]) == 1
assert longest_streak(["2026-03-03", "2026-03-01", "2026-03-02"]) == 3
assert longest_streak(["2026-03-01", "2026-03-01", "2026-03-03"]) == 1
assert longest_streak(["2026-02-28", "2026-03-01", "2026-03-02", "2026-03-05"]) == 3
```
model:
```python
from datetime import date, timedelta


def longest_streak(dates):
    days = sorted({date.fromisoformat(d) for d in dates})
    best = 0
    run = 0
    previous = None
    for day in days:
        if previous is not None and day - previous == timedelta(days=1):
            run += 1
        else:
            run = 1
        best = max(best, run)
        previous = day
    return best
```
hint: Remove duplicates with a set and sort the parsed dates.
hint: Walk the sorted days; extend the run if the day follows the previous one by exactly one day, otherwise restart at 1.
solution: Parse into `date` objects, deduplicate and sort, then track the current run length. A gap of more than one day restarts the run. Using real dates handles month boundaries such as 28 February to 1 March (2026 is not a leap year).
