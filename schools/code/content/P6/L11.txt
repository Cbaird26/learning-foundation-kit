@article
Software engineering offers many career shapes. You do not have to decide your whole future in your first year, but you do benefit from knowing what the options are and how growth is judged. People and companies below are **fictional**, and any numbers are **illustrative only**.

### Levels are local

Most companies define **levels** with expectations for each: scope, independence, impact and influence. Names and numbers differ widely (one company's "senior" is another's "mid-level"), the number of levels differs, and expectations change over time, so **never assume your company's ladder is universal.** Ask for the written ladder and your manager's interpretation. A commonly seen pattern, with imaginary example names:

| Level (example) | Typical scope | Typical expectations |
|---|---|---|
| Entry or junior | Well-defined tasks | Learns the codebase and tools, delivers small changes with guidance |
| Mid-level | Features | Works independently, writes tests and docs, reviews others' code |
| Senior | Projects and systems | Leads designs, handles ambiguity, mentors, improves team practices |
| Staff and above | Cross-team or organization-wide problems | Sets technical direction, influences without authority, multiplies others |

The pattern is **scope of problems you handle without supervision**, not years of experience. Time at a level varies a lot between people.

### Two tracks

Beyond senior, many companies offer an **individual contributor (IC)** track (staff, principal and so on) and a **management** track (engineering manager, director). They are not a ladder where management is "up": they are different jobs. ICs solve hard technical and cross-team problems; managers build teams, grow people and ensure delivery. Some people move back and forth. A good way to test management is to try parts of it: tech-lead a project, mentor an intern, run a retrospective, and see whether you enjoy the work and the lack of coding time.

### Specialties and environments

You can specialize or stay broad. Common areas: **backend**, **frontend**, **mobile**, **infrastructure, platform and site reliability**, **security**, **data and machine learning**, **embedded and systems**, **games**, **developer tools**. A "T-shaped" engineer has deep skill in one area and working knowledge of neighbors. Environments differ too: **startups** (broad responsibility, fast change, less structure), **large companies** (specialization, scale, process), **consultancies and agencies** (varied clients), **non-profits, government and research** (mission, different pace), and **open source** (public work). None is best; each trains different skills. Try more than one early if you can.

### How growth really happens

- **Do the work of the next level before you are promoted**, with your manager's agreement, then show the evidence.
- **Keep a record** (sometimes called a brag document): what you shipped, the problem it solved, the impact (numbers when possible), who you helped. It makes reviews and promotion cases much easier.
- **Ask for feedback regularly**, specifically ("What is one thing that would make my design docs easier to review?").
- **Find mentors and sponsors.** A mentor advises you; a sponsor uses their influence to create opportunities for you. Both help; sponsorship comes from visible good work.
- **Pick up unglamorous, high-leverage work**: onboarding docs, flaky tests, on-call improvements. Impact beats busyness.
- **Compensation** depends on location, company, level and market conditions, and it changes over time. Use current, reliable data sources, know your market range, and negotiate respectfully; this course gives no figures because they would be misleading.
- **Interviewing is a skill** that fades if unused. Keep notes on your accomplishments and keep in touch with your network even when you are happy where you are.
- **Setbacks happen:** layoffs, reorganizations, a project canceled. Keep your skills and relationships current, save some money if you can, and treat setbacks as information, not as a verdict on you.

### Setting a growth goal

A good goal is **specific, measurable, tied to a reason and dated**: "By the end of Q2, lead the design and rollout of one service change end to end, with a design doc approved and zero rollbacks" is better than "get better at design." Compare your current skills to those a target role needs (a skills gap) and choose a few goals; too many means none is finished.

title: Computing a skill gap
problem: On a 0 to 5 self-assessment, your fictional skills are testing 3, system design 2, on-call 1. The target role needs testing 4, system design 4, on-call 3, and observability 3 (which you have not rated). Which skills have gaps and how big?

step: Testing: $4 - 3 = 1$. System design: $4 - 2 = 2$. On-call: $3 - 1 = 2$. Observability: $3 - 0 = 3$.

answer: Gaps are testing 1, system design 2, on-call 2, observability 3.

@mistakes
- Assuming one company's titles and levels apply everywhere, or treating years of experience as the measure of level.
- Believing management is the only way to grow, or that IC work is "lesser."
- Waiting to be noticed instead of keeping records and asking for feedback and scope.
- Setting vague goals ("get better") with no measure or date, or too many goals to finish.

tests:
```python
cur = {"testing": 3, "design": 2, "oncall": 1}
tgt = {"testing": 4, "design": 4, "oncall": 3, "observability": 3}
assert skills_gap(cur, tgt) == {"testing": 1, "design": 2, "oncall": 2, "observability": 3}
assert skills_gap({"a": 5}, {"a": 3}) == {}

assert skills_gap({"extra": 4}, {"a": 1}) == {"a": 1}
```
model:
```python
def skills_gap(current, target):
    gaps = {}
    for skill, wanted in target.items():
        have = current.get(skill, 0)
        if wanted > have:
            gaps[skill] = wanted - have
    return gaps
```
hint: Loop over the target skills; use `current.get(skill, 0)` for missing skills.
hint: Add an entry only when the target is strictly higher.
solution: For each target skill, compare with the current level (default 0) and record the difference when positive. Skills only in `current` are irrelevant to the gap, which the last test checks.

model:
```python
from datetime import date


def invalid_goals(goals, today):
    now = date.fromisoformat(today)
    bad = []
    for goal in goals:
        measure = goal.get("measure")
        due = goal.get("due")
        if not measure or not measure.strip() or not due:
            bad.append(goal["name"])
            continue
        days = (date.fromisoformat(due) - now).days
        if days <= 0 or days > 365:
            bad.append(goal["name"])
    return bad
```
hint: Check for a missing or blank `measure` and a missing `due` before parsing any dates.
hint: Days between today and the due date must be at least 1 and at most 365.
solution: Use `dict.get` so missing keys do not raise, reject blank measures and missing dues, then compute the number of days from today and reject values outside 1 to 365. The `2027-01-01` goal is exactly 365 days away and is valid; `2027-01-02` is not.

model:
```python
from datetime import date


def quarter_index(start, due):
    days = (date.fromisoformat(due) - date.fromisoformat(start)).days
    if days < 0 or days > 364:
        return None
    return min(4, days // 91 + 1)
```
hint: Compute the number of days between the two dates first and reject out-of-range values.
hint: Integer division by 91 gives 0, 1, 2, 3 for the first four blocks; the last day (364) must still map to quarter 4.
solution: Compute `days`, return `None` outside 0 to 364, then use `days // 91 + 1` capped at 4 (day 364 would otherwise be 5, because the fourth block is 92 days long). The boundary tests at days 90, 91 and 364 check each edge.
