@article
**Encapsulation** means a class keeps its data hidden behind a small set of methods, so outside code cannot put the object into a broken state. Think of a bank account: nobody should be able to write `acct.balance = -1000000` and skip the rules. The rules about what a valid object looks like are its **invariants** (for example "the balance is never negative"), and a well-designed class enforces them in one place: its own methods.

### Python's conventions

Python has no strict `private` keyword. It uses naming conventions:

- `name`: public, part of the class's interface.
- `_name`: **internal by convention**. Other code should not touch it, but Python will not stop it.
- `__name`: **name mangling**. Inside `class Safe`, `self.__code` is stored as `_Safe__code`, which makes accidental access from outside (and clashes in subclasses) harder. It is still not real security.

```python
class Safe:
    def __init__(self):
        self.__code = 1234

s = Safe()
# s.__code             -> AttributeError
print(s._Safe__code)   # 1234: mangled, but reachable
```

Use the single underscore for ordinary internal data; mangling is rarely needed.

### Properties

A **property** looks like an attribute to callers but runs code. That lets you start with a plain attribute and add validation later without changing how the class is used:

```python
class Student:
    def __init__(self, name, age):
        self.name = name
        self.age = age          # goes through the setter below

    @property
    def age(self):
        return self._age

    @age.setter
    def age(self, value):
        if value < 0:
            raise ValueError("age cannot be negative")
        self._age = value
```

`s.age` calls the getter; `s.age = 17` calls the setter. Because `__init__` assigns `self.age`, the validation also runs when the object is created. A property with **no setter** is read-only: assigning to it raises `AttributeError`. Read-only properties are ideal for **derived values** such as `area` computed from `width` and `height`, since they can never go out of date.

### Do not leak internal state

If a method returns an internal list, the caller can modify it and bypass your rules. Return a copy (`list(self._items)`) or a tuple, or return only a derived answer.

### Designing a class from a description

Given a paragraph of requirements, a reliable method is:

1. Underline the **nouns**: candidates for classes or attributes (a *library*, a *book*, a *member*).
2. Underline the **verbs**: candidates for methods (*check out*, *return*).
3. Decide what each object must remember (attributes) and which of those are internal.
4. Write down the **rules** (invariants) and decide which method enforces each.
5. Write a few example calls as tests *before* the code.

Keep each class focused on one idea. If a class needs the word "and" to describe it ("it stores books *and* prints reports *and* sends email"), it is probably two or three classes. This is the *single responsibility* idea that you will meet again in design courses.

@example
title: Adding validation with a property
problem: A `Thermostat` stores a target temperature that must stay between 10 and 30. Write it so that the rule holds even when the target is assigned directly.
step: Store the value in `_target` and expose `target` as a property, so every assignment goes through code.
step: Write the getter, and the setter that checks the range before storing:

```python
class Thermostat:
    def __init__(self, target=20):
        self.target = target

    @property
    def target(self):
        return self._target

    @target.setter
    def target(self, value):
        if not 10 <= value <= 30:
            raise ValueError("target must be between 10 and 30")
        self._target = value
```
step: `Thermostat()` stores `20`. `t.target = 25` works. `t.target = 40` raises `ValueError`, and `t.target` is still `25`, because the setter raises before assigning.
step: `Thermostat(5)` also raises, since `__init__` uses the setter. The invariant holds from the first moment.

@example
title: From description to class
problem: "A reading list holds book titles. You can add a title (never the same one twice) and ask how many titles it holds." Design the class.
step: Noun: reading list, with titles it must remember: one attribute, a list `_titles`, created in `__init__`.
step: Verbs and questions: `add(title)` and `count()`. The rule "never twice" is enforced inside `add`.
step: Write it:

```python
class ReadingList:
    def __init__(self):
        self._titles = []

    def add(self, title):
        if title in self._titles:
            raise ValueError("already on the list")
        self._titles.append(title)

    def count(self):
        return len(self._titles)
```
step: Callers use `add` and `count`; they never touch `_titles`, so the rule cannot be bypassed by accident.

@mistakes
- Believing a leading underscore or double underscore makes data truly private. These are conventions and obfuscation; they signal intent only.
- Validating in a setter but writing `self._age = age` in `__init__`, which skips the check at creation.
- Returning the internal list from a method, so callers can change it without going through the rules.
- Writing a property setter that assigns to the property's own name (`self.age = value`), which calls the setter again forever. Store in `self._age`.

```python
class Temperature:
    def __init__(self, celsius=0.0):
        self.celsius = celsius

    @property
    def celsius(self):
        return self._celsius

    @celsius.setter
    def celsius(self, value):

        self._celsius = value

    @property
    def fahrenheit(self):
        return self._celsius * 9 / 5 + 32
```

@practice code
prompt: Write a class `Inventory` that tracks item counts. `add(item, qty=1)` and `remove(item, qty=1)` change the count; both raise `ValueError` if `qty` is not positive, and `remove` also raises `ValueError` if there is not enough stock (leaving the stock unchanged). `quantity(item)` returns the count (`0` for an unknown item). `items()` returns a **new sorted list** of the names currently in stock; an item whose count reaches `0` is no longer listed. Keep the data in a private attribute.
starter:
```python
class Inventory:
    pass
```
tests:
```python
inv = Inventory()
inv.add("pen", 5)
inv.add("cup")
inv.add("pen", 2)
assert inv.quantity("pen") == 7
assert inv.quantity("cup") == 1
assert inv.quantity("ink") == 0
assert inv.items() == ["cup", "pen"]
inv.items().append("zzz")
assert inv.items() == ["cup", "pen"]
inv.remove("cup")

assert raises(ValueError, inv.remove, "pen", 8)

assert raises(ValueError, inv.remove, "pen", 0)

assert raises(ValueError, inv.remove, "ink")
```
model:
```python
class Inventory:
    def __init__(self):
        self._stock = {}

    def add(self, item, qty=1):
        if qty <= 0:
            raise ValueError("qty must be positive")
        self._stock[item] = self._stock.get(item, 0) + qty

    def remove(self, item, qty=1):
        if qty <= 0:
            raise ValueError("qty must be positive")
        if qty > self.quantity(item):
            raise ValueError("not enough stock")
        self._stock[item] -= qty
        if self._stock[item] == 0:
            del self._stock[item]

    def quantity(self, item):
        return self._stock.get(item, 0)

    def items(self):
        return sorted(self._stock)
```
hint: A dictionary from item name to count works well; `dict.get(key, 0)` gives `0` for unknown items.
hint: `sorted(...)` always returns a new list, which is exactly what `items()` should hand out. Delete an entry when its count hits zero.
solution: Keep `_stock` as a dictionary. Validate before changing anything. `remove` deletes the key when the count reaches `0`, so `items()` (which returns `sorted(self._stock)`, a fresh list) never lists empty items.

@quiz code
prompt: Write a class `Grade` with a property `score`. `Grade(score)` stores a number from 0 to 100 inclusive; the setter raises `ValueError` outside that range and leaves the old score unchanged.     pass
tests:
```python
assert Grade(95).letter == "A"
assert Grade(90).letter == "A"
assert Grade(89.9).letter == "B"
assert Grade(70).letter == "C"
assert Grade(60).letter == "D"
assert Grade(59).letter == "F"

assert Grade(100).score == 100
g = Grade(50)
g.score = 85
assert g.letter == "B"

assert g.score == 85

assert raises(AttributeError, setattr, g, "letter", "A")
```
model:
```python
class Grade:
    def __init__(self, score):
        self.score = score

    @property
    def score(self):
        return self._score

    @score.setter
    def score(self, value):
        if not 0 <= value <= 100:
            raise ValueError("score must be between 0 and 100")
        self._score = value

    @property
    def letter(self):
        if self._score >= 90:
            return "A"
        if self._score >= 80:
            return "B"
        if self._score >= 70:
            return "C"
        if self._score >= 60:
            return "D"
        return "F"
```
hint: Make `score` a property with a validating setter, assigned in `__init__` through `self.score`.
hint: `letter` has only a getter, computed from the score each time, so it can never disagree with it.
solution: The setter checks `0 <= value <= 100` and raises before storing. `letter` is a getter-only property that tests the thresholds from highest to lowest, so a score of exactly 90 is an `A` and 89.9 is a `B`.
