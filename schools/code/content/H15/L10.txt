@article
Simple sorts such as selection sort and insertion sort compare many pairs of items: for $n$ items they take about $n^2$ steps, which is fine for 100 items and painful for a million. **Merge sort** and **quicksort** use recursion to do the job in about $n \log_2 n$ steps on typical input.

### Merge sort: divide, sort, combine

1. If the list has 0 or 1 items, it is already sorted.
2. Otherwise split it into a left half and a right half.
3. Sort each half recursively.
4. **Merge** the two sorted halves into one sorted list.

The key is merging, which is easy because both halves are sorted: keep one position in each list, repeatedly compare the two current items, and take the smaller.

```python
def merge(a, b):
    result = []
    i = j = 0
    while i < len(a) and j < len(b):
        if a[i] <= b[j]:
            result.append(a[i])
            i += 1
        else:
            result.append(b[j])
            j += 1
    result.extend(a[i:])
    result.extend(b[j:])
    return result


def merge_sort(items):
    if len(items) <= 1:
        return list(items)
    mid = len(items) // 2
    return merge(merge_sort(items[:mid]), merge_sort(items[mid:]))
```

Using `<=` takes the left item on ties, which makes the sort **stable** (equal items keep their original order). Merging two lists with $n$ items in total costs at most $n - 1$ comparisons. The list is halved about $\log_2 n$ times, and every level of the recursion does about $n$ work in total, so merge sort takes $O(n \log n)$ time in the best, average and worst cases. It needs $O(n)$ extra memory for the merged lists.

### Counting steps

You can measure the work by counting comparisons: add one to a counter each time the `while` loop compares `a[i]` with `b[j]`. For 8 items the count is at most $8 \log_2 8 = 24$; the actual numbers are somewhat lower. Counting comparisons is the standard way to compare sorting algorithms because it does not depend on how fast your computer is.

### Quicksort: partition around a pivot

1. If the list has 0 or 1 items, return it.
2. Choose a **pivot** item.
3. Partition: put items smaller than the pivot on the left, equal ones in the middle, larger ones on the right.
4. Sort the left and right parts recursively and join them.

```python
def quicksort(items):
    if len(items) <= 1:
        return list(items)
    pivot = items[0]
    smaller = [x for x in items if x < pivot]
    equal = [x for x in items if x == pivot]
    larger = [x for x in items if x > pivot]
    return quicksort(smaller) + equal + quicksort(larger)
```

When the pivot splits the list roughly in half, there are about $\log_2 n$ levels with $n$ work each, so the **average** time is $O(n \log n)$. But if the pivot is always the smallest or largest item (for example, the first item of a list that is already sorted), one part is empty and the other has $n - 1$ items. That makes about $n$ levels and the **worst case** is $O(n^2)$. Real implementations choose pivots more carefully (random, or the median of three items) to make bad splits unlikely, and partition in place to avoid extra lists.

### Comparing the two

| | merge sort | quicksort (simple version) |
|---|---|---|
| average time | $O(n \log n)$ | $O(n \log n)$ |
| worst time | $O(n \log n)$ | $O(n^2)$ |
| extra memory | $O(n)$ | $O(n)$ here; in-place versions need only $O(\log n)$ stack |
| stable | yes (with `<=`) | not in the usual in-place form |

Python's built-in `sorted` and `list.sort` use **Timsort**, a stable algorithm that combines merging with insertion sort and is very fast on partly sorted data. In real programs you use it; you write merge sort and quicksort to understand divide and conquer, which appears again and again in algorithms.

@example
title: Merging by hand
problem: Merge the sorted lists `[2, 5, 8]` and `[3, 4, 9, 10]`. How many comparisons are made?
step: Compare `2` and `3`: take `2`. Compare `5` and `3`: take `3`. Compare `5` and `4`: take `4`. (3 comparisons so far; result `[2, 3, 4]`.)
step: Compare `5` and `9`: take `5`. Compare `8` and `9`: take `8`. (5 comparisons; result `[2, 3, 4, 5, 8]`.)
step: The first list is now used up, so no more comparisons are needed: append the rest of the second list, `[9, 10]`.
step: The result is `[2, 3, 4, 5, 8, 9, 10]`, after 5 comparisons.
answer: `[2, 3, 4, 5, 8, 9, 10]` with 5 comparisons

@example
title: Tracing quicksort
problem: Show how `quicksort([3, 1, 4, 1, 5])` sorts, using the first item as the pivot.
step: Pivot `3`: smaller is `[1, 1]`, equal is `[3]`, larger is `[4, 5]`.
step: `quicksort([1, 1])`: pivot `1`, smaller is empty, equal is `[1, 1]`, larger is empty, so it returns `[1, 1]`.
step: `quicksort([4, 5])`: pivot `4`, smaller empty, equal `[4]`, larger `[5]`, so it returns `[4, 5]`.
step: Join: `[1, 1] + [3] + [4, 5]`, giving `[1, 1, 3, 4, 5]`. Handling equal items in their own list is what lets duplicates terminate.

@mistakes
- Forgetting to append the leftovers after the `while` loop in `merge`, which drops items from whichever list was not used up.
- Using `<` instead of `<=` when merging, which is still a valid sort but no longer stable.
- Putting the equal items into only one side in quicksort, which can recurse forever on a list of identical values; keep a separate `equal` list.
- Claiming quicksort is always $O(n \log n)$; with a poor pivot it degrades to $O(n^2)$.

```python
def merge_sort_count(items):
    if len(items) <= 1:
        return list(items), 0
    mid = len(items) // 2
    left, left_count = merge_sort_count(items[:mid])
    right, right_count = merge_sort_count(items[mid:])
    merged = []
    count = 0
    i = j = 0
    while i < len(left) and j < len(right):
        count += 1
        if left[i] <= right[j]:
            merged.append(left[i])
            i += 1
        else:
            merged.append(right[j])
            j += 1
    merged.extend(left[i:])
    merged.extend(right[j:])
    return merged, left_count + right_count + count
```

hint: Increase the counter once per pass of the `while` loop (each pass compares one pair), not when appending the leftovers.

For `[3, 1, 2]` the halves `[3]` and `[1, 2]` cost 0 and 1 comparisons, and merging them costs 2 more: 3 in total.

model:
```python
def kth_smallest(items, k):
    pivot = items[0]
    smaller = [x for x in items if x < pivot]
    equal = [x for x in items if x == pivot]
    larger = [x for x in items if x > pivot]
    if k < len(smaller):
        return kth_smallest(smaller, k)
    if k < len(smaller) + len(equal):
        return pivot
    return kth_smallest(larger, k - len(smaller) - len(equal))
```
hint: After partitioning, positions `0..len(smaller) - 1` hold the smaller items, then come the equal items, then the larger ones.
hint: If `k` falls in the equal block, the answer is the pivot; if it falls in the larger block, subtract the sizes of the two earlier blocks from `k`.
solution: Compare `k` with the block sizes. In the `smaller` block, recurse there with the same `k`. In the `equal` block, the pivot is the answer. Otherwise recurse into `larger` with `k` reduced by the number of items in the first two blocks. Only one side is explored, so on average this does less work than a full sort.
