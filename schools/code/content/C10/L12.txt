@article
Durability and atomicity must survive crashes. Main memory is lost when a machine fails, but the buffer pool holds modified pages that may not yet be on disk. **Recovery** restores a consistent state after a crash.

### Buffer management policies

Two policies decide what can be on disk at a crash. **Steal** allows a dirty page of an *uncommitted* transaction to be written to disk (to free buffer space); then recovery must be able to **undo** it. **No-force** means a transaction need not write its changed pages to disk at commit; then recovery must be able to **redo** committed work that never reached disk. Most systems use **steal and no-force** because it is the fastest, and rely on a log to repair the consequences.

### Write-ahead logging

The **log** is an append-only sequence of records on stable storage: `begin T`, update records `(T, item, old value, new value)`, `commit T` and `abort T`. The **write-ahead logging (WAL)** rule has two parts: a log record describing a change must reach disk **before** the changed data page does (so undo information exists), and all of a transaction's log records, including `commit`, must be on disk **before** commit is acknowledged (so redo information exists). Appending to a log is sequential and fast, while flushing scattered data pages is slow, so WAL makes commit cheap.

### Recovery with the log

After a crash the **ARIES** algorithm, the model for many real systems, runs three passes:

1. **Analysis**: scan the log from the last checkpoint to find which transactions were active (the *losers*) and which pages may have been dirty.
2. **Redo**: *repeat history*: reapply logged updates, including those of transactions that will be undone, to bring the database to its exact state at the crash. Each page stores the **log sequence number (LSN)** of its last applied update, so an already-applied update is skipped, which makes redo **idempotent**.
3. **Undo**: roll back the losers by undoing their updates in reverse order, writing **compensation log records (CLRs)** so that a crash during recovery never undoes the same change twice.

A **checkpoint** periodically records the active transactions and dirty pages so recovery need not read the whole log.

### NoSQL data models

"NoSQL" ("not only SQL") covers systems that relax parts of the relational model, usually to scale out across many machines or to fit a data shape better:

- **Key-value stores**: a hash-table-like map from key to opaque value; simplest and fastest (caches, sessions).
- **Document stores**: values are self-describing documents (JSON-like), queried by fields; flexible schema, good for nested data read as a unit.
- **Wide-column stores**: rows with many sparse columns grouped in families, partitioned by key; built for huge write volumes.
- **Graph databases**: nodes and edges are first-class, with traversal queries; fit relationship-heavy data.

Many support limited joins and transactions. The trade is flexibility and horizontal scaling against ad hoc queries and strong guarantees. Relational systems have also adopted JSON columns, and "NewSQL" or distributed SQL systems provide SQL with ACID transactions across machines.

### Distributing data

**Replication** keeps copies on several machines for availability and read throughput. In **leader-follower** replication writes go to the leader and are shipped to followers, **synchronously** (the write waits, so no committed data is lost on failover but latency rises) or **asynchronously** (faster, but a leader failure can lose recent writes, and followers can serve stale reads, called **replication lag**). **Sharding** (partitioning) splits the data by key across machines, by **hash** (even load, poor range scans) or by **range** (good range scans, risk of hot spots).

With $N$ replicas, a **quorum** system requires $W$ replicas to acknowledge a write and reads $R$ replicas. If $R + W > N$ every read quorum overlaps every write quorum, so a read sees the latest acknowledged write (given version numbers to choose the newest).

The **CAP theorem** says that when a network **partition** occurs, a replicated system must choose between **consistency** (every read returns the latest write, as if there were one copy) and **availability** (every request to a working node gets an answer). Partitions cannot be ruled out in real networks, so the real choice is made during partitions; when the network is healthy there is still a trade-off between latency and consistency. **Eventual consistency** guarantees only that replicas converge if updates stop, the model behind **BASE** ("basically available, soft state, eventually consistent"), as opposed to ACID.

### Distributed commit and consensus

To commit one transaction across several machines, **two-phase commit (2PC)** uses a coordinator. In the **prepare** phase each participant makes its changes durable and votes yes or no. If all vote yes, the coordinator logs *commit* and tells everyone to commit; any no vote means abort. A participant that voted yes must wait for the decision, so if the coordinator crashes at that moment participants are **blocked** while holding locks. Replicated systems use **consensus protocols** such as Paxos and Raft to make a group of machines agree on a log of operations despite failures of a minority.

@example
title: Replaying a log after a crash
problem: Log: begin T1; (T1, x, 0, 5); begin T2; (T2, y, 0, 7); commit T1; (T2, x, 5, 9). The crash happens before T2 commits. Give the recovered values of x and y.
step: Analysis: T1 committed; T2 has no commit, so T2 is a loser.
step: Redo repeats history: x = 5, y = 7, then x = 9.
step: Undo T2 in reverse log order: the update (T2, x, 5, 9) is undone, so x = 5; then (T2, y, 0, 7) is undone, so y returns to 0.
step: The result contains T1's committed change only.
answer: x = 5 and y = 0.

@example
title: Choosing quorum sizes
problem: A store has $N = 5$ replicas and writes need $W = 4$ acknowledgements. What is the smallest read quorum $R$ that guarantees reads see the latest write?
step: The overlap condition is $R + W > N$.
step: With $W = 4$ and $N = 5$ we need $R + 4 > 5$, so $R > 1$.
step: The smallest integer is $R = 2$.
answer: $R = 2$ (and a larger $W$ makes writes slower and less available).

@mistakes
- Believing that data pages must be written at commit; with no-force only the log must reach disk.
- Undoing a loser's changes before redoing history; ARIES redoes everything first, then undoes losers.
- Reading CAP as "choose any two of three"; partitions happen, so the choice is consistency or availability while one is happening.
- Assuming eventual consistency means data may be permanently inconsistent; it means replicas converge when updates stop.

model:
```python
def recover(log):
    db = {}
    committed = {rec[1] for rec in log if rec[0] == "commit"}
    for rec in log:
        if rec[0] == "update":
            _, _, item, _, new = rec
            if new is None:
                db.pop(item, None)
            else:
                db[item] = new
    for rec in reversed(log):
        if rec[0] == "update" and rec[1] not in committed:
            _, _, item, old, _ = rec
            if old is None:
                db.pop(item, None)
            else:
                db[item] = old
    return db
```
hint: Find the set of committed transactions first.
hint: Do two passes: a forward pass applying every `new` value, then a backward pass restoring `old` values for the transactions not in that set.
solution: Redo applies all updates in order so the state equals the state at the crash. Undo then walks the log backwards restoring each loser's `old` values, which correctly unwinds several updates of the same item (`lost` ends with `k` removed).
