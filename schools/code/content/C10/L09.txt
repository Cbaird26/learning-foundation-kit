@article
A relation is a logical idea; physically the rows live on disk (or SSD) and must be read into memory to be used. A **disk-oriented** database system organizes data into fixed-size **pages**, typically 4 KB to 16 KB (SQLite defaults to 4 KB, PostgreSQL to 8 KB). The page is the unit of transfer, so the main cost measure in this lesson is the **number of page reads and writes (I/Os)**, because reading a page is far slower than touching memory.

### Pages, heap files and the buffer pool

A **heap file** is an unordered collection of pages holding a table's rows. Within a page the **slotted page** layout keeps a slot directory at the front, pointing to variable-length rows; a row is addressed by a **record id** (page number, slot number). Rows that fit `r` per page occupy $\lceil n / r \rceil$ pages for $n$ rows, where $r = \lfloor \text{page size} / \text{row size} \rfloor$.

Reading a page goes through the **buffer pool**, a region of memory caching pages. If the page is in the pool (a *hit*) no I/O happens. Otherwise a page is evicted by a **replacement policy** (LRU, or the cheaper clock approximation) and the requested page is read. A full table scan reads every page: cost equals the number of pages.

### Why indexes

Without an index, `WHERE id = 42` scans the whole heap file. An **index** is an auxiliary structure mapping search-key values to record ids, so a lookup reads a few pages. It is a redundant copy of part of the data, so it speeds reads and **slows writes** (every insert, delete or key update must also change each index) and costs space.

### B+ trees

The **B+ tree** is the default index in nearly every relational system. It is a balanced multiway search tree:

- **All leaves are at the same depth**, so every lookup reads the same number of pages.
- **Internal nodes** hold sorted separator keys and child pointers, and route the search.
- **Leaves** hold the sorted keys with record ids (or the rows themselves), and are linked left to right as a list, so **range scans** follow leaf links after finding the start.
- Each node is a page. The **fanout** $f$ is the maximum number of children per node. Apart from the root, nodes stay at least half full.

With 4 KB pages and 8-byte keys and pointers a node holds roughly 250 entries, so a tree of 3 levels indexes about $250^3 \approx 15$ million entries. Lookup cost is $O(\log_f N)$ page reads, which in practice is 3 or 4, with the top levels usually cached.

**Search** for key $k$: at each internal node follow the child whose key range contains $k$, down to a leaf, then look in the leaf. A **range query** `k BETWEEN lo AND hi` searches for `lo`, then scans leaves rightward until a key exceeds `hi`.

**Insertion**: find the leaf, insert the key in sorted order. If the leaf now exceeds its capacity, **split** it into two halves and insert a separator key into the parent (for a leaf split the separator is a *copy* of the first key of the right half). If the parent overflows it splits too (for an internal split the middle key moves up). A split that reaches the root creates a new root, which is the only way a B+ tree gets taller. Deletion removes the key and, if a node becomes too empty, borrows from or merges with a sibling.

### Hash indexes

A **hash index** applies a hash function to the key to pick a **bucket** page. Equality lookup costs about one page read, but a hash index cannot answer range queries or sorting, because hashing destroys order. **Static hashing** with a fixed bucket count degrades as data grows (long overflow chains). **Extendible hashing** keeps a directory of $2^d$ bucket pointers, where $d$ is the **global depth**, indexed by the low-order $d$ bits of the hash value. A full bucket splits; if its **local depth** equals the global depth the directory doubles first. **Linear hashing** instead splits buckets one at a time in a fixed order, avoiding a directory.

### Index choices

A **clustered** index stores the rows in key order (one per table); other indexes are **unclustered**, so each match costs an extra page read. A **composite** index on $(a, b)$ sorts by $a$, then $b$, so it can seek on `a`, or on `a` and `b`, but not on `b` alone (the **leftmost-prefix** rule). A **covering** index contains every column a query needs, so the table is never read. Functions applied to the column (`WHERE UPPER(name) = 'X'`) or a leading wildcard (`LIKE '%x'`) prevent index seeks unless an index is built on that exact expression.

@example
title: Splitting a leaf
problem: A B+ tree leaf holds at most 3 keys: 10, 20, 30. Insert 40 and show the result.
step: Insert in sorted order: the leaf becomes 10, 20, 30, 40, which exceeds the capacity of 3.
step: Split into two halves: the left leaf keeps 10, 20 and the right leaf gets 30, 40.
step: The separator key copied up to the parent is the first key of the right leaf, 30.
step: The parent now routes keys below 30 to the left leaf and keys 30 and above to the right leaf. If there was no parent, a new root with the single key 30 is created and the tree grows by one level.
answer: Leaves [10, 20] and [30, 40] with separator 30.

@example
title: Estimating pages and lookup cost
problem: A table has 100,000 rows of 100 bytes in 4096-byte pages (ignore page headers). An index has fanout 200. How many pages does the table need, and how many page reads does an index lookup need at most for 100,000 keys?
step: Rows per page: $\lfloor 4096 / 100 \rfloor = 40$.
step: Pages: $\lceil 100000 / 40 \rceil = 2500$, so a full scan reads 2500 pages.
step: Levels needed: $200^2 = 40{,}000 < 100{,}000 \le 200^3$, so 3 levels.
step: A lookup reads about 3 index pages plus 1 data page (unclustered), roughly 4 reads instead of 2500.
answer: 2500 pages; about 3 index reads plus 1 table read.

@mistakes
- Using a B+ tree height formula with the wrong base: the base is the fanout, not 2.
- Expecting an index on `(a, b)` to help `WHERE b = 5`; the leftmost-prefix rule says it cannot seek on `b` alone.
- Adding an index for every column; each index slows writes and uses space.
- Thinking a hash index can serve `ORDER BY` or range queries.

```python
def split_leaf(keys, max_keys):
    if len(keys) <= max_keys:
        return list(keys), [], None
    mid = (len(keys) + 1) // 2
    left = keys[:mid]
    right = keys[mid:]
    return left, right, right[0]
```

@quiz code
prompt: Write `range_scan(sorted_keys, lo, hi)` that returns the list of keys `k` of the sorted list `sorted_keys` with `lo <= k <= hi`, in order, the way a B+ tree range scan would: locate the start with binary search (use the `bisect` module) and take the contiguous run. Duplicate keys are all returned. If `lo > hi` return `[]`.
starter:
```python
def range_scan(sorted_keys, lo, hi):
    pass
```
tests:
```python
keys = [2, 4, 4, 7, 9, 12]
assert range_scan(keys, 4, 9) == [4, 4, 7, 9]
assert range_scan(keys, 5, 6) == []
assert range_scan(keys, 0, 100) == keys
assert range_scan(keys, 9, 4) == []
assert range_scan([], 1, 5) == []
assert range_scan(keys, 12, 12) == [12]
```
model:
```python
from bisect import bisect_left, bisect_right


def range_scan(sorted_keys, lo, hi):
    if lo > hi:
        return []
    start = bisect_left(sorted_keys, lo)
    end = bisect_right(sorted_keys, hi)
    return sorted_keys[start:end]
```
hint: `bisect_left(keys, lo)` gives the first position holding a value at least `lo`.
hint: `bisect_right(keys, hi)` gives the position just after the last value at most `hi`.
solution: Two binary searches find the boundaries of the run, `bisect_left` for `lo` and `bisect_right` for `hi`, and a slice returns it. The cost is $O(\log n + k)$ for $k$ results, like a tree descent plus a leaf scan.
