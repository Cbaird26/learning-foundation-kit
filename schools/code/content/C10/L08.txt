@article
Bad table design stores the same fact in several rows. Consider `Order(order_id, product_id, product_name, customer_id, customer_city, qty)`. The product name repeats on every line of every order for that product. This causes three **anomalies**: an **update anomaly** (renaming a product means changing many rows; miss one and the data contradicts itself), an **insertion anomaly** (you cannot record a new product until someone orders it) and a **deletion anomaly** (deleting a product's last order erases the product). **Normalization** removes these by splitting tables according to **functional dependencies**.

### Functional dependencies

A **functional dependency** (FD) $X \to Y$ on a relation says that any two tuples with equal values on the attribute set $X$ also have equal values on $Y$. Like keys, FDs are rules of the schema about *every* valid instance. $X \to Y$ is **trivial** when $Y \subseteq X$.

Armstrong's axioms generate every FD implied by a given set $F$:

- **Reflexivity**: if $Y \subseteq X$ then $X \to Y$.
- **Augmentation**: if $X \to Y$ then $XZ \to YZ$.
- **Transitivity**: if $X \to Y$ and $Y \to Z$ then $X \to Z$.

They are **sound** (they derive only true FDs) and **complete** (they derive all implied ones).

### Attribute closure

The **closure** $X^+$ of an attribute set $X$ is the set of all attributes functionally determined by $X$. To compute it, start with $X$, and repeat: for each FD $L \to R$ in $F$ with $L \subseteq$ the current set, add $R$. Stop when nothing changes. For $F = \{A \to B,\; B \to C,\; CD \to E\}$: $\{A\}^+ = \{A, B, C\}$ and $\{A, D\}^+ = \{A, B, C, D, E\}$.

Closure answers the main questions. $X$ is a **superkey** of $R$ exactly when $X^+$ contains all attributes of $R$; a candidate key is a minimal such $X$. $F$ implies $X \to Y$ exactly when $Y \subseteq X^+$. An attribute that appears in some candidate key is **prime**.

### Normal forms

- **1NF**: all values are atomic (no repeating groups or lists in a cell).
- **2NF**: 1NF, and no non-prime attribute depends on a *proper part* of a candidate key (no partial dependencies). This only matters for composite keys.
- **3NF**: for every nontrivial FD $X \to A$, either $X$ is a superkey or $A$ is prime. This removes transitive dependencies of non-key attributes on the key.
- **BCNF** (Boyce-Codd normal form): for every nontrivial FD $X \to Y$, $X$ is a superkey. BCNF implies 3NF, which implies 2NF.

The slogan for 3NF is "every non-key attribute depends on the key, the whole key, and nothing but the key"; BCNF removes even the prime-attribute exception.

### Decomposition

To fix a violation $X \to Y$, split $R$ into $R_1(X \cup Y)$ and $R_2(R - (Y - X))$. A decomposition must be **lossless-join**: joining the pieces gives back exactly the original tuples, with no spurious ones. A binary decomposition of $R$ into $R_1, R_2$ is lossless exactly when $R_1 \cap R_2 \to R_1$ or $R_1 \cap R_2 \to R_2$ holds (the common attributes are a key of one piece). The split on a violating $X \to Y$ always satisfies this, since $X$ determines $Y$.

A decomposition is **dependency-preserving** if every original FD can still be enforced within a single table. Decomposing into BCNF is always possible and lossless, but may lose dependency preservation. 3NF can always be reached with both properties, which is why 3NF is the practical target when preservation matters.

**Example.** `R(A, B, C)` with $AB \to C$ and $C \to B$. The candidate keys are $AB$ and $AC$, so all attributes are prime and $R$ is in 3NF. But $C \to B$ has a non-superkey left side, so $R$ is not in BCNF. Decomposing gives $R_1(C, B)$ and $R_2(A, C)$, which is lossless, but $AB \to C$ can no longer be checked in one table.

### When to stop

Normalized schemas avoid anomalies and save space, but queries need more joins. Designers sometimes **denormalize** deliberately (for example to speed up a read-heavy report) and accept the responsibility of keeping copies consistent.

@example
title: Closure and keys
problem: `R(A, B, C, D)` with FDs $A \to B$, $B \to C$ and $CD \to A$. Find all candidate keys.
step: Attribute $D$ appears on no right-hand side, so every key contains $D$.
step: $\{D\}^+ = \{D\}$, so $D$ alone is not a key.
step: $\{A, D\}^+$: $A \to B$ adds $B$, $B \to C$ adds $C$, giving $\{A, B, C, D\}$. So $AD$ is a key.
step: $\{B, D\}^+$: $B \to C$ adds $C$, then $CD \to A$ adds $A$, then $A \to B$ is already included: all four attributes. So $BD$ is a key. $\{C, D\}^+$: $CD \to A$ adds $A$, then $B$: all four. So $CD$ is a key.
answer: The candidate keys are $AD$, $BD$ and $CD$.

@example
title: Decomposing into BCNF
problem: `R(A, B, C)` has the FD $A \to B$ only. Decompose it into BCNF.
step: The only key is $AC$ (since $\{A, C\}^+ = \{A, B, C\}$ and neither $A$ nor $C$ alone suffices).
step: $A \to B$ is nontrivial and $A$ is not a superkey, so $R$ violates BCNF.
step: Split into $R_1(A, B)$ and $R_2(A, C)$.
step: $R_1$ has key $A$ and $R_2$ has no FDs, so both are in BCNF. The common attribute is $A$ and $A \to R_1$, so the join is lossless.
answer: $R_1(A, B)$ and $R_2(A, C)$.

@mistakes
- Treating an FD seen in sample data as a rule of the schema; a pattern in rows is not a dependency.
- Testing only the given FDs for BCNF violations and forgetting FDs that are implied by them (check the closure).
- Splitting a relation so that the pieces share no attributes, or share attributes that are a key of neither piece; the join then invents tuples.
- Assuming a BCNF decomposition always preserves every dependency.

model:
```python
def closure(attrs, fds):
    result = set(attrs)
    changed = True
    while changed:
        changed = False
        for lhs, rhs in fds:
            if set(lhs) <= result and not set(rhs) <= result:
                result |= set(rhs)
                changed = True
    return "".join(sorted(result))
```
hint: Keep a set that starts as `attrs` and grows.
hint: Repeat passes over all FDs until a full pass adds nothing new.
solution: Apply every FD whose left side is already inside the current set, adding its right side, and repeat until a pass makes no change. The final set is the closure; sort it for a canonical string.

model:
```python
def closure(attrs, fds):
    result = set(attrs)
    changed = True
    while changed:
        changed = False
        for lhs, rhs in fds:
            if set(lhs) <= result and not set(rhs) <= result:
                result |= set(rhs)
                changed = True
    return result


def bcnf_violations(attrs, fds):
    bad = []
    for lhs, rhs in fds:
        if set(rhs) <= set(lhs):
            continue
        if closure(lhs, fds) != set(attrs):
            bad.append((lhs, rhs))
    return bad
```
hint: You need the attribute closure of each left side, computed with all of the FDs.
hint: Skip trivial FDs, and report an FD when the closure of its left side is not the whole attribute set.
solution: For each FD, skip it if trivial; otherwise compute the closure of its left side using all FDs. If the closure is not every attribute, the left side is not a superkey, so the FD violates BCNF and is collected.

@quiz mc
prompt: `R(A, B, C)` satisfies $B \to C$ and no other nontrivial dependency. Which decomposition is lossless-join?
choice*: $R_1(B, C)$ and $R_2(A, B)$
choice: $R_1(A, B)$ and $R_2(A, C)$
choice: $R_1(A, C)$ and $R_2(B, C)$
choice: $R_1(A, B)$ and $R_2(C)$
hint: Compute the common attributes of the two pieces and ask whether they determine one whole piece.
solution: In the first decomposition the common attribute $B$ determines $C$, so $B \to R_1$ and the join is lossless. In the others the common attributes are $A$, $C$ or nothing, and none of them determines a whole piece, so joining can create tuples that were never in $R$.
