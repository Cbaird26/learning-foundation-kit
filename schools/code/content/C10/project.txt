material: **Requirements: CityBike service.**

CityBike runs bike stations around a city. The database must store the following facts.

- A **station** has an id, a name (unique), a neighborhood and a dock capacity (a positive integer).
- A **bike** has an id, a model name and a purchase date. Every bike is either `standard` or `electric`. Each model has exactly one type, and the type is determined by the model.
- A **member** has an id, a name, a unique email address, a join date and one plan: `day-pass`, `monthly` or `annual`.
- A **trip** is made by one member on one bike. It records the start station, the start time and, once finished, the end station and the end time. Times are stored as ISO 8601 text such as `2025-06-14 08:30:00`. A trip that has not ended has no end time and no end station. A bike can be on at most one ongoing trip at a time. The end time must be later than the start time.
- A **technician** has an id, a name and a certification level (integer 1 to 3).
- A **maintenance event** is a repair or inspection of one bike by one technician on one date, with a description and a cost in cents. A technician may service many bikes, and a bike may be serviced many times.
- A **payment** is made by one member on one date for an amount in cents and refers to the trip it pays for, or to nothing if it is a plan fee.

@review
**Week 1: the relational model.** A relation is a set of tuples over named attributes; a SQL table is a bag. Superkeys identify tuples, candidate keys are minimal superkeys, foreign keys give referential integrity. `NULL` makes comparisons unknown, and `WHERE` keeps only true rows.

**Week 2: relational algebra.** Selection, projection (removes duplicates), union, difference, product, rename; joins and division are derived. "Not" questions use difference, "for all" questions use division.

**Weeks 3 to 5: querying.** Logical order: `FROM`, `WHERE`, `GROUP BY`, `HAVING`, `SELECT`, `ORDER BY`, `LIMIT`. `AND` binds tighter than `OR`. Inner joins drop unmatched rows, outer joins pad with NULL, and a filter on the right table of a left join belongs in `ON`. Aggregates ignore NULL, `COUNT(*)` counts rows, `WHERE` filters rows and `HAVING` filters groups. `NOT IN` with a NULL returns nothing; use `NOT EXISTS`.

**Week 6: changing data.** Always use `WHERE` on `UPDATE` and `DELETE`. Constraints (`PRIMARY KEY`, `UNIQUE`, `NOT NULL`, `CHECK`, `FOREIGN KEY`) are enforced by the database, and `CHECK` accepts unknown. Views are stored queries.

**Week 7: ER design.** Entities, attributes, relationships, cardinality, participation, weak entities. Mapping: foreign key on the N side of 1:N, a junction table for M:N, owner key plus partial key for weak entities.

**Week 8: normalization.** FDs, Armstrong's axioms, attribute closure, keys. BCNF: every nontrivial FD has a superkey on the left. Decompositions must be lossless; BCNF may lose dependency preservation, 3NF does not.

**Week 9: storage and indexes.** Pages are the unit of I/O; B+ tree height is about $\log_f N$; leaf splits copy a separator up; hash indexes only serve equality; composite indexes follow the leftmost-prefix rule.

**Week 10: query processing.** Iterator model, selection pushdown, join costs (block nested loop $M + \lceil M/(B-2) \rceil N$, hash join about $3(M+N)$ when partitioning), selectivity $1/V(A)$, and index choice from the workload.

**Week 11: transactions.** ACID, precedence graphs, strict 2PL, MVCC, anomalies (dirty read, non-repeatable read, phantom, lost update, write skew) and the isolation levels that allow them.

**Week 12: recovery and distribution.** WAL, steal/no-force, redo then undo, ARIES; NoSQL models; replication, quorums ($R + W > N$), CAP, two-phase commit.

**Self-check.** Can you: compute a closure and the keys of a schema; decompose to BCNF and test losslessness; write an anti-join and a division query; read an `EXPLAIN` plan; state which anomalies each isolation level allows; explain why commit needs only a log flush?

**Common errors.** Testing for NULL with `=`; forgetting that `HAVING` and `WHERE` run at different times; joining on a non-key and multiplying rows; assuming an index on `(a, b)` serves `b` alone; confusing a lost update with write skew; claiming serializability from one good run.

@exam code
prompt: Write `lossless_binary(attrs1, attrs2, fds)` that tells whether decomposing a relation into two relations with attribute strings `attrs1` and `attrs2` is lossless-join, given functional dependencies `fds` (a list of `(lhs, rhs)` string pairs). Compute the attribute closure of the common attributes (`set(attrs1) & set(attrs2)`); the decomposition is lossless exactly when that closure contains all of `attrs1` or all of `attrs2`. Return `True` or `False`.
starter:
```python
def lossless_binary(attrs1, attrs2, fds):
    pass
```
tests:
```python
fds = [("A", "B")]
assert lossless_binary("AB", "AC", fds) == True
assert lossless_binary("AB", "BC", fds) == False
assert lossless_binary("A", "B", fds) == False
assert lossless_binary("ABC", "AB", []) == True
chain = [("A", "B"), ("B", "C")]
assert lossless_binary("AB", "BC", chain) == True
```
model:
```python
def closure(attrs, fds):
    result = set(attrs)
    changed = True
    while changed:
        changed = False
        for lhs, rhs in fds:
            if set(lhs) <= result and not set(rhs) <= result:
                result |= set(rhs)
                changed = True
    return result


def lossless_binary(attrs1, attrs2, fds):
    common = set(attrs1) & set(attrs2)
    cl = closure(common, fds)
    return set(attrs1) <= cl or set(attrs2) <= cl
```
hint: You need the attribute closure of the common attributes; write it as a helper.
hint: Compare the closure with each of the two attribute sets using `<=` on sets.
solution: Compute the closure of the shared attributes with all FDs. If it covers one piece entirely, the shared attributes form a key of that piece, which is the condition for a lossless binary decomposition. With no shared attributes the closure is empty, so the test fails unless one piece is empty.

@exam self
prompt: A flight-booking table `flight(id, seats_left INTEGER)` has a row with `seats_left = 1`. The application runs: (1) `SELECT seats_left FROM flight WHERE id = 7`; (2) if the value is above 0, `UPDATE flight SET seats_left = <value - 1> WHERE id = 7`; each client runs it as its own transaction. Two clients do this at the same time. (a) Describe the interleaving that gives a wrong result and name the anomaly. (b) Say which isolation levels, under the standard's definitions, allow it, and which prevent it. (c) Give two ways to make the booking correct using SQL features from this course, and explain a cost of each.
solution: (a) Both clients read `seats_left = 1`, both see a value above 0, and both write 0 (computed from the value they read). Two seats were sold for one remaining seat and one update overwrote the other: a lost update (the schedule R1(x) R2(x) W1(x) W2(x) has a cycle in its precedence graph). (b) Under the standard's table, READ UNCOMMITTED and READ COMMITTED allow it, because the read and the write are not protected. REPEATABLE READ with read locks held to the end, or snapshot isolation, prevents it by making one transaction wait or abort (implementations differ: some systems' REPEATABLE READ still lets it happen), and SERIALIZABLE prevents it; in practice the losing transaction must be retried. (c) First, make the update itself conditional and atomic: `UPDATE flight SET seats_left = seats_left - 1 WHERE id = 7 AND seats_left > 0`, and check how many rows it changed (zero means sold out); the row lock held by the update serializes clients, at the cost of contention on a hot row. Second, keep the separate read and write but run the transaction at SERIALIZABLE (or under snapshot isolation, where the second writer fails) and retry the loser; the cost is that clients may see errors and must retry, and stronger levels reduce concurrency. A `CHECK (seats_left >= 0)` constraint is a useful safety net only together with the relative update `seats_left = seats_left - 1`; it does not catch two clients that both write the computed value 0.
rubric: Describes the interleaving where both read the same value and both write, and names it as a lost update.
rubric: Correctly states which standard isolation levels allow it and which prevent it, and mentions that a transaction may be aborted and retried.
rubric: Gives two valid fixes (an atomic conditional UPDATE, a relative update protected by a CHECK constraint, or stronger isolation with retry) with a cost of each.
hint: Write the two transactions' operations in the order they could run, and look at what each one read before it wrote.
hint: A fix can make the read-modify-write a single statement so the database does it atomically.
