@article
SQL says *what* you want. The **query processor** decides *how* to get it. A query goes through these stages:

1. **Parsing** checks syntax and resolves names against the catalog.
2. **Rewriting** turns the query into a **logical plan**, a tree of relational-algebra operators (week 2), and applies rules such as flattening views.
3. **Optimization** chooses a **physical plan**: for each logical operator an algorithm (index scan or table scan; which join algorithm) and an order of operations.
4. **Execution** runs the physical plan.

You can inspect the chosen plan with `EXPLAIN` (PostgreSQL and MySQL) or `EXPLAIN QUERY PLAN` (SQLite).

### The iterator model

Most engines run a plan with the **iterator** (Volcano) model. Every operator offers `open()`, `next()` and `close()`, and `next()` returns one row at a time by calling `next()` on its children. A root `LIMIT 1` only pulls the rows it needs, and a selection passes rows through without storing them (**pipelining**). Operators such as sorting and the build side of a hash join are **blocking**: they must consume all input first. Python generators mimic this pull-based style exactly.

### Join algorithms and their I/O cost

Let $M$ and $N$ be the page counts of tables $R$ (outer) and $S$ (inner), and $B$ the number of buffer pages. Cost counts page I/Os and ignores the cost of writing the final result.

- **Page nested-loop join**: for each page of $R$, scan all of $S$: $M + M \cdot N$.
- **Block nested-loop join**: load $B - 2$ pages of $R$ at a time (one page for reading $S$, one for output), scan $S$ once per block: $M + \lceil M / (B - 2) \rceil \cdot N$. Putting the *smaller* table outside usually helps.
- **Index nested-loop join**: for each row of $R$ look up matches in an index on $S$: $M + |R| \cdot c$, where $c$ is the cost of one index probe. Good when $R$ is small and $S$ is indexed.
- **Sort-merge join**: sort both inputs on the join key (external merge sort), then merge them in one pass: about sort cost $+ M + N$. The output is sorted on the join key, and the sort step is free when an input is already sorted (for example from a B+ tree).
- **Hash join**: build a hash table on the smaller input and probe it with the other. If the build side fits in memory the cost is $M + N$. Otherwise **Grace hash join** partitions both inputs with a hash function, writing the partitions out, then joins matching partitions: about $3(M + N)$ I/Os (read and write both inputs once, then read the partitions once).

Hash join requires an equality condition and sort-merge is designed for equijoins; nested loops handle any join condition.

### Optimization

**Heuristic rules** are always safe: push selections down (filter before joining, since a join on fewer rows is cheaper), push projections down, and avoid Cartesian products. A **cost-based optimizer** estimates the cost of alternatives from **statistics** stored in the catalog (row counts, number of distinct values, histograms) and picks the cheapest.

The **selectivity** of a predicate is the fraction of rows it keeps. For `A = c` under a uniform assumption it is $1 / V(A)$, where $V(A)$ is the number of distinct values of $A$. With 1000 rows and 50 distinct values, an equality predicate is expected to keep $1000 / 50 = 20$ rows. For an equijoin of $R$ and $S$ on $A$ the usual estimate of the output size is

$$\frac{|R| \cdot |S|}{\max(V(R, A),\, V(S, A))}.$$

These estimates assume uniform, independent values, so they can be far off for skewed or correlated data; stale statistics are a common cause of bad plans. For several tables the optimizer also chooses the **join order**. The number of orders grows factorially, so systems use dynamic programming over subsets, restrict to **left-deep** trees, or fall back to heuristics for large queries.

### Choosing indexes for a workload

List the workload's queries with their frequency, then ask for each: which predicate is selective, which columns does it filter, join on and sort by, and could one index serve several queries? Rules of thumb: index primary and foreign keys used in joins; index columns of selective equality and range predicates; make a composite index with equality columns first, then the range or ordering column; consider a covering index for a hot query; skip low-selectivity columns (a boolean flag); and weigh each index against the write cost it adds. Verify with the plan: the index should actually appear in `EXPLAIN`.

@example
title: Cost of a block nested-loop join
problem: $R$ has $M = 100$ pages and $S$ has $N = 50$ pages; the buffer has $B = 12$ pages. Compare the cost with $R$ outer and with $S$ outer.
step: With $R$ outer: blocks of $B - 2 = 10$ pages give $\lceil 100 / 10 \rceil = 10$ scans of $S$. Cost $= 100 + 10 \cdot 50 = 600$.
step: With $S$ outer: $\lceil 50 / 10 \rceil = 5$ scans of $R$. Cost $= 50 + 5 \cdot 100 = 550$.
step: The smaller table outside is cheaper, by 50 I/Os here.
answer: 600 I/Os with R outer, 550 with S outer.

@example
title: Estimating a join size
problem: $R$ has 1000 rows and $V(R, A) = 100$; $S$ has 500 rows and $V(S, A) = 50$. Estimate $|R \bowtie_A S|$.
step: Use $|R||S| / \max(V(R, A), V(S, A))$.
step: Numerator: $1000 \cdot 500 = 500{,}000$. Denominator: $\max(100, 50) = 100$.
step: Estimate: $500{,}000 / 100 = 5000$ rows.
answer: About 5000 rows.

@mistakes
- Joining first and filtering later; selections should be pushed below joins so the join sees fewer rows.
- Using the page count of the wrong table as the outer loop in the cost formula, or forgetting to reserve buffer pages for the inner scan and output.
- Trusting a cost estimate when statistics are stale or the data is skewed; check the actual plan and row counts.
- Adding indexes without measuring: an index the optimizer does not use is pure write overhead.

model:
```python
def hash_join(r, s, r_key, s_key):
    table = {}
    for y in s:
        if y[s_key] is not None:
            table.setdefault(y[s_key], []).append(y)
    out = []
    for x in r:
        if x[r_key] is None:
            continue
        for y in table.get(x[r_key], []):
            out.append({**x, **y})
    return out
```
hint: Build phase: group the rows of `s` in a dictionary mapping key to list of rows.
hint: Probe phase: for each row of `r`, look up its key in the dictionary, skipping `None`.
solution: Build `table[key] -> [rows of s]` skipping `None` keys, then probe it with each row of `r`. This costs $O(|R| + |S| + \text{output})$ expected time, compared with $O(|R| \cdot |S|)$ for nested loops.

@quiz code
prompt: Write `merge_join_count(a, b)`. `a` and `b` are lists of integers, each sorted in ascending order and possibly containing duplicates. Return the number of pairs `(i, j)` with `a[i] == b[j]`, using a single merge-style pass with two pointers (not a nested loop over all pairs, and not `Counter`). For a value occurring `p` times in `a` and `q` times in `b`, it contributes `p * q`.
starter:
```python
def merge_join_count(a, b):
    pass
```
tests:
```python
assert merge_join_count([1, 2, 2, 3], [2, 2, 3, 4]) == 5
assert merge_join_count([], [1, 2]) == 0
assert merge_join_count([1, 1, 1], [1]) == 3
assert merge_join_count([1, 3, 5], [2, 4, 6]) == 0
assert merge_join_count([2, 2], [2, 2, 2]) == 6
```
model:
```python
def merge_join_count(a, b):
    i = j = total = 0
    while i < len(a) and j < len(b):
        if a[i] < b[j]:
            i += 1
        elif a[i] > b[j]:
            j += 1
        else:
            value = a[i]
            p = 0
            while i < len(a) and a[i] == value:
                i += 1
                p += 1
            q = 0
            while j < len(b) and b[j] == value:
                j += 1
                q += 1
            total += p * q
    return total
```
hint: Advance the pointer that points at the smaller value.
hint: When the values are equal, count the run of that value in each list and add the product of the run lengths.
solution: Two pointers walk both sorted lists. A smaller value cannot match anything later, so it is skipped. On equality, count both runs of the value, add `p * q`, and move past both runs. The pass costs $O(|a| + |b|)$, which is why sorted inputs make merge join cheap.
