@article
Six months from now someone will look at your system and ask "why on earth did they do it this way?" That someone is often you. Code shows *what* the system does; it cannot show the options you rejected, the constraint that forced your hand or the assumption that has since expired. **Architecture decision records (ADRs)** are the cheapest effective answer: short documents, one per significant decision, kept with the code.

### What an ADR is

An ADR captures **one decision**, in a few paragraphs, with its reasoning. A widely used short template has these sections (the original format has title, status, context, decision and consequences; many teams add alternatives):

- **Title**: a short noun phrase with a number: `0007. Use PostgreSQL for order storage`.
- **Status**: `Proposed`, `Accepted`, `Deprecated` or `Superseded by 0012`.
- **Context**: the forces at play: requirements, constraints, the team, the deadline. State facts and name the trade-offs honestly.
- **Decision**: what you will do, in active voice: "We will use..."
- **Alternatives considered**: the options you rejected and why. This is the part future readers value most.
- **Consequences**: what becomes easier, what becomes harder, new risks, follow-up work. Include the negatives.

Keep each to one page. If you need ten, you are writing a design document; link to it.

### What deserves an ADR

Write one when a decision is **hard to reverse, expensive to get wrong or likely to be questioned**: the database or message broker, the service boundaries, an authentication approach, a major framework, a data format, the API style, a rule such as "services own their data". Do not write one for a variable name or a library you can swap in an afternoon. A useful test: "if a new engineer joined and reversed this without knowing the reason, would it hurt?"

### Life cycle: ADRs are append-only

An accepted ADR is a historical record, not a living page. If circumstances change, **do not edit the old decision**; write a new ADR that supersedes it, and update the old one's status to `Superseded by 0012`. The history of reasoning stays intact, so you can see why the first choice made sense then. Number records sequentially, store them in the repository (`docs/adr/0007-use-postgresql-for-orders.md`), and review them in pull requests like code, so the team debates the decision before it is merged, and the review is the record of agreement.

### Writing a good ADR: an example

*Context:* "Order confirmation emails block the checkout request for up to 8 seconds, and the mail provider fails about 1 percent of the time. We have 6 engineers and run one deployable." *Decision:* "We will publish an `OrderPlaced` event through a transactional outbox and send email from a worker." *Alternatives:* "Send email in the request (rejected: latency and failure coupling); a separate email microservice (rejected: operational cost for our team size)." *Consequences:* "Checkout no longer waits on email; emails may arrive seconds late; we must make the worker idempotent and monitor the outbox backlog."

Notice the numbers, the rejected options and the downsides. A record that says only "We chose X because it is best" teaches nothing.

### Documenting architecture at several levels: C4

The **C4 model** describes a system at four zoom levels, so each diagram has one audience and one message:

1. **Context**: your system as one box, with the users and external systems around it.
2. **Container**: the separately running pieces (web app, API, database, queue, worker) and how they communicate.
3. **Component**: the major parts inside one container (services, repositories, adapters).
4. **Code**: classes and functions; usually generated, rarely drawn by hand.

Label every arrow with what flows and how ("places order, JSON over HTTPS"). A diagram with unlabeled lines and no legend causes arguments.

### Documentation that survives

- Keep docs **next to the code** (docs-as-code): in the repository, in Markdown, changed in the same pull request as the behavior they describe.
- Write a **README** that answers: what is this, how do I run it and test it, where do things live, who owns it.
- Write **runbooks** for operations: what the alert means, how to check, how to fix, who to call.
- Prefer a few trustworthy documents over many stale ones. Date them, name an owner and delete what is wrong.
- Where possible, **enforce architecture in tests** (an architecture "fitness function"): a test that fails if the domain package imports the web framework keeps the diagram true.

### Habits

Decide in writing, ask for review early, link ADRs from code comments and pull requests ("see ADR 0007"), and when a decision turns out wrong, supersede it without blame. The goal is not paperwork. It is that the next person can disagree with you *knowing the reasons*.

@example
title: Writing a decision record
problem: Your team must choose how sessions are stored for a web app that will run on 3 servers behind a load balancer. Write the key parts of the ADR.
step: Title and status: `0004. Store sessions in Redis`, status `Proposed` until the review is finished.
step: Context with facts: three app servers; in-memory sessions would log users out when a request hits a different server; sticky sessions would unbalance load and lose sessions on deploy; sessions need to expire after 30 minutes idle.
step: Decision: "We will store sessions in Redis with a 30-minute sliding expiry, keyed by an unguessable session id in an HTTP-only cookie."
step: Alternatives: sticky sessions (rejected: uneven load, lost on deploy); database table (rejected: extra load on the primary database for every request); signed cookie sessions (rejected: cannot revoke a session, size limit).
step: Consequences: servers are stateless and can be replaced freely; Redis becomes a critical dependency we must monitor and back up; a brief outage logs users out; one more component for new engineers to learn.
answer: An ADR with title, status, factual context, a decision in active voice, three rejected alternatives and honest consequences.

@example
title: Superseding a decision
problem: ADR 0004 says sessions are stored in Redis. A year later the team moves to token-based authentication. How do you record it?
step: Do not edit the text of ADR 0004: it was correct for the situation then, and its reasoning is useful history.
step: Write `0015. Use short-lived access tokens instead of server-side sessions`, with the new context: mobile clients, third-party integrations and the Redis outage that logged everyone out.
step: In ADR 0015 write `Status: Accepted` and in its context say "This supersedes ADR 0004."
step: Change only the status line of ADR 0004 to `Superseded by 0015`.
step: A reader following either record can reconstruct the whole story: why Redis made sense, and why it stopped.
answer: Add ADR 0015 and mark ADR 0004 as superseded; leave 0004's reasoning untouched.

@mistakes
- Writing ADRs after the fact with only the winner and no rejected alternatives, so the record cannot help anyone challenge or revisit it.
- Editing an old ADR to match what the system does now. The history is lost; supersede instead.
- Recording every small choice, until nobody reads the folder. Keep records for significant, hard-to-reverse decisions.
- Drawing one giant diagram for every audience, with unlabeled arrows and no legend. Use levels and label the relationships.

model:
```python
import re

def parse_adr(text):
    lines = text.splitlines()
    match = re.match(r"#\s*(\d+)\.\s*(.+)", lines[0])
    number = int(match.group(1))
    title = match.group(2).strip()
    status = None
    for line in lines[1:]:
        if line.startswith("Status:"):
            status = line[len("Status:"):].strip()
            break
    return {"number": number, "title": title, "status": status}
```
hint: A regular expression with two groups can split the first line into number and title.
hint: Loop over the remaining lines and stop at the first one that starts with `Status:`.
solution: The first line yields the number and title (`\d+` then a literal period, then the rest of the line); a scan finds the status. Because only the first `. ` after the number splits, a title containing a period survives intact.

solution: ADR 0001. Use PostgreSQL for application data. Status: Accepted. Context: expense reports, line items, approvals and an audit trail are relational and need transactions (an approval and its audit entry must succeed or fail together). About 400 users and a few thousand reports a month, so scale is not a concern. Reporting by finance needs ad hoc queries and joins. The team knows SQL; nobody has operated a document database. Decision: We will use PostgreSQL, accessed through a repository port so storage can be swapped in tests. Alternatives: a document database (rejected: weaker multi-record transactions, reports would need extra tooling, no team experience); spreadsheets as database (rejected: no transactions or constraints, concurrent edits corrupt data, no audit guarantee). Consequences: strong integrity and easy reporting; we must manage schema migrations with the expand and contract method; we need backups and monitoring; scaling writes far beyond this size would need new work, which we accept. ADR 0002. Deploy as one container on a managed platform. Status: Accepted. Context: one deployable (a modular monolith), 400 users, business hours traffic, a 5-person team with no dedicated operations engineer, and a requirement of 99.5 percent availability. Decision: We will build one container image and run two instances of it on a managed container platform, with a managed PostgreSQL service. Alternatives: Kubernetes (rejected: operational cost and learning curve far exceed the need at this size); one virtual machine (rejected: manual patching, a single point of failure and slow, risky deployments). Consequences: deploys are a single command and rollbacks are easy; we depend on the platform vendor and its pricing; we give up fine control of networking; if we later split services, we will write a new decision record superseding this one.
rubric: Each record has a numbered title, status, context with concrete facts from the scenario, a decision stated in active voice, and consequences.
rubric: Each record lists at least two rejected alternatives with specific reasons tied to the team and scale, not generic claims.
rubric: Consequences include honest negatives or new obligations (for example vendor dependence, operations work or scaling limits), and the two decisions are consistent with each other.
