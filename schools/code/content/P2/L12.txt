@article
Nearly every system you will work on is a **legacy system**: it makes money, it was written under constraints nobody remembers and it has no tests. Greenfield design is rare. Most architecture work is *evolution*: moving a live system, step by step, toward a better shape without breaking it. This final lesson gives you the tools.

### Why not rewrite?

"Let's rewrite it from scratch" is tempting and usually fails. The old system contains years of hidden rules (the strange discount for one customer exists because of a contract); the rewrite takes longer than planned; the old system keeps changing meanwhile; and the cutover is a single high-risk event. The reliable alternative is **incremental change**: every step small, tested, deployed and reversible.

### Step 1: get it under test

Before you change code you do not understand, pin down what it does now. A **characterization test** records the current behavior, correct or not, as an assertion: call the function with real inputs and assert whatever it returns today. These tests do not claim the behavior is right. They tell you when you have *changed* it. To make code testable, find a **seam**: a place where you can alter behavior without editing the code under test, such as a parameter, an injected collaborator or a function you can replace. Introduce seams by the smallest safe edits (extract a function, pass a dependency in instead of constructing it inside) and then add tests.

### Step 2: strangle, do not rewrite

The **strangler fig pattern** puts a thin routing layer in front of the old system and moves capabilities to a new implementation one slice at a time. Requests for migrated slices go to the new code; everything else still goes to the legacy code. Over time the new system "strangles" the old one, which is finally switched off.

```python
class Router:
    def __init__(self, legacy, new):
        self._legacy, self._new = legacy, new
        self._migrated = []

    def migrate(self, prefix):
        self._migrated.append(prefix)

    def handle(self, path):
        for prefix in self._migrated:
            if path.startswith(prefix):
                return self._new(path)
        return self._legacy(path)
```

Rolling back a slice is removing its prefix. The same shape works inside a codebase as **branch by abstraction**: put an interface in front of the old implementation, add a new implementation behind the same interface, switch callers over gradually, then delete the old one. An **anti-corruption layer** is an adapter (week 5) that translates between the legacy model and your clean domain model, so legacy quirks do not leak into new code.

### Step 3: migrate data with expand and contract

Changing a database schema while the application keeps running needs the **expand and contract** (parallel change) method, because old and new code versions run at the same time during a deploy. Suppose `name` must become `first_name` and `last_name`:

1. **Expand**: add the new columns (nullable). Deploy code that **writes both** old and new and **reads** the new value with a fallback to the old.
2. **Migrate**: backfill existing rows in small batches, safely re-runnable (idempotent).
3. **Contract**: when every reader uses the new columns and the backfill is complete, deploy code that stops writing and reading the old one; later drop the old column.

Each step is deployable and reversible on its own. Never rename a column in one deploy: the running old code would break at once.

### Step 4: release changes safely

A **feature flag** lets you deploy code switched off, then enable it for a growing slice of users. Use a deterministic hash of the user id, so each user gets a consistent experience and raising the percentage only adds users. A **parallel run** (shadow mode) sends real traffic to both implementations, returns the old answer and logs any difference, which builds confidence before cutover. Always know your **rollback**: flipping a flag or reverting a route must be faster than fixing forward. Remove flags after rollout; old flags are their own debt.

### Managing technical debt

Technical debt is a trade-off, not a sin: you borrowed speed and pay interest in slower changes. Make it visible (a list with the cost of each item), pay down what blocks upcoming work first, and follow the **boy scout rule**: leave code a bit better than you found it, in small separate commits. Use architecture tests (week 11) so migrated parts do not slide back. Record each major decision as an ADR, including the decision to *keep* an ugly module because replacing it is not worth it.

### Putting it together

A realistic plan: write characterization tests around the legacy billing calculation; insert an interface; build the new implementation behind a flag; shadow-run it for two weeks and fix the differences; roll out to 5, 25, 100 percent with monitoring and a rollback; then delete the old code and the flag.

@example
title: Expand and contract in three states
problem: Rows have a `name` field. You are splitting it into `first` and `last`. Trace this reader through the three phases and say what it returns.

```python
def read_first(row):
    if "first" in row:
        return row["first"]
    return row["name"].split()[0]
```
step: **Before the migration** the row is `{"name": "Ada Lovelace"}`. There is no `first`, so the fallback splits the name and returns `"Ada"`.
step: **Expand and backfill** the row becomes `{"name": "Ada Lovelace", "first": "Ada", "last": "Lovelace"}`. The reader now finds `first` and returns `"Ada"`, with no change visible to callers.
step: **Contract**: once nothing reads `name`, the old field is removed, leaving `{"first": "Ada", "last": "Lovelace"}`; the reader still returns `"Ada"`.
step: The reader works in all three states, so old and new application versions can run side by side during each deploy, and any step can be reverted.
answer: `"Ada"` in all three phases.

@example
title: Strangling one route
problem: A legacy app serves `/invoices/...` and `/reports/...`. You rebuilt invoices. Show how requests are routed during migration and how to roll back.
step: Put a router in front of both systems, with the new invoice code and the legacy app behind it.
step: Initially nothing is migrated, so both `/invoices/9` and `/reports/3` go to the legacy handler.
step: Call `migrate("/invoices")`. Now `/invoices/9` goes to the new handler; `/reports/3` still goes to legacy.
step: If the new invoices misbehave in production, remove the prefix (or flip a flag) and traffic returns to legacy immediately, with no deploy of the old code needed.
step: Repeat for `/reports`, and when no prefix is routed to legacy, retire it.
answer: Migrated prefixes route to the new code and everything else to legacy; rollback is removing the prefix.

@mistakes
- Starting a refactor before there are tests around the behavior, so no one can tell whether a change broke something.
- Renaming or dropping a column in a single deploy, which breaks the old code that is still running during the rollout.
- Leaving feature flags and "temporary" dual paths in the code for years until nobody knows which one is live.
- Treating a characterization test as a statement that the behavior is correct. It only records what happens today.

@practice code
prompt: Write a class `Router(legacy, new)` where `legacy` and `new` are functions that take a path and return a string. `migrate(prefix)` marks a path prefix as migrated, and `unmigrate(prefix)` removes it. `handle(path)` calls `new(path)` if the path starts with any migrated prefix, and `legacy(path)` otherwise, and returns the result.
starter:
```python
class Router:
    pass
```
tests:
```python
router = Router(lambda p: "legacy:" + p, lambda p: "new:" + p)
assert router.handle("/invoices/9") == "legacy:/invoices/9"
router.migrate("/invoices")
assert router.handle("/invoices/9") == "new:/invoices/9"
assert router.handle("/reports/3") == "legacy:/reports/3"
router.migrate("/reports/")
assert router.handle("/reports/3") == "new:/reports/3"
router.unmigrate("/invoices")
assert router.handle("/invoices/9") == "legacy:/invoices/9"
router.unmigrate("/never-added")
assert router.handle("/reports/3") == "new:/reports/3"
```
model:
```python
class Router:
    def __init__(self, legacy, new):
        self._legacy = legacy
        self._new = new
        self._migrated = set()

    def migrate(self, prefix):
        self._migrated.add(prefix)

    def unmigrate(self, prefix):
        self._migrated.discard(prefix)

    def handle(self, path):
        for prefix in self._migrated:
            if path.startswith(prefix):
                return self._new(path)
        return self._legacy(path)
```
hint: Keep the migrated prefixes in a collection and test each with `startswith`.
hint: `set.discard` removes an item without an error if it is missing.
solution: The router is the strangler: migrated prefixes go to the new code and everything else stays on the legacy path. `unmigrate` is the instant rollback, and `discard` makes it safe to call for a prefix that was never added.

This makes the decision deterministic per user and flag, and raising `percent` only adds users. Use `hashlib`.

tests:
```python
assert all(rollout("new-billing", u, 0) is False for u in range(50))
assert all(rollout("new-billing", u, 100) is True for u in range(50))
assert rollout("new-billing", 42, 50) == rollout("new-billing", 42, 50)
on30 = [u for u in range(200) if rollout("new-billing", u, 30)]
on60 = [u for u in range(200) if rollout("new-billing", u, 60)]

assert 20 < len(on30) < 110
assert 60 < len(on60) < 180
```
model:
```python
import hashlib

def rollout(flag, user_id, percent):
    digest = hashlib.sha256(f"{flag}:{user_id}".encode()).hexdigest()
    return int(digest[:8], 16) % 100 < percent
```
hint: Hash the string `flag:user_id`, take the first 8 hex digits as a number, and reduce it modulo 100.
solution: A stable hash puts each user in a fixed bucket from 0 to 99; the feature is on when the bucket is below the percentage. Because buckets do not change, raising the percentage from 30 to 60 only adds users and nobody flips back and forth.

@quiz code
prompt: Write `migrate_rows(rows, drop_old=False)` for the name split. Each row is a dict. For every row that has a `"name"` key and no `"first"` key, add `"first"` (the text before the first space) and `"last"` (everything after it, or `""` if the name is a single word). Rows that already have `"first"` stay as they are. If `drop_old` is true, remove `"name"` from migrated rows. Return a new list of new dicts and leave the input unchanged. Running the function twice must give the same result as running it once.
starter:
```python
def migrate_rows(rows, drop_old=False):
    pass
```
tests:
```python
rows = [{"id": 1, "name": "Ada Lovelace"}, {"id": 2, "name": "Plato"}]
out = migrate_rows(rows)
assert out[0] == {"id": 1, "name": "Ada Lovelace", "first": "Ada", "last": "Lovelace"}
assert out[1] == {"id": 2, "name": "Plato", "first": "Plato", "last": ""}
assert rows == [{"id": 1, "name": "Ada Lovelace"}, {"id": 2, "name": "Plato"}]
assert migrate_rows(out) == out
final = migrate_rows(rows, drop_old=True)
assert final[0] == {"id": 1, "first": "Ada", "last": "Lovelace"}
done = [{"id": 3, "first": "Bo", "last": "Li"}]
assert migrate_rows(done) == done
assert migrate_rows([{"id": 4, "name": "Mary Ann Smith"}])[0]["last"] == "Ann Smith"
assert migrate_rows([]) == []
```
model:
```python
def migrate_rows(rows, drop_old=False):
    result = []
    for row in rows:
        new = dict(row)
        if "name" in new and "first" not in new:
            first, _, last = new["name"].partition(" ")
            new["first"] = first
            new["last"] = last
            if drop_old:
                del new["name"]
        result.append(new)
    return result
```
hint: Copy each row, and use `str.partition(" ")` to split at the first space only.
solution: The backfill is idempotent because rows that already have `first` are skipped, so it is safe to re-run in batches. Copying each row keeps the input unchanged, and `partition` splits at the first space, giving an empty `last` for single names.
