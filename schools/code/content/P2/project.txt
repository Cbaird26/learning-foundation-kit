material: **Specification: the Maple Street Tool Library.** A neighborhood tool library lends tools to registered members. Staff register members and add tools to the catalog; members borrow and return tools; the library sends a notification when a tool is borrowed, returned late or becomes available again.

Rules:

1. A member may have at most 3 tools on loan at the same time.
2. A tool can be on loan to only one member at a time.
3. A loan lasts 14 days from the day the tool is borrowed. Returning after the due date makes the loan late.
4. A member with any late, unreturned tool cannot borrow until they return it.
5. A member may reserve a tool that is on loan; when it is returned, the first member in the queue is notified, and the tool is held for that member for 2 days.
6. Notifications must not be sent twice for the same event, even if the system retries after a failure.

Use cases to implement: register a member, add a tool, borrow, return, reserve, list a member's loans. The interface must be usable from the command line now and from a web interface later, and the data must be movable from a file to a database later.

@review
This course is about making software easy to change. Here is the thread, week by week.

**Weeks 1 and 2: complexity, coupling, cohesion, information hiding.** Complexity shows up as change amplification, cognitive load and unknown unknowns. Coupling runs from data (best) through stamp, control and global to content (worst). Cohesion means a module has one purpose. Hide the decisions most likely to change behind small interfaces; return copies, not internals; tell objects what to do instead of asking for their data.

**Weeks 3 and 4: SOLID and composition.** Single responsibility (one reason to change), open/closed (extend by adding code), Liskov substitution (subtypes honor the parent's contract), interface segregation (small role interfaces), dependency inversion (depend on abstractions, inject collaborators). Prefer has-a to is-a: compose behavior from small parts, keep inheritance for true, stable is-a relationships and designed-for-extension parents.

**Weeks 5 and 6: patterns.** Factory, builder, adapter, decorator, facade; strategy, observer, command, state, template method. A pattern is a named answer to a named force; if you cannot name the force, skip the pattern.

**Weeks 7 and 8: domain and architecture.** Ubiquitous language; entities (identity) versus value objects (immutable, equal by value); aggregates enforce invariants; the model holds behavior. Layers: presentation, application, domain, infrastructure. Hexagonal architecture: dependencies point inward, ports are owned by the core, adapters implement them, one composition root wires everything.

**Weeks 9 and 10: APIs and distribution.** Resources as nouns, correct methods and status codes, idempotency keys, pagination, problem-details errors, additive changes, versioning and sunset. Events versus commands, at-least-once delivery with idempotent consumers, the transactional outbox, sagas with compensation, and the honest costs of microservices (start with a modular monolith).

**Weeks 11 and 12: decisions and evolution.** ADRs: one decision each, with context, alternatives and consequences, superseded rather than edited. C4 levels for diagrams. Evolve systems with characterization tests, seams, the strangler pattern, expand and contract migrations, feature flags and parallel runs.

**Self-check list**
- Can I name the coupling and cohesion problems in a snippet and fix each?
- Can I explain each SOLID principle with a smell and a fix?
- Can I turn a hierarchy into composition?
- Can I choose a pattern by naming the force?
- Can I separate entities, value objects and aggregates, and place invariants?
- Can I draw the layers and arrows with the domain depending on nothing?
- Can I design endpoints, errors, pagination and versioning for a service?
- Can I explain why consumers must be idempotent?
- Can I write an ADR with real alternatives?
- Can I plan a migration with tests, a strangler route and a rollback?

**Common errors**
- Treating principles as laws and adding abstractions for cases that never come.
- Hiding fields instead of hiding decisions, and returning internal lists.
- Putting rules in services or handlers and leaving the domain anemic.
- Letting the domain import a framework or database library.
- Using `200` for errors, or unbounded lists, or renaming fields in place.
- Assuming exactly-once delivery.
- Editing old ADRs, or writing ADRs with no rejected alternatives.
- Starting a migration without characterization tests, or renaming a column in one deploy.

@exam code
prompt: Write the application service for a tool library. Define exceptions `ToolUnavailable` and `LimitReached` (both subclasses of `Exception`) and a class `LendingService(repo, publish)`. The repository port has `borrower_of(tool_id)` (a member id or `None`), `loans_of(member_id)` (a list of tool ids) and `save_loan(member_id, tool_id)`. `borrow(member_id, tool_id)` must raise `ToolUnavailable` if the tool is on loan, and `LimitReached` if the member already has 2 tools on loan (if both apply, raise `ToolUnavailable`); otherwise it saves the loan and calls `publish` with the dict `{"type": "ToolBorrowed", "member_id": member_id, "tool_id": tool_id}`. Nothing is saved or published when it raises.

tests:
```python
class FakeRepo:
    def __init__(self):
        self.loans = {}

    def borrower_of(self, tool_id):
        return self.loans.get(tool_id)

    def loans_of(self, member_id):
        return [t for t, m in self.loans.items() if m == member_id]

    def save_loan(self, member_id, tool_id):
        self.loans[tool_id] = member_id

repo = FakeRepo()
events = []
service = LendingService(repo, events.append)
service.borrow("ana", "drill")
assert repo.loans == {"drill": "ana"}
assert events == [{"type": "ToolBorrowed", "member_id": "ana", "tool_id": "drill"}]
assert raises(ToolUnavailable, service.borrow, "bo", "drill")
service.borrow("ana", "saw")
assert raises(LimitReached, service.borrow, "ana", "ladder")
assert raises(ToolUnavailable, service.borrow, "ana", "drill")
assert "ladder" not in repo.loans
assert len(events) == 2
service.borrow("bo", "ladder")
assert repo.loans["ladder"] == "bo"
assert len(events) == 3
```
model:
```python
class ToolUnavailable(Exception):
    pass

class LimitReached(Exception):
    pass

class LendingService:
    def __init__(self, repo, publish):
        self._repo = repo
        self._publish = publish

    def borrow(self, member_id, tool_id):
        if self._repo.borrower_of(tool_id) is not None:
            raise ToolUnavailable(tool_id)
        if len(self._repo.loans_of(member_id)) >= 2:
            raise LimitReached(member_id)
        self._repo.save_loan(member_id, tool_id)
        self._publish({
            "type": "ToolBorrowed",
            "member_id": member_id,
            "tool_id": tool_id,
        })
```
hint: Check both rules before changing anything, so a rejected request leaves no trace.
solution: The service depends on a repository port and a publish function that are injected, so the tests use fakes. Both checks come first; only then is the loan saved and the event published, so a failed borrow changes nothing. Exceptions give callers (CLI or web adapter) distinct errors to translate, such as a 409.

class Bus:
    def __init__(self):
        self.handlers = []

    def subscribe(self, f):
        self.handlers.append(f)

    def publish(self, event):
        for f in self.handlers:

seen = set()
log = []

def handler(event):

@exam self
prompt: A teammate opens a pull request with this handler for a hotel booking service. Write a design review: identify at least five distinct problems, naming the concept from the course for each (coupling, cohesion, SOLID, layers, API design, errors, resilience); then describe the redesign: the layers and ports you would introduce, the response codes and error format, and how you would roll the change out safely in a live system.

```python
@app.route("/book", methods=["GET"])
def book():
    room = db.query("SELECT * FROM rooms WHERE id=" + request.args["id"])
    if room["status"] == "free":
        db.execute("UPDATE rooms SET status='busy' WHERE id=" + request.args["id"])
        smtp.send(room["owner_email"], "Booked!")
        STATS["bookings"] += 1
        return {"ok": True}
    return {"ok": False, "error": "busy"}
```
hint: Go through the layers from the database call up to the response, then through the course topics: coupling, domain rules, ports, API semantics, failure handling.
solution: Problems: (1) API design: `GET` changes state, so crawlers, prefetchers and caches can book rooms; it should be `POST /bookings`. (2) Errors and status codes: failure returns `200`-style `{"ok": False}` and the success body is not a resource; use `201` with `Location`, `409` when the room is taken and `422` for bad input, with a problem-details body. (3) Mixed responsibilities (low cohesion, single responsibility): one function parses HTTP, queries SQL, applies the booking rule, sends email and updates statistics. (4) Layering and dependency inversion: the handler talks to `db` and `smtp` directly, so the rule cannot be tested without them; the domain rule should live in a `Room` or `Booking` aggregate and the service should depend on a repository port and a notifier port, with adapters for SQL and SMTP. (5) Global coupling: `STATS` is shared mutable state; publish a `RoomBooked` event and let a subscriber update statistics. (6) Race condition: reading the status and then updating it is not atomic, so two requests can both book the room; enforce the invariant in the aggregate and the database (a conditional update or a unique constraint) inside one transaction, handling the conflict as `409`. (7) Security and robustness: string concatenation in SQL is injection-prone (use parameters), and the email call inside the request blocks it and can fail; use an outbox event and an idempotent worker, with retries and an idempotency key for the booking request. Redesign: driving adapter (route) calls `BookingService.book(room_id, guest_id)`; the service loads the `Room` through `RoomRepository`, calls `room.book(...)` (raising `RoomUnavailable`), saves, and records `RoomBooked` in an outbox; a worker sends the email and the statistics consumer updates counts. Rollout: write characterization tests of the current behavior, put the new service behind the route with a feature flag at a small percentage, compare results in a shadow run, keep the old route during a deprecation period, and roll back by turning the flag off.
