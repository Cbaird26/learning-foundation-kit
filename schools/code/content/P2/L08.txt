@article
You can have a perfect domain model and still end up with a codebase nobody can change, if SQL, HTTP handlers and business rules are mixed in the same functions. Architecture is the plan for **where code lives and who may depend on whom**. This week you learn the two most useful plans: layers and ports and adapters.

### The layered architecture

The classic **layered architecture** splits an application horizontally:

1. **Presentation** (or delivery): HTTP handlers, CLI commands, UI. Translates between the outside world and the application.
2. **Application** (service layer): use cases such as "place an order". Orchestrates: loads aggregates, calls the domain, saves, publishes events. Holds no business rules itself.
3. **Domain**: entities, value objects, aggregates and domain services. The rules.
4. **Infrastructure**: databases, message brokers, email, file systems.

In the *strict* classic version each layer depends on the one below, so the domain depends on the database layer. This has a cost: your most important code, the rules, cannot be tested or understood without the database.

### The dependency rule and hexagonal architecture

**Hexagonal architecture** (also called **ports and adapters**; onion and clean architecture are close relatives) reverses this. The **dependency rule**: source-code dependencies point **inward**, toward the domain. The domain imports nothing from the application layer, web framework or database library.

- A **port** is an interface the application *needs* or *offers*, defined in application or domain terms. Example: a `TaskRepository` with `add(task)`, `get(task_id)` and `all()`.
- An **adapter** is a concrete implementation that connects a port to a technology. `SqlTaskRepository` and `InMemoryTaskRepository` both implement the port.
- **Driving** (primary) adapters call the application: a Flask route, a CLI command, a test. **Driven** (secondary) adapters are called by the application: databases, email, payment gateways.

This is Dependency Inversion (week 3) used at the scale of the whole system: the service depends on the `TaskRepository` abstraction, and the SQL adapter depends on that abstraction too.

```python
class InMemoryTaskRepository:
    def __init__(self):
        self._tasks = {}

    def add(self, task):
        self._tasks[task.id] = task

    def get(self, task_id):
        return self._tasks.get(task_id)
```

```python
class TaskService:
    def __init__(self, repo):
        self._repo = repo

    def complete(self, task_id):
        task = self._repo.get(task_id)
        if task is None:
            raise LookupError(task_id)
        task.done = True
```

`TaskService` never mentions SQL. In production it receives `SqlTaskRepository(connection)`; in a unit test it receives `InMemoryTaskRepository()`, which is fast and needs no setup.

### The composition root

Somewhere the pieces must be assembled: construct the adapters, inject them into the services, hand the services to the delivery layer. Do it in **one place near the program's entry point**, the **composition root** (`main.py`, a `bootstrap()` function). Everything else receives its dependencies. The swap from SQLite to Postgres, or from a web UI to a command line, is a change to that one place plus a new adapter.

### Where does each thing go?

- Business rule ("no overlapping bookings"): domain.
- "Load the room, book it, save it, send the confirmation": application service.
- "Parse the JSON body, call the service, return a 201": driving adapter.
- "Run this SQL": driven adapter, behind a port.
- Transactions: usually started and committed by the service layer, using a unit of work, so use cases succeed or fail as a whole.

### Trade-offs

Ports and adapters buy testability and replaceability, and they cost extra classes and indirection. A script of 100 lines does not need them. A service that will live for years, talks to a database and an external API, and has real rules does. Do not build a port for something that will never be swapped *and* is easy to test as it is. A good compromise for a new system is: keep the domain pure, put storage behind a repository port, and keep the rest simple until a need appears.

### Testing strategy this enables

Domain tests: plain objects, no setup. Service tests: in-memory adapters, fast, covering use-case flow. Adapter tests (**integration tests**): a handful that prove the SQL adapter really works against a real database. Few end-to-end tests through the delivery layer. This is the shape of the **test pyramid**, and it only works if the layers are separable.

@example
title: Swapping storage through a port
problem: `TaskService` works with `InMemoryTaskRepository`. Show that a different adapter, such as one that logs each call, can be used without changing `TaskService`.
step: The port is informal: an object with `get(task_id)` and `add(task)`. `TaskService` calls only those.
step: Write a second adapter that wraps another repository and records calls:

```python
class LoggingRepository:
    def __init__(self, inner):
        self._inner = inner
        self.calls = []

    def get(self, task_id):
        self.calls.append(("get", task_id))
        return self._inner.get(task_id)

    def add(self, task):
        self.calls.append(("add", task.id))
        self._inner.add(task)
```
step: Compose at the entry point: `TaskService(LoggingRepository(InMemoryTaskRepository()))`.
step: `TaskService` is unchanged and untested for the new adapter, because it only relies on the port. The same trick lets you move from memory to SQL.
answer: Inject a different adapter that implements the same port; no change to the service.

@example
title: Drawing the layers for a to-do app
problem: A to-do app has a web page and a command-line tool, stores tasks in SQLite, and has the rule "a completed task cannot be completed again". Show the layers and where each piece lives.
step: Domain: `Task` (entity) with `complete()`, which raises an error if already done. Pure Python, no imports from outside.
step: Application: `TaskService` with `create(title)` and `complete(task_id)`; it depends on the port `TaskRepository`.
step: Driven adapters: `SqliteTaskRepository` (production) and `InMemoryTaskRepository` (tests), both implementing the port.
step: Driving adapters: a web route and a CLI command; each parses input, calls the `TaskService` and formats the result. Neither contains the rule.
step: Composition root: `main.py` builds the repository and service, and passes the service to whichever interface starts.
step: Arrows: web and CLI point to the service; the service points to the domain and the port; the SQLite and in-memory adapters point to the port. Nothing in the domain points outward.
answer: Delivery adapters then service then domain, with infrastructure adapters implementing a port owned by the application.

@mistakes
- Letting the domain import the ORM or web framework "just for one decorator". The dependency rule is broken and the domain is no longer testable alone.
- Putting business rules in route handlers or SQL queries, where they get duplicated across the web and CLI.
- Creating a port and adapter for every class, including ones that will never be swapped, then drowning in boilerplate.
- Treating an in-memory fake as proof the real adapter works. You still need integration tests against the real database.

@practice code
prompt: Write `InMemoryTaskRepository`, an adapter for a task repository port. `add(task)` stores a task by its `id` attribute and raises `ValueError` if that id already exists. `get(task_id)` returns the task or `None`. `all()` returns a list of all tasks sorted by id.
starter:
```python
class InMemoryTaskRepository:
    pass
```
tests:
```python
class T:
    def __init__(self, id, title):
        self.id = id
        self.title = title

repo = InMemoryTaskRepository()
assert repo.all() == []
repo.add(T(2, "b"))
repo.add(T(1, "a"))
assert [t.title for t in repo.all()] == ["a", "b"]
assert repo.get(2).title == "b"
assert repo.get(9) is None
assert raises(ValueError, repo.add, T(1, "dup"))
assert len(repo.all()) == 2
```
model:
```python
class InMemoryTaskRepository:
    def __init__(self):
        self._tasks = {}

    def add(self, task):
        if task.id in self._tasks:
            raise ValueError(f"duplicate id {task.id}")
        self._tasks[task.id] = task

    def get(self, task_id):
        return self._tasks.get(task_id)

    def all(self):
        return [self._tasks[i] for i in sorted(self._tasks)]
```
hint: A private dictionary keyed by id is enough.
solution: The adapter stores tasks in a private dict keyed by id, rejects duplicates in `add`, returns `None` from `get` for a missing id, and sorts keys in `all`. Because it follows the same interface as a SQL repository would, services can be tested with it.

model:
```python
class Task:
    def __init__(self, id, title):
        self.id = id
        self.title = title
        self.done = False

class TaskService:
    def __init__(self, repo):
        self._repo = repo
        self._next_id = 1

    def create(self, title):
        task = Task(self._next_id, title)
        self._next_id += 1
        self._repo.add(task)
        return task.id

    def complete(self, task_id):
        task = self._repo.get(task_id)
        if task is None:
            raise LookupError(task_id)
        task.done = True
```
hint: The service receives the repository in its constructor and never creates one.
solution: `create` builds a `Task`, hands it to the port and returns its id; `complete` loads through the port, changes the entity and reports a missing task with `LookupError`. The service has no idea whether the repository is SQL or a dictionary.

@quiz code
prompt: Write a driven adapter `JsonNoteRepository(path)` that stores notes (strings) as a JSON list in the text file at `path`. Assume the file already exists and contains a JSON list. `add(note)` appends a note and writes the list back; `all()` returns the list of notes read from the file. Two repository objects with the same path must see the same notes. Use `open()` and the `json` module.
starter:
```python
import json

class JsonNoteRepository:
    pass
```
tests:
```python
write_file("notes.json", "[]")
a = JsonNoteRepository("notes.json")
assert a.all() == []
a.add("buy milk")
a.add("call Ana")
assert a.all() == ["buy milk", "call Ana"]
b = JsonNoteRepository("notes.json")
assert b.all() == ["buy milk", "call Ana"]
b.add("third")
assert a.all() == ["buy milk", "call Ana", "third"]
import json as _json
assert _json.loads(read_file("notes.json")) == ["buy milk", "call Ana", "third"]
```
model:
```python
import json

class JsonNoteRepository:
    def __init__(self, path):
        self._path = path

    def all(self):
        with open(self._path, "r") as f:
            return json.load(f)

    def add(self, note):
        notes = self.all()
        notes.append(note)
        with open(self._path, "w") as f:
            json.dump(notes, f)
```
hint: Read the file fresh in `all()` and rewrite it in `add`; keep only the path in the object.
solution: The file is the shared state, so `all()` always reads it and `add()` reads, appends and writes back. A service written against `add` and `all` works with this adapter or an in-memory one.
