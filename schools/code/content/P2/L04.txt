@article
Inheritance is the first reuse tool most of us learn, and in a first job it is the one that most often gets teams into trouble. This week's principle is a default, not a ban: **prefer composition over inheritance**. Build an object by giving it other objects that do parts of its job (**has-a**), instead of making it a specialization of a parent class (**is-a**).

### What goes wrong with inheritance

**Tight coupling.** A subclass depends on the parent's implementation, not only its interface. The parent cannot change how its methods call each other without possibly breaking every subclass. This is the **fragile base class problem**:

```python
class Bag:
    def __init__(self):
        self.items = []

    def add(self, x):
        self.items.append(x)

    def add_all(self, xs):
        for x in xs:
            self.add(x)

class CountingBag(Bag):
    def __init__(self):
        super().__init__()
        self.count = 0

    def add(self, x):
        self.count += 1
        super().add(x)

    def add_all(self, xs):
        self.count += len(xs)
        super().add_all(xs)
```

Adding three items with `add_all` counts six, because `Bag.add_all` calls `self.add`, which the subclass overrides. The author of `CountingBag` had to know a private fact about `Bag`. If `Bag` is later changed to not call `add`, the count suddenly becomes right, and nothing flagged it.

**Combinatorial explosion.** Imagine `Employee` with subclasses `Manager` and `Contractor`. Product asks for a contractor who manages: `ManagerContractor`. Then "paid weekly" and "paid monthly" variants. Each independent trait multiplies the number of classes. Traits that vary independently do not belong on one hierarchy axis.

**Inflexibility.** The parent is chosen when the code is written. You cannot change an object's behavior at runtime, for example switching a game character from walking to flying.

**Substitutability traps.** Subclasses inherit every public method, including ones that make no sense (last week's `Stack(list)`).

### Composition and delegation

With composition, the object holds a reference to a collaborator and **delegates** to it:

```python
class CountingBag:
    def __init__(self):
        self._bag = Bag()
        self.count = 0

    def add(self, x):
        self.count += 1
        self._bag.add(x)

    def add_all(self, xs):
        for x in xs:
            self.add(x)
```

Now `CountingBag` controls exactly which calls happen and exposes only the methods it chooses. The count is correct no matter how `Bag` is written internally.

### Strategies: composing behavior

Pull out the part that varies and inject it. A character that can walk or fly:

```python
class Walk:
    def move(self, pos):
        return pos + 1

class Fly:
    def move(self, pos):
        return pos + 3

class Creature:
    def __init__(self, mover):
        self.mover = mover
        self.pos = 0

    def step(self):
        self.pos = self.mover.move(self.pos)
```

New behaviors are new small classes (or even plain functions), they are testable alone, and `Creature` can swap movers at runtime with `creature.mover = Fly()`. For the employee example, make pay and role independent parts: `Employee(name, role, pay_policy)` instead of a class for every combination. This is the **Strategy** pattern, which you will meet formally in week 6.

### So when is inheritance right?

Inheritance is appropriate when:

- the relationship is a true, stable **is-a** and the subclass honors the parent's whole contract (Liskov), and
- the parent is **designed for extension**: it documents which methods may be overridden, or it is an abstract base class whose only job is to define an interface and a template.

Typical good cases: implementing an abstract base class or `Protocol`; framework classes meant to be subclassed (`Exception` hierarchies, `unittest.TestCase`, an admin view class); and small, shallow hierarchies you control entirely. A second guideline: a mixin that adds one narrow capability is acceptable, but a deep chain of mixins that rely on each other's attributes is composition done badly.

### Refactoring a hierarchy: the recipe

1. List what varies independently (pay type, role, notification channel).
2. For each axis, define the smallest interface (one or two methods).
3. Create one small class per variant.
4. Give the main class those parts through its constructor.
5. Delete the subclasses and move their tests onto the parts.

@example
title: Fixing the double counting
problem: `CountingBag` (a subclass of `Bag`) reports `count == 6` after `add_all([1, 2, 3])`. Refactor so it reports 3, whatever `Bag` does inside.
step: Understand the cause. `Bag.add_all` calls `self.add`, which resolves to the subclass's override, so each item is counted by `add` and counted again by `add_all`.
step: Stop inheriting. `CountingBag` holds a `Bag` in a private attribute: `self._bag = Bag()`.
step: Make `add` count and delegate: `self.count += 1` then `self._bag.add(x)`.
step: Make `add_all` loop over its own `add`, so the counting happens in exactly one place:

```python
def add_all(self, xs):
    for x in xs:
        self.add(x)
```
step: After `add_all([1, 2, 3])`, `add` ran three times and `count` is 3. The behavior no longer depends on how `Bag` implements `add_all`.
answer: Use a private `Bag` and delegate; count only in `add`.

@example
title: Replacing a subclass explosion with parts
problem: You have `Employee`, `Manager`, `Contractor` and `ManagerContractor`, and each pay type needs its own variant. Redesign.
step: Identify the independent axes: the **role** (title, permissions) and the **pay policy** (how monthly pay is computed).
step: Give pay a tiny interface, `monthly(hours)`, with two implementations, `Salaried(amount)` and `Hourly(rate)`.
step: Give the employee both parts:

```python
class Employee:
    def __init__(self, name, role, pay):
        self.name = name
        self.role = role
        self._pay = pay

    def monthly_pay(self, hours):
        return self._pay.monthly(hours)
```
step: Now a "manager paid hourly" is `Employee("Ana", "manager", Hourly(40))`, with no new class. Adding a pay type adds one class; adding a role adds one string or object.
step: Replace the old four classes and their tests by tests of `Salaried`, `Hourly` and `Employee`.
answer: Compose `role` and `pay` into one `Employee`.

@mistakes
- Using inheritance only to reuse a few lines, then discovering you inherit methods that break your invariants. Delegate to a private helper instead.
- Making wrappers that expose every method of the inner object (or using `__getattr__` to forward everything), which recreates the inheritance coupling without the checks.
- Overriding a method and calling `super()` without knowing which other parent methods call it (the fragile base class problem).
- Banning inheritance outright. Abstract base classes, `Protocol` implementations and framework hooks are fine uses.

@quiz code
prompt: Write a class `Logger(formatter, sink)`. Its `log(message)` method calls `formatter(message)` to produce a line and passes the line to `sink(line)`. Both are plain callables passed to the constructor. `Logger` must not print or open files itself.
starter:
```python
class Logger:
    pass
```
tests:
```python
lines = []
log = Logger(lambda m: "[info] " + m, lines.append)
log.log("started")
log.log("done")
assert lines == ["[info] started", "[info] done"]
other = []
Logger(str.upper, other.append).log("quiet")
assert other == ["QUIET"]
assert len(lines) == 2
```
model:
```python
class Logger:
    def __init__(self, formatter, sink):
        self._formatter = formatter
        self._sink = sink

    def log(self, message):
        self._sink(self._formatter(message))
```
hint: Store both callables in the constructor and combine them in `log`.
solution: `Logger` is assembled from two parts, so a new format or destination needs no subclass. Compare the inheritance alternative, `JsonFileLogger`, `TextConsoleLogger` and so on, which multiplies classes for every pairing.
