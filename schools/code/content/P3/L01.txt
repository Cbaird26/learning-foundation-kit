@article
On your first week at a new job, a senior colleague pings you: "We need a service so support agents can attach files to tickets. Can you sketch a design?" Nothing in that sentence tells you whether it must handle ten files a day or ten million, whether files can be 50 KB or 5 GB, or whether losing a file is an annoyance or a legal problem. **System design is the discipline of turning an ambiguous request into a system whose behavior, cost and failure modes you can predict.** The first and most valuable step is not drawing; it is asking.

### A process you can repeat

Whether you are in a design review or a 45-minute interview, the same sequence works:

1. **Clarify requirements.** Who are the users? What must the system do? What must it never do?
2. **State constraints and estimate scale.** Traffic, data volume, latency, budget, team size, existing technology (next lesson).
3. **Sketch the API.** The two or three calls that matter, with inputs and outputs.
4. **Model the data.** What is stored, how it is keyed, how it is read.
5. **Draw a high-level design.** Clients, load balancer, services, stores, queues, caches.
6. **Deep-dive the hard parts.** Pick the one or two bottlenecks the numbers expose.
7. **Discuss trade-offs and failures.** What breaks first, how you would know, what you gave up.

Interviewers and design reviewers both grade the *reasoning*, so say your assumptions out loud and write them down.

### Functional requirements

A **functional requirement** says what the system does: "a user can upload a file to a ticket", "an agent can list a ticket's files". Write them as short verbs-and-nouns sentences, and keep the list small: three to six core features. Then write the **non-goals**: "no virus-scanning workflow in v1", "no editing files in place". A non-goal is a promise to your future self that a missing feature is a decision, not an oversight.

### Non-functional requirements

A **non-functional requirement** (NFR) describes how well the system does it: latency, throughput, availability, durability, consistency, security, cost. The classic failure is an unmeasurable NFR such as "must be fast" or "highly available". Make each one a number with a percentile or a time window: "p99 download start under 500 ms", "99.9% of requests succeed each calendar month", "an acknowledged upload is never lost (durability)". Different features may deserve different targets: a payment needs strong consistency; a "like" counter can lag.

### Availability as arithmetic

Availability is the fraction of requests (or time) that is successful. A **service-level objective (SLO)** is the target; the allowed failures form the **error budget**. Over a 30-day month (43,200 minutes):

| SLO | Allowed downtime per 30 days |
|---|---|
| 99% | 432 minutes |
| 99.9% | 43.2 minutes |
| 99.99% | 4.32 minutes |

Each extra nine typically costs much more (a common rule of thumb is about ten times) in redundancy, testing and on-call effort, so ask the business which nine it actually needs. A service that depends on three other services in series cannot be more available than their product: three 99.9% dependencies give about 99.7% at best.

### Constraints are requirements too

Constraints rarely appear in the request: "we run on one cloud region", "the team has four engineers", "data of EU users must stay in the EU", "the launch is in six weeks". They often decide the design more than any scaling number. A boring design that four engineers can operate beats an elegant one they cannot.

### Write it down

End the clarification phase with a half-page you can show: functional requirements, NFRs with numbers, non-goals, constraints and open questions. In a real review, circulate it before the design, because most disagreements are about requirements, not boxes.

@example
title: Clarifying a vague request
problem: Your lead says: "Design a leaderboard for our mobile game." Write the requirements you would confirm before designing anything.
step: Ask who uses it and how: "Players see their rank and the top 100 for the current week; a player's score can only go up during a week." That is the **functional** core: submit a score, get the top 100, get my rank.
step: Write the non-goals: "no friend-only boards in v1, no historical weeks beyond the last four". These cut scope in half.
step: Turn adjectives into numbers: "The top-100 page loads in under 200 ms at p99. A submitted score appears within 5 seconds (eventual consistency is fine). The service meets a 99.9% monthly availability SLO."
step: Record constraints: "The game has 2 million weekly players and runs in one region; the team is five engineers; launch in eight weeks."
step: Write open questions to settle with the product owner: "Are ties broken by earliest time? Do cheaters need to be removable after the fact?"
answer: Four short lists: functional requirements, NFRs with numbers, non-goals and constraints, plus open questions.

@example
title: From a nine count to minutes
problem: A product manager asks for "five nines". Your service must be up 99.999% of a 30-day month. How much downtime is that, and what should you say?
step: A 30-day month has $30 \times 24 \times 60 = 43{,}200$ minutes.
step: The allowed failure fraction is $1 - 0.99999 = 0.00001$.
step: Allowed downtime is $43{,}200 \times 0.00001 = 0.432$ minutes, about 26 seconds per month.
step: One slow deploy or one failed database failover can exceed that. A realistic reply: "Five nines means roughly 26 seconds a month, which needs multi-region active-active and mature automation. Which user journeys really need it? Maybe checkout does and the admin page does not."
answer: About 26 seconds per month; push back by asking which journeys need that target.

@mistakes
- Jumping to boxes and database brands before agreeing on requirements; the design then answers a question nobody asked.
- Writing NFRs as adjectives ("fast", "scalable") instead of numbers with a percentile or time window.
- Treating every feature as needing the same consistency and availability, which makes the design far more expensive than needed.
- Forgetting non-goals, so the scope silently grows during the review or interview.

@practice self
prompt: A teammate asks you to design a "paste service" where people share text snippets by link, like a simple code-sharing tool. Write the requirements section: 3 to 5 functional requirements, 4 non-functional requirements as measurable numbers (state any assumptions), 2 non-goals and 2 open questions.
hint: Start with the user journey: create, share a link, read. Then ask what could go wrong or scale up.
hint: For each non-functional requirement write a number and a time window or percentile.
solution: A model answer:

Functional requirements:
- A user can create a paste (text up to 1 MB, optional expiry) and receives a unique short link.
- Anyone with the link can read the paste.
- A paste expires and is deleted after its expiry time (default never).
- The owner can delete a paste.

Non-functional requirements (assumptions: 5 million new pastes per day, reads 10 times writes):
- Read latency: p99 under 200 ms for pastes up to 100 KB.
- Availability: reads succeed 99.9% of requests per 30 days; writes 99.5%.
- Durability: an acknowledged paste is not lost (replicated before acknowledging).
- Links are unguessable enough that pastes cannot be enumerated (at least 60 bits of entropy for unlisted pastes).

Non-goals: no accounts or editing in v1; no full-text search across pastes.

Open questions: Must expired data be erased within a fixed deadline for legal reasons? Is syntax highlighting server-side or client-side?
rubric: Functional requirements describe user-visible behavior and are not implementation details.
rubric: Every non-functional requirement contains a number plus a percentile, window or unit, and assumptions are stated.
rubric: At least two non-goals and two open questions appear and are specific to this service.
rubric: Durability or security of links is considered, not only latency.

@practice code
prompt: Write `allowed_downtime_minutes(slo_percent, days=30)` that returns the minutes of downtime an availability SLO allows over `days` days, as a float rounded to 2 decimal places. For example, `allowed_downtime_minutes(99.9)` is `43.2`.
starter:
```python
def allowed_downtime_minutes(slo_percent, days=30):
    pass
```
tests:
```python
assert allowed_downtime_minutes(99.9) == 43.2
assert allowed_downtime_minutes(99.99) == 4.32
assert allowed_downtime_minutes(99) == 432.0
assert allowed_downtime_minutes(99.9, days=7) == 10.08
assert allowed_downtime_minutes(100) == 0.0
```
model:
```python
def allowed_downtime_minutes(slo_percent, days=30):
    total_minutes = days * 24 * 60
    failure_fraction = (100 - slo_percent) / 100
    return round(total_minutes * failure_fraction, 2)
```
hint: Total minutes is days times 24 times 60. The failure fraction is 100 minus the SLO, divided by 100.
solution: Multiply the minutes in the window by the failure fraction and round. With 7 days, 10,080 minutes times 0.001 gives 10.08.

@quiz code
prompt: An API has an SLO of `slo_percent` percent of requests succeeding. Write `error_budget_remaining(slo_percent, total_requests, failed_requests)` that returns how many more requests may fail before the SLO is violated: the total allowed failures (rounded to the nearest whole request) minus `failed_requests`. The result may be negative when the budget is overspent. Example: SLO 99.9 over 1,000,000 requests allows 1000 failures.
starter:
```python
def error_budget_remaining(slo_percent, total_requests, failed_requests):
    pass
```
tests:
```python
assert error_budget_remaining(99.9, 1_000_000, 400) == 600
assert error_budget_remaining(99.0, 5000, 50) == 0
assert error_budget_remaining(99.9, 200_000, 350) == -150
assert error_budget_remaining(99.99, 100_000, 0) == 10
```
model:
```python
def error_budget_remaining(slo_percent, total_requests, failed_requests):
    allowed = round(total_requests * (100 - slo_percent) / 100)
    return allowed - failed_requests
```
hint: Allowed failures are total requests times the failure fraction.
solution: Compute allowed failures as `total_requests * (100 - slo_percent) / 100`, round, and subtract the failures so far. A negative result means the budget is overspent, which should trigger a freeze on risky releases.
