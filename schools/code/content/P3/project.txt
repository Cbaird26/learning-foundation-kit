## Week-by-week key ideas

- **Week 1, process and requirements.** Clarify first. Functional requirements say what; non-functional requirements say how well, as numbers. Write non-goals. Availability maps to downtime: 99.9 percent is 43.2 minutes per 30 days; the error budget is 1 minus the SLO.
- **Week 2, estimation.** Average QPS is per-day requests over 86,400; design for peak (2 to 3 times). Storage is items times size times retention times replicas. State every assumption, use units, add a sanity check. Latency order of magnitude: memory 100 ns, SSD 100 microseconds, data center round trip 0.5 ms, cross-ocean 100 to 150 ms.
- **Week 3, load balancing.** Stateless servers behind a layer 4 or layer 7 balancer; round robin, least connections, hashing. Health checks, draining, N+1 sizing, zone failure.
- **Week 4, caching.** Cache-aside, write-through, write-behind, write-around; TTL, explicit invalidation, LRU. Miss rate sets database load. Stampedes: coalescing, jitter, stale-while-revalidate.
- **Week 5, replication and sharding.** Leader-follower, sync versus async, lag and read-your-writes, failover and split brain. Range, hash and directory sharding; shard-key choice; consistent hashing; hot keys; resharding with logical shards.
- **Week 6, SQL versus NoSQL.** Choose from access patterns and consistency needs. Model from the queries; denormalize deliberately; index before you shard.
- **Week 7, queues and streams.** Decouple and level load; at-least-once delivery, acknowledgements, visibility timeouts, dead-letter queues, partition keys for ordering, backpressure, drain-time arithmetic, transactional outbox.
- **Week 8, consistency and idempotency.** CAP (choose C or A during a partition) and PACELC; quorums with R + W > N; idempotency keys; sagas; a job pipeline with leases, retries and idempotent stages.
- **Week 9, URL shortener and news feed.** Base-62 keys, 302 versus 301, cache sizing; fan-out on write, on read and hybrid, cursor pagination.
- **Week 10, chat and notifications.** WebSockets and gateways, per-conversation sequence numbers, client ids for duplicates, offline catch-up; notification pipeline with priorities, preferences, backoff with jitter.
- **Week 11, reliability.** Series and parallel availability, failure domains, timeouts, bounded retries, circuit breakers, bulkheads, token bucket, load shedding, degradation plans.
- **Week 12, observability.** Logs, metrics, traces; RED and USE; percentiles; SLIs, SLOs, burn rate, symptom-based alerts; runbooks, blameless postmortems, canary releases.

## Common errors

- Drawing boxes before agreeing on requirements and numbers.
- Forgetting peak versus average, replication, or bits versus bytes.
- Naming a technology without saying why it fits the access pattern.
- Assuming exactly-once delivery, independent failures, or that retries are free.
- Ignoring operations: no SLO, no alert, no runbook, no rollback.

@exam code
prompt: Implement a sliding-window rate limiter. `SlidingWindowLimiter(limit, window, clock)` allows at most `limit` requests in any window of `window` seconds, where `clock()` returns the current time in seconds. `allow()` returns `True` and records the request time if fewer than `limit` allowed requests have times strictly greater than `now - window`; otherwise it returns `False` and records nothing. Requests that were rejected do not count against the limit.
starter:
```python
class SlidingWindowLimiter:
    def __init__(self, limit, window, clock):
        pass

    def allow(self):
        pass
```
tests:
```python
now = [0]
limiter = SlidingWindowLimiter(3, 10, lambda: now[0])
assert [limiter.allow() for _ in range(4)] == [True, True, True, False]
now[0] = 5
assert limiter.allow() is False
now[0] = 10
assert [limiter.allow() for _ in range(4)] == [True, True, True, False]
now[0] = 19
assert limiter.allow() is False
now[0] = 20
assert limiter.allow() is True
```
model:
```python
from collections import deque


class SlidingWindowLimiter:
    def __init__(self, limit, window, clock):
        self.limit = limit
        self.window = window
        self.clock = clock
        self.times = deque()

    def allow(self):
        now = self.clock()
        while self.times and self.times[0] <= now - self.window:
            self.times.popleft()
        if len(self.times) < self.limit:
            self.times.append(now)
            return True
        return False
```
hint: Keep the times of allowed requests in a queue, oldest first.
hint: Before deciding, remove times that are at or before `now - window`; then compare the remaining count with the limit.
solution: A deque of accepted request times is the sliding window log. Expired entries (time at or before `now - window`) are dropped from the front, so each request is added and removed at most once, which makes the amortized cost constant. Unlike a fixed window it has no double-burst at boundaries, but it stores up to `limit` timestamps per client. At time 10 the three requests from time 0 are exactly 10 seconds old and have left the window.

answer: 288
check: 1_500_000/5*120*8/1e6
tol: 0.5
unit: Mbit/s
hint: First find updates per second, then bytes per second, then convert bytes to bits.
solution: Updates per second are $1{,}500{,}000 / 5 = 300{,}000$. Bytes per second are $300{,}000 \times 120 = 36{,}000{,}000$ (36 MB/s). Multiplying by 8 gives 288,000,000 bits per second, which is 288 Mbit/s. That is small for a data center, but 300,000 updates per second is a significant write rate for a store, so the latest location is kept in memory, not in a database.

@exam self
prompt: Design a ticket-sale system for a flash sale: 5,000 tickets go on sale at a fixed time, and 200,000 users click Buy within the first minute. Requirements: never sell more than 5,000 tickets, never charge a user without giving a ticket (or refunding), the site must stay up and responsive, and users must get a clear answer. Write the design: estimates (peak requests per second), the architecture (waiting room or queue, inventory control, payment flow), how you prevent overselling under concurrency, how retries and double clicks are handled, rate limiting and degradation, and the SLOs and alerts you would set for the sale.
hint: Estimate the request rate first, then decide what must be strongly consistent (inventory) and what can be eventual or cached (everything else).
hint: Think about how a user gets a hold on a ticket for a few minutes before paying.
solution: A model answer:

- Estimates: 200,000 users in 60 seconds is about 3,300 clicks per second on average, and with refreshes and retries (assume 5 requests per user) about 17,000 requests per second at the start. Only 5,000 can succeed, so more than 97 percent of users get "sold out" or a queue position: protect the system by making the rejection cheap.
- Architecture: static pages and the event description come from a CDN. A **waiting room** admits users to the purchase flow at a controlled rate (say 500 per second) using a queue of signed tokens, so the inventory service sees bounded load. A reservation service owns inventory; a payment service calls the payment provider; an order queue and workers handle confirmation emails.
- Overselling prevention: inventory is a single counter (or a set of numbered seats) in a strongly consistent store, decremented with an atomic conditional update ("decrement if remaining > 0"), so two concurrent buyers cannot both take the last ticket. The reservation is a **hold** with an expiry of 5 minutes: the ticket leaves the available pool at once and returns if payment does not complete in time.
- Payment flow: a small saga. Reserve (hold) then charge with an idempotency key then confirm the order. If the charge fails or times out the hold expires and the ticket is released; if the charge succeeded but confirmation failed, a reconciliation job completes the order or refunds, so a user is never charged without a ticket.
- Retries and double clicks: every purchase attempt carries a client-generated idempotency key; the reservation and the order are created under a unique constraint on that key, so a double click or a retried request returns the same hold or order. Per-user limits (for example 4 tickets) are enforced in the reservation transaction.
- Rate limiting and degradation: per-user and per-IP token buckets at the edge with 429 and a Retry-After header; bot detection before admission to the waiting room; if the inventory store slows down, the waiting room slows admission automatically (backpressure), and non-essential features (recommendations, account pages) are turned off by feature flags; the "sold out" answer is served from a cache after the count reaches zero.
- SLOs and alerts: purchase API availability 99.9 percent during the sale window with a page on a fast burn (14.4 times over 5 and 60 minutes); p99 reservation latency under 500 ms; zero oversells as an invariant checked by a reconciliation job that alerts immediately on any violation; alert on payment error rate and on hold expirations spiking, and a runbook for each.
rubric: The estimate converts the stated users and time into a request rate and recognizes that most requests cannot succeed.
rubric: Overselling is prevented with an atomic conditional update (or equivalent strongly consistent mechanism) on inventory, with a holding period that expires.
rubric: Idempotency keys, a saga or reconciliation for payment failures, and per-user limits are described so that no user is charged without a ticket.
rubric: Protects the system with a waiting room or queue, rate limiting and degradation, and gives SLOs and alerts that fit the event, including an invariant check for overselling.
