@article
Interviews are a skill that is separate from engineering, and like any skill it improves with deliberate practice. The good news is that the format is predictable. A senior engineer who has sat on a hundred hiring panels will tell you the same thing: the candidates who pass are rarely the ones who know the most tricks. They are the ones who stay calm, communicate clearly and finish a correct solution.

### The stages of a typical process

Processes vary, but most look like this:

| Stage | What happens | What is tested |
|---|---|---|
| Recruiter screen | 20 to 30 minute call | Motivation, level, logistics, salary range |
| Online assessment | Timed problems on a platform | Correctness under time pressure |
| Technical phone screen | One or two problems in a shared editor | Problem solving and clear communication |
| Final loop (virtual or on site) | Three to five rounds in one day | Coding, system design (mid-level and above), behavioral |
| Team match and offer | Conversations, then numbers | Fit, level, compensation |

Rules about tools differ between companies. Some forbid AI assistants or outside help in interviews, some permit them in specific rounds. Always follow the stated rules. Getting help that the interviewer does not know about is the fastest way to end an application, and you will be asked to explain your code anyway.

### What interviewers actually grade

Most rubrics score four things: **problem solving** (can you break the task down and find an approach?), **coding** (is the code correct, clean and idiomatic?), **verification** (do you test your own work?) and **communication** (can a teammate follow your thinking?). A silent correct solution often scores lower than a talkative, slightly flawed one, because the interviewer cannot see your reasoning.

### A method for every problem

Use the same seven steps every time. Under stress, a routine is what you fall back on.

1. **Clarify.** Ask about input size, value ranges, duplicates, empty input, and what to return when there is no answer.
2. **Examples.** Write one normal case and one edge case with the expected output.
3. **Brute force.** State the simplest correct approach and its cost, even if you will not code it.
4. **Optimize.** Look for the repeated work. Name the pattern: a hash map, two pointers, a stack, binary search.
5. **Code.** Write clean code while explaining each decision.
6. **Test.** Trace your examples by hand through the code. Look for off-by-one errors and empty input.
7. **Analyze.** State time and space complexity, and mention trade-offs.

Here is the method applied to a tiny problem: does a list contain a duplicate? The brute force compares every pair, which is $O(n^2)$ time and $O(1)$ space. The repeated work is the searching. A set answers "have I seen this?" in $O(1)$ average time:

```python
def has_duplicate(nums):
    seen = set()
    for n in nums:
        if n in seen:
            return True
        seen.add(n)
    return False
```

This is $O(n)$ average time and $O(n)$ space. You traded memory for speed, and saying that out loud is part of the answer.

### How to practice

- **Study by pattern, not by problem count.** Sixty problems solved with understanding beat three hundred skimmed. This course follows the standard patterns.
- **Keep a pattern log.** For each problem record the pattern, the key insight, the complexity and the mistake you made.
- **Time yourself.** A typical 45 minute round gives about 5 minutes to clarify, 10 to plan, 20 to code and 10 to test and discuss.
- **Space your review.** Redo a problem you struggled with after one day, one week and one month, without looking.
- **Practice out loud.** Explaining to a rubber duck, a friend or a recording exposes gaps that silent solving hides.
- **Run mock interviews** with a peer before the real thing.

The code in this course is Python and works on any version from 3.10 onward, including 3.14 and the newest 3.15. In an interview you can usually choose your language: pick the one you know best.

@example
title: Applying the method to a new problem
problem: The interviewer says: "Find the first number in a list that appears a second time." Walk through the method on the list `[3, 1, 4, 1, 5, 3]`.
step: **Clarify.** Can the list be empty? Yes. What if nothing repeats? Return `None`. "First" means the earliest position where a duplicate is detected while scanning left to right.
step: **Examples.** `[3, 1, 4, 1, 5, 3]` returns `1`: the second `1` at index 3 comes before the second `3` at index 5. `[2, 9]` returns `None`.
step: **Brute force.** For each index, look back through all earlier items. That is $O(n^2)$ time, $O(1)$ space.
step: **Optimize.** The look-back is repeated work. Keep a set of items already seen, so the look-back costs $O(1)$ on average.
step: **Code and trace.**

```python
def first_repeated(items):
    seen = set()
    for x in items:
        if x in seen:
            return x
        seen.add(x)
    return None
```

Tracing: `3`, `1`, `4` are added; the next `1` is already in `seen`, so we return `1` at once.
step: **Analyze.** One pass: $O(n)$ average time. The set holds up to $n$ items: $O(n)$ space.
answer: `1`, in $O(n)$ time and $O(n)$ space.

@example
title: Counting the cost of brute force
problem: A brute-force duplicate check compares every pair of items once. How many comparisons does it make for 1000 items, and why does that matter?
step: The number of pairs among $n$ items is $\binom{n}{2} = \frac{n(n-1)}{2}$.
step: For $n = 1000$ that is $\frac{1000 \cdot 999}{2} = 499{,}500$ comparisons.
step: Double the input to 2000 and the count becomes $1{,}999{,}000$, about four times larger. That is the signature of $O(n^2)$ growth.
step: The set approach does about 1000 lookups for 1000 items. When an interviewer says "can you do better?", this kind of reasoning is what they want to hear.
answer: 499,500 comparisons; quadratic growth is why the set version wins.

@mistakes
- Jumping straight to code without clarifying, then discovering a misunderstood requirement ten minutes in.
- Solving in silence. The interviewer cannot give hints, or credit, for thinking they cannot hear.
- Stopping at "it works" without tracing a test through the code or stating complexity.
- Grinding hundreds of problems without a log or review, so the same patterns are forgotten a month later.

@practice code
prompt: Write `is_anagram(a, b)` that returns `True` when the two strings contain exactly the same characters with the same counts (case-sensitive), and `False` otherwise. Aim for $O(n)$ time.
starter:
```python
def is_anagram(a, b):
    pass
```
tests:
```python
assert is_anagram("listen", "silent") is True
assert is_anagram("rat", "car") is False
assert is_anagram("", "") is True
assert is_anagram("aab", "abb") is False
assert is_anagram("a", "ab") is False
```
model:
```python
from collections import Counter


def is_anagram(a, b):
    return Counter(a) == Counter(b)
```
hint: Two strings are anagrams exactly when each character occurs the same number of times in both.
hint: `collections.Counter` builds a character-count dictionary in one pass.
solution: Pattern: frequency counting with a hash map. Build a `Counter` for each string and compare them; dictionaries compare equal when they have the same keys and counts. Time $O(n)$, space $O(k)$ where $k$ is the number of distinct characters. Sorting both strings also works but costs $O(n \log n)$.

@practice self
prompt: The interviewer says: "Given a string, return the index of the first character that appears exactly once, or -1 if none." Write what you would say and write down in your first five minutes: two clarifying questions, one example with its expected output, the brute-force approach with its complexity, and the optimized approach with its complexity.
hint: Think about what could be ambiguous in the statement, then how you would check every character without extra memory, and how to avoid rescanning.
hint: The optimized version needs two passes: one to count, one to find the first count of 1.
solution: Clarifying questions: Is the comparison case-sensitive? What characters can appear (ASCII or full Unicode), and how long can the string be? Return -1 for an empty string as well? Example: "swiss" returns 1, because `s` appears three times, `w` once; "aabb" returns -1. Brute force: for each index, scan the whole string to count occurrences of that character; the first index whose count is 1 wins. That is $O(n^2)$ time and $O(1)$ space. Optimized: make one pass to build a frequency dictionary of characters, then a second pass over the string returning the first index whose count is 1. That is $O(n)$ time and $O(k)$ space for $k$ distinct characters (at most the alphabet size). Then trace "swiss" and "aabb" through the code before declaring done.

rubric: Gives a concrete example with the correct expected output, including a no-answer case.
rubric: States the brute force as $O(n^2)$ time and the counting approach as $O(n)$ time with the space cost.
rubric: Describes two passes (count, then scan in original order) and why the second pass preserves "first".

@quiz code
prompt: Write `common_elements(a, b)` that returns a sorted list of the distinct values that appear in both lists `a` and `b`. Aim for $O(n + m)$ average time before sorting.
starter:
```python
def common_elements(a, b):
    pass
```
tests:
```python
assert common_elements([1, 2, 2, 3], [2, 2, 3, 4]) == [2, 3]
assert common_elements([], [1]) == []
assert common_elements([5], [5]) == [5]
assert common_elements([1, 2], [3, 4]) == []
assert common_elements([9, 8, 9], [8, 9, 9, 7]) == [8, 9]
```
model:
```python
def common_elements(a, b):
    return sorted(set(a) & set(b))
```
hint: Sets give membership in $O(1)$ on average and support intersection.
solution: Pattern: hash sets. Convert both lists to sets, intersect them and sort the result. Building the sets is $O(n + m)$ average, the intersection is at most $O(\min(n, m))$ average, and sorting $k$ results costs $O(k \log k)$. Space is $O(n + m)$.
