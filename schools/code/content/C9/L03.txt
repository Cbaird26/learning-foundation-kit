@article
The web is a client-server application. A browser (the client) requests **objects** (an HTML file, an image, a script) from a web server using the **Hypertext Transfer Protocol**, HTTP. Each object is named by a **URL** such as `https://www.example.com:443/shop/item?id=7#reviews`: a scheme (`https`), a host, an optional port (default 80 for `http`, 443 for `https`), a path, a query string and a fragment (the fragment is used by the browser and is never sent to the server).

### Messages

HTTP/1.1 messages are text. A request has a request line, header lines, a blank line, and an optional body; lines end with CRLF (`\r\n`):

```text
GET /index.html HTTP/1.1
Host: www.example.com
Accept: text/html

```

The response has a status line, headers, a blank line and the body:

```text
HTTP/1.1 200 OK
Content-Type: text/html
Content-Length: 1256

<html> ...
```

Common **methods** are `GET` (fetch), `HEAD` (headers only), `POST` (submit data), `PUT` (replace) and `DELETE`. `GET` and `HEAD` must be **safe** (no side effects). **Status codes** come in classes: 1xx informational, 2xx success (`200 OK`, `201 Created`), 3xx redirection (`301 Moved Permanently`, `304 Not Modified`), 4xx client error (`400 Bad Request`, `403 Forbidden`, `404 Not Found`) and 5xx server error (`500 Internal Server Error`, `503 Service Unavailable`). The `Host` header is required in HTTP/1.1 because one server address can host many sites.

### Statelessness and cookies

HTTP is **stateless**: the server keeps no memory of earlier requests. Sites that need state (a login session, a cart) use **cookies**. The server sends `Set-Cookie: session=abc123` in a response; the browser stores it and returns `Cookie: session=abc123` in later requests to that site. Cookies are also used for tracking, which is why browsers restrict third-party cookies.

### Caching and conditional GET

A cache (in the browser or a **proxy** or **CDN**) keeps copies of objects. A response may carry `Cache-Control: max-age=3600`, meaning the copy is fresh for an hour, and a **validator** such as `ETag: "v42"` or `Last-Modified`. When the copy is stale, the cache sends a **conditional GET** with `If-None-Match: "v42"` (or `If-Modified-Since`). If the object is unchanged, the server answers `304 Not Modified` with no body, saving the transfer; otherwise it sends `200` and the new object.

### Connections and page load time

HTTP runs over TCP. Opening a TCP connection costs one round-trip time (RTT) for the handshake, and each request-response then costs one more RTT plus the transmission time of the object. With **non-persistent** connections every object needs a new TCP connection: $2$ RTT per object. With **persistent** connections (the HTTP/1.1 default) the connection stays open and later objects cost 1 RTT each. With **pipelining** several requests are sent without waiting for earlier responses. Ignoring transmission times, a page with a base HTML file and $n$ embedded objects fetched one after another takes $2(1 + n)$ RTT non-persistent, $2 + n$ RTT persistent, and $3$ RTT persistent with all $n$ requests pipelined (when $n \ge 1$): 1 RTT to connect, 1 RTT for the base file, then 1 RTT for all the objects.

### HTTP/2 and HTTP/3

HTTP/2 (RFC 9113) keeps the same semantics but uses a binary framing layer and **multiplexes** many request-response streams on one TCP connection, with header compression. A lost TCP segment still stalls every stream behind it (head-of-line blocking). HTTP/3 (RFC 9114) runs over QUIC (RFC 9000), which is built on UDP, gives each stream independent loss recovery, and integrates the TLS 1.3 handshake into the transport handshake, so a new secure connection needs only 1 RTT.

@example
title: Page load times
problem: A page has one base HTML file and 8 embedded images. RTT is 50 ms; ignore transmission times. How long does the page take to load with non-persistent connections, with persistent connections, and with persistent connections plus pipelining?
step: Non-persistent: each of the 9 objects needs a TCP handshake (1 RTT) and a request-response (1 RTT), so $9 \times 2 \times 50 = 900$ ms.
step: Persistent without pipelining: one handshake, then one request-response per object: $(1 + 9) \times 50 = 500$ ms.
step: Persistent with pipelining: 1 RTT for the handshake, 1 RTT to fetch the base file (the browser cannot know the image names before it), then 1 RTT for all 8 image requests sent together: $3 \times 50 = 150$ ms.
answer: 900 ms, 500 ms and 150 ms

@example
title: A conditional GET
problem: A browser cached `/logo.png` with `ETag: "a1"`. Describe the exchange when the file has not changed and when it has changed to ETag `"b2"`.
step: The browser sends `GET /logo.png HTTP/1.1` with `Host: www.example.com` and `If-None-Match: "a1"`.
step: Unchanged: the server compares the validator, finds it equal, and replies `HTTP/1.1 304 Not Modified` with no body. The browser reuses its copy.
step: Changed: the validators differ, so the server replies `HTTP/1.1 200 OK` with `ETag: "b2"`, `Content-Length` and the new image in the body.
step: Either way one RTT is spent, but the 304 response is only a few hundred bytes, not the whole image.
answer: 304 with no body when unchanged; 200 with the new body and ETag "b2" when changed.

@mistakes
- Believing that HTTP keeps a session on the server by itself. Sessions are built on top of it with cookies or tokens.
- Treating a 304 response as an error. It means "your cached copy is still valid".
- Counting only one RTT per object for non-persistent HTTP and forgetting the TCP handshake.
- Forgetting that the browser must fetch the base HTML before it can request the embedded objects, so pipelining cannot start earlier.

tests:
```python
req = "GET /a/b?x=1 HTTP/1.1\r\nHost: example.com\r\nAccept: text/html\r\n\r\n"
assert parse_request(req) == (
    "GET", "/a/b?x=1", "HTTP/1.1",
    {"host": "example.com", "accept": "text/html"})
assert parse_request("GET / HTTP/1.1\r\nHost: localhost:8080\r\n\r\n")[3] == {
    "host": "localhost:8080"}
post = "POST /f HTTP/1.1\r\nContent-Length: 3\r\nX-Test:   hi  \r\n\r\nabc"
assert parse_request(post) == (
    "POST", "/f", "HTTP/1.1", {"content-length": "3", "x-test": "hi"})
assert parse_request("GET / HTTP/1.1\r\n\r\n") == ("GET", "/", "HTTP/1.1", {})
```
model:
```python
def parse_request(text):
    head = text.split("\r\n\r\n")[0]
    lines = head.split("\r\n")
    method, target, version = lines[0].split(" ")
    headers = {}
    for line in lines[1:]:
        name, _, value = line.partition(":")
        headers[name.strip().lower()] = value.strip()
    return method, target, version, headers
```
hint: The header section ends at the first blank line, that is, at the first `"\r\n\r\n"`.
hint: `str.partition(":")` splits at the first colon only, so `localhost:8080` survives.
solution: Cut the text at the first blank line, split what remains into lines, split the first line on spaces for the three request-line fields, and use `partition(":")` on each other line, lower-casing the name and stripping the value.

```python
assert parse_cookie_header("a=1; b=two") == {"a": "1", "b": "two"}
assert parse_cookie_header("session=abc==") == {"session": "abc=="}
```

model:
```python
def parse_cookie_header(value):
    cookies = {}
    for pair in value.split(";"):
        pair = pair.strip()
        if pair:
            name, _, val = pair.partition("=")
            cookies[name] = val
    return cookies
```
hint: Split on `;`, then strip each piece and skip empty ones.
hint: Use `partition("=")` so that a value that itself contains `=` is kept whole.
solution: Split on semicolons, strip spaces, skip empty pieces and partition each pair at its first equals sign, so `abc==` stays intact.
