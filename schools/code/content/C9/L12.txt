@article
A network gives an attacker places to listen, alter, forge and flood. The goals of defense are **confidentiality** (only the endpoints can read the data), **integrity** (changes are detected), **authentication** (you know who you are talking to) and **availability** (the service keeps working). Cryptography supplies the first three: **symmetric ciphers** (AES) encrypt fast with a shared key; **key exchange** (such as elliptic-curve Diffie-Hellman) lets two parties agree on a shared key over a public channel; **digital signatures** let a party prove it holds a private key; **hashes and MACs** detect modification. Modern designs combine encryption and integrity in **AEAD** ciphers (AES-GCM, ChaCha20-Poly1305).

### TLS 1.3

**Transport Layer Security** (TLS 1.3 is RFC 8446) runs above TCP and protects HTTP (HTTPS, port 443), mail and many other protocols. HTTP/3 uses the TLS 1.3 handshake inside QUIC. A full TLS 1.3 handshake takes **one round trip**:

1. **ClientHello**: the client lists its supported versions and cipher suites, the **server name** it wants (SNI), and a **key share**: the client's ephemeral public value for a key-exchange group such as X25519.
2. **ServerHello**: the server picks the parameters and sends its own key share. Both sides now compute the same shared secret and derive encryption keys from it; **everything after ServerHello is encrypted**.
3. The server sends its **Certificate** (a chain), **CertificateVerify** (a signature over the handshake transcript made with the private key matching the certificate, proving possession) and **Finished** (a MAC over the whole transcript, proving no one altered the handshake).
4. The client checks the certificate, verifies the signature and Finished, and sends its own **Finished**. Application data then flows, protected by an AEAD cipher with fresh keys and per-record sequence numbers, so records cannot be modified, replayed or reordered unnoticed.

Because the key exchange uses fresh ephemeral keys, TLS 1.3 provides **forward secrecy**: stealing the server's long-term private key later does not reveal past sessions. TLS 1.3 removed older weak features (RSA key transport, static Diffie-Hellman, compression, legacy ciphers). **Session resumption** lets a client reconnect quickly with a pre-shared key, and optional **0-RTT** data sends a request in the first flight, but it can be replayed by an attacker, so it is only safe for idempotent requests. TLS does not hide who talks to whom (IP addresses) or the sizes and timing of records; the SNI is visible unless the Encrypted Client Hello extension is used.

**Post-quantum cryptography.** A large quantum computer could break the elliptic-curve key exchanges and signatures in use today. NIST published FIPS 203 (ML-KEM, key encapsulation), FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA), both signature standards, in August 2024. Deployments already combine a classical and a post-quantum key exchange in **hybrid** form, to defend against attackers who record traffic now to decrypt it later.

### Certificates

A **certificate** (X.509) binds a public key to a name. A **certificate authority (CA)** signs it. The server sends a chain: its leaf certificate, signed by an intermediate CA, signed by a **root CA** whose certificate is already in the client's **trust store**. The client must check that each signature is valid, that every certificate is within its validity dates, that the chain ends at a trusted root, that the certificate has not been revoked, and that the **name in the certificate matches the host** it intended to reach (names are in the Subject Alternative Name field). A wildcard such as `*.example.com` matches exactly one label (`www.example.com`, not `example.com` and not `a.b.example.com`). If any check fails the browser must refuse the connection. **HSTS** tells browsers to use only HTTPS for a site, and **Certificate Transparency** logs make mis-issued certificates detectable.

### Firewalls

A **firewall** sits between a network and the outside and applies a policy. A **stateless packet filter** looks at each packet's header (protocol, addresses, ports) against an ordered list of rules; the **first matching rule** applies and a safe policy ends with **default deny**. A **stateful firewall** also tracks connections: it allows an inbound packet only if it belongs to a connection started from inside. An **application gateway** (proxy) understands the application protocol and can inspect content. **Intrusion detection and prevention systems** look for suspicious patterns. A firewall cannot protect against threats that arrive over allowed traffic or from inside.

### Attacks and defenses

- **Denial of service (DoS, DDoS):** exhaust bandwidth or server resources. In a **SYN flood** the attacker sends many SYNs and never completes the handshakes, filling the server's table of half-open connections; **SYN cookies** encode the state in the server's initial sequence number so no memory is used until the final ACK. Other defenses: rate limiting, anycast and scrubbing services.
- **Spoofing:** forging source addresses. **Ingress filtering** (BCP 38) at the edge drops packets whose source address does not belong to the network they come from.
- **ARP spoofing:** false ARP replies redirect local traffic; switches can validate ARP against known bindings (dynamic ARP inspection).
- **DNS cache poisoning:** forged DNS answers; defenses are random query IDs and source ports, and **DNSSEC** signatures.
- **BGP hijacks and leaks:** defended with route filtering and **RPKI** origin validation.
- **On-path eavesdropping and tampering:** defended by end-to-end encryption such as TLS.

@example
title: Timeline of an HTTPS request
problem: RTT is 50 ms. A client opens a TCP connection and runs a full TLS 1.3 handshake before sending an HTTP request. When can it send the request, and when does it receive the first response byte (ignore processing and transmission times)?
step: At time 0 the client sends SYN. The SYN-ACK returns at 50 ms. The client replies with ACK and ClientHello together.
step: The server receives ClientHello at 75 ms and answers with ServerHello, Certificate, CertificateVerify and Finished; these reach the client at 100 ms.
step: The client verifies, then sends Finished together with the HTTP request at 100 ms (2 RTT after the start).
step: The server receives the request at 125 ms and its response arrives at 150 ms.
answer: The request is sent at 100 ms and the response starts to arrive at 150 ms.

@example
title: First-match firewall rules
problem: Rules in order: (1) allow tcp port 443, (2) allow tcp port 80, (3) deny everything. How is a tcp packet to port 443, a tcp packet to port 22 and a udp packet to port 53 treated?
step: tcp port 443 matches rule 1: allowed. Evaluation stops.
step: tcp port 22 matches neither rule 1 nor rule 2, so it reaches rule 3: denied.
step: udp port 53 also falls through to rule 3: denied (so a DNS server behind this firewall would need an extra allow rule before the last one).
answer: allowed; denied; denied

@mistakes
- Saying that TLS hides everything. IP addresses, packet sizes and timing remain visible, and the endpoints still see the data.
- Thinking a valid signature chain is enough. The certificate's name must also match the host you meant to reach.
- Putting a broad allow rule before a specific deny rule. Rules are evaluated in order and the first match wins.
- Believing that a firewall makes a network secure by itself. It controls traffic between networks but cannot stop attacks over permitted traffic.

model:
```python
def hostname_matches(pattern, host):
    p = pattern.lower().split(".")
    h = host.lower().split(".")
    if len(p) != len(h):
        return False
    if p[0] == "*":
        return p[1:] == h[1:]
    return p == h
```
hint: Split both names into labels and compare the number of labels first.

model:
```python
class StatefulFirewall:
    def __init__(self):
        self.connections = set()

    def outgoing(self, src, sport, dst, dport):
        self.connections.add((src, sport, dst, dport))

    def incoming(self, src, sport, dst, dport):
        return (dst, dport, src, sport) in self.connections

    def close(self, src, sport, dst, dport):
        self.connections.discard((src, sport, dst, dport))
```
hint: Store each outgoing connection as a four-tuple in a set.
hint: An arriving packet is a reply when its tuple with source and destination swapped is in the set.
solution: Keep a set of `(src, sport, dst, dport)` four-tuples for connections started inside. A packet arriving as `(src, sport, dst, dport)` is allowed only if `(dst, dport, src, sport)` is in the set. `discard` makes `close` safe for unknown connections.

@practice self
prompt: Explain how TLS 1.3 protects an HTTPS connection to `https://www.example.com`. Walk through the handshake in order, and say how the connection achieves confidentiality, integrity and authentication of the server, what a certificate chain and hostname check contribute, why forward secrecy holds, and one thing TLS does not protect.
solution: The client sends ClientHello with its cipher suites, the server name and an ephemeral key share (for example X25519). The server answers with ServerHello and its own key share; both sides compute the same shared secret and derive keys, and every later handshake message is encrypted. The server sends its certificate chain, a CertificateVerify signature over the handshake transcript made with its private key, and Finished, a MAC over the transcript. The client checks that the chain leads to a trusted root CA, that the certificates are valid and unrevoked, and that the name www.example.com appears in the certificate; the signature proves the server holds the private key matching the certificate, so the client knows it is talking to the real server and not an on-path attacker. The Finished messages prove both sides saw the same handshake, so downgrades and tampering are detected. Application data then travels in records protected by an AEAD cipher (such as AES-GCM or ChaCha20-Poly1305): encryption gives confidentiality, the authentication tag and per-record sequence numbers give integrity and protect against reordering and replay. Because the keys come from ephemeral key shares that are discarded, stealing the server's long-term key later does not decrypt recorded sessions: forward secrecy. TLS does not hide the IP addresses, the timing and sizes of records, or (without Encrypted Client Hello) the server name, and it does not protect against a compromised endpoint or a denial of service.

rubric: Explains authentication of the server through the certificate chain, hostname check and the CertificateVerify signature.
rubric: Explains confidentiality and integrity of the data through an AEAD cipher, and forward secrecy through ephemeral keys.

Return the action of the first rule that matches the packet, or `"deny"` if no rule matches.
starter:
```python
def first_match(rules, packet):
    pass
```
tests:
```python
web = [("allow", "tcp", 443), ("allow", "tcp", 80), ("deny", "*", "*")]
assert first_match(web, ("tcp", 443)) == "allow"
assert first_match(web, ("udp", 53)) == "deny"
assert first_match([("deny", "tcp", 23), ("allow", "*", "*")], ("tcp", 23)) == "deny"
assert first_match([("deny", "tcp", 23), ("allow", "*", "*")], ("tcp", 22)) == "allow"
assert first_match([("allow", "*", "*"), ("deny", "tcp", 23)], ("tcp", 23)) == "allow"
assert first_match([], ("tcp", 80)) == "deny"
assert first_match([("allow", "udp", "*")], ("udp", 5353)) == "allow"
```
model:
```python
def first_match(rules, packet):
    protocol, port = packet
    for action, rule_protocol, rule_port in rules:
        if rule_protocol in ("*", protocol) and rule_port in ("*", port):
            return action
    return "deny"
```
hint: Go through the rules in order and stop at the first one that matches both fields.
hint: A field matches when the rule has `"*"` or the same value as the packet.
solution: Iterate over the rules in order; return the action of the first rule whose protocol and port each equal the packet's value or are `"*"`; if the loop ends, return the default `"deny"`.
