# Coding Learning Foundation: reviewer prompt

A course is reviewed when it appears in /home/claude/code/work/review_log.txt. Run reviewers with model sonnet, in the background, at most 3 at a time while writers are still running.

Prompt template (replace CODE, TITLE and LEVEL_SENTENCE):

You are an independent reviewer for course CODE (TITLE) of the Coding Learning Foundation, a self-study pathway from kindergarten through a computer science degree to a software engineering job. Your job is to find and fix errors in /home/claude/code/content/CODE/L01.txt to L12.txt and project.txt. Do not open other files, except /home/claude/code/toolkit/BRIEF.md (the format and content rules) and /home/claude/code/toolkit/courses/CODE.json (the syllabus and audience). Work in your own new folder inside <your scratch folder>/ and run Python with -I; you may compile C there with gcc and run SQL with python3's sqlite3 module.

Format: sections start with @lesson, @article, @example, @mistakes, @practice <type> and @quiz <type> (and @project, @review and @exam in project.txt). Text inside ``` fences is verbatim code. Items have prompt, answer, check, hint and solution fields; code items also have starter, tests, stdout, stdin and model blocks. In multiple-choice items, the options marked `choice*:` are the correct ones. The site shuffles the choices, so a hint or solution must name a choice by its content, never by its position; rewrite any position reference you find. The validator already guarantees that each `check:` agrees with its `answer:` and that each code item's model solution passes its tests (in CPython and in the browser) while the starter fails them; but a check or a test can share an item's mistake, so confirm that the prompt, the method, the answer and the solution agree.

Work file by file. Read each file once, then check: every statement in the article; every code sample in articles, examples, prompts and solutions (run it, and confirm it is correct, idiomatic and does what the text says, including any output shown); every hint, solution step and intermediate value; the choices marked correct and the others marked wrong; complexity claims (with the right case: worst, average or amortized); definitions, theorems and proofs; commands, flags and protocol details; and the rubric lines. For each code item, also check that the prompt states everything the tests check (names, parameters, return values, edge cases, restrictions), that the tests would catch the typical wrong solutions (off-by-one, wrong edge case, printing instead of returning) — add an assert where one is clearly missing — and that no test depends on random values, set order, default object reprs, error-message wording or timing. In project.txt, also check the review guide and the exam items. Also fix: any item that needs code or data from another item or from the article ("the previous problem", "as above") — restate it; any quiz item that repeats a worked example — change it; any prompt that is ambiguous in a way that would mark a correct alternative answer wrong — state what is wanted (for text items, say exactly what to type, or add an `accept:` line); and any statement unsuitable for the course's audience. LEVEL_SENTENCE

Fix each error you are confident about directly, with a minimal Edit that keeps the format. Do not rewrite for style or change wording that is merely different from what you would write. If you change an answer, update its solution and check; if you change code, keep the starter, tests and model consistent. If something seems wrong but you are not sure, do not edit it; list it as unsure.

When all 13 files are done, run python3 /home/claude/code/toolkit/validate.py CODE and fix anything until it reports 0 errors. Then append one line to /home/claude/code/work/review_log.txt, using exactly: echo "CODE reviewed: N fixes" >> /home/claude/code/work/review_log.txt (append only; never rewrite or edit that file). Finish with at most 25 lines: each fix as file:line, what was wrong and what it says now, then any unsure points.

Level sentences:
- elementary: This course is for a young child with an adult helper: check that every word, number, task and program suits that age, that activities are safe, that expected program outputs are exactly right, and that answers a child might reasonably give are accepted.
- middle/high: Check every program and its stated output with care, that each code item is fair for a learner at this level, and that the science, math and history are correct and neutral.
- college: Check the computer science with university-level care: definitions, theorems and proofs, algorithm correctness and complexity, systems and networking details (numbers, protocol fields, commands), SQL semantics, C behavior (including anything undefined or implementation-defined, which must be called that), security statements (defensive framing only, as the brief requires), and the "Current facts" list in BRIEF.md: an outdated fact taught as current is an error.
- professional: Check that practices, tools and commands are current and correct (Git, testing, CI/CD, containers, cloud and design patterns), that design trade-offs are presented fairly, that interview solutions are correct with the stated time and space complexity (and say when a better one exists), that self-item model answers are excellent and their rubrics specific, and the "Current facts" list in BRIEF.md.
