@article
How do you know a function is right? Running it once and looking at the answer proves very little. A **test** states in code what a function must do, so the computer can re-check it every time you change something.

### The assert statement

`assert condition` does nothing when the condition is true. When it is false, Python raises an `AssertionError` and the program stops:

```python
def double(x):
    return x * 2

assert double(4) == 8      # passes silently
assert double(0) == 0      # passes silently
assert double(3) == 7      # raises AssertionError
```

You can add a message that is shown with the failure: `assert double(3) == 6, "doubling 3 gives 6"`. A test file is a list of asserts: if the program ends without an error, every test passed.

### Choosing test cases

One passing test proves almost nothing, because a wrong function can match one example by luck. A good set of tests includes:

- a **typical** case, to show the main idea works;
- **edge cases**: an empty list or string, a single item, zero, negative numbers, values on the boundary of a rule (exactly 50 when the rule is "at least 50");
- **a case a typical wrong solution gets wrong**: if you can imagine the bug, write the test that catches it.

For example, the function `is_leap_year(year)` is often written as `year % 4 == 0`. That passes tests for 2024 (leap) and 2023 (not leap), but the real rule says years divisible by 100 are *not* leap years unless they are also divisible by 400. So `1900` is not a leap year and `2000` is. Those two tests catch the shortcut.

### Test first, or at least test early

Writing tests *before* the function (test-driven development) forces you to say exactly what the function should do, including the awkward cases. Even if you write tests afterwards, write them before you trust the code, and run them after every change so a fix in one place does not quietly break another.

### Floating-point numbers

Computers store most decimals approximately, so `0.1 + 0.2 == 0.3` is `False`. Test decimal results by checking that they are *close*:

```python
assert abs((0.1 + 0.2) - 0.3) < 1e-9
```

`math.isclose(a, b)` does the same job. Whole-number results and exactly representable decimals (like `0.5` or `2.25`) can still use `==`.

### What to test, and what not to

Test **return values**: they are easy to check. A function that only prints is harder to test, which is one more reason to make functions return their results and let a small outer part of the program print them. Also check that a function does not change its input when it should not, by comparing the list with a saved copy afterwards.

@example
title: Tests that expose a bug
problem: A student writes `absolute(n)` as `return n` after testing only `absolute(5)`. Write tests that reveal the bug, and fix the function.
step: The only test the student ran was `assert absolute(5) == 5`. It passes, which is why the bug survived.
step: Think about what is different for the other kinds of input. Negative numbers must change sign and zero must stay zero, so add tests for both.
step: Write the tests:

```python
assert absolute(5) == 5
assert absolute(0) == 0
assert absolute(-7) == 7
```
step: Run them against `return n`. The first two pass, but `absolute(-7)` gives `-7`, so the third raises `AssertionError` and points at the exact case that is wrong.
step: Fix the function, then run all three tests again:

```python
def absolute(n):
    if n < 0:
        return -n
    return n
```

@example
title: Comparing decimals safely
problem: Why does `assert average([0.1, 0.2]) == 0.15` fail, and how do you write the test so it works?
step: The function returns `(0.1 + 0.2) / 2`. Because `0.1 + 0.2` is `0.30000000000000004`, the result is not exactly the stored value of `0.15`.
step: The two numbers differ only in the 17th digit, so ask whether they are close instead of equal.
step: The test becomes:

```python
assert abs(average([0.1, 0.2]) - 0.15) < 1e-9
```
step: The difference is about `3e-17`, far below `1e-9`, so the test passes, and it would still fail for a truly wrong answer such as `0.2`.

@mistakes
- Testing only one easy case, so a wrong function passes by luck.
- Forgetting edge cases such as the empty list, zero and negative numbers.
- Comparing floating-point results with `==` and getting failures that are not real bugs.
- Writing a test whose expected value was copied from the function's output instead of worked out by hand, so the test can never disagree with the bug.

starter:
```python
def is_leap_year(year):
    pass
```
tests:
```python
assert is_leap_year(2024) is True
assert is_leap_year(2023) is False
assert is_leap_year(1900) is False
assert is_leap_year(2000) is True
assert is_leap_year(2100) is False
assert is_leap_year(1600) is True
```
model:
```python
def is_leap_year(year):
    if year % 400 == 0:
        return True
    if year % 100 == 0:
        return False
    return year % 4 == 0
```
hint: Check the most specific rule first: divisible by 400.
hint: Then years divisible by 100 are not leap years, and only after that apply the divisible-by-4 rule.
solution: Test the exceptions from the strongest to the weakest: divisible by 400 is a leap year, otherwise divisible by 100 is not, otherwise the ordinary rule `year % 4 == 0` decides. Equivalent single expression: `year % 4 == 0 and (year % 100 != 0 or year % 400 == 0)`.

@practice code
prompt: Write `all_pass(func, cases)` that tests a function. `cases` is a list of pairs `(argument, expected)`. Return a list of the arguments for which `func(argument)` does not equal `expected`, in the same order as in `cases`. If every case passes, return an empty list.
starter:
```python
def all_pass(func, cases):
    pass
```
tests:
```python
def double(x):
    return x * 2

def buggy_abs(n):
    return n

assert all_pass(double, [(1, 2), (5, 10), (0, 0)]) == []
assert all_pass(double, [(1, 2), (5, 11), (3, 7)]) == [5, 3]
assert all_pass(buggy_abs, [(4, 4), (-2, 2), (0, 0), (-9, 9)]) == [-2, -9]
assert all_pass(double, []) == []
```
model:
```python
def all_pass(func, cases):
    failures = []
    for argument, expected in cases:
        if func(argument) != expected:
            failures.append(argument)
    return failures
```
hint: Build a list of failures, starting empty, and return it after the loop.
hint: Unpack each pair with `for argument, expected in cases:` and compare `func(argument)` with `expected`.
solution: Loop over the pairs, call `func(argument)`, and append the argument to `failures` whenever the result differs from `expected`. Returning the failing arguments, not a count, tells you exactly which inputs to investigate.

@quiz code
prompt: Write `median(nums)` that returns the median of a non-empty list of numbers: the middle value of the sorted list, or the average of the two middle values when the list has an even number of items. The function must not change the list it is given.
starter:
```python
def median(nums):
    pass
```
tests:
```python
assert median([3, 1, 2]) == 2
assert median([4, 1, 3, 2]) == 2.5
assert median([5]) == 5
assert median([-1, -3]) == -2
data = [9, 7, 8]
assert median(data) == 8
assert data == [9, 7, 8]
```
model:
```python
def median(nums):
    ordered = sorted(nums)
    middle = len(ordered) // 2
    if len(ordered) % 2 == 1:
        return ordered[middle]
    return (ordered[middle - 1] + ordered[middle]) / 2
```
hint: Sort a copy first; the median depends on the sorted order.
hint: For an odd length the middle index is `len(ordered) // 2`; for an even length average the items at `middle - 1` and `middle`.
solution: Use `sorted(nums)`, which returns a new list, so the original is untouched (calling `nums.sort()` would reorder the caller's list). Odd length: return the item at index `len // 2`. Even length: return the average of the two middle items.
