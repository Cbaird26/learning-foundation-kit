@article
Running a reanalysis is mostly bookkeeping, and the bookkeeping decides whether anyone, including you in six months, can trust the result. Experienced analysts follow a few habits that look pedantic until the first time they save the day.

### Keep raw data raw

Download the data into a folder you treat as read-only. Never edit, rename or overwrite a raw file; every change happens in a script that reads the raw files and writes new files elsewhere. If you can delete the derived folder and regenerate everything with one command, your pipeline is reproducible; if you cannot, it is not yet. A typical layout has four parts: `data/raw` (untouched), `data/derived` (generated), `code` (numbered scripts, such as `01_load.py`, `02_exclude.py`, `03_estimate.py`) and `results` (tables and figures, also generated). Record the data version, the date of download and the software versions in a file that goes into version control with the code.

### Check as you go

Most errors in analysis are mundane: files read in the wrong order, a column mislabeled, a unit mixed up, a participant counted twice. Cheap checks at each stage catch them.

- After loading: is the number of participants equal to the number in the participant table? Are the trial counts per participant in the expected range? Are values plausible (reaction times in milliseconds rather than seconds, accuracy between 0 and 1)? How many values are missing?
- After exclusions: how many participants and trials remain, and does the count match the plan?
- After computing the estimate: does the sign agree with a plot of the raw condition means? Does one participant drive the result?

Look at the raw values for a few participants by hand. A figure of each participant's data, made before any statistics, is one of the most useful checks.

### The exclusion flow

Report how many participants or trials were removed at each step and why, as a short flow: downloaded, then missing files, then exclusions for each rule, then analyzed. Apply exclusion rules exactly as planned, and use only information that does not depend on the outcome (data quality, motion, trial counts), never "participants who go against the effect". The flow is a table in the paper's methods, and it is the first place a reader looks to see whether your sample matches the original's.

### An estimate needs its uncertainty

For paired differences $x_1, \dots, x_n$ with mean $\bar{x}$ and sample standard deviation $s$ (dividing by $n - 1$), the standard error is $s/\sqrt{n}$, and a 95% interval is $\bar{x} \pm t_{0.975,\,n-1}\, s/\sqrt{n}$, where the critical value of $t$ is slightly above 1.96 for small $n$ (2.365 for 7 degrees of freedom, 2.052 for 27, close to 1.96 for large samples). The standard error is the standard deviation of the sampling distribution of the mean: it shrinks with the square root of $n$, so quadrupling the sample halves it.

When the formula's assumptions are doubtful (skewed data, an unusual statistic such as a median or a decoding accuracy), use a **bootstrap**: resample the participants with replacement, recompute the statistic each time, and take the middle 95% of the results. With 4000 resamples, sort the 4000 values and take the one near rank 100 and the one near rank 3900 as the limits of a percentile interval. Use many resamples (thousands), resample participants and not trials when the participant is the unit of analysis, and fix the random seed so that a second run gives the same interval. Pseudocode:

```text
set seed
for b in 1..B:
    sample = n participants drawn with replacement
    stats[b] = statistic(sample)
sort stats
limits = stats[0.025 * B], stats[0.975 * B]
```

In NumPy, this is a few lines using a random generator's `choice` method, and permutation tests, which shuffle condition labels instead of participants, are written almost identically.

### Write the log as you go

Keep a running analysis log, a plain text file with a dated line for each run: what was run, with which data version, and what came out. When a number changes later, the log tells you why. This habit is also what you will need in week 4, when numbers disagree.

@example
title: An exclusion flow
problem: You download data from 52 participants. Three have no behavioral file, four of the remaining ones are excluded for head motion above the planned threshold, and two of the rest for accuracy below the planned 60%. How many participants are analyzed, and what should the report say?
step: Start with the downloaded participants: 52.
step: Remove the missing files: $52 - 3 = 49$.
step: Remove the motion exclusions: $49 - 4 = 45$.
step: Remove the accuracy exclusions: $45 - 2 = 43$.
step: Report the flow with reasons: "52 downloaded; 3 without behavioral files; 4 excluded for motion; 2 for accuracy below 60%; 43 analyzed". Compare 43 with the original sample size and note any difference.
answer: 43 participants are analyzed, with the flow reported step by step.

@example
title: A mean difference with its interval
problem: Eight participants have paired differences (in ms) of 12, 5, 9, 15, 3, 10, 7 and 11. Compute the mean, the standard error and a 95% interval (the critical value of $t$ for 7 degrees of freedom is 2.365).
step: The mean is $72/8 = 9.0$ ms.
step: The sample standard deviation is $s = \sqrt{\sum (x - 9)^2 / 7} = \sqrt{106/7} \approx 3.89$ ms.
step: The standard error is $3.89/\sqrt{8} \approx 1.38$ ms.
step: The interval is $9.0 \pm 2.365 \times 1.38 = 9.0 \pm 3.25$, so $[5.7, 12.3]$ ms.
answer: Mean 9.0 ms, SE 1.38 ms, 95% interval about $[5.7, 12.3]$ ms.

@mistakes
- Editing a raw file by hand, or saving a derived file over a raw one, so that the pipeline cannot be rerun from scratch.
- Dividing by $n$ instead of $n - 1$ when computing the sample standard deviation for an interval, or using 1.96 where the sample is small.
- Bootstrapping trials as if they were independent when the unit of analysis is the participant.
- Reporting only the final estimate, without the number of participants and trials that went into it.

prompt: The paired differences of 49 participants have a sample standard deviation of 14 ms. What is the standard error of their mean, in milliseconds?
answer: 2
unit: ms
check: 14 / sqrt(49)
hint: Divide the standard deviation by the square root of the number of participants.
solution: $14/\sqrt{49} = 14/7 = 2$ ms. To halve this standard error you would need four times as many participants.

@practice num
prompt: The mean paired difference in 28 participants is 6.4 ms with a sample standard deviation of 11.2 ms. Using the critical value $t = 2.052$ (27 degrees of freedom), what is the lower limit of the 95% interval, in milliseconds? Give your answer to two decimal places.
answer: 2.06
tol: 0.01
unit: ms
check: 6.4 - 2.052 * 11.2 / sqrt(28)
hint: Compute the standard error first, then multiply by the critical value and subtract it from the mean.
solution: The standard error is $11.2/\sqrt{28} \approx 2.117$ ms, the margin is $2.052 \times 2.117 \approx 4.34$ ms, and the lower limit is $6.4 - 4.34 \approx 2.06$ ms. The upper limit is about 10.74 ms.

@practice self
prompt: A student describes their analysis: "I downloaded the files, opened each one in a spreadsheet, deleted rows that looked wrong, saved over the original, ran the statistics in a point-and-click program, and typed the numbers into my draft." List the problems and describe a revised workflow in 120 to 200 words.
hint: Think about what a reader could check, what the student could redo, and what could go wrong silently.
solution: The workflow cannot be audited or repeated. Rows "that looked wrong" were removed by judgment, with no rule and no count, so exclusions might depend on the outcome. Saving over the originals destroyed the raw data, so nobody can check what was deleted, and a mistake cannot be undone. Point-and-click steps leave no record, and typing numbers into the draft invites transcription errors. A better workflow keeps the downloaded files read-only and puts one script after another between them and the results: a loader with checks on counts and ranges, an exclusion step with numerical rules written in the plan and a printed flow, a script that computes the estimate with its standard error or bootstrap interval from a fixed seed, and a script that writes the tables and figures used in the paper so that no number is typed by hand. The software versions and data version are saved in a file, the scripts are under version control, and a short log records each run. A reader or the student can then rerun everything and see what changed.
rubric: Identifies unrecorded judgment-based exclusions and overwriting of raw data as the main problems.
rubric: Names manual transcription and untracked software steps as sources of silent error.
rubric: Describes a scripted pipeline with read-only raw data, rule-based exclusions with counts, and generated results.
rubric: Mentions recording versions and a fixed seed or log so that the run can be repeated.

@quiz num
prompt: You compute a percentile bootstrap interval from 4000 resamples, sorted from smallest to largest. Approximately which rank gives the upper limit of the 95% interval (rank 1 is the smallest value)?
answer: 3900
tol: 1
check: 0.975 * 4000
hint: The upper limit is the 97.5th percentile of the sorted values.
solution: The middle 95% leaves 2.5% in each tail, so the upper limit is near rank $0.975 \times 4000 = 3900$ and the lower limit near rank $0.025 \times 4000 = 100$.

@quiz mc
prompt: Why do analysts fix the random seed when computing a bootstrap interval?
choice*: So that anyone who reruns the script obtains exactly the same interval.
choice: So that the interval becomes narrower and more precise.
choice: So that the bootstrap becomes unbiased for any statistic.
choice: So that fewer resamples are needed to cover the sampling distribution.
hint: The seed controls which random numbers the program draws.
solution: A fixed seed makes the sequence of random draws repeatable, so the result is reproducible. It does not make the interval narrower or unbiased and does not reduce the number of resamples needed.
